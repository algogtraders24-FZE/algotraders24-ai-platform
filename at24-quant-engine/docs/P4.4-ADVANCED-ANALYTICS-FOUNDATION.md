## 1. What changed, by layer

**Engine (`at24-quant-engine/src/domain/metrics.ts`)**: one new, additive, pure function — `computeRiskRatios(trades, equityCurve, coreMetrics)` — returning `RiskRatios`. Deliberately a **separate** function from `computeCoreMetrics`, never merged into it and never called from `simulation-engine.ts`'s own `runSimulation()`: post-hoc analysis over an *already-produced* trade list/equity curve, not a change to what `runSimulation()` itself computes. `computeCoreMetrics` itself is untouched.

**Services (`frontend/services/algo-test/`)**:
- `algo-test-analytics.ts` (new) — Tier 1: `buildPnlDistribution`, `buildSideBreakdown`, `buildDurationVsPnl`, `buildCalendar`. Pure functions over `AlgoTestTradeView[]`, no I/O, no mutation.
- `algo-test.service.ts` — `buildAnalyticsView()` composes Tier 1 + Tier 2 into `AlgoTestAnalyticsView`, called from `runAlgoTest`'s success path, `compileAndRunAiStrategy`'s success path, **and** `getAlgoTestRun`'s reopen path (see §3). `maxRangeDaysFor(timeframe)` replaces the flat `MAX_RANGE_DAYS` constant (see §2).

**Data**: no new provider capability. `maxRangeDaysFor` only covers the 7 timeframes the real historical-data provider already fetches (M1/M5/M15/M30/H1/H4/D1) — `W1`/`MN1` (real `Timeframe` union members with no provider coverage) throw a clear, typed error rather than returning a meaningless number.

**Product/UI (`AlgoTestPanel.tsx`)**: five new sections in `AlgoTestResults` (Risk Ratios, Side Breakdown, P&L Distribution, Duration vs. P&L, Calendar) — every existing section (lifecycle, evidence, compiled strategy, trades, equity curve) is unchanged and still renders exactly as P4.3 shipped it.

## 2. Phase C — the timeframe-aware range policy

The original `MAX_RANGE_DAYS = 14` was M5-only, hardcoded. `maxRangeDaysFor(timeframe)` is derived directly from that same, already-shipped, live-verified value — not a new number invented per timeframe:

```
DAY_BUDGET_BARS = 288 bars/day (M5) × 14 days = 4,032 bars
maxRangeDaysFor(tf) = floor(4,032 / barsPerDay(tf))
```

| Timeframe | Bars/day | Cap (days) |
|---|---|---|
| M1 | 1,440 | 2 |
| M5 | 288 | **14** (unchanged, the original live-verified value) |
| M15 | 96 | 42 |
| M30 | 48 | 84 |
| H1 | 24 | 168 |
| H4 | 6 | 672 |
| D1 | 1 | 4,032 |

**Disclosed honestly**: only M5 (14 days) has ever been live-verified against the real Twelve Data API. The other six are computed via the identical, documented formula but have not been independently re-verified live. The 5,000-bars-per-request ceiling this is derived from is a request-*size* limit, not a historical-*depth* one — D1's own ~4,032-day (~11 year) cap may still exceed what Twelve Data's actual D1 history covers on this plan, a separate, unverified question this formula cannot answer.

**A real sequencing consequence, handled**: the registry path (`runAlgoTest`) knows its real timeframe before validating (from `request.timeframe`). The AI path does not — the natural-language request itself names the timeframe, known only *after* compilation. The range-vs-cap check in `compileAndRunAiStrategy` is therefore deliberately deferred to just after compilation succeeds, reusing `buildDataValidFailureLifecycle` (a real `StrategySpec` existed; there was simply no valid window to run it in) rather than blocking before the LLM call the way the registry path can.

## 3. A genuine architectural improvement over the P4.3 precedent

P4.3 disclosed that `lifecycle`/`compiledStrategy`/`strategyHash` are computed live but never persisted, so a reopened run cannot show them. `analytics` does **not** have this gap: every one of its inputs — `trades`, `equityCurve`, `metrics` — is already a persisted JSON column on `AlgoTestRun`. `getAlgoTestRun()` now recomputes `analytics` on every reopen, for free, with no new persistence and no migration. Proven directly: `validate-algo-test-analytics.ts`'s own reopen test asserts `analytics` is present and byte-identical after reopening, in the same test that confirms `lifecycle`/`compiledStrategy` correctly remain absent (the P4.3 gap is real and unchanged, not silently fixed by this phase).

## 4. Two real bugs the visual QA pass caught

Screenshotting the actual, unmodified `AlgoTestPanel.tsx` (same headless-Chrome technique P4.3 established) against real engine-computed data surfaced:

1. **Max Drawdown was rendered with the wrong unit formatter since P3.2B.** `computeCoreMetrics()`'s own formula comment has always defined `maxDrawdown` as a *percentage* (`100 × (peak − equity) / peak`), never currency — but `AlgoTestPanel.tsx` rendered it through `formatPrice()`. Fixed to `formatPercent()`. Pre-existing, unrelated to this phase's own new code, but directly in scope (Calmar/Recovery Factor both needed the real, correct unit of this field to be implemented correctly at all).
2. **A demo-data-pipeline encoding artifact, diagnosed and ruled out.** An early screenshot showed mojibake (`â€"`) where the compiled-strategy view's real em dash should render. Traced precisely: the actual shipped source has a correct, valid UTF-8 em dash (confirmed via raw byte inspection); the corruption was introduced by this verification pass's own throwaway Python demo-data script reading the file without an explicit UTF-8 encoding on Windows. Not a product bug — confirmed by re-generating the demo data correctly and re-screenshotting clean.

## 6. Known limitations (disclosed, not silently worked around)

- Only M5's 14-day range cap has ever been live-verified against the real Twelve Data API; the other 6 timeframes' caps follow the identical formula but are unverified live (see §2).
- D1's ~11-year theoretical cap is a request-size-derived number, not a historical-depth guarantee — Twelve Data's real D1 coverage on this account's plan is a separate, unchecked question.
- `validate-algo-test-service.ts` (a pre-existing, live-network-only script) was updated to keep compiling against the new `maxRangeDaysFor` API, but — consistent with every prior phase this session — was not executed live (no reachable network in this sandboxed environment).
- MFE/MAE remains explicitly out of scope, per the sprint's own Tier 3 boundary — `SimulationTrade` has no intrabar-excursion capture, and adding one is real, bounded, future engine work.
- No MTF, no new indicator families, no optimization, no change to `runSimulation()`'s own behavior — all explicit non-goals, all honored.
