# Q0.8 MQL Semantics

## `semantic-analyzer.ts` — the ONLY place trading meaning is assigned

Q0.8's central rule restated: the parser (`docs/Q0.8_MQL_AST.md`) builds structure with zero knowledge of what a `CallExpression` named `iMA` or `OrderSend` MEANS. `analyzeMQLSemantics()` walks the already-built `ProgramNode` exactly once, dispatching every `CallExpression`/`BinaryExpression`/`IndexExpression`/`AssignmentExpression` it finds to a battery of pattern-matchers, each populating one array of `MQLSemanticModel` (`domain/mql-importer/semantic-model.ts`). No matcher ever re-parses source text or second-guesses the AST's structure.

## Event handlers and bar/tick mode (Q0.8.8/9)

`MQL5_EVENT_MAP`/`MQL4_EVENT_MAP` recognize `OnInit`/`OnDeinit`/`OnTick`/`OnTimer`/`OnTrade`/`OnTradeTransaction` (MQL5) and `init`/`start`/`deinit` (MQL4) by NAME — never inferring dialect from which one is present without cross-checking (`docs/Q0.8_MQL4_MQL5_PARITY.md`). `OnTick` is classified `BarTickMode: "TICK"`, never silently assumed to mean bar-close (Q0.8.9's explicit rule) — new-bar detection is a SEPARATE, further analysis (below), not folded into the bar/tick classification itself.

## New-bar detection (Q0.8.10) — provable vs. merely plausible

Two genuinely provable patterns are recognized directly from AST shape: `Time[0] != lastTime`/`Time[0] == lastTime` (`TIME_COMPARISON`) and calls to `iTime`/`CopyRates` (`ITIME_CALL`/`COPYRATES_CALL`). A call whose NAME merely looks like a new-bar check (matches `/newbar/i`, e.g. G01's own `G01_IsNewBar`) is recognized as a PLAUSIBLE new-bar guard for downstream heuristics (see the realtime-dependency detector below) but is explicitly marked `provable: false` with an accompanying WARNING diagnostic (`NEW_BAR_UNPROVABLE`) — its actual body lives in an unanalyzed `#include`, so trusting the name alone is a documented, honest assumption, never silently treated as equivalent to the provable patterns.

## Cross detection (Q0.8.16) — ONLY the provable shape

`detectCrossPattern()` matches EXACTLY `A[1] <= B[1] && A[0] > B[0]` (or the inverse for `cross_below`) where the SAME series/indicator pair appears on both sides at the correct literal offsets — never a rewrite of an arbitrary `&&`-joined comparison pair. `test/mql-semantic-analyzer.test.ts` proves a lookalike (`Fast[0]>Slow[0] && Bid>Ask`, same operators but different underlying pairs) is correctly NOT recognized.

## Indicator handle vs. buffer copy (Q0.8.14) — the mandatory distinction

`IndicatorCallSite.role` is one of `HANDLE_CREATION` (MQL5's `int h = iATR(...)`, creating a persistent handle), `DIRECT_READ` (MQL4's `iRSI(...)` called directly as a value, no handle), or `BUFFER_COPY` (MQL5's `CopyBuffer(handle, bufferIndex, shift, count, array)`, reading FROM an existing handle). These are never confused: `CopyBuffer`'s first argument is recorded as `handleVariable` (the variable holding the handle), its second as `bufferIndex` — genuinely distinct from a series-index SHIFT, which is `CopyBuffer`'s THIRD argument. `test/mql-semantic-analyzer.test.ts`'s dedicated test constructs both an `iATR` handle-creation site and a separate `CopyBuffer` read from that same handle, asserting their roles differ.

## State variables (Q0.8.17/18)

Every GLOBAL variable is, by MQL's own scoping rules, cross-bar state (persists across `OnTick`/`start()` calls) — `StateVariableSite` tracks each one's `readPositions`/`writePositions` independently, distinguishing pure computation (a global only ever read) from mutated state. A plain-assignment target (`g_x = 5`) is recorded as a WRITE ONLY — a real bug caught during this sprint's own testing double-counted assignment targets as reads too, fixed before shipping (`test/mql-failure-catalog.test.ts` item 24 pins this behavior). `static` LOCAL variables are a documented gap: none appear in the real G01 fixture, so tracking them was not required for this sprint's validation target; a future sprint extending coverage would add them to the same `StateVariableSite` model, not a parallel one.

## Realtime dependency / repainting (Q0.8.35)

An UNCONDITIONAL call in `OnTick` (a bare top-level statement, not nested in any `if`) to a locally-defined function whose OWN body reads live `SymbolInfoDouble(..., SYMBOL_BID|SYMBOL_ASK)` is flagged — this is exactly how the real G01 fixture's `G01_CheckRetestAndEnter()` (which fires the entry the instant price touches a computed level, independent of the bar-close state machine) is correctly classified `REALTIME_DEPENDENT`, not the too-optimistic `NON_REPAINTING`. This is a single-file, one-hop heuristic (it does not resolve calls into `#include`-defined functions) — documented, not silently assumed complete.

## What Q0.8 does NOT do

No dataflow analysis beyond the read/write tracking above (no constant propagation, no value-range analysis). No cross-file semantic resolution — every call into an `#include` is `UNRESOLVED_CROSS_FILE_CALL`, categorically, regardless of how confident a name-based guess might feel. No indicator formula verification (a recognized `iMA`/`iRSI`/`iATR`/`iMACD`/`iBands` call is trusted to mean what its MQL documentation says; this importer does not re-derive the indicator's math).
