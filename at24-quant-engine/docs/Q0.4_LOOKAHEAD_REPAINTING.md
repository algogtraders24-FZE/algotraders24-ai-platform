# Q0.4 Lookahead / Repainting Detection Model

Q0.4.40. Lookahead and repainting are related but distinct failure modes: **lookahead** is a decision using data unavailable at that moment; **repainting** is a VALUE that changes retroactively when recomputed with more data, whether or not any decision actually used the changed value. A value can repaint without ever causing lookahead (if nothing acted on it before it stabilized); a strategy can suffer lookahead without any single value "repainting" (e.g. reading tomorrow's already-known close in a walk-forward loop bug). Both must be independently detectable.

## Sources of each, catalogued

### Future bars
The most direct lookahead: an evaluation at bar N reads `bars[N+1]` or later. Structurally prevented for AT24's own primitives already — Q0.2's `IndicatorDefinition.next()` is an incremental step function that is only ever given bars up to the current one (it has no way to reach forward), proven empirically by the no-lookahead test; `TimeFrontier.availableBars()` enforces the same at the raw-series level. Any future construct (the Strategy IR's "Timeframe dependencies"/"Symbol dependencies" fields) must preserve this guarantee when it introduces new ways to read data — see MTF/multi-symbol below.

### Future ticks
Same failure, at tick granularity: using a tick that occurs after the current simulated instant. Relevant once a future engine supports `ON_EVERY_TICK`/tick-replay (Q0.4.6/`Q0.4_INTRABAR_ENGINE.md`) — the event queue's `(timestamp, sequence)` total order (`Q0.4_EVENT_MODEL.md`) is what makes "future tick" a well-defined, checkable concept at all; without it, "future" has no fixed meaning.

### HTF leakage
A strategy on a lower timeframe reads a higher-timeframe value (e.g. "the daily close") before that HTF bar has actually closed. This is Q0.4.2's researched `request.security()` lookahead concern — Pine's official `barmerge.lookahead_on` vs `barmerge.lookahead_off` parameter exists precisely because the underlying mechanism can go either way depending on how the call is written, and Pine's own docs treat the unsafe direction as a documented footgun, not a rare misuse. AT24's design commitment (elaborated in `Q0.4_EVENT_MODEL.md`'s MTF section, Q0.4.27): an HTF observation becomes available to a lower-timeframe evaluation only at the instant the HTF bar CLOSES, never before, with no equivalent of an opt-in "unsafe" mode — if a future sprint decides AT24 needs one (e.g. to intentionally study the effect), it must be as explicitly and unmissably labeled as Backtrader's `cheat_on_open`/`cheat_on_close` (researched in `Q0.4_PLATFORM_R&D.md`), never a silent default.

### MTF leakage
Generalizes HTF leakage to any cross-timeframe read, not just "higher" ones (e.g. a weekly-chart strategy occasionally sampling an intraday value for a filter) — same availability rule applies symmetrically: a timeframe's observation is available only once ITS OWN bar has closed, regardless of which direction the read points.

### Repainting
Per Q0.4.2's Pine research, the documented causes generalize beyond Pine specifically:
- **Indicator values recalculated retroactively** as more data arrives (a value plotted at bar N during realtime that later shifts once bar N+1's data confirms it) — any AT24 indicator that is NOT a pure step function of bars-up-to-and-including-the-current-one is a repainting risk by definition; Q0.2's `IndicatorDefinition` contract structurally forecloses this for the 6 shipped indicators, and any future indicator must meet the same bar.
- **Reading the still-forming current bar's close as if final** — using "close" mid-bar and later having that same variable name refer to a different, now-final value once the bar completes. AT24's `MarketState.asOf` + `bars` (Q0/Q0.2) always represents a specific, named point in time; there is no "the current, still-changing bar" concept smuggled in under the same field name.
- **Revised historical data** — a data vendor correcting/backfilling historical prices after the fact (a real, documented occurrence, distinct from a strategy bug) — this is a DATA PROVENANCE problem, not a strategy-logic problem, and must be addressed by `DatasetVersion`/`DatasetId` (Q0.2's `ResearchExperiment`, `Q0.4_BACKTEST_ARCHITECTURE.md`'s Provenance section) recording exactly which version of a dataset a result used, so a later data revision produces a NEW dataset version and a NEW, distinguishable result rather than silently altering history under a fixed identifier.
- **Synthetic chart leakage** — computing on a synthetic series (Renko/Heikin Ashi/etc.) whose "current bar" isn't well-defined until arbitrary future price action decides where the brick/bar boundary falls — covered fully in `Q0.4_INTRABAR_ENGINE.md`'s Synthetic Data Detection; the `REAL_MARKET_PRICE`/`SYNTHETIC_PRICE` classification exists specifically to make this checkable.
- **Unavailable quote access** — using a bid/ask or a specific price point that would not actually have been quotable/visible to a live trader at that instant (distinct from "future" in the strict time sense — the value exists at time T but was never actually observable, e.g. a same-instant cross-venue price a real trader's feed didn't carry). Reserved as a `DataFidelity` (`Q0.4_INTRABAR_ENGINE.md`) concern — a result's stated fidelity level implicitly bounds what was actually "visible."

## Detection strategy for AT24 (design intent, not implemented in Q0.4)

Three complementary approaches, in increasing order of rigor:

1. **Structural prevention** (cheapest, already partially shipped): design primitives so the failure is impossible by construction, not merely checked for. Q0.2's incremental-indicator-step-function pattern and `TimeFrontier` are exactly this. Extending this to MTF/multi-symbol reads (a future sprint) is the highest-leverage next step, since it closes the largest remaining structural gap.
2. **Differential replay testing** (the pattern Q0.2's own no-lookahead test already establishes): run the same evaluation twice — once against data truncated at time T, once against the full series — and assert the result at T is byte-identical. This is directly reusable, generalized, for any future MTF/multi-symbol/tick-level construct exactly as it already is for indicators.
3. **Provenance-based post-hoc audit**: every `BacktestResult`/`ResearchResult` records enough (`DataFidelity`, `DatasetVersion`, `ExecutionModel`, per `Q0.4_BACKTEST_ARCHITECTURE.md`'s Provenance block) that a suspicious result (implausibly high performance, suspiciously perfect entries) can be re-examined for HOW it was produced, even after the fact — this is the safety net for failure modes too subtle or too strategy-specific for (1)/(2) to catch automatically.

## What Q0.4 does NOT do

No lookahead/repainting DETECTOR is implemented — this document defines what must be detectable and the design principles a future detector/test-generalization sprint is measured against, extending patterns Q0.2 already proved out for the single-timeframe, single-symbol case.
