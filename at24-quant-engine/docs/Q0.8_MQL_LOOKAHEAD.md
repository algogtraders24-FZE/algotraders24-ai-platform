# Q0.8 MQL Lookahead Protection

## Future shifts are rejected at the semantic layer, not silently clamped (Q0.8.12/34)

`detectSeriesIndex()` (`semantic-analyzer.ts`) rejects any `Series[-N]`-shaped index — `UnaryExpression` with operator `"-"` wrapping the offset — with a BLOCKING `FUTURE_SHIFT_REJECTED` diagnostic, and separately flags any NON-literal offset (a variable, e.g. `Close[n]`) as a WARNING (`NON_LITERAL_SHIFT`, unprovable, never assumed safe). This is the MQL-source-text-level enforcement of the SAME rule Q0.7.9 already established at the IR level (`domain/strategy-ir/series.ts`'s `validateSeriesOffset`) — two independent, redundant checks at two different layers, never just one.

## MTF/HTF availability (Q0.8.32) — reuses Q0.7's canonical rule, does not reinvent it

`generateStrategyIR()` builds `timeframeSeries` from every timeframe actually referenced (both `symbolTimeframeSites` — generic calls carrying a `PERIOD_*` argument — AND `seriesReferences` — `iClose`/`CopyClose`/etc., which resolve to a series read before the generic detector ever runs; missing either would silently under-report real MTF usage, a real bug this sprint's own failure-catalog testing caught: item 25 originally failed because only `symbolTimeframeSites` was scanned). Every non-execution timeframe is assigned `role: HIGHER` or `role: LOWER` (via Q0.6's own `timeframeDurationMs()`, reused not reimplemented) and `availabilityPolicy: "HTF_CLOSE_AVAILABLE"` — the ONLY value Q0.7's validator (`docs/Q0.7_MTF_SEMANTICS.md`) ever treats as safe.

**The critical gate**: if additional timeframes are referenced but the semantic model recorded NO new-bar detection site anywhere (not even an unprovable, name-based one), the import records a BLOCKING `UnsupportedSemantic` ("multi-timeframe HTF availability... cannot be certified safe without a provable new-bar boundary") — `test/mql-failure-catalog.test.ts` item 25 proves this concretely with a bare `iClose(_Symbol,PERIOD_H4,1)` call and no gating whatsoever. When a plausible (even if unverified) new-bar gate DOES exist — G01's real case, gated by the cross-file `G01_IsNewBar` — the import instead records a WARNING, honestly noting the trust is placed in a naming convention, not independently proven.

## Q0.7's own IR validator runs unmodified on every MQL-imported IR

`validateStrategyIR()` (Q0.7, `runtime/strategy-ir/ir-validator.ts`) is never touched by Q0.8 — every MQL-imported `StrategyIR` passes through the EXACT SAME `checkHTFLookahead()`/`checkRepainting()`/`checkUnsupportedSemantics()` gates a hand-built or AI-compiled IR does. This is why the real G01 import correctly reports `executionEligible: false` — the same validator that would reject a hand-authored strategy with unresolved repainting semantics rejects an imported one for the identical, principled reason.

## Repainting classification is never claimed from mere compilability

Q0.8.35's explicit rule ("Do not claim 'non-repainting' merely because the source compiles") is enforced structurally: `repaintingModel` defaults to `NON_REPAINTING` ONLY when a new-bar detection site exists AND no realtime-dependency signal was found; a strategy with neither signal (no provable or plausible new-bar gate at all) defaults to `UNKNOWN` — never `NON_REPAINTING` by omission. `test/mql-failure-catalog.test.ts` item 16 proves a strategy whose only signal comes from an unresolvable `iCustom` call is never independently certified `NON_REPAINTING`.

## What Q0.8 does NOT do

No differential-replay lookahead detector for MQL constructs (that would require actually EXECUTING the imported IR twice, truncated vs. full — not possible while the entry/exit state machine remains unrepresentable, per `docs/Q0.7_TRANSLATION_CONTRACT.md`'s still-unbuilt IR→StrategySpec reducer). No cross-file resolution of a plausible-but-unverified new-bar check's actual body — the WARNING stays a WARNING permanently until a future sprint expands the importer to read `#include` files.
