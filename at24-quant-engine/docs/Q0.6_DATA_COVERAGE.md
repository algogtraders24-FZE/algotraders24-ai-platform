# Q0.6 Data Coverage

## DetailCoverage (Q0.6.11/12)

```ts
interface DetailCoverage {
  totalParents; completeParents; partialParents; missingParents;
  completeRatio: number; // completeParents / totalParents, 1 when totalParents === 0
}
```

Aggregated across EVERY parent bar the multi-fidelity engine processed in one run, not a single-bar snapshot — so a consumer can judge whether a D2/D3 result is trustworthy end-to-end or leaned on partial/missing data for a meaningful fraction of the run. Populated once, at the end of `runFidelityAwareSimulation()`, into `MultiFidelityProvenance.detailCoverage` — reproducible from the provenance alone, matching Q0.5's "every result reproducible from its provenance" guarantee (`docs/Q0.5_PROVENANCE.md`).

## FidelityQuality (Q0.6.36/37)

```ts
interface FidelityQuality {
  requestedFidelity: SimulationFidelity;
  detailCoverage: DetailCoverage;
  ambiguousResolutionCount: number;             // still-ambiguous SL/TP even at the finest available child bar
  parentsResolvedAtParentGranularity: number;   // parents that fell back to D1-equivalent resolution (missingDetailPolicy: FALLBACK_TO_D1)
}
```

This is the explicit, machine-readable split between "how much detail data did we actually have" and "how realistic is the execution model" (`docs/Q0.6_D2_D3_EXECUTION.md`'s Execution Reality vs Data Detail section) — `FidelityQuality` says NOTHING about spread/slippage/fee/latency realism, only about how much OHLC-level ambiguity the run's own detail coverage let it resolve. A `D2_LOWER_TIMEFRAME` run with `completeRatio: 1.0` and `ambiguousResolutionCount: 0` had every parent bar's ambiguity structurally resolved by real child data; a run with a high `parentsResolvedAtParentGranularity` leaned on the D1 fallback for a meaningful fraction of its bars and should be read with that caveat.

## Data integrity validation (Q0.6.39) and synthetic-data protection (Q0.6.38)

Reused, not reinvented: `runtime/fidelity/bar-magnifier.ts` calls Q0.2's own `validateMarketSeries()` (`domain/market-series.ts`) over every raw child-bar array before trusting it — the same OHLC-validity/chronological-order/duplicate-timestamp checks Q0.2 already proved correct, applied now to lower-timeframe data. No function anywhere in `runtime/fidelity/` ever fabricates, interpolates, or synthesizes a bar that was not already present in a `BarDetailProvider`'s own data — `reconstructIntrabarSequence()`'s only source of truth is `detailResult.bars`, copied field-for-field into `IntrabarObservation`s (`test/fidelity-bar-magnifier.test.ts`, `test/fidelity-failure-catalog.test.ts` items 4 and 14).

## Missing data policy (Q0.6.40)

See `docs/Q0.6_D2_D3_EXECUTION.md`'s "Missing/partial detail data" section — the default is always to FAIL LOUDLY (`INSUFFICIENT_DETAIL_DATA`), never to silently substitute parent-bar resolution; `FALLBACK_TO_D1` must be explicitly requested and is always tracked in `FidelityQuality`.

## What Q0.6 does NOT do

No per-parent-bar coverage HISTORY (only the run-wide aggregate is recorded — a future sprint wanting a bar-by-bar coverage timeline would need to extend `DetailCoverage`, additively). No coverage-based auto-tuning (the engine never silently switches fidelity or missingDetailPolicy mid-run based on observed coverage).
