# Q0.6 Bar Magnifier

## BarDetailProvider (Q0.6.2)

```ts
interface BarDetailProvider {
  providerId: string;
  getDetail(query: BarDetailQuery): BarDetailResult; // { parent: ParentBarIdentity, childTimeframe }
}
type BarDetailResult =
  | { status: "COMPLETE"; bars: readonly OHLCVBar[] }
  | { status: "PARTIAL"; bars: readonly OHLCVBar[]; reason: string }
  | { status: "MISSING"; bars: readonly []; reason: string };
```

The seam between "the engine needs lower-timeframe detail for this parent bar" and "wherever that detail actually lives" (Q0.6.48 — not coupled to any specific platform/broker/provider). `createStaticBarDetailProvider(childBars, childTimeframe)` (`runtime/fidelity/static-bar-detail-provider.ts`) is the in-memory reference implementation exercised by every Q0.6 test; a future sprint wiring a real data source implements the SAME interface, never a parallel one.

## Parent bar identity (Q0.6.3)

```ts
interface ParentBarIdentity { symbol; timeframe; openTimestamp; closeTimestamp; }
```

Derived from the parent `OHLCVBar`'s own timestamp via the established close-instant convention (`TimeFrontier`, Q0.2): `closeTimestamp = bar.timestamp`, `openTimestamp = bar.timestamp - timeframeDurationMs(bar.timeframe)`. A child bar belongs to a parent iff `parent.openTimestamp < child.timestamp <= parent.closeTimestamp` — half-open-left, closed-right, so the LAST child's close always equals the parent's own close.

## Timeframe compatibility (Q0.6.4/5)

`isValidChildTimeframe(parent, child)` (`runtime/fidelity/timeframe-duration.ts`) is a DETERMINISTIC RULE, not a hardcoded whitelist: `child` is valid iff it is strictly shorter than `parent` AND `parent`'s duration is an exact integer multiple of `child`'s (`H1`→`M15` = 4x, `H4`→`M1` = 240x, etc.) — every parent window then aligns cleanly on a child-bar boundary with no fractional/overlapping children possible. `MN1` (calendar month, no fixed millisecond length) is deliberately excluded and cannot participate in a parent/child relationship — a documented limitation, not an oversight.

## The Magnifier itself (Q0.6.6/7)

`reconstructIntrabarSequence(parent, instrument, childTimeframe, detailResult)` (`runtime/fidelity/bar-magnifier.ts`) turns a `BarDetailResult` into an ordered `IntrabarSequence`. It:

1. **Never creates a bar that was not already in `detailResult.bars`** — no interpolation, no synthesis, ever (Q0.6.38). A `MISSING` result produces zero observations; the caller decides whether that is fatal.
2. **Revalidates the raw child bars via Q0.2's own `validateMarketSeries`** (not a new validator) before trusting them — a structurally invalid child bar (`high < low`, OHLC outside range, duplicate timestamps) throws rather than silently producing a bogus fill/exit price (Q0.6.39).
3. **Preserves ambiguity it cannot resolve** — if a single child bar's own OHLC still has both a stop-loss and take-profit reachable, the resolution functions (`docs/Q0.6_D2_D3_EXECUTION.md`) report `ambiguous: true` exactly as Q0.5's `resolveProtectiveExit` already does, at the finer granularity — D2/D3 never fabricate certainty the data does not support.

`observationToBar(obs, instrument, timeframe)` adapts one reconstructed `IntrabarObservation` back into a plain `OHLCVBar` shape so Q0.5's own `resolveMarketFill`/`resolveLimitFill`/`resolveStopFill`/`resolveStopLimitFill`/`resolveProtectiveExit` can be called on it VERBATIM, unmodified — see `docs/Q0.6_D2_D3_EXECUTION.md` for how the fill/exit resolution layer reuses these functions.
