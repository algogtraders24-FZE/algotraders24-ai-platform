# P4.7 — Run History UI

## Tier 1 — Run History Contract + Data Wiring

**Status:** Implemented, tested (4 new focused contract tests), full algo-test-relevant regression green (74/74 across 8 offline validate scripts), full-tree `tsc`/ESLint clean, engine suite unaffected (1240/1240, zero engine files touched). Bounded to the locked Tier 1 scope: `AlgoTestRunView`, `listAlgoTestRuns()`, and a new `fetchAlgoTestRuns()` client wrapper only. No UI, no new persistence, no API route changes, no filtering/sorting/pagination.

## 0. Why this phase, in this position

Preceded by a dedicated investigation (P4.7 audit), whose headline finding reframed the whole phase: **the Run History backend already exists.** `GET /api/private/algo-test/runs` and `algoTestService.listAlgoTestRuns()` were both real, already returning 50 of a user's most recent runs with real identity (`strategyHash`, P4.5), real performance data (the full `metrics` object), and real timestamps — but had exactly zero consumers anywhere in the codebase, not even a client-side fetch wrapper. What was missing was never a persistence layer; it was a consumer plus one small, honest wire-contract gap.

## 1. What changed

**`frontend/types/algo-test.ts`** — one new optional field on the shared `AlgoTestRunView`: `completedAt?: string`. Deliberately `string`, never `string | null` — mirrors the exact optionality convention every other timestamp-adjacent field on this interface already uses (`strategyVersion?`, `resultVersion?`, etc.), not a new pattern.

**`frontend/services/algo-test/algo-test.service.ts`** — `listAlgoTestRuns()` gained one line: `completedAt: row.completedAt?.toISOString() ?? undefined`. The underlying Prisma column (`completedAt DateTime?`) has been written at every completion/failure call site since P3.2B — this exposes an already-persisted value on the wire contract for the first time; it does not create a new write, a new column, or a new migration.

**`frontend/lib/algo-test/store.ts`** — one new function, `fetchAlgoTestRuns()`, modeled directly on the existing `fetchAlgoTestStrategies()` — same never-throws-returns-`[]`-on-failure convention, same thin-wrapper shape. This is the **first client-side consumer** the already-real list endpoint has ever had.

**API route (`GET /api/private/algo-test/runs`)**: unchanged. Re-inspected directly as part of this phase's own hard gate — confirmed a clean passthrough (`ApiResponse.success({ runs }, ...)`), no query-parameter handling, no intermediate schema. No gap found; no change made.

**Persistence**: unchanged. No Prisma migration — `completedAt` has been a real column since the `AlgoTestRun` model's own original migration; this phase only starts reading it back.

## 2. A related, disclosed observation — not fixed in this phase

`getAlgoTestRun()` (the single-run reopen path) does **not** set `completedAt` on the `AlgoTestRunView` it returns, even though the type now allows it. This is harmless (an honestly-absent `undefined`, never a wrong value) but creates a real asymmetry: a Run History row will show a completion time that the same run's own detail page, opened via reopen, currently does not. This was **not** on Tier 1's own locked touch-point list (`AlgoTestRunView`, `listAlgoTestRuns()`, the GET route, `store.ts`, the validator, this doc) — per the locked instruction to report rather than silently expand scope, it is disclosed here as a candidate for Tier 2 or a small follow-up, not fixed in Tier 1.

## 3. Tests (`frontend/scripts/validate-algo-test-run-history-contract.ts`, 4 tests)

All run through the real, unmodified `algoTestService.listAlgoTestRuns()` (and one real `compileAndRunAiStrategy()` call to produce a genuine completed run) — never a hand-built fixture:
1. A real completed run's `completedAt` survives into the list as a genuine, parseable ISO timestamp.
2. A manually-inserted row with no `completedAt` (simulating a pending/never-terminal run) has the `completedAt` **key itself** absent after a JSON round-trip (the real HTTP/JSONB serialization boundary) — never `null`, never a fabricated value.
3. The list view still excludes every heavy field (`trades`/`equityCurve`/`lifecycle`/`compiledStrategy`/`analytics`/`assumptions`/`candles`) — a negative assertion, proving this phase did not accidentally widen the list's own existing size/cost tradeoff.
4. `take: 50` and `orderBy: { createdAt: "desc" }` are unchanged — read directly from source rather than inferred behaviorally, since constructing 50+ real rows to prove a constant nobody touched would be wasteful.

## Tier 2 — Run History UI

**Status:** Implemented, verified against real UI evidence for all 7 gate items, full algo-test-relevant regression green, full-tree `tsc`/ESLint clean, engine suite unaffected (1240/1240, zero engine files touched). Bounded to the locked Tier 2 scope: a new `/dashboard/algo-test-history` page, a nested nav entry, and nothing else.

### 1. What changed

**`frontend/app/dashboard/algo-test-history/page.tsx`** (new) — a client component rendering the real `fetchAlgoTestRuns()` (Tier 1) result as a card-per-run list, reusing the exact list-page shape `app/dashboard/licenses/page.tsx` already established (`EmptyState` + `Badge` + card-row `Link`), not a new UI pattern. Auth is inherited automatically from `app/dashboard/layout.tsx`'s server-side `requireUser()` gate — no separate check needed. Each card shows:
- A label: `parameters?.intent` when present (AI-compiled runs, whose `strategyId` is always the constant `"ai-generated"` and so is useless as a title), else `strategyId` (registry runs) — a better use of an already-in-contract field, not a new one.
- Status badge (`completed` = success tone, `failed` = danger tone, any other real-but-unexpected value = neutral tone, defensively — `AlgoTestStatus`'s own union is only `"completed" | "failed"`, but the DB column is a plain string and an orphaned/never-terminal row is a real, if rare, possibility per the T2 audit).
- Symbol / timeframe / date range.
- For a completed run: net P&L (`formatPrice`, signed color), win rate (`formatPercent`, matching `AlgoTestPanel.tsx`'s own real-data scale — the engine's `winRate` is 0-100, not a 0-1 fraction), trade count.
- For a failed run: `errorMessage`, or an honest fallback string if absent.
- For any other status (the orphaned/pending case): an honest "never reached a completed or failed state" message, no fabricated metrics.
- Created timestamp always; completed timestamp only when `completedAt` is actually present — otherwise "Not completed", never a fabricated value.
- The whole card is a `<Link href="/dashboard/workspace?algoTestId=<testId>">` — the exact, pre-existing `REOPEN_QUERY_PARAM` mechanism `AlgoTestPanel.tsx` already reads; no second reopen code path introduced.

Zero runs renders the same `EmptyState` primitive every other dashboard list page uses, with a `ButtonLink` back to `/dashboard/workspace`.

**`frontend/config/dashboard.config.ts`** — the existing "Algo Testing Pro" nav entry gained one nested child, `{ label: "Run History", href: "/dashboard/algo-test-history" }`, via the file's own pre-existing `children` convention (the same nesting "Quant" and "AI Assistant" already use). The parent entry's own `label`/`href`/`icon` are byte-for-byte unchanged.

**Nothing else changed.** `getAlgoTestRun()` was **not** touched — the Tier 1 audit's disclosed `completedAt` asymmetry (§2) was re-examined by Tier 2's own investigation and confirmed still unnecessary: the detail/reopen surface (`AlgoTestPanel.tsx` → `RunIdentityCard`) shows Run ID / Strategy Hash / Result Hash / Evidence Status, never a timestamp of any kind, so there is no consumer for `completedAt` on that path today.

### 2. Real UI verification

Verified with a temporary preview harness (`app/p47t2-preview/page.tsx`, deleted after capture — same disposable-harness technique used since P4.3): a client route mounting the real `AlgoTestHistoryPage` component with `window.fetch` intercepted only at the `/api/private/algo-test/runs` boundary, redirecting to local fixture JSON under `public/_p47t2-preview/` (also deleted after capture). Two fixtures, both against the real, unmodified page and nav code:

- **`mixed`** (4 rows): a completed registry run (`golden`, positive P&L, green), a completed AI-compiled run (label correctly shows the real `parameters.intent` string, not `"ai-generated"`; negative P&L, red), a failed AI-compiled run (danger badge, real error message shown), and an orphaned/pending run (`status: "pending"`, neutral badge, honest "never reached a completed or failed state" message, `completedAt` absent → "Not completed" shown, exactly as coded).
- **`empty`** (0 rows): the `EmptyState` primitive renders correctly with its "Go to Algo Testing Pro" `ButtonLink`.

Confirmed via `read_page` (not just visually) that all 4 mixed-fixture rows' `<Link>` hrefs are exactly `/dashboard/workspace?algoTestId=<testId>` — the real reopen mechanism, not a guess. Confirmed visually that no row renders any trade, equity-curve, or analytics payload — only the summary fields the locked scope allows.

One real bug was caught and fixed during this verification, in the **fixture data, not the page code**: the first draft of the `mixed` fixture used a 0-1 fraction for `winRate` (e.g. `0.58`), which rendered as `"0.58%"`. Checking `metrics.d.ts`'s own doc comment (`winRate = 100 * count(pnl>0)/tradeCount`) and `AlgoTestPanel.tsx`'s own already-proven `formatPercent(metrics.winRate, ...)` call confirmed the page's formatting call is correct and matches the established real-data convention exactly — the fixture was wrong, not the page. Corrected to a 0-100 value (`58`) before capturing the screenshots above.
