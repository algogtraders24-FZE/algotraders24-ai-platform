# Q1.5.2 — MQL5 `OrderGetInteger(ORDER_TYPE)` Semantics

## The gap (Q0.13/Q1.3/Q1.4-documented, closed here)

`resolveOrderTypeFilter()`'s `isTypeQuery()` helper (`semantic-analyzer.ts`) recognized only `OrderType()` (MQL4) and `PositionGetInteger(POSITION_TYPE)` — never MQL5's own idiomatic `OrderGetInteger(ORDER_TYPE)` read of a selected PENDING order's type. A real MQL5 EA using `if(OrderGetInteger(ORDER_TYPE)==ORDER_TYPE_BUY_STOP)` resolved to `UNKNOWN`, excluded from execution (`executableRules()`).

## The fix — two parts, landed together

Fixing recognition alone would have been actively wrong: even with `isTypeQuery()` recognizing the call, the resolved constant (e.g. `"ORDER_TYPE_BUY_STOP"`) still has to be looked up in `MQL_ORDER_TYPE_CONSTANT_MAP` (`pending-order-management-policy.ts`) by both the IR compiler (`ir-generator.ts`) and the runtime evaluator (`pending-order-management.ts`). Before this sprint that map held only MQL4's `OP_*` keys. Recognizing the call without extending the map would have produced a rule marked `provable`/`EXACT` in the IR — passing `executableRules()`'s gate — that then **silently never fires at runtime** (map-lookup miss → `conditionHolds()` always `false`). That is a worse, more deceptive bug than the honest pre-Q1.5 `UNKNOWN`. Both changes ship together:

1. **`isTypeQuery()`** (`semantic-analyzer.ts`): added `calleeName(e.callee) === "OrderGetInteger" && e.args.some((a) => argText(a) === "ORDER_TYPE")`. **Exact match**, never `.includes()` — MQL5 has genuinely distinct sibling properties `ORDER_TYPE_FILLING` and `ORDER_TYPE_TIME` that must never be misclassified as an order-type filter merely because their name contains the substring `"ORDER_TYPE"`.
2. **`MQL_ORDER_TYPE_CONSTANT_MAP`** (`pending-order-management-policy.ts`): added the four MQL5 pending-order constants, mapped exactly like their MQL4 equivalents:

| MQL5 constant | orderType | side | MQL4 equivalent |
|---|---|---|---|
| `ORDER_TYPE_BUY_LIMIT` | LIMIT | BUY | `OP_BUYLIMIT` |
| `ORDER_TYPE_SELL_LIMIT` | LIMIT | SELL | `OP_SELLLIMIT` |
| `ORDER_TYPE_BUY_STOP` | STOP | BUY | `OP_BUYSTOP` |
| `ORDER_TYPE_SELL_STOP` | STOP | SELL | `OP_SELLSTOP` |

## Explicitly out of scope

`ORDER_TYPE_BUY_STOP_LIMIT` / `ORDER_TYPE_SELL_STOP_LIMIT` (compound stop-limit pending types) are **deliberately not mapped**. The shared value type (`{orderType: "LIMIT" | "STOP", side: "BUY" | "SELL"}`) has no `"STOP_LIMIT"` case — mirroring MQL4's own `OP_BUY`/`OP_SELL` (market orders) also being absent from this map. Adding a third `orderType` value would touch `ir-generator.ts`'s `MODIFY_STOP`/`MODIFY_LIMIT` dual-branch compilation logic and widen scope well beyond this sprint. A source using these constants resolves the structural `ORDER_TYPE_FILTER` shape (the call itself is recognized), but the constant is absent from the map — `toOperationIR`'s `MODIFY_STOP`/`MODIFY_LIMIT` compilation falls to `UNKNOWN` (never fabricated), and `conditionHolds()` at runtime never matches any real order (`MQL_ORDER_TYPE_CONSTANT_MAP[c.orderTypeConstant]` is `undefined` → fails closed). **EXPLICITLY UNSUPPORTED, INVALID** to treat as executable.

## Evidence

`test/q15-order-type-semantics.test.ts` (43 tests): recognition for all 4 supported constants, EXACT-fidelity compilation, runtime firing (`evaluatePendingOrderManagementPolicy`) against real `SimulationOrder`s (side/type match required), STOP_LIMIT constants confirmed absent from the map, `ORDER_TYPE_FILLING`/`ORDER_TYPE_TIME` confirmed never misclassified, `OrderType()`/`PositionGetInteger(POSITION_TYPE)` regression-unaffected. `test/q14-end-to-end-pipeline.test.ts`'s `mql5-17` corpus test updated from "documented gap, UNKNOWN" to "recognized, EXACT."
