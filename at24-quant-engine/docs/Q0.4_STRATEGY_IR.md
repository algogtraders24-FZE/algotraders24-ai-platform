# Q0.4 Strategy Intermediate Representation (IR)

Q0.4.4: an Intermediate Representation between external strategy languages (MQL4, MQL5, Pine, NinjaScript, cBot, or an AI generator) and AT24's canonical `StrategySpec` (Q0). **No parser is built in Q0.4** — this document defines the target shape a future translator would produce, and what `StrategySpec` cannot yet represent that the IR must still be able to hold.

## Why an IR layer, not direct-to-StrategySpec translation

`StrategySpec` (Q0) is deliberately narrow: `Expression` trees of comparisons/AND/OR/NOT/cross operators, `EntryRule`/`ExitRule`, `RiskSpecification`, `ExecutionSpecification`. It has no concept of a mutable local variable, a loop, a custom function, or platform-specific state (e.g. Pine's `var`-persisted variables, MQL's global variables, NinjaScript's `OnBarUpdate` locals). Real strategies in every researched platform (Q0.4.1) use these constructs freely. Translating straight from, say, Pine source to `StrategySpec` would force a parser to solve full program analysis (constant-folding, symbolic execution, loop unrolling) in one step, with no intermediate checkpoint to inspect or test. The IR exists to absorb that complexity into a separate, inspectable stage: **Source → IR is program-structure translation (mechanical); IR → StrategySpec is semantic reduction (where limits are hit and must be reported explicitly, not silently dropped).**

```
MQL4 / MQL5 / Pine / NinjaScript / cBot / AI
                    |
                    v
              Strategy IR          <- this document
                    |
                    v
             StrategySpec           <- Q0's canonical, deterministic, minimal contract
```

## Required IR concepts (Q0.4.4's list, with AT24-specific notes)

| Concept | What it must hold | Note |
|---|---|---|
| **Variables** | name, declared type (number/bool/string/series), scope (global/per-bar/persistent-across-bars) | Distinguishes a Pine `var x = 0` (persists) from a plain `x = 0` (resets every bar) — this distinction has no equivalent in `StrategySpec` at all today; the IR must carry it even though a future reducer may have to reject or approximate it. |
| **Parameters** | name, type, default, min/max, step — the "inputs" a strategy exposes for optimization | Maps reasonably cleanly to `StrategyParameterDefinition` (Q0) already. |
| **State** | any value that depends on strategy history beyond the current bar (a running counter, a flag set on a prior signal, a manually-tracked "bars since X") | `StrategySpec` has no state concept — `Expression` evaluation is a pure function of one `MarketState`. IR-held state is exactly the category of thing a future reducer must either (a) prove is expressible as a derived indicator/cross-operator, or (b) flag `INCOMPATIBLE / REQUIRES DESIGN` (same discipline as Q0.1's migration policy). |
| **Indicators** | name, parameters, source series (which price/other-indicator it reads) | Maps to `IndicatorReference` (Q0.2) directly for known indicator families; an unrecognized/custom indicator formula is IR-only until a matching `IndicatorDefinition` exists. |
| **Expressions** | arithmetic and boolean expression trees, not just comparisons | `StrategySpec`'s `Expression` supports boolean logic and comparisons only, not arithmetic (no `+`/`-`/`*`/`/` node). The IR must hold full arithmetic so a reducer can attempt to fold it into indicator parameters or reject it as unsupported, rather than the IR itself being unable to represent the source in the first place. |
| **Conditions** | boolean expressions gating entries/exits — the eventual target of `EntryRule.condition`/`ExitRule.condition` | Closest 1:1 mapping to existing `Expression`. |
| **Events** | what triggers evaluation — bar close, every tick, order fill, custom timer (see Calculation Timing, Q0.4.6) | No equivalent in `StrategySpec` today (Q0's `generateSignal()` implicitly assumes "evaluate once, given a `MarketState`"); the IR must record the source platform's actual timing semantics so a reducer can flag a mismatch rather than silently assuming bar-close semantics for a tick-driven original. |
| **Entries** | direction, size, order type, price (for non-market orders) | Maps to `EntryRule` + order-type concepts from the Order Model (Q0.4.9) — `EntryRule` currently only implies a market order at signal time; the IR needs to hold pending-order intent so a reducer can decide whether AT24's model can represent it. |
| **Exits** | condition-based exits, and/or SL/TP-attached exits | Splits between `ExitRule` (condition-based) and `RiskSpecification.stopLoss`/`.takeProfit` (price-based) — the IR must record which kind the source used, since Pine/MQL often mix both in ways that don't cleanly separate. |
| **Orders** | pending order management (place, modify, cancel) beyond simple entry/exit | No `StrategySpec` equivalent — `OrderIntent` (Q0) is a runtime output, not something a strategy author directly manipulates. Source platforms (MQL's `OrderSend`/`OrderModify`, Pine's `strategy.order`) DO give the author this control. IR holds it; reduction to `StrategySpec` may need to approximate "author places a limit order 10 pips below close" as a derived `EntryRule` with an implicit price offset — flagged for design, not solved in Q0.4. |
| **Position management** | pyramiding count, scale-in/out rules, hedging vs netting assumption | Partially covered by Q0.3's `RiskSpecification` (`maxSimultaneousPositions`, `partialClose`) — pyramiding (multiple same-direction entries accumulating one net position) has no `StrategySpec` equivalent yet. |
| **Risk** | SL/TP, position sizing, breakeven/trailing — the source platform's native risk expression | Maps to `RiskSpecification` (Q0.2/Q0.3) for the concepts that already exist there; anything beyond (e.g. Pine's per-order `qty` overriding a global `default_qty_value`) is IR-only until designed. |
| **Sessions** | trading-hours restrictions expressed in source | Maps to `RiskSpecification.sessionHours` (Q0.2) directly. |
| **Pyramiding** | see Position management | (listed separately in the sprint brief; consolidated here to avoid duplication) |
| **Recalculation semantics** | bar-close-only vs every-tick vs on-fill (Q0.4.2's `calc_on_every_tick`/`calc_on_order_fills`, MT4/5's `OnTick`, NinjaScript's `Calculate` modes) | Directly informs the IR's `Events` field — this is the single most consequential semantic difference across platforms (Q0.4.6), and the IR must preserve it precisely rather than normalizing it away, since normalizing early is exactly how silent behavior changes creep in. |
| **Timeframe dependencies** | which timeframe(s) each expression/indicator reads (own chart TF vs. `request.security`-style HTF pulls) | No `StrategySpec` equivalent yet — `MarketState`/`Expression` assume a single implicit timeframe. Directly feeds the MTF availability rules in `Q0.4_EVENT_MODEL.md`. |
| **Symbol dependencies** | which instrument(s) each expression reads (own-symbol-only vs. cross-symbol) | `StrategySpec.instruments` is a flat list with no per-expression symbol binding — the IR needs one for any strategy that reads a second symbol (e.g. a correlation filter). |

## What the IR is NOT

Not an executable bytecode, not a virtual machine, not a general-purpose AST for arbitrary programs (no loops, no user-defined functions with recursion, no I/O) — it is scoped exactly to what a TRADING STRATEGY needs to express, per the concept list above. A source construct that falls outside this scope (e.g. a Pine strategy that reads an external webhook) is a translation boundary, not an IR gap — it is `UNSUPPORTED` at the Source Fidelity level (`Q0.4_ADOPT_IMPROVE_AVOID_INVENT.md`'s Source Fidelity grades), not something the IR is expected to model.

## Relationship to Source Fidelity (Q0.4.34)

Every IR node produced by a future translator must be tagged with how faithfully it represents the source: `EXACT` (the IR node is a lossless structural transcription — e.g. a Pine `and`/`or` maps 1:1 to AT24's `and()`/`or()`), `SEMANTICALLY_EQUIVALENT` (different structure, provably same runtime behavior — e.g. a `for` loop that always runs exactly 3 times unrolled into 3 explicit terms), `APPROXIMATE` (best-effort, documented divergence — e.g. Pine's `close[1]` reduced to AT24's `previousIndicatorValues` lookup, which is defined for indicators but not for raw price series without an explicit indicator wrapper), or `UNSUPPORTED` (the construct has no IR representation at all, translation fails loudly for that node). This tagging is a Source Fidelity requirement, not an IR structural requirement — but the IR's node shape must have room to carry it (a `provenance: { fidelity: SourceFidelity, note?: string }` field on every node), which this document reserves now so a future translator doesn't have to retrofit it.

## What Q0.4 does NOT do

No parser for any of MQL4/MQL5/Pine/NinjaScript/cBot is written. No IR-to-TypeScript-type is implemented in `src/`. This document is the target shape a future sprint's parser-and-reducer work is measured against.
