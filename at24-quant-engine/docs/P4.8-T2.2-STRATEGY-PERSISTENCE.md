# P4.8-T2.2 — Strategy Persistence

**Status:** Implemented, full acceptance matrix passing (8 dedicated tests + regression), full regression green. Bounded to the locked T2.2 scope: a new user-owned `Strategy` table for AI-compiled strategies only, a nullable non-cascading reference from `AlgoTestRun`, and the write/read wiring to use it. No Library UI, no Library API, no registry Strategy rows, no Run History changes, no execution semantics changes.

## 0. Why this phase, in this position

P4.8-T1 gave AI-compiled strategies a deterministic, per-user logical identity (`ai-${userId}-${computeCrossPlatformSemanticHash(ir)}`) — but the P4.8-T2.1 audit found that identity reached nowhere durable: every AI-run write site hardcoded `strategyId: "ai-generated"` in the DB, `compiledStrategy` only ever exposed `identity.name` (never `identity.strategyId`), and the one indexed grouping column (`strategyHash`) was proven unstable for AI strategies (T1's own disclosed finding). T2.2 makes T1's identity queryable and durable, and — per the locked scope decision — does so by persisting a genuinely **re-runnable executable artifact**, not just an identity label.

## 1. What changed

**`frontend/prisma/schema.prisma`** — one new model, one new nullable column:

```prisma
model Strategy {
  id         String   @id @default(cuid())
  userId     String
  strategyId String
  origin     String   // "ai-generated" today, a plain string
  name       String
  artifact   Json     // the engine's own StrategyVersionRecord
  createdAt  DateTime @default(now())
  updatedAt  DateTime @updatedAt
  runs AlgoTestRun[]
  @@unique([userId, strategyId])
  @@index([userId, createdAt])
}
```

`AlgoTestRun` gains `strategyRefId String?` + `strategy Strategy? @relation(fields: [strategyRefId], references: [id], onDelete: SetNull)`, plus `@@index([strategyRefId])`.

**`frontend/prisma/migrations/20260907090000_add_strategy_persistence/migration.sql`** (new) — hand-written, never run through `prisma migrate dev`/`db push` (the established, standing pgvector shadow-DB constraint on this repo). Verified byte-for-byte against Prisma's own generated SQL by diffing an isolated minimal schema fragment (`migrate diff --from-empty --to-schema`, which needs no shadow DB) before writing the real migration file — table/column/index/FK naming and the `ON DELETE SET NULL ON UPDATE CASCADE` clause all match Prisma's own conventions exactly.

**`frontend/services/algo-test/algo-test.service.ts`**:
- New `persistAiStrategy(userId, spec)` — freezes the compiled `StrategySpec` via the engine's own `freezeStrategyVersion()` (Q0.9/ADR-007, already public, previously unused anywhere in the frontend) into a `StrategyVersionRecord`, and upserts it by `(userId, strategyId)`. Called once, right after `compileAndRunAiStrategy`'s existing "did compilation reach a real StrategySpec" guard — so it runs for **every** outcome that produced a real spec (a completed run, a `RANGE_TOO_LARGE` rejection, or a `DATA_VALID` provider failure), never only for a fully-completed run. All three `prisma.algoTestRun.update()` call sites in that function now also set `strategyRefId`.
- New `algoTestService.getStrategyArtifact(userId, strategyId)` — reads a persisted Strategy back, verifies its `contentHash` via the engine's own `verifyStrategyVersionIntegrity()`, then validates the spec via the engine's own `validateStrategySpec()`. Throws loudly on either failure (a corrupted/tampered row is never silently handed back as safe to execute); returns `null` only for the honest "no such Strategy" case. Not wired to any route yet — a persistence-layer capability, proven by its own tests, for the Library API (P4.8-T3) to consume first.

### 1a. Artifact immutability — a pre-merge review fix

The first implementation's `upsert()` overwrote `artifact`/`name` on every recompile that matched an existing `strategyId` — a real bug, caught in review before merge: `StrategyVersionRecord`'s own contract is "changing strategy logic must produce a NEW version, not an edit to this one," and an in-place overwrite violated that the moment a user recompiled the same logic under different phrasing (Run #1 could have been produced from artifact A while the row subsequently held artifact B).

**Fixed**: the `update` branch is now deliberately `{}` — an existing row's `artifact`/`name`/`origin` are never touched by a later recompile; only `updatedAt` moves (Prisma's `@updatedAt` still bumps on an `update()` call with no other fields). No additional runtime "does the semantic content still match" check is needed on the existing-row path: `strategyId` itself (the upsert key) is `ai-${userId}-${computeCrossPlatformSemanticHash(ir)}` — two compiles landing on the same `strategyId` are, by that same construction, already proven to share identical executable semantics. The only fields that can ever differ between them are exactly what the hash excludes (`identity.name`/`metadata`/`provenance` — T1's own proven adversarial case), never anything execution-relevant. So there is no genuine "investigate" branch to guard against; first-write-wins on the artifact is sufficient and correct.

**`runAlgoTest`** (the registry path) is **untouched** — confirmed both by the diff itself and by a dedicated structural test reading the actual function body from source.

## 2. Registry strategies deliberately get no row

Per the P4.8-T2.1 audit and the locked scope: `golden`/`ref-ema-crossover` never call `persistAiStrategy` or touch `prisma.strategy` at all — the code registry remains their sole source of truth, exactly as decided. Verified by source-reading (`validate-algo-test-strategy-persistence.ts`'s own structural test), not inferred.

## 3. Backward compatibility

Every `AlgoTestRun` row created before this migration has `strategyRefId = NULL`, forever — never backfilled, never guessed, same convention as every prior nullable column added to this table (`parameters`/`strategyHash`/`lifecycle`/`compiledStrategy`). The FK is deliberately `onDelete: SetNull`, not `Cascade` — the one existing relation pattern in this schema is `Cascade` everywhere, but that convention doesn't fit here: run history is historical evidence and must survive a Strategy being edited/deleted later, even though no such deletion UX exists yet.

## 4. Tests (`frontend/scripts/validate-algo-test-strategy-persistence.ts`, 8 tests, offline)

Against the real, unmodified `algoTestService.compileAndRunAiStrategy()`/`getStrategyArtifact()`, a fake-Prisma boundary (same established technique as every other algo-test validate script):

1. Recompiling byte-identical logic under different phrasing/name, same user → the SAME Strategy row (upsert, never a duplicate).
2. The identical logic compiled by two different users → two different, isolated Strategy rows.
3. Two genuinely different strategies, same user → two different Strategy rows, never collapsed.
4. **Artifact immutability**: same user, same `strategyId`, a genuinely different generated name/restated intent on the second compile — the persisted artifact stays byte-identical to the FIRST compile's, including the artifact's own embedded `spec.identity.name`, never silently replaced. Added during the pre-merge review that caught §1a's bug.
5. **The payoff**: `getStrategyArtifact()`'s returned spec, fed directly into `runSimulation()` — no `compileNaturalLanguageStrategy`, no `AIProvider`, no LLM call anywhere in the test — produces real trades. Proves the persisted artifact is genuinely, independently re-runnable.
6. `getStrategyArtifact()` returns `null` for a strategyId that was never persisted.
7. `getStrategyArtifact()` throws if the persisted artifact's `contentHash` no longer matches its own spec (simulated corruption) — never silently trusted.
8. `runAlgoTest`'s own source never references `persistAiStrategy`/`prisma.strategy` — read directly from source.

## 6. Known limitations / explicitly deferred

- `getStrategyArtifact()` is not wired to any API route — a persistence-layer capability only. The Library API is P4.8-T3's responsibility.
- No Strategy Library UI, no run aggregation/rollups, no favorites/tags/duplicate/clone UX, no strategy editing/version UX — all explicitly out of T2 per the locked scope.
- `AlgoTestRunView` (the wire contract) does not expose `strategyRefId` or the Strategy's own `strategyId` anywhere yet — deliberately deferred to whichever future tier actually consumes it, per the "no Run History redesign" boundary.
- The existing `strategyHash` asymmetry (disclosed in P4.8-T1, unaffected by this phase) remains: `computeSemanticStrategyHash()` was not touched.

## 7. P4.8-T2.3 — closed by audit, no implementation needed

A follow-up investigation was opened to scope-lock "when and how does `AlgoTestRun.strategyRefId` get populated, and what relationship/query guarantees do we require" as a distinct write-path-integration tier. Re-reading the actual merged T2.2 code (not memory) found this question already fully answered by what shipped above:

- `strategyRefId` is set on all three post-compilation outcomes (`RANGE_TOO_LARGE`, completed, `DATA_VALID` failure) — every path where a real `StrategySpec` exists — and correctly absent on the one remaining path (`INVALID_STRATEGY`, where compilation never reached a spec at all).
- `getAlgoTestRun`/`listAlgoTestRuns` both query with a plain `findFirst`/`findMany` (no `select` field restriction), so the raw row's `strategyRefId` is never silently dropped at the query layer — it's simply not yet projected into `AlgoTestRunView`, a deliberate §6 deferral, not a gap.
- The `Strategy.runs` reverse relation is real and Prisma-generation-verified today, not aspirational.

One minor, low-risk characteristic noted for completeness, not fixed: `persistAiStrategy()` and the following `algoTestRun.update()` aren't wrapped in a DB transaction, so a process crash between them could leave a temporarily run-less Strategy row. Harmless — the upsert is idempotent and first-write-wins, so the next real run of that same logical strategy resolves to the same row regardless.

**Decision**: no new code. The only remaining open question — a read-side query surface (e.g. "runs for this Strategy," "a user's Strategies") — is itself the first slice of the Library API, and was deliberately left for P4.8-T3 rather than built speculatively with no consumer. P4.8-T2 is complete through T2.2; T2.3 required no separate implementation.
