# Q0.6 D2/D3 Execution

## The core design decision: reuse Q0.5's fill rules per child bar, never reimplement them

`runtime/fidelity/intrabar-fill.ts`'s `resolveIntrabarOrderFill()` and `resolveIntrabarProtectiveExit()` do not contain a single new fill/exit RULE. Each walks an `IntrabarSequence`'s observations in chronological order and calls Q0.5's OWN `resolveMarketFill`/`resolveLimitFill`/`resolveStopFill`/`resolveStopLimitFill`/`resolveProtectiveExit` on each child bar, returning the first one that resolves. This is what makes the following guarantee structural rather than tested-in-by-luck: **D2/D3 can only ever be MORE precise than D1, never contradict it** — it is literally the same conservative per-bar logic, applied at finer granularity, not a different policy. `test/fidelity-multi-engine-golden.test.ts`'s core proof: Fixture A's parent bar 4 has both its stop-loss (96) and take-profit (111) reachable in its own aggregate OHLC — D1 (`runMultiFidelitySimulation(... , { fidelity: "D1_OHLC" })`) reports the mandatory conservative case (`ambiguous: true`, exits at the stop-loss, `grossPnl = -6`); the SAME bars, given real M15 children, resolve cleanly to the take-profit via child 0 alone (`grossPnl = +9`) — because that child bar's own OHLC (`high=113, low=101`) unambiguously proves the take-profit was hit before the stop-level dip that shows up two children later.

A STOP_LIMIT that triggers partway through a parent's children continues to be walked as a LIMIT across the REMAINING children of that SAME parent — a precision D1 cannot offer (D1 only re-checks on the next PARENT bar). If it is still not filled by the last available child, `triggeredOnly: true` is returned so the caller transitions the order to `TRIGGERED` for subsequent parents, exactly mirroring D1's cross-bar semantics (`test/fidelity-intrabar-fill.test.ts`, Fixture D).

## The orchestrator: why it duplicates control flow but not business logic

`runtime/fidelity/multi-fidelity-engine.ts`'s `runFidelityAwareSimulation()` (private; reached only for D2/D3 via the public `runMultiFidelitySimulation()`) NECESSARILY duplicates the outer control-flow shape of Q0.5's `runSimulation()` — same `EventQueue`, same one-bar-at-a-time seeding discipline, same 8-step pipeline — because Q0.5's file is FROZEN and is never modified or made pluggable (`docs/Q0.6_MULTI_FIDELITY.md`). This is a deliberate, documented tradeoff: the alternative (refactoring Q0.5's tested, shipped orchestrator into a pluggable-fill-strategy shape) carries real regression risk against a file whose entire purpose this sprint is required to leave untouched. What is NOT duplicated is any FILL or PROTECTIVE-EXIT decision rule — every one of those still lives in exactly one place, `runtime/simulation/bar-fill-model.ts` (Q0.5).

**Same-bar entry+exit interleaving (Q0.6.21/22)**: Q0.5's Steps 1 (resolve pending orders) and 1b (check the open position's own protective exit) are wrapped in a loop over this parent's available child bars — for EACH child, in order: resolve pending orders against it, THEN check the (possibly just-opened) position's protective exit against that SAME child. This lets an order fill and its resulting position exit within the SAME parent bar, even the SAME child bar, when the data genuinely supports it (Fixture A: entry and exit both resolve on child 0). Steps 2-5 (mark-to-market, day-boundary, strategy calculation, risk evaluation) stay driven by the PARENT bar only, timed identically to D1 — Q0.6 does not invent a new recalculation timing model.

**Same-bar safety at child granularity**: the guard is unchanged (`order.creationTimestamp >= childBar.timestamp` skips resolution) — since an order's `creationTimestamp` is always a PARENT bar's own timestamp, and every child of the FOLLOWING parent has a timestamp strictly greater than that, the guard naturally allows resolution starting at the first child of the next eligible parent and never earlier — the exact same invariant D1 enforces, just checked at finer resolution.

## Missing/partial detail data (Q0.6.10/11/12/40)

- `MISSING` (no child bars in this parent's window) with the default `missingDetailPolicy: "FAIL"` **throws `INSUFFICIENT_DETAIL_DATA` explicitly** — no silent degrade.
- `MISSING` with `missingDetailPolicy: "FALLBACK_TO_D1"` resolves that ONE parent bar at parent-bar granularity (the parent bar itself is used as a single-element "child" sequence, so the SAME per-child loop code runs unmodified) — tracked in `FidelityQuality.parentsResolvedAtParentGranularity`, never silent.
- `PARTIAL` (fewer than the expected child count) proceeds using whatever children ARE available, tracked in `DetailCoverage.partialParents` — a legitimate, reduced-confidence case, not an error.

## Why the D1_OHLC delegation still changes `resultHash`

`runMultiFidelitySimulation(..., { fidelity: "D1_OHLC" })` calls Q0.5's `runSimulation()` verbatim, then wraps `provenance` with the additive `MultiFidelityProvenance` fields (`simulationFidelity`, `detailCoverage`, `fidelityQuality`, etc.) before recomputing `resultHash` over the WRAPPED result. Every trade/account/position VALUE is byte-identical to calling `runSimulation()` directly (`test/fidelity-d1-regression.test.ts` asserts this with `assert.deepEqual`) — only the provenance wrapper, and therefore the hash, differs. This is expected and intentional: fidelity identity is part of what `resultHash` is supposed to certify (Q0.6.30).

## Execution Reality vs Data Detail (Q0.6.36/37) — the explicit split, see `docs/Q0.6_DATA_COVERAGE.md` for `FidelityQuality`'s full shape

Higher DATA DETAIL (D3 > D2 > D1) does **not** imply higher EXECUTION REALISM. D2/D3 only reduce OHLC-level ambiguity in WHICH price/timestamp resolved a fill or protective exit — they do **not** model spread, slippage, latency, or fees any more realistically than D1: those remain governed by the exact same `SpreadModel`/`SlippageModel`/`FeeModel`/`LatencyModel` the `base` config specifies (a permanently separate axis, per Q0.4's reserved `MarginModel`/`SettlementModel`/reality-model split). A D3 result with `ZeroSpread`/`ZeroSlippage` is not more "realistic" than a D1 result with the same zero-cost models — it is only more PRECISE about timing/sequencing.

## What Q0.6 does NOT do

No tick/bid-ask/depth/microstructure engine (D4-D7 reserved). No new spread/slippage/fee/latency model implementations. No portfolio/multi-instrument simulation. No margin/liquidation model (same documented Q0.5 limitation, unchanged). No `ExitRule` evaluation.
