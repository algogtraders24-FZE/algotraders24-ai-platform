# Q0.10 — Trailing Stop Semantics

## Contract

`TrailingStopRule { activation: DistanceSpec; distance: DistanceSpec }` (Q0.2, unchanged). Once price has moved `activation` in the position's favor, the stop trails `distance` behind the CURRENT price (not entry — the defining difference from breakeven, see `docs/Q0.10_MQL_MANAGEMENT.md`'s detection-shape distinction). Supports both fixed distance (`mode: "absolute"`/`"percentage"`) and ATR-multiple distance.

## Evaluation (`runtime/risk/trailing.ts`, Q0.3, unmodified)

`evaluateTrailingStop(rule, direction, entryPrice, currentPrice, currentStopLoss, currentAtr)`:

1. `favorable = direction === "BUY" ? currentPrice - entryPrice : entryPrice - currentPrice`; must be `>= activationDistance` or nothing happens.
2. `proposedStop = direction === "BUY" ? currentPrice - trailDistance : currentPrice + trailDistance`.
3. **Risk-reducing only**: `BUY`'s stop never decreases, `SELL`'s stop never increases — enforced by the same "must strictly improve on `currentStopLoss`" check breakeven uses. `test/q10-golden-fixtures.test.ts`'s `PM_TRAILING` proves the stop only ever moves up (102 → 103 → 106) across three consecutive favorable bars, never backward even as price itself fluctuates.

## ATR-based trailing

`distance: { mode: "atr-multiple", atrMultiple, atrPeriod }` resolves via `resolveDistanceSpec(spec, entryPrice, atrValue)` using the SAME ATR value supplied to every other risk rule in a given simulation run (`SimulationConfig.atrByIndex`) — there is exactly one ATR series per run, not one per rule (see the eligibility-gate's ATR-period-consistency check, `docs/Q0.10_POSITION_MANAGEMENT_AUDIT.md`). `PM_ATR_TRAILING` (`test/q10-golden-fixtures.test.ts`) proves the atr-multiple path produces identical numeric outcomes to the fixed-distance path when the resolved distances agree.

## Warmup — handled exactly like Q0.9

An ATR-based trailing rule requires the ATR indicator to be both (a) declared in `ir.indicators` (fixed in Q0.10 — see the audit's "ATR-indicator-registration fix") and (b) past its warmup period before the FIRST bar it is evaluated against, exactly like any SL/TP ATR use. `compileToSimulation`'s existing warmup-slicing (Q0.9, `runtime/reduction/simulation-adapter.ts`, unmodified) computes the max warmup across ALL of a strategy's indicators — including one referenced only by a trailing rule — and slices `bars`/every indicator series/`atrByIndex` by that offset before simulation ever begins. `test/q10-mql-management-e2e.test.ts`'s `Q0.10.31` proves a real `iATR(...)`-based trailing EA runs end-to-end without ever evaluating against an `undefined` ATR value.

## No lookahead

`test/q10-lookahead-determinism-replay.test.ts`'s `Q0.10.21` proves the stop level trailing computes at bar N is identical regardless of what price does at bar N+1 or later — the decision uses only `bars[0..N]`.

## Same-bar conflict with the stop it is about to improve

`PM_SL_TRAILING_CONFLICT` (`test/q10-golden-fixtures.test.ts`) proves a stop-loss hit is always resolved against the stop level AS OF THE START of the bar (Step 1b), never an improved level trailing would have computed FROM that same bar's own high (Step 5, which runs after — and doesn't run at all once the position has closed). See `docs/Q0.10_CONFLICT_SEMANTICS.md`.
