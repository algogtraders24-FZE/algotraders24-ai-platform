# Q0.1 Architecture Comparison

OLD = `quant-engine/` + `quant_engine/` (Python, pandas/SQLite-based, built by a prior isolated session).
NEW = `at24-quant-engine/` (TypeScript, standalone package, built in Q0).

Correct architecture takes priority over feature count — several rows below correctly pick NEW despite OLD having more working functionality, because NEW's separation of concerns is what Q0 was chartered to establish and OLD's shortcuts around that separation are exactly what caused OLD's own demonstrated staleness problem (see the Strategy Library Audit).

| Dimension | OLD | NEW | Winner | Reason | Migration required? |
|---|---|---|---|---|---|
| Strategy representation | Flat JSON Spec: `entry_long`/`entry_short` as ANDed comparison lists only (no OR/NOT/nesting), SL/TP-only exits, no declared-parameter metadata beyond what's baked into indicator periods | `StrategySpec` with full `Expression` trees (nested AND/OR/NOT), explicit `EntryRule[]`/`ExitRule[]`, declared `StrategyParameterDefinition[]` with min/max | **NEW** | Q0.3 explicitly required nested logical expressions; OLD cannot represent them at all | No — NEW's shape is a strict superset for entry logic; OLD specs can be read into NEW's shape (see Strategy Library Audit §5), not the reverse |
| Strategy versioning | None — no version field, no content hash, no immutability guarantee anywhere in the Spec schema or library rows | `StrategyVersionRecord` with `freezeStrategyVersion()`/`verifyStrategyVersionIntegrity()`, content-hash based, tested | **NEW** | ADR-007 requires immutable versions; OLD's total absence of versioning is precisely what let `strategy_library.db` go stale relative to newer execution engines without any way to detect it | No — this is a NEW-only capability; nothing to port from OLD |
| Expressions | Flat AND-only comparison list; 7 operators (`>`,`<`,`>=`,`<=`,`==`,`cross_above`,`cross_below`) | Recursive `Expression` tree: comparison / logical (AND/OR/NOT) / boolean-reference nodes; 6 comparison operators (no `cross_above`/`cross_below` yet) | **NEW** (structure), **OLD has one operator NEW lacks** | NEW's structure is strictly more expressive; OLD's `cross_above`/`cross_below` operators are a genuine gap in NEW | Yes — `cross_above`/`cross_below` semantics should be added to NEW's `ComparisonOperator` or modeled as indicator-level crossover detection in a future sprint; not done in Q0/Q0.1 (functional development is out of scope here) |
| Indicators | Real, working implementations: EMA, SMA, RSI, ATR, MACD, BB, STOCH, ADX, DONCHIAN, SUPERTREND (`spec_engine/indicators.py`, 163 lines, includes documented cross-engine bug fixes vs. MT5/Pine conventions) | Abstraction only (`IndicatorReference`, `indicatorKey()`) — deliberately no computation, per Q0.3's explicit instruction not to implement every indicator | **NEW's abstraction is correct for Q0's scope; OLD has the only real math** | Q0.3 intentionally deferred indicator implementation to a future plugin layer — this is not a defect in NEW, it's the designed boundary | Yes, eventually — OLD's `indicators.py` is a strong candidate to port (as new TS code, not a copy) when a future sprint implements the indicator-plugin layer NEW's abstraction already anticipates |
| Signals | Implicit — `runner.py`'s backtest loop tracks "trades" as flat records; no distinct Signal/Decision separation | Explicit `Signal` type (`BUY`/`SELL`/`FLAT`) generated deterministically via `generateSignal()` | **NEW** | ADR-003 requires Signal as its own concept, not folded into a trade record | No |
| Decisions | None — no equivalent concept exists in OLD; a "signal" and "trade" are conflated | Explicit `Decision` (action + reasoning context), separate from `Signal` | **NEW** | ADR-003 | No |
| Orders | None — OLD goes straight from signal to simulated fill, no `OrderIntent` concept | Explicit `OrderIntent` (side, type, quantity, SL/TP) referencing a `Decision` | **NEW** | ADR-003; OLD's telescoping of signal→fill is exactly the kind of collapsed-concept design Q0 was chartered to avoid | No |
| Positions | Implicit in `runner.py`'s single-open-position tracking (explicitly limited to one position at a time per `pdhpdl_strategy_backtest.py`'s own comment) | Explicit `Position` type, `OPEN`/`CLOSED` status, referencing its originating `OrderIntent` | **NEW** | ADR-003; OLD's single-position limitation is a real functional constraint NEW's contract does not share (though NEW has no runtime yet to prove multi-position handling) | No |
| Risk | `RiskConfig`: risk_pct, spread, contract_size, breakeven trigger/lock, ATR trailing start/multiple, partial-close threshold/pct, daily-loss circuit breaker, session-hour windows — imperative, engine-coupled | `RiskSpecification`: sizing method union (fixed-qty/fixed-lot/%-equity/ATR-based), `StopLossRule`/`TakeProfitRule` unions, `maxPositionSize`/`maxExposure` — declarative, validated | **NEW's contract shape**, **OLD has materially more risk-management sophistication** | NEW's declarative validation approach (ADR-006) is correct architecture; but breakeven/trailing/partial-close/daily-loss-halt/session-hours are real, currently-missing capabilities | Yes — these OLD concepts should inform a future `RiskSpecification` extension; explicitly not built in Q0.1 (no functional development permitted this sprint) |
| Market data | Raw pandas DataFrame + ad hoc SQLite `candles` table, symbol-suffix convention (`_EXNESS`) baked into consumer code | `MarketDataSeries`/`OHLCVBar`/`MarketDataSource{providerId,datasetId}` — provider-independent by construction | **NEW** | ADR-009/Q0.4 explicitly required provider abstraction; OLD's `_EXNESS`-suffix convention is a real coupling to one provider's naming | No — but a future MT5/Exness `MarketDataSource` adapter reading from `quant_engine/market.db` is a plausible future integration point (not built here) |
| Backtesting | **Three working engines** at increasing fidelity: `runner.py` (bar-level), `execution_mtf.py` (1-minute replay with real time-varying spread), `execution_tick.py` (true tick-level, correct bid/ask side) — all real, all tested against real Exness data, with a documented ~9x drawdown divergence between the coarse and MTF engines for the same spec | Contract only (`BacktestConfig`/`BacktestResult`/`ReproducibilityMetadata`) — no engine, per Q0.7's explicit deferral | **OLD has the only working capability here; NEW's contract is scoped correctly for where Q0 stopped** | Q0.7 deliberately deferred building a backtester; OLD's actual engines (and the concrete lesson that execution fidelity changes results by up to 9x) are valuable input for when that engine gets built | Yes, at the concept/lesson level — OLD's fidelity-tiering approach and its concrete divergence findings should directly inform NEW's future backtest engine design; the Python code itself is not portable as-is (tied to pandas/SQLite/`quant_engine`) |
| Execution | Real fill simulation against 1-minute bars or ticks, with real time-varying spread from `candle_spread` | `ExecutionSpecification` contract only (`fillModel` enum, flat slippage/spread models) | **OLD has the only working capability; NEW's contract is a reasonable starting shape** | Same reasoning as Backtesting row | Yes, at the concept level, same as above |
| Determinism | Not tested or guaranteed anywhere — no content-hash, no repeated-run comparison; the strategy library's own staleness (built before the more realistic engines existed, never re-scored) is a direct symptom of this gap | `canonicalStringify()`/`computeCanonicalHash()`, tested: identical `StrategySpec`+`MarketState` inputs produce byte-identical `Signal`/hash across repeated runs (ADR-008) | **NEW** | This is the single clearest case where OLD's gap caused a real, demonstrated problem (Strategy Library Audit §8) | No |
| AI integration | `llm_parser.py`: real (never live-tested) Claude tool-use integration — idea text → forced tool call against a JSON-schema tool definition → `validate_spec()` retry loop (max 3 attempts) if the model's output is invalid | Boundary documented only (ADR-004, Q0.10) — no AI-facing code exists in NEW at all | **NEW's boundary is correct; OLD has the only working implementation of the exact pattern the boundary describes** | OLD's "AI proposes, deterministic validator gates" loop is precisely ADR-004's prescribed shape — a strong precedent, not a competing design | Yes, at the pattern level, for a future AI Strategy Agent targeting NEW's `StrategySpec`/`validateStrategySpec()` — OLD's Python+Anthropic-SDK code is not directly portable to a TypeScript package |
| Testing | No automated test suite — an import-time self-test in `template_builder.py` plus manual comparison/proof scripts, none of them asserting pass/fail | 40 `node:test` tests covering StrategySpec validation, Expression evaluation, Signal generation, Risk validation, Determinism, and Isolation (Q0.12's required areas) | **NEW** | Unambiguous — OLD has no automated regression protection at all | No |
| Provider abstraction | Tightly coupled to one SQLite schema and one provider's symbol-suffix convention (`_EXNESS`) | Explicit `MarketDataSource{providerId, datasetId}` abstraction, provider-opaque by design | **NEW** | ADR-009 | No |
| Reproducibility | No mechanism at all (see Determinism row) | Full `ReproducibilityMetadata` contract (strategy hash, dataset id/hash, config hash, execution-assumptions hash, runtime version) | **NEW** | Q0.8 | No |
| Extensibility (code generation) | Real, working MQL5/MQL4/Pine Script v5 code generation from a Spec, including documented cross-engine indicator-math bug fixes | None — not part of Q0's domain-model scope at all | **OLD, uncontested — this is a distinct capability area NEW doesn't address** | Codegen is orthogonal to the domain-model/determinism work Q0 was chartered to build; not a gap in NEW's current scope, just an unaddressed future capability | Not applicable to Q0.1 — flag as a distinct future capability area, not an architecture migration item |

## Summary

NEW wins on every dimension Q0 was explicitly chartered to establish: canonical strategy representation, immutable versioning, Signal/Decision/Order/Position separation, deterministic/reproducible evaluation, provider-independent market data, and automated testing. OLD wins on dimensions Q0 explicitly deferred: real indicator math, a working (multi-fidelity) backtest/execution engine, and code generation — none of these were supposed to exist yet in NEW, so their absence is not a NEW defect, it's Q0's designed scope boundary. OLD's one clear structural edge NEW should absorb regardless of migration timing is the `cross_above`/`cross_below` comparison operators, since that's a real expressiveness gap rather than a deferred-scope item.

This validates the sprint's default assumption: **`at24-quant-engine/` is the canonical architecture**, and OLD's genuinely valuable pieces (indicator math, walk-forward technique, LLM-parser pattern, multi-fidelity execution lessons, codegen) are future migration/extension candidates layered onto NEW's foundation — not a reason to prefer OLD's architecture wholesale.
