# Q0.12 — Order Expiration Semantics

## `OrderExpirationPolicy` (Q0.12.21)

```ts
type OrderExpirationPolicy =
  | { kind: "GTC" }
  | { kind: "DAY" }
  | { kind: "BAR"; maxBars: number }
  | { kind: "TIMESTAMP"; expiresAt: number };
```

Distinct from Q0.7's `TimeInForce` (`domain/strategy-ir/order-ir.ts`, `"GTC"|"DAY"|"IOC"|"FOK"|"GTD"`) — a strategy-AUTHORED intent vocabulary, unused by this runtime type. `OrderExpirationPolicy` is the runtime `SimulationOrder`'s own field.

## The one evaluator, reused by both fidelity tiers (`isOrderExpired`, `order-engine.ts`)

- **`GTC`** (or `expiration` absent — the original, only-ever-implemented pre-Q0.12 behavior): never expires here; the existing end-of-run finalize step remains the only thing that ever closes out a GTC order.
- **`DAY`**: expires the instant the current bar falls on a later trading day than the order's own creation timestamp, via `computeTradingDayKey()` (Q0.3, reused verbatim — no second day-boundary formula).
- **`BAR`**: expires once `currentBarIndex - creationBarIndex >= maxBars`. `creationBarIndex` is tracked in `SimulationState.orderCreationBarIndex` (a new map, mirroring `entryBarIndexByPosition`'s own established pattern) — bars elapsed is never inferred from a timestamp difference, since bar durations are not assumed uniform.
- **`TIMESTAMP`**: expires once `asOf >= expiresAt` — an explicit, absolute instant.

Checked at the START of Step 1, BEFORE fill resolution, in both `simulation-engine.ts` (D1) and `multi-fidelity-engine.ts` (D2/D3, checked per child bar) — an expired order never fills, even if that same bar's OHLC would otherwise have triggered it.

## Where "UNSUPPORTED must block" applies

`OrderExpirationPolicy` itself has no `UNSUPPORTED` member — an unsupported policy is never allowed to reach a real `SimulationOrder` in the first place. This sprint does not thread expiration from MQL source (no `OrderSend`'s expiration argument detection was built — an explicit, documented scope boundary, see `docs/Q0.12_ORDER_MODIFICATION.md`), so the "block at the IR/reduction layer" enforcement point is deferred to whichever future sprint builds that detection; for now, expiration is only ever set programmatically (via `MODIFY_EXPIRATION`/`REPLACE`) or left as the default `GTC`.

## Setting expiration on an already-pending order

Since no strategy-level field yet threads an expiration policy at ORDER CREATION time, the only way to attach one this sprint is via `MODIFY_EXPIRATION` (or `REPLACE`) on an already-pending order — proven end-to-end in `test/q12-golden-fixtures.test.ts`'s `EXPIRATION` fixture (a `BAR`-kind policy attached mid-flight, correctly expiring the order exactly at the computed bar before it would otherwise have filled).
