# Q0.4 Intrabar Ambiguity Engine

Q0.4.10 (mandatory), plus Q0.4.11 (bar magnification) and Q0.4.12/13 (data fidelity, synthetic data detection) — grouped because bar magnification and data fidelity are the two ways AT24 will ever *reduce* intrabar ambiguity, and synthetic data detection is about knowing when a series must never be trusted to resolve it at all.

## The problem, precisely

```
BUY @ 100
SL @ 95
TP @ 105

Candle:  High = 110, Low = 90
```

OHLC data alone cannot prove whether price touched 105 (TP) or 90 (SL) first within that candle — both are consistent with the same four numbers. This is not a corner case; it is a structural property of OHLC bars, and it is `Q0.4_BACKTEST_FAILURE_CATALOG.md`'s item 13 ("same-bar SL/TP") — one of the most consequential, most silently-mishandled sources of backtest fantasy across every platform researched in Q0.4.1.

## Resolution strategies (in order of increasing data fidelity, per Q0.4.12)

1. **Conservative**: assume the WORSE outcome for the trader (SL hit before TP). Never overstates performance; will understate it for strategies where TP-first was actually more common. AT24's mandatory FALLBACK when no higher-fidelity data is available and the caller has not opted into a different explicit choice — silence must never default to the favorable outcome (this is the sprint's explicit, non-negotiable instruction: "never silently select the favorable result").
2. **Optimistic**: assume the BETTER outcome for the trader (TP hit before SL). Only ever valid as an explicitly-labeled, explicitly-opted-into research mode (e.g. to establish an upper bound on a strategy's theoretical performance) — never a default, and every `BacktestResult`/`ResearchResult` produced this way must carry a visible flag, never presented alongside conservative-resolved results without that flag.
3. **Deterministic heuristic**: a fixed, documented rule inferred from the bar's own shape — e.g. "assume price moved open → the extreme closer to open → the extreme farther from open → close" (an OHLC-shape-based ordering guess). Better than a blind conservative/optimistic coin flip in aggregate, but still a GUESS with a name, not evidence — must be labeled as a heuristic, never presented as fact.
4. **Lower-timeframe reconstruction**: replay the ambiguous bar using a lower timeframe (e.g. resolve an H1 bar's ambiguity using its constituent M1 bars) — this is what Q0.4.11's Bar Magnification concept exists for (see below). Materially better than a heuristic because it is evidence, not a guess, though it can still contain its OWN ambiguity one level down (an M1 bar can itself have SL/TP ambiguity, recursively) — the resolution quality improves but does not become certain until the fidelity floor (tick or bid/ask data) is reached.
5. **Tick replay**: replay against actual historical ticks — resolves the ambiguity with certainty, PROVIDED the tick data itself is complete and accurate (a real, separate concern — see Data Fidelity below; MT5's researched tick-reconstruction algorithm for gaps in real tick history, Q0.4.1, is itself a form of heuristic filling in for missing certainty).
6. **Bid/Ask replay**: the highest-fidelity resolution — replays against actual bid AND ask (not just a single trade-price tick stream), which additionally resolves spread-dependent fill questions (a limit order's fill depends on which side of the spread it rests on) that even trade-tick replay cannot fully answer.
7. **Unresolved ambiguity**: the honest, explicitly-representable outcome when NONE of 1-6 can be applied with confidence (e.g. even the lower-timeframe data is itself missing for that period) — AT24 must have a way to say "this trade's SL/TP order cannot be determined" rather than being forced to guess. This status must propagate into `ExecutionRealityGrade` (`Q0.4_BACKTEST_ARCHITECTURE.md`) as a first-class outcome, not get silently coerced into option 1 or 3.

**Hard rule, repeated for emphasis**: no future AT24 execution simulator may pick strategy 2 (Optimistic) as an unlabeled default under any circumstance. The sprint brief states this explicitly and it is treated as non-negotiable.

## Bar Magnification (Q0.4.11) — `BarDetailProvider`

A platform-neutral abstraction, inspired directly by Q0.4.2's researched TradingView Bar Magnifier feature: a pluggable source of higher-resolution data used to resolve ambiguity on a coarser bar, without requiring the whole simulation to run at that higher resolution.

```
interface BarDetailProvider {
  // Returns the best-available finer-grained observations covering [bar.timestamp, bar.timestamp + barDuration),
  // or null if no finer data exists for that window at all.
  getDetail(bar: OHLCVBar, targetResolution: DataFidelity): FinerObservations | null
}
```

Potential sources, from lowest to highest fidelity: `M1` (or whatever the next-finer standard timeframe is), an arbitrary lower timeframe, tick data, bid/ask tick data. **Not implemented in Q0.4** — this is the seam a future `Q0.5+` sprint plugs an actual data source into. The interface's job is only to let the Intrabar Engine ask "do you have anything finer for this window?" without caring where the answer comes from (a synthetic-fixture provider for tests, a real historical-tick provider for production research — both satisfy the same interface).

## Data Fidelity Model (Q0.4.12)

Every future backtest/experiment result MUST record which fidelity level its execution assumptions were resolved at:

| Level | Meaning |
|---|---|
| `D0` | Open only — a strategy that only ever sees/acts on the bar's open price (rare, but some platforms' `ON_BAR_OPEN` timing implies this) |
| `D1` | OHLC — the standard case; the source of the ambiguity problem this document exists to address |
| `D2` | Lower Timeframe — resolved via Bar Magnification against a coarser-than-tick, finer-than-D1 series |
| `D3` | M1 — the specific, commonly-available finest-standard-timeframe case (called out separately from generic D2 because M1 is what most historical data vendors, including MT5's own tick-reconstruction per Q0.4.1's research, actually guarantee) |
| `D4` | Tick — full historical trade-tick replay |
| `D5` | Bid/Ask — tick-level bid AND ask, resolving spread-dependent questions D4 cannot |
| `D6` | Depth — order-book depth data (Q0.4.23's Liquidity Model territory; no AT24 support planned near-term) |
| `D7` | Microstructure — the theoretical ceiling (queue position, order-flow-level detail); reserved, not expected to be reachable with retail-accessible data |

`DataFidelity` is a field on the future `BacktestResult`/`ResearchResult` provenance block (`Q0.4_BACKTEST_ARCHITECTURE.md`'s Provenance section, Q0.4.38) — every result states its own ceiling, so two results at different fidelities are never silently compared as if equivalent.

## Synthetic Data Detection (Q0.4.13)

Heikin Ashi, Renko, Range, Kagi, Line Break, and Point & Figure bars are all **derived** series — none of their OHLC values are directly tradeable market prices:

- **Heikin Ashi**: each bar's open/close are averages involving the PRIOR Heikin Ashi bar, not the raw market open/close — a Heikin Ashi "close" is not a price anyone could have traded at.
- **Renko**: bars form purely from price movement exceeding a fixed brick size, with NO time axis at all — a Renko bar's timestamp is arbitrary/synthetic, and its open/close are brick boundaries, not trade prices at those instants.
- **Range bars**: similar to Renko — form when price moves a fixed range, decoupled from clock time.
- **Kagi**: reverses direction based on a reversal amount, again decoupled from both fixed time intervals and raw OHLC.
- **Line Break**: forms new lines only on directional reversal, unrelated to real-time price sampling.
- **Point & Figure**: box/reversal based, no time axis, X/O columns are a pure abstraction over price movement.

Q0.4.2's research confirms TradingView itself explicitly warns against backtesting strategies on these chart types for exactly this reason — a strategy backtested against Renko "prices" is being tested against numbers that could not have been the actual fill prices, producing results with no connection to what live execution would do.

**AT24's mandatory design response**: every `MarketSeries` (Q0.2) must be classifiable as `REAL_MARKET_PRICE` or `SYNTHETIC_PRICE`. A future execution simulator must refuse to treat a `SYNTHETIC_PRICE` series' OHLC values as fillable prices for order execution, and must emit an explicit, unavoidable warning (not a quiet log line) whenever a `BacktestResult`/`ResearchResult` is produced from execution based on synthetic prices — this is a required field in the Execution Reality Grade's inputs (`Q0.4_BACKTEST_ARCHITECTURE.md`, Q0.4.36). A synthetic series remains legitimate for VISUALIZATION or as an INDICATOR INPUT (e.g. computing a signal FROM Renko bars is a valid strategy design choice), but the resulting order's actual fill must be resolved against a `REAL_MARKET_PRICE` series, never the synthetic one — this is a design constraint for whatever future engine consumes this document, not something implemented in Q0.4.

## What Q0.4 does NOT do

No fill model implementation, no actual tick-replay engine, no `BarDetailProvider` implementation, no synthetic-vs-real classification logic in `src/`. This document fixes the vocabulary and the non-negotiable "never silently favorable" rule that all of that future code must be built against.
