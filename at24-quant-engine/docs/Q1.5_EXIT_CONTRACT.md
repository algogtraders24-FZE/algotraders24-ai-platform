# Q1.5.3 — Generic `SIGNAL_EXIT` Execution Contract

## Audit, with code evidence (performed before any implementation)

- **Entry condition representation**: `EntryIR.condition: Expression`, evaluated per-bar by `decision-builder.ts`/`signal-generator.ts`.
- **Exit condition representation**: `ExitIR` (`entry-exit-ir.ts`) already had a `SIGNAL_EXIT` kind with `condition?: Expression` — the type existed since Q0.7.
- **Could a condition close a position, pre-Q1.5?** **No.** Confirmed independently in two places: `eligibility-gate.ts` unconditionally blocked any `SIGNAL_EXIT`, citing "never evaluated by Q0.5's engine"; `execution-compatibility-engine.ts` reported it `UNSUPPORTED` for the identical reason. `ir-to-spec-reducer.ts`'s `exitRules` array was **always** `[]` — eligibility excluded `SIGNAL_EXIT` before reduction could ever populate it. This was not "partially satisfies the contract" — the type was declared, execution was 100% absent, deliberately double-gated.
- **vs. SL/TP**: price-triggered, Q0.3's risk engine, no condition involved. **vs. pending cancellation**: Q0.13's source-structural mechanism, unrelated. **vs. explicit SIGNAL_EXIT**: no evaluator at all, pre-Q1.5.

## The contract, implemented as scoped

```
Expression
   ↓
Decision Builder (Step 1c, per bar)
   ↓
SIGNAL_EXIT (StrategySpec.exitRules, now genuinely populated)
   ↓
Position/Order Management Operation (closePosition, an EXISTING universal primitive)
   ↓
Universal Execution Engine (applyRealizedTrade, an EXISTING universal primitive)
   ↓
Position Close/Reduction
```

Reuses `evaluateExpression` (`expression-evaluator.ts`) — the **exact same** evaluator entries use, via a new `firstMatchingExitRule()` (`signal-generator.ts`, mirrors `firstMatchingEntryRule()`'s own established shape). No second evaluator. No MQL-specific mechanism — this is a generic `StrategySpec.exitRules` capability, platform-neutral by construction (`ExitRule.condition`/`appliesTo` are field-for-field identical between `ExitIR` and `StrategySpec.ExitRule`).

### Reduction (`ir-to-spec-reducer.ts`)

`exitRules` now populated from `ir.exits.filter(e => e.kind === "SIGNAL_EXIT" && e.condition)` — a direct structural passthrough, same pattern as `entryRules`.

### Eligibility (`eligibility-gate.ts`) — updated only after the runtime existed

A `SIGNAL_EXIT` is eligible **only** when it carries a real `condition` (validated structurally by `validateStrategyIR` upstream). One with no condition remains explicitly blocked — "nothing to evaluate can never be executed." No silent fallback.

### Execution compatibility (`execution-compatibility-engine.ts`)

Mirrors eligibility exactly: `SUPPORTED` with a condition, `UNSUPPORTED` without one.

### Runtime (Step 1c, both `simulation-engine.ts` and `multi-fidelity-engine.ts`)

A new step, placed **after** Step 1b (protective SL/TP) and **before** Step 4 (entry-signal generation): evaluates `firstMatchingExitRule(spec.exitRules, position.side, marketState)` against the position that survived Step 1b; on a match, closes via `closePosition()`/`applyRealizedTrade()` — the identical universal primitives protective exits already use. `marketState`'s construction was moved up from Step 4 to this point so both steps use the exact same closed-bar view (never a second, divergent notion of "current market state").

## Same-bar entry/exit policy — explicit, documented, deterministic, tested

**Exit-before-entry, sequential, never simultaneous.** Existing evidence dictated this, not invention: Step 1b (protective SL/TP) already closes a position **before** Step 4 computes that bar's own entry decision — Step 4 reads `state.openPositions` fresh, so a protective exit on bar N already made the position appear flat to bar N's own entry check. SIGNAL_EXIT (new Step 1c) was placed in the identical sequential position, extending an established precedent rather than inventing a new one. Concretely: if a SIGNAL_EXIT condition closes the open position on bar N, and bar N's entry condition is *also* true (using the same bar's closed-bar data), a fresh ENTER decision fires in the same bar's Step 4 — the position closes, then (if warranted) reopens, never both "at once."

## No-look-ahead

Unaffected by construction: `MarketState.bars` passed to `firstMatchingExitRule` is always `bars.slice(0, barIndex + 1)` — the exact same slice entries already use. There is no separate, looser data source for exits.

## Evidence

`test/q15-signal-exit.test.ts` (10 tests): long/short close, no-position no-erroneous-close, repeated-signal no double-close, exit-then-later-entry, same-bar entry/exit (proven via order count + final position provenance), `appliesTo` side-filtering, `firstMatchingExitRule` unit tests, 2 dedicated no-look-ahead tests (prefix/extended-bars trade-ledger equality; direct structural proof via a past-only `MarketState`). `test/q09-eligibility-gate.test.ts`/`test/strategy-ir-execution-compatibility.test.ts` updated (2 tests each) to assert the new, correct eligible/`SUPPORTED` behavior for a real condition, and continued blocking for a missing one. `test/q15-fidelity-parity.test.ts`: D1/D2/D3 identical trades.
