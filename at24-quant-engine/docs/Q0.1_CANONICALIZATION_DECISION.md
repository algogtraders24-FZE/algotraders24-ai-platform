# Q0.1 Canonicalization Decision

## 1. Which directory is canonical?

**`at24-quant-engine/`.**

Justification: it is the only implementation with a correct Signal/Decision/OrderIntent/Position separation (ADR-003), immutable content-hashed strategy versioning (ADR-007), tested determinism (ADR-008), a provider-independent market-data contract (ADR-009), and an automated test suite (40/40 passing) — the exact architectural properties Q0 was chartered to establish, none of which exist in either OLD directory (see [Q0.1_ARCHITECTURE_COMPARISON.md](Q0.1_ARCHITECTURE_COMPARISON.md)). It is also the only implementation with zero external dependents and zero forbidden-path imports, verified by its own isolation test.

## 2. Which old directories are retained?

All three: `quant-engine/`, `quant_engine/`, `quant-engine-handoff/`. **None are moved, renamed, merged, or deleted in this sprint.** See §9 (filesystem decision) for why, per directory.

## 3. Which are research-only?

`quant-engine/` (the Python spec→code engine, including `spec_engine/`, its demo/build scripts, and `strategy_library.db`) and `quant-engine-handoff/` (the origin handoff package). Both have zero production or M-Series-adjacent consumers (confirmed by repo-wide search, [Q0.1_QUANT_INVENTORY.md](Q0.1_QUANT_INVENTORY.md) §Q0.1.5).

## 4. Which are archived?

None, yet. `quant-engine/`, its subcomponents, and `quant-engine-handoff/` are **candidates** for a future archive location, but no archive move happens in Q0.1 — see §9 for why (no established archive convention exists in this repo, and moving now would be speculative cleanup with no functional benefit, which the sprint brief explicitly prohibits).

## 5. Which are retired?

None outright deleted. One component is flagged **CANDIDATE_FOR_RETIREMENT** (low priority, not acted on): `quant_engine/data_import.py`, which is already effectively dead code — it assumes a `data_raw/` directory that doesn't exist anywhere in this repo, and has been superseded by `quant-engine/scripts/import_exness.py` as the real data-ingestion path into `market.db`. Retiring it is safe (nothing calls it successfully in its current form) but not urgent, and is left for a future sprint to action explicitly rather than silently deleted here.

## 6. Which components should eventually migrate (concept-level, not code copy)?

Per [Q0.1_ARCHITECTURE_COMPARISON.md](Q0.1_ARCHITECTURE_COMPARISON.md):
- Indicator math (`spec_engine/indicators.py`) → future indicator-plugin implementation, once `at24-quant-engine` builds one (the `IndicatorReference` abstraction already anticipates this).
- Walk-forward robustness scoring methodology (`spec_engine/robustness.py`) → future `BacktestResult.metrics` extension.
- The LLM-parser validation-retry pattern (`spec_engine/llm_parser.py`: AI proposes → deterministic `validate_spec()` gates → repair loop) → precedent for a future AI Strategy Agent targeting `StrategySpec`/`validateStrategySpec()` (this is exactly ADR-004's prescribed shape, already proven out in Python).
- Multi-fidelity execution lessons (`runner.py` vs. `execution_mtf.py` vs. `execution_tick.py`, and the documented ~9x drawdown divergence between them) → design input for NEW's future backtest engine (Q0.7 deferred building one).
- `cross_above`/`cross_below` comparison semantics → a genuine expressiveness gap in NEW's `Expression` engine, worth closing regardless of any other migration.
- A small, robustness-score-selected sample of the 1,764-strategy library → staged per [Q0.1_STRATEGY_LIBRARY_AUDIT.md](Q0.1_STRATEGY_LIBRARY_AUDIT.md)'s 8-stage plan, never wholesale.
- Codegen (MQL5/MQL4/Pine Script v5) → a distinct future capability area, not a migration of Quant Engine architecture — flagged for separate future evaluation.

## 7. Which components must NOT migrate?

- The old flat, AND-only JSON Spec schema shape itself — `StrategySpec`'s `Expression` tree is already strictly more expressive and correctly versioned; do not regress NEW's shape to match OLD's.
- `quant_engine/engine.py`'s single-open-position, imperative backtest-loop architecture — superseded by the Signal/Decision/OrderIntent/Position separation (ADR-003); OLD's feature-completeness here does not outweigh the architectural regression migrating it would cause.
- `strategy_library.db`'s stored metrics, as-is — they are demonstrably stale relative to higher-fidelity execution engines built after the library was generated (Strategy Library Audit §8, §Migration Difficulty) and must never be copied forward without re-validation.
- `quant_engine/market.db`'s data file itself is not a "migration" candidate at all — it is external research/market data, not architecture; if a future `MarketDataSource` adapter ever reads from it, that is a new, separate integration decision, not a Q0.1 outcome.

## 8. Migration order (when a future sprint takes this up)

1. Close the `cross_above`/`cross_below` expressiveness gap in `at24-quant-engine`'s `Expression` engine (small, self-contained, no dependency on anything else in this list).
2. Extend `RiskSpecification` to model breakeven/ATR-trailing/partial-close/daily-loss-halt/session-hours, informed by OLD's `RiskConfig` — a design task, not a code port.
3. Design and build an indicator-plugin layer, porting OLD's `indicators.py` math as new TypeScript code.
4. Only then attempt the staged strategy-library migration (Q0.1_STRATEGY_LIBRARY_AUDIT.md's 8 stages) — it depends on both (1) and (2) being resolved first, since a meaningful fraction of the library's specs use risk fields that don't have a home in `RiskSpecification` yet.
5. Backtest engine design, informed by OLD's multi-fidelity lessons — this is a large, separate future sprint, not a quick follow-on.
6. AI Strategy Agent — only after (1)-(5) give it a stable, sufficiently expressive `StrategySpec` to target.

Codegen and any `MarketDataSource` adapter reading `quant_engine/market.db` are independent tracks, not gated on the above order.

## 9. Filesystem cleanup decision (per directory)

**`quant_engine/` (underscore) — RETAIN IN PLACE, mandatory, not discretionary.** `market.db` is a live, actively-appended-to (candle data through 2026-08-21) data dependency for the `ea-research/marketplace-research/` M4/M12 evidence-generation pipeline (`tag_trades_with_regime.py`, `regime_classifier.py`, `pdhpdl_strategy_backtest.py`, `generate_pdhpdl_extended_evidence_chain_full_real.py`), all of which hardcode a relative path (`Path(__file__).parent.parent.parent.parent / "quant_engine" / "market.db"`) to this exact location. `ea-research/` is explicitly out of scope for this sprint to touch — moving, renaming, or archiving this directory would break those scripts, which counts as touching M-Series-adjacent code by consequence even though no M-Series file itself would be edited. **Blocker for any future move: the M4/M12 scripts' hardcoded relative paths would need to be updated first, and that update is itself out of scope for a Quant-side sprint.**

**`quant-engine/` (hyphenated) — RETAIN IN PLACE.** Not mandatory in the same way as `quant_engine/`, but no safe, non-speculative reason to move it now: (a) it has a hard runtime dependency on `quant_engine/` via `sys.path` hacks, and `quant_engine/` itself cannot move (see above), so moving `quant-engine/` alone would require rewriting its internal path references for zero functional benefit; (b) no archive/legacy directory convention exists anywhere else in this repo to move it into; (c) it has zero external consumers, so leaving it in place creates no confusion risk beyond what this Q0.1 audit has already resolved by documenting it clearly. Per the sprint's explicit "no cleanup merely for appearance" rule, moving it now would be exactly that.

**`quant-engine-handoff/` — RETAIN IN PLACE.** Lowest priority of the three (~3.5MB, zero references anywhere, purely historical). CANDIDATE_FOR_ARCHIVE in a future low-priority cleanup sprint once an archive convention exists, but there is no urgency or functional reason to act now.

**No directory was moved, renamed, merged, or deleted by this sprint.**

## 10. What should happen to the 1,764 strategies?

Nothing, in Q0.1. They remain exactly where they are (`quant-engine/spec_engine/strategy_library.db`), unmigrated. The staged, evidence-gated approach in [Q0.1_STRATEGY_LIBRARY_AUDIT.md](Q0.1_STRATEGY_LIBRARY_AUDIT.md) (audit → classify → small robustness-selected sample → map → test equivalence → tooling only if proven → batch migrate → re-validate against a higher-fidelity engine) is the recommended future path, gated on the `RiskSpecification` extension and indicator-plugin work in §8 above. They must never be treated as trusted merely for having been successfully converted to `StrategySpec` — this mirrors `quant-engine/reports/INTEGRATION_DECISION.md`'s own prior conclusion about promotion into M-Series Evidence.

## Q1 Starting Point

Q1 should build directly on `at24-quant-engine/` as-is. Recommended first Q1 task, in order of leverage: close the `cross_above`/`cross_below` gap (cheap, self-contained, immediately removes OLD's one clear structural edge), then begin the `RiskSpecification` extension design informed by OLD's `RiskConfig`. Do not start Q1 with the strategy-library migration or a backtest engine — both depend on groundwork this sprint identified as not yet in place (§8).

## Stop Condition Check

**Not triggered.** Selecting `at24-quant-engine/` as canonical required no modification to any M-Series file, Prisma schema, or production code. The one real constraint discovered — `quant_engine/market.db` being load-bearing for the `ea-research/` M4/M12 pipeline — changes the filesystem-cleanup recommendation (retain in place) but does not require modifying M-Series or anything M-Series-adjacent to complete this sprint.
