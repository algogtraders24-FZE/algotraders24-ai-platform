# Q0.12 — Platform Execution Semantics & Order Modification Contract

## Scope

This sprint formalizes two things Q0.11 left open: (1) a dedicated `pendingOrderFill` contract on `PlatformSemanticProfile` (Q0.7), capturing per-platform LIMIT/STOP touch-vs-penetration/gap-through/bid-ask-dependency semantics that Q0.11's own order-type work didn't yet formalize; and (2) a genuine `OrderModificationIntent` mechanism (MODIFY_PRICE/MODIFY_STOP/MODIFY_LIMIT/MODIFY_EXPIRATION/CANCEL/REPLACE) with a minimal orchestrator, wired into the actual simulation loop for the first time.

## What already existed vs. what this sprint built

| Capability | Status before Q0.12 |
|---|---|
| Order lifecycle (`NEW→SUBMITTED→ACCEPTED→TRIGGERED→...→FILLED`, `CANCELLED`/`EXPIRED`/`REJECTED` terminal) | Fully implemented (Q0.4/Q0.5), `CANCELLED` legal but nothing ever called it |
| `PlatformSemanticProfile` (order model, account mode, intrabar, etc.) | Fully implemented (Q0.7), no dedicated pending-order-fill dimension |
| A strategy actually MODIFYING/CANCELLING a pending order | **Did not exist** — no contract, no orchestrator, no wiring |
| Order expiration (GTC/DAY/BAR/TIMESTAMP) | **Did not exist** — every order was implicitly GTC (end-of-run expiry only) |

## The contract chain

```
OrderModificationIntent (domain/simulation/order-modification.ts)
        ↓ validateOrderModification() — pure, checks terminal-state/price/directional validity
        ↓ applyOrderModification() (runtime/simulation/order-modification.ts) — pure orchestrator,
        ↓   reuses transitionOrder()/createOrder() (Q0.5, UNMODIFIED) — never a second order engine
SimulationConfig.orderModifications — a deterministic, declarative schedule
        ↓ Step 0.5 (NEW, both simulation-engine.ts AND multi-fidelity-engine.ts) —
        ↓   applied BEFORE that bar's own Step 1 fill/expiration resolution
Q0.5's existing pendingOrders map, fill resolvers, position/ledger pipeline — UNCHANGED
```

Three files needed additive edits to wire this in (`simulation-engine.ts`, `multi-fidelity-engine.ts`, `order-engine.ts`'s new `isOrderExpired` export); the fill resolvers, position accounting, and trade ledger required zero changes — a filled MODIFIED/REPLACED order becomes a `Position`/`SimulationTrade` through the exact same code path any other order always has.

## The D1/D2/D3 mirror discipline (learned from Q0.11, applied proactively this time)

`multi-fidelity-engine.ts` (Q0.6) has its own independent copy of Step 0.5/Step 1 — Q0.11 discovered this the hard way (a fix made only to D1 silently left D2/D3 unaware of order-type threading, found by a failing test). This sprint mirrored the identical Step 0.5/expiration logic into BOTH engines from the start, and `test/q12-fidelity-integration.test.ts` proves the mirror is correct rather than merely hoping it is.

## Deliberately out of scope this sprint

No strategy-authored "auto-modify" trigger exists (no MQL `OrderModify()`/`OrderDelete()` detection was built) — `orderModifications` is a declarative, test/tooling-facing schedule, not something derived from parsed source. Partial fills, hedging, and live/broker execution remain deferred exactly as Q0.11 left them. See `docs/Q0.12_ORDER_MODIFICATION.md` for the full reasoning behind this scope boundary.
