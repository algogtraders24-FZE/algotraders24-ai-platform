# Q0.11 — Universal Order & Entry Execution Semantics

## The headline finding

Q0.5's order engine, fill-model resolvers (`resolveMarketFill`/`resolveLimitFill`/`resolveStopFill`/`resolveStopLimitFill`), and order-lifecycle state machine (`NEW → SUBMITTED → ACCEPTED → TRIGGERED → PARTIALLY_FILLED → FILLED`, plus `CANCELLED`/`EXPIRED`/`REJECTED`) already fully and correctly implemented all four order types, generically, unit-tested — **before this sprint touched anything**. The gap was entirely structural: `RiskAction.ALLOW_ENTRY` (the only thing that can ever cause an order to be created) had no way to express anything but `MARKET`, and `StrategySpec.EntryRule` had no field to carry an order type or price at all. Every LIMIT/STOP/STOP_LIMIT order this engine's own fill-model logic was ready to resolve was structurally unreachable. Q0.11 is the sprint that connects the two ends of a bridge whose middle was already built.

## The contract chain

```
EntryIR.executionType / limitPrice / stopPrice          (domain/strategy-ir/entry-exit-ir.ts, Q0.7 + Q0.11 additive fields)
        ↓ ir-to-spec-reducer.ts (Q0.9, Q0.11 fix: field was previously silently dropped)
StrategySpec.EntryRule.executionType / limitPrice / stopPrice   (domain/strategy-spec.ts, Q0.11 additive fields)
        ↓ simulation-engine.ts Step 5 (Q0.5, frozen — Q0.11's one necessary additive edit)
        ↓   resolvePriceReference(ref, marketState) → concrete number
ProposedEntry.orderType / limitPrice / stopPrice          (domain/risk-evaluation.ts, Q0.3 + Q0.11 additive fields)
        ↓ evaluateRisk() → pipeline.ts (Q0.3, unmodified logic, additive passthrough)
RiskAction.ALLOW_ENTRY.orderType / limitPrice / stopPrice  (domain/risk-evaluation.ts, Q0.3 + Q0.11 additive fields)
        ↓ mapRiskAction() (Q0.5, frozen — Q0.11's second necessary additive edit)
RiskActionMapping.CREATE_ENTRY_ORDER.orderType / limitPrice / stopPrice
        ↓ createOrder() (Q0.5, UNMODIFIED — already accepted all four types)
SimulationOrder → bar-fill-model.ts resolvers (Q0.5, UNMODIFIED) → Position → TradeLedger
```

Four files needed a minimal, additive edit to complete this chain; everything downstream of `createOrder()` required zero changes.

## `PriceReference` — the platform-neutral price contract (Q0.11.3)

`domain/strategy-ir/price-reference.ts` defines the canonical kinds: `ABSOLUTE`/`CLOSE`/`OPEN`/`HIGH`/`LOW` (all `OPERAND`, directly reusing Q0.2/Q0.7's own `Operand` type — never a second value representation), `MID` (the reference bar's own `(high+low)/2`, computable without a live feed), `ATR_OFFSET` (a base price ± an ATR-multiple distance, reusing the exact `RiskLegBinding`-style arithmetic Q0.9/Q0.10 established for SL/TP), and `INDICATOR_VALUE` (also `OPERAND`, an indicator operand). `BID`/`ASK` are represented explicitly as `UNSUPPORTED` — named, not omitted — precisely so a detected `Bid`/`Ask`-based price reference is recorded and BLOCKED, never silently dropped or approximated with an OHLCV proxy (Q0.11.3's own rule).

`runtime/strategy-ir/price-reference-resolver.ts`'s `resolvePriceReference()` is the ONE resolver from a `PriceReference` to a concrete number, reusing `runtime/expression-evaluator.ts`'s `resolveOperand()` (exported additively — zero behavior change for its existing caller) for the `OPERAND` case, rather than re-implementing series/indicator/literal resolution a second time.

## Order Intent — not overloading a single price field (Q0.11.2)

`EntryIR`/`EntryRule` gained THREE new fields, kept deliberately separate: `executionType` (which of MARKET/LIMIT/STOP/STOP_LIMIT), `limitPrice` (a `PriceReference`, required for LIMIT/STOP_LIMIT), `stopPrice` (a `PriceReference`, required for STOP/STOP_LIMIT). The existing `condition` (WHEN to consider entering) and `trigger` field remain untouched — a LIMIT/STOP order's ENTRY CONDITION and its PRICE are two separate concerns, never conflated into one field.

## A genuine bug this sprint's own new capability exposed and fixed

`buildDecision()` (`runtime/simulation/decision-builder.ts`, Q0.5, frozen) only ever checked `hasOpenPosition` to decide whether to create a new entry order. Before Q0.11, every entry order was MARKET and always resolved within the SAME bar-processing step, one bar after creation, before the next signal check could ever run — so `hasOpenPosition` alone was sufficient. A LIMIT/STOP/STOP_LIMIT order can now remain PENDING for many bars while its condition stays true, which would otherwise create a NEW duplicate pending order on every one of those bars — a real "phantom position"/"duplicate fill" risk (Q0.11.38). Fixed via an additive `hasPendingOrder` parameter (default `false`, so every pre-Q0.11 all-MARKET strategy is byte-identical), computed from `state.pendingOrders` filtered by symbol. Proven in `test/q11-intrabar-fixtures.test.ts`'s `MULTIPLE_PENDING_ORDERS` and `test/q11-failure-catalog.test.ts` items 11/16.

## A second refinement: SL/TP reference price for non-MARKET orders

Since `simulation-engine.ts`'s Step 5 was already being edited to thread order-type information through, it also now uses the order's own DETERMINISTICALLY KNOWN price (`limitPrice ?? stopPrice ?? bar.close`) as the reference for `resolveStopLossPrice`/`resolveTakeProfitPrice`/`resolvePositionSize`, rather than always using the decision bar's close. A LIMIT/STOP order's whole purpose is to enter at a DIFFERENT price than the current one — continuing to compute SL/TP relative to `bar.close` when a more accurate, already-known reference exists would be even more misleading than the same characteristic already documented for MARKET orders (Q0.9/Q0.10's "decision price vs fill price" note). MARKET orders are completely unaffected (still use `bar.close`, unchanged). See `test/q11-intrabar-fixtures.test.ts`'s `PENDING_ORDER_PLUS_SL`/`PENDING_ORDER_PLUS_TP`.

## The D2/D3 mirror (a second, real gap this sprint's own testing found)

`runtime/fidelity/multi-fidelity-engine.ts` (Q0.6) does not call `simulation-engine.ts`'s internals at all — Q0.6 was built with its OWN independent copy of Step 4/5 (signal generation, entry-order creation), reusing only low-level functions (`resolveStopLossPrice`, `createOrder`, `mapRiskAction`, etc.) directly, per Q0.6's own established "duplicate outer control-flow shape" architecture. The four fixes above, made only in `simulation-engine.ts`, were therefore invisible to D2/D3 until mirrored into this second copy — every D2/D3 entry would have silently remained MARKET regardless of the declared `executionType`. Found by `test/q11-fidelity-compatibility.test.ts`'s own D2 run (an entry price inconsistent with the declared STOP order), fixed via the identical additive mirror. See `docs/Q0.11_GAP_EXECUTION.md`.

## What Q0.11 deliberately did NOT touch

Q0.5's fill-model resolvers, order lifecycle state machine, and event-queue ordering are byte-for-byte unmodified. Position accounting, trade-ledger construction, and metrics computation are unmodified — a filled LIMIT/STOP/STOP_LIMIT order becomes a `Position`/`SimulationTrade` through the EXACT same code path a MARKET order always has.
