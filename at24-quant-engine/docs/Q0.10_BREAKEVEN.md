# Q0.10 — Breakeven Semantics

## Contract

`BreakevenRule { trigger: DistanceSpec; lockOffset: DistanceSpec }` (`domain/risk-specification.ts`, Q0.2, unchanged). Once price has moved `trigger` in the position's favor (measured from `entryPrice`), the stop is proposed to move to `entry ± lockOffset` (sign matching the favorable direction). `lockOffset` may be exactly `0` — "move to exactly entry" — a documented, common, and (as of Q0.10) correctly-validated case; see the audit doc for the `validateDistanceSpec` bug this fixed.

## Evaluation (`runtime/risk/breakeven.ts`, Q0.3, unmodified)

`evaluateBreakeven(rule, direction, entryPrice, currentPrice, currentAtr, currentStopLoss)`:

1. Resolve `triggerDistance`/`lockDistance` via `resolveDistanceSpec` (absolute / percentage-of-entry / atr-multiple). An `atr-multiple` spec with no supplied `currentAtr` produces a `BREAKEVEN_CONSTRAINT` violation (not a crash) — the caller must supply ATR context before this policy can be evaluated.
2. `favorable = direction === "BUY" ? currentPrice - entryPrice : entryPrice - currentPrice`. If `favorable < triggerDistance`, not triggered — no violation, simply nothing to do yet.
3. `proposedStop = direction === "BUY" ? entryPrice + lockDistance : entryPrice - lockDistance`.
4. **The stop can only improve.** If a current stop exists, the proposal is only `triggered: true` when it is STRICTLY better (`BUY`: `proposedStop > currentStopLoss`; `SELL`: `proposedStop < currentStopLoss`). A position with no stop at all is always improved by adding one.

Deterministic, activates once per qualifying bar (re-evaluated every bar, but only returns `triggered: true` when the proposal is a genuine improvement — see `PM_MULTI_ACTION` in `test/q10-golden-fixtures.test.ts` for the exact "activates once, then correctly falls through to trailing" sequence). No future-bar information: `currentPrice` is always the bar's own close, supplied by the (frozen) simulation loop at Step 5, one bar after any stop change takes effect for protective-exit purposes (Step 1b runs before Step 5 — see `docs/Q0.10_CONFLICT_SEMANTICS.md`).

## Long/short symmetry

Verified directly: `PM_LONG_BREAKEVEN` and `PM_SHORT_BREAKEVEN` (`test/q10-golden-fixtures.test.ts`) run the identical trigger/offset configuration through both directions and assert an identical R=0 outcome (`grossPnl` differs only by sign convention, `-0` vs `0`, both mathematically zero).

## R-multiple at a breakeven exit

Computed from `Position.initialStopLoss` (the stop AT ENTRY, immutable), never the current (breakeven-moved) stop — see `docs/Q0.10_POSITION_MANAGEMENT_AUDIT.md`'s R-multiple fix. A trade that exits exactly at breakeven reports a well-defined `R = 0`, not a crash.

## MQL source-pattern detection

See `docs/Q0.10_MQL_MANAGEMENT.md` — the provable shape is `if (<currentPrice> - OrderOpenPrice() >= <literal>) { OrderModify(ticket, ..., OrderOpenPrice() [± <literal>], ...) }` (or the MQL5 `PositionModify`/`PositionGetDouble(POSITION_PRICE_OPEN)` equivalent), distinguished from trailing by whether the new-SL argument's arithmetic base is the entry-price call itself.
