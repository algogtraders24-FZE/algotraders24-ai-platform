## Q0.8.39 — expected semantic contract, as literally written

```ts
test("Q0.8.39: real account/broker dependencies (AccountInfoDouble, SYMBOL_TRADE_STOPS_LEVEL/FREEZE_LEVEL) are recognized and separated from strategy semantics", () => {
  const { model } = importG01();
  assert.ok(model.unsupportedConstructs.some((u) => u.category === "ACCOUNT_DEPENDENCY" && u.functionName === "AccountInfoDouble"));
  assert.ok(model.unsupportedConstructs.some((u) => u.category === "BROKER_CONSTRAINT_DEPENDENCY"));
});
```

Two independent claims: (1) G01 calls `AccountInfoDouble` and it is classified `ACCOUNT_DEPENDENCY`; (2) G01 contains SOME construct classified `BROKER_CONSTRAINT_DEPENDENCY` (per the test's own title, implicitly `SYMBOL_TRADE_STOPS_LEVEL`/`FREEZE_LEVEL`).

## Current committed G01 semantics — measured directly

Running `importMQLSource()` against the real, committed v0.1 blob produces:

| Category | Count | Detail |
|---|---|---|
| `ACCOUNT_DEPENDENCY` | 2 | `AccountInfoDouble` (line 449); the unconditional-realtime-bid/ask wrapper `G01_CheckRetestAndEnter` (line 569) |
| `BROKER_CONSTRAINT_DEPENDENCY` | **0** | — |

Direct source inspection (`grep`) confirms: the committed v0.1 blob contains **zero** occurrences of `SYMBOL_TRADE_STOPS_LEVEL`, `SYMBOL_TRADE_FREEZE_LEVEL`, `SYMBOL_VOLUME_MIN`, `SYMBOL_VOLUME_MAX`, or `SYMBOL_VOLUME_STEP` anywhere. It DOES contain three genuine `SymbolInfo*` calls: `SymbolInfoDouble(_Symbol, SYMBOL_BID)` (line 386), `SymbolInfoDouble(_Symbol, SYMBOL_ASK)` (line 387) — both correctly recognized as the live-bid/ask realtime-dependency shape, not flagged separately — and `SymbolInfoInteger(_Symbol, SYMBOL_SPREAD)` (line 409), which is **not** one of the five canonical `BROKER_CONSTRAINT_TOKENS` and falls through to the generic `UNRESOLVED_CROSS_FILE_CALL` bucket.

## Is Q0.8.39 correctly scoped?

**No — its second assertion is miscoupled.** The first assertion (`AccountInfoDouble` → `ACCOUNT_DEPENDENCY`) is correct and passes against the real, committed source. The second assertion (`BROKER_CONSTRAINT_DEPENDENCY` present) asserts a fact that is true of a source revision that does not exist in git — it was never true of what this test actually reads, from the moment it was first committed. This is not a regression (nothing "broke" it); it is a baseline that was authored against the wrong committed reference from day one, most likely because the test/documentation-generation step was run against a locally-edited (never-committed) working copy of G01 at the time.

## Outcome selected

**Outcome A — the test is incorrectly coupled to v0.2.** See `Q0.8.39_BASELINE_REPAIR_REPORT` (delivered as this sprint's final chat report) for the exact repair applied: `test/mql-g01-import.test.ts`'s Q0.8.39 is corrected to test only what the committed v0.1 source actually and provably contains; the underlying `BROKER_CONSTRAINT_DEPENDENCY` detector's own correctness (present/absent/unknown) is proven separately, against small, dedicated, non-G01 fixtures, in `test/q0.8.39-broker-constraint-contract.test.ts` — so the detector's own contract remains fully tested even though G01 v0.1 itself doesn't happen to exercise it.

## A genuine, separate, deliberately-undressed finding

`SymbolInfoInteger(_Symbol, SYMBOL_SPREAD)` (G01 line 409) is misclassified `UNRESOLVED_CROSS_FILE_CALL` — implying an unresolved *user-defined* function — when it is in fact a well-known MQL5 built-in whose specific *argument* (a live spread reading, not a static trading constraint) this importer simply has no dedicated category for. This is a real, narrowly-scoped, genuinely generic (not G01-specific) semantic-analyzer gap. **It is intentionally NOT fixed in this repair** — fixing it is out of Q0.8.39's own scope (Q0.8.39 makes no claim about `SYMBOL_SPREAD` or about `UNRESOLVED_CROSS_FILE_CALL` counts), and per this sprint's own "smallest justified repair" mandate, expanding `BROKER_CONSTRAINT_TOKENS` or adding a new category to accommodate it would be an unrelated semantic change bundled into a baseline-repair commit. Recorded here as a known limitation and a candidate for a dedicated future sprint.
