# Q0.10 — Partial Close Semantics

## Contract

`PartialCloseRule { trigger: DistanceSpec; closePercent: number }` (Q0.2, unchanged; `closePercent` validated `(0, 100]`). Once price has moved `trigger` in the position's favor, close `closePercent` of the REMAINING position size (not the original — relevant after a scale-in via `increasePosition`, though Q0.10's fixtures don't exercise pyramiding+partial-close together).

## Evaluation (`runtime/risk/partial-close.ts`, Q0.3, unmodified)

`evaluatePartialClose(rule, direction, entryPrice, currentPrice, currentAtr, alreadyTriggered)`:

1. `if (alreadyTriggered) return { triggered: false }` — **one-time behavior, checked first.** `closePercent` always comes from an already-validated spec (`(0, 100]`), so no separate "would this exceed the position" check is needed — the invariant is guaranteed upstream.
2. Otherwise resolves `triggerDistance` and checks the same favorable-move condition breakeven/trailing use.

`alreadyTriggered` is threaded from `state.partialCloseTriggered` (a `Set<positionId>`, `simulation-engine.ts`, Q0.5, unmodified) — set the moment a `REDUCE_POSITION` action is applied, checked on every subsequent bar for that position. `test/q10-failure-catalog.test.ts`'s item 6 proves a position already flagged never re-triggers even when the price condition is still met on a later bar.

## Execution (`simulation-engine.ts`'s `REDUCE_POSITION` mapping, Q0.5, unmodified)

`reduceQty = currentPosition.quantity * (closePercent / 100)`; `reducePosition()` (`position-engine.ts`) validates `0 < reduceQuantity <= position.quantity` structurally (throws otherwise — see the failure catalog items 1/2), computes `grossPnl` for exactly the reduced quantity, and records ONE new `TradeLedger` entry via `applyRealizedTrade` for that leg alone — the remaining, still-open quantity keeps its own `stopLoss`/`initialStopLoss` unchanged. `PM_PARTIAL_CLOSE` (`test/q10-golden-fixtures.test.ts`) proves the resulting ledger has exactly two independent entries (the partial leg and the eventual full stop-out of the remainder), with `Q0.10.34` (`test/q10-metrics-provenance.test.ts`) proving the account's `realizedPnl`/`balance` sum both legs exactly once — no double counting, no dropped remainder.

## Quantity invariants

- Cannot become negative: `reducePosition` throws for `reduceQuantity <= 0`.
- Cannot exceed the remaining position: `reducePosition` throws for `reduceQuantity > position.quantity`.
- The resulting position is always valid: `remaining === 0` closes the position fully (status `"CLOSED"`); `remaining > 0` keeps it open with the reduced `quantity`, all other fields (stop, entry price, `initialStopLoss`) carried over unchanged via `...position` spreads.

## Same-bar conflicts

`PM_PARTIAL_SL_CONFLICT` (`test/q10-golden-fixtures.test.ts`) proves a same-bar stop-loss hit resolves the FULL position via Step 1b before Step 5's partial-close evaluation ever runs — never a partial close immediately followed by a second, separate full-close event on the same bar. See `docs/Q0.10_CONFLICT_SEMANTICS.md`.

## MQL source-pattern detection

See `docs/Q0.10_MQL_MANAGEMENT.md` — the provable shape is `if (<favorable-move-trigger>) { OrderClose(ticket, <lotsVar> * <literal in (0,1)>, ...) }`, where `<lotsVar>` is bound to `OrderLots()`/`PositionGetDouble(POSITION_VOLUME)`.
