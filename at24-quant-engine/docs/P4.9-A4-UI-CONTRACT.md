## R1 findings that shaped this contract (not assumptions — read directly from real code)

1. **The Strategy Detail page (`app/dashboard/algo-test-library/[strategyId]/page.tsx`) has zero action buttons today.** It is read-only by its own locked T3.4 scope. "Optimize Parameters" is the *first* action button ever added there — not a sibling to an existing "Run Backtest" link (none exists).
2. **There is no list-all endpoint for optimization experiments.** `GET /optimization` does not exist and is not being added (locked: no API changes). Only `GET /optimization/[experimentId]` (single, by id) exists.
3. **`CompiledStrategyCard`'s parameter data (`{key, defaultValue}`) is presentation-only** — no `min`/`max`/`step`/`type`. The real `StrategyParameterDefinition[]` the Setup form and the "should this button show" check both need comes from `GET /api/private/algo-test/strategies` (`fetchAlgoTestStrategies()`), already used by `AlgoTestPanel.tsx` — a different, already-existing endpoint from the Strategy Library one.
4. **The actual functional backtest entry point today, `AlgoTestPanel.tsx` (1288 lines), is embedded per-chart-pane in `/dashboard/workspace`**, tightly coupled to overlaying one run's trades on that specific pane. Architecturally the wrong home for a longer-running, non-chart-overlay, multi-step flow — and out of scope to modify regardless.
5. **`∞` display already has a real precedent**: `AlgoTestPanel.tsx:678`, `Number.isFinite(metrics.profitFactor) ? metrics.profitFactor.toFixed(2) : "∞"`.
6. **No progress-bar primitive exists anywhere in the codebase.** Genuinely new, small, built from existing tokens — not a new design system.

## Page-by-page contract

### Setup (`/dashboard/algo-test-optimize`)

**Data in**: `GET /api/private/algo-test/strategies` (filtered client-side to registry strategies with `parameters.length > 0`); `?strategyId=` query param preselects one.

**Fields**: strategy picker (defaults to the preselected one if present and eligible), symbol (from `supportedSymbols`), timeframe (from `supportedTimeframes`), start date, end date, initial balance — same conventions/helpers `AlgoTestPanel.tsx` already uses (`isoDateNDaysAgo`, `toEngineTimestamp`), reimplemented here rather than imported (those helpers are module-private in a 1288-line client component locked out of scope — extracting them would itself be a change to that file).

**Per selected parameter**: min / max / step, three number inputs, styled identically to `AlgoTestPanel`'s existing `ParameterField` (`w-full rounded-control border border-border bg-ink-3 px-2 py-1.5 text-sm text-text`). A parameter the user does not add to the sweep is simply omitted from `searchSpace` — the service fills its own default, per the already-locked contract.

**Live candidate count**: `Π floor((max−min)/step) + 1` per swept parameter, computed client-side, shown as `Estimated candidates: N / 256`. This is a UX convenience only — never trusted as the creation gate; `POST /optimization`'s own `400 TOO_MANY_CANDIDATES` (or any other validation code) is what actually blocks submission, surfaced as an inline error using the response's real `message`.

**Client-side checks** (UX only, service remains authoritative): missing/invalid min, max, or step; `max < min`; `> 256` estimated candidates; zero parameters swept is **allowed** (a valid 1-candidate degenerate sweep, per the already-locked service contract — never blocked client-side either).

**Submit** → `POST /api/private/algo-test/optimization` → on `201`, `router.push` to the Monitor/Results route with the real `experimentId`. On `400`, show the real `{code, message}` inline — never a generic "something went wrong".

### Monitor + Results (`/dashboard/algo-test-optimize/[experimentId]`)

One component tree, branching only on `experiment.status` (mirrors `AlgoTestResults`'s own status-driven rendering — never a second route/page for "the same experiment, later").

**Load**: `GET /api/private/algo-test/optimization/[experimentId]` on mount. `Skeleton` while loading — **and the loading flag must reset to true whenever `experimentId` changes** (the exact stale-state bug P4.8-T3.4.2 fixed on the Strategy Library detail page — this page must not repeat it).

**`404 NOT_FOUND`** → `ErrorState` (not `EmptyState` — a missing/not-owned experiment is a real failure state for a URL someone navigated to directly, not an honestly-empty list).

**`QUEUED` / `RUNNING`** (Monitor view):
- Header block: strategy, symbol/timeframe, date range, `Badge` for status.
- Progress bar (new, small, existing tokens) + `processedCandidates / totalCandidates` text, driven **only** by the real fields on the fetched `experiment` — never a client-invented estimate or fake incremental animation.
- On an interval, call `POST .../continue`, replace local state with its real response. **Never framed as passive server progress** — the UI is the thing driving continuation (per A.2/A.3's own stateless-chunk design, and per your explicit "do not present this as a background worker" rule).
- "Cancel Optimization" button → `Modal` confirmation: *"Cancel optimization? The current candidate will finish before the optimization stops. Unprocessed candidates will not be executed."* → `POST .../cancel` → replace state with the real response (now `CANCELLED`) → render the terminal view. No fake instant interruption — the confirmation copy itself sets that expectation.

**`COMPLETED`** (Results view):
- `bestCandidateId` present → Winner card: profit factor (via the shared `∞`-aware formatter, decision below), trade count, full parameter set — read directly off the winning candidate the API already returns, **never recomputed client-side** (locked: "UI must not independently calculate the winner").
- `bestCandidateId` null → explicit empty-but-real state: *"No eligible winner — no candidate met the minimum requirement of 20 trades."* (the `20` here is the currently-real `OPTIMIZATION_MIN_ELIGIBLE_TRADES` value, displayed as a fact, never hardcoded as a UI literal disconnected from the API's own semantics — if the service constant changes, this copy must not silently go stale; sourcing it from the response is preferred if a field exists for it, otherwise flagged as a known small drift risk at T5 implementation time.)
- Candidate table (`Table`/`Thead`/`Tbody`/`Tr`/`Td`, already responsive via `overflow-x-auto`): status (🏆 winner / candidate / rejected / failed), parameters, trade count, profit factor. `profitFactor` wire value is `number | "Infinity" | null` — displayed as `∞` for the string `"Infinity"`, the formatted number otherwise, `—` for `null` (a `FAILED`/`REJECTED` candidate with nothing computed).

**`FAILED`** → `ErrorState` with the real `experiment.errorMessage`.

**`CANCELLED`** → terminal view showing whatever candidates did complete (retained, not hidden) with **no** winner section at all — never "no winner" (that phrasing is reserved for a genuine `COMPLETED` + null-winner outcome; a cancelled experiment never ran winner selection, a different fact).
