# Q1.3 — Pending Order Semantics

Consolidated reference for the pending-order behavior this engine implements, per Q1.3's own required documentation checklist. Every claim below is proven by a named test (`test/q1.3-pending-order-management.test.ts` and, for the underlying mechanism, `test/simulation-fill-model.test.ts`/`test/q11-*`/`test/q12-*`).

## 1. Supported pending order types

`BUY_LIMIT`, `SELL_LIMIT`, `BUY_STOP`, `SELL_STOP` (this sprint's required four) plus `BUY_STOP_LIMIT`/`SELL_STOP_LIMIT` (a pre-existing fifth type, kept as-is). Represented as an orthogonal pair — `orderType: "LIMIT"|"STOP"|"STOP_LIMIT"` × `side: "BUY"|"SELL"` (`domain/simulation/order.ts`) — rather than a single four/six-way enum; the two fields together carry exactly the same information a `BUY_LIMIT`-style literal would, with zero duplication against the existing, already-validated `OrderTypeIR`/`OrderSide` vocabulary.

## 2. Trigger semantics

| Order | Trigger condition (this engine's actual, tested behavior) |
|---|---|
| `BUY_LIMIT` | Strict trade-through: `bar.low < limitPrice` (a bare touch, `low == limitPrice`, does NOT fill) — or a favorable gap (`bar.open <= limitPrice`) |
| `SELL_LIMIT` | Strict trade-through: `bar.high > limitPrice` — or a favorable gap (`bar.open >= limitPrice`) |
| `BUY_STOP` | Touch-triggers: `bar.high >= stopPrice` — or an unfavorable gap (`bar.open >= stopPrice`) |
| `SELL_STOP` | Touch-triggers: `bar.low <= stopPrice` — or an unfavorable gap (`bar.open <= stopPrice`) |

**LIMIT orders use strict trade-through, not touch** — a deliberate, documented divergence from a literal `<=`/`>=` reading, in place since Q0.5 (`docs/Q0.4_ADOPT_IMPROVE_AVOID_INVENT.md`'s "never silently favorable" finding, citing LEAN's `EquityFillModel` precedent over Pine's lenient touch-fill default). STOP orders already use inclusive touch semantics, matching a literal `<=`/`>=` reading exactly. See `docs/Q1.3_PENDING_ORDER_AUDIT.md` §4 for the full rationale and why it is preserved rather than changed.

## 3. Fill-price semantics

A LIMIT fills at the requested level (or better, on a favorable gap) — never worse. A STOP fills at the requested level (or worse, on an unfavorable gap) — never better. Neither ever fills at a price the bar's own OHLC did not actually contain.

## 4. Gap behavior

A gap that crosses the order's level triggers it — the fill price is the REAL price the gap landed at (`bar.open`), never the nominal limit/stop level fabricated as if no gap occurred. Proven directly against this sprint's own worked example (limit=100, price gaps 105→98 → fills at 98) in `test/q1.3-pending-order-management.test.ts`'s GAP tests.

## 5. OHLC (bar-based) behavior

Exactly one evaluation per pending order per bar, using ONLY that bar's own `open`/`high`/`low`/`close` — no bar beyond the one currently being processed is ever consulted (proven via a "does bar 2 change bar 1's outcome" test). The canonical same-bar ambiguity policy: a `STOP_LIMIT` order whose stop condition is reachable but whose open does not ALSO unambiguously prove the limit condition never manufactures a same-bar fill — it becomes `TRIGGERED` and is re-evaluated as a plain `LIMIT` starting the next bar (`resolveStopLimitFill`'s `triggeredOnly` branch, `runtime/simulation/bar-fill-model.ts`). This is the project's existing, tested ambiguity policy — not invented by this sprint.

## 6. Tick behavior — not implemented, honestly documented

This engine has **no tick-level (sub-minute, sequential, non-OHLC) fidelity tier**. `domain/fidelity/simulation-fidelity.ts` implements exactly `D1_OHLC`/`D2_LOWER_TIMEFRAME`/`D3_M1` — all three are bar-based; `D4_TICK` is declared `Reserved`, never implemented, never produced or accepted by any runtime code. `D3_M1` (the finest implemented tier) walks 1-minute OHLC child bars through the SAME `resolveLimitFill`/`resolveStopFill`/`resolveStopLimitFill` resolvers listed above (via `runtime/fidelity/intrabar-fill.ts`), never a separate tick-shaped resolver. This is a real, permanent-for-now limitation — no tick engine is built in this sprint (an explicit non-goal: "new backtesting engine").

## 7. Cancellation

`OrderModificationIntent{modificationType:"CANCEL"}` (`domain/simulation/order-modification.ts`, Q0.12) transitions the order to `CANCELLED` and removes it from `state.pendingOrders` the same bar. A cancelled order can never fill afterward (structurally — it is no longer in the map the fill loop iterates), never creates a position, never creates a trade-ledger entry, and cancelling an already-terminal order is explicitly rejected (`ORDER_MODIFICATION_REJECTED`), never silently re-applied.

## 8. Expiration

`OrderExpirationPolicy` (`GTC`/`DAY`/`BAR`/`TIMESTAMP`, `domain/simulation/order.ts`, Q0.12) is checked at the start of each bar's fill-resolution step, before any fill is attempted — an expired order never fills, even if that same bar's OHLC would otherwise have triggered it.

## 9. State transitions

`NEW → SUBMITTED → ACCEPTED → {TRIGGERED, PARTIALLY_FILLED, FILLED, CANCELLED, EXPIRED}`, `TRIGGERED`/`PARTIALLY_FILLED` also leading to the same terminal set. `FILLED`/`CANCELLED`/`EXPIRED`/`REJECTED` are terminal — zero outgoing transitions; `FILLED→CANCELLED`, `CANCELLED→FILLED`, `EXPIRED→FILLED` (and every other invalid transition) throw deterministically (`runtime/simulation/order-engine.ts`'s `transitionOrder`). Q1.3's generic "PENDING" label maps to the union `{ACCEPTED, TRIGGERED, PARTIALLY_FILLED}`.

## 10. Ambiguity policy

Stated fully in §5 above. The one place genuine same-bar ambiguity can arise (a `STOP_LIMIT`'s two-stage trigger) is resolved conservatively, never by inventing an intrabar sequence the OHLC data cannot prove.

## 11. Known limitations

- LIMIT orders require strict trade-through, not touch (§2) — a deliberate divergence from Q1.3's own literal wording, preserved for compatibility with a frozen, extensively-tested execution core.
- No tick-level fidelity exists (§6).
- No cross-order OCO/bracket linkage exists — two independent pending orders for the same instrument (e.g. a bracketing BUY_STOP and SELL_STOP) are evaluated and can both fill independently within the same bar; this engine has no concept of "filling one cancels the other" (explicitly out of scope — "advanced cancel/replace orchestration").
- Expiration policies must be attached via a modification (there is no strategy-authored "expire N bars after creation" declaration at order-creation time yet — a pre-existing Q0.12 scope boundary, unchanged by this sprint).

## 12. Deterministic guarantees

Identical `strategySpec` + market data + `SimulationConfig` always produces an identical `resultHash` across repeated runs (proven directly in this sprint's own determinism test, and exhaustively by `test/q11-determinism-provenance.test.ts`/`test/q12-determinism-provenance.test.ts`). No wall-clock, no `Math.random()`, no environment dependency anywhere in the simulation runtime (enforced structurally by `test/simulation-determinism.test.ts`'s static source scan, which this sprint's changes remain subject to and pass).
