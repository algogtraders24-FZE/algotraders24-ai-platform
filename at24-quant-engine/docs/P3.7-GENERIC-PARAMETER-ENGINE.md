# P3.7 — Generic Parameter Engine

**Status:** Implemented, tested, scoped deliberately narrower than the phase's own original diagram — see section 1. Builds on P3.4–P3.6 (`docs/P3.6-MULTI-STRATEGY-REGISTRY.md`).

## 1. Investigation before implementation — why this phase is scoped to engine-reference strategies only

Before writing any code, `StrategySpec.parameters` (the engine field P3.4's audit found with "zero runtime consumers anywhere") was traced for an *imported* strategy, not just Golden's hand-authored case. Two things, both confirmed directly:

- **The importer auto-populates `spec.parameters` from raw MQL `input` declarations, with zero category filtering.** For `ref-ema-crossover` (P3.6), it produced `[{key: "InpLotSize", type: "number", defaultValue: 0.1}]` — `InpLotSize` is category #2 (risk/execution config) under P3.4's own taxonomy, the exact category Golden Strategy's human-curated list correctly excludes. The importer has no concept of that taxonomy; it dumps every `input`.
- **It is completely disconnected from execution.** `REF_EMA_CROSSOVER_SPEC.risk.sizing.quantity` is `1`, hardcoded at generation time — `ir-to-spec-reducer.ts` passes `parameters: ir.parameters` straight through with no wiring back into any other field. Changing the value in `spec.parameters` today does nothing.
- **The engine's own `StrategyParameterDefinition` type is `{key, type, defaultValue, min?, max?}`** — no label, description, category, step, or options. Far poorer than the metadata schema this phase's original design target called for (name/type/default/min/max/step/category/description).

Making imported-strategy parameters genuinely metadata-driven end to end (declare → override → re-execution) would require either teaching the importer to categorize `input` declarations and wire an accepted override back into the specific expression/risk field it came from (a real codegen-level feature, not built anywhere today), or a formal parameter-substitution concept in the IR itself. Both are genuine engine redesigns, not a wiring fix — the opposite of P3.5's own finding (where the "generic mechanism" already existed and only needed to be used).

**Decision** (confirmed with the user before implementation): P3.7 formalizes the generic mechanism for **engine-reference strategies only** (Golden Strategy today, any future TypeScript-authored strategy). MQL-imported strategies' `spec.parameters` stays informational-only and uncategorized — an explicit non-goal this phase, not a silently-dropped one. `ref-ema-crossover` continues to correctly expose zero Strategy Parameters in the frontend registry (P3.6 already got this right, by disciplined audit rather than by accident of scope).

## 2. What "generic" actually means here

Before this phase, adding a numeric parameter to an engine-reference strategy required THREE hand-written, per-field pieces kept in sync by convention, not by structure: an optional field on the strategy's own `*Params` interface (e.g. `GoldenStrategyParams.stopLossDistance`), a `StrategyParameterDefinition` entry in the frontend registry, and a line in a hand-written override-mapping function (`toGoldenStrategyOverrides`) translating a validated submission into that specific named field.

P3.7 replaces the third piece with one generic function, `pickNumericOverrides<K>(parameterIds, overrides)` (`frontend/services/algo-test/strategy-registry.ts`), driven entirely by the strategy's own declared parameter-id list — never a second, independent id list. Golden's registry entry now reads:

```ts
buildSpec: (overrides) => buildGoldenStrategySpec(pickNumericOverrides(GOLDEN_PARAMETERS.map((p) => p.id), overrides)),
```

`GOLDEN_PARAMETERS` is the exact same array assigned to `parameters:` — one list, not two. Adding a new engine-reference strategy's numeric parameter needs: (1) an optional field on its own `*Params` interface, (2) a metadata entry whose `id` matches that field's name. No new mapping function. This is safe, not magic, because of one formal, now-documented contract: **a `StrategyParameterDefinition`'s `id` must equal the corresponding optional field name in the strategy's own build-params interface.** `pickNumericOverrides`'s own `typeof` check is defensive (against a caller that bypassed `validateParameterValues()`'s own guarantee that every declared parameter is already present and type-checked), not where new business logic lives.

## 3. `category`, formalized

`StrategyParameterCategory = "signal" | "risk" | "execution" | "provider"` (P3.4's own audit taxonomy, `docs/P3.4-STRATEGY-PARAMETERS.md` section 1) is now a real, required field on `StrategyParameterDefinition` — previously only prose in comments. Golden's four parameters are classified explicitly: `priceThreshold` = `"signal"` (the one genuine, category-#1 parameter), the other three = `"risk"`. Mirrored on the wire type (`types/algo-test.ts`'s `AlgoTestParameterDefinition`/`AlgoTestParameterCategory`) so the classification reaches the client, though `AlgoTestPanel.tsx` does not yet group or filter by it — a real, honestly-disclosed non-goal, not a silent gap (the panel's own parameter rendering needed, and got, zero other changes this phase, confirmed by direct diff).

## 4. Evidence

`frontend/scripts/validate-algo-test-parameters.ts` (23/23, offline/no-network, +4 from P3.6's 19): `pickNumericOverrides` proven strategy-agnostic with a wholly synthetic parameter-id list neither Golden nor `ref-ema-crossover` declares (zero new mapping code, the phase's own central claim, proven directly rather than asserted); a non-numeric value for a declared id is ignored, not coerced or thrown; `golden.buildSpec()` exercised end-to-end through the real registry entry (not just the helper in isolation), proving both a genuine override and the omitted-field-reproduces-the-engine-default guarantee P3.5 already proved at the engine level, now proven again at this generic-wiring layer; every registered engine-reference strategy's parameters carry a real, valid category.
