# P3.6 — Multi-Strategy Registry + Generic Strategy Contract

**Status:** Implemented, tested. Builds on P3.1–P3.5 (`docs/P3.5-RISK-CONFIGURATION.md`) and the reproducibility principles locked in `docs/ALGO_TESTING_PRO_ROADMAP.md`.

## 1. What this phase actually proves

Before this phase, `STRATEGY_REGISTRY` had exactly one entry (Golden Strategy) and the service layer (`algo-test.service.ts`) called Golden-Strategy-specific functions directly (`toGoldenStrategyOverrides()`, `runGoldenBacktest()`). "The registry" was a registry in name, not in the sense that mattered: nothing had ever proven a *second, differently-sourced* strategy could reach execution through the same code path without a `strategyId` branch appearing somewhere.

P3.6 proves it, with a real second strategy sourced a genuinely different way: Golden Strategy is authored directly as TypeScript (`at24-quant-engine/src/reference/golden-strategy.ts`); the new `ref-ema-crossover` strategy is produced by running a real MQL5 source string through the actual import pipeline (`importMQLSource()` → `reduceStrategyIRToSpec()`, the same Q0.8–Q1.5 machinery G01 research uses). Both reach `algo-test.service.ts` through the identical `StrategyDefinition` contract, and `algo-test.service.ts` itself contains zero `strategyId === "golden"` (or any other strategyId) conditionals.

## 2. Why G01 is NOT this phase's second strategy — investigated, not assumed

Before writing any registry code, the real, frozen G01 v0.1 baseline (`ea-research/G01_LiquiditySweep_MSS_FVG/AT24_GOLD_G01_LiquiditySweep_MSS_FVG.mq5`) was run through `importMQLSource()` unmodified. Result, not inferred:

- **34 `UNRESOLVED_CROSS_FILE_CALL` diagnostics.** G01's entire strategy logic (`G01_DetectSweep`, `G01_DetectMSS`, `G01_DetectFVG`, `G01_CalculateSL/TP`, `G01_CalculateLotSize`, …) lives in 12 `#include` files. The importer records include *paths* as metadata but never resolves their content — a real, current, documented limitation, not new to this sprint.
- **The entry logic is separately unreachable even if includes were resolved**: G01 dispatches through a state-machine `switch` in `AT24_G01_StateMachine.mqh`, and the importer's own AST has an independent, pre-existing limit here — `"switch" statement not modeled by the minimal AST (Q0.8.5) — skipped structurally`.
- **The resulting IR is honest, not broken**: the importer's no-fabrication discipline produces `condition: literal(1) == literal(0)` — an intentional, permanently-false placeholder, never a guessed real one. Registering this IR and simulating it would produce a strategy that structurally imports without crashing but never trades — not a meaningful "G01 runs through the pipeline" proof, an empty shell wearing G01's name.

The same probe was run against another real, already-existing single-file EA in this repo (`Q16-E2E-RSI-Test-Strategy.mq5`) — also produces a hollow placeholder (`direction: "FLAT"`), because its entry logic is wrapped in custom helper functions (`OpenTrade`, `HasOpenPosition`) rather than the one inline, unwrapped condition shape the importer's semantic analyzer actually reconstructs (`test/fixtures/q14-mql-corpus.ts`'s own established EMA-cross pattern, confirmed against the real corpus, not invented for this finding).

**Decision, made explicitly rather than worked around silently**: G01 import is out of scope for P3.6. It becomes its own named future item — see `docs/ALGO_TESTING_PRO_ROADMAP.md` section 13, "Future: G01 Full Import Fidelity" — requiring recursive `#include` resolution AND `switch`/state-machine AST modeling, with its own acceptance bar (behavioral equivalence to the frozen native baseline, not merely "imports without crashing").

## 3. The reference strategy — real, not a fixture built to pass an assertion

`ref-ema-crossover` (`at24-quant-engine/src/reference/ref-ema-crossover-strategy.ts`) is a genuine, classic EMA(9)/EMA(21) crossover: single file, no `#include` dependencies, no state machine, inline entry conditions in `OnTick` — the one shape the corpus already proves the importer reconstructs faithfully. It is embedded as a string constant (matching `test/fixtures/q14-mql-corpus.ts`'s own convention) because a separate `.mq5` file would not survive the frontend's vendor-sync step (`frontend/scripts/vendor-quant-engine.mjs` copies `dist/`, not raw MQL source).

**A second real finding, discovered empirically while building it**: an initial version declared literal stop-loss/take-profit prices directly on `trade.Buy()`/`trade.Sell()` (e.g. `trade.Buy(lots, symbol, 0.0, 1900.0, 1920.0, comment)`). This did **not** resolve — the importer treats *any* price argument there (literal or computed) as an unresolved cross-file formula, and a declared-but-unresolved protective exit **blocks eligibility entirely** (the same rule `test/fixtures/q14-mql-corpus.ts`'s `mql5-23` fixture already demonstrates: "a declared STOP_LOSS/TAKE_PROFIT exit whose price cannot be resolved BLOCKS the whole strategy"). The final version declares no SL/TP price arguments at all (`0.0, 0.0`, matching every eligible corpus fixture) — honestly reflecting what the importer can actually prove, rather than declaring a risk contract it cannot back.

**A third finding, also discovered empirically, documented so it is not silently rediscovered later**: this D1 engine's opposite-direction handling is more limited than the IR's own `pyramiding.oppositeDirectionBehavior: "REVERSAL"` field implies. Grepping `decision-builder.ts`/`simulation-engine.ts` confirms `oppositeDirectionBehavior` is set at IR/reduction time (`ir-generator.ts`) but is **not read anywhere in the D1 simulation path** — an opposite-direction signal while a position is already open simply `HOLD`s (per `decision-builder.ts`'s own doc comment: "opposite-direction handling is a separate, pre-existing reversal mechanism, untouched by this" — a mechanism this investigation could not locate as actually wired into D1's decision loop for a strategy with no declared exit rules). This is **not a P3.6 bug to fix** — it is a pre-existing engine characteristic, now documented rather than assumed. The reference strategy's own test proves both entry rules independently (two separate flat-start simulations — one crossing up, one crossing down) rather than relying on an in-run reversal this engine does not actually perform here.

## 4. The generic contract

`StrategyDefinition` (`frontend/services/algo-test/strategy-registry.ts`) gained four fields, present on every entry:

- `source: StrategySource` — `{kind: "engine-reference", module}` or `{kind: "mql-import", dialect, sourceFileName, sourceHash}`. Every future adapter this roadmap names (cTrader/cBot, NinjaScript, Pine, natural language, direct IR) adds its own `kind` here — nothing outside this type declaration branches on it.
- `reproducibility: { baseContentHash }` — `computeSemanticStrategyHash()` of the strategy's default-parameter spec, computed once at registry load.
- `buildSpec(overrides) => StrategySpec` — the one piece of genuinely per-strategy logic: turning already-validated parameter overrides into this strategy's spec. Golden Strategy's own `toGoldenStrategyOverrides()` mapping (previously living in `algo-test.service.ts`) moved here, into Golden's own entry — `algo-test.service.ts` now calls `strategy.buildSpec(parameters)` identically for every strategy.
- `buildIndicatorSeries(bars) => ReadonlyMap<...>` — the other per-strategy piece: which indicators this strategy's entry conditions reference, computed via the engine's own `calculateSeries()` (`runtime/indicator-engine.ts`, already-existing production infrastructure, not new math). Golden's own PRICE-pseudo-indicator logic and the reference strategy's real EMA(9)/EMA(21) computation each own their own function.

`algo-test.service.ts`'s execution path is now: resolve `strategy` from the registry → `validateParameterValues(strategy, request.parameters)` → `strategy.buildSpec(normalized)` → `runBacktest({ ..., strategySpec, buildIndicatorSeries: strategy.buildIndicatorSeries }, provider)`. No strategy-specific code remains in that file.

`run-golden-backtest.ts` (P3.2A) is deliberately **untouched** — it still exists, unchanged, for the two P3.2A/P3.2A.1-era live-verification scripts (`validate-algo-test-foundation.ts`, `validate-algo-test-production-data.ts`) that are specifically about Golden Strategy's own data-provider foundation and are out of scope here. The new `run-backtest.ts` is a separate, generic sibling — the one `algo-test.service.ts` actually calls.

`AlgoTestPanel.tsx` required **zero changes** for the registry/parameter/spec-building path — its rendering was already fully generic (confirmed in P3.5). It does **not** yet expose a strategy-picker UI (the mount effect still auto-selects `strategies.find(s => s.strategyId === "golden") ?? strategies[0]`) — a real, honestly-disclosed gap, not silently left implicit: a second registered strategy is reachable through the API and the generic execution path, but not yet selectable by a user through the panel. Left for a future phase, since it is a UI/UX decision, not part of this phase's stated acceptance bar.

`frontend/scripts/validate-algo-test-parameters.ts` updated and passing (19/19, offline/no-network): the registry now has 2 entries through the generic contract (`source.kind` differs correctly per entry); Golden's own 4 parameters remain intact.
