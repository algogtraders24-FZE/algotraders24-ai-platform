# P4.5 — Strategy & Run Identity Persistence

**Status:** Implemented, tested (9 new offline tests + 1 existing P4.4 test corrected to the new, intended behavior), visually verified against the real, unmodified `AlgoTestPanel.tsx` component. Bounded scope, exactly as locked: identity persistence only — zero engine changes, zero MFE/MAE, zero optimization, zero MTF, zero UI redesign.

## 0. Why this phase, in this position

The P4.5 audit (`P4.5 — Post-P4.4 Architecture & LuxAlgo Gap Audit`) traced real dependencies through the code and found that lifecycle/strategy identity persistence is a genuine prerequisite for three later items — run-history UI, strategy library, and optimization/walk-forward all either need a stable, queryable identity to group or link runs, or would require redoing this exact migration retroactively once per feature. MFE/MAE and true MTF execution are both fully independent of it. That evidence moved this phase ahead of Trade Analytics Expansion (MFE/MAE) in the locked roadmap, even though the original ranking had analytics first.

## 1. What changed

**Schema** (`frontend/prisma/schema.prisma`, migration `20260904120000_add_algo_test_identity`): three new nullable columns on `AlgoTestRun` — `strategyHash` (String), `lifecycle` (JSONB), `compiledStrategy` (JSONB) — plus an index, `AlgoTestRun_userId_strategyHash_idx`, supporting a future run-history/library/optimization feature grouping or comparing a user's own runs by exact strategy identity. Purely additive; no column removed, no type changed, no existing data touched. Hand-authored (never `prisma migrate dev` — this repo's pgvector column defeats Prisma's shadow-database drift check and would demand a full reset; the established safe pattern is a hand-written `migration.sql` applied via `prisma migrate deploy`). **This migration has not been applied to any real database in this sandboxed environment** — it needs `prisma migrate deploy` run against the real target database as a manual step before this reaches production.

**Service** (`frontend/services/algo-test/algo-test.service.ts`): `strategyHash`/`lifecycle`/`compiledStrategy` were already computed on every request (P3.8/P4.3) but only ever returned in the response, never written to the row. Every write site that already computes them now also persists them, in the same `update()` call that already writes `metrics`/`trades`/`equityCurve` — never a second round trip:
- `runAlgoTest` success path and its DATA_VALID-failure catch block (registry strategies).
- `compileAndRunAiStrategy`'s four branches: no-compiled-spec failure (lifecycle only — genuinely no spec exists), RANGE_TOO_LARGE failure, success, and post-compile execution-failure catch block.

`getAlgoTestRun` (reopen) now reads all three back from the row instead of leaving them `undefined`. `listAlgoTestRuns` (the run-history list) now also carries `strategyHash` — deliberately not `lifecycle`/`compiledStrategy` (heavy JSON blobs, excluded from the summary view for the same reason `trades`/`equityCurve` already are); `strategyHash` is the one small field the audit's own "groundwork for Run History" requirement actually needs.

**UI** (`frontend/components/chart-engine/AlgoTestPanel.tsx`): only the two "Unavailable — not persisted this phase" captions changed, since they described a P4.3 gap that no longer exists for any run created after this phase ships. They now read "this run predates lifecycle/evidence persistence" / "this run predates compiled-strategy persistence" — accurate for both a genuinely pre-P4.5 row and, going forward, never shown at all for a new run. No layout, structure, or new section — this is a wording correction tied directly to the persistence change, not a UI redesign.

**Types** (`frontend/types/algo-test.ts`): doc comments on `lifecycle`/`compiledStrategy`/`strategyHash`/`analytics` updated to state the new, correct reopen guarantee, replacing the P4.3-era "not persisted" language.

## 2. A real, disclosed finding: AI-compiled `strategyHash` is not yet reproducible across separate compilations

While proving "identity survives repeated runs" (an explicit acceptance criterion), the new test suite surfaced a genuine, pre-existing architectural fact, not introduced by P4.5: `compileAIStrategyToIR()` (`at24-quant-engine/src/runtime/strategy-ir/ai-compiler.ts`) assigns every AI compilation a fresh `identity.strategyId` of the form `ai-${userId}-${compiledAt}` — a real timestamp, unique per call. This lands in `StrategySpec.identity.strategyId`, a field `computeSemanticStrategyHash()` does **not** strip (only `spec.metadata` is excluded — `identity` is semantic content, by the same rule that makes a registry strategy's own `strategyId` part of its identity). The practical consequence: **two independent AI compilations of byte-identical trading logic get different `strategyHash` values today**, because their `identity.strategyId` differs even though everything that actually governs execution (indicators, entries, exits, risk) is the same.

This is real, verified with a direct test (`validate-algo-test-identity-persistence.ts`), and deliberately **not fixed in P4.5** — changing how the AI compiler assigns identity is a compiler-boundary decision (should two identical natural-language requests, submitted independently, be considered "the same strategy"? that's a product question, not a bug fix) explicitly outside this phase's bounded persistence-only scope. The registry path is unaffected: `strategyId` there is a fixed, stable label ("golden", "ref-ema-crossover") assigned once in the registry, never regenerated per call, so registry-strategy identity is genuinely reproducible across repeated runs today (proven directly).

**Practical implication for the roadmap this unblocks**: a future run-history/library/optimization feature that groups by `strategyHash` will correctly group repeated runs of a *registry* strategy, but will **not** currently group two separate AI-compiled runs of "the same" natural-language strategy unless that identity scheme changes first. This is worth resolving before P4.8 (Strategy Library) is built for AI-compiled strategies specifically, but is out of scope here.

## 3. Tests

New file: `frontend/scripts/validate-algo-test-identity-persistence.ts`, 9 tests, all offline (no live network, no live Postgres — the same fake-Prisma-at-the-boundary technique `validate-ai-run-backtest-wiring.ts` established):
1. Registry-path reproducibility at the engine level: same strategy + same override, twice → same hash.
2. Registry-path parameter sensitivity: same strategy, different override → different hash (strategyHash is finer-grained than the pre-existing `strategyId`/`strategyVersion` pair).
3. The write actually lands on the persisted row (read back directly from the fake DB, not trusted from the function's own return value).
4. Reopen reconstructs all three fields from the persisted row.
5. A simulated pre-P4.5 row (all three genuinely `null`) reopens with all three honestly `undefined` — analytics (P4.4, independent mechanism) still recomputes correctly regardless.
6. The AI-compiled non-reproducibility finding (§2 above), documented as a passing, intentional assertion of real current behavior.
7. Registry-path reproducibility proven through the actual persisted-row write/read path (two rows, deliberately shared hash, both round-trip correctly).
8. Changing AI-compiled parameters produces different persisted hashes on both rows.
9. `listAlgoTestRuns` carries `strategyHash` correctly, including grouping two rows that share one hash, and correctly excludes the legacy row.

One existing test updated: `validate-algo-test-analytics.ts`'s own P4.4 reopen test asserted `lifecycle`/`compiledStrategy` stay `undefined` on reopen — that was the P4.3 gap this phase closes, so the assertion was corrected to expect (and verify byte-for-byte) that they now round-trip, exactly as the new P4.5 suite proves independently.

## 5. Known limitations (disclosed, not silently worked around)

- **The migration has not been applied to any real database.** `prisma migrate deploy` against the actual target database is a required manual step before this reaches production — never `prisma migrate dev` or `prisma db push` in this repo (see §1).
- AI-compiled `strategyHash` is not reproducible across separate compilations of equivalent logic, for the reason and by the design tradeoff disclosed in §2 — a real, pre-existing fact this phase surfaced and documented, not fixed.
- `lifecycle`/`compiledStrategy` are intentionally excluded from `listAlgoTestRuns`' summary view (heavy JSON, no current consumer needs them there) — only `strategyHash` was added to that view.
- `validate-algo-test-service.ts` (a pre-existing, live-network-only script) was not affected by this phase and was not executed live, consistent with every prior phase this session (no reachable network in this sandboxed environment).
- No run-history UI, no strategy library, no optimization — all explicitly out of scope per the locked roadmap; this phase only lays the persistence groundwork those phases will build on.
