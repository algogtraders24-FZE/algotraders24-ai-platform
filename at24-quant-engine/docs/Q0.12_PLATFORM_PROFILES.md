# Q0.12 — Platform Profiles (MQL4/MQL5/Pine/NinjaTrader/cTrader/AT24)

Full per-field detail lives in `domain/strategy-ir/platform-matrix.ts`'s `PLATFORM_SEMANTIC_MATRIX` (Q0.7, extended this sprint with `pendingOrderFill` — see `docs/Q0.12_PENDING_ORDER_FILL.md`). This document summarizes each platform's order-modification-relevant semantics specifically (Q0.12.8-12), reusing Q0.4's own real, cited research — never inventing platform behavior.

## MQL4 (Q0.12.8)

`OrderModify(ticket, price, stoploss, takeprofit, expiration, [color])` modifies a pending order's price/SL/TP/expiration in one call — MQL4 has no Order/Deal/Position separation (flat ticket model), so "order modification" and "position modification" are the SAME call for an already-filled ticket's SL/TP. `OrderDelete(ticket)` cancels a pending order (distinct from `OrderClose()`, which closes a filled position). Pending order types: `OP_BUYLIMIT`/`OP_SELLLIMIT`/`OP_BUYSTOP`/`OP_SELLSTOP` (Q0.11's own mapping, unchanged). Expiration is a `datetime` argument on `OrderSend`/`OrderModify` — MQL4's own `TIMESTAMP`-kind equivalent.

## MQL5 (Q0.12.9)

`CTrade::OrderModify(ticket, price, sl, tp, type_time, expiration, stoplimit)` modifies a PENDING order. `PositionModify(ticket_or_symbol, sl, tp)` is the explicitly SEPARATE call for an OPEN position's protective levels — MQL5's Order→Deal→Position three-stage separation makes this distinction structural, not just conventional (unlike MQL4). `OrderDelete(ticket)` cancels a pending order. This maps directly onto Q0.12.30's own separation: `OrderModify` ≈ this sprint's `OrderModificationIntent`; `PositionModify` ≈ Q0.10's `PositionManagementInstruction` — MQL5's own API already keeps these two concepts apart, which is exactly why AT24's contract does too.

## Pine / TradingView (Q0.12.7)

Pine has no direct "modify a pending order" primitive in the same sense — `strategy.entry()`/`strategy.order()` calls with the SAME `id` on a later bar effectively REPLACE the prior pending request (Pine's own OCA-like id-based semantics), closer in spirit to this sprint's `REPLACE` than to `MODIFY_*`. `strategy.cancel(id)`/`strategy.cancel_all()` cancel pending orders by id. `process_orders_on_close`/`calc_on_order_fills` (already documented in the base platform matrix) govern WHEN a modification-equivalent call is even evaluated relative to bar close — a real, cited timing subtlety AT24 does not attempt to replicate (AT24's own Step 0.5/Step 1 ordering is its own explicit, documented rule, not an attempt to match Pine's).

## NinjaTrader (Q0.12.10)

`SetStopLoss`/`SetProfitTarget` calls issued on a later bar with the SAME signal name update the existing protective order (NinjaScript's own "same name = modify" convention, again closer to REPLACE-by-identity than an explicit modify call). Explicit cancellation is via `CancelOrder(order)`. No parser was built — documented as a semantic reference only, per Q0.12.10's explicit instruction.

## cTrader (Q0.12.11)

`Position.ModifyStopLossPrice`/`ModifyTakeProfitPrice` for open positions; `PendingOrder.ModifyLimitPrice`/`ModifyStopPrice` (cAlgo API) for still-pending orders — cTrader's Position/PendingOrder split (already documented in the base matrix) makes this the same structural separation MQL5 has. `PendingOrder.Cancel()` cancels. Bid/ask-native pricing (documented `bidAskRequirement: REQUIRED`) means a cTrader pending-order's reference price for directional validation would be the LIVE bid/ask, not a bar close — a real, cited divergence from AT24's own OHLCV-only reference price (`bar.close`, used in `validateOrderModification`'s calls from both simulation engines).

## AT24-native (Q0.12.12) — the reference profile

Fully deterministic, explicit assumptions, no hidden platform behavior (Q0.12.12's own requirement): `OrderModificationIntent` + `validateOrderModification` + `applyOrderModification` (this sprint) is the ENTIRE mechanism — no broker-side timing, no undocumented tick generation, no live bid/ask. Every modification's reference price is the bar's own `close` (D1) or child bar's `close` (D2/D3) — explicit, deterministic, and identical across fidelity tiers for the SAME declared modification (`test/q12-fidelity-integration.test.ts`).
