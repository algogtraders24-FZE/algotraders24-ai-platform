# Q0.11 — Order & Entry Execution Failure Catalog

20 failure modes, each proven in `test/q11-failure-catalog.test.ts` against the real function that must reject it — never a description of intended behavior.

| # | Failure | Guarded by | Behavior |
|---|---|---|---|
| 1 | Invalid order type | `validateStrategyIR`'s `KNOWN_ORDER_TYPES` check | Rejects an unrecognized `executionType` string |
| 2 | Missing price | `validateStrategySpec`'s executionType-vs-price checks | LIMIT/STOP/STOP_LIMIT without the required `limitPrice`/`stopPrice` fails validation |
| 3 | Invalid limit price | `validatePriceReference` | An `ATR_OFFSET` with `atrMultiple <= 0` is rejected |
| 4 | Invalid stop price | `validatePriceReference` | An `ATR_OFFSET` with `atrPeriod <= 0` is rejected |
| 5 | Wrong directional price | `resolveLimitFill`'s own defined rule | A limit placed on the "wrong" side of the market still resolves deterministically (fills at the favorable current price), never crashes or is silently ignored |
| 6 | Stop-limit trigger without fill | `simulation-engine.ts`'s TRIGGERED-state + end-of-run expiry | The order expires with zero trades; the trigger stays visible (`ORDER_TRIGGERED` event) |
| 7 | Gap-through | `resolveLimitFill`/`resolveStopFill` | Fill price is never assumed to equal the trigger/limit level when a bar gaps past it |
| 8 | Same-bar ambiguity | `resolveProtectiveExit` | Both SL and TP reachable in one bar resolves conservatively (stop-loss), flagged `ambiguous: true` |
| 9 | Future-bar leakage | Step ordering (Step 1 processes only bars up to the current index) | A pending order's fill decision made using bars 0-N is identical regardless of what bar N+1 contains |
| 10 | Illegal lifecycle transition | `transitionOrder`'s `VALID_TRANSITIONS` guard | A terminal order (`FILLED`) throws rather than accepting a further transition |
| 11 | Duplicate fill | `buildDecision`'s new `hasPendingOrder` check (Q0.11's own fix) | Exactly one order is ever created while a pending LIMIT/STOP remains unfilled, even across many bars where the entry condition stays true |
| 12 | Phantom position | The same `hasPendingOrder` fix + fill-model correctness | No position exists unless a real `ORDER_FILLED` event actually occurred |
| 13 | Cancel-after-fill | `transitionOrder` | `FILLED → CANCELLED` throws |
| 14 | Expiry-after-fill | `transitionOrder` | `FILLED → EXPIRED` throws |
| 15 | Partial-fill accounting error | Absence of any partial-fill-producing code path (Q0.11.26's own instruction) | Every fill is all-or-nothing; there is no partial quantity to ever miscount |
| 16 | Netting collision | `hasPendingOrder`, direction-agnostic | A pending order of ANY direction blocks a new entry of either direction until it resolves |
| 17 | Pyramiding violation | `hasOpenPosition` (Q0.5, unmodified) | A new entry is never evaluated while ANY position is open, regardless of the new entry's order type |
| 18 | Risk rejection | `evaluateRisk()`'s existing size/geometry checks (Q0.3, unmodified) | A LIMIT/STOP entry failing risk validation is rejected before any order is created |
| 19 | Source fidelity mismatch | The eligibility gate's ATR-period/price-reference checks (Q0.10/Q0.11) | An `UNSUPPORTED` price reference or an undeclared-ATR-period rule is `BLOCKED`, never silently executed |
| 20 | Platform semantic mismatch | `computeCrossPlatformSemanticHash` (Q0.8, unmodified) | A genuinely different order type (STOP vs. LIMIT) never hashes the same across platforms, even though equivalent orders of the SAME type do |

See `docs/Q0.11_ORDER_SEMANTICS.md` for the two real, previously-undiscovered gaps this catalog's own construction surfaced and fixed: item 11/12's `hasPendingOrder` duplicate-order protection (needed the moment a non-MARKET order could remain pending across bars for the first time), and the D2/D3 mirror documented in `docs/Q0.11_GAP_EXECUTION.md` (found while proving item 9's future-bar-leakage guarantee holds under every fidelity tier, not just D1).
