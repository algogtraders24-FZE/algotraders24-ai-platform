# Q0.13 — MQL5 Pending-Order-Management Mapping

## Detected call shapes

| Source pattern | `functionName` | `targetArgIndex` | `priceArgIndex` | `expirationArgIndex` |
|---|---|---|---|---|
| `trade.OrderModify(ticket, price, sl, tp, type_time, expiration, stoplimit)` | `"CTrade.OrderModify"` | 0 | 1 | 5 |
| `trade.OrderDelete(ticket)` | `"CTrade.OrderDelete"` | 0 | — | — |
| `trade.PositionModify(symbol_or_ticket, sl, tp)` / bare `PositionModify(...)` | `"CTrade.PositionModify"` / `"PositionModify"` | 0 | — | — |
| `trade.PositionClose(symbol_or_ticket)` / bare `PositionClose(...)` | `"CTrade.PositionClose"` / `"PositionClose"` | 0 | — | — |

`isMethodCall` (a `MemberExpression` callee, e.g. `trade.OrderModify`) selects the `"CTrade."`-prefixed `functionName`; a bare call selects the un-prefixed one — both `PositionModify`/`PositionClose` genuinely exist as both a raw MQL5 built-in AND a `CTrade` method, so both forms are recognized. **`OrderModify`/`OrderDelete` have no bare-function form in MQL5** — `classifyPendingManagementCall` still recognizes a hypothetical bare `OrderModify(...)`/`OrderDelete(...)` call the same way it does for MQL4 (the detector is dialect-agnostic by design, matching every other detector in this file — see `Q0.13_EXISTING_ARCHITECTURE_AUDIT.md`), which is harmless: no real MQL5 source would ever emit that shape.

**The MQL4/MQL5 argument-offset difference that matters**: `OrderModify`'s `expiration` argument sits at index 4 in MQL4 but index 5 in MQL5 (MQL5 inserts `type_time` at index 4 first) — `classifyPendingManagementCall` hard-codes this distinction per `functionName`, never a shared offset table (Q0.13's own "never assume MQL4 and MQL5 are equivalent" rule, made concrete).

## Target resolution

Identical structural rule to MQL4 (`resolvePendingOrderTarget()` is dialect-agnostic): a plain identifier resolves `TICKET`; `_Symbol`/`Symbol()`/a string literal resolves `SYMBOL`; anything else resolves `UNKNOWN`. MQL5's `ticket_or_symbol` argument is genuinely polymorphic (accepts either), so this is not an approximation — it is a correct, direct mapping of MQL5's own API shape.

## Condition resolution — a real, documented limitation

The SAME two shapes as MQL4 apply structurally (`resolveOrderTypeFilter`/`resolveFavorableTriggerDistance`), but `resolveOrderTypeFilter`'s `isTypeQuery()` helper only recognizes `OrderType()` (MQL4-native) or `PositionGetInteger(POSITION_TYPE)` (a POSITION query, not a pending-order one) as the left/right operand of an order-type comparison. **It does NOT recognize `OrderGetInteger(ORDER_TYPE)`** — the idiomatic MQL5 way to read a SELECTED PENDING order's own type. A real MQL5 EA using `if(OrderGetInteger(ORDER_TYPE)==ORDER_TYPE_BUY_STOP)` resolves this importer's condition to `UNKNOWN`, not `ORDER_TYPE_FILTER` — honestly unresolved rather than silently guessed, but a genuine coverage gap. **Documented here explicitly and named as the top Q0.14 recommendation** (see the final report) rather than hidden.

Fixture `mql5-18-ctrade-ordermodify-executable` (`test/fixtures/q13-mql-fixtures.ts`) demonstrates the mechanism using `OrderType()` directly (syntactically valid in any dialect this importer parses, even though a real MQL5 EA would more idiomatically write `OrderGetInteger(ORDER_TYPE)`) — proving the COMPILATION machinery works correctly once a provable condition exists, independent of the coverage gap above.

## Operation resolution

Identical rule to MQL4: only `CTrade.OrderDelete` (→ `CANCEL_PENDING`) and `CTrade.OrderModify` guarded by a provable `ORDER_TYPE_FILTER` with a resolvable price-distance binding (→ `MODIFY_STOP`/`MODIFY_LIMIT`) ever compile into a real operation.

## `PositionModify`/`PositionClose` — detected, distinguished, never compiled

Both are recorded under their own distinct `functionName` (never confused with `OrderModify`/`OrderDelete` — Q0.13's own success criteria 5/6), classified `isPositionLevelCall: true` in `ir-generator.ts`, and marked `INFO`-severity ("this call acts on an OPEN POSITION — Q0.10's own domain") rather than `WARNING` (reserved for genuine gaps). Their `operation.kind` is always `UNKNOWN` — by design, not by failure — since compiling them would duplicate Q0.10's `RiskSpecification.breakeven`/`trailingStop` execution path (Q0.12.30/Q0.13.14's risk/execution boundary).

## Expiration modification — detected, never compiled

`CTrade.OrderModify`'s `expiration` argument (a raw `datetime`, i.e. absolute epoch seconds) IS captured as `newExpirationExpr` whenever it is a non-zero literal, but `toOperationIR` never produces a `MODIFY_EXPIRATION` operation from source at all in this sprint — converting an absolute datetime into Q0.12's `OrderExpirationPolicy.BAR.maxBars` (a bar-COUNT, not a timestamp) requires knowing the execution timeframe's real duration and the CURRENT bar's own timestamp, a resolution this sprint deliberately did not build (Q0.12 itself documented the identical scope boundary: "no strategy-authored expiration-at-creation detection was built"). Proven in `test/q13-mql-detection.test.ts`'s `mql5-19` and `test/q13-failure-catalog.test.ts`'s item 8.
