# Q0.11 — Platform Order Semantic Mapping

## MQL4 (`OrderSend`)

| Source pattern | Canonical `OrderTypeIR` | Detection |
|---|---|---|
| `OrderSend(..., OP_BUY, ...)` / `OP_SELL` | `MARKET` | `cmd?.startsWith("OP_BUY"/"OP_SELL")`, unchanged from Q0.8 |
| `OrderSend(..., OP_BUYLIMIT, ...)` / `OP_SELLLIMIT` | `LIMIT` | Checked BEFORE the `OP_BUY`/`OP_SELL` prefix match (which would otherwise also match them) — new in Q0.11 |
| `OrderSend(..., OP_BUYSTOP, ...)` / `OP_SELLSTOP` | `STOP` | Same precedence fix — new in Q0.11 |

MQL4's `OrderSend` has exactly ONE "price" argument (`args[3]`), reused by the platform itself as either the market reference price or the pending trigger price depending on `cmd` — this importer never overloads its OWN fields the same way: the SAME source expression is recorded into `limitPriceExpr` or `stopPriceExpr` depending on which pending-order kind was detected (`OrderCallSite`, `domain/mql-importer/semantic-model.ts`).

## MQL5 (`CTrade` pending-order methods)

Previously **not detected at all** — Q0.8 only recognized `CTrade.Buy`/`CTrade.Sell` (market orders). Q0.11 adds:

| Source pattern | Canonical `OrderTypeIR` | Argument mapping |
|---|---|---|
| `trade.BuyLimit(volume, price, symbol, sl, tp, ...)` | `LIMIT` | `args[1]` → `limitPriceExpr` |
| `trade.SellLimit(...)` | `LIMIT` | same shape |
| `trade.BuyStop(volume, price, symbol, sl, tp, ...)` | `STOP` | `args[1]` → `stopPriceExpr` |
| `trade.SellStop(...)` | `STOP` | same shape |
| `trade.BuyStopLimit(volume, price, stoplimit, symbol, sl, tp, ...)` | `STOP_LIMIT` | `args[1]` → `stopPriceExpr`, `args[2]` → `limitPriceExpr` |
| `trade.SellStopLimit(...)` | `STOP_LIMIT` | same shape |

`findOrderDirectionIn()` (used by the shared entry-condition detector) was extended to recognize all six methods — a real gap found while building this: an `if` statement whose ONLY order call was e.g. `g_trade.BuyStop(...)` would otherwise never be recognized as a provable entry condition at all, forcing the honest-but-unnecessary `UNREPRESENTABLE_CONDITION` fallback even though the pattern IS provable (see `test/q11-mql-platform-fixtures.test.ts`).

## MQL4/MQL5 dialect parity (Q0.11.15)

`computeCrossPlatformSemanticHash()` (Q0.8, unmodified) already excludes platform-identity fields — an equivalent MQL4 `OP_BUYSTOP` and MQL5 `CTrade.BuyStop` strategy hash identically once reduced to the same canonical `executionType`/`stopPrice`. A genuinely different order type (STOP vs. LIMIT) still hashes differently — the negative control. Both proven in `test/q11-mql-platform-fixtures.test.ts`'s `Q0.11.15` test.

## Pine / TradingView (research only — reusing `docs/Q0.4_PINE_SEMANTICS.md`, no parser built)

- `strategy.entry()` is pyramiding-aware and direction-aware: an opposite-direction entry automatically closes/reverses the existing position (AT24's `REVERSE` semantics, Q0.5/Q0.9, is directly comparable); once the configured pyramiding count is reached, further same-direction calls are **silently ignored, not queued** — a materially different queuing behavior than AT24's own `hasPendingOrder` gate (Q0.11), which BLOCKS rather than drops.
- `strategy.order()` is a lower-level command that ignores pyramiding entirely — net position is simply current ± signed fill quantity. AT24 has no equivalent "raw order, no bookkeeping" primitive; every AT24 entry goes through the SAME risk-gated path regardless of order type.
- **Limit fill assumption — a documented, deliberate AT24 divergence, not an oversight**: Pine's *default* behavior fills a limit order whenever the bar's range simply TOUCHES the level, not necessarily trades meaningfully through it (a stricter opt-in tick-tolerance exists but is not the default). AT24's `resolveLimitFill()` requires genuine strict trade-through (or a favorable gap) as its ONLY behavior, with no lenient mode — matching Pine's stricter opt-in INTENT but making it the unconditional default, consistent with Q0.4's "never silently favorable" mandate. **This is a real semantic difference from Pine's out-of-the-box behavior, not something AT24 replicates.**
- **Bar Magnifier**: TradingView's own mechanism for resolving intrabar order sequencing using real lower-timeframe data, directly analogous to AT24's `BarDetailProvider`/D2/D3 fidelity (Q0.6). Pine's version is plan-gated and capped at 200,000 bars per script, meaning long backtests can silently mix magnified and non-magnified segments within one run — the exact motivating case for AT24 treating `dataFidelity` as a per-result field rather than an assumed run-wide constant (already true since Q0.5/Q0.6).
- **Recalculation semantics**: Pine adds an extra recalculation pass the instant an order fills (`calc_on_order_fills`), capped at ~4 points/bar (O/H/L/C) on historical bars but uncapped per-tick in realtime — a documented, acknowledged source of backtest/live divergence on TradingView's own part. AT24 has no equivalent "recalculate mid-bar" concept at all (Step 4/signal generation runs exactly once per bar, ON_BAR_CLOSE) — this is a genuine, structural difference, not a gap to close.

**Pine behavior is explicitly NOT claimed to be identical to MT4/MT5 or to AT24's own semantics anywhere above** — per Q0.11.16's own instruction, every difference is named, not smoothed over.

## NinjaTrader / NinjaScript (research only, no parser)

NinjaScript's `OrderType` enum (`Market`, `Limit`, `StopMarket`, `StopLimit`) maps directly onto AT24's canonical four (`MARKET`/`LIMIT`/`STOP`/`STOP_LIMIT`) at the naming level — `StopMarket` is NinjaTrader's name for what AT24 (and MQL) call a plain `STOP` order (a stop that fills at market once triggered, as opposed to `StopLimit`'s two-stage behavior). NinjaTrader's documented historical-backtest limitation is that intrabar order resolution defaults to a 4-price (OHLC) model unless real tick or minute data is supplied — the same category of limitation AT24's own D1 vs. D2/D3 fidelity split already exists to make explicit and provenance-visible, rather than a silent constant assumption. This mapping is recorded as a semantic contract only; no NinjaScript AST/parser exists in this package (explicitly deferred, Q0.11.45).

## cTrader / cBot (research only, no parser)

cAlgo's `TradeType`/pending-order API distinguishes `Market`, `Limit`, `Stop`, and `StopLimit` orders with a directly comparable four-way split, and cBots have first-class `Bid`/`Ask` properties available at signal time — a genuinely LIVE bid/ask feed AT24's OHLCV-only simulation model does not have, which is exactly why `PriceReference`'s `BID`/`ASK` kinds are represented but always `UNSUPPORTED`/`BLOCKED` in this package (Q0.11.3) rather than approximated from OHLC. This mapping is documented as a semantic contract only, per Q0.11.18's explicit "do not implement a cTrader parser yet" instruction.

## `PlatformOrderSemantics` (Q0.11.19)

A dedicated new difference-model type was NOT added this sprint — Q0.7 already shipped exactly this shape: `PlatformSemanticProfile` (`domain/strategy-ir/platform-matrix.ts`) and its populated `PLATFORM_SEMANTIC_MATRIX` (all six platforms: MT4/MQL4, MT5/MQL5, TradingView/Pine, NinjaTrader/NinjaScript, cTrader/cBot, AT24-native) already carry `orderModel` (flat-ticket vs. order→deal→position vs. declarative vs. bracket-native vs. collection-based), `intrabar` (bar-magnifier/tick-generation/bid-ask-native differences), and `historicalRealtime` (documented vs. undisclosed backtest-vs-live divergence) fields, each populated with real, cited facts from Q0.4's own platform research — not invented for this sprint. `getPlatformProfile(platform)` is the existing, reusable query function.

What Q0.11 adds, in the prose above, is detail this matrix's existing fields don't carry at the LIMIT/STOP fill-philosophy level specifically (Pine's lenient-touch default vs. AT24's strict trade-through; cTrader's bid/ask-native pending-order pricing vs. AT24's OHLCV-only `BID`/`ASK`-unsupported stance) — a future sprint extending `PlatformSemanticProfile` with a dedicated `pendingOrderFill` field would be the natural, non-duplicating place to formalize it, rather than inventing a parallel type.
