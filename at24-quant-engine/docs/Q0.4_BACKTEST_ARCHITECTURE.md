Q0.4.44 (master pipeline) plus Q0.4.14-39 (the execution/account/portfolio/provenance design that isn't platform-specific research, but AT24's own synthesis, informed by it). **No implementation in Q0.4** — every model below is an interface/contract to be built in Q0.5+.

**Risk Evaluation remains independent from Execution** — the one rule repeated across Q0.3 and this sprint's brief. `evaluateRisk()` (Q0.3) already returns `RiskAction` and stops there; nothing in this architecture merges its logic into the Order Engine or Execution Reality Layer. The Order Engine consumes a `RiskAction` as input and is a wholly separate future module.

## Execution Reality models (Q0.4.14-18)

Each is an interface only — `reality-models.ts` (Q0.2) already reserved `FeeModel`/`SpreadModel`/`SlippageModel`/`FillModel`/`MarginModel`/`LatencyModel` as the behavioral seam; this section names the concrete FUTURE implementations that will satisfy those interfaces, none built here.

**FillModel** implementations (Q0.4.14): `BarFillModel` (D1 fidelity — resolves via `Q0.4_INTRABAR_ENGINE.md`'s conservative/optimistic/heuristic strategies), `IntrabarFillModel` (D2/D3 — Bar Magnification), `TickFillModel` (D4), `BidAskFillModel` (D5), `LiquidityFillModel` (D6, depends on the future `LiquidityModel`), `QueueAwareFillModel` (D7, theoretical ceiling).

**SpreadModel** implementations (Q0.4.15): `FixedSpread` (a constant, explicit value — never an implicit zero, per Q0.2's `costsExplicitlyZero` guard), `HistoricalSpread` (replayed from real bid/ask history), `VariableSpread` (a modeled function of e.g. volatility/session, not raw history), `BidAskSpread` (direct bid/ask series difference — the ground truth when D5 data exists), `SyntheticSpread` (an explicitly-labeled approximation when no real spread data exists — must never impersonate `HistoricalSpread`), `SessionDependentSpread` (varies by trading session, informed by MT5's researched fixed-per-minute-bar spread limitation in `Q0.4_PLATFORM_R&D.md` — AT24's `SessionDependentSpread` is the adopted improvement over that limitation, see `Q0.4_ADOPT_IMPROVE_AVOID_INVENT.md`).

**SlippageModel** implementations (Q0.4.16): `Zero` (explicit, never implicit), `Fixed`, `Percentage`, `VolatilityBased`, `VolumeShare`, `LiquidityBased`, `MarketImpactBased`, `Stochastic`. **Stochastic models must use a deterministic seed** — the seed itself becomes part of a result's Provenance (below), so "the same input twice" still reproduces exactly, even when the model's underlying distribution is randomized in concept. This directly satisfies Q0.4.39's Deterministic Replay requirement without banning randomness as a MODELING tool, only as an UNREPRODUCIBLE one.

**FeeModel** implementations (Q0.4.17): `PerTrade`, `PerLot`, `PerUnit`, `Percentage`, `Notional`, `Tiered` (volume-based fee brackets), `MakerTaker` (distinct rates for liquidity-adding vs liquidity-taking fills — relevant once `QueueAwareFillModel`/exchange-style execution exists). **Fees stay independent from fill logic** — a `FillModel` decides IF and AT WHAT PRICE an order executes; a `FeeModel` is applied afterward, purely as a function of the resulting fill's size/notional, never influencing whether/where the fill happened.

**LatencyModel** implementations (Q0.4.18), separated into four distinct stages (a single lumped "latency" number, as informally used by most researched platforms, hides which stage actually caused a delay): `SignalLatency` (time from market event to strategy decision — relevant once `ON_EVERY_TICK`-class async processing is modeled), `SubmissionLatency` (decision to order-submitted), `BrokerLatency` (submission to broker acknowledgment — directly informed by MT5's researched Random/Fixed Delay tester settings, `Q0.4_PLATFORM_R&D.md`), `FillLatency` (acknowledgment to actual fill). Each stage independently supports `ZERO`, `FIXED`, or `DISTRIBUTION` (a statistical delay model) — `DISTRIBUTION` is subject to the same deterministic-seed rule as `Stochastic` slippage above; no genuinely nondeterministic implementation is ever permitted.

## Margin / Buying Power (Q0.4.19)

Explicit, separate concepts — **kept structurally apart from `RiskSpecification`** (a strategy's OWN risk policy, Q0.2/Q0.3) since these describe the ACCOUNT's capacity, not the strategy's intent:

`Balance` (cash, unaffected by open positions' floating P&L), `Equity` (`Balance` + unrealized P&L), `Margin` (capital currently locked by open positions), `FreeMargin` (`Equity - Margin`, available for new positions), `InitialMargin` (required to OPEN a position), `MaintenanceMargin` (required to KEEP a position open — can be lower than `InitialMargin`), `Leverage`, `BuyingPower` (a derived, instrument/leverage-aware capacity figure, not simply `FreeMargin` — different instruments can consume margin at different rates), `MarginCall` (a threshold event, not a hard stop — informed by MT5's researched `ACCOUNT_MARGIN_CALL_LEVEL`, `Q0.4_PLATFORM_R&D.md`), `Liquidation` (forced position closure, informed by MT5's researched Stop Out Level behavior, including its "largest losing position first" documented convention).

## Settlement (Q0.4.20)

Interface only: instant settlement (most FX/CFD retail conventions) vs. delayed settlement (T+1/T+2 for many cash-equity/ETF conventions — LEAN's researched explicit settlement-delay modeling, once the LEAN research agent's findings land, will inform whether this needs asset-class-specific defaults). Distinguishes `realized cash` (settled, spendable) from `unsettled proceeds` (realized on paper, not yet available) — this is `Q0.4_BACKTEST_FAILURE_CATALOG.md` item 21's direct target: a backtest that lets a strategy immediately reuse unsettled proceeds is overstating real capital efficiency. Financing/overnight costs (swap/rollover) are a related but distinct concept — a recurring cost applied to positions held across a settlement/rollover boundary, reserved here, not implemented.

## Brokerage Model (Q0.4.21)

A future abstraction bundling `BrokerRules` (which order types/fill policies a simulated broker supports — not every broker supports every `ORDER_TYPE_*`, per the MT4-vs-MT5 stop-limit gap researched in `Q0.4_PLATFORM_R&D.md`), `TradingHours`, `OrderRules` (min/max size, tick size), `MarginRules`, `FeeRules`, `ExecutionRules` (which `FillModel`/`LatencyModel` combination that broker's realistic behavior implies). **No broker API dependency** — a `BrokerageModel` is a configuration bundle for the simulator, informed by research (e.g. "model MT5-hedging-account-like behavior"), never a live connection.

## Market Impact (Q0.4.22) and Liquidity (Q0.4.23)

Reserved, undesigned-in-detail: a future `MarketImpactModel` would take order size, market volume, liquidity, spread, volatility, participation rate, and depth as inputs and return an expected adverse price impact. A future `LiquidityModel` (kept a SEPARATE interface from `FillModel`, per the sprint's explicit instruction) would answer "how much of this order can actually fill, and at what queue position" — `LiquidityFillModel`/`QueueAwareFillModel` (above) would consume a `LiquidityModel`'s output rather than compute liquidity themselves, preserving the same separation-of-concerns discipline already established between `RiskSpecification`/`RiskEvaluation`/Execution (Q0.3).

## Position Model (Q0.4.24)

Extends Q0's existing `Position` contract (unchanged in Q0.4) with the operations a real position lifecycle needs: `LONG`/`SHORT` direction (already present), `quantity`, `averagePrice` (volume-weighted, recomputed on every scale-in), `realizedPnl`/`unrealizedPnl` (split, not a single blended number — matches LEAN's researched Portfolio/Holdings convention, pending confirmation from the LEAN research agent), `fees` (accumulated, separate from P&L so gross vs. net performance stays distinguishable), `entryTime`/`exitTime`. Position-management OPERATIONS — scale-in, scale-out, partial close, pyramiding, hedging, netting — are not new fields on `Position` itself; they are OrderEngine-level operations that each produce a state transition on an existing `Position` or open/close one, governed by the account's Position Accounting Mode (below), directly informed by the MT4/MT5 researched netting-vs-hedging distinction (`Q0.4_PLATFORM_R&D.md`) — this is treated as a first-class, explicit, account/portfolio-level configuration, never an unstated assumption.

## Account Model (Q0.4.25)

```
Account
 |- Balance
 |- Equity
 |- Margin
 |- FreeMargin

```

Kept structurally separate from `RiskSpecification` (a strategy's policy), `Position` (one position's state), and `Portfolio` (below, the aggregate across positions/strategies) — `Account` is the CAPITAL container everything else draws against.

## Portfolio Model (Q0.4.26)

Future support for multiple symbols, multiple strategies, multiple concurrent positions, capital allocation across them, aggregate exposure, correlation, and portfolio-level risk — this is exactly the Portfolio Risk boundary Q0.3.22 already reserved (`domain/portfolio-risk-boundary.ts`: `ExposureContext`, `PortfolioDrawdownContext`, `RiskBudget`). Q0.4 does not extend those interfaces further; it places them correctly in this larger pipeline, confirming they sit between `Position`/`Account` and `Trade Ledger`.

## Multi-Timeframe Engine (Q0.4.27)

Exact availability semantics, generalizing Q0.4.6's calculation-timing table and `Q0.4_LOOKAHEAD_REPAINTING.md`'s HTF-leakage design commitment: an observation on timeframe X becomes available to any OTHER timeframe's evaluation only at the instant X's bar closes — never earlier, regardless of whether the reader is on a higher or lower timeframe than X. Q0.4.2's `request.security()` research (once it lands) is the direct precedent this generalizes from — Pine's own `lookahead_off`/`lookahead_on` distinction is exactly the "correct vs. leaking" choice this rule forecloses at the architecture level rather than leaving as a per-call parameter a strategy author could get wrong.

## Multi-Symbol Synchronization (Q0.4.28)

When symbols have different tick frequencies, different sessions, different timestamps, or different holiday calendars, or when one symbol has missing data at a moment another does: the event queue (`Q0.4_EVENT_MODEL.md`'s `(timestamp, sequence)` total order) is the single mechanism that keeps this deterministic — every symbol's events interleave into ONE ordered stream, so "what was known when" has one unambiguous answer regardless of how ragged the underlying data is across symbols. **Never silently forward-fill unavailable information** — if symbol B has no observation at the timestamp symbol A just produced one, a future engine must represent that explicitly (an `undefined`/absent observation for B at that instant), never synthesize a same-as-last-known value and present it as real. This directly extends `Q0.4_BACKTEST_FAILURE_CATALOG.md` item 23 (stale quotes) to the multi-symbol case.

## Session / Calendar Engine (Q0.4.29)

Timezone, DST, sessions, overnight sessions, market breaks, and holidays — per-instrument, never a single global assumption (an equity's NYSE calendar and a forex pair's broker-server-time convention are genuinely different systems, per the MT4/MT5 research's own broker-server-time findings). **Never uses the machine's local timezone** — extends Q0.3's already-established `Intl.DateTimeFormat`-with-explicit-IANA-zone discipline (`runtime/risk/session.ts`) to the full calendar engine, not just entry-session gating.

## Research Modes (Q0.4.30)

| Mode | Speed | Data requirement | Execution assumptions | Fidelity ceiling |
|---|---|---|---|---|
| `FAST_OHLC` | fastest | D1 (OHLC only) | Conservative intrabar resolution (`Q0.4_INTRABAR_ENGINE.md`) | D1 |
| `INTRABAR` | moderate | D2/D3 (lower-TF via Bar Magnification) | Reconstructed intrabar path | D2/D3 |
| `LOWER_TIMEFRAME` | moderate-slow | explicit lower-TF series supplied | Direct replay of the supplied series | D2/D3 |
| `TICK` | slow | D4 | Full tick replay | D4 |
| `BID_ASK` | slowest of the realistic modes | D5 | Full bid/ask replay, spread-aware fills | D5 |
| `DEPTH` | slowest, and least realistically available | D6 | Order-book-aware fills | D6 (rarely reachable) |
| `MICROSTRUCTURE` | theoretical | D7 | Queue-aware | D7 (research ceiling, not expected to ship) |
| `STRESS` | varies | any | deliberately worsened assumptions (wider spread, higher slippage/latency, reduced liquidity) applied on top of whichever base mode — an explicit robustness tool, not a "more realistic" mode | inherits the base mode's fidelity, explicitly labeled as stressed |

## Deep Backtesting (Q0.4.31)

| Mode | Meaning |
|---|---|
| `QUICK` | a short, fast-iteration range for early research |
| `FULL_RANGE` | the complete available history for the dataset |
| `DEEP_HISTORY` | intentionally extends beyond what a platform's default/free data tier offers — directly inspired by TradingView's researched Deep Backtesting concept (once the Pine research agent's findings confirm specifics, this row will be refined) |
| `CUSTOM_RANGE` | an explicit, user-chosen window |
| `CHUNKED_RESEARCH` | a long range processed in bounded chunks (memory/performance discipline for very long histories or tick-level data), reassembled into one continuous result |

Every result, regardless of mode, records exact `dataset`, `range`, `dataVersion`, and `runtimeVersion` — see Provenance below; this is not a separate requirement per mode, it is the same Provenance block every result already carries.

## Cross-Fidelity Testing (Q0.4.32)

The SAME `StrategySpec` + parameters + instrument + date range must be runnable, unmodified, under every Research Mode above, and the resulting `BacktestResult`s compared on: trade count, win rate, profit factor, net P&L, max drawdown, Sharpe (once implemented — reserved per Q0.2's `ReservedMetricName`), exposure, and — critically — WHERE the execution assumptions themselves diverged (not just where the outcome numbers diverge, but which specific fills/orders differed and why, traceable back to the Intrabar Engine's resolution strategy used in each mode). This is the direct, formalized generalization of Q0.1's own finding (the OLD engine's `compare_engines.py`, which discovered a ~9x drawdown divergence between its coarse and MTF-replay engines for the identical spec) — Cross-Fidelity Testing is AT24's answer to "how do we know fidelity actually matters for THIS strategy," made a first-class, repeatable capability rather than an ad hoc one-off comparison script.

## Cross-Platform Semantic Comparison (Q0.4.33)

Future capability: the same strategy LOGIC (via the Strategy IR), reduced separately under each researched platform's OWN documented execution semantics (MT4-style ticket-based hedging, MT5-style netting-OR-hedging, Pine-style next-bar-open-unless-configured, NinjaScript-style `Calculate` modes, cBot-style tick-native, LEAN-style pluggable fill models, Backtrader-style next-bar-open-with-labeled-cheat-flags) vs. AT24's own semantics, compared on signals/orders/fills/positions/P&L, producing a `PlatformDiscrepancyReport`. This is architecture only — no comparison engine exists yet; it depends on the Strategy IR (Q0.4.4) and a translator (explicitly not built) existing first.

## Source Fidelity (Q0.4.34)

`EXACT` / `SEMANTICALLY_EQUIVALENT` / `APPROXIMATE` / `UNSUPPORTED` — already defined in `Q0.4_STRATEGY_IR.md`'s Relationship to Source Fidelity section; repeated here only to confirm its place in the pipeline: it is a property of the Strategy IR → StrategySpec reduction step, consumed by `PlatformDiscrepancyReport` (above) and by the Execution Reality Grade (below) as one of its inputs. **Never claim `EXACT` without deterministic evidence** — i.e. a passing differential-replay test (same pattern as `Q0.4_LOOKAHEAD_REPAINTING.md`'s detection strategy #2) comparing the translated AT24 execution against the source platform's own documented/observed behavior for that specific construct, not an assumption based on the translation "looking right."

## Execution Reality Grade (Q0.4.36)

```
ExecutionRealityGrade: A | B | C | D | E | INSUFFICIENT_DATA
```

Computed from: `DataFidelity` (`Q0.4_INTRABAR_ENGINE.md`), bid/ask availability, spread-model quality (real historical vs. fixed vs. synthetic), which `SlippageModel`/`FeeModel`/`LatencyModel`/`FillModel` were used (an explicit `Zero`/`Fixed` choice is graded differently from a data-driven one — but `Zero` is never silently assumed, per Q0.2's existing guard, so a grade always reflects a DELIBERATE choice, not an omission), liquidity/market-impact modeling presence, whether intrabar ambiguity was resolved via Conservative/Optimistic/Heuristic/Reconstruction/Replay/Unresolved (`Q0.4_INTRABAR_ENGINE.md`'s 7-way classification — `Optimistic` or `Unresolved` results cap the grade low, structurally), Source Fidelity (above), and lookahead status (a detected/possible lookahead issue is disqualifying, not merely grade-lowering — informed by `Q0.4_LOOKAHEAD_REPAINTING.md`), and synthetic-data status (`Q0.4_INTRABAR_ENGINE.md` — a `SYNTHETIC_PRICE` execution basis caps the grade regardless of everything else).

**Execution Reality Grade is NOT Profit Probability, NOT Strategy Quality, and NOT AI Confidence** — repeated here because it is the sprint's own explicit, load-bearing distinction. A grade of `A` says "this result's execution assumptions are highly realistic and well-evidenced"; it says NOTHING about whether the strategy is good, profitable, or should be traded. Keeping these three concepts separate is what prevents Execution Reality Grade from becoming a disguised trust/validation signal — which would violate ADR-004/ADR-006 (AI/execution realism cannot substitute for M-Series' actual Evidence/Validation/Trust chain).

## Statistical Robustness Boundary (Q0.4.37)

Three separate concepts, not to be conflated:

- **Execution Reality** (above) — did the SIMULATION realistically model what would have happened.
- **Statistical Robustness** — GIVEN a realistic simulation, is the observed result likely to hold up out-of-sample, or is it a statistical artifact of overfitting to one dataset/parameter choice. Future systems: Walk Forward, Out-of-Sample holdout, Monte Carlo, Parameter Perturbation, Trade Resampling, CPCV (Combinatorial Purged Cross-Validation) — architecture only, none implemented; this is exactly the category Q0.1's `INTEGRATION_DECISION.md` (from the OLD engine's own prior research) already flagged `robustness.py`'s walk-forward technique as worth reusing at the CONCEPT level for.
- **Strategy Quality** — a judgment call about whether the strategy is fundamentally sound, which belongs to a human/AI-assisted research process informed by both of the above, never computed automatically by either.

A future `ResearchResult` may eventually need fields for both an Execution Reality Grade AND a Statistical Robustness summary — kept as two separate, independently-gradeable fields, never merged into one combined "quality score."

## Provenance (Q0.4.38)

```

ExecutionModel, FillModel, SpreadModel, SlippageModel, FeeModel, LatencyModel, MarginModel, SettlementModel,
```

## Deterministic Replay (Q0.4.39)

Same `Strategy` + `Dataset` + `Configuration` + `Runtime` must reproduce identical Events, Signals, Orders, Fills, Positions, Equity, and Metrics — exactly. This is Q0.2/Q0.3's determinism principle (ADR-008, `Q0.3`'s pure-function `evaluateRisk`) extended across the full pipeline above. No `Date.now()`, no `Math.random()`, no environment-dependent behavior anywhere in the deterministic simulation path — including inside any `Stochastic`/`DISTRIBUTION` model (Q0.4.16/18), which must be seeded, with the seed itself part of Provenance, exactly as this document's Execution Reality models section already specifies. The static-source-scan test pattern Q0.3 established (`risk-determinism.test.ts` scanning for forbidden calls) is the template a future sprint's Order Engine/Execution Reality Layer test suite should reuse and extend.

## What Q0.4 does NOT do

No `FillModel`/`SpreadModel`/`SlippageModel`/`FeeModel`/`LatencyModel`/`MarginModel`/`SettlementModel`/`BrokerageModel`/`MarketImpactModel`/`LiquidityModel` implementation. No Order Engine, no Trade Ledger, no Account/Portfolio runtime code. No Execution Reality Grade computation. No Robustness system. This document is the pipeline and interface contract a Q0.5+ sprint's actual code is measured against — none of it exists in `src/` after Q0.4.
