# Q0.5 Provenance

## Fields recorded from day one (Q0.5.40)

```ts
interface SimulationProvenance {
  strategyHash: string;           // computeSemanticStrategyHash() (Q0.2, reused)
  strategyVersion: string;
  datasetId: string;
  datasetVersion: string;
  dataFidelity: DataFidelityLevel; // always "D1" in Q0.5 (docs/Q0.4_INTRABAR_ENGINE.md's ladder)
  executionModel: string;          // "SimulationEngine-v1"
  fillModel: string;                // "BarFillModel"
  spreadModel: string;               // e.g. "ZeroSpread", "FixedSpread(2)"
  slippageModel: string;
  feeModel: string;
  latencyModel: string;
  initialBalance: number;
  positionAccountingMode: PositionAccountingMode; // always "NETTING" in Q0.5
  runtimeVersion: string;
}
```

Every `SimulationResult` carries exactly one `SimulationProvenance`, computed once at the end of `runSimulation()` from the same `SimulationConfig` that drove the run — never reconstructed after the fact, never approximated. `strategyHash` reuses Q0.2's `computeSemanticStrategyHash()` (excludes `StrategySpec.metadata`, so two structurally-identical strategies with different descriptions/authorship hash identically) — not a new hash function.

This extends, rather than replaces, Q0.2's existing `ResearchExperiment`/`ReproducibilityMetadata` contracts (which already carry `strategyHash`/`strategyVersion`/`datasetId`/`datasetVersion`/`runtimeVersion`/`executionAssumptions`) — `SimulationProvenance` is the concrete, populated instance of what those contracts anticipated; a future sprint building the full `Q0.4_BACKTEST_ARCHITECTURE.md` provenance block (which additionally reserves `SourcePlatform`/`SourceVersion`/`TranslationVersion`/`MarginModel`/`SettlementModel`) will extend this same object, not invent a parallel one.

## Reproducibility guarantee

Every `SimulationResult` is reproducible FROM its `provenance` field alone, GIVEN the same `bars` array and `indicatorSeries` — `test/simulation-e2e-golden.test.ts`'s provenance test asserts every field is populated and non-empty; `test/simulation-failure-catalog.test.ts` item 17 proves two runs with genuinely different configured models (a different `SpreadModel`) produce visibly different provenance AND a different `resultHash` — i.e. provenance is not a decorative label, it actually reflects what was configured, and a mismatch between two runs' provenance reliably predicts a mismatch in their results (and vice versa: item 18 proves a real input change — `initialBalance` — always changes the hash, so the hash is not vacuously constant).

## `resultHash`: the single-equality-check fingerprint

`computeCanonicalHash()` (Q0.2, reused) over every field of `SimulationResult` except `resultHash` itself — a 64-character SHA-256 hex digest. This is what makes Q0.5.36's three-run determinism check and Q0.5.37's replay check reducible to one `assert.equal(a.resultHash, b.resultHash)` rather than a bespoke field-by-field comparison for every future consumer of this contract.

## What Q0.5 does NOT do

No `SourcePlatform`/`SourceVersion`/`TranslationVersion` fields (no Strategy IR/translator exists yet to populate them meaningfully). No `MarginModel`/`SettlementModel` fields (no such models are implemented — see `docs/Q0.5_EXECUTION_MODEL.md`'s Known Limitations). No persistence layer — a `SimulationProvenance` object lives only in memory as part of its `SimulationResult`; storing/querying historical provenance records is a future sprint's concern.
