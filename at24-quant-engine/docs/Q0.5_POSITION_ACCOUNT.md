# Q0.5 Position & Account

## Position model (Q0.5.18)

`src/runtime/simulation/position-engine.ts` — four pure functions operating on Q0's existing `Position` type (`domain/position.ts`), additively extended with `fees?: number` and `lastModifiedTimestamp?: number` (both optional, so the frozen contract stays backward-compatible; see `docs/Q0.3_RISK_ARCHITECTURE.md`-style contract-freeze discipline applied here too).

| Function | Behavior |
|---|---|
| `openPosition()` | creates a new `OPEN` position; rejects non-positive quantity |
| `increasePosition()` | scale-in — recomputes the volume-weighted average entry price (`(oldQty*oldPrice + addQty*addPrice) / totalQty`); requires the position to be `OPEN` and `addQuantity > 0` |
| `reducePosition()` | scale-out / partial close — validates `0 < reduceQuantity <= currentQuantity` (Q0.5.20), throws otherwise; if the full remaining quantity is reduced, the position transitions to `CLOSED` |
| `closePosition()` | `reducePosition()` by the full current quantity — same function, same guarantees |
| `computeUnrealizedPnl()` | direction-aware (`BUY`: `(price - entry) * qty`; `SELL`: `(entry - price) * qty`); always `0` for a `CLOSED` position |

Every function is pure — none mutates its `Position` argument (`test/simulation-position-engine.test.ts`). Realized P&L returned by `reducePosition`/`closePosition` is **GROSS** (before fees) — fees are tracked separately (on both the `Position.fees` accumulator and the `Account`), netted out only at the `Trade`/metrics level, matching the gross/fees/net split the Trade Ledger requires (Q0.5.23).

## Netting vs. Hedging (Q0.5.19): NETTING is the only implemented mode

**Decision**: NETTING — at most one net position per instrument; an opposite-direction fill first reduces/closes the existing position (via `reducePosition`), and any leftover quantity opens a new position in the new direction (a "reversal," matching Pine's documented `strategy.entry()` auto-reverse behavior researched in Q0.4).

**Why**: (1) Q0.5 is explicitly single-instrument, single-strategy scoped — there is no portfolio/multi-ticket concept to hedge against yet. (2) Q0.2/Q0.3's `RiskSpecification` (`maxSimultaneousPositions`, `partialClose`, breakeven/trailing) was designed around a single "the position" concept per instrument, not independently-tracked tickets — netting is the accounting mode those contracts already implicitly assume. (3) MT5's researched default design (`docs/Q0.4_PLATFORM_R&D.md`) was originally netting-only before hedging was added as an alternative — a reasonable, precedented starting point. `PositionAccountingMode` (`domain/simulation/position-accounting-mode.ts`) reserves the `"HEDGING"` value so the type itself doesn't need to change when a future sprint implements it; nothing in the position engine's function signatures assumes NETTING specifically (they operate on one `Position` at a time), so adding HEDGING later is additive, not a rewrite.

## Account model (Q0.5.21/22)

```
Account
 |- balance          (cash, unaffected by open positions' floating P&L)
 |- realizedPnl       (cumulative GROSS P&L from closed/reduced trades)
 |- fees               (cumulative, tracked separately from P&L)
 |- unrealizedPnl        (mark-to-market, recomputed every bar an open position exists)
 |- equity                 = balance + unrealizedPnl
 |- margin                  (always 0 in Q0.5 — no MarginModel wired in yet)
 |- freeMargin                = equity - margin
```

`src/runtime/simulation/account-engine.ts`: `createAccount(initialBalance, asOf)` validates `initialBalance >= 0`. `applyFill(account, grossPnl, fee, timestamp)` updates `balance += grossPnl - fee`, `realizedPnl += grossPnl`, `fees += fee`, then recomputes `equity`/`freeMargin`. `markToMarket(account, unrealizedPnl, timestamp)` recomputes `equity`/`freeMargin` from a fresh unrealized figure WITHOUT touching `balance`/`realizedPnl`/`fees` — the two functions never overlap in what they change, so the accounting identity `balance = initialBalance + sum(grossPnl) - sum(fees)` always holds and is directly tested (`test/simulation-account-engine.test.ts`, `test/simulation-failure-catalog.test.ts` item 8).

**Settlement is instant** (Q0.5.22) — `equity = balance + unrealizedPnl` has no "unsettled obligations" subtraction term at all. This is the `ImmediateSettlementModel` case Q0.4 reserved (`docs/Q0.4_BACKTEST_ARCHITECTURE.md`'s Settlement section); `DelayedSettlementModel` remains unimplemented. No hidden financing/swap cost exists anywhere in Q0.5.

## Trade Ledger (Q0.5.23/24)

`SimulationTrade` (`domain/simulation/trade.ts`) — named distinctly from Q0's own placeholder `Trade` type (`domain/backtest-result.ts`, never implemented, reserved for the future full `BacktestResult`) to avoid a naming collision while keeping both types intact. Fields: `tradeId`, `strategyVersion`, `instrument`, `side`, `entryPrice`/`entryTimestamp`, `exitPrice`/`exitTimestamp`, `quantity`, `grossPnl`, `fees`, `netPnl` (`= grossPnl - fees`), `rMultiple`, `executionMetadata` (which fill/spread/slippage/fee model produced this trade).

`rMultiple` reuses Q0.3's `computeRealizedR()` (`runtime/risk/r-multiple.ts`) directly — **no second R formula was written** (Q0.5.24's explicit instruction). It is `null`, never `0` or `NaN`, when the position had no `stopLoss` (R is undefined without a risk distance; `computeRealizedR` would throw in that case, so `buildTrade()` checks for a stop first rather than swallowing the throw).

`TradeLedger` (`runtime/simulation/trade-ledger.ts`) is append-only: `record()` freezes every `SimulationTrade` via `Object.freeze()` before storing it, and no update/remove method exists at all — a mutation attempt on a returned trade throws (`test/simulation-trade-ledger.test.ts`). `all()` returns a defensive copy, so external code can never corrupt the internal array.
