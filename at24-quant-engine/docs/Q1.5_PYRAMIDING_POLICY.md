# Q1.5.4 — Pyramiding / Position-Limit Policy

## Historical correction (read this first)

`docs/Q1.4_FUTURE_PLATFORM_CONTRACT_CHECK.md` and `docs/AT24_QUANT_ENGINE_MASTER_BLUEPRINT.md` previously stated that `maxEntries`/`maxPositions` were "declared but never enforced anywhere... unlimited accumulation actually happens." **That specific claim is corrected here, based on new evidence from this sprint's own runtime tracing — not merely "still not implemented," but factually inaccurate about pre-Q1.5 behavior.**

**Pre-Q1.5, actual behavior**: `decision-builder.ts`'s `buildDecision()` gated every ENTER decision on `!hasOpenPosition` — unconditionally, with **zero reference to `PyramidingPolicy.allowPyramiding`/`sameDirectionBehavior` anywhere in the call**. Once any position was open, no second ENTER decision was ever generated for that instrument, regardless of policy. `position-engine.ts`'s `increasePosition()` (the actual same-direction accumulation function) existed and was wired into the fill-handling code, but was **genuinely unreachable** from the real per-bar decision pipeline — confirmed by: (a) direct code trace of `buildDecision`'s single boolean gate; (b) grep across the full test suite showing `increasePosition()` was exercised only by `test/simulation-position-engine.test.ts`'s unit-level calls, never by a full `runSimulation()` integration test; (c) `test/q14-future-platform-contract.test.ts`'s own pyramiding test proved only that the numeric cap doesn't affect *eligibility* — it never claimed, and never proved, that accumulation executed.

**Correct statement, pre-Q1.5**: pyramiding was structurally configured in the IR (passed eligibility with `sameDirectionBehavior: "ACCUMULATE"`) but was completely unreachable through the normal simulation decision path — not "unlimited," **zero**.

**Q1.5**: pyramiding becomes genuinely executable when `allowPyramiding: true`, bounded by `maxEntries`.

## Derived semantics

Nothing in the existing IR/tests/docs directly distinguished `maxEntries` from `maxPositions` beyond one comment ("`allowPyramiding: false` with `maxEntries: 1` is the conservative default"). Derived, not assumed, from two architectural facts:

1. `PositionAccountingMode` (`position-accounting-mode.ts`) is **NETTING-only** — HEDGING is a reserved-but-unimplemented value, already blocked at eligibility.
2. `Position` (`position.ts`) is a single object; `position-engine.ts`'s `increasePosition()` always blends same-direction fills into that ONE object. There is no "array of concurrent positions" anywhere in the domain model.

**`maxEntries`** = maximum number of qualifying entry **fills** accumulated into the currently open (netted) position, resetting to 0 when the position returns to flat. Directly matches the doc-comment's own example, and matches Pine's real `pyramiding` input semantics (relevant per Q1.5's Phase-6 cross-platform goal — not yet built this sprint, see Remaining Gaps).

**`maxPositions`** = maximum concurrently open positions. Under NETTING, this is **structurally always ≤ 1 by construction** — the engine physically cannot create a second concurrent position for one instrument today (`increasePosition` always blends into the existing one; the position-engine has no code path that creates a second, separate `Position` object for the same symbol while one is already open). Genuine `maxPositions > 1` runtime enforcement requires HEDGING, not implemented in Q1.5.

## Implementation

### Admission (`decision-builder.ts`)

`buildDecision(signal, hasOpenPosition, hasPendingOrder, pyramiding?: PyramidingAdmission)` — new optional 4th parameter. `PyramidingAdmission = { allowPyramiding, maxEntries?, currentEntryCount, openPositionSide? }`. A pyramid ENTER is admitted only when: signal direction matches the open position's own side (opposite-direction stays reversal's separate, untouched mechanism), no pending order exists, `allowPyramiding === true`, and (`maxEntries` unset, i.e. unbounded — an explicit opt-in — OR `currentEntryCount < maxEntries`). Omitting the 4th argument (every pre-Q1.5 call site untouched, e.g. existing `simulation-position-engine.test.ts` unit calls) preserves byte-identical HOLD-while-open behavior.

### Entry-count tracking (`SimulationState.entryCountByPosition`)

New `ReadonlyMap<string, number>` field, keyed by position id (additive, mirrors `entryBarIndexByPosition`'s established pattern). Set to `1` when `openPosition()` fires; incremented on each `increasePosition()` fill (same id — accumulation never changes a position's id); removed the moment the position fully closes (protective SL/TP, SIGNAL_EXIT, REDUCE_POSITION-to-zero, FORCE_EXIT, or the pre-existing reversal-leg close) — "the counter must not survive a complete position lifecycle." Duplicated identically in both `simulation-engine.ts` (D1) and `multi-fidelity-engine.ts` (D2/D3), following Q0.6's own established "duplicate outer control-flow shape, never a shared mutable engine" convention.

### A separate, independent entry-risk evaluation (Step 5)

`RiskEvaluationInput`'s own contract (`domain/risk-evaluation.ts`) is explicit: **a single input drives either an entry evaluation or a management evaluation, never both**. Rather than bending that frozen Q0.3 contract, a pyramid-entry bar runs **two** independent `evaluateRisk()` calls: the existing management evaluation (using `existingPosition`, unchanged) and a new, separate entry evaluation (using `proposedEntry`, structurally identical to how a flat first entry is evaluated). Both apply through the identical `processRiskInput()` handling code (extracted, not duplicated). `evaluateRisk()` itself is untouched.

### `maxPositions` validation (`strategy-ir.ts`)

`validateStrategyIR` now rejects `maxPositions < 1` and `maxEntries < 1` as invalid configuration (a policy that could never be satisfied by the netting engine's own structural guarantee). `maxPositions >= 1` validates successfully but has no additional runtime effect beyond what NETTING already guarantees.

## What counts, precisely

Only actual fill events increment the counter — the map is written in **exactly one place** in each engine (the `outcome.filled` branch of the order-resolution loop). Rejected orders (risk evaluation returns `REJECT_ENTRY`), cancelled orders, and orders that never fire (condition never true a second time) never reach that code, by construction — not via a special case.

## Evidence

`test/q15-pyramiding.test.ts` (18 tests): `buildDecision` unit tests (allowPyramiding false/true/undefined, cap reached, unbounded, opposite-direction never pyramided, pending-order still blocks); full-simulation integration tests (first/second/third-rejected-at-cap with exact quantity proof via volume-weighted average price, flat-reset-then-fresh-sequence, risk-rejected entry never increments, no-second-signal never increments); `maxPositions`/`maxEntries` IR validation (valid ≥1, invalid 0/negative); NETTING single-position invariant. `test/q15-fidelity-parity.test.ts`: D1/D2/D3 identical trades.

## Verification Closure update

**Newly proven, this sprint** (`test/q15-pending-pyramiding-interaction.test.ts`, `test/q15-adversarial-corpus.test.ts`, `test/q15-intrabar-fidelity.test.ts`):
- Pending orders cannot bypass `maxEntries`/`allowPyramiding` admission — 6 dedicated cases: a valid additional entry admitted; the cap rejecting a third entry even across many bars of a continuously-true signal; `allowPyramiding=false` blocking every subsequent bar; the natural "position open + one order simultaneously pending" window never admitting a competing second order for the same slot (both unit-level `buildDecision` and full-simulation integration proof); a risk-rejected proposal never incrementing the counter; a full flat-reset-then-fresh-cycle after a cap-then-close sequence.
- `maxEntries`/pyramiding admission proven under the REAL (non-empty-provider) D2/D3 intrabar path, not just D1 — see `docs/Q1.5_FIDELITY_PARITY.md`.
- Long-side and short-side pyramiding proven as standalone, symmetric adversarial cases.
- 15 total dedicated adversarial cases (`test/q15-adversarial-corpus.test.ts`), each asserting real ledger/position/execution-statistics outcomes.

**Still not proven** (honest, unresolved — not attempted this sprint):
- Cross-platform (Pine/NinjaScript/cBot) hand-built-IR equivalence check for pyramiding.
- A genuine intrabar scenario where a pyramid fill and a `PendingOrderManagementPolicy` action resolve on the SAME child bar (the two mechanisms remain architecturally independent — pending-order-management only ever modifies/cancels an ALREADY-selected pending order, never creates one — but this has still not been proven with a dedicated combined fixture).
- Performance benchmarking of the admission/counter machinery at scale.
