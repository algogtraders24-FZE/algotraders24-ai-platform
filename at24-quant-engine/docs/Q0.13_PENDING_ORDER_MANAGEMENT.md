# Q0.13 — PendingOrderManagementPolicy Contract

## The three layers, kept genuinely separate (Q0.13.4's own critical rule)

```
PendingOrderManagementPolicy   "what the strategy INTENDS to do"
        (domain/pending-order-management-policy.ts)
              ↓ evaluated per bar, per pending order, by
        evaluatePendingOrderManagementPolicy()
        (runtime/simulation/pending-order-management.ts)
              ↓ produces, only when a condition genuinely holds
OrderModificationIntent        "what the execution engine SHOULD do"
        (domain/simulation/order-modification.ts, Q0.12, UNMODIFIED)
              ↓ consumed by
validateOrderModification() / applyOrderModification()   "HOW that intent changes an order"
        (Q0.12, UNMODIFIED)
```

No type, validator, or evaluator is shared between the Policy layer and Q0.12's Intent layer — a `PendingOrderManagementRule` and an `OrderModificationIntent` look superficially similar (both eventually specify "cancel" or "move a stop") but are never the same object and never validated by the same function.

## Also deliberately separate from Q0.10's `PositionManagementPolicy`

| | `PositionManagementPolicy` (Q0.10) | `PendingOrderManagementPolicy` (Q0.13) |
|---|---|---|
| Acts on | An OPEN `Position` | A still-PENDING `SimulationOrder` |
| Evaluated by | Q0.3's frozen `evaluateRisk()`, via `RiskSpecification.breakeven`/`trailingStop`/`partialClose`/`maxHoldingPeriod` | A new, independent evaluator, `evaluatePendingOrderManagementPolicy()` |
| MQL source shape | `OrderModify`/`PositionModify` changing SL/TP relative to entry/current price | `OrderDelete`/`OrderModify` (pending price)/`CTrade.OrderDelete`/`CTrade.OrderModify` |
| Attaches to | `StrategySpec.risk` | `StrategySpec.pendingOrderManagement` |

A single MQL source file's `OrderModify`/`PositionModify` calls may be recorded by BOTH Q0.10's `ManagementPatternSite` (if the call is inside a favorable-distance-triggered SL/TP-changing `if`) AND Q0.13's `PendingOrderManagementCallSite` (dual-booking is deliberate and safe — see `Q0.13_EXISTING_ARCHITECTURE_AUDIT.md`); they compile into two entirely independent, non-overlapping execution mechanisms.

## The vocabulary (`domain/pending-order-management-policy.ts`)

- **`OrderTargetSpec`** — `kind: "SYMBOL"|"TICKET"|"UNKNOWN"`, plus an optional `orderTypeFilter`/`sideFilter` narrowing WHICH pending order(s) of that target the rule applies to. `provable: false` for `UNKNOWN`.
- **`ManagementCondition`** — `kind: "ALWAYS"|"ORDER_TYPE_FILTER"|"FAVORABLE_DISTANCE"|"UNKNOWN"`. The two provable shapes: an order-type comparison (needs no live value — an order's type is fixed at creation) and Q0.10's own favorable-distance-trigger arithmetic, reused verbatim and applied to a PENDING order's own reference price instead of a position's entry price.
- **`PendingOrderManagementOperation`** — `CANCEL_PENDING | MODIFY_STOP | MODIFY_LIMIT | MODIFY_EXPIRATION | UNKNOWN`. `MODIFY_STOP`/`MODIFY_LIMIT` carry a `DistanceSpec` (Q0.2's existing generic distance vocabulary, reused unchanged) expressing the new price as an offset from the CURRENT bar's own close — never a live bid/ask (Q0.11.3's rule, unchanged), never the source's own literal base expression (see `Q0.13_COMPILATION.md` for why the base is deliberately discarded and only the magnitude survives).
- **`executableRules(policy)`** — the ONE gate: a rule reaches the runtime evaluator only when `target.provable && condition.provable && operation.kind !== "UNKNOWN"`, all three simultaneously. Consulted at TWO points (`runtime/reduction/simulation-adapter.ts` when assembling the `SimulationConfig`, and defensively again inside `evaluatePendingOrderManagementPolicy` itself) — belt-and-braces, never trusted from a single call site.

## Unsupported/unknown state is a first-class, always-present value

Every `OrderTargetSpec`/`ManagementCondition` always resolves to SOME value, including `UNKNOWN` — there is no "absent" state that could be silently mistaken for "not analyzed." A rule with `semanticFidelity: "UNKNOWN"` is still fully present in `StrategySpec.pendingOrderManagement.rules` (for provenance/audit visibility, Q0.13's "never silently drop" rule) — it is excluded from EXECUTION only, never from the record.
