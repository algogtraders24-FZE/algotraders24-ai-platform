# Q0.10 — MQL4/MQL5 Position Management Detection

## Why this was needed

Q0.8's semantic analyzer already detected `OrderModify`/`PositionModify` calls (`ModifyCallSite`, classification always `"UNKNOWN"`) and `OrderClose`/`PositionClosePartial` calls (`PartialCloseCallSite`) — but never interpreted WHAT they did. Every MQL-imported strategy's `RiskSpecification.breakeven`/`trailingStop`/`partialClose`/`maxHoldingPeriod` were always absent, regardless of what the source actually implemented. Q0.10 adds real interpretation, following the exact same "narrow, provable, never-guess" philosophy Q0.9 used for entry conditions and SL/TP legs.

## The four provable shapes (`semantic-analyzer.ts`'s `detectManagementPattern`, hooked into every `if` statement walked, mirroring `detectSimpleEntryCondition`)

All four share ONE favorable-move trigger shape: `<currentPrice> - OrderOpenPrice() >= <literal>` or `OrderOpenPrice() - <currentPrice> >= <literal>` (`resolveFavorableTriggerDistance`) — exactly one side of the subtraction must be the entry-price call (`OrderOpenPrice()` in MQL4, `PositionGetDouble(POSITION_PRICE_OPEN)` in MQL5), never both or neither.

1. **BREAKEVEN**: the trigger shape above, with an `OrderModify`/`PositionModify` call in the consequent whose new-SL argument resolves (via `resolveManagementDistance`, reusing Q0.9's `resolveRiskLegBinding` arithmetic) to `OrderOpenPrice()` bare (zero offset) or `OrderOpenPrice() ± <literal>` — the arithmetic BASE is the entry price.
2. **TRAILING**: the identical trigger and modify-call shape, but the new-SL argument's base is something OTHER than the entry price (current bid/ask) — `<currentPrice> ± <literal>` (fixed-distance) or `<currentPrice> ± (<atrVar> * <literal>)` (atr-multiple, `<atrVar>` bound to a recognized `iATR(...)` call via the SAME per-function variable-binding tracking Q0.9 built).
3. **PARTIAL_CLOSE**: the identical trigger shape, with an `OrderClose`/`PositionClosePartial` call in the consequent whose volume argument resolves to `<lotsVar> * <literal in (0,1)>` (`resolvePartialCloseFraction`), `<lotsVar>` bound to `OrderLots()`/`PositionGetDouble(POSITION_VOLUME)`.
4. **MAX_HOLDING**: an independent trigger shape, `TimeCurrent() - OrderOpenTime() >= <literalSeconds>` (or the MQL5 `PositionGetInteger(POSITION_TIME)` equivalent), with an `OrderClose`/`PositionClose`/`PositionClosePartial` call anywhere in the consequent.

Each `if` statement is tried against these shapes in order (modify-based first, then close-based, then time-based); the first provable match wins. An `if` matching none of these — a dynamic/cross-file new-SL expression, a non-literal volume fraction, a bar-count-based rather than literal-second holding check — records NOTHING here (Q0.8's raw `modifyCalls`/`partialCloseCalls` detection still records the call site regardless, so nothing is silently lost from the model; `test/q10-failure-catalog.test.ts`'s item 13 proves this).

## Reduction into `RiskSpecification` (`ir-generator.ts`)

`bindingToDistanceSpec` converts the resolved `RiskLegBinding` (`{kind:"fixed-distance",distance}` or `{kind:"atr-multiple",atrMultiple,atrPeriod}`) into Q0.2's own `DistanceSpec` — never a third representation. Each reduced rule (`breakevenRule`/`trailingStopRule`/`partialCloseRule`/`maxHoldingRule`) is disclosed via a WARNING-level `UnsupportedSemantic` noting the reconstruction is a best-effort pattern match, consistent with how SL/TP arithmetic reconstruction was disclosed in Q0.9. Any ATR indicator referenced by one of these rules is registered into `ir.indicators` via `registerAtrIndicatorIfNeeded` (a real gap this sprint found and fixed — an ATR indicator used ONLY by a risk/management rule, never by the entry condition, previously never made it into `ir.indicators` at all).

## Long/short symmetry

The trigger shape's "exactly one side is the entry price" check is direction-agnostic by construction — `Q0.10.30` (`test/q10-mql-management-e2e.test.ts`) proves the SAME detector correctly reduces a SELL-side breakeven pattern (`OrderOpenPrice() - g_bid >= trigger`) with the sign relationship inverted, with zero special-cased SELL logic anywhere in the detector.

## The pyramiding/reversal heuristic fix this detection REQUIRED

Detecting breakeven/trailing at all necessarily observes `OrderOpenPrice()`/`OrderLots()` calls — which Q0.9's eligibility heuristic ("`positionQueries.length === 0` ⇒ assume safe platform defaults") counted as "custom position-management code," permanently blocking pyramiding/reversal eligibility for ANY strategy using these features. Fixed by splitting `POSITION_QUERY_FUNCTIONS` into `MANAGEMENT_ACCESSOR_FUNCTIONS` (pure value reads: `OrderOpenPrice`/`OrderLots`/`OrderStopLoss`/`OrderTakeProfit`, excluded from the gating signal) vs. genuine counting/selecting functions (`PositionsTotal`/`PositionSelect`/`OrderSelect`/etc., which remain the real signal). G01's real source uses only the latter (`PositionsTotal`/`PositionGetTicket`), confirmed unaffected by grepping the actual file — see `docs/Q0.10_POSITION_MANAGEMENT_AUDIT.md`.

## MQL parity (Q0.10.18)

The detection shapes are dialect-agnostic at the AST level — `isEntryPriceExpr`/`resolvePartialCloseFraction` recognize both the MQL4 form (`OrderOpenPrice()`/`OrderLots()`) and the MQL5 form (`PositionGetDouble(POSITION_PRICE_OPEN)`/`PositionGetDouble(POSITION_VOLUME)`) as equivalent, producing the identical `RiskLegBinding`/`DistanceSpec` regardless of which platform's syntax was used — consistent with Q0.8's own MQL4/MQL5 canonical-hash parity guarantee (no new hash-affecting field was introduced; management rules ride inside the existing `RiskSpecification`, already covered by `computeSemanticStrategyHash`).
