# Q0.10 — Conflict & Priority Semantics

## The governing fact: step ordering, not arbitration

`simulation-engine.ts`'s (Q0.5, frozen) per-bar loop already resolves every same-bar conflict Q0.10 was asked to formally verify, purely by WHEN each check runs — never by a separate arbitration layer:

```
Step 1:  resolve pending orders (fills)
Step 1b: check the OPEN position's protective SL/TP against THIS bar's OHLC
         → if hit, position CLOSES HERE. Nothing below runs for it this bar.
Step 2:  mark to market
Step 4:  strategy calculation (new signals)
Step 5:  risk evaluation for the (still-open) position:
           1. max holding period → FORCE_EXIT_REQUIRED
           2. breakeven → MOVE_STOP
           3. trailing → MOVE_STOP (only if breakeven did not trigger)
           4. partial close → PARTIAL_CLOSE (only if neither stop policy triggered)
```

Two structural facts make every required conflict deterministic:

1. **Step 1b always runs before Step 5, using the stop/target AS OF THE START of the bar.** Any level Step 5 computes this bar cannot affect this bar's own protective check — only the NEXT bar's.
2. **`evaluateManagement()` is a strict sequential if-chain that returns on the first trigger.** At most one management action is ever produced per call — there is no scenario where two actions race.

## The nine required conflicts (Q0.10.8), each with a golden fixture

| Conflict | Resolution | Fixture |
|---|---|---|
| SL + TP | Both reachable within one bar → conservative rule, stop-loss always wins (`bar-fill-model.ts`'s `resolveProtectiveExit`, flagged `ambiguous: true`) | `PM_SL_TP_CONFLICT` |
| Breakeven + SL | Breakeven's own stop move IS the new SL; no separate conflict — proven via `PM_BASIC_BREAKEVEN`/`PM_LONG_BREAKEVEN`'s move-then-hit sequence | `PM_LONG_BREAKEVEN` |
| Trailing + SL | A stop hit resolves against the level as of the START of the bar, never an improved level trailing would compute from that SAME bar's later price action | `PM_SL_TRAILING_CONFLICT` |
| Partial close + SL | A same-bar SL hit closes the FULL position via Step 1b; partial-close (Step 5) never runs for a position that no longer exists | `PM_PARTIAL_SL_CONFLICT` |
| Partial close + TP | Symmetric to the above — TP is also checked in Step 1b, ahead of Step 5 | (same code path as `PM_PARTIAL_SL_CONFLICT`; TP case not separately fixtured — identical mechanism) |
| Holding expiry + SL | A same-bar SL hit closes the position in Step 1b; the holding-period check (Step 5, highest management priority) never runs for a closed position | `PM_EXPIRY_CONFLICT` |
| Holding expiry + TP | Symmetric — same mechanism | (same code path) |
| Multiple management actions same bar | Impossible by construction — `evaluateManagement()`'s sequential if-chain returns on the first trigger | `PM_MULTI_ACTION` (proves priority order across TWO bars instead: breakeven fires while it still improves, trailing correctly takes over once it doesn't) |

No ambiguity required inventing new conservative rules — Q0.5's OWN `resolveProtectiveExit()` (SL+TP) and step ordering (everything else) already resolve all nine cases correctly; Q0.10's job was proving it, not building it (see `docs/Q0.10_POSITION_MANAGEMENT_AUDIT.md`).

## R-multiple consistency (Q0.10.10)

Breakeven/trailing/partial-close triggers all resolve their distances via the SAME `resolveDistanceSpec()` (`runtime/risk/distance-spec.ts`, Q0.3, unmodified) — no duplicate arithmetic. The final trade's R-multiple (computed once, at close, in `trade-ledger.ts`'s `buildTrade()`) uses `Position.initialStopLoss` (the Q0.10 fix — see the audit doc), never re-derived per-management-action. There is exactly one R-multiple formula (`runtime/risk/r-multiple.ts`'s `computeRMultiple`/`computeRealizedR`) in the entire codebase; `test/q10-golden-fixtures.test.ts` and `test/q10-metrics-provenance.test.ts` verify its output for every management scenario, never a second computation.
