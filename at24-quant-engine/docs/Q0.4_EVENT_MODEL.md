# Q0.4 Event-Driven Market Model

Covers Q0.4.5 (canonical events), Q0.4.6 (strategy calculation timing), Q0.4.7 (order timing), Q0.4.8 (order lifecycle), and Q0.4.9 (order types) — grouped together because they are one connected design: **what happens, in what order, and when does a strategy get to react.** No implementation in Q0.4; this is the contract a Q0.5 Event-Driven Simulation Core is built against.

## Canonical events (Q0.4.5)

### Market events
`MarketEvent` (base), `TickEvent`, `QuoteEvent` (bid/ask update, distinct from a trade tick), `BarOpen`, `BarUpdate` (an in-progress bar's high/low/close changed), `BarClose`, `SessionOpen`, `SessionClose`.

### Order events
`OrderCreated`, `OrderSubmitted`, `OrderAccepted`, `OrderRejected`, `OrderTriggered` (a stop/stop-limit's trigger condition was met), `OrderPartiallyFilled`, `OrderFilled`, `OrderCancelled`, `OrderExpired`.

### Strategy events
`StrategyCalculated`, `StrategyRecalculatedAfterFill` (the Pine `calc_on_order_fills` case — Q0.4.2 — generalized as a named event rather than a hidden side effect).

### Position events
`PositionOpened`, `PositionModified`, `PositionReduced`, `PositionClosed`.

### Shared envelope (every event, regardless of category)

```
{
  timestamp: number       // epoch ms — the event's logical time, never wall-clock at simulation time
  sequence: number        // strictly increasing, tie-breaks same-timestamp events deterministically
  type: <one of the event names above>
  source: string          // which subsystem emitted it (MarketDataFeed, OrderEngine, RiskEvaluation, ...) — for
                           // provenance/debugging, never used for ordering decisions
  payload: <event-specific data>
}
```

**Determinism requirement**: `(timestamp, sequence)` together totally order every event in a simulation run. Two events sharing a `timestamp` (e.g. a `BarClose` and an `OrderTriggered` that logically happens at that same instant) are disambiguated by `sequence`, assigned by a single, deterministic event-queue discipline (a strict priority queue keyed on `(timestamp, sequence)`, `sequence` incremented monotonically at insertion time in a fixed, documented processing order — e.g. market events before strategy events before order events at the same timestamp, itself a specific ordering decision a future Q0.5 must fix and document, not leave implicit). This is what makes Q0.4.39's deterministic replay possible at all: without a total order, "the same input twice" is ambiguous about which of two same-timestamp events happened first.

## Strategy calculation timing (Q0.4.6)

| AT24 future mode | Meaning | Platform equivalents |
|---|---|---|
| `ON_BAR_OPEN` | strategy evaluates once, at the instant a new bar begins | closest to nothing evaluated live on most platforms; useful for AT24-native "decide only at open" strategies |
| `ON_BAR_UPDATE` | strategy evaluates every time the current (still-forming) bar's OHLC changes | NinjaScript's `Calculate = OnEachTick` / `OnPriceChange` (Q0.4.1 research); Pine's realtime-only tick-by-tick recalculation |
| `ON_BAR_CLOSE` | strategy evaluates once, when a bar finalizes — the default, safest mode | MT4/MT5's default `OnTick`-but-acting-only-on-new-bar pattern; NinjaScript's `Calculate = OnBarClose` (its documented default and recommended mode); Pine's default historical-bar-close evaluation |
| `ON_EVERY_TICK` | strategy evaluates on every raw price tick | MT4/MT5's raw `OnTick()`; Pine's `calc_on_every_tick = true` (realtime only — Q0.4.2 flags this diverges from backtest-time behavior); NinjaScript `Calculate = OnEachTick` |
| `ON_QUOTE` | strategy evaluates on a bid/ask quote update, distinct from a trade tick | cTrader's quote-driven model (Q0.4.1 research — cTrader is bid/ask-native) |
| `ON_ORDER_FILL` | strategy evaluates immediately after one of its own orders fills, before the next scheduled tick/bar event | Pine's `calc_on_order_fills = true`; MT5's `OnTrade()`/`OnTradeTransaction()` |
| `ON_EVENT` | strategy evaluates on a custom timer/scheduled event, independent of price | NinjaTrader's timer-based indicators; LEAN's `Schedule.On` (Q0.4.1 research) |

**Why this matters architecturally**: `StrategySpec`'s current runtime (`generateSignal()`, Q0) implicitly assumes `ON_BAR_CLOSE` — it is called once per `MarketState`, with no notion of "this is bar 3 of 7 ticks within the same bar." A future Q0.5 simulation core must make the calculation-timing mode an explicit, per-strategy configuration (carried in the IR per `Q0.4_STRATEGY_IR.md`'s "Events" field), not a hard-coded assumption, precisely because Q0.4.1's research shows every platform treats this as a first-class, author-controlled setting with materially different backtest results depending on the choice.

## Order timing (Q0.4.7)

No hidden order timing — every future order must declare, explicitly, when it is assumed to interact with the market:

| Mode | Meaning |
|---|---|
| `NEXT_TICK` | order becomes eligible for fill at the next tick after submission |
| `NEXT_BAR_OPEN` | order fills (if fillable) at the next bar's open price — Backtrader's documented default (Q0.4.1 research) and the safest, most common lookahead-avoidance convention |
| `SAME_BAR_CLOSE` | order fills within the same bar it was generated, at/near that bar's close — Pine's default (signal bar's close is known, fill assumed at/after it) unless `process_orders_on_close` changes this (Q0.4.2) |
| `IMMEDIATE` | order fills instantly at the current simulated price, no timing delay at all — only valid for `ON_EVERY_TICK`/`ON_QUOTE`-timed strategies, since a bar-close-timed strategy has no "current price" between bars to fill against without smuggling in intrabar knowledge |
| `CUSTOM_LATENCY` | order fills after an explicitly configured delay (see Q0.4.18's `LatencyModel`) |

Platform default comparison (from Q0.4.1/Q0.4.2 research, consolidated): MT4/MT5's `OnTick`-driven EAs typically place orders that fill at the current tick (`IMMEDIATE`-like in live trading, but the Strategy Tester's bar-based modes approximate this against synthesized ticks); Pine defaults to next-bar-open fills unless `process_orders_on_close` is set; Backtrader defaults to next-bar-open explicitly and calls out `cheat_on_open`/`cheat_on_close` as deliberately-labeled exceptions (Q0.4.1 research) — this is the single clearest precedent for "no hidden order timing" as a design value, since Backtrader's own maintainers chose to name the lookahead-permitting flags after what they are (cheating), rather than hide them.

## Order lifecycle (Q0.4.8)

```
NEW -> SUBMITTED -> ACCEPTED -> [TRIGGERED] -> PARTIALLY_FILLED* -> FILLED
                        |                                       \
                        v                                        -> CANCELLED
                    REJECTED                                     -> EXPIRED
```

- `NEW`: order object constructed by the strategy/risk layer, not yet handed to the (simulated) broker.
- `SUBMITTED`: handed to the execution layer; not yet acknowledged.
- `ACCEPTED`: execution layer has validated and accepted it (passed basic sanity — this is distinct from, and downstream of, Q0.3's `RiskEvaluation`, which already gated whether the order should be proposed at all).
- `REJECTED`: execution layer refused it (e.g. insufficient margin) — terminal.
- `TRIGGERED`: for stop/stop-limit orders only — the trigger price condition was met; the order is now live as a market/limit order. Market and limit orders skip this state (they are immediately eligible, subject to `ACCEPTED`).
- `PARTIALLY_FILLED`: some but not all quantity filled — may recur multiple times before reaching `FILLED`/`CANCELLED`/`EXPIRED`.
- `FILLED`: fully executed — terminal.
- `CANCELLED`: withdrawn before full execution (by the strategy or a risk/expiry rule) — terminal.
- `EXPIRED`: time-in-force elapsed before full execution — terminal.

**Valid transitions only** (a future runtime must reject anything else, e.g. `FILLED -> TRIGGERED` is nonsensical and must be a hard error, not silently ignored): `NEW->SUBMITTED`, `SUBMITTED->ACCEPTED|REJECTED`, `ACCEPTED->TRIGGERED|PARTIALLY_FILLED|FILLED|CANCELLED|EXPIRED` (market/limit orders skip straight past `TRIGGERED`), `TRIGGERED->PARTIALLY_FILLED|FILLED|CANCELLED|EXPIRED`, `PARTIALLY_FILLED->PARTIALLY_FILLED|FILLED|CANCELLED|EXPIRED`. `REJECTED`/`FILLED`/`CANCELLED`/`EXPIRED` are terminal — no transition leaves them. This state machine is deliberately more explicit than any single researched platform's (MT4's ticket model barely exposes intermediate states at all; MT5 separates order/deal/position but doesn't name a `TRIGGERED` state distinctly) — AT24 names every state explicitly so a future runtime's invalid-transition rejection has something concrete to check against.

## Order types (Q0.4.9)

For each: trigger condition, activation, execution price, expiry, cancellation, partial-fill behavior, and gap behavior (see also `Q0.4_INTRABAR_ENGINE.md` for the deeper gap-handling design).

| Type | Trigger | Execution price | Gap behavior |
|---|---|---|---|
| `MARKET` | none — immediate | current simulated price (subject to Spread/Slippage models, Q0.4.15/16) | not applicable — market orders don't wait for a level |
| `LIMIT` | price reaches or betters the limit level | the limit price or better — **never worse**, per Q0.4.2's researched Pine rule that a limit only fills if price actually traded through it, not merely "closed past it" | if the market gaps THROUGH the limit price, AT24 must decide: fill at the limit (understating the favorable gap) or fill at the gapped-through price (the more realistic, and more favorable-to-the-trader, outcome) — this is a modeling decision reserved for `Q0.4_INTRABAR_ENGINE.md`, not resolved here |
| `STOP` | price reaches the stop level | market price at/after trigger (subject to slippage) | if the market gaps THROUGH the stop price, realistic fill is at the gapped-through (worse) price, not the stop level — this is the "stop gap-through" failure mode (`Q0.4_BACKTEST_FAILURE_CATALOG.md` item 14) and must never be silently modeled as filling exactly at the stop |
| `STOP_LIMIT` | price reaches the stop level, THEN becomes a limit order at the limit level | limit price or better, once triggered | can fail to fill entirely if price gaps through both the stop and the limit without trading between them — a real, documented risk this order type carries that AT24 must be able to represent (an order that triggers but then expires unfilled) |
| `TRAILING_STOP` | dynamically-adjusted stop level, per Q0.3's `TrailingStopRule` semantics (activation, distance, never-moves-backward) | same as `STOP` once triggered | same gap-through risk as `STOP` |

Expiry/cancellation are cross-cutting (any order type can carry a time-in-force: GTC, day-order, specific expiry timestamp, or immediate cancel-if-not-filled) rather than being per-type properties — this matches every researched platform's convention (Q0.4.1) and avoids duplicating expiry logic per order type.
