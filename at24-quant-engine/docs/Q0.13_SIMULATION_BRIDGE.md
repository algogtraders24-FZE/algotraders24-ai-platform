# Q0.13 — Simulation Bridge

## The risk/execution boundary (Q0.13.14), restated precisely

```
MQL Source
    ↓
Semantic Analyzer            (new detection only — zero execution logic)
    ↓
Strategy IR
    ↓
Compilation
    ↓
PendingOrderManagementPolicy  (StrategySpec-level, strategy-authored INTENT)
    ↓
SimulationConfig.pendingOrderManagementPolicy   (only executableRules())
    ↓  — Step 0.4, evaluated once per pending order per bar
evaluatePendingOrderManagementPolicy()          (runtime/simulation/pending-order-management.ts)
    ↓ produces, only when a rule's condition holds
OrderModificationIntent                          (Q0.12, UNMODIFIED)
    ↓
validateOrderModification() → applyOrderModification()   (Q0.12, UNMODIFIED)
    ↓
SimulationState.pendingOrders (mutated exactly as Q0.12's own declarative schedule already does)
```

Q0.3's `evaluateRisk()` is **never called** by this path and **never consulted** by `evaluatePendingOrderManagementPolicy()` — the two mechanisms are structurally disjoint (proven in `test/q13-negative.test.ts` NEG 8: `maxSimultaneousPositions` remains fully authoritative and untouched by pending-order-management activity).

## Step 0.4 — where it sits, and why

`simulation-engine.ts`/`multi-fidelity-engine.ts` already had a "Step 0.5" (Q0.12's declarative `orderModifications` schedule), inserted before Step 1 (fill/expiration resolution). Q0.13 adds a new **Step 0.4**, immediately before Step 0.5, in BOTH engines simultaneously (the D1/D2/D3 mirror discipline applied proactively — see `Q0.13_EXISTING_ARCHITECTURE_AUDIT.md`):

1. **Step 0.4** (new): for every currently-pending order of this bar's symbol (excluding same-bar-created orders, the identical safety guard Step 1 already uses), evaluate `config.pendingOrderManagementPolicy` via `evaluatePendingOrderManagementPolicy()`. If it produces an intent, validate and apply it exactly like Step 0.5 does (same functions, same event types: `ORDER_CANCELLED`/`ORDER_MODIFIED`/`ORDER_MODIFICATION_REJECTED`).
2. **Step 0.5** (unchanged): the declarative schedule runs next, on whatever pending orders remain after Step 0.4.
3. **Step 1** (unchanged): fill/expiration resolution runs last, on whatever survives Steps 0.4 and 0.5.

This ordering is the ENTIRE race-resolution rule — identical in spirit to Q0.12's own "one explicit rule, never wall-clock timing" (`Q0.12_RACE_SEMANTICS.md`), extended by exactly one more deterministic step.

## Why the evaluator never emits `REPLACE`

`PendingOrderManagementOperation`'s vocabulary (`CANCEL_PENDING`/`MODIFY_STOP`/`MODIFY_LIMIT`/`MODIFY_EXPIRATION`) has no `REPLACE` member — Q0.13.12's own instruction ("detect only PROVABLE cancel-then-create patterns... in uncertain cases, BLOCKED/UNKNOWN") led to a design that never attempts to SYNTHESIZE a replace relationship at all; Q0.13's importer only ever detects an `OrderDelete` and a LATER, structurally UNRELATED `OrderSend`/`OrderModify` as two independent facts (proven never fabricated in `test/q13-negative.test.ts` NEG 12 and `test/q13-mql-detection.test.ts`'s `mql4-09` fixture). Consequently `applyOrderModification`'s `"REPLACED"` outcome variant is structurally unreachable from this sprint's own evaluator — the Step 0.4 loop in both engines handles it only defensively, for type-safety, with a code comment explaining it is never expected to execute.

## `SimulationConfig.pendingOrderManagementPolicy` — wiring

Additive, optional field on `SimulationConfig` (`simulation-engine.ts`); `MultiFidelityConfig.base` is a plain `SimulationConfig` (composition, not inheritance — Q0.6.10's existing design), so no separate field was needed on `MultiFidelityConfig` itself. `runtime/reduction/simulation-adapter.ts`'s `compileToSimulation()` — the ONE function connecting a compiled strategy to the engine (Q0.9.34-36) — gained exactly one additive line threading `executableRules(spec.pendingOrderManagement)` into `baseConfig`.

## E2E proof

`test/q13-e2e.test.ts` proves, for both an MQL4 and an MQL5 strategy, and for both `D1_OHLC` and `D2_LOWER_TIMEFRAME`: zero blocking diagnostics, a compiled `StrategySpec.pendingOrderManagement`, and a successful `compileToSimulation()` run producing a `simulationResultHash`. `test/q13-failure-catalog.test.ts`'s final structural test additionally proves D1 and D2/D3 produce the IDENTICAL `ordersCancelled` count for the identical policy — the mirror is behaviorally, not just textually, identical.
