# Q0.4 Pine/TradingView Deep Semantics

Q0.4.2: TradingView/Pine treated as a first-class research target, given its scale of adoption and its unusually well-documented (and unusually well-designed, in several places) treatment of exactly the ambiguity problems this whole sprint is about. Findings below are drawn from TradingView's own official docs (`pine-script-docs`) and support articles, researched live for this sprint; confidence level is noted per section. **This document extracts execution SEMANTICS for AT24 to adopt/adapt — no Pine code or parser is written.**

## `strategy()` parameters (confirmed)

`pyramiding` (max concurrent same-direction trades from `strategy.entry()`, default 1 — governs `strategy.entry()` only, not `strategy.order()`), `default_qty_type`/`default_qty_value` (fixed/cash/percent-of-equity sizing default), `commission_type` (percent / cash-per-contract / cash-per-order) × `commission_value`, `slippage` (integer TICKS, applied adversely to market/stop fills only — never to limit fills, which by construction fill at their limit price or better), `margin_long`/`margin_short` (percent of notional required — sets simulated leverage), `initial_capital`, `currency`, `process_orders_on_close`, `calc_on_every_tick`, `calc_on_order_fills`, `close_entries_rule` (`"FIFO"` default or `"ANY"`), `max_bars_back`, `use_bar_magnifier`.

## Entry/exit commands (confirmed)

- `strategy.entry()`: pyramiding-aware, direction-aware — an opposite-direction entry automatically closes/reverses the existing position first, sized to cover both the reversal and the new request. Once the pyramiding count is reached, further same-direction calls are silently ignored (not queued) until a trade closes.
- `strategy.order()`: a lower-level command that IGNORES pyramiding and most of `strategy.entry()`'s bookkeeping — no auto-reverse; net position is simply current + signed fill quantity.
- `strategy.exit()`: always exits FROM a named open entry — does nothing if no matching entry exists (not queued for later). Can emit stop-loss, take-profit, and/or trailing-stop orders simultaneously from one call, with partial-exit support (`qty`/`qty_percent`). Multiple `strategy.exit()` orders against the same entry default to the same OCA group (`strategy.oca.reduce`) — a fill on one leg auto-reduces/cancels the sibling.
- `strategy.close()`: closes one specific entry ID via market order; no-op if that ID isn't open.
- `strategy.close_all()`: closes the entire position via market order, regardless of entry ID.
- `close_entries_rule`: even when a specific entry ID is targeted, `"FIFO"` (the default) still closes the OLDEST open entry first — `"ANY"` is required to actually target by ID.

**AT24 relevance**: this is a strong precedent for keeping `EntryRule`/`ExitRule` semantics precise about "which entry does this exit apply to" — a gap the current `StrategySpec` (Q0) doesn't yet address (there is no entry-ID concept at all), directly informing the Strategy IR's "Position management" field (`Q0.4_STRATEGY_IR.md`).

## Order fill verification — the core mechanism (confirmed, high confidence)

Pine's broker emulator does NOT use the bar's close to decide fills. It infers an intrabar PATH from O/H/L/C using a documented heuristic: if the bar's high is closer to open than the low is, it assumes open→high→low→close; otherwise open→low→high→close. A pending order fills the instant this INFERRED path reaches its level.

**Critical, easy-to-miss nuance**: by default, this "assumes no gaps exist between prices within bars... considers any price within the bar's range as a valid level for filling" — meaning a limit order fills whenever the bar's range simply TOUCHES the level, not necessarily trades meaningfully through it. TradingView's stricter, opt-in mode (`backtest_fill_limits_assumption`, a tick-count parameter, default 0) requires price to exceed the limit by N ticks before considering it filled, for more conservative results — **the current exact UI naming/options for this setting could not be independently re-confirmed against a live TradingView UI in this research pass** (the underlying script parameter is stated to remain available; the dialog's labeling may have changed since it was originally documented as "Verify price for limit orders").

**AT24's adopted standard** (per `Q0.4_BACKTEST_FAILURE_CATALOG.md` item 15, `Q0.4_ADOPT_IMPROVE_AVOID_INVENT.md`): a limit fill requires genuine price-through, tunable via an explicit tolerance, exactly matching Pine's stricter opt-in mode's INTENT — but AT24 should make the stricter behavior the DEFAULT, not opt-in, given the sprint's "never silently favorable" mandate (`Q0.4_INTRABAR_ENGINE.md`) — Pine's lenient default is precisely the kind of unlabeled-default AT24 exists to avoid.

## Margin / liquidation (confirmed, high confidence)

Liquidation triggers when `CurrentEquity <= MarginRequired`, where `MarginRequired = LastPrice × PointValue × AbsPositionSize × (MarginPercent/100)`. A specific, non-obvious implementation detail: the emulator liquidates **4x the minimum amount required** to restore compliance, explicitly to avoid a thrash of repeated margin-call events on subsequent bars. Worth preserving as a design option (not a hard requirement) for AT24's future `MarginModel` — over-liquidation-to-avoid-thrash is a reasonable, documented trade-off other platforms might not make as explicitly.

## `process_orders_on_close` (confirmed)

Default: signal computed at bar N's close can only fill starting bar N+1's open (or later, per the fill-verification logic above). Setting `true` allows same-bar-close fills — TradingView's own FAQ explicitly warns this "can lead to repainting, where the behavior of the strategy's simulation on historical bars differs from that seen in live trading," since live trading has no way to guarantee an order submitted "at close" executes before the next tick. **AT24 relevance**: directly maps to `Q0.4_EVENT_MODEL.md`'s `SAME_BAR_CLOSE` vs `NEXT_BAR_OPEN` order timing modes — Pine's own documentation independently arrives at treating same-bar-close fills as a labeled, warned-about risk rather than a safe default, reinforcing AT24's "no hidden order timing" principle.

## `calc_on_order_fills` (confirmed)

Adds an extra recalculation pass the instant an order fills, rather than waiting for bar close — but capped, on HISTORICAL bars, at effectively 4 recalculation points per bar (open/high/low/close), while REALTIME bars have no such cap (recalculates per actual tick). This asymmetry is explicitly documented by TradingView itself as a genuine source of backtest/live divergence, not a corner case.

## `calc_on_every_tick` (confirmed, high confidence)

TradingView's own documentation states directly: **"calc_on_every_tick doesn't change the strategy's behaviour on historical bars"** — historical Pine data carries only ONE committed OHLC record per bar (no retained tick history), so the flag only takes effect once the strategy reaches the live/forming realtime bar. **This means a Pine backtest report using this flag is not actually simulating what the flag will do going forward** — it only shows bar-close-based historical results, with true tick-level behavior only manifesting post-deployment. This is the single clearest, most explicitly-documented example, across all seven researched platforms, of exactly the historical-vs-realtime asymmetry `Q0.4_STRATEGY_IR.md`'s "Recalculation semantics" field and `Q0.4_EVENT_MODEL.md`'s calculation-timing table exist to make an explicit, first-class IR/architecture concern rather than an unstated platform quirk.

## `use_bar_magnifier` (confirmed mechanism; some specifics unconfirmed)

Replaces the default 4-point (O/H/L/C) intrabar-path inference with REAL lower-timeframe OHLC data, when available — directly informing AT24's own `BarDetailProvider` design (`Q0.4_INTRABAR_ENGINE.md`). Documented limitations, both directly relevant to AT24's own design: (1) **plan-gated** (Premium+ only on TradingView — AT24 has no equivalent commercial gating concern, but the PRINCIPLE that "this is a paid/limited resource" is worth remembering for AT24's own future compute-cost tradeoffs between fidelity tiers); (2) a **200,000-bar cap** per script on lower-timeframe data requests — for long backtests, this means the EARLIEST portion of a run may silently fall back to standard 4-point resolution while later bars get magnified, a genuinely subtle within-one-run inconsistency AT24 must avoid by making its own `DataFidelity` (Q0.4.12) a PER-RESULT or even per-trade field, not an assumed-constant-for-the-whole-run property, precisely because Pine's own implementation shows this constancy assumption can silently break down. The exact lower-timeframe mapping table (e.g. which sub-timeframe 1D magnifies to) was reconstructed from search-summarized excerpts rather than independently re-fetched verbatim — flagged as not fully re-confirmed.

## Bar Replay (confirmed, lower confidence on integration specifics)

A manual/visual, chart-level feature for discretionary practice — steps a chart forward bar by bar, hiding future data. **Separate and non-integrated from the Strategy Tester** — a Pine strategy's backtest report is computed independently of chart replay state. This characterization is drawn from TradingView's help-center structure and secondary sources rather than one explicit official statement of the (non-)relationship; treated as provisional.

## Deep Backtesting (confirmed, high confidence)

Calculates over ALL available historical data for a symbol (up to 2M bars / 1M trades), not just what's chart-loaded, over a user-selected date range — a DATA-WINDOWING capability, not (per the evidence found) a different execution/fill engine. Critically, **Deep Backtesting begins its calculation at the SELECTED range's start**, while regular backtesting always begins at the chart's first loaded bar — since history-dependent calculations (moving averages, recursive smoothing) are sensitive to their accumulation start point, **the two modes can produce genuinely different trade signals over the nominally same date range**, a fact TradingView states outright. Results display only in the Strategy Report tab, with no chart trade markers. **AT24 relevance**: this is the clearest available real-world validation of `Q0.4_BACKTEST_ARCHITECTURE.md`'s Provenance requirement to record exact `DataRange`/`DatasetVersion` per result — two results over "the same" nominal range can differ purely from where calculation warmup began, exactly the kind of silent discrepancy Provenance exists to make auditable rather than mysterious.

## Historical vs. realtime asymmetry (confirmed, the load-bearing Pine concept)

The root cause behind §`calc_on_order_fills`/§`calc_on_every_tick` above: historical bars carry one committed OHLC record; realtime/forming bars carry continuously-updating values until close. Consequences TradingView documents explicitly: `barstate.isnew` is TRUE AT CLOSE historically but TRUE AT OPEN in realtime (an explicit inversion); `request.security()` returns only confirmed values historically but can surface unconfirmed live values in realtime; a bar that "was live" during one session becomes purely historical (with per-tick detail gone) on the next reload, so a script's own past behavior on that bar can appear to have shifted. TradingView's own framing treats this not as an edge case but as a NAMED, expected characteristic of the execution model — precisely the discipline `Q0.4_STRATEGY_IR.md`'s Source Fidelity grading and `Q0.4_LOOKAHEAD_REPAINTING.md`'s repainting-cause catalog both build directly on.

## Repainting — documented causes (confirmed, high confidence, direct source for `Q0.4_LOOKAHEAD_REPAINTING.md`)

1. Reading `high`/`low`/`close` of the still-forming realtime bar (fluid values that later fix once the bar closes) — mitigated via `barstate.isconfirmed`, a `[1]` offset, or relying only on `open` (fixed at bar start).
2. `request.security()` misuse (see below).
3. `varip`-declared variables (persist raw per-tick state unreproducible historically).
4. Certain `barstate.*` built-ins behaving inconsistently between historical/realtime (e.g. `barstate.isnew`'s documented inversion above).
5. `timenow` (no historical analog to "current wall-clock time" exists at all).
6. `calc_on_every_tick=true` strategies (ties directly to the asymmetry above).
7. Retroactive/backward plotting of a feature detected with inherent confirmation delay — TradingView's own stated guidance: default to non-retroactive plotting, make backward-plotting an explicit opt-in, never a silent default.
8. Dataset-provenance causes (differing historical start by account tier, exchange-side data revisions) — data problems, not script-logic problems.

## `request.security()` and lookahead (confirmed, high confidence — the sprint's most load-bearing single finding)

`barmerge.lookahead_off` (default): on historical bars, returns the LAST completed value — repaint-safe. `barmerge.lookahead_on`: on historical bars, returns the FIRST intrabar value of the requested (typically higher) timeframe context — **without further offsetting, this is a genuine, quotable future-data leak**: "it will look to the future states of historical HTF bars, retrieving values before the times at which they're available in the feed." TradingView states outright: **"Using lookahead to produce misleading results is not allowed in script publications"** — treated as a publication-POLICY violation, not merely a technical footgun. The documented safe pattern: combine `lookahead_on` with an explicit `[1]` offset on the requested expression, which "does not repaint... because it always uses the last confirmed value from the higher timeframe" — functionally equivalent to `lookahead_off` in safety, with some performance benefit. TradingView's guidance for strategies specifically: "always use `barmerge.lookahead_off`."

**This is the single strongest real-world precedent in all of Q0.4's research for `Q0.4_BACKTEST_ARCHITECTURE.md`'s MTF availability rule** ("an observation becomes available only at its own bar's close, never earlier") — Pine independently arrived at exactly this rule as the correct default, with the unsafe alternative available but explicitly disallowed in any publishable, trustworthy context.

## Non-standard chart types — the explicit warning (confirmed, high confidence, directly informs `Q0.4_INTRABAR_ENGINE.md`'s Synthetic Data Detection)

Heikin Ashi, Renko, Line Break, Kagi, Point & Figure, and Range charts are documented as **"not suited for strategy backtesting or automated trading systems execution, because the prices and time intervals do not match market prices and times"** — TradingView's own stated reasoning: "distortion of price data and the omission of time in non-standard charts lead to unrealistic and potentially misleading backtesting results." Explicit recommendation: use standard chart types for backtesting.

Why each is synthetic, per TradingView's own characterization: **Heikin Ashi** bars are analytically averaged/smoothed from real OHLC (HA close = average of that period's real O/H/L/C; HA open = average of the prior HA bar's open/close) — never actually-traded values. **Renko/Line Break/Kagi/Point&Figure/Range** form new units purely from price movement (or reversal thresholds), omitting time entirely — a bar can represent seconds or weeks of real time depending on volatility, and its O/H/L/C are constructed boundary levels, not observed trade prices at those instants.

**One documented partial mitigation, Heikin Ashi only**: a "Fill orders using standard OHLC" Strategy Properties option lets the broker emulator fill against REAL underlying market OHLC while the script's own logic still references HA values — explicitly scoped to Heikin Ashi alone: "On other synthetic chart types such as Renko, backtesting will continue to fill orders at the synthetic chart prices, regardless of the feature's setting." This is directly the model AT24's `REAL_MARKET_PRICE`/`SYNTHETIC_PRICE` classification (`Q0.4_INTRABAR_ENGINE.md`) generalizes and extends to ALL synthetic types, not just Heikin Ashi — Pine solved this for one case; AT24's design commitment is to solve it structurally for all of them.
