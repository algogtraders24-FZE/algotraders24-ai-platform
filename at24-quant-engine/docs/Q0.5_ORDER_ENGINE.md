# Q0.5 Order Engine

## Order model (Q0.5.5)

```ts
interface SimulationOrder {
  orderId: string;
  strategyVersion: string;
  instrument: Instrument;
  side: "BUY" | "SELL";
  quantity: number;
  orderType: "MARKET" | "LIMIT" | "STOP" | "STOP_LIMIT";
  limitPrice?: number;
  stopPrice?: number;
  attachedStopLoss?: number;   // carried onto the resulting Position once filled
  attachedTakeProfit?: number;
  creationTimestamp: number;
  sequence: number;
  status: OrderStatus;
  filledQuantity: number;
  averageFillPrice?: number;
  terminalReason?: string;     // populated only on REJECTED/CANCELLED/EXPIRED
}
```

`createOrder()` (`src/runtime/simulation/order-engine.ts`) validates: `quantity` must be finite and `> 0`; `LIMIT`/`STOP_LIMIT` require `limitPrice`; `STOP`/`STOP_LIMIT` require `stopPrice`. All violations throw immediately — an order is never constructed in an invalid state.

## Order identity (Q0.5.6)

```
orderId = `${strategyVersion}:${instrument.symbol}:${side}:${orderType}:${creationTimestamp}:${sequence}`
```

Purely a function of its own inputs — no `Date.now()`, no `Math.random()`, no machine-generated UUID anywhere in the order engine (statically enforced by `test/simulation-determinism.test.ts`'s source scan). `sequence` is supplied by the caller — in practice, the `EventQueue`-assigned sequence of the `ORDER_CREATED` event that triggered the order's construction (`docs/Q0.5_EVENT_QUEUE.md`), so an order's identity is traceable back to the exact event that produced it.

## Order lifecycle (Q0.5.8, reusing Q0.4's frozen state machine verbatim)

```
NEW -> SUBMITTED -> ACCEPTED -> [TRIGGERED] -> PARTIALLY_FILLED* -> FILLED
                        |                                       \
                        v                                        -> CANCELLED
                    REJECTED                                     -> EXPIRED
```

| From | Valid next states |
|---|---|
| NEW | SUBMITTED |
| SUBMITTED | ACCEPTED, REJECTED |
| ACCEPTED | TRIGGERED, PARTIALLY_FILLED, FILLED, CANCELLED, EXPIRED |
| TRIGGERED | PARTIALLY_FILLED, FILLED, CANCELLED, EXPIRED |
| PARTIALLY_FILLED | PARTIALLY_FILLED, FILLED, CANCELLED, EXPIRED |
| FILLED / CANCELLED / EXPIRED / REJECTED | *(none — terminal)* |

`transitionOrder(order, next)` throws immediately for any transition not in this table — `test/simulation-order-engine.test.ts` proves every valid transition succeeds and specific invalid ones (`FILLED -> NEW`, `CANCELLED -> FILLED`, `REJECTED -> FILLED`, `SUBMITTED -> TRIGGERED`) throw. Market and Limit orders skip `TRIGGERED` entirely (they go `ACCEPTED -> FILLED` directly); only Stop and Stop-Limit orders pass through it, matching their actual "does the level get reached first" semantics (`docs/Q0.5_EXECUTION_MODEL.md`).

`transitionOrder()` is pure — it returns a new `SimulationOrder`, never mutates the input (`test/simulation-order-engine.test.ts`'s explicit mutation check).

## End-of-run finalization

Q0.5.9's "unavailable price" case for MARKET orders — and the analogous case for any still-`ACCEPTED`/`TRIGGERED` LIMIT/STOP/STOP_LIMIT order — is handled by the orchestrator (`docs/Q0.5_SIMULATION_ARCHITECTURE.md`): any order still pending when the bar stream is exhausted is explicitly transitioned to `EXPIRED` with `terminalReason: "simulation ended with no further bars"`. No order is ever left dangling in a non-terminal state at the end of a run — `test/simulation-same-bar-safety.test.ts`'s single-bar scenario proves this directly (an order created on the only available bar can never fill, since Q0.5.30's same-bar-safety rule forbids resolving it against its own creation bar, and it correctly ends the run as `EXPIRED`, not `ACCEPTED`).
