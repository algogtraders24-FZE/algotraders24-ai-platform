# Q0.6 MTF (Multi-Timeframe) Safety

## HTF lookahead protection (Q0.6.23) — CRITICAL

The parent-level strategy calculation (`generateSignal()`, Q0's own unmodified function) in Q0.6's D2/D3 orchestrator is called EXACTLY as it is in D1: on the PARENT `bars` array only, sliced to `bars[0..barIndex]`. It never receives child bars in any form — indicator computation and signal generation have zero code path through `runtime/fidelity/` at all. This means HTF lookahead safety for strategy calculation is not a new guarantee Q0.6 had to invent; it is structurally impossible for child-bar data to reach `generateSignal()` because nothing wires it there.

What Q0.6 DOES need to guarantee is narrower and just as critical: **a `BarDetailProvider` query for parent bar T must never return a child bar belonging to a later parent T+1, T+2, ...**, even when the provider's own backing dataset already holds that later data (a realistic scenario — a real provider is usually loaded with a full historical child-bar series up front, not incrementally). This is enforced structurally, not by discipline: `createStaticBarDetailProvider`'s `getDetail()` filters PURELY by the requested `ParentBarIdentity`'s `(openTimestamp, closeTimestamp]` window — there is no code path by which a later parent's children, however present in the backing array, can satisfy that window check for an earlier parent's query (`test/fidelity-lookahead.test.ts`, `test/fidelity-failure-catalog.test.ts` item 8).

## Child future-leak equivalence (Q0.6.24)

Directly proven: `test/fidelity-lookahead.test.ts` builds two providers — one whose backing array holds only parent 40's children, one whose backing array ALSO holds parent 41's (later) children — and asserts `provider.getDetail({parent: parent40, ...})` returns `deepEqual` results from both. Appending future data to a provider's dataset cannot retroactively change an already-computed historical query result.

## MTF strategy safety / TimeFrontier reuse (Q0.6.25/26)

Q0.6 does not implement a genuine dual-timeframe STRATEGY (e.g. "H1 signal, M5 execution" where the signal ITSELF reads two timeframes' indicator series simultaneously) — that remains a Q0.4-deferred capability, unchanged by this sprint (`docs/Q0.4_LOOKAHEAD_REPAINTING.md`'s MTF/cross-symbol rules still apply once it is built). What Q0.6 proves instead is that the ONE existing point-in-time-visibility primitive, `TimeFrontier` (Q0.2, `runtime/time-frontier.ts`), is already timeframe-agnostic and requires ZERO new code to apply to a lower-timeframe child series: `test/fidelity-lookahead.test.ts` constructs a `TimeFrontier` directly over a `MarketSeries` of M15 child bars and proves the same "at cursor T, a future bar is not visible" guarantee Q0.2 already proved for parent bars. This is the concrete fulfillment of "reuse existing TimeFrontier, do not duplicate" — when a future sprint builds a real MTF strategy, the HTF-availability boundary is `TimeFrontier` applied to the HTF series, exactly as today; nothing about Q0.6's fidelity work required a second frontier class.

## What Q0.6 does NOT do

No dual-timeframe strategy calculation (signal generation stays single-timeframe, unchanged from Q0/Q0.5). No cross-symbol MTF. No incremental/streaming `BarDetailProvider` (the reference implementation is a static, fully-loaded in-memory array — a future sprint building a real streaming provider must still satisfy the same "never return a later parent's children for an earlier query" contract, but the mechanism by which it does so is its own concern).
