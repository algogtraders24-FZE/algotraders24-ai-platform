# Q0.12 — Order Modification Contract

## `OrderModificationIntent` (Q0.12.14)

```ts
interface OrderModificationIntent {
  orderId: string;
  modificationType: "MODIFY_PRICE" | "MODIFY_STOP" | "MODIFY_LIMIT" | "MODIFY_EXPIRATION" | "CANCEL" | "REPLACE";
  newPrice?: number;       // MODIFY_PRICE only — the unambiguous single price of a plain LIMIT or STOP order
  newStopPrice?: number;   // MODIFY_STOP
  newLimitPrice?: number;  // MODIFY_LIMIT
  newExpiration?: OrderExpirationPolicy; // MODIFY_EXPIRATION
  reason: string;
}
```

"Only fields applicable to the operation may be populated" (Q0.12.14) is enforced structurally by `validateOrderModification()` (`domain/simulation/order-modification.ts`) — e.g. `MODIFY_PRICE` rejects an intent that also sets `newStopPrice`/`newLimitPrice`; `MODIFY_PRICE` itself is rejected outright for a `STOP_LIMIT` order (ambiguous — it has two prices) or a `MARKET` order (no pending price exists).

## Distinct from Q0.10's position management (Q0.12.30)

`OrderModificationIntent` acts ONLY on a still-PENDING `SimulationOrder`. `PositionManagementInstruction` (Q0.10, `domain/position-management.ts`) acts ONLY on an already-OPEN `Position`. A `MODIFY_STOP` order-modification (this sprint — moves a STOP order's own trigger price before it fills) and Q0.10's `MODIFY_STOP` risk action (moves an open position's protective stop after it fills) are name-alike but share no type, no validator, and no evaluation function. `test/q12-separation-risk.test.ts` proves both operate correctly on the SAME strategy's lifecycle without ever colliding.

## Validation (Q0.12.19/20)

Every listed failure mode is rejected explicitly, never silently coerced:

- **Terminal-state guard**: `FILLED`/`CANCELLED`/`EXPIRED`/`REJECTED` reject EVERY operation, including a second `CANCEL` (Q0.12.16).
- **Directional price** (Q0.12.20): a BUY LIMIT must remain below the reference price, SELL LIMIT above, BUY STOP above, SELL STOP below — mirroring `bar-fill-model.ts`'s own BUY/SELL asymmetry (Q0.11), never a second directional convention.
- **Missing order**: `validateOrderModification(undefined, ...)` fails explicitly rather than the caller silently skipping it — a genuine bug found and fixed during this sprint's own race-fixture testing (see `docs/Q0.12_RACE_SEMANTICS.md`).
- **Unsupported operation**: an unrecognized `modificationType` fails via exhaustiveness-checked `default` case, never silently ignored.

## Why no strategy-authored auto-trigger exists (a deliberate scope boundary, not an oversight)

Q0.10/Q0.11 detected MQL patterns (breakeven/trailing conditions, `OP_BUYLIMIT`/`CTrade.BuyStop`) and reduced them into `RiskSpecification`/`EntryRule` fields evaluated automatically every bar. Building the equivalent for order modification would require a NEW `RiskSpecification`-level "pending order management policy" (e.g. "cancel if not filled within N bars," "trail the limit as price moves") — a genuine new feature, not a formalization of an existing one. Q0.12's own DoD asks for the CONTRACT and ORCHESTRATOR to exist and be proven (Q0.12.14/15/16/17/18), not for MQL detection of `OrderModify()`/`OrderDelete()` call sites. `SimulationConfig.orderModifications` is therefore a deterministic, declarative schedule (known before the run starts, exactly like the `bars` array itself) — never something inferred from live strategy conditions during the run. A future sprint building a real "when to modify" POLICY would consume the SAME `OrderModificationIntent`/`applyOrderModification` machinery this sprint built, not replace it.
