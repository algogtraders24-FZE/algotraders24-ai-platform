# Q0.1 Strategy Library Audit

Subject: `quant-engine/spec_engine/strategy_library.db` (SQLite, 2,629,632 bytes, mtime 2026-08-22 23:19).

## 1. Where strategies are stored

Single table `library` (+ SQLite's internal `sqlite_sequence`), 1,764 rows, 4 indexes (`idx_library_symbol_tf`, `idx_library_pf`, `idx_library_dd`, `idx_library_robustness`).

## 2. Format

Each row is one strategy: identifying columns (`name`, `symbol`, `timeframe`, `trigger_key`, `filter_key`, `risk_preset`), computed backtest metrics (`trades_total`, `win_rate_pct`, `profit_factor`, `total_return_pct`, `max_drawdown_pct`, `final_balance`), walk-forward robustness metrics (`wf_valid_folds`, `wf_pct_profitable`, `wf_avg_fold_pf`, `wf_min_fold_pf`, `wf_robustness_score`), and a `spec_json TEXT NOT NULL` column holding the full JSON Spec (see §3 of [Q0.1_QUANT_INVENTORY.md](Q0.1_QUANT_INVENTORY.md) for the schema shape — `indicators`/`entry_long`/`entry_short`/`risk`/`built_from`).

## 3. Complete definitions, templates, or metadata-only?

**Complete, independently re-runnable strategy definitions**, not templates or metadata stubs. Verified by reading back full `spec_json` content on sample rows (below) — every row carries the entire Spec: indicator definitions, entry conditions, risk block, and provenance (`built_from`: which trigger/filter/risk-preset combination produced it). `COUNT(DISTINCT spec_json) = 1764` — no duplicate specs.

## 4. Content coverage per strategy

| Element | Present? |
|---|---|
| Indicators | Yes — full `indicators` list per spec |
| Entry conditions | Yes — `entry_long`/`entry_short`, ANDed comparisons only (no OR/NOT, no nesting) |
| Exit conditions | **No explicit exit-condition list** — exits are entirely SL/TP-driven via the `risk` block (ATR-based or fixed-distance), not a separate `exit_long`/`exit_short` rule set |
| Stop-loss / take-profit | Yes — `risk.sl_mode`/`tp_mode` (ATR or PIPS), plus breakeven/trailing/partial-close thresholds on `template_builder`-generated specs |
| Risk rules | Yes, but scoped to per-trade sizing/exit management only — no portfolio-level `maxExposure`/`maxPositionSize` equivalent |
| Timeframe | Yes — single timeframe per spec (`"1h"`/`"4h"`) |
| Instruments | Yes — single symbol per spec (`"EURUSD"`/`"XAUUSD"`) |
| Parameters | Implicit only, baked into `indicators[].period` etc. and `built_from.trigger_params`/`filter_params` — no separate declared-parameter-with-default/min/max structure the way the new `StrategySpec.parameters` has |

## 5. Mapping to the new StrategySpec

**Partially compatible, with real gaps**:
- Entry conditions (`entry_long`/`entry_short`, flat ANDed comparisons) map mechanically onto an `and(comparison(...), comparison(...))` `Expression` tree in the new `StrategySpec` — this direction is straightforward.
- SL/TP-only exits do **not** map onto the new `ExitRule[]` shape, which expects an explicit `Expression` condition — a Spec's SL/TP-driven exit has no equivalent `ExitRule` today; representing it would require either (a) treating stop/target purely as `RiskSpecification.stopLoss`/`takeProfit` (which the new domain model already supports) and leaving `exitRules` empty, or (b) extending `RiskSpecification` to carry the breakeven/trailing/partial-close fields these specs actually use, neither of which exists yet.
- `built_from` (wizard provenance) has no equivalent field in the new `StrategySpec` — would need to go into `StrategyMetadata.tags` or `description` as unstructured info, or a new field.
- No `StrategyIdentity.strategyId`/`version` equivalent exists in the old Spec at all (see §8 below) — every migrated spec would need these synthesized.
- **Marked INCOMPATIBLE / REQUIRES DESIGN**: the breakeven/ATR-trailing/partial-close/daily-loss-halt/session-hours fields that `template_builder`-generated risk blocks carry have no home anywhere in the current `RiskSpecification` — do not force these into the existing `StopLossRule`/`TakeProfitRule` unions.

## 6. Duplicated or invalid strategies

- **No duplicates**: `COUNT(DISTINCT spec_json) = COUNT(*) = 1764`.
- **Not all are meaningfully valid/useful as trading strategies**: 186 rows have `trades_total = 0` (no trade ever fired over the backtest window), 231 rows have `profit_factor IS NULL` (no losing trades to divide by, or zero trades), and 365 rows have `wf_robustness_score IS NULL` (too few trades per walk-forward fold to score at all). A naive "sort by profit_factor DESC" surfaces exactly the overfitting trap walk-forward scoring exists to catch: the top-3 XAUUSD/1h rows by profit_factor (8.65, 5.59, 4.76) all have only 9-11 total trades and `wf_valid_folds = 0` — i.e., unscoreable, statistically thin results that should not be trusted despite the impressive-looking profit factor.
- 1,383 of 1,764 rows clear a basic `trades_total >= 30` bar; 1,399 of 1,764 have `wf_valid_folds >= 3` (enough for a robustness score to exist at all).

## 7. Tests

**None.** No test file references `strategy_library.db`. The only quality gate applied to any row's data is the walk-forward scoring computed once at generation time (Aug 22 23:19) and stored statically — there is no re-validation mechanism.

## 8. Provenance / version information

**None, at the schema level.** No `spec_version`, `generated_at`, or content-hash field exists anywhere in the Spec schema or in any `library` table column (confirmed by the full column list in Q0.1_QUANT_INVENTORY.md's source audit). The only provenance is `built_from` (wizard choices: trigger/filter/risk-preset keys) on `template_builder`-generated specs, which records *what produced the spec*, not *when* or *against which code version*. File-level provenance is the closest available signal: `strategy_library.db` has mtime **2026-08-22 23:19**, while the more realistic execution engines (`execution_mtf.py`, `execution_tick.py`) were added later, mtime **2026-08-23 23:02–23:03** — roughly a day after the library was built.

## 9. Dependency on the old Quant runtime

Yes, entirely — every row's metrics were computed by `spec_engine/runner.py`'s bar-level backtest loop (the coarser of the three execution engines that exist in `quant-engine/`), which itself imports `RiskConfig`/`summarize` from `quant_engine/engine.py`. The library cannot be regenerated or re-scored without that full dependency chain (see [Q0.1_QUANT_INVENTORY.md](Q0.1_QUANT_INVENTORY.md) §Q0.1.4 dependency graph).

## 10. Production usage

**None.** No file outside `quant-engine/` reads `strategy_library.db` or imports `library_search.py`/`library_generator.py` (confirmed by the repo-wide reference search in Q0.1_QUANT_INVENTORY.md §Q0.1.5). It is consumed only by `quant-engine/demo_library.py`/`demo_library_v2.py` within the same directory.

## Library Structure Summary

```
library (1,764 rows)
  ├─ ('EURUSD', '1h'): 588 rows
  ├─ ('XAUUSD', '1h'): 588 rows
  └─ ('XAUUSD', '4h'): 588 rows
       588 = 8 triggers × 4 filters × 3 risk presets (with per-trigger/filter param grids folded in)
```

Only **three symbol/timeframe combinations** are covered — this is not a broad library across many instruments, it is three deep grids over a fixed trigger/filter/risk parameter space.

## Representative Example (full, unabridged — top result by profit_factor, XAUUSD 1h)

```
id=351  bb_reversion[period20_mult2.0] + rsi_midline[period14] + aggressive
        trades_total=9  win_rate_pct=87.5  profit_factor=8.65
        total_return_pct=8.7  max_drawdown_pct=-1.11  final_balance=10869.61
        wf_valid_folds=0  wf_robustness_score=null   <- too few trades/fold to score; NOT a trustworthy result
```
This is a real, complete Spec — but exactly the kind of thin-sample result the sprint's "never auto-trust" rule (Q0.1.9) exists to guard against.

## Reusable Concepts

- The **flat-AND condition list + separate risk block** shape is a clean subset that maps mechanically onto `StrategySpec.entryRules[].condition` as an `and(...)` `Expression`.
- The **walk-forward robustness scoring methodology** (`pct_folds_profitable`, `avg_fold_pf`, `min_fold_pf`, composite `robustness_score`) is a genuinely useful technique independent of this specific library — it directly demonstrates why `at24-quant-engine`'s future `BacktestResult.metrics` should carry equivalent fields, and is exactly the kind of signal that should gate any future migration sampling (§Stage 3 below).
- The **`built_from` provenance pattern** (recording which deterministic generator choices produced a spec) is a reasonable precedent for extending `StrategyMetadata`.

## Incompatible Concepts

- SL/TP-only exits with no `ExitRule` equivalent (§5).
- Breakeven / ATR-trailing / partial-close / daily-loss-halt / session-hours risk fields — no home in current `RiskSpecification` (§5).
- No `strategyId`/`version`/content-hash — every migrated spec needs these synthesized, not extracted.

## Missing Metadata

Generation timestamp, code/engine version, content hash, human-authored rationale — none exist per-row (§8).

## Migration Difficulty

**Moderate for the happy path (entry conditions), high for full fidelity (risk management, provenance, re-validated metrics).** The mechanical spec-shape translation is easy; the metrics currently stored are **stale relative to the more realistic execution engines built after the library was generated** (see `quant-engine/output/compare_engines_v2.log`'s real finding: the same "Bollinger Mean Reversion" spec diverges from -15.33%/-31.26% max-drawdown under the coarse engine to -140.78% max-drawdown, `account_blown=True`, under the 1-minute-replay engine) — so no migrated strategy's stored metrics should be trusted without re-backtesting through a higher-fidelity engine first.

## Recommended Future Migration Approach (staged, per Q0.1.9 — none of this happens in Q0.1 itself)

1. **Stage 1 — Audit** (this document; done).
2. **Stage 2 — Classify**: partition the 1,764 rows by `wf_valid_folds >= 3 AND wf_robustness_score IS NOT NULL` (1,399 rows) vs. the remainder (365 unscoreable rows) — treat the unscoreable set as excluded from any migration sample by default, not as "top candidates" merely because a raw profit_factor looks high.
3. **Stage 3 — Select a small representative sample**: from the scoreable 1,399, pick by `wf_robustness_score` (not `profit_factor`), across all three symbol/timeframe groups, capped small (e.g. 10-20 total) — never a naive top-N-by-return sort, given the demonstrated overfitting trap in §6.
4. **Stage 4 — Map to StrategySpec**: mechanical translation of `entry_long`/`entry_short` to `Expression` trees; explicit design decision (not silent default) for how each sample's SL/TP/breakeven/trailing fields are represented, given the gap in §5.
5. **Stage 5 — Test semantic equivalence**: re-run each sampled spec's entry logic through both the old `runner.py` and the new `at24-quant-engine` expression evaluator against the same historical bars, and confirm identical entry-rule firing before trusting any migrated `StrategySpec`.
6. **Stage 6 — Migration tooling**: only build a translator/CLI if Stage 4/5 prove the mapping is stable across the sample; do not build tooling speculatively ahead of that proof.
7. **Stage 7 — Batch migration**: only after tooling is validated, and only for the scoreable subset.
8. **Stage 8 — Validate migrated strategies**: **re-backtest every migrated strategy through the newer, more realistic execution model** (the equivalent of `execution_mtf.py`/`execution_tick.py`, once such a component exists in `at24-quant-engine`) before treating any of its stored metrics as current — given the demonstrated ~9x drawdown divergence between engines, the `strategy_library.db` numbers must never be copied forward as-is.

**Hard rule carried forward from the sprint brief**: none of the 1,764 strategies become trusted merely by surviving conversion to `StrategySpec`. They remain research candidates pending independent evaluation, exactly as `quant-engine/reports/INTEGRATION_DECISION.md` (the prior session's own conclusion) already states for promotion into M-Series Evidence.
