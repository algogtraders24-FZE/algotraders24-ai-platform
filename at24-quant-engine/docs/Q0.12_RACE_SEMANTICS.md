# Q0.12 — Race Semantics

## The one governing rule (Q0.12.22/23/24)

`SimulationConfig.orderModifications` schedules an intent for a specific `atBarIndex`. Within that bar's processing, the NEW "Step 0.5" (apply scheduled modifications) always runs BEFORE the existing Step 1 (fill/expiration resolution) — for both `simulation-engine.ts` (D1) and `multi-fidelity-engine.ts` (D2/D3, evaluated once per PARENT bar, ahead of any child-bar walking). This is the ENTIRE rule; every race resolves from it alone, never from wall-clock timing or an incidental code-path ordering.

## The five required race fixtures (`test/q12-race-fixtures.test.ts`)

| Fixture | What it proves |
|---|---|
| `CANCEL_BEFORE_TRIGGER` | A cancel scheduled for the SAME bar the order would otherwise trigger wins — Step 0.5 removes the order before Step 1 ever gets a chance to fill it |
| `TRIGGER_BEFORE_CANCEL` | The order fills on an EARLIER bar than a later-scheduled cancel — the cancel attempt targets a `FILLED` (terminal) order and is explicitly REJECTED (`ORDER_MODIFICATION_REJECTED` recorded), never silently ignored or somehow undoing the fill |
| `MODIFY_BEFORE_TRIGGER` | A modification scheduled for the SAME bar the order would otherwise trigger applies first — the fill uses the NEW price, never the original |
| `TRIGGER_BEFORE_MODIFY` | Symmetric to `TRIGGER_BEFORE_CANCEL` — a modify attempt against an already-`FILLED` order is rejected, the fill price never retroactively changes |
| `SAME_TIMESTAMP_SEQUENCE_ORDER` | The control case: absent any scheduled modification, the same bar fills normally — proving the other four fixtures' outcomes genuinely depend on Step 0.5 existing, not on some other incidental cause |

## A real bug this sprint's own race-fixture testing found and fixed

The original Step 0.5 implementation silently `continue`d when a scheduled intent's target order was missing (already filled/cancelled/expired) — a modify/cancel attempt against a terminal order produced NO record at all, rather than the explicit `ORDER_MODIFICATION_REJECTED` event Q0.12.19 requires. `validateOrderModification()` already handled `order: undefined` correctly (returns a clear failure) — the bug was that the calling code's own early-exit guard (`if (!target || ...) continue`) bypassed validation entirely for the missing-order case, discovered when `TRIGGER_BEFORE_CANCEL`/`TRIGGER_BEFORE_MODIFY` failed their `assert.ok(eventsByType["ORDER_MODIFICATION_REJECTED"])` checks. Fixed by only short-circuiting on an instrument-symbol mismatch (a legitimate "not this loop's concern" case) and always routing a missing/terminal order through the SAME explicit validation-and-record path — mirrored identically into both `simulation-engine.ts` and `multi-fidelity-engine.ts`.

## No new ordering mechanism (Q0.12.22's own instruction)

Fills, positions, and trades continue to use Q0.5's existing `EventQueue` `(timestamp, sequence)` ordering entirely unchanged. Modification scheduling is declarative CONFIGURATION (known before the run starts, like `bars` itself), not a second event-processing pipeline — it never competes with or reorders the actual event queue.
