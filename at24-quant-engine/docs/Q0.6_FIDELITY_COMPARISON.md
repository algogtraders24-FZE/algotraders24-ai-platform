# Q0.6 Fidelity Comparison

## `compareFidelities()` (Q0.6.32-35)

`runtime/fidelity/fidelity-comparison-engine.ts`'s `compareFidelities(baseline, compared)` takes two `MultiFidelitySimulationResult`s produced from the SAME `bars`/`strategySpec`/`base` config (differing only in `fidelity`) and returns a `FidelityComparison`:

```ts
interface FidelityComparison {
  baselineFidelity; comparedFidelity;
  baselineResultHash; comparedResultHash;
  identical: boolean;
  baselineTradeCount; comparedTradeCount;
  netPnlDelta: number;
  matchedTrades: readonly TradeMatch[];       // { baselineTradeId, comparedTradeId, priceDelta, timingDelta }
  unmatchedBaselineTradeIds: readonly string[];
  unmatchedComparedTradeIds: readonly string[];
  differenceClassification: "IDENTICAL" | "PRICE_ONLY" | "TIMING_ONLY" | "PRICE_AND_TIMING" | "STRUCTURAL";
}
```

**Trade matching is POSITIONAL** (index `i` of one ledger against index `i` of the other) — correct under NETTING's single-position-per-instrument model, where a finer fidelity can only ever refine WHEN/AT-WHAT-PRICE an existing trade happened, never conjure an unrelated trade ahead of another. If the resultHashes are equal, the function short-circuits to `IDENTICAL` without touching the ledgers at all.

## Classification rule (Q0.6.35)

- **`STRUCTURAL`**: trade COUNT differs — the finer fidelity changed WHICH trades occurred, not just their details. Takes priority over the other categories.
- **`PRICE_AND_TIMING`** / **`PRICE_ONLY`** / **`TIMING_ONLY`**: trade count/order matches; whether any matched pair's entry/exit PRICE differs, TIMESTAMP differs, both, or neither, determines the bucket.
- **`IDENTICAL`**: only reachable via the resultHash short-circuit, or when every matched trade is byte-identical despite the overall hash differing for a reason unrelated to trades (e.g. provenance-only differences) — the classification is about the LEDGER, the boolean `identical` field is about the WHOLE RESULT; they can, in principle, disagree, and callers should treat `identical` as authoritative for "is this run reproducible-equivalent" and `differenceClassification` as authoritative for "what changed in the trades."

`test/fidelity-comparison.test.ts`'s core proof, reusing Fixture A: comparing the D1 run (exits at the stop-loss, 96) against the D2 run (exits at the take-profit, 111) for the SAME bars/strategy classifies as `PRICE_AND_TIMING` — both the exit price (96 vs 111) and the exit timestamp (parent bar 4's close vs. child 0's earlier intrabar timestamp) differ, with `netPnlDelta = 15` (D2's `+9` minus D1's `-6`).

## Direction sensitivity

`compareFidelities(a, b)` and `compareFidelities(b, a)` report the same `identical` bit and the same `differenceClassification`, but `netPnlDelta` and each `TradeMatch`'s deltas negate — `compareFidelities` has no notion of which side is "canonical," only which argument the caller passed first (`test/fidelity-failure-catalog.test.ts` item 16).

## What Q0.6 does NOT do

No N-way comparison (only pairwise `baseline`/`compared`). No automatic "which fidelity is more accurate" verdict — `FidelityComparison` reports WHAT differed, never which result is "right"; that judgment (ground truth vs. simulated) is outside this sprint's scope and remains a future `PlatformDiscrepancyReport`-style concern (`Q0.4_BACKTEST_ARCHITECTURE.md`). No persistence — a `FidelityComparison` is computed on demand from two in-memory results.
