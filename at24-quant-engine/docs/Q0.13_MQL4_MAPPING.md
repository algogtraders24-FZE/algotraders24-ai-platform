# Q0.13 — MQL4 Pending-Order-Management Mapping

## Detected call shapes (`runtime/mql-importer/semantic-analyzer.ts`)

| Source pattern | `functionName` | `targetArgIndex` | `priceArgIndex` | `expirationArgIndex` |
|---|---|---|---|---|
| `OrderModify(ticket, price, sl, tp, expiration, [color])` | `"OrderModify"` | 0 | 1 | 4 |
| `OrderDelete(ticket)` | `"OrderDelete"` | 0 | — | — |

`isMethodCall` is `false` for both (bare identifier calls, never a `MemberExpression`) — MQL4 has no `CTrade`-equivalent object model.

## Target resolution

`resolvePendingOrderTarget()` inspects `args[targetArgIndex]` only: a plain identifier (the common `ticket`/`g_ticket` pattern) resolves `TICKET`; `_Symbol`/`Symbol()`/a string literal resolves `SYMBOL` (rare for MQL4's ticket-first calls, but structurally supported identically to MQL5); anything else (a nested call, e.g. `GetActiveTicket()`) resolves `UNKNOWN`.

## Condition resolution

Two provable shapes, both reused directly from earlier sprints' own arithmetic reconstruction:

1. **`OrderType() == <OP_CONST>`** (or the reverse operand order) → `ORDER_TYPE_FILTER`, `orderTypeConstant` = the raw constant text (`"OP_BUYSTOP"`/`"OP_SELLSTOP"`/`"OP_BUYLIMIT"`/`"OP_SELLLIMIT"`). Mapped to a concrete `{orderType, side}` pair via `MQL_ORDER_TYPE_CONSTANT_MAP` (`domain/pending-order-management-policy.ts`) — the SAME table `Q0.11_PLATFORM_MAPPING.md`'s own `OrderSend` command mapping already established, reused rather than reinvented.
2. **`<currentPrice> - OrderOpenPrice() >= <literal>`** (or the entry-price-on-the-right variant) → `FAVORABLE_DISTANCE`, reusing `resolveFavorableTriggerDistance()` verbatim (Q0.10's own private method, called from the new detector). `OrderOpenPrice()` doubles as "this pending order's own set price" in MQL4's flat ticket model — the SAME accessor Q0.10 already reads for a FILLED position's entry price.

Anything else (a bare `newSL > currentSL` comparison, a `TimeCurrent()`-based trigger, an unresolved custom function call in the test) resolves `UNKNOWN` — the raw source text is still preserved via `describeExpr()`.

## Operation resolution (`ir-generator.ts`'s `toOperationIR`)

- `OrderDelete`/`OrderModify` are the ONLY two MQL4 functions this importer compiles into a real operation.
- `OrderDelete` always compiles to `CANCEL_PENDING` (target/condition provability permitting).
- `OrderModify` compiles to `MODIFY_STOP`/`MODIFY_LIMIT` ONLY when BOTH: (a) the price argument (`args[1]`) resolves to a provable `<price> ± <literal>`/`<price> ± (<atrVar>*<literal>)` arithmetic shape (`resolveRiskLegBinding`, reused verbatim), AND (b) the guarding condition is a provable `ORDER_TYPE_FILTER` (the ONLY way this importer can know, statically, whether the ticket names a LIMIT or a STOP order — see `Q0.13_COMPILATION.md`). Every other case — SL/TP-only modification, expiration-only modification, an unresolved price function, a favorable-distance-but-not-type-filtered condition — resolves `UNKNOWN`.

## What is deliberately NOT claimed

An `OrderModify` call changing ONLY `stoploss`/`takeprofit` (MQL4's flat model reuses this exact call for a FILLED position's protective-level adjustment) is recorded here too (dual-booked alongside Q0.10's own `ManagementPatternSite`), but its operation always resolves `UNKNOWN` in THIS contract — that behavior remains entirely owned by `RiskSpecification.breakeven`/`trailingStop` (Q0.10), never re-executed a second time by Q0.13's policy.
