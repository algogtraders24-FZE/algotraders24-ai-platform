# Q0.12 — Cancel & Replace Semantics

## Cancel (Q0.12.16)

`CANCEL` transitions a non-terminal order to `CANCELLED` via `transitionOrder()` (Q0.4/Q0.5, unmodified) — the SAME state machine every other transition already uses, never a second one. Legal only from `ACCEPTED`/`TRIGGERED`/`PARTIALLY_FILLED` (per `VALID_TRANSITIONS`); `FILLED → CANCELLED` and `CANCELLED → CANCELLED` are both illegal and throw deterministically (`test/q11-failure-catalog.test.ts` items 10/13, `test/q12-failure-catalog.test.ts` items 5/14).

## Replace (Q0.12.17)

`REPLACE` is explicitly a two-step operation, never an in-place mutation:

1. The OLD order transitions to `CANCELLED` with `terminalReason: "replaced: <reason>"`.
2. A genuinely NEW `SimulationOrder` is created (via `createOrder()`, Q0.5, unmodified) with:
   - `parentOrderId` set to the old order's `orderId` — an explicit, queryable link, never inferred from timing or proximity.
   - `replacementReason` set to the intent's `reason`.
   - Its own new, deterministic identity (`${strategyVersion}:${symbol}:${side}:${orderType}:${creationTimestamp}:${sequence}`) — the NEW `creationTimestamp` (the bar the replace was applied) guarantees a different orderId than the parent, even if every other field is identical (Q0.5.6's own identity formula, reused unchanged).
   - Any fields NOT specified in the intent (`newLimitPrice`/`newStopPrice`/`newExpiration`) carried over from the original order unchanged.

`applyOrderModification()` (`runtime/simulation/order-modification.ts`) returns the cancelled order plus a `CreateOrderInput` for the caller to actually create — it never mints the new order's `sequence` itself, since only the simulation loop (which owns the event queue) can supply a deterministic one (Q0.5.6).

## Why REPLACE never silently mutates

`SimulationOrder` fields (other than status/fill bookkeeping) are otherwise immutable once created — allowing REPLACE to just overwrite `limitPrice`/`stopPrice` in place would blur the line between "this order was always at this price" and "this order's price changed partway through," breaking any provenance/audit trail that assumes one order = one price history. The cancel+recreate design keeps the OLD order's full original state permanently visible (a real historical record: it existed, at its original price, until it was cancelled for replacement) while the NEW order starts a clean history of its own.

## Proven

`test/q12-golden-fixtures.test.ts`'s `REPLACE_ORDER` (full end-to-end: old cancelled, new fills at the new price, identity differs); `test/q12-failure-catalog.test.ts` items 14 (a replaced order cannot itself be replaced again — it's `CANCELLED`, terminal), 15 (an invalid REPLACE intent — nothing to change — never reaches order creation at all), 17 (the new order's identity never collides with its parent).
