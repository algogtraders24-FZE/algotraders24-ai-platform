# Q0.9 Semantic Loss

Every `ReductionResult` carries a `semanticLoss: SemanticLossReport` alongside its `status`, `unsupportedFeatures`, and `approximations` — the same "never hide a gap" discipline Q0.7's `UnsupportedSemantic`/`ApproximationRecord` contract already established, applied one layer further to the reduction step itself.

## The four-tier `semanticStatus` computation (Q0.7.32's own invariant, correctly enforced)

Q0.7's structural rule: `APPROXIMATED` requires `provenance.approximations.length > 0` — an approximation must never be silently implied by an unsupported-semantic note alone. `ir-generator.ts` computes the tier in this order:

1. **`UNSUPPORTED`** — any `BLOCKING`-severity `unsupportedSemantics` entry exists.
2. **`APPROXIMATED`** — a formal `ApproximationRecord` exists (e.g. G01's `percent-equity-risk` sizing inference from `InpRiskPercent`).
3. **`SEMANTIC_EQUIVALENT`** — only non-blocking (`WARNING`) `unsupportedSemantics` notes exist, with no formal approximation.
4. **`EXACT`** — nothing at all.

This sprint's own development caught a real bug here: `semanticStatus` was originally claimed `APPROXIMATED` whenever *any* non-blocking unsupported-semantic note existed, even with zero `ApproximationRecord`s — which fails Q0.7's own validator (`"provenance.semanticStatus is APPROXIMATED but provenance.approximations is empty"`) the moment a real fixture had only WARNING-level notes. Fixed to the four-tier logic above; verified against the full regression suite.

## Disclosed assumptions vs. actual blocks (two independent axes)

A strategy can be `SEMANTIC_EQUIVALENT` (a disclosed, reasonable platform-default assumption) and still be execution-*ineligible* for an unrelated reason — these are genuinely independent axes, exercised directly by `test/q09-failure-catalog.test.ts` items 9 and 12 (`fixtureTimezoneSensitive`, `fixturePineRequestSecurity`). Disclosure is never a substitute for eligibility, and eligibility failure is never evidence of a disclosure gap.

## The one legitimate "assume the platform default" inference (Q0.9's own, narrow addition)

MT4/MT5 netting-mode accounts have a *documented* default behavior: accumulate same-direction fills, reverse atomically on an opposite-direction fill. Q0.9's `ir-generator.ts` may assume this default — with an explicit WARNING-level `UnsupportedSemantic` disclosure — **only when** `model.positionQueries.length === 0`, i.e. the source contains no `PositionSelect`/`PositionsTotal`/`OrderSelect`/etc. call anywhere. The absence of custom position-management code is the actual signal, not a guess: it is direct, checkable evidence that nothing in the source could override the platform default. The moment even one such call is detected (G01's real case: 17 of them), the importer stays on the conservative `REJECT`/`PLATFORM_DEFINED` path unchanged from Q0.8 — custom logic might override the default in a way the importer cannot see, so it must not assume anything.
