# Q0.13 — MQL4/MQL5 Order Modification Research

Real, cited platform facts, distinguishing syntactic detection, semantic interpretation, and execution behavior — never assumed identical merely because two functions share a name across dialects.

## MQL4 — the flat-ticket model

MQL4 has no Order/Deal/Position separation: a single numeric **ticket** identifies either a pending order OR an open position, and the SAME functions act on both depending on the ticket's current state.

- **`OrderModify(ticket, price, stoploss, takeprofit, expiration, [arrow_color])`** — for a PENDING order, `price` changes its trigger/limit price; for an OPEN position, `price` is ignored by the platform (a position has no "price" to move) and only `stoploss`/`takeprofit`/nothing-else apply. This importer does not attempt to distinguish "pending" from "open" at the CALL SITE (the same call shape serves both) — it records the call, resolves what it structurally can (target, condition, price/expiration arguments), and lets `toOperationIR`'s own order-type-filter requirement (see Q0.13_COMPILATION.md) decide whether enough is known to compile a real operation.
- **`OrderDelete(ticket)`** — cancels a PENDING order only; calling it on an open position's ticket is a broker-level error (MQL4 returns `false`, not silently a close). Distinct from `OrderClose()`.
- **`OrderSelect(ticket, select_flag, pool)`** / **`OrderSelect(index, select_flag, pool)`** — the two-argument-shape overload selects EITHER by ticket number OR by pool index depending on `select_flag` (`SELECT_BY_TICKET` vs `SELECT_BY_POS`) — a genuinely different targeting mechanism this importer does not attempt to disambiguate (both are recorded structurally the same way: an argument-shape-based target resolution, never a `select_flag`-aware one — see `Q0.13_TARGET_RESOLUTION.md`).
- **`OrderType()`** returns one of `OP_BUY`/`OP_SELL`/`OP_BUYLIMIT`/`OP_SELLLIMIT`/`OP_BUYSTOP`/`OP_SELLSTOP` for the CURRENTLY SELECTED order/position — its own value never changes once an order is created (a pending order's type is fixed at creation), which is exactly why a guard of the shape `if(OrderType()==OP_BUYSTOP)` is fully provable/deterministic without needing any live state beyond the order's own already-known type.
- **Modification return/error behavior**: `OrderModify`/`OrderDelete` return `bool`; a `false` return (checked via `GetLastError()`) means the broker rejected the request (e.g. price too close to market, "Invalid stops"). This importer has no notion of broker-side rejection at all — AT24's own `validateOrderModification` (Q0.12) is the ONLY rejection authority, and its reasons (directional-price violation, terminal-order, missing fields) are a DIFFERENT set of checks than a real MT4 broker would apply. Never conflated.
- **Expiration** is a `datetime` (an epoch-seconds absolute instant), only meaningful when the order's own `type_time` implies `ORDER_TIME_SPECIFIED`-equivalent behavior (MQL4 has no explicit `type_time` field — a non-zero `expiration` argument alone signals "this order expires at this time").

## MQL5 — the Order → Deal → Position three-stage model

- **`CTrade::OrderModify(ticket, price, sl, tp, type_time, expiration, stoplimit)`** — modifies a PENDING order ONLY. Structurally impossible to apply to an open position (there is no "price" field on a position at all in MQL5's object model).
- **`CTrade::PositionModify(symbol_or_ticket, sl, tp)`** — modifies an OPEN POSITION's protective levels ONLY. A DIFFERENT method, a DIFFERENT underlying trade-server request (`TRADE_ACTION_SLTP`, vs `OrderModify`'s `TRADE_ACTION_MODIFY`). MQL5's own API keeps these structurally separate — this importer's distinct `functionName` literals (`"CTrade.OrderModify"` vs `"CTrade.PositionModify"`) mirror a REAL platform distinction, not an AT24 invention.
- **`CTrade::OrderDelete(ticket)`** — cancels a PENDING order (`TRADE_ACTION_REMOVE`).
- **`CTrade::PositionClose(symbol_or_ticket, deviation)`** — closes an OPEN position (`TRADE_ACTION_DEAL` with an opposite-direction volume). A genuinely different trade-server action than `OrderDelete`.
- **`OrderGetTicket(index)`** / **`OrderSelect(ticket)`** — select a pending order by POOL INDEX or by TICKET respectively, populating the "currently selected order" context `OrderGetDouble`/`OrderGetInteger` then read from.
- **`PositionSelect(symbol)`** / **`PositionSelectByTicket(ticket)`** — select an open position by symbol or ticket for `PositionGetDouble`/`PositionGetInteger` reads.
- **Netting vs hedging**: in NETTING mode (MT5's default, and the ONLY mode Q0.5/Q0.6 implement — see Q0.9.16), `PositionSelect(symbol)` returns AT MOST one position per symbol, making symbol-based targeting unambiguous. In HEDGING mode, multiple simultaneous positions per symbol exist and symbol-based targeting is genuinely ambiguous (a real semantic difference this importer does not attempt to resolve — Q0.13 remains a netting-only contract, matching the frozen engine's own scope).
- **Retcode/result semantics**: `CTrade`'s methods return `bool` and populate `ResultRetcode()`/`ResultComment()` on failure (e.g. `TRADE_RETCODE_INVALID_STOPS`). Exactly like MQL4, this is broker-level rejection semantics this importer does not model — AT24's own `validateOrderModification` is the sole rejection authority for simulated execution.

## Syntactic detection vs semantic interpretation vs execution behavior — kept genuinely separate

| Layer | What it does | Where |
|---|---|---|
| Syntactic detection | "this line calls a function literally named `OrderModify`/`CTrade.OrderDelete`/etc., with these argument expressions" | `runtime/mql-importer/semantic-analyzer.ts`'s new detector methods — zero trading-meaning assigned yet |
| Semantic interpretation | "this call's target resolves to TICKET/SYMBOL/UNKNOWN; this condition resolves to an order-type filter or a favorable-distance trigger; this operation resolves to CANCEL_PENDING/MODIFY_STOP/MODIFY_LIMIT/UNKNOWN" | `runtime/mql-importer/ir-generator.ts`'s `toTargetIR`/`toConditionIR`/`toOperationIR` |
| Execution behavior | "given this compiled, EXECUTABLE rule and the CURRENT bar's own data, does the condition hold, and if so what `OrderModificationIntent` results" | `runtime/simulation/pending-order-management.ts`'s `evaluatePendingOrderManagementPolicy`, feeding Q0.12's unmodified `validateOrderModification`/`applyOrderModification` |

MQL4 and MQL5 are NOT assumed equivalent anywhere: `functionName` is always the literal, dialect-specific call name (`"OrderModify"` vs `"CTrade.OrderModify"`), and the argument-index mapping for price/expiration genuinely differs between them (see `Q0.13_MQL4_MAPPING.md`/`Q0.13_MQL5_MAPPING.md`).
