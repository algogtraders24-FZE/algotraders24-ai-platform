# P4.9 — Optimization / Walk-Forward (Algo Testing Pro)

## R1 — Execution & Experiment Mechanics Audit (locked, no implementation)

Investigation only. Key finding: the Vercel platform has no `functions.maxDuration` override in `vercel.json` and (per the existing Hobby-plan constraint already documented for cron) no persistent background worker exists at all. This rules out any long-running in-memory sweep and locks all P4.9-A execution to **stateless, chunked, resumable, client-polled continuation** — the single most load-bearing constraint on the entire design that follows.

## R2 — Optimization Contract & Persistence Design (locked, no implementation)

**Scope**: Algo Testing Pro's own registry-strategy parameter optimization, explicitly separate from the unbuilt, unrelated "Quant Pro" product's own planned (and still unbuilt) walk-forward feature.

**Locked v1 contract**:
- Registry strategies only, no per-candidate recompilation. In practice this means the golden strategy alone today — `ref-ema-crossover` also has `parameters: []`, and this v1 explicitly does not manufacture parameters for it to force it into scope.
- AI-compiled strategies (`parameters: []`, unconditionally) and AI parameterization generally: explicitly excluded from P4.9-A.
- Objective: Profit Factor v1 (`grossProfit / abs(grossLoss)`, the engine's own existing `computeCoreMetrics()` — unmodified). A minimum-eligible-trades threshold is a **validity guard**, not a second objective — `profitFactor` is `Infinity` whenever `grossLoss === 0 && grossProfit > 0`, which is trivially reachable with too few trades to mean anything.
  - §4 Max candidate count: **256**.
  - §5 Minimum eligible trades: **20** — measured, not assumed, via a disposable seeded-random-walk audit script (`at24-quant-engine/test/_p49r2t5-tradecount.ts`, run then deleted) exercising the golden strategy's SL/TP grid at both `maxRangeDaysFor()` bar ceilings (2016/4032 bars).
- Execution model: stateless/chunked/resumable (per R1's Vercel finding). No genuine parallelism required for v1 - atomic candidate claiming via `updateMany({ where: { id, status: "UNRUN" }, data: { status: "RUNNING" } })`, checking `count === 1`, relies on ordinary Postgres MVCC.
- Candidate identity: **deterministic** — `computeCanonicalHash({ experimentId, parameterValues })` (the engine's own existing universal identity primitive, Q0.2 family) — makes a retried chunk naturally idempotent: it re-derives the same hash and finds the row already claimed/completed.
- Candidate lifecycle: `UNRUN → RUNNING → COMPLETED → (REJECTED | CANDIDATE) → VALIDATED`. Reuses the engine's existing `ResearchResultStatus` vocabulary (`domain/research-result.ts`) with one disclosed addition — `RUNNING` — since that type models a completed research record, not a live in-progress claim; `VALIDATED` is reachable only via the engine's own real `markValidated()` guard, and only from `CANDIDATE`.
- Winner selection: at most one candidate per experiment ever holds `VALIDATED`, referenced denormalized on the experiment via `bestCandidateId` once selection completes.
- Wire format: `profitFactor` is `number | "Infinity" | null` on the API boundary — `JSON.stringify(Infinity) === "null"`, so raw JS `Infinity` is never serialized; DB storage stays a plain nullable `Float` (Postgres natively stores IEEE `Infinity`).
- Reproducibility: two distinct fingerprints, not one —
  - `strategyArtifactHash` (`computeSemanticStrategyHash(spec)`, already real, already reused for `AlgoTestRun.strategyHash`) answers "which exact strategy artifact was optimized?"
  - `fingerprint` (`computeCanonicalHash(...)` over the full experiment configuration — `strategyId`, `strategyArtifactHash`, `symbol`, `timeframe`, `startTime`, `endTime`, `searchSpace`, `objective`, `minEligibleTrades`, `candidateCap`) answers "which exact optimization experiment/configuration was performed?" and incorporates `strategyArtifactHash` as one of its own inputs.

  `strategyArtifactHash` is not a replacement for `fingerprint` — both are persisted, per the user's explicit correction during A.1 review.
- P4.9-B (deeper walk-forward semantics) and AI-parameterization: strictly deferred, out of this scope entirely.

**`frontend/prisma/migrations/20260908063000_add_optimization_experiments/migration.sql`** — hand-written, verified byte-for-byte against Prisma's own generated SQL via `prisma migrate diff --from-schema=<pre-edit schema.prisma> --to-schema=<post-edit schema.prisma> --script` (a direct schema-to-schema diff, no shadow DB, no `migrate dev`/`db push`). Purely additive: 2 new tables, 1 new column, 4 new indexes (one of them the `AlgoTestRun.experimentCandidateId` unique index), 2 new foreign keys. No historical backfill — every new NOT NULL column belongs to a brand-new table with no pre-existing rows; the one new column on the pre-existing `AlgoTestRun` table (`experimentCandidateId`) is nullable.

### Locked contract corrections applied during design review (before any code was written)

- **Fingerprint expanded**: not just the original 10 config fields — also `engineVersion` (`RUNTIME_VERSION`, read before any candidate executes) and `executionModel` (`dataFidelity`/`spreadModel`/`slippageModel`/`feeModel`/`latencyModel` names). `strategyArtifactHash` answers "which exact strategy artifact was optimized"; `fingerprint` answers "under exactly what conditions" and incorporates `strategyArtifactHash` as one of its own inputs — a strictly stronger reproducibility boundary, not a replacement.
- **Winner selection is automatic**, on experiment completion, from the `CANDIDATE`-status pool only (never `COMPLETED`/`REJECTED`/`FAILED`) — highest `profitFactor`, tie-broken by lowest `candidateHash` (lexicographic).
- **No `ResearchResult` stand-in**: the original design proposed exercising the engine's `markValidated()` domain guard via a constructed fake `ResearchResult` object purely for its throwing side-effect. Rejected in review as misleading coupling between two differently-shaped aggregates. Replaced with a conditional `updateMany({ where: { id, experimentId, status: "CANDIDATE" }, data: { status: "VALIDATED" } })`, `count === 1` required — the same transition guard, enforced directly against the real persisted row, no engine call.
- **TX1 (experiment creation) is an interactive transaction**, not array-style — the candidate rows need the experiment's just-generated `id`, which an array-style `$transaction([...])` cannot provide (both operations are constructed before either runs).
- **TX3 (finalization) is one full transaction**: ownership acquisition (`RUNNING` + `processedCandidates === totalCandidates` → `COMPLETED`), winner query, `CANDIDATE → VALIDATED`, and `bestCandidateId` all commit together or not at all. The original design's separate-writes version left a real window where an experiment could be externally `COMPLETED` with its winner still `CANDIDATE` — caught in review before implementation.
- **Chunk budget**: wall-clock, `OPTIMIZATION_CHUNK_BUDGET_MS = 8_000`, deliberately not coupled to any specific Vercel `maxDuration` value. Exact ordering: check budget → claim → execute → persist terminal state + increment (TX2) → finalize check (TX3) → re-check cancellation → loop. A claimed candidate always runs to its own terminal persistence, never aborted mid-flight.
- **Stale-`RUNNING` reclaim: explicitly not built.** A process killed between claim and terminal write strands that one candidate `RUNNING` forever — accepted as a known v1 limitation (leases/heartbeats were judged a disproportionate correctness-surface increase for a gap that may never occur in practice; a real occurrence in beta is the trigger for a dedicated recovery phase, not speculative infrastructure now).
- **`cancelledAt`** added back to `OptimizationExperiment` (a small additive migration on top of A.1) — deliberately not reusing `completedAt` for a genuinely different fact.
- **Cancellation** is an atomic conditional transition (`updateMany({ where: { status: { in: ["QUEUED","RUNNING"] } }, data: { status: "CANCELLED", cancelledAt } })`) — mutually exclusive with TX3's own ownership-acquiring update by construction (whichever commits first makes the other's `WHERE` match nothing). Honored at **chunk granularity**: a cancellation landing mid-chunk does not interrupt the candidate currently executing; the *next* `continue()` call claims nothing further.

### Conventions confirmed by investigation, then followed exactly (no new pattern introduced)

- `withContext(handler)` on every route; `getUserOrNull()` checked before any service call; `sessionUser.profile.id` is the sole `userId`, never a client-supplied value — identical to every existing private route.
- `withContext`'s `RouteHandler` has no Next.js `params` argument — `experimentId` is parsed from `ctx.path` via a small local `experimentIdFromPath()` helper, duplicated per file (matching the established convention — `runIdFromPath`/`strategyIdFromPath`/`positionIdFromPath` are each independently defined too, never shared). - `ErrorHandler.normalize()` collapses any non-`AppError` to a generic `500 INTERNAL`, discarding its own code. `OptimizationServiceError` is not an `AppError`, so every route that can receive one catches it explicitly and maps `.code` to the locked HTTP status — never left to fall through to the middleware catch-all.
- **Locked HTTP-status mapping**: every validation-shaped code from `createOptimizationExperiment` → `400` (mirrors `POST /runs`'s own convention for its equivalent codes); `NOT_FOUND` → `404`; `PROVIDER_ERROR` → `500` (the existing middleware-fallback status — explicitly **not** extended to `502`/`503` for this, even though `types/api.ts`'s `HttpStatusCode` union happened to gain those values from an unrelated parallel change during this tier; A.3 never touched that file). The application-level error identity (`code: "PROVIDER_ERROR"`) is preserved verbatim in the response body — only the transport status stays the existing `500`.
- Only request-*shape* is checked at the route (non-empty strings, `searchSpace` array shape) — every semantic check (parameter bounds, the 256 cap, date-range caps) stays exclusively in `optimization.service.ts`, never duplicated.
- A terminal `continue()` call is a plain `200` no-op (the service's own locked semantics) — `OptimizationErrorCode`'s unused `"ALREADY_TERMINAL"` member is never returned by any route, and was left untouched per the explicit decision that this minor cleanup doesn't belong in A.3.

### A.4-T2 — Monitor + Client-driven Continuation (implemented)

`/dashboard/algo-test-optimize/[experimentId]` (`app/dashboard/algo-test-optimize/[experimentId]/page.tsx`) — the same page this tier's own locked contract (`P4.9-A.4-T2-R1`, see below) designated as the eventual Results page too (one state-driven component, extended by later tiers, never replaced). Strictly scoped to monitor + continuation per the locked boundary — no cancel button, no winner/results presentation, no candidate table (later tiers).

**Locked P4.9-A.4-T2-R1 contract, implemented exactly:**
- Initial `GET /optimization/[experimentId]` always precedes any `continue()` call (covers fresh load, refresh, and a bookmarked URL alike).
- `QUEUED`/`RUNNING` both drive the loop; any of `COMPLETED`/`FAILED`/`CANCELLED` stops it — checked generically (`isTerminalStatus()`), so a future `CANCELLED` from a later tier's cancel button needs zero changes here.
- `continue()` fires immediately after the initial `GET` resolves (no artificial pre-delay); each subsequent `continue()` is scheduled with a **1000ms minimum floor** after the previous response, via `setTimeout` (never `setInterval` — the loop reschedules itself only after a response actually arrives).
- Ref-based in-flight guard (`inFlightRef`, not state) — never a duplicate `continue()` while one is outstanding.
- The exact `cancelled`-flag mount-effect convention already established by `AlgoTestPanel.tsx`/the Strategy Library detail page, extended to this async loop — a late response after `experimentId` changes or the component unmounts is never applied to state. `timeoutRef` is explicitly `clearTimeout`'d on cleanup (belt-and-suspenders alongside the flag).
- `PROVIDER_ERROR` (or any other `continue()` failure) **stops automatic polling**, preserves whatever state was last real (never fabricated), and shows the real server message via a manual-Retry `Alert` — never an automatic retry loop.
- Progress display sourced only from the real `processedCandidates`/`totalCandidates`/`status` fields — a small new progress-bar element (no existing primitive for this; built from existing tokens, not a new design system).
- Terminal state renders a plain, honest placeholder (status badge + "N/N candidates processed" + the real `errorMessage` when `FAILED`) — explicitly not a winner/results UI (T4's own scope).

### A.4-T3 — Cancellation UX (implemented)

Adds a Cancel button + confirmation `Modal` to the same Monitor page, wired to `POST /optimization/[experimentId]/cancel`. Still strictly no winner/results presentation, no candidate table (later tiers).

**One real correctness gap this tier's own audit found in T2's original code, fixed before it could ever surface as a live bug**: `runContinue()` applied every `continue()` response unconditionally. Once a `cancel()` response could also apply to the same `view` state, a `continue()` call already in flight when cancellation resolves could arrive *later* and silently overwrite the terminal `CANCELLED` state with whatever stale, non-terminal status that chunk found. Fixed by routing every response (GET, `continue()`, and `cancel()` alike) through one `applyResult()` function that tracks the latest applied status in a `statusRef` and discards any response once that ref is already terminal — the critical invariant locked for this tier: **no later-arriving response of either kind may un-terminal an already-terminal state.**

**Locked P4.9-A.4-T3 contract, implemented exactly:**
- Cancel button rendered only in the non-terminal branch (not a disabled ghost once terminal) — stays enabled throughout normal polling, never blocked by an in-flight `continue()` (no correctness reason to block it; the backend's own atomic `WHERE status IN (QUEUED,RUNNING)` on cancel already makes concurrent `continue()`/`cancel()` safe).
- Confirming the `Modal` (exact copy: *"The current candidate will finish before the optimization stops. Unprocessed candidates will not be executed."*) sets `cancelRequestedRef` immediately — stops scheduling any *further* `continue()` calls right away, but an *already* in-flight one is never aborted, only its late response is discarded per the invariant above.
- `CANCELLED` gets its own distinct copy/tone (`warning` `Badge`, "Cancelled — N/M candidates processed before cancellation.") — never the `COMPLETED` branch's "finished" framing.
- A failed `cancel()` call shows the real server message via its own `Alert`, and — since the experiment is presumably still `QUEUED`/`RUNNING` server-side, never assumed cancelled just because the client wanted it to be — resets `cancelRequestedRef` and resumes the polling loop automatically rather than leaving the UI stuck.

**One further real fix found only through live testing, not assumed**: the cancel-failure `Alert` never cleared once polling successfully resumed afterward — a stale "Could not cancel the optimization" banner would sit on screen indefinitely even after the experiment kept completing candidates normally. Fixed by clearing `cancelError` in the same place `continueError` already clears, on every successful `continue()` response.

**Verified live against the real, unmodified component.** The race in the critical invariant is inherently timing-sensitive and this environment's own tool round-trip latency made a fixed-duration delay unreliable to land a click inside a narrow window (an entire 5-chunk sequence completed in under 9 real seconds in testing, faster than a navigate-then-click round trip) — so the harness was built to hold a `continue()` response on a manually-resolved `Promise` instead of a wall-clock delay, making the race fully deterministic rather than probabilistic:
- Held `continue()` #1 in flight → confirmed cancellation (`CANCELLED`, `2/10`) → released the held response → confirmed the UI **stayed** `CANCELLED` (the late response was discarded, not applied) — the critical invariant, proven directly, not inferred.
- A scripted cancel failure showed the real error, left the experiment's real state untouched, and automatically resumed polling once released — the resumed sequence correctly obeyed the existing in-flight guard (no duplicate `continue()` fired for the still-outstanding original call).
- The stale cancel-error banner correctly cleared the moment continuation next succeeded, confirming the second fix above.

Full regression green: `tsc` 0 errors; ESLint 0 new problems (12 pre-existing, unrelated); all 13 pre-existing algo-test/strategy validators + A.2 (14/14) + A.3 (26/26) unchanged. No dedicated T3 validator - same disclosed reasoning as T1/T2.

- **Table:** the existing `components/ui/Table` shell (scrollable, no virtualization — the `TradeTable.tsx` precedent). **No pagination** — every candidate row, up to the 256 cap. Never re-sorted client-side.
