# Q0.9 G01 Reduction

G01 (`ea-research/G01_LiquiditySweep_MSS_FVG/AT24_GOLD_G01_LiquiditySweep_MSS_FVG.mq5`) is Q0.9's primary real-world negative case, tested in `test/q09-g01-reduction.test.ts`. **G01 remaining `BLOCKED` at the reduction/compilation layer is itself the pass condition** — never something to work around by altering G01's own source, which is read-only throughout this package (`fs.readFileSync`, never an ES `import`, never written to).

## Why G01 blocks — three independently-sufficient reasons, unchanged from Q0.8

1. **Unresolvable entry/exit state machine.** G01's real entry logic is a multi-bar liquidity-sweep + market-structure-shift + fair-value-gap sequence spanning multiple `OnTick()` invocations and cross-file state. `buildRealConditionEntry()`'s single provable shape (`if (indicatorA <op> indicatorB)` or `if (indicator <op> literal)`, with an order call directly inside the winning branch) cannot match this — correctly, since attempting to would require inventing behavior Q0.9 is explicitly forbidden from inventing. The entry stays the honest placeholder, tagged `"entry/exit signal logic"` as a BLOCKING unsupported semantic (Q0.8's own finding, still true after Q0.9's real-condition reconstruction was added — the reconstruction only recognizes a narrow shape that G01's real logic doesn't fit, so it correctly does nothing here).
2. **Unresolved SL/TP formula.** G01 computes its stop-loss/take-profit via a cross-file `G01_CalculateSL(...)`-style call, not `<price> ± <literal>` or `<price> ± (<atrVar> * <literal>)` — the only two arithmetic shapes `resolveRiskLegBinding()` recognizes. `ir.risk.stopLoss`/`takeProfit` stay `undefined`, which independently trips the eligibility gate's exit-kind check.
3. **17 detected position-management calls.** G01 genuinely calls `PositionSelect`/`PositionsTotal`/`OrderSelect`-family functions, so the Q0.9 "assume MT4/MT5's documented netting default" relaxation (see `docs/Q0.9_SEMANTIC_LOSS.md`) never applies — G01 stays on the conservative `REJECT`/`PLATFORM_DEFINED` path, which independently trips the eligibility gate's pyramiding/reversal check.

Any ONE of these three would be sufficient to block G01; all three holding simultaneously is deliberate defense in depth, not redundancy for its own sake — `test/q09-g01-reduction.test.ts` asserts `blockingReasons.length >= 2`.

## What Q0.9 adds on top of Q0.8's findings

- A formal `compileStrategy(ir)` call (not just `validateStrategyIR`) confirms `reductionReport.status === "BLOCKED"` and `strategySpec === undefined` — proving the block holds all the way through the NEW Q0.9 layer, not just Q0.7/Q0.8's structural validator.
- Determinism: compiling G01 three times produces byte-identical `status` and `diagnostics` (extends Q0.8.50's IR-hash determinism proof one layer further).
- An explicit assertion that G01's SL/TP genuinely stay unresolved even with Q0.9's new risk-leg-binding reconstruction in play — proving the new capability doesn't accidentally "fix" G01 by pattern-matching something it shouldn't.

## What would unblock G01 (for a future sprint — not attempted here)

- A genuine cross-file, multi-bar state-machine IR representation (explicitly deferred per Q0.9's own scope: "full state-machine compiler" is on the deferred list).
- A resolver for arbitrary cross-file function calls used in SL/TP arithmetic (would require either inlining `G01_CalculateSL`'s own logic or a formal cross-file call-graph resolution — both out of scope).
- None of these are attempted in Q0.9; forcing G01 through with a fabricated condition or a guessed risk formula would be exactly the "fake execution" this sprint's own critical success criterion forbids.
