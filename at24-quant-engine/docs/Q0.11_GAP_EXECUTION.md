# Q0.11 — Gap Execution Semantics

## The core rule (Q0.11.11): trigger price is never assumed to equal fill price

Every one of Q0.5's four order-fill resolvers (`bar-fill-model.ts`, unmodified) already encodes this correctly — Q0.11's contribution is proving it end-to-end for real entry orders, which was previously impossible (see `docs/Q0.11_ORDER_SEMANTICS.md`).

| Order type | Unfavorable gap (bad for the trader) | Favorable gap (good for the trader) |
|---|---|---|
| MARKET | N/A — a market order has no "requested price" to gap past; whatever the next open is, IS the fill (adjusted only by spread/slippage) | N/A |
| LIMIT | Never happens by construction — a limit only ever fills at its own price or better | Fills at the OPEN, strictly better than the limit (`resolveLimitFill`) |
| STOP | Fills at the OPEN, strictly worse than the stop level — the engine never pretends the stop price was actually achieved (`resolveStopFill`) | N/A — a stop is a "chase the breakout" order; there is no favorable-gap concept symmetric to LIMIT's |
| STOP_LIMIT | The stop leg gaps the same way a plain STOP does; if the resulting open ALSO clears past the limit, the two-stage lifecycle is skipped and the order simply doesn't fill that bar until the limit condition is later met on its own terms (`resolveStopLimitFill`) | An open landing strictly between stop and limit fills immediately, unambiguously, at that open |

## Golden fixtures (Q0.11.34)

- `LIMIT_GAP_THROUGH` (`test/q11-gap-fixtures.test.ts`): a BUY limit at 99, bar opens at 97 — fills at 97 (favorable, better than requested), never at the stale 99.
- `STOP_GAP_THROUGH`: a BUY stop at 103, bar opens at 106 — fills at 106 (worse than the stop), never fabricated as if the stop level itself were achieved.
- `STOP_LIMIT_NO_FILL`: the stop triggers intrabar, price never returns to satisfy the limit before the run ends — zero trades, the order EXPIRES, the trigger stays visible via `ORDER_TRIGGERED`/`executionStatistics.ordersExpired`.
- `STOP_LIMIT_FILL`: the stop triggers, a LATER bar's favorable gap satisfies the limit — the full two-stage lifecycle completes with a real fill at the gap price, not the stale limit level.

## Ambiguous intrabar resolution (Q0.11.12) — conservative always, D1 or D2/D3

D1 (whole-bar OHLC only) resolves same-bar SL+TP ambiguity conservatively — stop-loss always wins, flagged `ambiguous: true` (`resolveProtectiveExit`, Q0.5, unmodified; re-verified for a non-MARKET-entered position in `test/q11-intrabar-fixtures.test.ts`). D2/D3, when real child-bar data is available, may resolve the SAME ambiguity precisely (proving which level was ACTUALLY reached first) — this is Q0.6's own, pre-existing, unmodified capability at the RESOLVER level (`resolveProtectiveExit` itself is reused verbatim, per child bar).

**A real gap Q0.11's own D1/D2 compatibility test found and required fixing**: `multi-fidelity-engine.ts` (Q0.6) does NOT call `simulation-engine.ts`'s internals — per Q0.6's own established architecture (master blueprint rule 24: "duplicate outer control-flow shape, reuse frozen inner functions"), it has its OWN, independently-written copy of Step 4/5's signal-generation and entry-order-creation logic. The Q0.11 order-type/price-reference/`hasPendingOrder` fixes made to `simulation-engine.ts` (`docs/Q0.11_ORDER_SEMANTICS.md`) were therefore **invisible to D2/D3** until mirrored into this second copy — before that mirror, every D2/D3 entry silently remained MARKET regardless of the declared `executionType`, discovered only because `test/q11-fidelity-compatibility.test.ts`'s own D2 run produced an entry price inconsistent with the declared STOP order. Fixed via the identical additive edit (`hasPendingOrderForSymbol`, `matchedRule`/`riskReferencePrice` resolution, `limitPrice`/`stopPrice` passed to `createOrder`) applied to `multi-fidelity-engine.ts`'s own copy of that logic — never a call into `simulation-engine.ts`, consistent with Q0.6's own architecture. Proven in `test/q11-fidelity-compatibility.test.ts`.

## What "may resolve ambiguity" does NOT mean

D2/D3 having real child-bar data never means AT24 invents evidence for a D1 run that lacks it — the conservative D1 rule is not "wrong," it is the correct, honest answer to a strictly harder question (what MUST be true given only whole-bar data) than the one D2/D3 can sometimes answer (what a specific intrabar sequence proves). Both are documented, both are correct answers to different questions, matching the SAME "two correct answers to different questions" principle already established for Q0.8's platform-inclusive vs. platform-exclusive semantic hashes.
