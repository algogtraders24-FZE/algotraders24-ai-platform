# Q0.11 — Order Lifecycle

## The canonical state machine (Q0.4, frozen, unmodified by Q0.11)

```
NEW → SUBMITTED → ACCEPTED → TRIGGERED → PARTIALLY_FILLED → FILLED
                      ↓            ↓             ↓
                  CANCELLED    CANCELLED     CANCELLED
                  EXPIRED      EXPIRED       EXPIRED
                                (also: ACCEPTED → PARTIALLY_FILLED/FILLED directly)
```

`FILLED`/`CANCELLED`/`EXPIRED`/`REJECTED` are terminal — zero outgoing transitions (`order-engine.ts`'s `VALID_TRANSITIONS`, Q0.4). `transitionOrder()` throws for any illegal transition — never silently ignores or coerces it (`test/q11-failure-catalog.test.ts` items 10/13/14 prove `FILLED → CANCELLED` and `FILLED → EXPIRED` both throw).

**Q0.11's own contribution is proving `TRIGGERED` is reachable and meaningful**, not adding a new state. `TRIGGERED` existed in the type since Q0.4 specifically to support STOP_LIMIT's two-phase entry, but no code path could ever reach it before Q0.11 (every order was MARKET, which never triggers — it either fills or doesn't). `simulation-engine.ts`'s Step 1 dispatch already correctly re-evaluates a `TRIGGERED` order as a plain `LIMIT` order on every subsequent bar (`order.status === "TRIGGERED" ? resolveLimitFill(...) : resolveStopLimitFill(...)`) — this logic was written, complete, and untested end-to-end before Q0.11 supplied its first real `TRIGGERED` order.

## What "visible" means for a triggered-but-never-filled order (Q0.11.7)

A STOP_LIMIT order whose stop triggers but whose limit is never subsequently reached does not produce a `TradeLedger` entry (correctly — no fill occurred). Its state remains visible through two channels: the `ORDER_TRIGGERED` event (`result.eventStatistics.eventsByType["ORDER_TRIGGERED"]`) and the end-of-run finalize step, which transitions any still-`ACCEPTED`/`TRIGGERED` order to `EXPIRED` (`result.executionStatistics.ordersExpired`) rather than leaving it dangling. Proven in `test/q11-gap-fixtures.test.ts`'s `STOP_LIMIT_NO_FILL`.

## Same-bar unambiguous fills skip `TRIGGERED` entirely

When a STOP_LIMIT order's bar opens strictly between the stop and the limit (`open >= stop && open <= limit` for BUY), `resolveStopLimitFill()` fills it immediately at the open — the two-stage lifecycle is a FALLBACK for when the stop and limit can't both be proven satisfied within one bar, not a mandatory intermediate step. Proven in `test/q11-intrabar-fixtures.test.ts`'s `SAME_BAR_TRIGGER_FILL` (zero `ORDER_TRIGGERED` events recorded).

## Cancel/replace and order modification (Q0.11.29/30)

This sprint implements no new cancel/replace mechanism — `CANCELLED` already exists as a legal transition from `ACCEPTED`/`TRIGGERED`/`PARTIALLY_FILLED`, reachable by a future caller (no orchestrator code currently calls it; nothing in Q0.11's scope needed to). Q0.11 explicitly keeps ENTRY ORDER modification (which would mean changing a pending order's own limit/stop price before it fills — not built, not needed by any current strategy shape) structurally distinct from Q0.10's POSITION management actions (`MOVE_STOP`/`PARTIAL_CLOSE`/`FORCE_EXIT`, which act on an already-open `Position`, never a pending `SimulationOrder`) — the two never share code or a domain type, per Q0.11.30's explicit instruction.
