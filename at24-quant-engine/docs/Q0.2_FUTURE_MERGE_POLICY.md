# Q0.2 Future Merge Policy

Governs how — and under what evidence — anything from OLD (`quant-engine/`, `quant_engine/`) or a future AI-generated `StrategySpec` may ever be merged into, or trusted alongside, `at24-quant-engine/`. This is a policy document; no merge happens as part of Q0.2.

## The pipeline

```
OLD SYSTEM
    |
    | frozen — never modified to "make it match" NEW
    |
NEW QUANT (at24-quant-engine/)
    |
    | independently validated — NEW's own correctness is established on
    | its own tests/reference implementations, never by assuming OLD was right
    |
COMPATIBILITY TEST
    |
    | does OLD's concept have a faithful, lossless representation in
    | NEW's current contracts? (see Q0.1_MIGRATION_PLAN.md's per-candidate
    | compatibility assessments)
    |
SEMANTIC COMPARISON
    |
    | run the SAME input through OLD and NEW, compare outputs within a
    | defined, documented tolerance — not "looks similar"
    |
EVIDENCE
    |
    | a written record of what was compared, on what data, with what
    | result — reusing this package's own determinism/reference-
    | implementation pattern (test/reference/, Q0.2.21), not a new one
    |
CONTROLLED MERGE
```

## Hard rule

A merge must never happen simply because **"new engine works."** NEW working correctly on its own tests is necessary but never sufficient — it says nothing about whether a specific OLD component's behavior has been reproduced. Every merge must satisfy ALL of the following before it lands:

1. **Semantic compatibility** — a written compatibility assessment (per the Q0.1_MIGRATION_PLAN.md pipeline: Old Component → Compatibility Assessment → Specification Mapping → Test → Migration → Validation → Old Component Retired/Archived) exists and concludes the concept maps cleanly, or is explicitly marked `INCOMPATIBLE / REQUIRES DESIGN` and deferred.
2. **Deterministic behavior** — the migrated/merged component passes NEW's determinism tests (same input twice → identical output; see `runtime/determinism.ts`'s pattern).
3. **Test coverage** — new tests exist for the merged component at the same standard as Q0.2's own (known-sequence, warmup/edge cases, reference-implementation cross-check where applicable, not just "returns a number").
4. **Evidence** — a documented semantic-comparison run exists (OLD's output vs. NEW's output on the same input, with the observed divergence, if any, explained).
5. **No M-Series regression** — confirmed by the same isolation test pattern this package already uses (`test/isolation.test.ts`): the merge must not introduce an import of `frontend/`, `ea-research/`, `quant-engine/`, `quant_engine/`, `quant_engine/market.db`, or Prisma into `at24-quant-engine/`'s runtime dependency graph.
6. **No production regression** — nothing about the merge may change any existing production behavior; if the merge is ever wired into a consuming system (M-Series adapter, marketplace, etc.), that wiring is itself a separate, explicitly-approved future integration step (see `docs/AT24_QUANT_ENGINE_MASTER_BLUEPRINT.md`'s integration boundary), never a side effect of a Quant Engine merge.

## Applies equally to AI-proposed StrategySpecs

The same pipeline governs a future AI Strategy Agent's output (Q0.2.24): an AI-generated `StrategySpec` is not "mergeable" into anything trusted just because `validateStrategySpec()` passed. `validateStrategySpec()` proves structural validity, not that the strategy is profitable, robust, or worth running — those still require the full Evidence/Validation chain (M-Series' job, per ADR-006), which this pipeline explicitly routes through rather than bypasses.

## Explicitly out of scope for this policy

This document governs merges *within* the Quant Engine's own boundary (OLD Python code/data → NEW TypeScript contracts, or AI-proposed specs → trusted specs). It does NOT define, and must never be read as pre-authorizing, the separate future M-Series integration adapters (Evidence Adapter, Validation Adapter, Risk Adapter) that Q0.11/ADR-010 already deferred — those require their own, separately-approved policy when that work is actually undertaken.
