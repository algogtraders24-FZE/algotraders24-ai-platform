# Q0.5 Event Queue

## Event identity (Q0.5.1)

```
{
  eventId: `${eventType}:${timestamp}:${sequence}`,
  timestamp: number,
  sequence: number,
  eventType: SimulationEventType,
  source: string,
  payload: unknown,
}
```

`eventId` is a pure, deterministic function of its own fields — never a random UUID, never derived from the wall clock. `sequence` is the load-bearing field: it is assigned by `EventQueue.enqueue()` at the moment of insertion, as a strictly monotonically increasing counter starting at 0. Ordering is `(timestamp ASC, sequence ASC)` — total, because `sequence` is globally unique within one queue instance, so no two events can ever tie.

**A real bug this discipline caught during Q0.5's own testing**: the orchestrator originally seeded every input bar into the queue in one bulk pass before processing began. Because `sequence` is a single shared counter, that meant bar 10's `MARKET_BAR` event consumed sequence numbers 0..9 (one per bar) *before* bar 0's own derived events (`STRATEGY_CALCULATED`, `ORDER_CREATED`, ...) got a chance to claim any — so the mere presence of *future* bars shifted the sequence numbers, and therefore the deterministic IDs, assigned to *historical* events, even though no decision or price ever changed. Fixed by seeding only the first bar, then enqueuing bar N+1 only once bar N's entire processing pipeline (and every event it produced) has already consumed its sequence numbers — see `docs/Q0.5_DETERMINISM.md` for the full writeup. This is exactly the kind of subtle lookahead-adjacent bug the sequence-based identity scheme was designed to make *provable*, not just *hoped-for*.

## Canonical events implemented (Q0.5.3, subset of Q0.4's full frozen set)

`MARKET_BAR`, `STRATEGY_CALCULATED`, `ORDER_CREATED`/`ORDER_SUBMITTED`/`ORDER_ACCEPTED`/`ORDER_REJECTED`/`ORDER_TRIGGERED`/`ORDER_PARTIALLY_FILLED`/`ORDER_FILLED`/`ORDER_CANCELLED`/`ORDER_EXPIRED`, `POSITION_OPENED`/`POSITION_MODIFIED`/`POSITION_REDUCED`/`POSITION_CLOSED`. `TickEvent`/`QuoteEvent`/`BarOpen`/`BarUpdate`/`BarClose`/`SessionOpen`/`SessionClose`/`StrategyRecalculatedAfterFill` remain reserved (Q0.4's full set) but unimplemented — Q0.5 is ON_BAR_CLOSE-only.

## Queue implementation (Q0.5.2)

A binary min-heap keyed on `(timestamp, sequence)` — `src/runtime/simulation/event-queue.ts`. O(log n) `enqueue`/`dequeue`, O(1) `peek`/`isEmpty`/`size`. `clear()` empties the heap AND resets the sequence counter to 0, so a cleared-and-reused queue reproduces identical sequence numbers on a subsequent identical sequence of `enqueue()` calls — required for Q0.5.37's replay guarantee.

Required operations, all implemented: `enqueue()`, `peek()`, `dequeue()`, `isEmpty()`, `size()`, `clear()`.

**Invalid events are rejected explicitly**: `enqueue()` throws if `timestamp` is not a finite number (`NaN`/`Infinity`/`-Infinity`) — never silently accepted and sorted arbitrarily.

## What Q0.5 does NOT do

No tick-level event volume has been benchmarked beyond the N=100,000 synthetic baseline (`docs/Q0.5_SIMULATION_ARCHITECTURE.md`'s Performance Baseline section) — no attempt at a lock-free, allocation-free, or otherwise more exotic queue implementation. Correctness first, per Q0.4.22/Q0.5.45.
