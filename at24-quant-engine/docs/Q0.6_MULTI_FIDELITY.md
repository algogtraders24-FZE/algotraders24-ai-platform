# Q0.6 Multi-Fidelity Simulation

## The fidelity ladder (Q0.6.1)

`SimulationFidelity` (`domain/fidelity/simulation-fidelity.ts`): `"D1_OHLC" | "D2_LOWER_TIMEFRAME" | "D3_M1"`, plus a separately-declared `ReservedSimulationFidelity` union (`D4_TICK | D5_BID_ASK | D6_DEPTH | D7_MICROSTRUCTURE`) — declared now so a future sprint extends this type rather than inventing a parallel one, but not implemented and not selectable through any Q0.6 API. This is a DIFFERENT type from Q0.5's `DataFidelityLevel` (`domain/data-fidelity.ts`, the generic `"D0"-"D7"` labels frozen in Q0.4) — `SimulationFidelity` names are tied directly to a concrete execution model each level implies. `SimulationConfig.dataFidelity` (Q0.5, frozen) is left completely alone; `MultiFidelityProvenance.simulationFidelity` is the new, authoritative field for anything Q0.6-aware.

## D1 is frozen; D2/D3 are new and additive

Q0.5's `runSimulation()`, `bar-fill-model.ts`, `simulation-engine.ts`, and every one of its tests are **never modified** by Q0.6 — confirmed by `git status` and by `test/fidelity-d1-regression.test.ts`, which imports `runSimulation` directly and re-runs Q0.5's own `GOLDEN_BARS`/`GOLDEN_BARS_WITH_REENTRY` fixtures unchanged, asserting byte-identical trade/account/position values.

`runMultiFidelitySimulation(bars, config)` (`runtime/fidelity/multi-fidelity-engine.ts`) is the single new public entry point:

- `config.fidelity === "D1_OHLC"` **delegates directly to Q0.5's unmodified `runSimulation(bars, config.base)`**, then wraps the result's `provenance` with the additive `MultiFidelityProvenance` fields (`docs/Q0.6_D2_D3_EXECUTION.md`'s "why the wrapper" note explains why this still changes `resultHash` even though every trade/account/position value is identical).
- `config.fidelity === "D2_LOWER_TIMEFRAME" | "D3_M1"` runs a new orchestrator (`docs/Q0.6_D2_D3_EXECUTION.md`) that reuses Q0.5's exact fill/protective-exit functions, applied per available child bar instead of once per parent bar.

## MultiFidelityConfig: composition, not inheritance (Q0.6.10)

```ts
interface MultiFidelityConfig {
  base: SimulationConfig;            // Q0.5's own config, used verbatim
  fidelity: SimulationFidelity;
  detailProvider?: BarDetailProvider; // required for D2/D3
  detailTimeframe?: Timeframe;        // required for D2/D3
  missingDetailPolicy?: "FAIL" | "FALLBACK_TO_D1"; // default "FAIL"
}
```

`MultiFidelityConfig` wraps a `SimulationConfig` (`base`) rather than extending it, so there is never ambiguity about which `dataFidelity`-shaped field is authoritative. It lives in `runtime/fidelity/`, not `domain/fidelity/`, because `SimulationConfig` itself is a runtime type (it carries function-valued model instances, not pure structural data) — the same reason Q0.5 placed `SimulationConfig` in `runtime/simulation/simulation-engine.ts` rather than `domain/`.

## What Q0.6 does NOT do

No D4-D7 (tick/bid-ask/depth/microstructure) implementation — reserved only. No portfolio/multi-instrument simulation. No new spread/slippage/fee/latency model implementations (D2/D3 reuse whatever `SpreadModel`/`SlippageModel`/`FeeModel`/`LatencyModel` the `base` config specifies — see `docs/Q0.6_D2_D3_EXECUTION.md`'s Execution Reality vs Data Detail distinction). No change to NETTING-only position accounting. No `ExitRule` evaluation (still deferred from Q0.5).
