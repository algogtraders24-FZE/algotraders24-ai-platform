# P3.5 — Risk Configuration → Real Strategy Parameters

**Status:** Implemented, tested. Builds on the production-verified P3.4 architecture (`docs/P3.4-STRATEGY-PARAMETERS.md`) and the reproducibility/evidence principles locked in `docs/ALGO_TESTING_PRO_ROADMAP.md`.

## 1. What this phase actually is

P3.4's own audit (`P3.4-STRATEGY-PARAMETERS.md` section 1) classified the Golden Strategy's risk block — `risk.sizing.quantity`, `risk.stopLoss.distance`, `risk.takeProfit.rMultiple` — as **category #2** ("execution/risk configuration, not a signal parameter") and deliberately left it hardcoded, out of that sprint's scope. P3.5 is the sprint that opens that slot up, on its own terms, with the exact same discipline P3.4 applied to `priceThreshold`: additive, backward-compatible, no invented risk shapes, no new UI mechanism.

**The architectural finding that made this a small change, not a redesign**: `computeSemanticStrategyHash()` (`at24-quant-engine/src/runtime/identity.ts`) already hashes every field of `StrategySpec` except `metadata` — which means `risk` **already participated in `strategyHash`/`resultHash` identity before this sprint touched anything**, since `risk` is a top-level `StrategySpec` field, not buried under `metadata`. P3.5 did not need to build a new identity mechanism; it needed to stop hardcoding the values that mechanism already tracks. This was confirmed by direct test (`test/golden-strategy-risk-parameters.test.ts`), not assumed.

## 2. What changes

- `GoldenStrategyParams` (`src/reference/golden-strategy.ts`) gains three optional fields — `positionSizeQuantity`, `stopLossDistance`, `takeProfitRMultiple` — each threaded into the existing `risk` block shape unchanged (`sizing.method` stays `"fixed-quantity"`, `stopLoss.type` stays `"fixed-distance"`, `takeProfit.type` stays `"risk-multiple"` — same shapes `domain/risk-specification.ts` already declares).
- Three new `GOLDEN_STRATEGY_DEFAULT_*` exported constants, matching the exact pre-P3.5 hardcoded literals (1, 5, 2) — so a caller who omits every new field gets a byte-identical `StrategySpec` to every pre-P3.5 caller.
- The Strategy Registry's `"golden"` entry (`frontend/services/algo-test/strategy-registry.ts`) declares these as three new `StrategyParameterDefinition`s, using the exact same mechanism `priceThreshold` already used — `validateParameterValues()` required zero changes, since it was already fully generic over `strategy.parameters`.
- `run-golden-backtest.ts` and `algo-test.service.ts`'s `toGoldenStrategyOverrides()` thread the validated values through, mirroring `priceThreshold`'s existing plumbing exactly.
- `AlgoTestPanel.tsx` required **zero changes** — its parameter rendering (`parameters.map((p) => <ParameterField .../>)`), form-value mapping, and reset-to-defaults logic were already fully generic over the registry's declared parameter list, with no hardcoded field names anywhere. Confirmed by direct code read before writing any implementation, not assumed. This is a genuinely important data point for P3.7 (Generic Parameter Engine) — the UI layer was already built to that standard; the gap was entirely upstream of it.

## 3. A real detail discovered empirically, not assumed

While building the behavioral test proving `stopLossDistance` has a genuine effect, an incorrect assumption (that the protective stop is computed from the actual fill price) produced a wrong expected result on the first run. Debugging traced the actual mechanism: **the protective stop-loss and take-profit prices are computed from the signal bar's own close price** (the bar whose condition triggered the entry decision), **not the realized next-bar-open fill price** the position later actually enters at. Concretely, for the Golden Strategy's BUY case: `stopPrice = signalClose - stopLossDistance`, and `takeProfitPrice = signalClose + takeProfitRMultiple * stopLossDistance` — both computed in `decision-builder.ts` at signal time, before `bar-fill-model.ts` resolves the actual fill. This is a real, existing engine behavior (not introduced by P3.5), now directly documented and covered by a dedicated regression test rather than left as an implicit, undocumented detail future work could get wrong again.

## 4. Evidence

`test/golden-strategy-risk-parameters.test.ts` (7 tests): no-arg call unchanged; explicit default-matching values structurally identical to the no-arg call; a non-default value changes only the `risk` block; a changed risk parameter changes `computeSemanticStrategyHash`; reverting to documented defaults reproduces the exact pre-P3.5 hash; a tighter stop-loss produces a real, different trade ledger than a wider one (the §3 mechanism, proven — not just a structural hash difference); determinism across two independent runs with identical non-default parameters.

`frontend/scripts/validate-algo-test-parameters.ts` and `validate-algo-test-service.ts` (P3.4's own live-verification scripts) updated: the registry now declares 4 parameters, not 1; every assertion checking a full persisted/returned `parameters` snapshot now expects all 4 registered defaults, not just `priceThreshold`, matching `validateParameterValues()`'s own "every declared parameter always appears, defaults filled in" contract.

## 6. A pre-existing gap this phase's own build step surfaced and fixed

`frontend/vendor/at24-quant-engine/dist/` (the built copy `next build` actually imports — see `frontend/scripts/vendor-quant-engine.mjs` and `docs/P3.2A.1-DEPLOYMENT-GATE.md`) had not been regenerated since the Q1.5 + P3.4 merge landed on `main` (PR #11): only the two files P3.4 hand-edited (`golden-strategy.d.ts`/`.js`) were current, but the rest of the vendored `dist/` — including `simulation-engine.js`'s Q1.5 `SIGNAL_EXIT`/pyramiding/`entryCountByPosition` code — was still the pre-Q1.5 build. Running the existing `npm run vendor:quant-engine` script (a mandatory step for P3.5's own new exports to reach the frontend at all) also brought the vendored copy current with everything already merged into `at24-quant-engine/src/`. This is disclosed here explicitly because it changes more files than P3.5's own diff alone would suggest — the additional changes are build output catching up to already-reviewed, already-tested source, not new behavior.
