# Q0.9 Simulation Bridge

`compileToSimulation(compilation, bars, options)` (`src/runtime/reduction/simulation-adapter.ts`) is the ONLY function in this package that connects a compiled strategy to Q0.5/Q0.6's simulation engine. It duplicates none of their logic — it only:

1. **Builds indicator series** (`buildIndicatorSeriesFromIR`) — computes each `ir.indicators` entry's full series over `bars` using Q0.2's own `calculateSeries()` and the exact same `sma`/`ema`/`rsi`/`atr` implementations Q0.5's production path uses. This is the concrete indicator-parity guarantee: the values fed into `SimulationConfig.indicatorSeries` come from the identical code a hand-written `StrategySpec` would use, never a second math implementation.
2. **Assembles `SimulationConfig`/`MultiFidelityConfig`** — Q0.5's and Q0.6's own shapes, unmodified.
3. **Makes exactly one call** to `runMultiFidelitySimulation()` (Q0.6, unmodified — which itself delegates to Q0.5's unmodified `runSimulation()` for `D1_OHLC`).

Only the four single-output indicator families (`SMA`/`EMA`/`RSI`/`ATR`) have a direct `SimulationConfig.indicatorSeries` mapping today; a strategy using `MACD`/`BOLLINGER_BANDS` (multi-output) or any `generic` (non-named) indicator is BLOCKED at this boundary with an explicit reason, never partially wired.

## The warmup problem (found and fixed this sprint)

Q0.5's frozen `generateSignal()`/`firstMatchingEntryRule()` (`src/runtime/signal-generator.ts`) has **no warmup guard** — it evaluates the entry condition unconditionally starting at bar 0, and **throws** if any referenced indicator's value is still `undefined` (i.e. within its warmup period — e.g. `EMA(21)` needs 21 bars before it has a first value). Q0.5's own golden fixtures never hit this because they use a synthetic zero-warmup `PRICE` pseudo-indicator; a real imported strategy with an `EMA(21)` does not have that luxury.

Because `signal-generator.ts` is frozen (Q0.5, cannot be modified), the fix lives entirely in this adapter:

1. `buildIndicatorSeriesFromIR` now also returns `warmupBars`, computed as `max(def.warmup(params).bars)` across every successfully-resolved indicator (each `IndicatorDefinition`'s own `warmup()` function — `sma.warmup({period}).bars === period`, `rsi.warmup({period}).bars === period + 1`, etc.).
2. `compileToSimulation` slices `bars`, every entry in the indicator `series` map, and `atrByIndex` by the identical `warmupBars` offset **before** calling `runMultiFidelitySimulation()` — so index 0 of every sliced array is guaranteed to be the first bar where every indicator this strategy uses already has a real value.
3. If `bars.length <= warmupBars`, `compileToSimulation` throws an explicit `"insufficient bars for indicator warmup"` error — never a silent truncation to zero usable bars.

This is a compile-time responsibility, not a Q0.5 defect: Q0.5's engine correctly assumes its caller supplies fully-warmed-up data (true for hand-written `SimulationConfig`s in Q0.5's own tests); Q0.9 is the first caller that must derive indicator series from an arbitrary imported strategy, so it is the first layer that has to actually enforce that assumption.

## A second, unrelated pitfall this sprint's own testing surfaced (documented, not a code fix)

An early synthetic price fixture used bar-to-bar volatility far larger than its chosen SL/TP distances (0.5-unit swings against 0.005-unit stops). Because entries execute `NEXT_BAR_OPEN` (the stop-loss price is computed from the signal bar's close, but the fill happens on the *next* bar's open), a large enough gap between those two prices can put the stop on the wrong side of the actual fill price before the position even opens — which correctly surfaces as `riskDistance must be > 0` in Q0.3's `computeRMultiple` (`src/runtime/risk/r-multiple.ts`) the first time that position closes. This is not a bug: it is Q0.3's own risk-geometry invariant doing exactly its job. The fix was fixture realism, not code — `test/fixtures/q09-mql-e2e-fixtures.ts`'s `buildSyntheticFxBars()` now uses FX-pip-scale bar-to-bar movement (~0.0002-0.0008) proportional to the SL/TP distances the golden fixtures actually use (0.005/0.01).

## D2/D3 fidelity

`compileToSimulation`'s `options.fidelity` accepts any `SimulationFidelity` Q0.6 supports (`D1_OHLC`/`D2_LOWER_TIMEFRAME`/`D3_M1`) and passes it straight through to `runMultiFidelitySimulation` unmodified — the adapter itself is fidelity-agnostic. This sprint's own test coverage exercises `D1_OHLC` end-to-end; D2/D3 integration is structurally supported (same code path, same `MultiFidelityConfig` shape) but not separately golden-fixture-tested here, since doing so would require the caller to also supply a `BarDetailProvider`, which is an application-layer concern (Q0.6 already covers `BarDetailProvider`'s own correctness in `test/fidelity-bar-detail-provider.test.ts`).
