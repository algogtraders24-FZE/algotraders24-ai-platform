# Q0.2 Research Foundation

## Risk semantics (Q0.2.9)

All new `RiskSpecification` fields (`src/domain/risk-specification.ts`) share a `DistanceSpec` union for expressing a price/profit distance three ways:

| Mode | Meaning | Units |
|---|---|---|
| `absolute` | raw price units | same units as the instrument's quote price (e.g. $3.00 for XAUUSD) |
| `percentage` | percent of entry price | `(0, ...)`, no fixed upper bound enforced (a >100% distance is unusual but not structurally invalid) |
| `atr-multiple` | multiple of `ATR(atrPeriod)` at entry time | `atrMultiple` dimensionless, `atrPeriod` in bars |

| Field | Meaning | Default | Valid range | Interaction | Edge cases |
|---|---|---|---|---|---|
| `breakeven.trigger` / `.lockOffset` | move stop to breakeven once price has moved `trigger` in the position's favor; new stop sits `lockOffset` past entry (0 = exactly at entry) | none (feature disabled if `breakeven` absent) | both `DistanceSpec`s must be `> 0` | interacts with `stopLoss` — the breakeven adjustment supersedes the original stop once triggered (evaluation-layer concern, not specified here) | `lockOffset = 0` means "lock at entry exactly," which is valid and common |
| `trailingStop.activation` / `.distance` | once price has moved `activation` in favor, trail the stop `distance` behind current price | none | both `> 0` | independent of `breakeven` — a spec may declare both; which one governs at a given moment is an evaluation-layer decision, not specified here | `activation = distance` is valid (trailing begins exactly where the trail distance would first bind) |
| `partialClose.trigger` / `.closePercent` | close `closePercent` of remaining size once price has moved `trigger` in favor | none | `trigger > 0`; `closePercent` in `(0, 100]` | `closePercent = 100` means "close everything," effectively an early full exit rather than a partial | multiple `partialClose` events are not represented — this is a single-trigger contract only |
| `sessionHours.timezone` / `.windows` | new positions only open within one of `windows`, all in `timezone` (IANA name) | none (no restriction if absent) | at least one window; each window's start strictly before its end, hours `0-23`, minutes `0-59` | does not affect exits — this is an entry-time-only gate | a window crossing midnight (e.g. 22:00-02:00) is NOT representable by a single window in this contract (start must be < end) — express it as two windows if needed; documented limitation, not silently wrong |
| `maxHoldingPeriod.maxBars` / `.maxDurationMs` | close the position after this many bars OR this much time, whichever comes first | none | at least one of the two must be set; each `> 0` if set | if both set, the FIRST to trigger governs (documented, not left ambiguous) | setting only one is valid and common |
| `maxSimultaneousPositions` | portfolio-level cap on concurrently open positions | none (unlimited) | `> 0`, integer semantics implied (not enforced as an integer by this contract — a future evaluation layer must round/reject non-integers) | distinct from `maxPositionSize` (a per-position size cap) and `maxExposure` (an aggregate notional/equity cap) — all three may be set simultaneously and independently | `= 1` means the strategy is single-position-only, matching OLD's `quant_engine/engine.py` limitation as a special case, not the default |
| `dailyLossLimit` | once the trading day's REALIZED loss reaches this limit, no new positions may open for the rest of that day | none | `percent-equity` mode: `(0, 100]`; `fixed-amount` mode: `> 0` | deliberately excludes unrealized/floating P&L (see field doc in code) — evaluating this against actual trades is a future Risk Evaluation concern, not this contract's | "trading day" boundary (which timezone, which rollover hour) is NOT specified here — a future evaluation layer must define it explicitly, not assume UTC midnight silently |

**Specification vs. Evaluation vs. Execution (Q0.2.8's mandatory separation)**: every field above describes *what the strategy wants*, structurally validated by `validateRiskSpecification()`. None of it is evaluated against real trades or bars anywhere in Q0.2 — no function in this package answers "has the daily loss limit been hit" or "should breakeven trigger now." That is Risk Evaluation, a distinct future layer; and turning an evaluation decision into an actual order modification is Execution, a further distinct future layer. Conflating these three was exactly OLD's `RiskConfig`/`engine.py` design (an imperative, engine-coupled config object) — Q0.2 deliberately keeps them apart.

## Metric semantics (Q0.2.14)

See `src/domain/metrics.ts` for exact formulas (also reproduced in code comments there). Core metrics implemented and tested: `totalReturn`, `netProfit`, `grossProfit`, `grossLoss`, `profitFactor`, `winRate`, `expectancy`, `maxDrawdown`, `averageTrade`, `tradeCount`. Reserved-but-not-implemented: `sharpeRatio`, `sortinoRatio`, `calmarRatio`, `recoveryFactor`, `ulcerIndex` — the names exist in `ReservedMetricName` so a future implementation cannot silently pick a different name for the same concept.

**The point is not statistical completeness** — it's that `profitFactor` (or any other name) means exactly one mathematical thing everywhere it appears in this codebase, verified by `test/metrics.test.ts`'s hand-computed known sequence.

## Execution assumption boundary (Q0.2.15 / Q0.2.16)

`ExecutionSpecification` (`src/domain/execution-specification.ts`) is a static, declarative "what was assumed" contract (fill model, spread/slippage/fee/commission, latency, price basis, margin). `validateExecutionSpecification()` enforces that costs can never be silently zero: if spread, slippage, commission, and fee are all unset, the spec must set `costsExplicitlyZero: true` or validation fails. This is the concrete fix for the exact failure mode OLD never guarded against.

`src/domain/reality-models.ts`'s `FeeModel`/`SpreadModel`/`SlippageModel`/`FillModel`/`MarginModel`/`LatencyModel` are the future "how is this actually computed" plug points — pure interfaces, zero implementation, so a future backtest engine is written against these seams from day one instead of hard-coding assumptions the way OLD's `runner.py`/`execution_mtf.py`/`execution_tick.py` each did independently (see Q0.1_ARCHITECTURE_COMPARISON.md).

## Strategy taxonomy (Q0.2.18)

`src/domain/strategy-taxonomy.ts` defines 13 canonical tags: `TREND`, `MOMENTUM`, `MEAN_REVERSION`, `BREAKOUT`, `REVERSAL`, `VOLATILITY`, `PRICE_ACTION`, `MARKET_STRUCTURE`, `LIQUIDITY`, `MTF`, `SESSION`, `STATISTICAL`, `HYBRID`. Multiple tags may apply to one strategy (no exclusivity enforced). This is a reusable foundation only — the 1,764-strategy library is NOT tagged or migrated using this taxonomy in Q0.2 (see below).

## AI boundary (Q0.2.24)

```
AI
 |
 v
StrategySpec
 |
 v
AT24 Quant Engine (deterministic)
 |
 v
Objective Result
 |
 v
Validation
 |
 v
Evidence
```

AI **may**: generate a `StrategySpec`, explain a strategy in natural language, propose a research hypothesis, suggest parameter values, summarize a completed result. AI **may NOT**: bypass `StrategySpec` (i.e. no execution path exists that skips the typed spec), bypass `validateStrategySpec()`, directly declare a strategy profitable or validated (see `research-result.ts`'s `markValidated()` — reachable only from `CANDIDATE`, never assignable as a raw literal), override any deterministic risk rule, become required for backtesting to function, or become required for correctness. Every primitive built in Q0/Q0.2 works with zero AI involvement — the 161-test suite proves this by never invoking an AI API anywhere.

This extends Q0's ADR-004 and is enforced the same structural way: no type in this package's public surface (`Signal`, `Decision`, `BacktestResult`, `ResearchResult`) has a field an AI output could write a confidence score or trust claim into.

## Performance baseline (Q0.2.22)

Recorded via `npm run benchmark` (`scripts/benchmark.ts`), N=10,000 synthetic bars, this machine, 2026-08-24. Correctness-first: these numbers are a baseline for future comparison, not a gate — nothing in the test suite asserts a timing threshold.

| Operation | Total (N=10,000) | Per-op |
|---|---|---|
| SMA(20) `calculateSeries` | 28.5ms | 2.85us |
| EMA(20) `calculateSeries` | 4.4ms | 0.44us |
| RSI(14) `calculateSeries` | 8.2ms | 0.82us |
| ATR(14) `calculateSeries` | 8.6ms | 0.86us |
| MACD(12,26,9) `calculateSeries` | 9.6ms | 0.96us |
| Bollinger(20,2) `calculateSeries` | 34.8ms | 3.48us |
| Expression evaluation (AND of 2 comparisons) | 23.1ms | 2.31us |
| `validateStrategySpec` | 68.7ms | 6.87us |
| `computeCanonicalHash(strategySpec)` | 1163.9ms | 116.4us |
| `TimeFrontier.availableBars()` at a fixed cursor | 2401.7ms | 240.2us |
| MarketSeries iteration (plain `for..of`), x10 passes | 22.7ms | 2.27us |

**Observations, not yet acted on** (correctness-first, per Q0.2.22): SMA and Bollinger are the slowest indicators because their step function re-slices and re-reduces an O(period) window every bar, unlike EMA/RSI/ATR's O(1) incremental recurrence — a straightforward future optimization (maintain a running sum instead of re-summing the window) if this ever matters. `TimeFrontier.availableBars()` is, as documented in its own source comment, a deliberately unoptimized O(n) linear filter per call — calling it N times over an N-bar series is the expected O(n²) cost shown above, and is the clearest first target if/when a real backtest engine calls it in a tight loop. `computeCanonicalHash` is the second-clearest target (JSON stringify + SHA-256 per call) if experiment/strategy hashing ever needs to happen in a hot loop rather than once per spec/experiment as currently intended.
