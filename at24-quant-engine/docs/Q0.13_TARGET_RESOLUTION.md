# Q0.13 — Order Target Resolution

## The explicit target-kind vocabulary

`OrderTargetKind = "SYMBOL" | "TICKET" | "UNKNOWN"` (`domain/pending-order-management-policy.ts`, `domain/mql-importer/semantic-model.ts`'s `PendingOrderTargetKind`).

| Source pattern | Resolved kind | Why |
|---|---|---|
| `OrderDelete(ticket)` where `ticket` is a plain local/global variable | `TICKET` | The ONE structural signal this importer uses: an `Identifier` in the call's first argument position |
| `trade.PositionClose(_Symbol)` | `SYMBOL` | The argument is the `_Symbol` built-in identifier |
| `trade.PositionClose(Symbol())` | `SYMBOL` | The argument is a call to the `Symbol()` built-in |
| `trade.OrderDelete("EURUSD")` | `SYMBOL` | A bare string literal |
| `OrderModify(GetActiveTicket(), ...)` | `UNKNOWN` | The argument is an arbitrary call expression — never assumed to be a ticket just because it occupies the ticket position |

## What this importer deliberately does NOT do

Real MQL4/MQL5 code frequently uses an idiom this importer does NOT resolve:

```text
OrderSelect(ticket, SELECT_BY_TICKET);
...
OrderModify(OrderTicket(), price, sl, tp, 0);   // or even bare OrderModify() in some MQL4 styles
```

Tracing `OrderSelect(ticket)` (or `PositionSelect(symbol)`) EARLIER in the same function FORWARD to a LATER call that implicitly acts on "whatever is currently selected" would require genuine cross-statement data-flow analysis — a capability this importer does not have anywhere else in its architecture either (`variableIndicatorBindings`/`variableRiskBindings`, the two existing binding-tracking mechanisms, are both scoped to "the SAME statement's own last assignment within the SAME function," never a control-flow-sensitive selection state machine). Extending target resolution to understand `OrderSelect`/`PositionSelect`/`OrderGetTicket`/`PositionSelectByTicket` as STATE-MUTATING selection operations, and threading that state through subsequent calls, is explicitly deferred to a future sprint (see the Q0.14 recommendation in the final report) — attempting it narrowly here, only for pending-order management, would create an inconsistent, partially-data-flow-aware importer that behaves differently for this ONE feature than for every other detector in the file.

**The honest result**: a real EA using the `OrderSelect`-then-bare-`OrderModify` idiom resolves to `target.kind: "UNKNOWN"`, `provable: false` — correctly EXCLUDED from execution, never silently treated as "the current order" (Q0.13's own explicit prohibition, proven in `test/q13-negative.test.ts`'s NEG 4).

## `orderTypeFilter`/`sideFilter` — narrowing, not identifying

`OrderTargetSpec.orderTypeFilter`/`sideFilter` are a SEPARATE narrowing mechanism, populated only when the rule's own CONDITION is a provable `ORDER_TYPE_FILTER` (e.g. `if(OrderType()==OP_BUYSTOP)`). They restrict WHICH of the potentially-many pending orders of a `SYMBOL`/`TICKET` target the rule's operation actually applies to at runtime (`targetMatches()`, `runtime/simulation/pending-order-management.ts`) — they do not, by themselves, identify a target; a rule with `target.kind: "SYMBOL"` and no filters at all applies to EVERY pending order of that symbol, which is intentional (MQL4's own flat model similarly has no per-order-type distinction unless the source itself adds one).

## Never a silent fallback

`resolvePendingOrderTarget()` (`runtime/mql-importer/semantic-analyzer.ts`) has exactly four branches (`_Symbol`, `Symbol()`, string literal, plain identifier) and a `default` that ALWAYS returns `{kind: "UNKNOWN", sourceExpr: ...}` — there is no code path that returns anything else for an unrecognized shape. Proven directly in `test/q13-mql-detection.test.ts` (fixtures 10 and 20) and `test/q13-negative.test.ts` (NEG 4).
