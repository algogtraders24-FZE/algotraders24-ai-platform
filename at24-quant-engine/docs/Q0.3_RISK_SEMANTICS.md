# Q0.3 Risk Semantics

## Violation model (Q0.3.3)

Every `RiskViolation` has 6 fields — `code`, `severity`, `message`, `relevantValue`, `configuredLimit`, `reason` — with only `message` being free-form; `code` (13 values, see below), `severity` (`BLOCKING`/`WARNING`), and `reason` (a closed 8-value taxonomy: `BELOW_MINIMUM`/`EXCEEDS_MAXIMUM`/`AT_OR_BEYOND_LIMIT`/`INVALID_NUMERIC_VALUE`/`INVALID_CONFIGURATION`/`MISSING_REQUIRED_VALUE`/`INVALID_DIRECTION_RELATIVE_TO_ENTRY`/`OUTSIDE_ALLOWED_WINDOW`) are all structured. This satisfies Q0.3.3's "no free-form-only error reporting" — a caller can branch on `code`/`reason` programmatically without parsing `message`.

Every violation code in Q0.3 is `severity: "BLOCKING"` — Q0.3 does not yet produce `WARNING`-severity violations (reserved for a future sprint where a rule might be auto-corrected instead of rejected).

## Risk actions (Q0.3.14)

`NO_ACTION`, `ALLOW_ENTRY`, `REJECT_ENTRY`, `MOVE_STOP` (carries `newStopPrice`), `PARTIAL_CLOSE` (carries `closePercent`), `FORCE_EXIT_REQUIRED` (carries `reasonCode: "MAX_HOLDING_PERIOD"`). Exactly one action is returned per `evaluateRisk()` call — never a list — per Q0.3.15's conflict-resolution requirement.

## Outcome (Q0.3.2) — three meanings of REJECTED

`ALLOWED`, `MODIFIED`, `REJECTED`. `REJECTED` covers three distinct situations, disambiguated by `action.type`:

1. `REJECT_ENTRY` — a proposed entry was blocked by input validation, session, position-limit, or daily-loss rules.
2. `FORCE_EXIT_REQUIRED` — an open position exceeded its max holding period.
3. `NO_ACTION` with a `*_CONSTRAINT` violation — a management policy (breakeven/trailing/partial-close) could not be evaluated because required context (e.g. an ATR value) was missing. This is the one case where `REJECTED` does not mean a market/portfolio rule failed — it means the evaluation itself was under-specified by the caller.

No "risk score" concept exists anywhere in Q0.3 — every decision traces to an explicit, named rule.

## Daily loss (Q0.3.6)

**What counts**: REALIZED P&L only, for the current trading day. Explicitly EXCLUDES: unrealized/floating P&L, and any fee/commission/financing not already netted into the caller-supplied `realizedPnlToday` (this layer trusts, never re-derives, that number). A profitable day does not "bank" against a future loss within the same evaluation — `lossSoFar = max(0, -realizedPnlToday)`, clamped at zero, so a positive `realizedPnlToday` simply produces `lossSoFar = 0`.

**Percent-equity mode** is computed against `equityAtDayStart`, not live/current equity — the day's dollar target is fixed at the start of the day, not a moving target as losses (or gains) accrue.

**Day boundary**: `computeTradingDayKey(timestampMs, dayBoundaryOffsetMinutes)` (`daily-loss.ts`) buckets a timestamp into a day using an explicit numeric UTC-offset parameter (never the machine's local timezone or an environment variable). `evaluateDailyLossLimit()` itself does not call this — it stays a pure function of the caller's already-bucketed `realizedPnlToday` (Q0.3.17 purity). A future stateful caller (a backtester) is expected to use `computeTradingDayKey`/`isSameTradingDay` to decide when to reset its own accumulator to 0.

**Only gates NEW entries** — matches Q0.2's original field doc ("no new positions may be opened for the remainder of that day"). It does not force-close already-open positions; that would be a distinct, not-yet-built policy.

## Session hours (Q0.3.8)

Timestamps are converted to local hour/minute in the configured IANA timezone via `Intl.DateTimeFormat` — deterministic, dependent only on the `timezone` string and Node's bundled ICU data, never on the host machine's local zone. Window membership is a **half-open interval `[start, end)`**: the start minute is inside the window, the end minute is not. An unrecognized timezone string produces a deterministic `SESSION_RESTRICTION` / `INVALID_CONFIGURATION` violation rather than an uncaught exception. **Entry-time-only gate** — does not affect exits, matching Q0.2's field doc. An overnight session (crossing midnight) cannot be expressed as one window (Q0.2's `start < end` constraint) — express it as two windows; this is a known, carried-forward limitation, not something Q0.3 works around.

## Max holding period (Q0.3.7)

Whichever of `maxBars`/`maxDurationMs` is configured AND reached first triggers (OR logic). "At the limit" (`>=`, not `>`) counts as exceeded, consistent with every other limit in this layer. Produces `FORCE_EXIT_REQUIRED` — **never closes the position itself**; that remains execution/simulation responsibility. Invalid/non-finite timestamps produce a deterministic violation rather than a wrong duration.

## Stop/target geometry and risk distance (Q0.3.9/10)

BUY: SL strictly below entry, TP strictly above. SELL: SL strictly above entry, TP strictly below. Equal entry/SL or entry/TP is invalid (not "below"/"above"). Missing SL or TP is not itself an error — both remain optional; geometry is validated only for whichever is provided. `riskDistance` = `entry - stop` (BUY) or `stop - entry` (SELL), must be `> 0` for a valid risk. No broker-specific minimum-distance rule is imposed — that remains future `ExecutionSpecification` territory.

## R-multiple (Q0.3.21)

`1R` = the initial risk distance. `computeCurrentR`/`computeRealizedR`/`computeTargetR` are the SAME underlying formula (`favorablePriceMove / riskDistance`) applied at different moments (mid-trade, at exit, at the configured target) — "realized" vs. "current" is about *when* a caller invokes it, not a different calculation. Throws (does not return a violation) if `riskDistance <= 0`, since that represents malformed trade geometry the caller should have caught via `validateEntryGeometry`/`validateRiskDistance` first — this is a primitive for future backtest metrics/Monte Carlo/expectancy work, not itself risk-evaluation output.

## Breakeven (Q0.3.11)

Simplest deterministic model: once price has moved `trigger` (a `DistanceSpec` — absolute/percentage/ATR-multiple) in the position's favor, propose moving the stop to `entry +/- lockOffset`. Like trailing, the proposed stop only "triggers" if it strictly improves on the current stop (never moves backward); a position with no stop yet is always improved by adding one. An ATR-multiple `DistanceSpec` with no ATR value supplied produces a deterministic `BREAKEVEN_CONSTRAINT`/`MISSING_REQUIRED_VALUE` violation, not a thrown exception escaping `evaluateRisk()`.

## Trailing stop (Q0.3.12)

Trigger/Distance/Adjustment kept explicit and separate: once price has moved `activation` in favor, the stop trails `distance` behind the current price. **The stop may only move in a risk-reducing direction and must never move backward** — if the naive computed trail is not strictly better than the current stop, the function returns `triggered: false` (not a violation; simply nothing to do this call). An invalid `currentPrice` produces a deterministic violation.

## Partial close (Q0.3.13)

One-time behavior only (Q0.3's "start simple" directive): once `alreadyTriggered` is true, it never re-triggers, preventing repeated unintended partial closes. `closePercent` always comes from a spec already constrained to `(0, 100]` by `validateRiskSpecification()` (Q0.2) — this layer trusts that invariant rather than re-validating it, so a partial close can never be proposed above 100% of the position by construction.

## Conflict resolution (Q0.3.15)

Explicit, documented priority — safety dominates optimization/management, exactly as suggested:

**Entry evaluation**: (1) input validation (size/geometry/risk-distance/max-position, all collected together) → (2) session → (3) max simultaneous positions → (4) daily loss limit. First blocking failure wins; ALLOWED only if every stage passes.

**Management evaluation**: (1) max holding period (`FORCE_EXIT_REQUIRED`, highest — overrides any stop/partial-close action) → (2) breakeven (`MOVE_STOP`) → (3) trailing stop (`MOVE_STOP`, only reached if breakeven did not trigger this call) → (4) partial close (`PARTIAL_CLOSE`, only reached if neither stop policy triggered) → `NO_ACTION` if nothing above triggers.

No implicit priority anywhere — see `pipeline.ts`'s doc comment and `RISK_CONFLICT` in the golden fixtures for a worked example (max holding period, breakeven, and trailing all individually satisfied simultaneously; max holding period wins).

## Old-engine R&D harvest (Q0.3.25)

Inspected, not imported: `quant_engine/engine.py`'s `RiskConfig` (breakeven trigger/lock, ATR trailing start/multiple, partial-close threshold/pct, daily-loss halt, session hours — the exact concept set Q0.2 already ported as contract fields and Q0.3 now evaluates).

| OLD behavior | NEW semantics | Difference | Reason |
|---|---|---|---|
| `RiskConfig` is one flat, mutable, engine-coupled object; breakeven/trailing/partial-close are evaluated inline inside `run_backtest()`'s loop, directly mutating trade state | `RiskSpecification` (policy) and `evaluateRisk()` (pure evaluation) are separate; nothing is mutated | OLD conflates specification, evaluation, and execution into one imperative loop | Q0.3.17/Q0.3.23 — purity and the Specification/Evaluation/Execution separation are non-negotiable architectural rules this sprint exists to establish |
| OLD's trailing/breakeven distances are configured as fixed engine-wide multipliers (single `RiskConfig` per backtest run) | NEW's `DistanceSpec` supports absolute/percentage/ATR-multiple per-rule, and the whole `RiskSpecification` lives on a per-`StrategySpec` basis | NEW is more granular and strategy-scoped | Matches Q0's StrategySpec-centric design; OLD's engine-global config doesn't fit a multi-strategy research tool |
| OLD's daily-loss halt operates on live/running equity during the backtest loop | NEW's `evaluateDailyLossLimit` takes `equityAtDayStart` (fixed) plus a caller-supplied `realizedPnlToday` | NEW fixes the day's target at day-start rather than letting it drift with intraday equity swings | A day-start-fixed target is simpler to reason about and test deterministically; OLD's live-equity coupling is exactly the kind of hidden-state dependency Q0.3.17 forbids |
| OLD has no explicit "stop must never move backward" guard visible as a separate, testable rule — trailing/breakeven logic is inline and untested (Q0.1's audit found zero automated tests in `quant_engine/`) | NEW makes "never move backward" an explicit, separately tested invariant (Q0.3.19 property test #1) for both breakeven and trailing | NEW adds a safety guarantee OLD never made explicit or verified | Directly addresses a real gap Q0.1's inventory found in OLD |

The new engine remains canonical; nothing above was copied — every NEW function here is freshly written and tested against its own fixtures, only informed by having read OLD's `RiskConfig`.
