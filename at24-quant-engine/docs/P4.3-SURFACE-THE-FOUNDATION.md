# P4.3 — Surface the Foundation: AI Strategy Run + Evidence-First Results

**Status:** Implemented, tested, and visually verified against real, live-rendered UI (headless-Chrome screenshots of the actual shipped component, real engine-computed data). Product-surface sprint over the existing P3/P4 backend — zero `at24-quant-engine/src` changes, zero new execution semantics, zero new indicator families.

## 0. Two real bugs the visual QA pass caught (neither was visible from the offline scripts alone)

Before merge, the actual `AlgoTestPanel.tsx` component was rendered live (a temporary, since-deleted dev-only harness: the real component, real `toCompiledStrategyView()`/`computeSemanticStrategyHash()` output, `window.fetch` intercepted only at the network boundary — never a mockup or a second implementation) and screenshotted via headless Chrome for all three states (registry success, AI success, AI failure). This surfaced two genuine defects the offline scripts did not catch, because they never render the component tree:

1. **Symbol/timeframe from the compiled spec, not the request.** `toCompiledStrategyView()` originally read `spec.instruments[0]?.symbol`/`spec.timeframes[0]` for the "Symbol / Timeframe" field. For an AI-compiled strategy this is correct (the compiler sets it from the real request) — but Golden Strategy's own real `StrategySpec` (`at24-quant-engine/src/reference/golden-strategy.ts`) declares `instruments: [{symbol:"SIMFIXTURE"}]`, `timeframes:["H1"]` as an internal engine fixture identity, unrelated to what it actually traded. The first screenshot showed **"SIMFIXTURE · H1"** where it should show **"XAUUSD · 5m"**. Fixed by removing `symbol`/`timeframe` from `AlgoTestCompiledStrategyView` entirely and reading `AlgoTestRunView.symbol`/`.timeframe` instead — the one field that is always set from the real request, for every strategy source, never re-derived from the spec.
2. **A handled run failure was hidden behind a less-informative duplicate banner.** `AlgoTestPanel`'s top-level render gate was `run && error === undefined`, and `applyResult()`'s failure branch set the top-level `error` state from `run.errorMessage` — meaning a genuinely failed run (compile/validation/data failure) never actually rendered `AlgoTestResults`, and with it the real lifecycle badges and the "did not reach a valid form" compiled-strategy note this phase built specifically for that case. Only a generic red banner showed. Fixed: a handled `status: "failed"` result no longer sets the top-level `error` (reserved now for a genuinely thrown exception, where no `run` object exists at all); `AlgoTestResults` renders unconditionally whenever `run` exists, and its own internal failure rendering (banner + full lifecycle + compiled-strategy note) is what a failed run now shows.

Both fixes are captured in this same PR, verified by re-running the full regression suite (§5) and re-screenshotting all three states.

## 1. Persistence audit (section 11) — done BEFORE any implementation

Read `algo-test.service.ts`, `types/algo-test.ts`, and the Prisma `AlgoTestRun` model before writing any UI code, per the sprint's own instruction.

**What is stored** (`AlgoTestRun` row): `id, userId, strategyId, strategyVersion, symbol, timeframe, startTime, endTime, initialBalance, status, resultHash, resultVersion, engineVersion, parameters, metrics, trades, equityCurve, assumptions, errorCode, errorMessage, createdAt, completedAt`.

**What is NOT stored, for every run regardless of source (registry or AI):** the 8-stage `lifecycle` (P3.8), the compiled `StrategySpec` (`compiledStrategy`), and — new in P4.3 — the semantic `strategyHash`. This was already partially self-disclosed before this phase: `lifecycle`'s own doc comment in `types/algo-test.ts` already said *"Deliberately NOT reconstructed on GET .../[id] reopen... undefined there means 'not (yet) recomputed on reopen'"* — P4.3 confirms this is real (traced through `getAlgoTestRun`, which reads only persisted JSON columns and never sets these three fields) and extends the same honest disclosure to `compiledStrategy`/`strategyHash`, which had no such disclaimer yet.

**Answering the audit questions directly:**
1. What is stored? — see above.
2. What is retrievable after the run? — everything stored, plus `candles` (a live, read-only re-fetch from the historical provider on reopen — never persisted, by design, to avoid storing huge raw datasets).
3. Can a historical AI run be reopened? — yes, generically (`getAlgoTestRun` has no `strategyId`-based branch), but with `lifecycle`/`compiledStrategy`/`strategyHash` absent.
4. Is `StrategySpec` persisted? — no.
5. Is evidence/lifecycle persisted? — no, for **any** run, registry or AI.
6. Is the result persisted? — yes (metrics/trades/equityCurve/resultHash/assumptions).
7. Can the UI reconstruct the complete result from stored data? — mostly, minus lifecycle/compiledStrategy/strategyHash.

**DISCOVERED GAP** (reported, not silently patched, per section 18):
```
Capability: evidence/lifecycle and compiled-strategy visibility surviving a page reload
Current backend state: lifecycle, compiledStrategy, strategyHash are computed at run time
  and returned in the live POST response, but never written to the AlgoTestRun row
Why P4.3 cannot honestly implement full persistence: doing so requires two new nullable
  JSON columns - an actual database migration, which section 11 explicitly puts outside
  this sprint's default scope ("do not automatically create a migration... report the
  gap first")
Recommended future phase: a small, additive migration (nullable `lifecycle Json?`,
  `compiledStrategy Json?`, `strategyHash String?` columns) - low-risk (nullable, additive,
  no existing column touched), scoped as its own tiny phase rather than folded into P4.3
```

**What P4.3 did instead**, staying within the supported portion: the UI renders lifecycle/compiledStrategy/strategyHash fully for a **live** run (the one just executed, still in React state), and shows an explicit, honest **"unavailable — not persisted across a page reload"** state (one of the sprint's own required four visual states) when reopening a run via its URL-round-tripped `testId`. Never fabricated, never silently blank.

## 2. What changed, by layer

**Engine (`at24-quant-engine/src`):** nothing. `git status` on the engine directory is empty for this entire phase.

**Services (`frontend/services/algo-test/algo-test.service.ts`):**
- `toCompiledStrategyView(spec: StrategySpec)` (new, exported for direct testing) — the ONE projection from a real `StrategySpec` to a human-readable `AlgoTestCompiledStrategyView`, used identically for registry and AI-compiled strategies. Built from `describeExpression()`/`describeOperand()` — a generic, recursive renderer over the real `Expression`/`Operand` union (never a per-strategy special case) — plus `describeSizing()`/`describeStopLoss()`/`describeTakeProfit()` over the real `RiskSpecification`. Deliberately has **no** "Filters" field: the real `StrategySpec` has no structurally distinct filter concept (a filter is just another AND-ed clause inside the same entry condition), and inventing one would violate the sprint's own "do not fabricate fields not present in StrategySpec" rule.
- `strategyHash` — `computeSemanticStrategyHash(spec)` (the existing, unmodified engine export), now included in every completed/DATA_VALID-failed response, for both `runAlgoTest` and `compileAndRunAiStrategy`.
- `compiledStrategy` is now populated for **registry** runs too (previously AI-only) — the same function, same field, one fewer asymmetry between the two strategy sources.
- No other behavioral change. `runBacktest()`, the simulation call, the lifecycle-building functions are untouched.

**API routes:** none added or changed. The existing `/api/private/algo-test/runs`, `/runs/[id]`, `/strategies`, `/ai-runs` are consumed as-is.

**Frontend (`frontend/components/chart-engine/AlgoTestPanel.tsx`, `frontend/lib/algo-test/store.ts`):**
- `compileAndRunAiStrategy()` client function added to `store.ts` — a thin wrapper over the existing `/ai-runs` endpoint, matching `runAlgoTest()`'s own shape exactly. Not a second AI execution path.
- A Registry/AI mode toggle replaces the hardcoded `strategies.find(s => s.strategyId === "golden")` — the strategy picker now renders every entry the real registry returns (today: Golden Strategy, ref-ema-crossover); Golden stays the default *selection*, never the only *option*.
- AI mode: a natural-language textarea, no structured parameter form (matches P4.1's own compiler contract — the intent IS the input).
- `AlgoTestResults` is now the single, unified result component for both sources — every new section (`LifecycleSection`, `CompiledStrategyCard`, `RunIdentityCard`) branches only on which fields `run` carries (`run.lifecycle`, `run.compiledStrategy`, `run.strategyHash`), never on `strategyId` or a `mode` flag.
- The chart-symbol gate that previously blocked the whole panel when the pane's active symbol didn't match the strategy's supported symbol is now scoped to Registry mode only (per-selected-strategy). AI mode has no pre-known symbol until the natural-language request is actually compiled (the compiler supports 7 symbols, not one) — gating the entire mode on the current chart pane's symbol would have been dishonest. If a completed AI run's resulting symbol differs from the pane it was launched from, the results still render fully; the chart overlay is simply not pushed, with an explicit inline note saying so.

## 3. Validation / Evidence display (section 4)

The real backend model has 3 `StageOutcome` values (`PASSED`/`NOT_APPLICABLE`/`FAILED`) — there is no 4th "not reached" value. `classifyStage()` recovers the sprint's required 4-state model (passed / failed / not reached / unavailable) **structurally**, from stage order relative to `lifecycle.reachedStage` (P3.8's own documented invariant: *reachedStage stops at the LAST PASSED/NOT_APPLICABLE stage before any failure*) — never by pattern-matching a detail string, which could change wording without notice. "Unavailable" is a separate, outer state: the whole section renders it when `run.lifecycle` itself is `undefined` (the reopen case above).

Two real, separately-computed badges are shown, never merged into one trust score: **"Strategy Valid"** (execution-eligible — `EXECUTION_VALID` reached) is distinct from **"Evidence Verified"** (`lifecycle.fullyVerified`) — exactly the distinction the sprint required.

## 4. Honest failure states (section 12)

- **Compilation/validation/data failure** — `run.status === "failed"` renders a red banner with the real `errorMessage`, plus the real lifecycle badges (showing exactly which stage blocked and why) and, when a `StrategySpec` did exist before the failure (a DATA_VALID-stage failure, i.e. compilation succeeded but historical data could not be fetched), the compiled strategy card too — so the user can see what was *about* to run even though it didn't. No metrics/equity/trades section renders for a failed run.
- **Zero-trade result** — unchanged backend semantics (`EVIDENCE_VERIFIED` still `PASSED` with a "0 trades — a legitimate, reproducible result" detail); the UI renders the full completed-run view (green P&L styling, since `0 >= 0`), with an explicit neutral-toned "0 trades in this window — a legitimate, reproducible result... not necessarily an error" message instead of hiding the trades section.
