# Q0.10 Position Management Audit

## Headline finding

**Breakeven, trailing-stop, partial-close, and max-holding-period execution already exist, fully wired, in Q0.3 (`evaluateRisk()`) and Q0.5 (`simulation-engine.ts`'s action mapping).** Q0.10 is not building this machinery from scratch. What was actually missing, found by this audit:

1. A real, previously-undiscovered bug in Q0.5's frozen `trade-ledger.ts`: R-multiple was computed from the position's *current* (mutable, management-adjusted) stop-loss rather than the stop-loss *at entry*, which crashes the entire simulation the first time breakeven/trailing does its job (moves the stop past entry) and the position later closes. No existing Q0.5/Q0.6 test ever exercised trailing/breakeven through the real simulation engine to a completed trade, so this was never triggered before. **Fixed** — see "The R-multiple fix" below.
2. The MQL4/MQL5 importer (Q0.8) detects `ModifyCallSite`/`PartialCloseCallSite` at the semantic-model level but never reduces either into `RiskSpecification.breakeven`/`trailingStop`/`partialClose`/`maxHoldingPeriod` fields — every MQL-imported strategy's management fields are always empty, regardless of what the source actually does.
3. The Q0.9 eligibility gate never explicitly evaluates management fields at all — they pass through as an unchecked side effect of nothing blocking them, not because anything positively confirmed them safe. `docs/Q0.9_IR_TO_SPEC.md` even documented this as an open gap ("not yet wired through the eligibility gate").

**Where execution stops, precisely**: for a hand-built `StrategyIR`/`StrategySpec` (Q0.7's own golden fixtures `fixtureBreakeven`/`fixtureTrailing`/`fixturePartialClose` already exist), execution does NOT stop anywhere in the Policy→Evaluation→Action→Execution chain — it runs correctly today, after the R-multiple fix below. For an MQL4/MQL5-*imported* strategy, execution stops at the **ir-generator** — the semantic model has already detected the relevant source pattern, but nothing converts it into a `RiskSpecification` field, so the imported IR's `ir.risk.breakeven`/`trailingStop`/`partialClose`/`maxHoldingPeriod` are always absent regardless of what the source does.

## The R-multiple fix (Q0.10.9 / Q0.10.10)

**Root cause**: `trade-ledger.ts`'s `buildTrade()` computed `rMultiple` via `computeRealizedR(side, position.entryPrice, position.stopLoss, exitPrice)` — using `position.stopLoss`, the CURRENT protective stop, which breakeven/trailing correctly and deliberately move past entry once a trade is profitable enough (that is the entire point of those features: lock in profit). Once the stop sits past entry, `computeRiskDistance` correctly returns a non-positive value (the position is now risk-free or better), and `computeRMultiple` correctly throws per its own existing, deliberately-strict, already-tested contract (`test/risk-r-multiple.test.ts`'s `"computeRMultiple throws for a non-positive risk distance"` — this guard is correct and was NOT changed).

**Fix**: `Position` (Q0's frozen domain type, already additively extended once before by Q0.5 itself for `fees`/`lastModifiedTimestamp`) gains one new optional field, `initialStopLoss` — the stop-loss level at the moment the position opened, which never changes afterward. `position-engine.ts`'s `openPosition()` populates it equal to the opening `stopLoss` (one line). `trade-ledger.ts`'s `buildTrade()` now computes R-multiple from `position.initialStopLoss ?? position.stopLoss` instead of `position.stopLoss` alone (one line).

**Why this is safe**: `initialStopLoss` always equals `stopLoss` at the moment a position opens, and every other position-engine function (`increasePosition`/`reducePosition`/`closePosition`) passes it through unchanged via `...position` spreads — it only ever diverges from `stopLoss` once breakeven/trailing has moved the stop, a scenario **zero existing Q0.5/Q0.6 test exercises through the real simulation engine** (confirmed: no `test/simulation-*.test.ts` or `test/fidelity-*.test.ts` file references `trailingStop`/`breakeven` at all — they are only unit-tested in isolation against `evaluateBreakeven()`/`evaluateTrailingStop()` directly, never run through `runSimulation()` to a completed trade). The full 771-test regression suite was re-run immediately before and after this change with byte-identical pass counts — every existing R-multiple value in every existing test is unaffected.

**Why this required touching two files the sprint marks frozen**: the crash occurs entirely inside `runSimulation()`'s call chain, before any `SimulationResult` is ever returned — there is no extension point outside Q0.5's own code where an "additive layer" could intercept it, because there is nothing to post-process; the function throws instead of returning. The alternative — leaving Q0.5 untouched and only proving breakeven/trailing through fixtures engineered to never let a management-adjusted stop actually get hit — was considered and rejected: it would make this sprint's own Critical Success Criterion (breakeven+trailing executing to a genuine, complete ledger) provably false while appearing to pass. The change made is the minimal one that resolves the actual defect: two one-line insertions, additive-only, fully regression-proven.

## Conflict/priority architecture — verified correct, no code change needed

`pipeline.ts`'s `evaluateManagement()` implements the documented priority (max holding > breakeven > trailing > partial close) as a strict sequential if-chain: the first stage that triggers returns immediately, so **at most one management action is ever produced per bar** — there is no scenario where two management actions race or need arbitration within a single `evaluateRisk()` call. This is correct by construction, not by convention.

Same-bar SL/TP conflicts are resolved **before** management evaluation ever runs, in `bar-fill-model.ts`'s `resolveProtectiveExit()` (Step 1b in `simulation-engine.ts`, ahead of Step 5's risk evaluation): if both levels are reachable within one bar, the conservative rule (stop-loss wins, flagged `ambiguous: true`) already applies, and — because Step 1b runs first — a position that closes there never reaches Step 5's management evaluation that same bar at all. This means "trailing + SL", "partial close + SL/TP", and "holding expiry + SL/TP" same-bar conflicts are already structurally resolved by step ordering: whichever protective exit fires in Step 1b wins outright, and management (including a same-bar holding-period expiry) simply never gets evaluated for a position that no longer exists. Golden fixtures in `test/q10-conflict-semantics.test.ts` prove this holds for every pairing in Q0.10.8's list, rather than merely asserting it from reading the code.

## What Q0.10 actually had to build (the real, net-new scope)

1. The R-multiple fix above (2 lines, 2 frozen files, additive).
2. Explicit, positive eligibility-gate support for management fields (`checkReductionEligibility` now evaluates `RiskSpecification.breakeven`/`trailingStop`/`partialClose`/`maxHoldingPeriod` against a fixed catalog of currently-representable shapes, distinguishing SUPPORTED from an as-yet-UNSUPPORTED variant, rather than silently letting everything through unchecked).
3. New domain contracts (`PositionManagementPolicy`, `StopAdjustment`, `PartialCloseInstruction`, `ForcedExitInstruction`) as an explicit, audit-facing vocabulary layered on top of the existing `RiskSpecification`/`RiskAction` types — never a duplicate execution path.
4. MQL4/MQL5 detection and reduction of `OrderModify`/`PositionModify`-based breakeven and trailing patterns, partial-close volume patterns, and time-based exit patterns — entirely new semantic-analyzer/ir-generator logic, since Q0.8 only detected these calls, never interpreted them.
5. 12 golden fixtures, a 14-item failure catalog, lookahead/determinism/replay/immutability tests, real MQL E2E fixtures (management strategy, partial-close E2E, short E2E, ATR E2E), G01 regression, D1/D2 compatibility test, metrics/provenance verification, a benchmark, and 9 documentation files — all genuinely new deliverables, detailed in the sibling `Q0.10_*.md` documents.
