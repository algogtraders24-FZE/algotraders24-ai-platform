# Q0.5 Simulation Architecture

## The orchestrator's pipeline (Q0.5.29)

`runSimulation(bars, config)` (`src/runtime/simulation/simulation-engine.ts`) — a single function, not a class, driven by one `EventQueue` seeded ONE bar at a time (see `docs/Q0.5_EVENT_QUEUE.md` for why bulk-seeding was tried and rejected). Per `MARKET_BAR` event dequeued:

```
1. Resolve pending orders for this instrument against this bar
   (skip any order created at or after this bar's timestamp — same-bar safety)
2. Check the open position's own stop-loss/take-profit against this bar
   (resolveProtectiveExit — the mandatory conservative SL/TP-ambiguity case)
3. Mark to market (recompute unrealizedPnl/equity from this bar's close)
4. Day-boundary tracking (resets realizedPnlToday when computeTradingDayKey changes)
5. Strategy calculation: build MarketState -> generateSignal() (Q0, unmodified) -> buildDecision()
6. Risk evaluation: build a RiskEvaluationInput (ENTRY or MANAGEMENT mode) -> evaluateRisk() (Q0.3, UNMODIFIED)
7. Map the returned RiskAction to an order-engine operation (see below) and execute it
8. Enqueue the NEXT bar (only now — after every derived event above has its sequence number)
```

Only `ON_BAR_CLOSE` calculation timing is implemented — `generateSignal()` is Q0's own, unmodified function, called once per bar. No new recalculation semantics were invented (Q0.5.29's explicit boundary); `ON_EVERY_TICK`/`ON_ORDER_FILL`/etc. remain reserved (`docs/Q0.4_EVENT_MODEL.md`).

## Same-bar safety (Q0.5.30) — exactly one documented answer

A signal computed at bar T's close can only produce an order that becomes eligible starting bar T+1. This is enforced in two independent, redundant places: (1) structurally, by the event-driven flow itself — an order created while processing bar T is only ever checked against bars dequeued AFTER T; (2) an explicit guard in the pending-order resolution loop (`if (order.creationTimestamp >= bar.timestamp) continue;`), which exists specifically so this invariant holds even if a future refactor changes the event flow. `test/simulation-same-bar-safety.test.ts` proves both the normal case and the edge case (a signal on the LAST available bar — the resulting order can never fill and is finalized `EXPIRED`, never a phantom same-bar fill).

## Risk integration (Q0.5.25) — Q0.3 is consumed, never modified

```
Strategy -> Signal -> Decision -> evaluateRisk() -> RiskAction -> Order Engine -> Execution -> Position
```

The orchestrator imports `evaluateRisk` from `runtime/risk/pipeline.js` directly — Q0.3's source files are untouched by this sprint (confirmed by `git status`; see the final report). Two `RiskEvaluationInput` shapes are constructed depending on state:

- **No open position, `Decision.action === "ENTER"`**: an ENTRY-mode input — `proposedEntry.quantity` resolved via `resolvePositionSize()`, `.stopLoss`/`.takeProfit` via `resolveStopLossPrice()`/`resolveTakeProfitPrice()` (`docs/Q0.5_EXECUTION_MODEL.md`'s rule-resolvers, all reusing Q0.2/Q0.3's `StopLossRule`/`TakeProfitRule`/`PositionSizingMethod` types, never redefining them).
- **An open position exists**: a MANAGEMENT-mode input — `existingPosition.barsHeld` computed from a per-position entry-bar-index map in `SimulationState`; `partialCloseAlreadyTriggered` from a per-position set (Q0.3's one-time partial-close semantics, reused not reimplemented).

## Risk-action mapping (Q0.5.26)

| RiskAction | Mapping | Effect |
|---|---|---|
| `ALLOW_ENTRY` | `CREATE_ENTRY_ORDER` (type `MARKET`) | a new `SimulationOrder` is created, `SUBMITTED`, `ACCEPTED` |
| `REJECT_ENTRY` | `NO_OP` | nothing |
| `NO_ACTION` | `NO_OP` | nothing |
| `MOVE_STOP` | `MODIFY_STOP` | the open position's `stopLoss` field is updated in place (a NEW Position object, per immutability — not a mutation) |
| `PARTIAL_CLOSE` | `REDUCE_POSITION` | `reducePosition()` by `quantity * closePercent/100`, realized via `applyRealizedTrade` |
| `FORCE_EXIT_REQUIRED` | `FORCE_EXIT` | `closePosition()` at the current bar's close |

`mapRiskAction()` (`runtime/simulation/risk-action-mapping.ts`) is a pure function returning a discriminated-union description of the intended operation — kept separate from the orchestrator's actual side-effecting code so the mapping itself is independently unit-testable (`test/simulation-risk-action-mapping.test.ts`). An unrecognized `RiskAction` shape throws explicitly via an exhaustive-switch `default` branch (Q0.5.26's "any unsupported mapping must fail explicitly") — unreachable through TS's closed union today, but a real safety net if a future sprint adds a new `RiskAction` variant without updating this mapping.

## Simulation clock and state (Q0.5.27/28)

There is no separate "clock" object — `SimulationState.clock` is simply the timestamp of the most recently processed event, updated once per bar. No `Date.now()`, no system time, no local machine timezone anywhere in the simulation runtime (statically enforced, `test/simulation-determinism.test.ts`). `SimulationState` (`domain/simulation/simulation-state.ts`) is a plain, immutable snapshot — every processing step produces a NEW state object via spreads/copies, never an in-place mutation; `ReadonlyMap`/`ReadonlySet` types make this the TypeScript-enforced default, not just a convention.

## Performance baseline (Q0.5.45)

Recorded via `npm run benchmark:simulation` (`scripts/benchmark-simulation.ts`), N=100,000 synthetic operations (N=1,000 for the full end-to-end case), this machine, 2026. Correctness-first: not a gate, no thresholds asserted anywhere in the test suite.

| Operation | Total | Per-op |
|---|---|---|
| EventQueue enqueue+dequeue | 251ms | 2.51us |
| Order create + full lifecycle transition | 145ms | 1.45us |
| MARKET fill resolution | 18ms | 0.18us |
| LIMIT fill evaluation | 25ms | 0.25us |
| Position open + reduce (full close) | 48ms | 0.48us |
| Account applyFill | 13ms | 0.13us |
| Full end-to-end simulation (6-bar golden fixture) | 448ms / 1,000 runs | 448us/run |

**Observations, not yet acted on** (correctness-first, per Q0.5.45): the full end-to-end run's 448us includes a fresh `StrategySpec`/`SimulationConfig` object construction and a `computeSemanticStrategyHash()` call every single run in the benchmark loop (not something a real backtest would repeat per-bar) — a future sprint optimizing this path should hoist the hash computation and static config construction outside any per-run hot loop before assuming the simulation core itself is the bottleneck. `EventQueue`'s per-op cost (2.51us) is the single largest per-op figure among the primitives — consistent with it being the one O(log n) structure in an otherwise O(1)-per-operation set; this is the first place to look if a future sprint's tick-level (D4/D5) fidelity work needs to process orders of magnitude more events.

## What Q0.5 does NOT do

No tick engine, no bid/ask engine, no depth/liquidity/market-impact modeling, no advanced slippage/variable-latency/settlement engine, no Strategy IR parser (Pine/MQL/NinjaScript/cBot), no optimizer/WFO/Monte Carlo/CPCV, no portfolio allocation across multiple instruments, no broker adapters, no live execution, no AI-driven execution. All remain exactly as deferred by Q0.4.
