# Q0.10 — Max Holding Period Semantics

## Contract

`MaxHoldingPeriodRule { maxBars?: number; maxDurationMs?: number }` (Q0.2, unchanged; validated to require at least one of the two). A position must be closed once EITHER configured limit is reached, whichever comes first (OR logic).

## Evaluation (`runtime/risk/holding-period.ts`, Q0.3, unmodified)

`evaluateMaxHoldingPeriod(spec, position, asOf)`:

- `durationMs = asOf - position.entryTimestamp`; `durationExceeded = maxDurationMs !== undefined && durationMs >= maxDurationMs`.
- `barsExceeded = maxBars !== undefined && position.barsHeld !== undefined && position.barsHeld >= maxBars`.
- **Exact boundary semantics**: `>=`, not `>` — "at the limit" counts as exceeded, consistent with every other limit in the package (matching `test/q10-golden-fixtures.test.ts`'s `PM_MAX_HOLDING`: `maxBars: 2`, force-exits exactly when `barsHeld === 2`, not one bar later).
- Non-finite timestamps (`entryTimestamp`/`asOf`) produce an explicit `MAX_HOLDING_PERIOD`/`BLOCKING` violation rather than a silently-wrong duration (`test/q10-failure-catalog.test.ts` item 7). An inverted clock (`asOf` before `entryTimestamp`, item 8) produces a negative duration that never falsely compares `>=` a positive limit — never a false-positive force-exit.

`barsHeld` is threaded from `simulation-engine.ts`'s `entryBarIndexByPosition` map (Q0.5, unmodified): `barsHeld = barIndex - entryBarIndexByPosition.get(positionId)`, recorded the instant a position opens.

## Priority — always highest

`pipeline.ts`'s `evaluateManagement()` checks max-holding FIRST, before breakeven/trailing/partial-close, matching the documented, tested priority: safety/mandatory-exit constraints dominate optimization/management constraints (rule 16 in the master blueprint's non-negotiable list). `PM_MULTI_ACTION`-style reasoning applies identically here — a bar where BOTH max-holding has expired AND a management rule would also trigger only ever produces the `FORCE_EXIT_REQUIRED` action; the lower-priority checks are structurally unreached (early `return` in `evaluateManagement`).

## No lookahead

`test/q10-lookahead-determinism-replay.test.ts`'s second `Q0.10.21` case proves the DECISION to force-exit at bar N (because `barsHeld >= maxBars`) is identical regardless of what bar N's own price does — only the resulting exit PRICE (always `bar.close` of the evaluation bar, per `simulation-engine.ts`'s `FORCE_EXIT` mapping) legitimately varies with that bar's actual data.

## Same-bar conflict with a protective stop

`PM_EXPIRY_CONFLICT` (`test/q10-golden-fixtures.test.ts`) proves a stop-loss reachable on the SAME bar the holding period would also expire resolves via Step 1b (the protective check) before Step 5 (holding-period evaluation) ever runs — exactly one exit is recorded, never a stop-loss exit immediately followed by a separate forced exit. See `docs/Q0.10_CONFLICT_SEMANTICS.md`.

## MQL source-pattern detection

See `docs/Q0.10_MQL_MANAGEMENT.md` — the provable shape is `if (TimeCurrent() - OrderOpenTime() >= <literalSeconds>) { OrderClose(...) }` (or the MQL5 `PositionGetInteger(POSITION_TIME)` equivalent), reduced to `maxHoldingPeriod.maxDurationMs = literalSeconds * 1000`.
