## Why G01 stays blocked

G01's blocking reason is, and remains, its multi-bar, cross-file, `#include`-spanning entry/exit STATE MACHINE (Liquidity Sweep → Displacement → MSS → FVG → Retest) — a shape no version of this importer's `simpleEntryConditions` reconstruction (`if(indicatorA <op> indicatorB)`) has ever been able to represent, honestly reported as a `BLOCKING` `UnsupportedSemantic` since Q0.8. Q0.13 adds NO new entry/exit-condition reconstruction capability whatsoever — it is scoped entirely to PENDING-ORDER MANAGEMENT (a call detected once an order already exists), which is structurally downstream of, and irrelevant to, whether G01's own entry logic can be represented at all.

## Did the `MANAGEMENT_ACCESSOR_FUNCTIONS` fix (adding `"OrderType"`) accidentally unblock G01?

No. G01's real source calls `OrderType()` alongside genuinely gating calls (`PositionsTotal`/`PositionGetTicket`, cited explicitly in `ir-generator.ts`'s own doc comment since Q0.9) — `gatingPositionQueries.length` remains well above zero regardless of whether `OrderType` is counted as an accessor, so the pyramiding/reversal heuristic is completely unaffected for G01. This was verified directly: the identical 17/17 G01 test outcomes before and after the fix, including the specific test asserting G01's `positionManagement` falls to the conservative (`PLATFORM_DEFINED`) branch.

## Did Q0.13's new pending-order-management detection change ANY G01 diagnostic?

No new detector in this sprint fires on G01's real source in any way that changes its reported diagnostics — `test/mql-g01-import.test.ts`'s existing assertions (all 17) passed byte-for-byte identically before and after. G01's `#include`-spanning `AT24_G01_Risk.mqh`/order-management logic (if it contains `OrderModify`/`OrderDelete` calls at all) lives in a file this importer does not parse at all (Q0.8's own `#include`-resolution scope boundary, unchanged by Q0.13 — see rule 16 of Q0.13's own safety rules, honored: "do NOT attempt full `#include` resolution... this is especially important for eventually unblocking G01-class systems... do not weaken G01's existing BLOCKED status merely to improve the test score"). Any `OrderModify`/`OrderDelete` call physically present in G01's OWN top-level `.mq5` file (not its `#include`d headers) WOULD be detected by Q0.13's new call-site logic exactly like any other source — but this has zero bearing on G01's overall BLOCKED status, since that status is entirely determined by the entry/exit state-machine gap, independent of anything pending-order-management related.
