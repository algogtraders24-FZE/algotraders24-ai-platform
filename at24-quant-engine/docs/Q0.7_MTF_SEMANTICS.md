# Q0.7 MTF Semantics

## SeriesAvailability and roles (Q0.7.19)

Every timeframe a StrategyIR touches is declared in `ir.timeframeSeries: readonly SeriesAvailability[]` (`domain/strategy-ir/mtf-ir.ts`), each with an explicit `role` (`EXECUTION|SIGNAL|HIGHER|LOWER`), `availabilityPolicy`, and `alignmentPolicy` — never an implicit "the strategy's own chart timeframe." This is a genuinely NEW concept relative to Q0/Q0.5's `MarketState`, which assumes a single implicit timeframe throughout.

## The canonical HTF-lookahead rule (Q0.7.20) — CRITICAL

**An HTF observation becomes available to a lower-timeframe evaluation only at the instant the HTF bar CLOSES, never before.** Restated directly from `docs/Q0.4_LOOKAHEAD_REPAINTING.md`'s HTF-leakage research, now enforced by `runtime/strategy-ir/ir-validator.ts`'s `checkHTFLookahead()`: any `timeframeSeries` entry with `role: "HIGHER"` whose `availabilityPolicy` is anything other than `"HTF_CLOSE_AVAILABLE"` is BLOCKING — `HTF_OPEN_AVAILABLE`/`INTRABAR_AVAILABLE` exist ONLY so a translator can RECORD that a source platform's construct claims earlier availability; the validator never treats either as a safe, executable alternative (`test/strategy-ir-failure-catalog.test.ts` item 9).

## request.security()-shaped MTF reads (Q0.7.21)

`RequestSecurityCapability` (`domain/strategy-ir/mtf-ir.ts`) gives the IR enough structure to represent Pine's `request.security()` semantics WITHOUT a Pine parser: `sourceTimeframe`/`requestedTimeframe`/`lookahead: "ON"|"OFF"`/`gapsFilled`/`confirmedOnly`. The validator rejects `lookahead: "ON"` outright (the unsafe direction Q0.4 researched — AT24 never executes it, only records that a source strategy used it) and rejects `confirmedOnly: false` too (an unconfirmed HTF read is, by definition, a repainting/lookahead risk — see `docs/Q0.7_LOOKAHEAD_REPAINTING.md`). Fixture 15 (`fixturePineRequestSecurity`) demonstrates the SAFE case (`lookahead: "OFF"`, `confirmedOnly: true`); fixture 23 (`fixtureRepainting`) demonstrates the unsafe one and is proven BLOCKED.

## Execution capability vs. structural validity

`computeExecutionCompatibility()` (`docs/Q0.7_TRANSLATION_CONTRACT.md`) separately confirms that AT24's OWN engine cannot yet execute a genuine `HIGHER`-role dual-timeframe STRATEGY (as opposed to `LOWER`-role execution-fidelity detail, which Q0.6's D2/D3 engine DOES support) — `test/strategy-ir-execution-compatibility.test.ts` proves a `HIGHER`-role series is `UNSUPPORTED` regardless of target fidelity, while a `LOWER`-role series is `UNSUPPORTED` against `D1_OHLC` but `SUPPORTED` against `D2_LOWER_TIMEFRAME`/`D3_M1` — the two axes (structural IR validity, and whether AT24's simulation engine can currently execute the declared semantics) are independently checkable and must never be conflated.

## `TimeFrontier` reuse, not duplication

`docs/Q0.6_MTF_SAFETY.md` already proved `TimeFrontier` (Q0.2) applies unmodified to a lower-timeframe child series. Q0.7 adds no second frontier primitive — a future sprint building a genuine dual-timeframe STRATEGY (reading a `HIGHER`-role series' indicator values, not just execution-fidelity child bars) would gate that HTF series' availability with the SAME `TimeFrontier`, applied at the HTF's own bar boundaries.

## What Q0.7 does NOT do

No genuine dual-timeframe STRATEGY calculation exists (`generateSignal()` remains single-timeframe, unchanged). No cross-symbol MTF. No alignment-policy EVALUATION logic (`AlignmentPolicy` is recorded, not yet interpreted by any runtime function).
