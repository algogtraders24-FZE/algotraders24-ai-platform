# Q0.11 — STOP_LIMIT Two-Stage Lifecycle

## The two stages

1. **STOP trigger**: once price reaches the stop level, the order is armed. If the bar's own OPEN already proves the trigger AND satisfies the limit in the same bar (`open >= stop && open <= limit` for BUY, mirrored for SELL), the order fills IMMEDIATELY at that open — no separate trigger stage needed (`resolveStopLimitFill()`'s "unambiguous gap" branch). Otherwise, if only the STOP is provably reached (bar's high/low crosses it) without open-proof of the limit, the order transitions to `TRIGGERED` and is NOT filled this bar.
2. **LIMIT activation → fill**: on every subsequent bar, a `TRIGGERED` order is re-evaluated as a plain LIMIT order at the SAME limit price (`simulation-engine.ts`'s Step 1 dispatch: `order.status === "TRIGGERED" ? resolveLimitFill(...) : resolveStopLimitFill(...)`) — reusing `resolveLimitFill()` verbatim, never a second limit-fill implementation.

## The possible "triggered but never filled" outcome (Q0.11.7's explicit requirement)

If price never again satisfies the limit before the simulation ends, the order stays `TRIGGERED` (never `FILLED`) and is transitioned to `EXPIRED` at end-of-run (`simulation-engine.ts`'s finalize step, Q0.5, unmodified). This state remains fully visible: the `ORDER_TRIGGERED` event was recorded when the stop fired, and `executionStatistics.ordersExpired` reflects the eventual expiry — no trade is fabricated, and no state silently disappears. Proven exhaustively in `test/q11-gap-fixtures.test.ts`'s `STOP_LIMIT_NO_FILL` (contrasted directly against `STOP_LIMIT_FILL`, the successful case, using the identical stop-trigger setup with only the LATER bars differing).

## Golden fixtures

`test/q11-golden-fixtures.test.ts`'s `STOP_LIMIT_BUY`/`STOP_LIMIT_SELL` exercise the full two-bar TRIGGERED→FILLED sequence for both directions. `test/q11-intrabar-fixtures.test.ts`'s `SAME_BAR_TRIGGER_FILL` exercises the unambiguous one-bar fast path. `test/q11-gap-fixtures.test.ts`'s `STOP_LIMIT_FILL`/`STOP_LIMIT_NO_FILL` exercise the multi-bar TRIGGERED-then-eventually-resolved and TRIGGERED-then-never-resolved cases respectively.

## Why this required no new fill-resolution code

`resolveStopLimitFill()` already existed, complete and unit-tested in isolation (`test/simulation-fill-model.test.ts`), before Q0.11 began. The ONLY missing piece was a real caller ever constructing a `STOP_LIMIT` order at all — see `docs/Q0.11_ORDER_SEMANTICS.md` for the full chain of additive fixes that made this reachable.
