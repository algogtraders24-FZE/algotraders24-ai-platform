# Q0.5 Determinism

## The success criterion (repeated because it is the whole point of this sprint)

Same input data + same strategy + same configuration + same risk rules must produce the EXACT SAME events, orders, fills, positions, account, trades, metrics, and provenance — on repeated execution AND on replay.

## A real bug this sprint found and fixed

Q0.5's first implementation of `runSimulation()` seeded every input bar into the `EventQueue` in one bulk pass before processing began. Because `EventQueue`'s `sequence` counter is a single, shared, monotonically-increasing value, that meant every bar's `MARKET_BAR` event claimed a sequence number up front — so bar 10's event consumed sequence 10 *before* bar 0's own derived events (`STRATEGY_CALCULATED`, `ORDER_CREATED`, `ORDER_FILLED`, ...) had a chance to claim any sequence numbers at all. Concretely: a `runSimulation` call over a 6-bar window and an otherwise-identical call over an 8-bar window produced **different `tradeId`/`orderId` strings for the same, identically-priced, identically-timed first trade** — not because any decision or fill price differed, but because the mere PRESENCE of two additional future bars shifted every subsequent sequence number.

This was caught by `test/simulation-lookahead.test.ts`'s very first assertion (`assert.deepEqual(longRun.tradeLedger[0], shortRun.tradeLedger[0])`) — exactly the kind of test the sprint's Q0.5.39 requirement exists to demand, and exactly why "the trade's *values* matched" is not sufficient; the *identity* has to match too, since a future consumer (a `PlatformDiscrepancyReport`, a re-run comparison, an audit) may key off the ID.

**The fix**: only the first bar is seeded upfront. Each subsequent bar is enqueued only once the CURRENT bar's entire processing pipeline — including every derived event it produces — has already consumed its sequence numbers. This makes sequence assignment a pure function of "what has actually been processed so far," never of "what exists in the input, including the future."

## Determinism sources, verified

1. **No wall-clock, no randomness, no environment access anywhere in the simulation runtime** — statically enforced by `test/simulation-determinism.test.ts` scanning every file in `src/runtime/simulation/` for `Date.now()`, `Math.random()`, `process.env`, bare `new Date()`, and `crypto.randomUUID` (the same pattern Q0.3's `risk-determinism.test.ts` established, now extended to the simulation layer).
2. **Every ID is a deterministic string function of its own inputs** — event IDs (`docs/Q0.5_EVENT_QUEUE.md`), order IDs (`docs/Q0.5_ORDER_ENGINE.md`), trade IDs (`${position.id}:${timestamp}:${ledgerLength}`) — never a random UUID.
3. **Every state transition is a pure function** — `transitionOrder`, `openPosition`/`increasePosition`/`reducePosition`/`closePosition`, `applyFill`/`markToMarket` all return new objects; none mutates its input (independently verified per-module in their respective test files, and end-to-end in `test/simulation-immutability.test.ts`).
4. **The result hash** — `SimulationResult.resultHash` is `computeCanonicalHash()` (Q0.2's `runtime/determinism.ts`, reused not reimplemented) over every field of the result except the hash itself, giving a single equality check that certifies the ENTIRE outcome matched (`test/simulation-determinism.test.ts`'s three-run comparison, `test/simulation-e2e-golden.test.ts`'s hash-length sanity check).

## Replay (Q0.5.37)

`test/simulation-replay.test.ts`: replaying the identical recorded bar stream (and separately, a JSON-round-tripped copy of it, proving serialization boundaries don't introduce drift) through a second, fully independent `runSimulation()` call reproduces an identical `finalAccount`, `finalPositions`, `tradeLedger`, `metrics`, and `resultHash`.

## Lookahead safety (Q0.5.39)

Proven two ways: (1) directly, by comparing a truncated simulation's first trade against the same-length PREFIX of a longer simulation's trade ledger — after the sequence-numbering fix above, these are now byte-identical; (2) against the existing `TimeFrontier` primitive (Q0.2) — bars sliced via `TimeFrontier.availableBars()` at a given cursor produce the identical `resultHash` as a plain array slice to that same point, both at the end of the available window and at an arbitrary mid-run cursor (`test/simulation-lookahead.test.ts`).

## Immutability (Q0.5.38)

Historical `Order`/`Trade`/`Position`/`Account` records are never silently rewritten. Proven by deep-freezing the input `bars` array (and separately, the `SimulationConfig`, which is frozen directly rather than `structuredClone`d, since its model objects carry function properties `structuredClone` cannot clone — `Object.freeze` works fine on functions) before calling `runSimulation()`: `Object.freeze` throws a `TypeError` on any attempted write in strict-mode ESM, so a silent mutation attempt surfaces as a thrown error rather than passing unnoticed (`test/simulation-immutability.test.ts`). Every `Trade` the `TradeLedger` records is independently frozen at creation time, regardless of whether the caller froze anything.
