# Q0.13 — Compilation (IR → StrategySpec)

## The chain

```
MQLSemanticModel.pendingOrderManagementCalls[]      (domain/mql-importer/semantic-model.ts, Q0.13)
        ↓ ir-generator.ts's toTargetIR/toConditionIR/toOperationIR
StrategyIR.pendingOrderManagement.rules[]            (domain/strategy-ir/pending-order-management-ir.ts)
        ↓ ir-to-spec-reducer.ts's toPendingOrderManagementRule (direct structural passthrough)
StrategySpec.pendingOrderManagement.rules[]          (domain/pending-order-management-policy.ts)
        ↓ simulation-adapter.ts's executableRules() filter
SimulationConfig.pendingOrderManagementPolicy        (runtime/simulation/simulation-engine.ts)
```

Every arrow above is a NEW, additive edge in an already-existing pipeline — no existing arrow (e.g. `ir.risk → strategySpec.risk`) was altered.

## Why the IR→Spec passthrough never filters

`toPendingOrderManagementRule()` (`ir-to-spec-reducer.ts`) copies EVERY rule — including `semanticFidelity: "UNKNOWN"` ones — from IR to StrategySpec unfiltered, exactly mirroring how `ir.risk` passes through to `strategySpec.risk` untouched (Q0.9.17/18's own precedent). Filtering happens exactly ONCE, at the LAST possible point before real execution (`simulation-adapter.ts`'s `executableRules()` call) — never earlier, so a rule's non-executable status remains visible in `StrategySpec` for provenance/audit tooling that inspects a compiled spec without running it.

## Why `markUnsupported` uses WARNING, not BLOCKING, for an unresolved rule

See `Q0.13_EXISTING_ARCHITECTURE_AUDIT.md`'s dedicated section — `validateStrategyIR()`'s frozen Q0.7.31 rule makes ANY `BLOCKING`-severity `UnsupportedSemantic` fail the WHOLE IR's execution eligibility, which would mean one unprovable pending-order rule blocks an otherwise-perfectly-executable strategy for an unrelated reason. `WARNING` matches Q0.10's own established precedent for the identical situation (a partially-reconstructed management pattern).

## Why `MODIFY_STOP`/`MODIFY_LIMIT` require an `ORDER_TYPE_FILTER` condition

`OrderModify`'s price argument means different things depending on whether the target ticket is a LIMIT or a STOP order — but `OrderModify` itself carries no type information (the ticket does, but this importer never resolves a ticket's ACTUAL runtime type, only structural facts about the source). The ONLY way this importer can know, statically and without guessing, whether to emit `MODIFY_STOP` or `MODIFY_LIMIT` is when the SAME `if` that guards the call ALSO asserts the order's type (`if(OrderType()==OP_BUYSTOP) OrderModify(...)`). Absent that, the operation resolves `UNKNOWN` — this is a deliberate, documented precision/coverage tradeoff, not an oversight (Q0.13's "never guess" rule applied literally).

## Why the new price's arithmetic BASE (Bid/Ask/OrderOpenPrice/anything) is discarded, only its MAGNITUDE survives

`resolveRiskLegBinding()` (Q0.9, reused verbatim) extracts ONLY the literal/ATR-multiple DISTANCE from a `<base> ± <term>` expression — it has never cared what `<base>` was, for SL/TP legs OR for Q0.10's breakeven/trailing reconstruction. A source expression like `Bid + 0.0015` yields `distance: 0.0015` regardless of whether the base was `Bid`, `Ask`, `OrderOpenPrice()`, or `Close[0]` — the SAME pre-existing precedent this sprint reuses rather than invents. At runtime, `evaluatePendingOrderManagementPolicy` applies that magnitude against AT24's own canonical, deterministic reference (the CURRENT bar's `close`) — never attempting to reconstruct what "Bid" would have been (no live bid/ask feed exists in this OHLCV-only engine, Q0.11.3's rule, unchanged). This is a real, acknowledged divergence from a live broker's exact tick-level price, documented here rather than hidden, and structurally identical in kind to Q0.9/Q0.10's own SL/TP-distance reconstruction (never flagged as a special new approximation because it is the SAME one already accepted for those rules).
