# Q0.8 MQL Execution Mapping

## Orders (Q0.8.19-21)

`OrderCallSite` records exactly what the source passed, as SOURCE-TEXT expressions (`volumeExpr`/`priceExpr`/`slExpr`/`tpExpr`/`commentExpr`), never evaluated — a future reducer decides whether/how to turn `"lots"` (a variable name) into an actual number. Two distinct calling conventions are correctly distinguished by their real, different argument positions:

- **MQL4 `OrderSend(symbol, cmd, volume, price, slippage, stoploss, takeprofit, comment, magic, expiration, color)`** — `cmd` (args[1]) determines `side`; `stoploss`/`takeprofit` are args[5]/args[6].
- **MQL5 `CTrade::Buy/Sell(volume, symbol, price, sl, tp, comment)`** — `sl`/`tp` are args[3]/args[4].

Never conflated: an early implementation of this sprint used the SAME argument indices for both (a bug caught before shipping — see `docs/Q0.8_MQL4_MQL5_PARITY.md`).

## `Entry IR` mapping — MARKET only, always `INTRABAR` timing

Both `OrderSend` and `CTrade.Buy/Sell` map to `EntryIR.executionType: "MARKET"` in the current importer — Q0.8.20's fuller "recognize market/limit/stop/stop-limit where representable" requirement is PARTIALLY implemented: the underlying `OrderTypeIR` distinction exists in Q0.7 and `MQL_GOLDEN_FIXTURES.limitOrder`/`stopOrder` prove the semantic ANALYZER recognizes `OP_BUYLIMIT`/`OP_BUYSTOP` order-command constants as distinct order calls, but the IR GENERATOR does not yet thread that distinction through to `EntryIR.executionType` — every entry currently generates as `MARKET`. This is a documented, honest limitation, not a silent misrepresentation: no fixture claims a LIMIT/STOP entry actually executes as one in the generated IR today.

`timing: "INTRABAR"` (rather than Q0.7's other four `EntryTiming` values) reflects that MQL order calls execute at the instant the surrounding code runs — there is no MQL equivalent of "wait for the next bar's open" built into the order call itself; G01's own real behavior (fires the moment live bid/ask crosses a computed level, checked every tick) is the clearest real-world confirmation of this choice.

## SL/TP: presence detected, formula honestly left unresolved (Q0.8.24)

A literal `0`/`0.0` SL or TP argument means "not set for this leg" (MQL's own convention) — `isMeaningfulPriceExpr()` in `ir-generator.ts` treats it as absent, not "a stop-loss of exactly zero" (a real bug this sprint's failure-catalog testing caught, `docs/Q0.8_MQL4_MQL5_PARITY.md`). When BOTH SL and TP are meaningfully present, `exits: [{kind:"STOP_LOSS"}, {kind:"TAKE_PROFIT"}]` are added structurally, but `risk.stopLoss`/`risk.takeProfit` are left `undefined` — the ACTUAL price values almost always come from expressions like `"sl"`/`"tp"` (local variables computed by unresolved cross-file functions in every fixture this sprint tested against), so fabricating a `StopLossRule`/`TakeProfitRule` shape from a variable NAME would be a guess, not a translation. A BLOCKING `UnsupportedSemantic` records this explicitly.

## Position sizing (Q0.8.40) — approximated, never silently guessed

An input whose name matches `/risk.*percent/i` (case-insensitive) triggers a `PositionSizingMethod { method: "percent-equity-risk", percent: <literal default> }` — but this is recorded as an `ApproximationRecord` (`original`/`replacement`/`difference`/`impact` all populated), never presented as a verified fact. Without such an input, sizing defaults to `{ method: "fixed-quantity", quantity: 1 }` — the conservative, no-information default, never an invented percentage (`test/mql-failure-catalog.test.ts` item 23).

## Position management and account mode (Q0.8.22)

`positionManagement.accountingMode` is always set to `"NETTING"` with an accompanying WARNING-level `UnsupportedSemantic` ("assumed... never verified against the actual account") — account mode is genuinely account-LEVEL broker configuration, invisible to EA source code, so no amount of static analysis can determine it with certainty; the importer picks the common default and says so, rather than either refusing to produce an IR at all or silently asserting certainty.

## Sessions, timezone (Q0.8.29/30)

`TimeCurrent()`/`TimeToStruct()` usage (broker/server time) sets `strategyTimezone: "UNSPECIFIED_BROKER_SERVER_TIME"` with a WARNING (server time is not a fixed IANA zone — must be confirmed per-deployment). `TimeLocal()` usage sets `strategyTimezone: "LOCAL_MACHINE_TIME_UNSAFE"` with a BLOCKING diagnostic (results are not reproducible across machines). Neither is ever silently mapped to `"UTC"`. A custom multi-named-session ENUM classifier (G01's real pattern: `SESSION_ALL`/`SESSION_ASIA`/`SESSION_LONDON`/etc., driven by input-configurable hour boundaries) is NOT force-fit into Q0.2's `SessionHoursRule` (a simple allowed-window list) — `session` is left `undefined` with a WARNING explaining why, rather than approximating away the real structure.

## What Q0.8 does NOT do

No LIMIT/STOP/STOP_LIMIT distinction threaded into `EntryIR.executionType` yet (detected by the semantic analyzer, not yet reflected in the generated IR — see above). No margin/leverage/commission modeling (Q0.5/Q0.6's execution engine remains the only place that logic lives, and this importer never wires an imported IR into it). No trailing-stop/breakeven CLASSIFICATION beyond recording `OrderModify`/`PositionModify` calls with `classification: "UNKNOWN"` (Q0.8.25's explicit "never assume every modification is trailing").
