# Q1.5.6/7 — D1/D2/D3 Fidelity Parity for Q1.5 Capabilities

## Scope

Verifies pyramiding admission (Q1.5.4) and `SIGNAL_EXIT` (Q1.5.3) behave identically between Q0.5's D1 engine (`simulation-engine.ts`) and Q0.6's D2/D3 engine (`multi-fidelity-engine.ts`), which duplicates the outer control-flow shape by Q0.6's own established, documented design (`simulation-engine.ts` is frozen and never made pluggable — see `docs/Q0.6_D2_D3_EXECUTION.md`'s Known Limitations).

## What was duplicated, and why identically

Both `entryCountByPosition` tracking (open=1, increase=+1, close=removed) and the new Step 1c (`SIGNAL_EXIT` evaluation, placed after protective-exit resolution and before entry-signal generation) were implemented as parallel, hand-mirrored edits in `multi-fidelity-engine.ts`, matching every existing Q0.6 pattern in that file (e.g. Q0.11's own order-type mirroring, explicitly commented at the D2/D3 entry-order-creation site). The `RiskEvaluationInput` split (management vs. a separate entry evaluation) was mirrored the same way.

## Test methodology

`test/q15-fidelity-parity.test.ts` fixtures use a real (not stubbed-out) `BarDetailProvider` — `createStaticBarDetailProvider([], "M15", ...)`, deliberately empty — combined with `missingDetailPolicy: "FALLBACK_TO_D1"`. This exercises the genuine `multi-fidelity-engine.ts` code path (`runFidelityAwareSimulation`, not the `D1_OHLC` delegation shortcut) while resolving every parent bar at parent-bar granularity — honestly tracked in the result's `FidelityQuality`, never silently assumed. This proves the Q1.5 duplication into `multi-fidelity-engine.ts` was done correctly, without requiring genuine intrabar data these fixtures don't need (the new conditions are evaluated at parent-bar closes only, exactly like entry conditions already are).

## Results

| Scenario | D1 | D2 (fallback) | Match |
|---|---|---|---|
| `maxEntries=2`, cap reached, `SIGNAL_EXIT` close | 2-fill trade, entry/exit price | identical | ✓ |
| `SIGNAL_EXIT` long close | 1 trade, entry/exit price | identical | ✓ |
| `SIGNAL_EXIT` short close | 1 trade, entry/exit price | identical | ✓ |
| `allowPyramiding=false` | quantity=1, capped | identical | ✓ |

## Documented, pre-existing fidelity differences (unaffected by Q1.5)

Protective SL/TP (Step 1b) resolves at intrabar (child-bar) granularity in D2/D3 vs. parent-OHLC in D1 — a real, already-documented Q0.6 difference, unchanged. `SIGNAL_EXIT`/entry-signal generation is deliberately **parent-bar-only** in both engines (matching entries' own established granularity — a condition over the strategy's own timeframe/indicators, not an intrabar price-level trigger), so this difference does not apply to the new Q1.5 capabilities.

## Remaining gaps

- No genuine (non-empty) `BarDetailProvider` scenario tested for the new capabilities — only the `FALLBACK_TO_D1` path. A true D2/D3 intrabar scenario involving a same-child-bar entry+`SIGNAL_EXIT` interaction (analogous to the existing Fixture-A same-bar-entry+protective-exit golden test) was not built this sprint.
- D3_M1 specifically was not separately exercised (D2_LOWER_TIMEFRAME only) — the two share the identical `runFidelityAwareSimulation` code path, so this is a coverage gap, not a known behavioral difference.
