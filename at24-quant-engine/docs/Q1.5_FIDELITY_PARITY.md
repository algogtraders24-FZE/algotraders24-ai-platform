# Q1.5.6/7 — D1/D2/D3 Fidelity Parity for Q1.5 Capabilities

## Scope

Verifies pyramiding admission (Q1.5.4) and `SIGNAL_EXIT` (Q1.5.3) behave identically between Q0.5's D1 engine (`simulation-engine.ts`) and Q0.6's D2/D3 engine (`multi-fidelity-engine.ts`), which duplicates the outer control-flow shape by Q0.6's own established, documented design (`simulation-engine.ts` is frozen and never made pluggable — see `docs/Q0.6_D2_D3_EXECUTION.md`'s Known Limitations).

## What was duplicated, and why identically

Both `entryCountByPosition` tracking (open=1, increase=+1, close=removed) and the new Step 1c (`SIGNAL_EXIT` evaluation, placed after protective-exit resolution and before entry-signal generation) were implemented as parallel, hand-mirrored edits in `multi-fidelity-engine.ts`, matching every existing Q0.6 pattern in that file (e.g. Q0.11's own order-type mirroring, explicitly commented at the D2/D3 entry-order-creation site). The `RiskEvaluationInput` split (management vs. a separate entry evaluation) was mirrored the same way.

## Test methodology

`test/q15-fidelity-parity.test.ts` fixtures use a real (not stubbed-out) `BarDetailProvider` — `createStaticBarDetailProvider([], "M15", ...)`, deliberately empty — combined with `missingDetailPolicy: "FALLBACK_TO_D1"`. This exercises the genuine `multi-fidelity-engine.ts` code path (`runFidelityAwareSimulation`, not the `D1_OHLC` delegation shortcut) while resolving every parent bar at parent-bar granularity — honestly tracked in the result's `FidelityQuality`, never silently assumed. This proves the Q1.5 duplication into `multi-fidelity-engine.ts` was done correctly, without requiring genuine intrabar data these fixtures don't need (the new conditions are evaluated at parent-bar closes only, exactly like entry conditions already are).

## Documented, pre-existing fidelity differences (unaffected by Q1.5)

Protective SL/TP (Step 1b) resolves at intrabar (child-bar) granularity in D2/D3 vs. parent-OHLC in D1 — a real, already-documented Q0.6 difference, unchanged. `SIGNAL_EXIT`/entry-signal generation is deliberately **parent-bar-only** in both engines (matching entries' own established granularity — a condition over the strategy's own timeframe/indicators, not an intrabar price-level trigger), so this difference does not apply to the new Q1.5 capabilities.

## Verification Closure update — genuine, non-empty D2/D3 intrabar validation

The section above (Q1.5 initial implementation) only proved the `FALLBACK_TO_D1` machinery — real, but not sufficient on its own to claim the new capabilities were exercised through genuine intrabar resolution. `test/q15-intrabar-fidelity.test.ts` closes that gap with a real, non-empty `BarDetailProvider` (`createStaticBarDetailProvider`, H1 parent / M15 child, mirroring `test/fixtures/fidelity-fixtures.ts`'s own established Fixture-A pattern), exercised through **both** `D2_LOWER_TIMEFRAME` and `D3_M1` (the two share the identical `runFidelityAwareSimulation` code path — proven directly, not assumed).

**Newly proven, this sprint:**

| Claim | Evidence |
|---|---|
| Fills resolve at the REAL child bar's own open, not the parent's open, not `FALLBACK_TO_D1` | entry fills at 105 and 110 (child opens) vs. 101 (the parent's own open) — direct price assertion |
| D2 and D3 produce identical results for this fixture | trade-level equality assertion across both fidelities |
| `maxEntries` is enforced through the real intrabar fill path | exactly 2 orders admitted despite the cap-reached signal recurring; a 3rd, unrelated order only appears after a genuine flat-reset (proving the cap AND the reset both hold under real intrabar fills) |
| `SIGNAL_EXIT` is genuinely evaluated through the D2/D3 path | the position built from real intrabar fills correctly closes |
| No look-ahead from the lower-timeframe provider | appending a later parent bar's real (and deliberately extreme) child data to the SAME provider array never changes the earlier parents' already-computed trades — plus a direct `FidelityQuality` check on which parents had real vs. fallback coverage |

**What legitimately differs, D1 vs. D2 (never claimed as parity):** entry fill prices — D1 fills at the parent's own open (101 for both fills here); D2/D3 fill at the more precise child-bar open (105, 110) when real data exists. This is the CORRECT, expected fidelity behavior (D2/D3 exists specifically to be more precise than D1's whole-bar OHLC), asserted explicitly and directly (`assert.notEqual`) rather than glossed over. What DOES stay equal: trade count, fill quantity, and the exit outcome, since `SIGNAL_EXIT`/entry-decision generation remain deliberately parent-bar-only in both engines (unchanged from the original Q1.5 implementation, restated above) — the new fixture does not, and was never intended to, prove intrabar `SIGNAL_EXIT` resolution, because no such capability was built.
