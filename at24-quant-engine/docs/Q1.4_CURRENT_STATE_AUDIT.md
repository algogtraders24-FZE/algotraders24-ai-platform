## Duplicated-logic check (§6 of Q1.4)

Grepped for every place a `SimulationOrder`/`Position`/`OrderModificationIntent` fill/trigger/cancel decision is made:

- **Fill/trigger logic**: exists in exactly ONE place — `runtime/simulation/bar-fill-model.ts`'s four resolvers (`resolveMarketFill`/`resolveLimitFill`/`resolveStopFill`/`resolveStopLimitFill`). Both `simulation-engine.ts` (D1) and `multi-fidelity-engine.ts` (D2/D3, via `intrabar-fill.ts`) call these SAME functions — never a second implementation.
- **Cancellation/modification logic**: exists in exactly ONE place — `domain/simulation/order-modification.ts`'s `validateOrderModification` + `runtime/simulation/order-modification.ts`'s `applyOrderModification`. Both the Q0.12 declarative schedule (Step 0.5) and Q1.3's policy evaluator (Step 0.4) call these SAME functions.
- **Expiration logic**: exactly one evaluator, `order-engine.ts`'s `isOrderExpired()`, called identically from both D1 and D2/D3.
- **Verdict: no duplication defect found.** No smallest-safe-correction was required — Q1.4 makes zero changes to any of these files.

## Eligibility bypass risk (§4)

`git grep`-level check confirms `runtime/reduction/ir-to-spec-reducer.ts` is the only file constructing a `StrategySpec` literal anywhere in `src/`. `compileStrategy()` (`compilation.ts`) always calls `reduceStrategyIRToSpec`, which always calls `checkReductionEligibility` first and returns no `strategySpec` at all when ineligible. **No bypass exists for the IR→Spec path.**

One nuance, honestly documented rather than glossed over: `runSimulation()` (Q0.5's raw entry point) accepts a `StrategySpec` DIRECTLY inside `SimulationConfig` — nothing prevents a caller from hand-authoring a `StrategySpec` (never having gone through MQL import at all) and running it. This is **by design, not a bypass**: `checkReductionEligibility` exists specifically to certify a TRANSLATION's fidelity; a hand-authored (or AI-proposed, per ADR-004) `StrategySpec` never claimed to be a translation of anything, so there is no translation fidelity to certify — `validateStrategySpec()` (structural validity) is the correct and complete gate for that case. This distinction is proven directly in `test/q14-negative-corpus.test.ts`'s item 25.

## Two real, verified (not newly introduced) behaviors surfaced by this audit's own corpus testing

1. **`OrderSelect()` (unlike bare `OrderType()`) is a genuine selecting/counting call** and correctly trips Q0.10's conservative pyramiding/reversal heuristic, blocking the whole strategy — this is REAL, EXISTING, CORRECT behavior (verified via `test/q14-end-to-end-pipeline.test.ts`'s `mql4-07` fixture), not a Q1.4 regression. It confirms the Q0.13 `MANAGEMENT_ACCESSOR_FUNCTIONS` fix (which added `OrderType`, deliberately NOT `OrderSelect`) was correctly scoped.
2. **A declared STOP_LOSS/TAKE_PROFIT exit whose price cannot be resolved BLOCKS the whole strategy**, not merely a warning — `ir-generator.ts` marks unresolved SL/TP `BLOCKING`, and `checkReductionEligibility` refuses any exit declaring `STOP_LOSS`/`TAKE_PROFIT` without a resolved `risk.stopLoss`/`risk.takeProfit`. Verified via `test/q14-end-to-end-pipeline.test.ts`'s `mql5-23` fixture. This is the correct, conservative behavior ("nothing would actually be simulated" is refused outright) — not a defect.

Neither finding required a code change; both are documented here as real, positive confirmations that the eligibility boundary is working as designed.
