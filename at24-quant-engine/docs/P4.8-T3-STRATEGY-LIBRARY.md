# P4.8-T3 — Strategy Library

## Tier 3.1 — Contract (locked, no implementation)

**Locked shapes**: `StrategyLibraryItem` (list) and `StrategyLibraryDetail` (detail), a presentation-level union of registry `StrategyDefinition` (global, code-defined) and persisted `Strategy` rows (P4.8-T2.2, user-owned) — never forcing either into the other's persistence shape. No best-metric field (deliberately excluded — `runCount`/`lastRunAt` only, objective and cheap; a single "best" number was judged more semantic baggage than value). Raw `StrategySpec`/`StrategyVersionRecord` never crosses the wire — detail carries the same `AlgoTestCompiledStrategyView` every run detail already uses. `artifactVerified` reflects server-side integrity verification only, never implies the client received the artifact or that a rerun action exists.

Best-metric aggregation, the one open architectural question from the T3 audit, was locked to **service-layer computation over a bounded/appropriate run set, never `$queryRaw`** — then the metric itself was dropped from T3 entirely rather than defined, per the above.

## Tier 3.2 — Prisma/service (this tier)

**Status:** Implemented, 9/9 dedicated tests passing, full regression green (108/108 across all algo-test validators, 1240/1240 engine). No schema migration, no changes to the existing `GET /strategies` route, no changes to Run History's wire contract, no raw artifact over the wire, no best-metric aggregation — every T3.1 boundary held.

### What changed

**`frontend/types/algo-test.ts`** — `StrategyLibraryItem`, `StrategyLibraryDetail`, `AlgoTestStrategyOrigin` added, exactly per the T3.1 lock with one disclosed refinement (below).

**`frontend/services/algo-test/algo-test.service.ts`** — two new methods:

- **`listStrategyLibrary(userId)`** — registry entries (via the existing, unmodified `listAvailableStrategies()`) followed by up to 50 of the user's own persisted Strategies, newest first. Exactly **two** `groupBy` queries total for run-count/last-run aggregation, per the locked "two groupBy queries, no N+1" requirement:
  - `algoTestRun.groupBy({ by: ["strategyId"], where: { userId, strategyId: { in: registryIds } }, ... })` for registry runs
  - `algoTestRun.groupBy({ by: ["strategyRefId"], where: { userId, strategyRefId: { not: null } }, ... })` for AI runs — aggregates **all** of the user's AI runs, not narrowed to the returned 50 Strategies, per your explicit "don't introduce extra query complexity merely to optimize this now" clarification.

  Neither query touches `metrics`/`trades`/`equityCurve` — only indexed/lightweight columns.

- **`getStrategyLibraryDetail(userId, strategyId)`** — tries the registry first (in-memory, no ambiguity risk — every AI `strategyId` is `ai-`-prefixed, no registry entry is), falls back to a user-owned `Strategy` row. For an AI strategy, calls the existing `getStrategyArtifact()` to obtain the real, integrity-verified spec and projects it through the existing `toCompiledStrategyView()` — the identical function every run detail already uses, never a second projection path.

### The one disclosed refinement to the locked T3.1 type

`StrategyLibraryDetail.compiledStrategy` is **optional**, not required as originally written. Reason: `artifactVerified: boolean` was locked as a genuinely meaningful field, which means `false` must be a real, reachable state — a corrupted/tampered AI artifact (exactly the case `getStrategyArtifact()` already throws loudly for at its own layer). When that happens, there is no real spec to project into a `compiledStrategy` view. `getStrategyLibraryDetail()` catches that thrown error and turns it into an honest `{ artifactVerified: false }` for **display purposes only** — `getStrategyArtifact()` itself is unchanged and still throws loudly for any caller (e.g. a future rerun action) that actually needs a trustworthy artifact to proceed. Every other identity/display field (`name`, `createdAt`, `runCount`, `lastRunAt`) stays present and honest even when the artifact can't be trusted.

### Tests (`frontend/scripts/validate-algo-test-strategy-library.ts`, 9 tests, offline)

1. Every available registry strategy always appears, with `createdAt` genuinely absent (never fabricated) and `runCount: 0` when unused.
2. A registry strategy's `runCount`/`lastRunAt` reflect real runs.
3. AI strategies appear after registry entries, ordered `createdAt desc`, with per-strategy aggregation correctly keyed by the `Strategy.id` (the FK target `AlgoTestRun.strategyRefId` actually references) — not the semantic `strategyId` string, a real distinction the test deliberately exercises with two strategies whose runs would otherwise be easy to mis-attribute.
4. Structural proof that no `StrategyLibraryItem` ever carries any metric-shaped key (`netProfit`/`profitFactor`/`winRate`/`bestMetric`/`metric`) — a regression guard against the locked "no best metric" boundary being silently reintroduced later.
5. Registry detail: real `compiledStrategy`, `artifactVerified: true`, real aggregation.
6. AI detail: `compiledStrategy` derived from the **real persisted artifact** via `getStrategyArtifact()` — asserted against the actual compiled entry-rule text, not just "truthy."
7. Non-existent `strategyId` → `null`, never fabricated, never throws.
8. Ownership isolation: a Strategy owned by a different user → `null`, never leaked.
9. A corrupted artifact → `artifactVerified: false`, `compiledStrategy` absent, identity fields still honest — never crashes, never fabricates.

## Tier 3.3 — API (thin adapter over T3.2)

**Status:** Implemented, full regression green. Bounded to a genuinely thin HTTP layer — no business logic, aggregation logic, persistence behavior, or schema changes in this tier.

### What changed

Two new routes, both mirroring the existing `GET /runs`/`GET /runs/[id]` conventions exactly (auth via `getUserOrNull()`, `ApiResponse.success`/`ApiResponse.error`, path-parsed id since `withContext`'s `RouteHandler` carries no `params`):

- **`GET /api/private/algo-test/strategy-library`** → `{ data: { strategies: StrategyLibraryItem[] } }`. Body is exactly one line: `algoTestService.listStrategyLibrary(sessionUser.profile.id)`.
- **`GET /api/private/algo-test/strategy-library/[strategyId]`** → `{ data: { strategy: StrategyLibraryDetail } }`, or `404 NOT_FOUND` when `getStrategyLibraryDetail()` returns `null` (a nonexistent strategy and one owned by another user are indistinguishable at this layer — ownership scoping and the honest-`null` convention are already `getStrategyLibraryDetail()`'s own responsibility, not reimplemented here).

Neither route adds validation, filtering, pagination, or any decision `algo-test.service.ts` doesn't already make. Both files together are ~50 lines, most of it the same auth/error boilerplate every other private route already carries.

### Verification

Typecheck and lint clean. A live dev-server smoke test confirmed both routes are correctly registered and reach the same `getUserOrNull()` auth layer as the already-proven `GET /runs` — all three returned byte-identical `500 Missing Supabase env vars` responses in this credential-less environment (no `.env.local` exists here, the same class of gap as every other credential-gated boundary this whole program has already disclosed — `ANTHROPIC_API_KEY`, `TWELVEDATA_API_KEY`, a live Postgres). This proves routing/registration correctness; it does not exercise a real authenticated 200/404 round trip, which isn't reachable in this environment. The actual response-building logic (`listStrategyLibrary`/`getStrategyLibraryDetail`) is already fully proven by T3.2's own 9 dedicated tests — this tier adds no new logic for a route-level test to exercise beyond what a live-environment smoke test would confirm.
