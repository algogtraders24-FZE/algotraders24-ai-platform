# Q0.5 Execution Model

D1/OHLC fidelity only (Q0.5.7) — no tick/bid-ask/depth/liquidity/queue awareness. Everything here is `src/runtime/simulation/bar-fill-model.ts` unless stated otherwise.

## Intrabar policy (Q0.5.8): CONSERVATIVE, the only implemented policy

Where a bar's OHLC cannot prove which of two reachable levels was hit first, this module never assumes the favorable outcome — it resolves what it CAN prove (an unambiguous gap, or one condition simply unreachable) or defers, never manufactures a fill. `OPTIMISTIC`/`LOWER_TIMEFRAME`/`TICK_REPLAY` remain reserved future policies (`docs/Q0.4_INTRABAR_ENGINE.md`), not implemented.

## Per-order-type semantics (Q0.5.9-12)

| Order type | Eligible | Execution price | Gap behavior |
|---|---|---|---|
| MARKET | first bar with timestamp strictly after `creationTimestamp` | that bar's open, spread/slippage-adjusted | no special case — a gap IS the fill price; there is nothing to be "unfavorable" relative to |
| LIMIT | any bar strictly after creation, re-evaluated every bar until filled/expired | limit price, UNLESS the bar's open already cleared it (favorable gap) — then that open | a favorable gap fills at the better open price; touching the level alone (`low == limit` for BUY) does NOT fill — strict trade-through required (adopts LEAN's `EquityFillModel` precedent, `docs/Q0.4_ADOPT_IMPROVE_AVOID_INVENT.md`) |
| STOP | any bar strictly after creation | stop price, UNLESS the bar's open already gapped through it — then that (worse) open | an unfavorable gap NEVER fills at the nominal stop price — always the realistic, worse, gapped-through open (LEAN's "unfavorable gap" check, `docs/Q0.4_BACKTEST_FAILURE_CATALOG.md` item 14) |
| STOP_LIMIT | any bar strictly after creation | see below | only an UNAMBIGUOUS gap (open simultaneously past the stop AND within the limit) fills same-bar; otherwise the stop merely triggers (`TRIGGERED` status) and the order is re-evaluated as a plain LIMIT starting the NEXT bar — never a manufactured same-bar fill (Q0.5.12's explicit mandate) |

Every function returns a `BarFillOutcome` (`{ filled, fillPrice?, triggeredOnly?, reason }`) — the `reason` string is always populated, so no fill/no-fill decision is ever silently unexplained.

## Protective exit (position-level SL/TP)

A position's own `stopLoss`/`takeProfit` fields are checked against every bar it is open for (including the bar it opened on) via `resolveProtectiveExit()`, using the identical conservative gap-aware logic as standalone STOP/LIMIT orders. **The mandatory case**: if both levels are reachable within one bar, the function resolves to the stop-loss (the worse outcome) and sets `ambiguous: true` — it never reports a clean take-profit exit in that situation. Golden scenarios for all 8 required cases (Q0.5.32) live in `test/simulation-fill-model.test.ts`.

## Spread / Latency / Slippage / Fee boundaries (Q0.5.13-16)

Each satisfies the behavioral interface Q0.2's `reality-models.ts` already reserved:

| Model | Implementations shipped | Reserved, not built |
|---|---|---|
| SpreadModel | `ZeroSpread`, `FixedSpread(value)` | Historical/Variable/BidAsk/Synthetic/SessionDependent (`docs/Q0.4_BACKTEST_ARCHITECTURE.md`) |
| LatencyModel | `ZeroLatency` | FixedLatency, DistributionLatency |
| SlippageModel | `ZeroSlippage` | Percentage/VolatilityBased/VolumeShare/LiquidityBased/MarketImpactBased/Stochastic |
| FeeModel | `ZeroFee` | PerTrade/PerUnit/Percentage/Tiered |

The default simulation configuration never silently implies a realistic spread — every model is an explicit, named choice a caller must supply to `SimulationConfig`; there is no fallback default baked into the orchestrator.

## ExecutionResult (Q0.5.17)

```ts
interface ExecutionResult {
  orderId: string;
  status: "FILLED" | "PARTIALLY_FILLED" | "REJECTED" | "NO_FILL";
  requestedQuantity: number;
  filledQuantity: number;
  requestedPrice?: number;
  fillPrice?: number;
  fees: number;
  slippage: number;
  executionTimestamp: number;
  executionModel: string;
  reason: string;
}
```

Defined in `src/domain/simulation/execution-result.ts` as the required structured shape (Q0.5.17's "no free-form-only execution result"). The orchestrator's actual fill-handling currently derives its own event/trade records directly from `BarFillOutcome` rather than constructing a separate `ExecutionResult` object per attempt — this type remains the canonical target shape for a future sprint that wants to expose per-attempt (including failed-attempt) execution telemetry as a first-class stream, not just the aggregate ledger.

## Known Limitations (documented, not silently glossed over)

1. **Stop-loss/take-profit reference price**: for a new entry, `resolveStopLossPrice`/`resolveTakeProfitPrice` (`src/runtime/simulation/rule-resolvers.ts`) use the DECISION bar's close as the reference entry price — not the eventual next-bar-open fill price (which isn't known yet at decision time). This is realistic (real order-management systems request SL/TP relative to the signal price, then the order fills at a slightly different price) but means the position's actual risk distance can differ slightly from what the `RiskSpecification`'s rule nominally requested. A future sprint could re-resolve SL/TP against the actual fill price for tighter precision; Q0.5 does not.
2. **`atr-based` position sizing has no resolved quantity formula.** `RiskSpecification.sizing`'s `atr-based` method was defined in Q0.2 with no risk-percent field to normalize against — there is no way to derive a concrete position size from `{ atrMultiple, atrPeriod }` alone without inventing an undocumented convention. `resolvePositionSize()` throws a clear, explicit error naming the supported alternatives (`fixed-quantity`, `fixed-lot`, `percent-equity-risk`) rather than guessing.
3. **No margin/buying-power/liquidation model.** An account's balance can go negative if losses exceed capital — Q0.5.21 only requires the accounting to stay internally consistent (`balance = initial + realizedPnl - fees`, verified by `test/simulation-failure-catalog.test.ts` item 8), not that overdraft is prevented. `MarginModel`/`BuyingPowerModel` remain reserved (`docs/Q0.4_BACKTEST_ARCHITECTURE.md`).
4. **`ExitRule`-based exits are not evaluated.** `StrategySpec.exitRules` (Q0) are never consulted by the Q0.5 orchestrator — only Q0.3's `evaluateRisk()` (breakeven/trailing/partial-close/max-holding-period) drives position management. Wiring condition-based exits is out of scope for this sprint (Q0.5.29 explicitly forbids inventing new recalculation semantics beyond what was already frozen).
