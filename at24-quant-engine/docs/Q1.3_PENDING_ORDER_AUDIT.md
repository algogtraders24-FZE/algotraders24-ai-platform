# Q1.3 — Pending Order Audit

Performed before any implementation, per Q1.3's own mandatory "audit first" instruction. **Headline finding: the overwhelming majority of Q1.3's required scope already exists**, built across Q0.5 (frozen simulation core), Q0.11 (order types), and Q0.12 (modification/cancellation/expiration). This audit exists to prove that claim file-by-file, not merely assert it, and to identify the small number of genuine gaps this sprint actually needs to close.

## 1. Universal Order IR

`domain/strategy-ir/order-ir.ts`'s `OrderTypeIR = "MARKET" | "LIMIT" | "STOP" | "STOP_LIMIT"` (Q0.7) is the canonical strategy-authored order-type vocabulary. Combined with `EntryIR.direction: "BUY" | "SELL" | "FLAT"` (Q0.7) and `EntryIR.limitPrice`/`stopPrice: PriceReference` (Q0.11), this is a full, unambiguous representation of BUY_LIMIT/SELL_LIMIT/BUY_STOP/SELL_STOP as an **orthogonal pair** (`executionType` × `direction`) rather than a single four-way enum. This is a genuine architectural choice, not a gap: a cross-product enum would duplicate information already carried by two independent, already-validated fields. **No change made or needed.**

## 2. `OrderTypeIR`

Already covers all four required types plus `STOP_LIMIT` (a superset — MT4/MT5's real fifth pending-order concept, kept since removing it would be a regression). `MARKET` is unchanged throughout this audit — Q1.3's "existing market-order behavior must remain unchanged" requirement is trivially satisfied since nothing in `resolveMarketFill` is touched anywhere in this sprint.

## 4. Fill resolvers (`runtime/simulation/bar-fill-model.ts`, 197 lines, Q0.5-frozen + Q0.11 usage)

| Function | Semantics | Matches Q1.3 §4/§6 literally? |
|---|---|---|
| `resolveLimitFill` | Strict trade-through required (`low < limit` / `high > limit`), NOT touch (`<=`/`>=`) — a favorable gap (open already past the limit) fills at that open. | **Deliberately stricter than Q1.3's literal wording** (`price <= limit_price`) — see §4 "Compatibility risk" below. |
| `resolveStopFill` | Touch-triggers (`high >= stop` / `low <= stop`) — an unfavorable gap fills at the worse open, never at the stop level itself. | **Matches Q1.3's literal wording exactly.** |
| `resolveStopLimitFill` | Two-stage: unambiguous same-bar gap fills immediately; an intrabar-only stop trigger becomes `triggeredOnly` (no manufactured fill), re-evaluated as a plain LIMIT starting the NEXT bar. | This IS the project's existing canonical same-bar ambiguity policy Q1.3 §6 asks for. |
| `resolveProtectiveExit` | SL/TP on an OPEN POSITION (not a pending order) — both-reachable-in-one-bar resolves to the stop-loss, flagged `ambiguous: true`, never the favorable outcome. | Out of Q1.3's scope (position management, not pending orders) — audited for completeness only. |

### Compatibility risk: LIMIT touch vs. strict trade-through

Q1.3 §4/§6 states LIMIT semantics as `price <= limit_price` (BUY) / `price >= limit_price` (SELL) — read literally, a bar merely TOUCHING the limit (`low == limit`) should fill. The existing, frozen, extensively-tested `resolveLimitFill` (Q0.5.10, unchanged since) requires **strict** trade-through (`low < limit`), a deliberate design decision citing LEAN's `EquityFillModel` precedent and Q0.4's own "never silently favorable" research finding (Pine's lenient touch-fill-by-default was explicitly rejected as AT24's default — `docs/Q0.4_ADOPT_IMPROVE_AVOID_INVENT.md`, `docs/Q0.5_SIMULATION_ARCHITECTURE.md`, rule 39 of the master blueprint). STOP orders already use inclusive touch-semantics (`high >= stop`), matching Q1.3's wording exactly — only LIMIT diverges, and only in the touch/strict-trade-through boundary case (`low == limit` exactly).

**Decision: preserve the existing strict-trade-through policy, do not change it.** Rationale: (a) it is Q0.5's frozen execution core — rule 24 ("a frozen, tested execution core is never modified to accommodate a new capability") applies directly; (b) changing it would silently make backtests MORE favorable to the trader in the exact boundary case Q0.4's research specifically studied and rejected; (c) it is exhaustively tested (`test/simulation-fill-model.test.ts`, `test/q11-golden-fixtures.test.ts`, `test/q11-gap-fixtures.test.ts` — dozens of assertions depend on strict trade-through); (d) Q1.3 §16's own regression requirement ("No Q1.3 implementation is acceptable if it breaks existing execution semantics") would itself be violated by changing it. This divergence is documented explicitly in `docs/Q1.3_PENDING_ORDER_SEMANTICS.md` rather than silently kept — never hidden, per this whole codebase's own standing rule.

## 5. Gap handling

Already implemented and tested exactly per Q1.3 §5's own worked example (BUY_LIMIT=100, price gaps 105→98 → triggers, fills at the realistic gap price). See `resolveLimitFill`'s "favorable gap" branch and `test/q11-gap-fixtures.test.ts`'s `LIMIT_GAP_THROUGH`/`GAP-DOWN + LIMIT BUY` cases. STOP gap-through (unfavorable, fills at the worse open) is likewise already implemented and tested (`STOP_GAP_THROUGH`, `GAP-UP + STOP BUY`).

## 6. Bar-based (OHLC) simulation

`simulation-engine.ts`'s Step 1 loop calls the resolvers above once per bar per pending order, using ONLY that bar's own OHLC — no future bar is ever consulted (`state.pendingOrders` iteration + `order.creationTimestamp >= bar.timestamp` same-bar guard, Q0.5.30). Trigger conditions (`Low <= limit` for BUY_LIMIT etc.) match Q1.3 §6 exactly for the inclusive STOP case and (with the documented strict-vs-touch divergence above) for LIMIT. The canonical same-bar ambiguity policy Q1.3 §6 requires already exists (`resolveStopLimitFill`'s `triggeredOnly` branch) — **not a gap**.

## 7. Tick-level simulation — genuine limitation, honestly flagged

`domain/fidelity/simulation-fidelity.ts` defines exactly three IMPLEMENTED fidelity tiers: `D1_OHLC`, `D2_LOWER_TIMEFRAME`, `D3_M1`. All three are **bar-based** (D2/D3 walk finer-granularity CHILD BARS via `bar-magnifier.ts`'s `reconstructIntrabarSequence`/`intrabar-fill.ts`'s `resolveIntrabarOrderFill` — reusing the SAME `resolveLimitFill`/`resolveStopFill`/`resolveStopLimitFill` resolvers per child bar). `D4_TICK` is explicitly declared in `ReservedSimulationFidelity` — **reserved, not implemented, no runtime code produces or accepts it** (documented since Q0.6, rule stated verbatim in `simulation-fidelity.ts`'s own doc comment and the master blueprint's "Future Architecture" section). **This package has no genuine tick-level (sequential, sub-minute, non-OHLC) simulation capability at all.** Per Q1.3 §7's own "if the existing architecture does not have X, flag as a limitation rather than inventing behavior" instruction (echoing §10's identical instruction for expiration), this is documented as a known, permanent-for-now limitation in `Q1.3_PENDING_ORDER_SEMANTICS.md` — no tick engine is built in this sprint (matches the explicit non-goal list: "new backtesting engine").

## 8. Pending order state machine

`runtime/simulation/order-engine.ts`'s `VALID_TRANSITIONS` (Q0.4-frozen) already implements exactly the required states plus more granular sub-states: `NEW → SUBMITTED → ACCEPTED → {TRIGGERED, PARTIALLY_FILLED, FILLED, CANCELLED, EXPIRED}`. `FILLED`/`CANCELLED`/`EXPIRED`/`REJECTED` are terminal (zero outgoing transitions) — `FILLED → PENDING`, `CANCELLED → FILLED`, `EXPIRED → FILLED` all throw deterministically via `transitionOrder()`'s own guard. Q1.3's simpler `PENDING` label maps to the union `{ACCEPTED, TRIGGERED, PARTIALLY_FILLED}` (any non-terminal status) — a strict superset, never a gap. **No change made or needed.**

## 9. Cancellation

Fully implemented in Q0.12: `OrderModificationIntent{modificationType:"CANCEL"}` → `validateOrderModification` (rejects a terminal order) → `applyOrderModification` → `transitionOrder(order,"CANCELLED")` → removed from `state.pendingOrders`. The exact scenario Q1.3 §9 requires ("create → cancel → price reaches trigger → CANCELLED, no fill, no position") is already proven by `test/q12-race-fixtures.test.ts`'s `CANCEL_BEFORE_TRIGGER` and `test/q12-golden-fixtures.test.ts`'s `LIMIT_CANCEL`/`STOP_CANCEL`/`STOP_LIMIT_CANCEL`. A cancelled order is removed from `pendingOrders` the same bar it's cancelled, structurally guaranteeing it can never generate a `POSITION_OPENED` or a trade-ledger entry.

## 10. Expiration

Fully implemented in Q0.12: `OrderExpirationPolicy` (`GTC`/`DAY`/`BAR`/`TIMESTAMP`) + `isOrderExpired()`, checked at the START of Step 1 before fill resolution in both D1 and D2/D3. The exact scenario Q1.3 §10 requires is already proven by `test/q12-golden-fixtures.test.ts`'s `EXPIRATION` fixture. Per Q1.3 §10's own instruction ("do NOT invent a large scheduling system... implement only the minimum safe contract"), no scheduling infrastructure beyond this was ever built, matching the instruction precisely — **not a gap, already the minimum correct contract.**

## 11. Duplicate/repeated trigger protection

Structurally guaranteed, not merely tested: a filled/cancelled/expired order is removed from `state.pendingOrders` (a `Map`) the SAME bar the terminal transition occurs — there is no code path that re-evaluates an order once it leaves that map, so a "second fill" is not merely prevented by a check, it is **structurally impossible** (the resolver is simply never called again for that `orderId`). `MULTIPLE_PENDING_ORDERS` (`test/q11-intrabar-fixtures.test.ts`, Q0.11.24) proves the adjacent guarantee (a still-true entry condition never creates a SECOND pending order while one remains active — `hasPendingOrder`, `decision-builder.ts`). **Gap identified**: no existing test explicitly proves "price crosses the SAME level on multiple bars AFTER an order already filled produces exactly one fill/one position/one trade" at the full-simulation level — added in this sprint (`test/q1.3-pending-order-management.test.ts`).

## 12. Position integration

`simulation-engine.ts`'s Step 1 fill-handling branch (unchanged, Q0.5) calls `openPosition()`/`increasePosition()`/`reducePosition()` (`position-engine.ts`) directly upon any order's fill — MARKET, LIMIT, STOP, and STOP_LIMIT orders all funnel through the exact same code path, already proven by every Q0.11 golden fixture. **No separate pending-order position path exists; none is created by this sprint.**

## 13. Trade ledger

`trade-ledger.ts`'s `buildTrade()` (unchanged, Q0.5+Q0.10) already records `tradeId`/`position`/`exitPrice`/`quantity`/`grossPnl`/`fees`/`fillModel`/`spreadModel`/`slippageModel`/`feeModel` per trade, sourced from the `Position` object a pending-order fill created via `openPosition()`. R-multiple computation (`Position.initialStopLoss`, Q0.10) is unaffected — this sprint touches no ledger code.

## 14. Determinism

Already proven for order types generally (`test/q11-determinism-provenance.test.ts`) and for modification/cancellation/expiration specifically (`test/q12-determinism-provenance.test.ts`) — 3-run byte-identical `resultHash`.
