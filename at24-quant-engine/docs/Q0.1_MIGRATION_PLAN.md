# Q0.1 Migration Plan

Consolidates the controlled migration policy (Q0.1.8) referenced by [Q0.1_CANONICALIZATION_DECISION.md](Q0.1_CANONICALIZATION_DECISION.md) §6/§8. Nothing in this document is executed by Q0.1 — it is the checklist a future sprint follows before moving any OLD component into `at24-quant-engine/`.

## The pipeline (mandatory for every migration candidate, no exceptions)

```
Old Component
    |
    v
Compatibility Assessment   <- does the OLD concept have a home in NEW's current contracts?
    |
    v
Specification Mapping      <- explicit field-by-field mapping, written down, reviewed
    |
    v
Test                       <- semantic-equivalence test comparing OLD's and NEW's behavior
    |                          on the same input, before trusting the migrated form
    v
Migration                  <- the actual port (new TypeScript code, not a copy of Python)
    |
    v
Validation                 <- re-run in NEW, confirm output matches the Test step's baseline
    |
    v
Old Component Retired/Archived   <- only after Validation passes
```

Every migration must preserve: semantics, determinism, provenance, version information, and test coverage. **If an old concept cannot be represented safely by `StrategySpec`/`RiskSpecification`/etc. as they exist today, it is marked `INCOMPATIBLE / REQUIRES DESIGN` and left alone — it is never forced into an ill-fitting shape.**

## Candidate-by-candidate plan

### 1. `cross_above`/`cross_below` operators
- **Compatibility assessment**: NEW's `ComparisonOperator` union lacks these; OLD's `interpreter.py` implements them as prev-bar-aware comparisons.
- **Mapping**: extend `ComparisonOperator` to `">" | ">=" | "<" | "<=" | "==" | "!=" | "cross_above" | "cross_below"`, and extend `MarketState`/the evaluator to have access to the previous bar's resolved indicator value (currently the evaluator only sees the current `indicatorValues` map).
- **Test**: unit tests reproducing OLD's crossover semantics on a small synthetic bar sequence.
- **Status**: `CANDIDATE_FOR_MIGRATION`, cheapest and most self-contained — recommended first Q1 task.

### 2. Indicator math (`spec_engine/indicators.py`)
- **Compatibility assessment**: `IndicatorReference`/`indicatorKey()` already provide the addressable plug-in point; no computation exists yet on the NEW side.
- **Mapping**: one TypeScript module per indicator family, keyed identically to `indicatorKey()`'s output format, producing values to inject into `MarketState.indicatorValues`.
- **Test**: for each ported indicator, compare NEW's output against OLD's `indicators.py` output on the same historical bars (from `quant_engine/market.db`, read-only) within a numerical tolerance.
- **Status**: `CANDIDATE_FOR_MIGRATION`, medium effort, no dependency on other items in this list.

### 3. `RiskSpecification` extension (breakeven / ATR-trailing / partial-close / daily-loss-halt / session-hours)
- **Compatibility assessment**: `INCOMPATIBLE / REQUIRES DESIGN` as of today — no field in `RiskSpecification`, `StopLossRule`, or `TakeProfitRule` can represent these.
- **Mapping**: needs a design pass (not a mechanical port) — OLD's `RiskConfig` is an imperative engine-config object, NEW's `RiskSpecification` is a declarative contract; the shapes don't correspond 1:1.
- **Test**: N/A until design is settled.
- **Status**: `REQUIRES DESIGN` before it can even become a migration candidate. Blocks item 5 below.

### 4. Walk-forward robustness scoring (`spec_engine/robustness.py`)
- **Compatibility assessment**: `BacktestResult.metrics` (`BacktestMetrics`) has no walk-forward fields today.
- **Mapping**: extend `BacktestMetrics` with `walkForward?: { validFolds, pctFoldsProfitable, avgFoldProfitFactor, minFoldProfitFactor, robustnessScore }` (naming TBD at design time), computed the same way OLD does (composite score gated on `>=3` valid folds).
- **Test**: reproduce OLD's exact `strategy_library.db` scores for a handful of rows once a backtest engine exists to run against.
- **Status**: `CANDIDATE_FOR_MIGRATION`, blocked on a backtest engine existing at all (item 6).

### 5. 1,764-strategy library sample
- **Compatibility assessment**: entry conditions map cleanly; exits/risk fields partially blocked on item 3.
- **Mapping / Test / Migration / Validation**: the full 8-stage plan in [Q0.1_STRATEGY_LIBRARY_AUDIT.md](Q0.1_STRATEGY_LIBRARY_AUDIT.md).
- **Status**: `CANDIDATE_FOR_MIGRATION`, staged, explicitly blocked on items 3 and 6 for full-fidelity results (a partial migration covering entry-only logic without SL/TP fidelity is possible sooner but of limited value).

### 6. Backtest engine
- **Compatibility assessment**: NEW has only a contract (`BacktestConfig`/`BacktestResult`), no runtime, by design (Q0.7).
- **Mapping**: not a port of OLD's Python engines — a new TypeScript implementation, informed by OLD's three-tier fidelity lesson (bar-level vs. minute-replay vs. tick-level) and the concrete ~9x drawdown divergence finding between them.
- **Test**: determinism tests (already have the pattern from `at24-quant-engine`'s existing `test/determinism.test.ts`) plus fidelity-comparison tests analogous to OLD's `compare_engines.py`.
- **Status**: `CANDIDATE_FOR_MIGRATION` at the lessons-learned level only; this is a full future sprint, not a quick follow-on. Blocks item 5's full-fidelity validation and item 4.

### 7. LLM-parser pattern (`spec_engine/llm_parser.py`)
- **Compatibility assessment**: matches ADR-004's "AI proposes, deterministic runtime gates" boundary exactly; NEW has `validateStrategySpec()` as the gate already.
- **Mapping**: a future AI Strategy Agent would call an LLM with a forced tool-call against `StrategySpec`'s shape, then loop `validateStrategySpec()` → repair-prompt → retry, mirroring OLD's `MAX_REPAIR_ATTEMPTS` pattern.
- **Test**: schema-validation retry-loop unit tests (can be tested without a live API key by mocking the model response, same as OLD's own `demo_parser_check.py` approach).
- **Status**: `CANDIDATE_FOR_MIGRATION`, independent of the other items — could be built any time after `StrategySpec`'s shape is considered stable enough to target.

### 8. Code generation (MQL5 / MQL4 / Pine Script v5)
- **Compatibility assessment**: no overlapping concept in NEW at all — this is a distinct capability, not a Quant Engine architecture component.
- **Status**: out of scope for any Quant Engine migration plan; flag as a separate future capability area if ever prioritized.

## What is explicitly excluded from ever migrating

See [Q0.1_CANONICALIZATION_DECISION.md](Q0.1_CANONICALIZATION_DECISION.md) §7 — OLD's flat Spec schema shape, OLD's imperative single-position engine architecture, and `strategy_library.db`'s stored metrics as-is.
