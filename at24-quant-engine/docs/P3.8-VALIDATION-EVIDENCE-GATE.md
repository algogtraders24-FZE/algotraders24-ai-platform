# P3.8 — Validation / Evidence Gate

**Status:** Implemented, tested. Builds on P3.5–P3.7 (`docs/P3.7-GENERIC-PARAMETER-ENGINE.md`) and the reproducibility principles locked in `docs/ALGO_TESTING_PRO_ROADMAP.md`.

## 1. The question this phase answers

Not "can we put a green checkmark beside a strategy" — whether AT24 can actually prove a registered strategy is valid, executable, reproducible, and backed by trustworthy evidence, with an honest, specific reason recorded the moment it stops being any of those things. The critical rule (stated explicitly by the user, and directly motivated by P3.6's own real investigation): **a strategy must not advance past a stage merely because the previous stage technically ran.**

## 2. The lifecycle, and what backs each gate — not invented, composed from what already existed

`STRATEGY_LIFECYCLE_STAGES = [IMPORTED, PARSED, IR_VALID, EXECUTION_VALID, DATA_VALID, BACKTEST_VALID, REPRODUCIBLE, EVIDENCE_VERIFIED]` (`at24-quant-engine/src/domain/strategy-lifecycle.ts`). Investigated before writing any glue code — every gate maps onto a capability that already existed, most of it since Q0.7–Q0.9:

| Stage | Backed by | Existed since |
|---|---|---|
| IMPORTED | `importMQLSource()` produced a document/report at all (this importer never throws — genuine failures degrade to diagnostics) | Q0.8 |
| PARSED | `blockingDiagnostics(report).length === 0` (`domain/mql-importer/import-report.ts`'s own doc comment: "the ONLY condition under which the resulting StrategyIR may be execution-eligible") | Q0.8.42/45 |
| IR_VALID | `validateStrategyIRStructure(ir).valid` | Q0.7 |
| EXECUTION_VALID | `checkReductionEligibility(ir).eligible` — the gate that actually catches a placeholder/always-false condition, via `ir.provenance.unsupportedSemantics`' BLOCKING severity | Q0.7.31/Q0.9 |
| DATA_VALID | the historical-data fetch produced real bars (`run-backtest.ts`'s existing "no valid historical bars" throw) | P3.2A |
| BACKTEST_VALID | `runSimulation()` completed and returned a `SimulationResult` | Q0.5 |
| REPRODUCIBLE | **new this phase** — see section 4 | — |
| EVIDENCE_VERIFIED | DATA_VALID + BACKTEST_VALID + REPRODUCIBLE all passed, with an explicit trade-count classification — see section 5 | — |

Only REPRODUCIBLE and EVIDENCE_VERIFIED are genuinely new computation; the first six stages are existing facts, newly exposed as structured, inspectable data instead of an internal throw-or-silent decision.

For an engine-reference strategy (Golden Strategy — authored directly as TypeScript, never imported), IMPORTED/PARSED/IR_VALID/EXECUTION_VALID are `NOT_APPLICABLE`, not `PASSED` — a real, distinct outcome (`engineReferenceImportStages()`, `domain/strategy-lifecycle.ts`): these four gates exist to catch problems the import/reduction pipeline introduces, a pipeline Golden Strategy never goes through. `NOT_APPLICABLE` still carries a `detail`, same as `FAILED` — an unexplained skip is exactly what this phase exists to prevent.

## 3. The critical rule, proven with G01's own real source — twice, and the second finding corrected the first

`test/strategy-lifecycle.test.ts` runs G01's actual, frozen v0.1 production `.mq5` file (not a synthetic strawman) through `mqlImportLifecycleStages()`. The first version of this test assumed (carrying over P3.6's own investigation) that G01 would stop at EXECUTION_VALID, on the unresolved-cross-file-call problem. Running it revealed a different, equally real, and more precise finding: **G01 actually stops one stage earlier, at IR_VALID** — its `#property version "1.00"` fails `validateStrategyIRStructure`'s strict `MAJOR.MINOR.PATCH` check. `EXECUTION_VALID` is correctly marked `FAILED` with `"not evaluated — IR_VALID already failed"`, never silently defaulted to `PASSED`. This is precisely the kind of thing this phase exists to get right, not approximately right — the test was corrected to match the real, empirically-found reason, not the original assumption. (A fixed version string would still leave G01 blocked one stage later by the real unresolved-entry-condition problem P3.6 already found — both are real, independent gaps.)

A second, narrower test constructs a minimal fake `MQLImportOutput` with a deliberately BLOCKING parse-level diagnostic, confirming the ordering contract structurally: once PARSED fails, IR_VALID/EXECUTION_VALID are marked `FAILED` with an honest `"not evaluated"` reason, never silently defaulted to `PASSED`.

## 4. REPRODUCIBLE — a real, live check, not an assumption

`run-backtest.ts`'s `runBacktest()` now calls `runSimulation()` a **second time**, over the identical already-fetched `bars`/`config` (no second network call — cheap, local, sub-second). `reproducible: boolean` compares the two `resultHash`es. The roadmap (`docs/ALGO_TESTING_PRO_ROADMAP.md` section 5) already states "identical inputs → identical resultHash" as an established invariant, proven by unit tests at the engine level (Q0.5.36, P3.5's own determinism tests) — this proves it again, live, for *this specific run*, not just for the engine in the abstract. `false` here would be a genuine engine-level regression, never an expected outcome.

## 5. EVIDENCE_VERIFIED and the zero-trade distinction — the requirement named explicitly

The user's own test: *"A zero-trade result must not automatically be treated as a valid strategy result... the system needs to distinguish 'valid strategy that legitimately produced zero trades' from 'strategy never executed because its entry logic was unresolved.'"*

This is handled structurally, not by a new heuristic: a strategy whose entry logic never resolved never reaches this point at all — it already stopped at EXECUTION_VALID (section 2/3). By the time `EVIDENCE_VERIFIED` is evaluated, EXECUTION_VALID has *already* confirmed the entry logic is real, non-placeholder. So a 0-trade result reaching `EVIDENCE_VERIFIED` is always the legitimate case — and its own `detail` says so explicitly (`"0 trades - a legitimate, reproducible result (EXECUTION_VALID already confirmed real, non-placeholder entry logic; this run's own bars/window simply never satisfied it), not a fabricated or unresolved-strategy zero"`), rather than reading identically to a populated-ledger result. The distinction is visible in the evidence itself, not collapsed.

## 6. What was deliberately NOT built this phase

- **Persistence.** `lifecycle` is computed live and returned on `runAlgoTest`'s own response only — not persisted to a new `AlgoTestRun` column, not reconstructed on `getAlgoTestRun` (reopen) or `listAlgoTestRuns`. This environment has no live database connection to actually apply and verify a new Prisma migration against (every other change this session was empirically tested end-to-end; a migration here could not have been, unlike everything else) — adding one blind would be the one place this phase's own discipline (never claim untested things work) would have been violated. Recorded here as a real, disclosed deferral, not a silent gap. `types/algo-test.ts`'s own `lifecycle` field doc comment states this explicitly.
- **"Valid" vs "Proven" as a formal, separate distinction.** The user drew this distinction sharply (public Marketplace/Strategy-Library claims will need it eventually). This phase's `fullyVerified: boolean` and the `EVIDENCE_VERIFIED` stage's own `detail` (trade count, reproducibility) already carry enough information for a *future* consumer to make that judgment (e.g. "proven" might require N trades across M reproducible runs, a Marketplace-specific policy) — but this phase does not invent that policy. Doing so here would mean fabricating a trustworthiness threshold with no established basis, the opposite of this phase's own purpose.
- **Data-provider-coverage nuance beyond "did we get bars."** `DATA_VALID` today is binary (real bars vs. none) — it does not yet distinguish "this symbol/timeframe combination is genuinely unsupported" from "network hiccup." `toAlgoTestErrorCode()`'s existing `NO_HISTORICAL_DATA`/`PROVIDER_ERROR` split already carries this nuance in the error code; folding it into `DATA_VALID`'s own detail is a natural, small future refinement, not attempted here.

## 7. Evidence

**Engine** (`test/strategy-lifecycle.test.ts`, 7 tests): stage order matches the roadmap's own spec exactly; a fully-passing synthetic lifecycle reaches `EVIDENCE_VERIFIED`/`fullyVerified`; a `FAILED` stage stops `reachedStage` at the last passing stage, never further; `NOT_APPLICABLE` stages advance `reachedStage` exactly like `PASSED` (Golden Strategy reaches `EVIDENCE_VERIFIED` despite 4 `NOT_APPLICABLE` stages); `ref-ema-crossover`'s real import genuinely passes all 4 import stages (not `NOT_APPLICABLE`, not a placeholder pass); G01's real source correctly stops at `IR_VALID` with the real reason (section 3); a deliberately-constructed `BLOCKING` parse diagnostic stops the lifecycle at `PARSED` with honest `"not evaluated"` markers downstream.

**Registry** (`frontend/scripts/validate-algo-test-parameters.ts`, 25/25, +2 from P3.7's 23): every registered strategy's `importLifecycle` covers exactly the 4 stages in order with none `FAILED` (a strategy that failed its own import lifecycle could never safely be registered at all — proven, not assumed); Golden's 4 stages are `NOT_APPLICABLE`, `ref-ema-crossover`'s are `PASSED` — the two real, different `source.kind`s producing genuinely different, correct outcomes.

**Live-verification script** (`frontend/scripts/validate-algo-test-service.ts` — requires a real DB + Twelve Data connection this environment does not have; updated but **not run** here, disclosed honestly): the canonical Golden Strategy request must reach `EVIDENCE_VERIFIED`/`fullyVerified: true`, with `EVIDENCE_VERIFIED`'s own detail naming the real, live P3.3-canonical trade count (26).

## 9. Acceptance bar

| Requirement | Status |
|---|---|
| Generic validation lifecycle | **YES** — `buildLifecycleResult()`, strategy-source-agnostic |
| No Golden-Strategy-specific validation branches | **YES** — the SAME `mqlImportLifecycleStages()`/`engineReferenceImportStages()` functions serve every registered/future strategy of their respective `source.kind` |
| Every state transition has an explicit gate | **YES** — 8 named stages, each backed by a real check (section 2) |
| Fatal vs non-fatal diagnostics differentiated | **YES** — `blockingDiagnostics()` (BLOCKING only); WARNING/INFO diagnostics never fail a stage |
| Unsupported execution semantics block the appropriate gate | **YES**, proven directly with G01's real source |

| Backtest configuration part of reproducibility | **YES** — REPRODUCIBLE re-runs the identical `config`/`bars` |

| A successful strategy can reach EVIDENCE_VERIFIED | **YES** |
| A deliberately invalid/unsupported strategy stops at the correct stage | **YES**, proven with G01's real source (section 3) |
