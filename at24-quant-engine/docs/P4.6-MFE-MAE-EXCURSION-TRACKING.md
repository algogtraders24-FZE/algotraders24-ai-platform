# P4.6-T1 — MFE/MAE & Trade Excursion Analytics: Engine Contract + Tracking

**Status:** Implemented, tested (18 new tests, 3-part contract), full engine regression green (1240/1240, 1222 baseline + 18 new). Bounded to the locked Tier 1 scope: engine-level tracking only — `Position`, `SimulationTrade`, `simulation-engine.ts`. Zero frontend/API/UI changes (Tier 2). Zero execution-semantic changes: fill prices, SL/TP resolution, position sizing, and realized P&L are all byte-identical to pre-P4.6 behavior.

## 0. Why this phase, in this position, and its locked semantic contract

Preceded by a dedicated pre-implementation scoping/blast-radius audit (P4.6-0) and a fully locked semantic contract, both produced before any code was written. The locked contract, in summary:

1. **Unit: R-multiple primary.** `mfeR`/`maeR`, not a raw price/currency field. Price is engine-internal derivation state only.
2. **Entry bar included** — matching `resolveProtectiveExit`'s own established precedent ("entry happens at that bar's open and the rest of the bar's range still applies").
3. **Exit bar included, no look-ahead** — the exit bar's own full range counts; a bar after the exit must never leak backward into an already-closed trade.
4. **Timestamps stored** (`mfeTimestamp`/`maeTimestamp`) at the finest fidelity actually available (bar timestamp) — never a manufactured sub-bar precision.
5. **Trade-row, not position-level.** Each `SimulationTrade` row (including a partial-close row) gets its own MFE/MAE.
6. **Pyramiding/partial closes preserve existing trade-row semantics** — no new "trade" concept, no retroactive redistribution.
7. **Intrabar precision explicitly out of scope** — bar-level (D1/OHLC) fidelity only, matching the currently-connected simulation.

## 1. What changed, by file

**`at24-quant-engine/src/domain/position.ts`** — four new optional, side-agnostic fields: `highestPriceSinceEntry`/`highestPriceSinceEntryTimestamp`/`lowestPriceSinceEntry`/`lowestPriceSinceEntryTimestamp`. Intermediate engine state only — never the canonical public representation.

**`at24-quant-engine/src/domain/simulation/trade.ts`** — four new fields on `SimulationTrade`: `mfeR: number | null`, `maeR: number | null`, `mfeTimestamp?: number`, `maeTimestamp?: number`. A timestamp is present if and only if its own R value is non-null.

**`at24-quant-engine/src/runtime/simulation/position-engine.ts`**:
- `openPosition()` seeds excursion at `entryPrice`/`entryTimestamp` — a brand-new position (including a reversal leg opened mid-bar) always starts fresh, never inherits a prior position's history.
- New pure function `updateExcursion(position, bar): Position` — folds one bar's high/low into the running extremes. Strictly incremental (reads only the one `bar` passed in, never a slice of `bars`) and idempotent per bar (verified directly, test A9) — this is what makes the two call sites in `simulation-engine.ts` safe to overlap without double-counting.
- `increasePosition()`/`reducePosition()` required no changes — both already spread `...position`, so excursion state passes through pyramids and partial closes unchanged, exactly matching the locked "preserve existing trade-row semantics" requirement.

**`at24-quant-engine/src/runtime/simulation/simulation-engine.ts`** — two injection points, both additive:
1. Inside Step 1's opposite-side-fill reduce/close branch: `updateExcursion()` is applied to the closing position's own state *before* `buildTrade()` is called, since that path builds and records its trade directly inside Step 1 — before the general Step 1.5 update (below) would ever run this bar.
2. A new **Step 1.5**, right after Step 1's entire fills/opens/increases/reduces/reversals loop completes and strictly before Step 1b (protective SL/TP): folds the current bar's high/low into whichever position is open at that point. This single call correctly covers a fresh entry, a same-bar pyramid, a same-bar reversal, or a pre-existing untouched position — and because Step 1b/1c/Step 5 all read `state.openPositions` *after* this point, any trade built later in the same bar's processing already has that bar's own range included.

**`at24-quant-engine/src/runtime/risk/r-multiple.ts`** — one new, additive function: `tryComputeR()`, a null-safe sibling of `computeCurrentR`/`computeRealizedR` that returns `null` instead of throwing when `riskDistance <= 0`. Reuses the exact same `computeRiskDistance`/`favorableMove`/`computeRMultiple` primitives — no second formula. **Does not change `computeRealizedR`'s own existing throwing behavior**, and is not called from it.

**`at24-quant-engine/src/runtime/simulation/trade-ledger.ts`** — `buildTrade()` gained a `buildExcursion()` helper: applies the side-aware favorable/adverse mapping exactly once (BUY: favorable=high/adverse=low; SELL: reversed, mirroring `resolveProtectiveExit`'s own convention) over `Position.highestPriceSinceEntry`/`lowestPriceSinceEntry`, using the identical `riskBasisStop` (`initialStopLoss ?? stopLoss`) `rMultiple` already uses, via `tryComputeR()`.

## 2. A real, load-bearing finding: `riskDistance <= 0` is ONE underlying condition, not two

While proving the locked contract's null-safety requirement, this phase discovered — and the user's own review sharpened — a precise architectural fact: `computeRiskDistance(direction, entryPrice, stopLoss)` depends **only** on `entryPrice` and `stopLoss`, never on the price being measured against. This means `rMultiple`'s own risk distance and `mfeR`/`maeR`'s risk distance are **the exact same underlying quantity**, computed twice, for any given trade.

The pre-existing `rMultiple` computation in `buildTrade()` runs **first**, unconditionally, and throws uncaught when `riskDistance <= 0` (a real, reachable, pyramiding-specific case: a volume-weighted-average `entryPrice` shift can cross the fixed `initialStopLoss`). This means: **`mfeR`/`maeR`'s own null-guard is correct and total at its own function boundary (`tryComputeR`, proven directly — tests A4-A6, C2), but it cannot currently be observed end-to-end through a real `runSimulation()` call**, because the pre-existing defect throws before `mfeR`/`maeR` are ever reached in that exact scenario (proven directly — test C1, which asserts the throw happens, not that it doesn't).

This is disclosed, not silently patched around. Fixing `rMultiple` was explicitly, deliberately **not** pulled into P4.6's scope — doing so would have turned a bounded analytics phase into an existing execution/ledger defect remediation, exactly the scope-creep the locked contract's hard constraints forbid. A separate, standalone fix has been flagged (background task, out-of-band from this PR) with the sharper dependency this phase's own review surfaced: fixing it is also what will make P4.6's own "total and non-throwing" guarantee observable end-to-end, not just at the helper boundary.

**The precise, refined guarantee this phase actually delivers**: *the MFE/MAE R-normalization function (`tryComputeR`) is total and non-throwing for invalid risk denominators; current end-to-end trade construction remains subject to the pre-existing `rMultiple` exception.*

## 2b. A pre-existing execution capability gap (not a P4.6 test limitation): `oppositeDirectionBehavior` is declared but not runtime-consumed

While building a review-requested integration test for the "opposite-side order fill reduced/closed the position" branch (Step 1, the branch injection point 1's explicit `updateExcursion()` call was added to — including its own "leftover quantity → reversal" sub-case), this phase traced two independent facts:

1. `decision-builder.ts`'s `buildDecision()` has an explicit, unconditional rule: an ENTER signal while `hasOpenPosition` is true is admitted **only** when `pyramiding.openPositionSide === signal.direction` (a same-direction pyramid). An opposite-direction signal while a position is open always resolves to `HOLD` — there is no code path in this function that ever creates an opposite-side order while a position of the other side is open.
2. `PyramidingPolicy.oppositeDirectionBehavior` (the field whose `"REVERSAL"` value conceptually names this exact scenario) has **zero consumers anywhere in `src/runtime/`** (confirmed by direct search) — it is read only by the MQL-importer/AI-compiler's own IR *generation* (declared metadata), never by the execution engine.

Combined with a direct search confirming the pre-existing (pre-P4.6) test suite has no test exercising this exact branch either (by its own literal reason string), the finding is recorded precisely as follows, for future audits:

> **`oppositeDirectionBehavior` is represented in strategy/IR semantics but is not currently consumed by runtime decision/execution logic. Consequently, the opposite-fill/reversal branch in `simulation-engine.ts` is currently not reachable through a normal runtime strategy signal. P4.6 does not wire this behavior because doing so would change execution semantics and exceed the phase boundary.**

This is a genuine, pre-existing engine capability gap — not introduced by, not a defect of, and not fixable within P4.6's own bounded scope (wiring `oppositeDirectionBehavior` into `buildDecision` would be real execution-semantic engine work, a separate initiative in its own right, not a P4.6 concern). Rather than force a synthetic, non-representative scenario to claim integration coverage that would falsify the actual current engine contract, this is disclosed directly (test B7) and the underlying primitives that branch's own added line depends on (`openPosition`'s fresh seeding, `updateExcursion`'s composition) are proven correct in isolation instead. **This gap should not be treated as a reason to reopen P4.6-T1** — closing it is a distinct, future, execution-semantics initiative.

## 3. Tests (`at24-quant-engine/test/p4.6-mfe-mae.test.ts`, 18 tests)

Three-part contract, per the locked refinement:

- **A. Isolated excursion normalization** (A1-A6: `tryComputeR` — BUY/SELL, positive distance, zero distance, negative distance, all directly, no simulation; A7-A9: `updateExcursion` — new-extreme, within-range no-op, same-bar idempotence).
- **B. Clean end-to-end paths through `runSimulation()`** (B1: entry-bar inclusion; B2: exit-bar inclusion + no-look-ahead in one scenario; B3: BUY/SELL asymmetry; B4: partial-close row-level correctness, proving the second row's excursion correctly *continues* the position's pre-partial-close history rather than resetting; B5: a clean pyramid where `riskDistance` stays positive throughout, proving `mfeR`/`maeR` attach correctly to the one resulting trade row; B6: risk-engine `FORCE_EXIT` — max-holding-period, proving Step 1.5 updates state before Step 5's own management read; B7: the §2b finding, proving the underlying primitives injection point 1's reversal sub-case depends on, since the branch itself is unreachable).
- **C. Documented negative-path limitation** (C1: `buildTrade()` genuinely throws via the pre-existing `rMultiple` line for a stop-crossing pyramid — asserted as the *expected*, disclosed behavior, not hidden; C2: `tryComputeR` alone, same inputs, correctly returns `null`).

## 5. Known limitations (disclosed, not silently worked around)

- The `riskDistance <= 0` case cannot be proven end-to-end via `runSimulation()` today — see §2. A separate, already-flagged task tracks the dependency.
- **A pre-existing engine capability gap, not a P4.6 defect** — see §2b: `oppositeDirectionBehavior` is represented in strategy/IR semantics but is not currently consumed by runtime decision/execution logic. Consequently, injection point 1's own "opposite-side order fill/reversal" branch in `simulation-engine.ts` is currently not reachable through a normal runtime strategy signal. P4.6 does not wire this behavior, because doing so would change execution semantics and exceed the phase boundary. Proven at the underlying-primitive level instead (test B7).
- True intrabar precision remains out of scope (per the locked contract, item 7) — MFE/MAE is bar-level (D1/OHLC) approximation, identical fidelity to the rest of the currently-connected simulation.
- No frontend/API/UI surface yet — `mfeR`/`maeR`/`mfeTimestamp`/`maeTimestamp` exist on `SimulationTrade` but are not yet projected into `AlgoTestTradeView` or rendered anywhere. That is Tier 2's own, separately-checkpointed scope.
- No aggregate analytics (e.g., an "average MFE ratio" summary statistic) — deferred to a future tier once the raw per-trade values exist and have been used for at least one real cycle.
