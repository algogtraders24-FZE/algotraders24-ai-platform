# Q1.4 — Future-Platform Contract Check

Hand-built IR fixtures only (`test/q14-future-platform-contract.test.ts`) — no Pine/NinjaScript/cBot parser is built here, and none of these are "implemented importer features." This checks whether the CURRENT `StrategyIR`/`PendingOrderManagementIR`/eligibility contracts can represent representative future-platform concepts WITHOUT adding platform-specific fields into simulation business logic.

## Classification

`REPRESENTABLE` = the current type/contract can express it, and `checkReductionEligibility`/`validateStrategyIR` accept a correctly-formed instance. `PARTIALLY REPRESENTABLE` = some real dimension of the concept has no field, or exists as a field but is not actually enforced by the execution engine. `NOT REPRESENTABLE` = no field/contract exists for the concept at all. `UNKNOWN` = insufficient research to classify (none found this sprint — every concept below was resolved to one of the other three).

## Pine

| Concept | Classification | Reasoning |
|---|---|---|
| `strategy.entry` (market/limit/stop) | `REPRESENTABLE` | `EntryIR.executionType`/`limitPrice`/`stopPrice` — proven directly |
| `strategy.order` (raw, no pyramiding bookkeeping) | `NOT REPRESENTABLE` | Every AT24 entry goes through the same risk-gated path; no "bookkeeping-free" primitive exists anywhere |
| `strategy.exit` (id-bound SL/TP/trailing bracket) | `PARTIALLY REPRESENTABLE` | The SL/TP/trailing MECHANISM exists (`risk.stopLoss`/`takeProfit`/`trailingStop`) at the strategy level; binding it to a SPECIFIC named entry id (multiple simultaneous brackets) has no representation — AT24's NETTING model tracks one position per symbol, not per-entry-id brackets |
| `strategy.close` (condition-authored close) | `NOT REPRESENTABLE` | No `ExitRule`-based condition-driven CLOSE is evaluated by Q0.5 (documented deferred item, unchanged) — only risk-rule-driven exits exist |
| `strategy.cancel` | `REPRESENTABLE` | `PendingOrderManagementOperation.CANCEL_PENDING` — the SAME contract Q0.13/Q1.3 built for MQL, proven by hand-built fixture |
| pyramiding (count-limited) | `PARTIALLY REPRESENTABLE` — **a real, newly-precise finding** | `PyramidingPolicy.maxEntries`/`maxPositions` (Q0.7) exist as TYPE fields, but `grep`-verified to be referenced NOWHERE else in `src/` — `checkReductionEligibility` only checks `sameDirectionBehavior === "ACCUMULATE"`, never the numeric cap, and Q0.5's engine has no "reject after N entries" code path at all. A translator CAN set `maxEntries: 1`, and it will pass eligibility, but the cap is silently unenforced at runtime (unlimited accumulation actually happens). Proven directly by hand-built fixture. |
| `process_orders_on_close` (bar-close vs. next-bar-open timing) | `REPRESENTABLE` | `barCloseSemantics: "ON_BAR_CLOSE" \| "INTRABAR"` (Q0.7) already models exactly this distinction |
| `request.security` (MTF data pull) | `REPRESENTABLE` | `RequestSecurityCapability`/`SeriesAvailability` (Q0.7) — semantic representation only, unchanged |

## Verdict

**The canonical abstraction is sufficient for every representative order-lifecycle concept across all three future platforms** (entry, pending-order create/modify/cancel) WITHOUT adding platform-specific fields into simulation business logic — `PendingOrderManagementOperation` in particular is proven to be a genuinely universal vocabulary, not an MQL-specific one. The two real, honest gaps found (condition-authored `close`/`exit` calls, and pyramiding's unenforced numeric cap) are NOT platform-parser gaps — they are pre-existing, already-documented architectural scope boundaries (`ExitRule`-based exits are explicitly deferred; `maxEntries`/`maxPositions` enforcement was never built for ANY platform, MQL included) that would need to be closed once, generically, benefiting every future platform simultaneously — never platform-by-platform.

No platform-specific field was added to any simulation-business-logic file this sprint (§15 — `PlatformSemanticProfile` itself was found sufficient, unmodified).
