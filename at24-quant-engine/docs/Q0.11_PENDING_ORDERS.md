# Q0.11 — Pending Orders (LIMIT/STOP)

## LIMIT order semantics (Q0.11.5)

`resolveLimitFill()` (`bar-fill-model.ts`, Q0.5, unmodified): a BUY limit fills at the bar's own OPEN if the open already satisfies the limit (a favorable gap — cheaper than requested), otherwise at the LIMIT PRICE ITSELF if the bar's low trades strictly through it (touch alone, without penetration, is never sufficient — `test/simulation-fill-model.test.ts`'s existing unit tests already proved this; `test/q11-golden-fixtures.test.ts`'s `LIMIT_BUY`/`LIMIT_SELL` prove it end-to-end for a real entry order for the first time). SELL mirrors exactly. A gap-through favorable price is always taken — never worse than the requested limit, sometimes better (`test/q11-gap-fixtures.test.ts`'s `LIMIT_GAP_THROUGH`).

## STOP order semantics (Q0.11.6)

`resolveStopFill()`: the trigger price is NOT automatically the execution price. An unambiguous (no-gap) trigger fills exactly at the stop level; a gap-through trigger fills at the bar's own (worse) open — the engine never assumes trigger price == fill price (`test/q11-golden-fixtures.test.ts`'s `STOP_BUY`/`STOP_SELL`, `test/q11-gap-fixtures.test.ts`'s `STOP_GAP_THROUGH`).

## Duplicate-order protection (a real gap this sprint's own capability required fixing)

Before Q0.11, no entry order could remain pending across more than one bar (every order was MARKET, always resolved one bar after creation). `buildDecision()`'s existing `hasOpenPosition` check was therefore never tested against a genuinely multi-bar-pending order — and would have created a NEW duplicate pending order on every bar the entry condition stayed true while a LIMIT/STOP order waited to fill. Fixed via an additive `hasPendingOrder` check (see `docs/Q0.11_ORDER_SEMANTICS.md`). Proven in `test/q11-intrabar-fixtures.test.ts`'s `MULTIPLE_PENDING_ORDERS`: a condition true for 3 consecutive bars while a LIMIT stays unfilled still produces exactly one order.

## Risk interaction (Q0.11.23)

A pending order's proposed entry passes through Q0.3's `evaluateRisk()` exactly like a MARKET order — session eligibility, max simultaneous positions, daily loss limit, size/geometry validation all apply identically, using the order's own known price (not `bar.close`) as the reference where relevant (see `docs/Q0.11_ORDER_SEMANTICS.md`'s SL/TP reference-price refinement). `test/q11-failure-catalog.test.ts` item 18 proves a LIMIT entry exceeding `maxPositionSize` is rejected before any order is created — risk remains authoritative, order type carries no special exemption.

## Pyramiding/netting interaction (Q0.11.24/27/28)

The SAME `hasOpenPosition`/`hasPendingOrder` gate that prevents duplicate orders also structurally prevents pyramiding via a pending order — a new entry (of either direction) is never even evaluated while a position is open OR an order is pending, regardless of order type (`test/q11-failure-catalog.test.ts` items 16/17). Q0.5's NETTING accounting model is unchanged; HEDGING remains explicitly deferred (no code written toward it this sprint — only the documented difference model in `docs/Q0.11_PLATFORM_MAPPING.md`).

## Partial fills (Q0.11.26)

No code path in this engine ever produces a `PARTIALLY_FILLED` order — every `resolve*Fill()` function returns a boolean `filled` for the FULL requested quantity, never a partial one. This is the correct, safe answer per Q0.11.26's own instruction ("if not safely implementable: represent the state semantically, but BLOCK execution rather than inventing fills") — the `PARTIALLY_FILLED` status remains reserved in the type (Q0.4) for a future sprint that would need to implement genuine partial-fill logic; nothing here fabricates one. `test/q11-failure-catalog.test.ts` item 15 proves every fill is all-or-nothing.
