# Q1.5 Parts 4/5/6/7/12/13/14/15 — Security Audit

**No secret values appear anywhere in this document.**

## Part 4 — API security (`/api/quant-lite/backtest`, `/backtest/[jobId]`, `/coverage`, `/codegen`)

All four routes follow the same pattern, confirmed by direct code reading plus 375 total automated assertions (this sprint's own 67 + 308 carried-forward from Q0.9–Q1.4, all re-run this sprint, all still passing):

- Request bodies are parsed defensively (`try { req.json() } catch` → `400 INVALID_REQUEST`, never an unhandled crash).
- Every strategy spec is re-validated server-side via `validateStrategySpecServerSide` / `validate_spec()` regardless of what the client claims — the same authoritative validator for both backtest and codegen, so nothing about codegen's security posture was invented separately.
- `targetLanguage` and `symbol`/`timeframe` are checked against fixed allow-lists (`SUPPORTED_CODEGEN_LANGUAGES`, `QUANT_LITE_CAPABILITY`), never passed through to a shell or file path.
- Responses are built from explicit, typed field lists (`GetBacktestJobResponse`, `CodegenResponse`, etc.) — never a spread of an internal object — so internal-only fields (see Part 13) cannot leak by accident.
- `GET /backtest/[jobId]` validates the path-derived `jobId` against a strict UUID regex before any lookup; an invalid or unknown id gets `400`/`404`, never a filesystem operation on unsanitized input.

## Part 5 — Job system security

Reviewed `jobStore.ts` and `executionAdapter.ts`/`codegenAdapter.ts` directly:

- **Path traversal**: every job/temp-file path is built from `path.join(JOBS_DIR, ...)` using either a server-generated `crypto.randomUUID()` or a `jobId` that has already passed `isValidJobId()` (`^[0-9a-f]{8}-...$`). No `../` or separator character can survive that regex, so the resulting path can never escape `JOBS_DIR` — confirmed by reading `recordPath`/`configPath`/`resultPath`, all three of which throw before touching the filesystem on an invalid id.
- **Orphan processes**: both adapters set a hard timeout (`180s` backtest / `20s` codegen), send `SIGTERM`, and follow with `SIGKILL` after a 2s grace period — documented as necessary because Windows doesn't reliably honor `SIGTERM` for a plain Node child. No orphan survives a timeout.
- **Race conditions / duplicate execution**: `findActiveJobByRequestHash` gives idempotent re-submission of an identical in-flight request (Q0.9 Part 26, re-confirmed present, unchanged).
- **jobId guessing**: ids are `crypto.randomUUID()` — never sequential, never derived from request content.
- **Stale artifacts**: both adapters `fs.rmSync(..., {force:true})` their scratch config/output files in a `finally`/end-of-function block regardless of success or failure.
- **Concurrency/rate limits**: `MAX_CONCURRENT_BACKTESTS = 2` (env-overridable), a simple FIFO in-memory queue beyond that. Documented (pre-existing, Q0.9) as correct for the current single-process deployment and wrong for a future multi-instance one — not a new finding, still true.

## Part 6 — Frontend security

- No `dangerouslySetInnerHTML` anywhere under `components/quant-lite/` or `app/quant-lite/` (checked directly; the one repo-wide match is in the pre-existing, unrelated root `app/layout.tsx`).
- `LegacyEvidenceBadge.tsx` (see Part 7) takes no props — its text is a compile-time literal, not data-driven, so no client-side value can alter it.
- Code-generation downloads are client-side `Blob` construction from the API's own `code` string with a deterministic filename derived from the strategy name — nothing server-side is ever written to a client-influenced path.
- No client-controlled field feeds into `performanceClass`/`coverage`/`dataQuality`/`resultHash` — all computed server-side and returned as opaque, typed response fields (`performanceClassification.ts`, `coveragePolicy.ts`, `resultMapper.ts`), confirmed via code reading and via this sprint's + Q1.2/Q1.3's own spoofed-request tests.

## Part 7 — Result / evidence honesty

Searched the whole frontend for `VALIDATED-PERFORMANCE` and `LEGACY-BACKTEST-EVIDENCE`: the string `"VALIDATED-PERFORMANCE"` **does not exist anywhere in this codebase** — Quant Lite has no validation-chain status to promote into, structurally. `LEGACY-BACKTEST-EVIDENCE` is rendered by exactly one component, `LegacyEvidenceBadge.tsx`, which is a zero-prop component with hardcoded copy ("This result predates the current canonical execution engine ... not validated performance. It is not labeled Verified, Validated, or Guaranteed.") — there is no data path, client or server, that can change what it displays. No fabricated win-rate/PF/drawdown/coverage value is possible: every number shown comes from the server-computed `result`/`dataQuality`/`coverage` fields, never from client state.

## Part 13 — Production configuration audit

**One real finding, found and fixed this sprint.**

`run_backtest_job.py` and `run_codegen_job.py` both had a generic `except Exception as e:` fallback that placed the **full Python traceback** — every frame including this machine's absolute source paths (e.g. `File "E:\...\schema.py", line 65, ...`) — into the job's `details` field. That field is not internal-only: `executionAdapter.ts`/`codegenAdapter.ts` forward it unmodified into `job.error.details` / the codegen route's `details: { errors: e.details ?? [] }`, both of which are part of the typed, whitelisted client-facing response. Any unhandled engine exception (a genuine internal bug, not directly attacker-triggerable through normal validated input, but a real defense-in-depth gap) would have leaked internal filesystem structure to the client.

**Fix**: both scripts now `print(tb, file=sys.stderr)` (captured server-side only, as `stderrTail` — confirmed via Part 4/6 review that `stderrTail` is never included in any client-facing response type) and send a fixed, non-identifying string in `details` instead. The top-level `str(e)` message is left as-is (the overwhelming majority of exceptions here are plain `ValueError`/`KeyError` text with no path in their own message) — only the traceback, the actual path-bearing artifact, was removed from the client-visible path.

Verified safe: `ast.parse()` syntax check on both files, a live 200 OK codegen call after the edit, and a full re-run of the Q0.9 regression suite (22/22 — the other three `fail()` call sites, which only ever emit fixed/config-derived messages with no traceback, are untouched) and the Q1.5 suite (67/67).

**Residual, lower-severity, documented (not fixed)**: the `--config`/`--out` file-read failure paths (`could not read config file: {e}`) still interpolate `str(e)`, which for a `FileNotFoundError`/`PermissionError` would include the (server-generated, non-secret, already-fixed-pattern) temp file path. This path requires a disk/permission-level failure to trigger — not reachable through any attacker-controlled input in normal operation — and is called out here rather than silently left, per this sprint's own honesty requirement, as a known low-severity residual item for a future pass.

## Part 14 — Dependency audit

`npm outdated` / `npm audit` were run (read-only). Findings, **not acted on** — see reasoning below:

- **12 known vulnerabilities** (8 high, 4 moderate) reported by `npm audit`, the material ones being Next.js (`16.2.9` → fixed in `16.3.3`: SSRF via rewrites, unauthenticated Server Function endpoint disclosure, unbounded Server Action payload in Edge runtime, image-optimization DoS) and its bundled `postcss`/`sharp`.
- A moderate `valibot` advisory, fixable via non-`--force` `npm audit fix` — but `npm ls valibot` shows it's a transitive dev-only dependency of `@prisma/dev` (Prisma's CLI tooling, not shipped at runtime), and a dry-run confirms the fix would bump `prisma`/`@prisma/client` from `7.8.0` to `7.10.0`.

**Decision: documented, not executed.** Both fixes reach outside Quant Lite's isolated footprint — the Next.js bump is framework-wide (every route in the app, not just quant-lite) and the Prisma bump touches the client library this program's own standing rule treats with extra care ("never touch production Prisma schema/architecture"). Per this sprint's explicit instruction ("no blind upgrades — any upgrade must pass tests/typecheck/build/regression"), a change of this blast radius needs a whole-app regression pass that is out of proportion for a sprint scoped to Quant Lite. Recommended as a **separate, dedicated** follow-up (not Q1.6, not implied to be this agent's next action) with full-app testing, not silently deferred — flagged here explicitly rather than omitted.
