# Q1.1 — Failure Catalog

Minimum 15 categories per the sprint brief, each mapped to where it's actually handled in this codebase.

| # | Failure | Handled where | Behavior |
|---|---|---|---|
| 1 | Unexpected timestamp gap | `q11_gap_registry.py` | Classified into a `GapInterval` (type + severity); never silently skipped |
| 2 | Duplicate timestamp | `q10_data_coverage_audit.py` (Q1.0) | Detected via `GROUP BY ts HAVING COUNT(*)>1` - zero found across all 45 pairs |
| 3 | Missing OHLC | `q10_data_coverage_audit.py` | Detected via `high<low`/non-positive-price checks - zero found |
| 4 | Negative/invalid OHLC | same as above | Same query, zero found |
| 5 | Timezone mismatch | Documented in `Q1.0_DATA_COVERAGE_AUDIT.md` | Legacy `XAUUSD`/`EURUSD` store naive timestamps; `_EXNESS` symbols store UTC-aware - the gap registry only processes `_EXNESS` + legacy symbols consistently within their own series (never compares across the two), so this never produces a false gap |
| 6 | Session false-positive (a real gap wrongly called a closure) | `q11_gap_registry.py`'s closure window (20-96h, Thu/Fri/Sat start only) | Bounded tightly enough that a genuine multi-week outage cannot be misclassified as a weekend |
| 7 | Holiday false-positive (a closure wrongly called a real gap) | Same closure window, upper-bounded at 96h | A holiday extending a weekend by 1-2 extra days is absorbed; one extending further is intentionally NOT absorbed (documented limitation, not a full holiday calendar) |
| 8 | Central historical gap (a large gap inside an otherwise-decent range) | `coveragePolicy.ts`'s `FRAGMENTED` rule | A dominating gap forces `FRAGMENTED`/`RESTRICTED` regardless of overall coverage % |
| 9 | Partial coverage | `coveragePolicy.ts`'s `PARTIAL_CONTIGUOUS`/`SUPPORTED_WITH_WARNING` | Never silently truncated - `actual` period always shown alongside `requested` |
| 10 | Provider discontinuity (e.g. USOIL's 1h-vs-4h coverage gap) | `Q1.1_COVERAGE_SEMANTICS.md` | Documented as an open finding, not silently averaged away |
| 11 | Stale gap registry | `registryVersion` (Q1.1.22) | Detectable by comparing a stored result's version to the current one; no automatic re-labeling |
| 12 | Coverage hash mismatch | Same `registryVersion` mechanism | A result computed under one registry state is never silently presented as current |
| 13 | Performance timeout | `executionAdapter.ts`'s existing hard timeout (Q0.9, unchanged) | Still enforced - a large gap-policy-restricted job is not exempt |
| 14 | Memory pressure | `Q1.1_PERFORMANCE_BENCHMARK.md` | Measured (not limited) this sprint - see peak memory figures for full-history 1m/5m |
| 15 | Result/provenance mismatch | `resultMapper.ts` | `dataQuality` is threaded through from the exact job record used to create the run - never re-derived from a possibly-different current registry state at result-read time |

## Job-lifecycle failure codes (unchanged from Q0.9, still complete)

`INVALID_REQUEST`, `DATA_UNAVAILABLE`, `BACKTEST_FAILED`, `BACKTEST_TIMEOUT`, `ENGINE_ERROR`, `RESULT_INVALID`, `UNKNOWN_ERROR` - see `Q0.9_FAILURE_CATALOG.md` for the full table. Q1.1 adds no new job-level error code; `RESTRICTED` and `SUPPORTED_WITH_WARNING` are not failures, they are non-blocking data-quality disclosures on an otherwise-successful job.
