# Q0.9 — Provenance & Reproducibility

Every completed job's `provenance` block (`run_backtest_job.py`'s output, embedded in the `BacktestResult`) records:

```json
{
  "jobId": "...", "requestHash": "...", "resultHash": "...",
  "symbol": "XAUUSD_EXNESS", "signalTimeframe": "1h", "execTimeframe": "1m",
  "dateRange": { "start": "...", "end": "..." },
  "initialCapital": 10000, "riskPct": 1.0, "spreadPrice": 0.30, "contractSize": 100,
  "engineVersion": "execution_mtf-q0.6-lookahead-fixed",
  "signalBarsLoaded": N, "execBarsLoaded": N,
  "generatedAt": "..."
}
```

- **`requestHash`** — deterministic hash of the semantic request (see `Q0.9_JOB_LIFECYCLE.md`). Reproducing a result means resubmitting a request that hashes to the same value.
- **`resultHash`** — SHA-256 over `{stats, trades}` (sorted keys, `run_backtest_job.py`), so two result files can be compared byte-for-byte without re-running the engine.
- **`engineVersion`** — a fixed string identifying the exact engine state (`execution_mtf-q0.6-lookahead-fixed`), not a git commit hash (this repo's Q0.6/Q0.7/Q0.8 work is itself uncommitted at the time of Q0.9 — see the sprint's own git-safety notes) — sufficient to distinguish "the look-ahead-fixed engine" from any future engine revision, without depending on a commit that may not exist yet.
- **`signalBarsLoaded`/`execBarsLoaded`** — real row counts from the actual query, letting anyone auditing a result confirm how much data actually fed it, not just the requested date range.

## Reproducibility, demonstrated

The automated regression test (`quant-engine/scripts/q09_regression_test.py::test_determinism`) runs the identical config twice and asserts `stats` and the full trade list are byte-identical via `JSON.stringify`/`json.dumps` comparison — confirmed passing. Separately, the MACD regression test reproduces Q0.6's own known-good numbers (208 trades, 43.75% win rate, PF 1.15, +19.61% return, $11,961.23 final balance, identical first-trade entry price/time) exactly, both via the standalone script and via the live HTTP API — proof that the same config, run through two different invocation paths (direct script call vs. the full API+adapter+subprocess chain), produces the identical result.
