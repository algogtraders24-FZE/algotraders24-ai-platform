# Q0.9 — Execution Adapter (Process Boundary)

`frontend/services/quant-lite/backend/executionAdapter.ts` is the only place in `frontend/` that spawns a process (confirmed nothing did before Q0.9, via a repo-wide grep for `child_process|spawn(|execFile`).

## The boundary

```
executionAdapter.submitJob(jobId)
  -> writeJobConfig(jobId, config)          # a JSON file, server-generated path + content
  -> child_process.spawn("python", [JOB_RUNNER_SCRIPT, "--config", cfgPath, "--out", outPath])
  -> capture stdout/stderr (bounded to last 4000 chars)
  -> hard timeout (default 180s, QUANT_LITE_BACKTEST_TIMEOUT_MS) -> SIGTERM, then SIGKILL after 2s grace
  -> on close: read outPath, map via resultMapper.ts, update the job record
  -> delete the per-job config/out scratch files
```

**Never** executes a shell string. `spawn(cmd, argsArray, { shell: false })` — arguments are passed as an array, so there is no shell to interpret metacharacters even if a value somehow contained them. The only things on the command line are: a fixed script path (`JOB_RUNNER_SCRIPT`, a repo-relative constant) and two flags pointing at files this module itself created with server-generated names (`crypto.randomUUID()`-based job ids, never user input).

## Config/result files

Written under `quant-engine/output/jobs/<jobId>.config.json` and `<jobId>.result.json`. `jobId` is always a server-generated UUID; every path-building function validates it against a UUID regex first (`jobStore.ts::isValidJobId`), so no user-controlled string ever reaches a filesystem path. Both scratch files are deleted after the job finishes — only the persistent `<jobId>.json` job record remains.

## Timeout

Enforced by the Node side (`setTimeout` + `child.kill("SIGTERM")`, escalating to `SIGKILL` after a 2s grace period — Windows does not reliably honor `SIGTERM` for a plain child process, so the grace-then-kill pattern is required to guarantee no orphan survives). Verified live: a job forced to run against an 800ms timeout was killed, marked `FAILED`/`BACKTEST_TIMEOUT` at 838ms, and `tasklist` confirmed zero orphaned `python.exe` processes afterward (see `Q0.9_REAL_EXECUTION_VALIDATION.md`).

## Concurrency

`MAX_CONCURRENT_BACKTESTS` (env `QUANT_LITE_MAX_CONCURRENT_BACKTESTS`, default `2`). An in-memory counter + FIFO array queue — jobs beyond the limit stay `QUEUED` until a running slot frees. Verified live with 3 simultaneous real jobs across 3 different symbols: exactly 2 ran concurrently at any moment, results were fully isolated (no cross-job data), and the third started automatically once a slot freed.

**Known limitation**: this is a single-process, in-memory singleton. It is correct for the current single dev-server deployment and would need a real shared coordinator (e.g. a Postgres-backed queue via the existing Prisma schema) for a future multi-instance deployment — noted as a Q1 follow-up, not solved here, per Q0.9.45's "do not optimize" instruction.

## What run_backtest_job.py guarantees on its side

Every failure path (bad config, invalid spec, no data, any uncaught exception) writes a structured `{"status": "FAILED", "errorCode": ..., "errorMessage": ...}` to `--out` and exits 1 — the script never crashes without leaving a result file behind, so the Node adapter's "no result file" case (mapped to `ENGINE_ERROR`) is reserved for genuine process-level failures (e.g. Python itself missing), not ordinary engine errors.
