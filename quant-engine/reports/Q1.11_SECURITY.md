## Not directly re-tested this sprint (inherited from existing, unchanged code, verified via reading)

- **Oversized request**: not explicitly load-tested against the new service this sprint. The service parses the JSON body via FastAPI's default request handling before any size-specific check exists — this is a real, named gap, consistent with the same "oversized junk field accepted" observation already flagged as a known limitation in `Q1.7_COMPLETE.md` and specifically called out as worth building into this new network-facing surface in `Q1.9_SECURITY.md`'s own design notes. **Not fixed this sprint** — flagged honestly rather than silently left implicit.
- **Shell injection / arbitrary filesystem path / arbitrary command strings** inside the strategy spec's own string fields (name, indicator ids): inherited unchanged from `schema.py`'s `ID_PATTERN`/`_validate_ref` (the Q1.4/Q1.5 fixes) — not re-tested against this specific service this sprint, since the validation code path is byte-identical to what Q1.5's 67-assertion suite already exhaustively covered against the local adapter. Re-running that exact suite against the new HTTP service (rather than assuming the shared validator behaves identically) is a real gap for a future pass — noted, not performed.

## No Python traceback returned to client — verified by design, inherited from Q1.5's own fix

`_run_job()`'s exception paths (in `quant_lite_execution_service.py`) never place a caught exception's traceback into any HTTP response — the only place a raw exception message could reach a client is the `except Exception as e` block around subprocess startup itself (`fail to start engine process`), which uses `str(e)` only, the same low-risk pattern Q1.5 already reasoned about for the equivalent local-adapter code path (`err.message`, not a traceback). The engine's own internal exceptions (inside `run_backtest_job.py`) are still routed to `stderr` only, per the unchanged Q1.5 fix — the service captures that as `stderrTail` on the job record but **never returns it** in `GET /backtest/{jobId}`'s response body (explicit whitelist, confirmed by reading the handler: `jobId`, `status`, `createdAt`, `startedAt`, `completedAt`, `durationMs`, `result`, `error` only).

## No absolute filesystem paths returned

Same explicit whitelist as above — `JOBS_DIR`, `JOB_RUNNER_SCRIPT`, `ROOT` (all real absolute paths on the server) never appear in any response field.

## No secret/token in logs

The bearer token is never logged, printed, or included in any `Write-Host`/response — confirmed by reading every line of `_require_secret()` and every call site; the only place the configured secret value is ever read is the `hmac.compare_digest` call itself.

## No `market.db` leakage

No endpoint returns raw database content, a file path to it, or any value derived from it beyond the same aggregate strategy-result numbers the local adapter has always returned. `market.db` is opened exactly once per job, inside `run_backtest_job.py`'s own unmodified `load_candles()`, and never referenced anywhere in the new service file itself.

## No internal process details exposed

`engineExitCode` was **deliberately not carried over** to the new service's job record schema (it existed in `jobStore.ts`'s local record but the remote job record doesn't need or return it) — one fewer internal-implementation-detail field in the new surface than the old one had, not more.

## Full regression suite re-run against the Vercel adapter configured in remote mode

`q09_backend_tests.ts` (28 assertions — request validation, coverage gating, job-ID format rejection) re-run this sprint with `QUANT_LITE_EXEC_SERVICE_URL` pointed at the live local service: **28/28 pass**. These are mostly pre-adapter validation-layer tests (unaffected by which execution path is configured, by construction — the validation happens before the local/remote branch), but this confirms the branch itself introduces no regression in the request-rejection paths that run first.
