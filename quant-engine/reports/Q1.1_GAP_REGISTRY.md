# Q1.1 — Gap Registry

## Build pipeline

```
quant_engine/market.db (read-only)
  -> quant-engine/scripts/q11_gap_registry.py       (real audit -> quant-engine/output/q11_gap_registry.json)
  -> quant-engine/scripts/q11_generate_frontend_registry.py  (-> frontend/data/quant-lite-gap-registry.ts)
  -> services/quant-lite/backend/coveragePolicy.ts   (consumes the generated .ts file, server-only)
```

Same two-stage "Python audits, generates a static TS data file" pattern this program has used since Q0.8 (`q08_gen_frontend_data.py`) and Q1.0 (`q10_*` scripts) - not a new pattern invented for this sprint.

## Versioning (Q1.1.22)

```python
registry_version = sha256(market_db_sha256 + audit_rule_version)[:16]
```

Deterministic by construction: the same `market.db` file plus the same `AUDIT_RULE_VERSION` string (`"q1.1-gap-rules-v1"`, bumped by hand whenever the classification rules themselves change) always produces the same `registryVersion` - no wall-clock timestamp is part of the hash. Current value: `d233071da0c6cece`. Every `CoverageAssessment` carries this value, so a stored result's data-quality label can be checked against whether the registry that produced it is still the current one.

## Scale

45 symbol/timeframe pairs audited, 15,764 total gap intervals found (98.6% of them `LOW` severity - short, ordinary irregularities). The generated registry file is ~2.9MB - large for a source file, negligible for a server-only Node module (never bundled to the browser, see `Q1.1_DATA_QUALITY_CONTRACT.md` "Server-authoritative").

## Refresh model (Q1.1.38)

**Explicit audit command, not silent per-request recalculation** - exactly as instructed. To refresh after `market.db` gains new data:

```bash
python quant-engine/scripts/q11_gap_registry.py
python quant-engine/scripts/q11_generate_frontend_registry.py
```

This is a manual, deliberate step (not wired into any request path, cron job, or build step in this sprint). The registry file is committed as source (not `.gitignore`d), so a refresh is a visible, reviewable code change - a stale registry is a known limitation (see `Q1.1_COMPLETE.md`), not a silent-corruption risk, since `registryVersion` changing is itself the signal that a refresh happened.

## What is NOT in the registry

Individual public holidays (see `Q1.1_GAP_POLICY.md` "Session model"). A per-timeframe view is fully computed independently for every one of the 7 timeframes per symbol - no timeframe's classification is inferred or copied from another (Q1.1.14); cross-timeframe comparison for the same symbol is documented separately in `Q1.1_COVERAGE_SEMANTICS.md` (Q1.1.15).
