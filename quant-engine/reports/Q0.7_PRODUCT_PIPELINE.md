# Q0.7 — Quant Lite Product Pipeline

## Part 1 — Existing product entry-point audit

1. **How strategies currently enter the system:** three code paths, all
   library-level Python functions, none product-facing —
   `template_builder.py::build_spec()` (deterministic wizard), a
   hand-written spec dict (every demo script), or
   `llm_parser.py::parse_idea_to_spec()` (never live-tested, no API key
   available in this environment).
2. **How specs are represented:** a plain JSON-serializable dict —
   `name`, `symbol`, `timeframe`, `indicators[]`, `entry_long[]`,
   `entry_short[]`, `risk{}` — validated by `schema.py::validate_spec()`.
3. **How `spec_engine` works:** `schema.py` (validation) →
   `indicators.py` (10 indicator formulas) → `interpreter.py`
   (condition evaluator) → one of three backtest engines.
4. **How code generation works:** `codegen_mql5.py`/`codegen_mql4.py`/
   `codegen_pine.py` take a spec dict and return source-code strings —
   entirely decoupled from the backtest engines (no shared runtime
   state), callable independently. Not part of this sprint's pipeline
   scope by the brief's own pipeline diagram, but a natural
   closely-related capability — flagged as an open question under
   Save/Export below, not assumed either way.
5. **How `execution_mtf.py` is invoked:** `run_spec_backtest_mtf(df_signal,
   df_exec, spec, risk)` — a plain function call, no queueing, no async
   boundary, no persistence layer. Caller supplies both DataFrames
   (signal-timeframe and 1-minute execution-timeframe candles) and a
   `RiskConfig` instance.
6. **How results are returned:** a 3-tuple —
   `(trades_df: pd.DataFrame, equity: pd.Series, stats: dict)` — all
   in-memory, nothing written to disk or a database by the engine itself.
7. **How reports are generated:** they aren't, currently — every script
   in this program (`demo.py`, `scripts/q0*_*.py`) prints the `stats`
   dict and optionally dumps `trades_df` to JSON by hand. No report
   template, no HTML/PDF generation, no persistence schema exists.
8. **Existing CLI/API/product entry point:** **none**. Confirmed by
   direct inspection — every entry point in `quant-engine/` is a
   `demo_*.py` or `scripts/*.py` script with an `if __name__ ==
   "__main__":` block, not a reusable function-as-a-service, CLI tool,
   or API route.
9. **Existing frontend location:** none exists. Repository-wide search
   confirms zero references to `quant_lite`, `execution_mtf`, or
   `spec_engine` anywhere under `frontend/`, and no `/backtest` or
   `/quant-lite` route exists under `frontend/app/`. The frontend does
   have an established structure (`/dashboard`, `/platform`,
   `/marketplace`, `/products`, `/pricing`, plus a full private API
   surface under `app/api/private/`) that a future Quant Lite section
   could plausibly extend — noted as context, not a decision, and not
   touched this sprint.
10. **Frontend code belonging to another workstream:** all of it. The
    entire `frontend/` tree belongs to the platform/homepage program
    (D2.x sprint series), a separate workstream from this Legacy Engine
    audit series. Confirmed via read-only inspection only — nothing
    under `frontend/` was modified.

**Conclusion, stated as instructed: no production Quant Lite entry point
currently exists.**

## Part 2 — Target pipeline

```
USER
 |
 v
Strategy Creation        (Option A: template wizard; Option C: LLM parser, not yet live-tested)
 |
 v
Strategy Validation       (schema.py::validate_spec())
 |
 v
Strategy Specification    (the validated spec dict - the single source of truth)
 |
 v
Quant Lite Risk Config    (quant_lite_risk.py::quant_lite_risk_config() - BE/trailing/partial pinned OFF)
 |
 v
Canonical execution_mtf.py (run_spec_backtest_mtf(df_signal, df_exec, spec, risk))
 |
 v
Deterministic Backtest    (trades_df, equity, stats)
 |
 v
Evidence Calculation      (see Part 6 - the result contract)
 |
 v
Result Validation         (sanity checks - see below)
 |
 v
Report                    (user-facing presentation - not yet built)
 |
 v
Save / Export             (persistence + optional spec/code export - open question, see below)
```

### Stage-by-stage contract

**Strategy Creation**
- Input: user choices (wizard dropdowns) or free-text idea (LLM path,
  not currently usable — no live key).
- Output: a spec dict, not yet guaranteed valid (wizard-built specs are
  self-tested at import and always valid in practice; LLM-parsed specs
  are not guaranteed until the next stage).
- Validation: none at this stage — deferred to the next stage
  deliberately, so both creation paths share one validation gate.
- Failure conditions: wizard path cannot fail (bounded dropdown choices,
  `template_builder.py::_self_test()` proves every combination is valid
  at import time). LLM path can fail after its own internal
  self-correction retry loop (`MAX_REPAIR_ATTEMPTS = 3`) is exhausted.
- User-visible behavior: wizard — immediate, synchronous, no loading
  state needed. LLM path — needs a loading state (API round-trip) and a
  clear failure message if repair attempts are exhausted (not built —
  no live test has ever exercised this path in this environment).

**Strategy Validation**
- Input: spec dict.
- Output: same dict, or a list of error strings
  (`schema.py::validate_spec()`).
- Validation: indicator types (10 supported), condition operators (7
  supported), and ATR-mode risk fields referencing a real ATR indicator
  in the spec. Does **not** validate numeric ranges (a zero or negative
  period/multiplier passes and only misbehaves downstream — see Q0.3's
  audit) — this is a known, pre-existing gap, not something Q0.7
  proposes fixing.
- Failure conditions: any unknown indicator type/op, or an ATR-mode risk
  block missing a valid `atr_id` reference.
- User-visible behavior: a specific, itemized error list (the function
  already returns exactly this) — never a generic "invalid strategy."

**Strategy Specification**
- Input/Output: the validated spec dict itself — the single artifact
  that flows into every downstream stage. No separate "compiled" or
  "normalized" representation exists.

**Quant Lite Risk Configuration**
- Input: user-chosen `risk_pct`, `spread_price` (or a data-driven
  default — see Part 5), `contract_size`, `start_balance`.
- Output: a `RiskConfig` instance via `quant_lite_risk_config(**kw)` —
  `use_breakeven`/`use_trailing`/`use_partial` pinned `False` regardless
  of any kwarg passed (Q0.4's design: pinned *after* `**kw` is applied,
  so this cannot be silently bypassed).
- Validation: none currently beyond what `RiskConfig.__init__` itself
  does (none — it accepts any values). A product surface should add
  range checks (e.g. `risk_pct` between 0.1 and 10) — not built this
  sprint, flagged for the UI implementation plan.
- Failure conditions: none currently enforced.
- User-visible behavior: the Quant Lite risk configuration should be
  **shown**, not just applied silently — see
  `Q0.7_EXECUTION_DISCLOSURE.md`.

**Canonical `execution_mtf.py`**
- Input: `df_signal` (spec timeframe), `df_exec` (1-minute, with real
  spread), spec, risk config.
- Output: `(trades_df, equity, stats)`.
- Validation: `validate_spec()` re-run internally (defense in depth);
  `len(sig) < 50` guard returns an empty, well-formed result rather than
  crashing.
- Failure conditions: invalid spec raises `ValueError`; insufficient
  data returns `{"trades_total": 0, "error": "not enough signal bars"}`
  rather than raising.
- User-visible behavior: for a real product, this call needs a
  synchronous-vs-async decision — see Part 17 (resource limits) and the
  UI implementation plan's loading-state design. A full year of 1-minute
  execution data backtests in ~6-10 seconds (measured, Q0.6) — likely
  fast enough to run synchronously for a single symbol/year, but this
  should be confirmed against real product-scale inputs (multi-year
  ranges, concurrent users) before assuming it never needs a job queue.

**Deterministic Backtest**
- Output: fully deterministic given fixed inputs — proven repeatedly
  (Q0.3 through Q0.6, every determinism check passed). This property
  should be surfaced to the user as a stated guarantee (see
  `Q0.7_EXECUTION_DISCLOSURE.md`), not just an internal property.

**Evidence Calculation**
- Input: `stats` dict (from `quant_engine.engine.summarize()`).
- Output: the result contract defined in Part 6.
- Validation/failure: see Result Validation below — kept as a distinct
  stage per the brief's own pipeline, even though today `summarize()`
  and "evidence calculation" are the same function call. A future
  product layer may add derived metrics (see Part 6) that go beyond
  what `summarize()` returns today — documented as a gap, not built.

**Result Validation**
- Not implemented anywhere in the current engine. Recommended minimum
  sanity checks for a product surface (design only, not built): negative
  `final_balance` should never occur (superseded by `account_blown`,
  already correct); `profit_factor` should be `None` (not a fabricated
  number) when `trades_total == 0`, already correct; a trade ledger
  whose PnL sum disagrees with `final_balance - start_balance` beyond
  floating-point tolerance would indicate an internal bug and should
  block the report from rendering rather than display silently — not
  currently checked anywhere.

**Report**
- Not built. See `Q0.7_UI_INFORMATION_ARCHITECTURE.md` Screen 5.

**Save / Export**
- Not built. Open design question, not resolved this sprint: does
  "export" mean (a) downloading the report/metrics, (b) downloading the
  trade ledger as CSV, (c) exporting the underlying spec as JSON, or
  (d) generating MQL5/MQL4/Pine source via the existing, already-working
  codegen functions? All four are plausible and none conflict
  architecturally — codegen in particular is a zero-new-code integration
  (`codegen_mql5.generate_mql5(spec)` already exists and works) — but
  which ones ship in Quant Lite v1 is a product decision, not an
  engineering one, and is left open here rather than assumed.

## Part 3 - Strategy creation: implemented indicator audit

All 10 confirmed implemented in indicators.py and mirrored in all
three code generators (re-confirmed this sprint by direct source
inspection, consistent with every prior audit in this program).

| Indicator | Parameters | Timeframe support | Strategy conditions supported | Status | Known limitations |
|---|---|---|---|---|---|
| EMA | period | any (spec-defined) | single-value compare, cross | IMPLEMENTED | none found |
| SMA | period | any | single-value compare, cross | IMPLEMENTED | none found |
| RSI | period | any | single-value compare, cross | IMPLEMENTED | Wilder-smoothed, standard formula |
| ATR | period | any | used for SL/TP sizing, not typically a direct entry condition | IMPLEMENTED | none found |
| MACD | fast,slow,signal | any | .line/.signal/.hist compare or cross | IMPLEMENTED | none found |
| BB (Bollinger) | period,mult | any | .upper/.middle/.lower compare | IMPLEMENTED | none found |
| STOCH | k_period,d_period | any | .k/.d compare or cross | IMPLEMENTED | slowing=1 convention (documented, matches Python) |
| ADX | period | any | .adx/.plus_di/.minus_di compare | IMPLEMENTED | measures strength not direction - typically used as a filter, not a standalone trigger |
| DONCHIAN | period | any | .upper/.middle/.lower compare | IMPLEMENTED | excludes current bar by design (shift-1), matches standard Turtle definition |
| SUPERTREND | period,mult | any | .line/.trend compare or cross-zero | IMPLEMENTED | iterative (not vectorized) - fine at current data sizes, would need attention at much larger scale |

No new indicators added or redesigned this sprint, per instruction.

## Part 4 - Strategy specification: minimum model for a free user

| Category | Supported | Status |
|---|---|---|
| Entry - BUY | entry_long condition list (AND-combined) | IMPLEMENTED |
| Entry - SELL | entry_short condition list (AND-combined) | IMPLEMENTED |
| Conditions - indicator comparison | left/op/right refs | IMPLEMENTED |
| Conditions - price comparison | close/open/high/low as a valid ref | IMPLEMENTED |
| Conditions - AND | multiple entries in entry_long/entry_short are ANDed | IMPLEMENTED |
| Conditions - OR | UNSUPPORTED / FUTURE - no OR logic exists anywhere in interpreter.py |
| Exit - SL | risk.sl_mode (ATR or PIPS) + distance | IMPLEMENTED |
| Exit - TP | risk.tp_mode (ATR or PIPS) + distance | IMPLEMENTED |
| Exit - opposite signal | UNSUPPORTED / FUTURE - engines close only via SL/TP; entry evaluation is fully gated while a position is open, so an opposite signal is never even evaluated |
| Risk - fixed risk % | risk_pct, applied against current balance each trade | IMPLEMENTED |
| Risk - position sizing | risk_money / (sl_dist x contract_size), floor 0.01 lot | IMPLEMENTED |
| Risk - breakeven/trailing/partial | exist in the engine, forced OFF for Quant Lite by quant_lite_risk_config() | IMPLEMENTED IN ENGINE / DISABLED IN PRODUCT - must stay disabled, not a gap |
| Risk - max position count | hardcoded single-position-only, not user-configurable | IMPLEMENTED (as a fixed constraint) |
| Session/trading-hours filter | UNSUPPORTED / FUTURE - RiskConfig has the field, no spec engine honors it (Q0.3/Q0.5 finding) |
| Multi-symbol / portfolio strategies | UNSUPPORTED / FUTURE - one symbol per spec |

## Part 6 - Result contract

Minimum metrics, all already computed by quant_engine.engine.summarize()
(confirmed by source inspection, no new calculation required):
trades_total, trade_cycles, win_rate_pct, profit_factor,
total_return_pct, max_drawdown_pct, final_balance, account_blown.

Requested but NOT currently computed anywhere - must not be exposed
until built: winning/losing trade counts, average trade, largest
win/loss, a standalone "final equity" field (distinct from final
balance). None require new engine logic - all are trivial aggregations
of the already-returned trades_df/equity - but none exist as named
fields today.

Trade list fields present today: entry_time, exit_time, direction,
entry_price, exit_price, volume, pnl, reason (SL, TP, or PARTIAL,
though PARTIAL never appears for Quant Lite since it's forced off).
SL/TP LEVELS at entry time are NOT currently stored in trades_df - only
the exit reason, not the originally-set stop/target price. Real gap,
not fabricated - would need a small explicit engine-output addition.

Equity curve: the equity Series already exists, minute-resolution,
not currently persisted or shaped for chart consumption.

Do NOT expose: anything requiring commission/slippage modeling
(fabricated precision), Sharpe/Sortino or any risk-adjusted ratio (not
computed anywhere), Monte Carlo/robustness metrics (explicit Quant Pro
boundary item).

## Part 13 - Future API contract (design only, not implemented)

POST /quant-lite/backtest

Input: strategy (validated spec), symbol, timeframe, dateRange, capital,
risk, executionAssumptions (echoed back, not independently settable -
the execution model itself is fixed by the canonical engine).

Backend flow: validate spec, then validate symbol/date-range against
market.db coverage, then quant_lite_risk_config(...), then load
df_signal/df_exec from market.db, then execution_mtf.run_spec_backtest_mtf(...),
then evidence calculation (Part 6), then result validation (Part 2),
then persist (backtestId assigned; persistence layer not designed this
sprint).

Output: backtestId, status, metrics (Part 6), equityCurve, trades
(Part 6), assumptions (Part 5, echoed), warnings list, provenance (Part 15).

Conceptual contract for a future sprint - no route created this sprint.

## Part 15 - Provenance contract (design only)

Every future Quant Lite result should carry: strategy specification
(hash it for a compact reference), engine version (not currently
tracked anywhere - needs a version-string convention, not designed this
sprint), the resolved Quant Lite risk configuration actually used,
symbol/timeframe/date range, initial capital, execution assumptions
(Part 5's fixed list), data source (which market.db symbol/provenance),
timestamp, and a result-schema version so future format changes don't
break old saved results.

No provenance storage system is built this sprint. This is the field
list a future implementation should populate, matching the same
discipline the M-Series' own Evidence.provenance field already enforces
one layer over (M0.1_product_model_freeze.md principle 7) - Quant Lite
does not get a lower bar just because it's simpler.
