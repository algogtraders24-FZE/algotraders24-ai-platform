# Q1.2 Part 5/6/7 — Large-Run UX

## Threshold — evidence-based, not guessed

From Q1.1's real measured benchmark (`Q1.1_PERFORMANCE_BENCHMARK.md`): only 1m/5m signal timeframes were benchmarked at full-history scale and showed `SLOW`-tier runtime (70-82s). Every other timeframe stayed `FAST`/`NORMAL` even at its longest tested window (Q1.0's timeframe sweep: 3-35s). The warning is therefore scoped to 1m/5m only — extending it elsewhere would be exactly the "guesswork" the sprint rules out.

Within 1m/5m, the threshold is set at the last data point Q1.1 actually measured as still `NORMAL`: the 1-year window (39.9s/42.3s, under the 45s `NORMAL`/`SLOW` boundary). A request longer than 365 days on 1m or 5m triggers the notice; the full-history window (70-82s, `SLOW`) is comfortably past it. Implementation: `services/quant-lite/backend/performanceClassification.ts`.

## What the warning does NOT do

- Does not expose the measured memory figures (1.7GB/1GB) — generic wording only.
- Does not promise a completion time — no number of seconds anywhere in the message.
- Does not appear for any range/timeframe combination that wasn't actually measured as slow.

Copy: *"Larger historical runs may take significantly longer and use more server resources. This is a performance notice only - it does not indicate a problem with your strategy, the requested data, or the backtest result."* Verified live in the browser (real 1m/2024-01-01→2026-05-31 request) rendering in a neutral, non-alarming style, visually and semantically distinct from the RESTRICTED/warning data-quality banner shown alongside it.

## Server-authoritative (Q1.2 Part 7)

`performanceClass`/`performanceWarning` are computed inside `assessCoverage()` (`coveragePolicy.ts`), the same server-only function that already produces the coverage/gap policy — embedded in every `CoverageAssessment` returned by `GET /api/quant-lite/coverage` and stored on the job at creation. Verified live: a `POST /api/quant-lite/backtest` request with spoofed `performanceClass: "FAST"`/`performanceWarning: null` fields in the body was accepted and a job created, but the server's own computed assessment (not the spoofed one) is what gets stored and returned — the same mechanism already proven for `dataQuality` spoofing in Q1.1, reused here rather than rebuilt.

## RUNNING state (Q1.2 Part 6)

`ResultsView.tsx`'s `QUEUED`/`RUNNING` card now explicitly shows symbol, timeframe, and requested date range (read from `job.dataQuality`, already available at job creation — no new field needed), in addition to the existing spinner/status text and the `CoverageAssessmentPanel` (which itself carries the performance notice when applicable). No fabricated progress percentage was added — unchanged from Q0.9/Q1.1's explicit rule.

## Not implemented this sprint

A live, ticking estimate ("about 60 seconds remaining") was considered and rejected — Q1.1's benchmark used one representative symbol/strategy; promising a specific number for an arbitrary request would not be evidence-based for every case, and the sprint explicitly says not to promise completion time.
