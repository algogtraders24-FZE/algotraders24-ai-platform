disable breakeven, ATR trailing, and 50% partial-close for Quant Lite

## 3. RiskConfig tracing

Repository-wide search (`grep -r RiskConfig --include=*.py`) found the
class referenced in exactly 12 files, **all under `quant-engine/` or
`quant_engine/`** — zero references anywhere in `ea-research/`,
`frontend/`, `at24-quant-engine/`, or `mt5-bridge/`. This directly
answers the sprint's own investigation questions:

1. **Where are defaults defined?** `quant_engine/engine.py:13-36`,
   class `RiskConfig.__init__(self, **kw)` — `use_breakeven`,
   `use_trailing`, `use_partial` all default `True` via
   `kw.get("...", True)`.
2. **Where are they overridden?** Only at construction, via keyword
   arguments — the class already supports `RiskConfig(use_breakeven=
   False, ...)` without any class change needed.
3. **Which backtest path does Quant Lite use?** None existed as a named
   path before this sprint — the closest real candidate was
   `execution_tick.py` (the canonical-engine recommendation from
   `QUANT_LITE_LEGACY_AUDIT.md`/`QUANT_LITE_PRODUCT_BLUEPRINT.md`),
   which is what this sprint's verification uses.
4. **Does the 1,764-strategy library use the same path?**
   `build_one_library.py`'s single `RiskConfig(...)` call site
   (line 23) uses the identical unmodified-defaults pattern as every
   other call site — confirmed, not touched or re-run this sprint.
5. **Does `demo.py` use the same construction pattern?** Yes — identical
   pattern, not touched this sprint.
6. **Does any M-Series component import or use `RiskConfig`?** No —
   confirmed by the repository-wide search above; zero matches outside
   `quant-engine/`/`quant_engine/`.
7. **Does any unrelated legacy product depend on these defaults?** None
   found. All 7 real construction call sites are `quant-engine/`'s own
   demo/verification scripts and the library builder — no external
   dependency exists on `RiskConfig`'s class defaults specifically.

No code was modified during this investigation step.

## 4. Quant Lite configuration path

**New file:** `quant-engine/spec_engine/quant_lite_risk.py` — a single
function, `quant_lite_risk_config(**kw) -> RiskConfig`, that forces
`use_breakeven=False`, `use_trailing=False`, `use_partial=False` (pinned
*after* the caller's `**kw` is applied, so a stray keyword argument
cannot silently re-enable any of the three) and passes every other field
through to `RiskConfig` unchanged.

This is the "explicit Quant Lite RiskConfig" boundary the sprint brief
asked for. `RiskConfig`'s own class defaults in `quant_engine/engine.py`
were **not changed** — any other, non-Quant-Lite caller in this
repository that continues to call `RiskConfig(...)` directly (e.g.
`demo.py`, `build_one_library.py`) is completely unaffected and keeps
getting the historical, feature-active defaults exactly as before.

## 17. Remaining execution gaps

Unchanged from Q0.3, per the sprint's explicit "do not implement
trailing/breakeven/partial-close in code generators during Q0.4"
instruction:

- GAP-01/02/03 (breakeven/trailing/partial in codegen) — **the
  honesty gap is now closed on the backtest side** (Quant Lite no longer
  claims these features); the *better* long-term fix (implementing them
  in codegen, per Q0.3 Decision C) remains deferred, not started.
- GAP-04 (static spread in `runner.py`) — unaffected by this sprint;
  `execution_tick.py` (used for this sprint's verification) and
  `execution_mtf.py` already solve this correctly.
- GAP-05 (slippage), GAP-07 (session filter), GAP-09 (stop-distance
  validation) — unchanged, still marked unsupported/research-only per
  Q0.3.
- GAP-06 (three Python engines not cross-validated on identical
  windows) — unchanged, still deferred to a future test-execution
  sprint.
- GAP-08 (dead commission hook) — unchanged, cosmetic only.
- The canonical-engine decision (`execution_mtf.py` recommended over
  `runner.py`/`execution_tick.py`) remains **not yet formally exercised
  for Quant Lite** — this sprint's verification used `execution_tick.py`
  because it was the most rigorous available check (real ticks, exact
  SL-price provability), not because it's being declared canonical;
  that decision is still open per Q0.3.
