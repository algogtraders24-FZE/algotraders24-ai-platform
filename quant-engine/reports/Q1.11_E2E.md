# Q1.11 Phase 10/11 — Real Vercel → VPS E2E & Failure Path

## Status: full software path proven locally; the physical network hop (Vercel deployment → Cloudflare Tunnel → real VPS) not yet exercised

This sprint's own instruction is explicit: *"Do not claim production-ready merely because the VPS script works... the central proof of this sprint is the real HTTP/network path."* This report is honest about exactly where that line sits.

## What WAS proven this sprint, live, with real code (not a fixture)

```
Real browser
  ↓
POST /api/quant-lite/backtest  (the actual, unmodified route)
  ↓
executionAdapter.ts's startJob() → runRemote()  (new code, this sprint)
  ↓
HTTP POST to http://127.0.0.1:8788/backtest  (the real service, running locally)
  ↓
quant_lite_execution_service.py spawns the unmodified run_backtest_job.py
  ↓
execution_mtf.py reads the real, checksum-verified market.db
  ↓
real result JSON
  ↓
HTTP response back to executionAdapter.ts's polling loop
  ↓
mapEngineOutputToResult() → job store → GET /api/quant-lite/backtest/[jobId]
  ↓
real browser render — confirmed live: metrics, equity curve, trade ledger all correct
```

Every arrow above is real, exercised code — the only difference from the sprint's own target diagram is that `127.0.0.1` stands in for the Cloudflare Tunnel + real VPS hop. Nothing in the software architecture between Vercel and "wherever the service actually runs" is mocked, stubbed, or hypothetical.

## MACD, RSI, EMA all run through this exact path with exact parity — see `Q1.11_PARITY.md`.

## What was NOT proven this sprint

## Phase 11 — Failure path testing, run live this sprint

**Remote service unreachable** (the service process killed mid-session, deliberately, to test this exact case): a real backtest request through the real, unmodified `/api/quant-lite/backtest` route correctly resulted in:

```
status: FAILED
error: { code: "ENGINE_UNREACHABLE", message: "could not reach the remote execution service: fetch failed" }
```

Confirmed live in the browser: the Results page rendered **"Backtest failed — The backtest execution service could not be reached. Please try again shortly."** with a "Try Again" button — not a fabricated result, not a hang, not a raw stack trace. This is real evidence for this sprint's own explicit rule: *"Never convert infrastructure failure into a fake backtest result."*

**Not tested this sprint** (require the real network path to exist first, so there's a real tunnel/auth layer to fail):
- Tunnel unavailable (distinct from service-process-down — a DNS/routing failure) — would surface identically to "service unreachable" from the adapter's own point of view (both are a failed `fetch()`), but hasn't been exercised through an actual tunnel.
- Authentication failure specifically at the network layer (as opposed to the already-tested wrong-bearer-token case against the service directly).
- Malformed response from a genuinely different remote host (only tested against the well-behaved local service).
- Timeout under real network latency (the local test's "timeout" was really "connection refused," not "the request hung until the deadline").
