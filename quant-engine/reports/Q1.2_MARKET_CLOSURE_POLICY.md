# Q1.2 Part 3 — Market Closure Policy

## Decision: Option E (Hybrid) — explicit closure classification + a narrow, evidence-derived pattern library, not a static exchange calendar

A static per-exchange holiday calendar (Option A) was considered and rejected for this sprint: Quant Lite's symbols are CFD/synthetic instruments from a single data provider (Exness), not exchange-listed contracts with a single authoritative published calendar — "which calendar applies" is itself ambiguous (Gold and Oil CFDs don't strictly follow NYMEX/COMEX hours; this provider's own observed closure pattern, confirmed in Q1.1/Q1.2, doesn't match any single textbook calendar exactly). Inventing one would mean **pretending to know a holiday is a holiday merely because there is no data** — the one thing this sprint is explicitly told not to do.

Instead: every gap is classified by **evidence found in the data itself**, using the four categories requested:

| Category | Rule | Evidence standard |
|---|---|---|
| `KNOWN_MARKET_CLOSURE` | Gap starts Thu/Fri/Sat, lasts 20-96 hours (`EXPECTED_MARKET_CLOSURE` in code — same name kept from Q1.1 for continuity) | The dominant, near-universal weekly pattern across every WEEKLY_CLOSURE symbol (Q1.1) |
| `EXPECTED_SESSION_BREAK` | Gap starts 20:00-22:00 UTC, lasts 1-4 hours, any weekday | New in Q1.2 — only classified this way because it recurs on ~74%+ of eligible weekdays for the symbols where it appears (USOIL_EXNESS, XAUUSD_EXNESS/XAUUSD_ZS_EXNESS); the same time-pattern rule applied to EURUSD/GBPUSD/BTCUSD correctly finds almost none, because the evidence isn't there for those symbols — the rule is time-pattern-based, not a symbol allowlist, so it can't over-claim |
| `DATA_GAP` | Every other classified gap (`TEMPORAL_GAP`/`NO_DATA`/`LOW_FREQUENCY_SEGMENT`/`PARTIAL_DATA` from Q1.1) | A real, located, typed, severity-graded interval — never silently absorbed |
| `UNKNOWN_GAP` | Not a distinct code-level category — see below | |

**`UNKNOWN_GAP` was not implemented as a separate type.** Every gap this sprint's classifier produces already gets a specific, evidenced type (`DATA_GAP`'s four sub-types retain their real classification, not a generic "unknown" bucket) — introducing a fifth catch-all would mean either (a) it's never actually used, which is dead code, or (b) it starts absorbing gaps that *do* have a real classification just because no one looked closely, which is the opposite of this sprint's goal. If a future gap is found that genuinely resists classification by the existing rules, it will show up as `PARTIAL_DATA`/`TEMPORAL_GAP` (the correct fallback categories) rather than a fabricated "unknown" label that implies investigation happened when it didn't.

## What was found but NOT classified as a closure this sprint

Calendar-holiday-shaped gaps (Dec 24-25, Dec 31-Jan 1, recurring 2024/2025/2026 across multiple symbols) that don't start on a Thu/Fri/Sat and so aren't absorbed by `KNOWN_MARKET_CLOSURE`. These are visible, real, and plausibly holiday-driven — but confidently mapping specific calendar dates to specific named holidays for a CFD provider (rather than an exchange) was judged to cross the line into "pretending to know," especially since only 3-4 recurring instances per symbol were found (far short of the 74%+/500+-instance evidentiary bar that justified `EXPECTED_SESSION_BREAK`). Documented as a known limitation (`Q1.2_COMPLETE.md`), not silently absorbed and not invented.

## Stop condition check

Per the sprint's own Stop Condition #7 ("A holiday calendar cannot be established reliably → STOP"): a *complete* calendar could not be reliably established with the available evidence, and per instruction, that limitation is documented rather than worked around with an invented one. This did not require stopping the sprint — the hybrid policy above is the documented outcome, matching Option D/E's explicit allowance to "keep holidays as data gaps but clearly label them."

## Effect on the coverage model

`AUDIT_RULE_VERSION` bumped `q1.1-gap-rules-v1` → `q1.2-gap-rules-v2` (Q1.1.22's own versioning mechanism, used exactly as designed — a rule change is a new, detectable registry version, not a silent recalculation). `EXPECTED_SESSION_BREAK` gaps are excluded from "missing" time the same way `EXPECTED_MARKET_CLOSURE` gaps are, tracked separately (`sessionBreakCount`/`sessionBreakDays` per `DataCoverage` entry) so the exclusion is visible, not hidden. Real before/after coverage numbers: `Q1.2_COMPLETE.md` §2.
