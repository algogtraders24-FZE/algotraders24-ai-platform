## Target topology

```
Vercel
  ↓ HTTPS, Authorization: Bearer <QUANT_LITE_EXEC_SECRET>
Cloudflare Tunnel  (named tunnel, same one already carrying mt5.algotraders24.ai)
  ↓
127.0.0.1:8788  (the new execution service, localhost-only — verified bound this way in local testing)
```

**No new public VPS port.** The execution service binds to `127.0.0.1` only (confirmed in `quant_lite_execution_service.py`'s own default `--host 127.0.0.1`) — the only thing that ever needs to change at the network-boundary layer is adding one more ingress rule to the **same** tunnel already running, exactly the way a single `cloudflared` process can carry multiple hostnames.

## Proposed `cloudflared` config addition (illustrative — verify against the real file first)

A typical named-tunnel `config.yml` has an `ingress:` list of hostname→service rules. The MT5 bridge's own entry is presumably something like:

```yaml
ingress:
  - hostname: mt5.algotraders24.ai
    service: http://localhost:8787
  - service: http_status:404   # catch-all, must stay last
```

The proposed addition — one more rule, inserted **before** the catch-all, changing nothing about the existing `mt5.algotraders24.ai` entry:

```yaml
ingress:
  - hostname: mt5.algotraders24.ai
    service: http://localhost:8787
  - hostname: quant-lite-exec.algotraders24.ai
    service: http://localhost:8788
  - service: http_status:404
```

**This is a template, not a diff against the real file** — the actual existing config must be read first (`Q1.9_VPS_TOPOLOGY.md`'s and `Q1.9_SECURITY.md`'s already-prepared read-only inspection command) so the real hostname/rule ordering is respected exactly, not guessed.

## DNS

A named Cloudflare Tunnel's hostname routing is typically managed via `cloudflared tunnel route dns <tunnel-name> quant-lite-exec.algotraders24.ai` (creates the CNAME automatically) rather than manual DNS panel editing — the exact command depends on how the existing tunnel was originally provisioned, which this agent cannot see. Documented as the standard mechanism, not run.

## TLS

Automatic — Cloudflare Tunnel terminates TLS at Cloudflare's edge for every hostname it routes, same as the existing `mt5.algotraders24.ai` entry already benefits from. No certificate management needed on the VPS itself, matching the existing MT5 bridge's own zero-cert-management story.

## Reachability verification (once the route exists — not yet run)

```powershell
# From the VPS itself, confirm the local service first:
Invoke-RestMethod -Uri "http://127.0.0.1:8788/health"
# Then, once the tunnel route is added, from anywhere:
Invoke-RestMethod -Uri "https://quant-lite-exec.algotraders24.ai/health"

```

## No direct unauthenticated VPS exposure

`/health` is intentionally unauthenticated (matches the MT5 bridge's own documented reasoning — liveness only, no strategy/result data). Every other endpoint (`POST /backtest`, `GET /backtest/{jobId}`) requires the bearer token regardless of which hostname or network path reaches it — the auth check happens in the service itself, not just at the network boundary, so even if the tunnel or firewall configuration had a gap, the service's own `_require_secret()` is a second, independent gate.
