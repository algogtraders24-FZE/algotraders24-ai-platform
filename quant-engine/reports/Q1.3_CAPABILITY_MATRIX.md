# Q1.3 — Frozen Quant Lite Capability Matrix

This is the canonical, frozen reference for what Quant Lite's real execution backend supports, consolidating Q1.0's engine/data verification, Q1.1's gap-policy engine, and Q1.2/Q1.3's investigation and calibration work. It does not introduce new capability logic — it is a snapshot of what `frontend/data/quant-lite-capability.ts` (symbol/timeframe offering) and `frontend/data/quant-lite-gap-registry.ts` (per-request coverage/performance, via `coveragePolicy.ts`) already enforce, verified self-consistent by 65 new Q1.3 tests.

## Two complementary layers (not duplicated — Part 5 confirmed)

1. **Symbol-level capability** (`quant-lite-capability.ts`) — is this symbol/timeframe combination *offered* at all. Answers: SUPPORTED / CONDITIONALLY_SUPPORTED / not offered.
2. **Request-level coverage policy** (`coveragePolicy.ts::assessCoverage()`) — for an *offered* combination, is *this specific date range* good enough. Answers: SUPPORTED / SUPPORTED_WITH_WARNING / RESTRICTED / DATA_UNAVAILABLE, plus `performanceClass`/`performanceWarning`.

These answer different questions and were verified this sprint to never disagree about which symbols exist (`q13_tests.ts::capability.every_offered_symbol_has_registry_data`). No merge was needed or attempted.

## Performance class applicability (Layer 2)

Only `1m`/`5m` signal timeframes carry a large-run performance notice, and only beyond 365 requested days (confirmed, not moved, this sprint — `Q1.3_PERFORMANCE_BENCHMARK.md`). All other timeframes (15m/30m/1h/4h/1d) are `NORMAL` at any tested window (Q1.0's timeframe sweep, 3-35s at full-year windows).

## Per-request status (Layer 2, illustrative — computed live, not fixed)

Every request gets a real, specific `SUPPORTED`/`SUPPORTED_WITH_WARNING`/`RESTRICTED`/`DATA_UNAVAILABLE` verdict from `assessCoverage()`, independent of the symbol's whole-range status above. Examples verified this program:

- EURUSD_EXNESS, 2024-02-01→2024-03-01 (1h): `SUPPORTED`.
- XAUUSD_EXNESS, 2024-01-01→2024-12-31 (1h) — the Q0.9/Q1.1/Q1.2 MACD baseline: `RESTRICTED` (87.27% coverage, 28-day gap) — **unchanged this sprint, confirmed still correct** (Part 7).
- BTCUSD_EXNESS, 2024-09-01→2024-10-01 (1h) — inside its 155-day gap: `DATA_UNAVAILABLE`.

## API enforcement (Part 5)

Unchanged mechanism, re-verified: `validateBacktestRequest()` → `checkDataCoverage()` → `assessCoverage()` runs before `createJob()`/`submitJob()`. `DATA_UNAVAILABLE` blocks — no job created, no Python process spawned (verified by construction, unchanged since Q0.9/Q1.1). `RESTRICTED`/`SUPPORTED_WITH_WARNING` proceed with disclosure. `performanceClass`/`performanceWarning` are embedded in the same server-only assessment — a client cannot set or influence any of these fields (re-verified live via spoofed-request tests in Q1.1/Q1.2, mechanism unchanged in Q1.3).

## UI (Part 6)

`BacktestSetupForm`/`ResultsView` (via the shared `CoverageAssessmentPanel`) show symbol, timeframe, requested range, actual usable range, coverage %, largest gap, quality grade, policy status, and the performance notice when applicable — on both Setup (before submit) and Results (above the fold, including the `QUEUED`/`RUNNING` state). No user-requested date range is ever silently shortened — `actual` is always shown alongside `requested`, distinctly.
