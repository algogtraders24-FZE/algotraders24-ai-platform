# Q1.1 COMPLETE — Data Integrity, Gap Policy & Full-History Performance Hardening

**Verdict: Q1.1 PASS.**

Quant Lite now knows, and tells the user, exactly what period was requested, what period actually exists, how much of it is real, where the holes are, whether they're expected market closures or real provider gaps, and whether the resulting backtest is trustworthy as a continuous simulation — before the job runs (Setup) and after (Results). No result can look stronger than its underlying data.

## 1. Gap registry

Built from real `market.db` timestamps only (never config), across all 45 real symbol/timeframe pairs: `quant-engine/scripts/q11_gap_registry.py` → `quant-engine/output/q11_gap_registry.json` → `quant-engine/scripts/q11_generate_frontend_registry.py` → `frontend/data/quant-lite-gap-registry.ts` (server-only, ~2.9MB, never bundled to the browser). 15,764 real gap intervals found. Deterministic version hash `d233071da0c6cece` = `sha256(market.db sha256 + audit-rule version)[:16]` (Q1.1.22). **A real bug was caught and fixed during this sprint**: the first version of the audit script never compared gaps against each timeframe's own expected bar interval, so it flagged *every single normal bar-to-bar step* as a "gap" (0% coverage everywhere) — caught by sanity-checking the output before trusting it, fixed, re-run, verified sane. Full detail: `Q1.1_GAP_REGISTRY.md`.

## 2. Coverage model

Duration-based, not row-count-based (explicit instruction) — `expected_trading_time = calendar_time - real_market_closures`, `coverage% = covered/expected`. Weekly market closures detected empirically from the data itself (Thu/Fri/Sat-starting, 20-96 hour gaps), not assumed from a textbook calendar. Full formula and rationale: `Q1.1_GAP_POLICY.md`, `Q1.1_COVERAGE_SEMANTICS.md`.

## 3. Severity thresholds

`NONE/LOW/MEDIUM/HIGH/CRITICAL`, fixed in code before any per-symbol result was inspected: `TEMPORAL_GAP` ≤14d MEDIUM; `NO_DATA` 14-90d HIGH, >90d CRITICAL; `LOW_FREQUENCY_SEGMENT` (3+ consecutive weekly-shaped gaps merged into one interval) ≤30d MEDIUM else HIGH. Full table: `Q1.1_GAP_POLICY.md`.

## 4. Session/holiday handling

Weekly closures excluded from "missing" time entirely (`EXPECTED_MARKET_CLOSURE`, severity `NONE`). Individual public holidays are **not** modeled as a full exchange calendar — a holiday-extended weekend up to 4 days is absorbed by the same closure-detection window; longer ones are (correctly, conservatively) treated as real gaps. Documented explicitly, not hidden, in `Q1.1_GAP_POLICY.md`.

Longest clean contiguous stretch: 2024-01-01→2024-07-29 (~210 days). **CONDITIONALLY_SUPPORTED status confirmed correct**, now with quantified backing.
- **XAUUSD_EXNESS** (Q1.1.17): 55.73% whole-range coverage (1h). The ~169-day gap (2025-07-16→2026-01-01) and the Nov-Dec 2024 low-frequency stretch were both precisely located and classified — the latter is a real `LOW_FREQUENCY_SEGMENT` of exactly 28 days (Nov 24→Dec 22), flanked by separate 6-day and 10-day `TEMPORAL_GAP`s. **Neither period produces a "warning" — both push the containing request into RESTRICTED** once the request's largest gap exceeds 14 days (see finding #8 below).
- **XAUUSD_ZS_EXNESS** (Q1.1.18): 42.30% whole-range coverage — the most gap-affected symbol (313 gaps at 1h, several `LOW_FREQUENCY_SEGMENT`s of 35-70 days plus a 130-day `NO_DATA` gap). **CONDITIONALLY_SUPPORTED status confirmed correct.**

## 7. Coverage statuses (date-range policy)

Four-way `SUPPORTED / SUPPORTED_WITH_WARNING / RESTRICTED / DATA_UNAVAILABLE`, computed per specific request (not just per symbol) by `coveragePolicy.ts::assessCoverage()`. 25 automated scenario/boundary/status tests, all passing (`frontend/scripts/q11_gap_policy_tests.ts`). Thresholds and full decision table: `Q1.1_GAP_POLICY.md`.

## 8. API behavior

`GET /api/quant-lite/coverage` (new) — live, server-authoritative pre-submit check, called by Backtest Setup as the user edits dates. `POST /api/quant-lite/backtest` now computes and stores the assessment on job creation; only `DATA_UNAVAILABLE` blocks job creation (confirmed: no job created, no Python process spawned) — `RESTRICTED` and `SUPPORTED_WITH_WARNING` still execute, per instruction ("may still execute if technically possible"). Verified live: submitting a request with spoofed `dataQuality`/`resultDataQualityStatus` fields in the body was silently ignored — the server computed and stored its own real assessment (94.73%/SUPPORTED_WITH_WARNING) regardless of the claimed values (100%/SUPPORTED) (Q1.1.41).

## 9. UI behavior

`CoverageAssessmentPanel` (new, shared component) renders Requested/Actual/Coverage%/Largest gap/Gaps in range/Quality on both Backtest Setup (live, debounced, before submit) and Results (above the fold, alongside execution assumptions) — verified live in the browser for both a `RESTRICTED` case (real 83.13%/28-day-gap MACD-baseline window) and a `DATA_UNAVAILABLE` case (Run Backtest button correctly disabled). A `RESTRICTED` completed result additionally shows a fixed, unmissable "DATA QUALITY RESTRICTED" banner above the metrics — no fake/successful-looking result screen for a rejected request (Q1.1.33).

## 27. Known limitations

- No full exchange holiday calendar — a closure longer than 4 days (rare) is classified as a real gap rather than an expected holiday. Documented, not silently absorbed.
- USOIL_EXNESS's 1h-vs-4h/1d coverage discrepancy (6.91-point spread) is measured but not root-caused this sprint.
- No "large historical run" UI notice was implemented (Q1.1.27) — scoped out since no tested window approached the timeout; real benchmark numbers now exist to base one on in a future sprint.
- Gap registry is a static, versioned snapshot — refreshing after `market.db` grows is an explicit manual command (`q11_gap_registry.py` + `q11_generate_frontend_registry.py`), not automatic (by design, per instruction).
- `dataQuality` is optional on job/result types for backward compatibility with pre-Q1.1 job records (which genuinely lack it) — a real gap in the old data, not a defect in the new contract.
- No explicit job-cancellation endpoint exists (unchanged scope from Q0.9) — "cancellable" per Q1.1.43 refers to the existing hard timeout, not a user-initiated cancel.
