# Q1.5 Part 1 — Credential Rotation

**No secret values appear anywhere in this document, per instruction.**

## Status: BLOCKED (requires user action) — reported honestly, not falsely marked complete

Both credentials require action on a platform this agent has no account access to (Binance's own dashboard; Vercel's own token issuance), and entering/managing credentials on the user's behalf is outside this agent's permitted actions regardless of platform. Per this sprint's own explicit instruction ("If a credential cannot safely be rotated during this sprint: STOP and report BLOCKED"), this is reported as **BLOCKED**, not claimed as ROTATED/REVOKED.

## Binance API key / SEC_KEY

**Usage audit** (variable-name search only, no values printed): `frontend/lib/market-data/env.ts` and `frontend/lib/market-data/providers/binance.provider.ts` were checked directly. Finding, already documented in the codebase's own comments before this sprint: **`BinanceProvider` never reads `BINANCE_API_KEY` at all** — Binance's public market-data REST endpoints (`/ticker/24hr`, `/klines`, `/ticker/price`) require no API key or signature; only private/trading endpoints (order placement, account info — neither of which this codebase calls) need one. The `.env.local` line itself is additionally noted as malformed (two values concatenated onto one line rather than separate `BINANCE_API_KEY`/`SEC_KEY` variables).

**Practical implication**: this specific key has **zero functional impact on this application** whether rotated or not — nothing here reads or depends on it. This does not make rotation unnecessary (the key may be valid and tied to the user's real Binance account for something outside this codebase), only lower-urgency from this system's own perspective.

**Required user action** (cannot be performed by this agent): log into Binance's own API management dashboard, revoke the exposed key, and — only if some other system actually depends on it — generate a replacement and update wherever that other system reads it. Nothing in this codebase needs updating either way, confirmed by the usage audit above.

## Vercel OIDC token

**Usage audit**: found only in `frontend/.env.local`, added automatically by the Vercel CLI (`vercel env pull` / `vercel dev`) for local-dev authentication to Vercel-hosted resources — not a credential any application code in this repo reads directly.

**Practical implication**: Vercel OIDC tokens are short-lived by design (auto-issued, auto-expiring, refreshed automatically on the next CLI invocation) — not a static secret a user manually rotates. Given the elapsed time since the Q0.9 exposure (multiple sprints, multiple days), the specific exposed token has very likely already expired on its own. This agent cannot verify its current validity without either printing it (prohibited) or querying Vercel's API on the user's behalf (an account-touching action requiring their own authentication).

**Required user action** (optional, low-urgency): if the user wants certainty rather than relying on natural expiry, running `vercel env pull` or `vercel dev` again locally will silently issue a fresh token, superseding the exposed one — no manual "revocation" step exists for this token type on Vercel's side.

## What was verified safe

- `.env.local` was never committed to git — confirmed via `git log --all --full-history` (empty result) across the entire repository history, and confirmed still `.gitignore`d.
- No report, script, or generated file produced by this agent (across every sprint, Q0.9 through Q1.4) contains either credential's value — the exposure was confined to that one session's live tool-output stream, never written to a persisted file this agent controls.
- No command was run this sprint that echoes, greps for, or otherwise surfaces the actual values — only variable *names* were searched for, and only file paths (not contents) were inspected where values could appear.

## Q1.5 verdict on Part 1

**BLOCKED.** The rotation actions this sprint's checklist requires (revoke the Binance key on Binance's dashboard; optionally force-refresh the Vercel OIDC token via the CLI) are both actions only the user can take. This agent has completed everything it safely can: confirmed neither credential is functionally load-bearing for anything this agent can fix in code (Binance: unused by design; Vercel: self-expiring), confirmed no further leakage occurred, and given the user clear, actionable next steps. Recommend the user perform the Binance revocation directly — it takes under a minute on Binance's own site — before this sprint's Part 1 can be marked ROTATED rather than BLOCKED.
