# Q1.1 — Gap Policy

## Gap types (Q1.1.2)

| Type | Meaning |
|---|---|
| `EXPECTED_MARKET_CLOSURE` | A normal weekly (or holiday-adjacent) closure - not a real gap, excluded entirely from "missing" time |
| `NO_DATA` | A large, unexplained span with zero rows |
| `TEMPORAL_GAP` | An isolated, moderate unexplained span (3-14 days) |
| `LOW_FREQUENCY_SEGMENT` | Rows exist but density collapsed far below expected - a run of 3+ consecutive near-weekly-only bars |
| `PARTIAL_DATA` | A small (<3 day), irregular, non-closure-shaped gap |
| `OUTSIDE_COVERAGE` | The requested date falls entirely outside the symbol/timeframe's recorded range (a request-time classification, not a stored gap interval) |

## Session model (Q1.1.13)

Every `_EXNESS` symbol except BTCUSD closes weekly (standard FX/CFD convention); BTCUSD trades continuously (`sessionModel: CONTINUOUS`). The weekly closure window is detected empirically from real data (not assumed from a textbook calendar): a gap starting Thursday/Friday/Saturday and lasting 20-96 hours is classified `EXPECTED_MARKET_CLOSURE`. The 96-hour (4-day) upper bound is wide enough to absorb a holiday-extended weekend (e.g. a Friday-Monday closure) without swallowing a genuine multi-week provider outage.

**Not modeled**: a full exchange holiday calendar (specific dates for Christmas, Good Friday, etc.). This is an explicit, documented simplification - a holiday that falls entirely within the 96-hour window is correctly absorbed as an expected closure; one that extends further (rare) would be classified as a real `TEMPORAL_GAP`/`NO_DATA` instead of `EXPECTED_MARKET_CLOSURE`, which is the conservative (not overly generous) direction to be wrong in.

## Severity model (Q1.1.3) — thresholds fixed before any symbol's result was inspected

| Gap type | Severity rule |
|---|---|
| `EXPECTED_MARKET_CLOSURE` | Always `NONE` |
| `PARTIAL_DATA` | Always `LOW` |
| `TEMPORAL_GAP` | `MEDIUM` if ≥3 days (by construction, all `TEMPORAL_GAP` entries are ≥3 days - see gap-type boundary below) |
| `LOW_FREQUENCY_SEGMENT` | `MEDIUM` if segment ≤30 days, `HIGH` if longer |
| `NO_DATA` | `HIGH` if 14-90 days, `CRITICAL` if >90 days |

Gap-type boundary logic (`quant-engine/scripts/q11_gap_registry.py::classify_gap`): a gap ≤1.5x the timeframe's own expected bar interval is not a gap at all (ordinary jitter). Beyond that, up to 3 days and not closure-shaped → `PARTIAL_DATA`; 3-14 days → `TEMPORAL_GAP`; >14 days → `NO_DATA` (severity by duration above); a run of ≥3 consecutive ~168-hour (weekly-shaped) gaps is instead merged into one `LOW_FREQUENCY_SEGMENT` regardless of individual gap size.

## Coverage ratio (Q1.1.4)

**Never** `rows / expected_rows` - deliberately avoided per instruction, since timeframe density and session calendars differ. Instead:

```
expected_trading_seconds = total_calendar_seconds - sum(EXPECTED_MARKET_CLOSURE durations)   [WEEKLY_CLOSURE symbols]
                          = total_calendar_seconds                                              [CONTINUOUS symbols, i.e. BTCUSD]
missing_trading_seconds  = sum(duration of all non-closure gaps overlapping the range)
coverage_pct              = (expected_trading_seconds - missing_trading_seconds) / expected_trading_seconds * 100
```

This is duration-based, not row-based, so it is identical in principle whether the underlying timeframe is 1m or 1d (confirmed live: a request that shows ~97% coverage at 1h shows the same ~96-97% at 1m for EURUSD_EXNESS - Q1.1_COVERAGE_SEMANTICS.md has the full cross-timeframe table).

## Contiguous coverage (Q1.1.5)

| Classification | Rule |
|---|---|
| `FULL_CONTIGUOUS` | coverage ≥98% AND largest gap ≤3 days |
| `FRAGMENTED` | largest gap >30 days, OR largest gap >20% of the requested range's own duration - **regardless of overall coverage %** (this is the explicit rule preventing "90% coverage with one huge central gap" from being treated as a normal 90% sample) |
| `NO_OVERLAP` | 0% coverage |
| `PARTIAL_CONTIGUOUS` | everything else |

## Date-range policy (Q1.1.6) — `services/quant-lite/backend/coveragePolicy.ts::assessCoverage()`

| Policy | Condition |
|---|---|
| `DATA_UNAVAILABLE` | coverage <40%, or `NO_OVERLAP` |
| `RESTRICTED` | `FRAGMENTED`, or coverage <80%, or the single largest gap in range exceeds 14 days |
| `SUPPORTED` | `FULL_CONTIGUOUS` and coverage ≥98% |
| `SUPPORTED_WITH_WARNING` | everything else (i.e. real but minor gaps present) |

**Threshold rationale**: 98%/3-day for unqualified SUPPORTED reflects "a user could reasonably assume this is a normal continuous backtest." 80%/14-day marks where a result stops being safely comparable to a normal one. 40% is the floor below which a backtest is more hole than data. These were fixed while writing `coveragePolicy.ts`, before running it against any real symbol - not adjusted afterward. One concrete consequence, reported honestly rather than smoothed over: the Q0.6/Q0.9 MACD baseline's own request (XAUUSD_EXNESS, 2024-01-01→2024-12-31) is **RESTRICTED** under these rules (83.13% coverage, a real 28-day gap from the Nov-Dec 2024 low-frequency stretch) - this did not motivate loosening the thresholds; the trade metrics themselves are completely unaffected (verified in `Q1.1_COMPLETE.md` Part 13/regression), only the metadata attached to that result changed.

## Never silently continues (Q1.1.11)

The engine (`execution_mtf.py`) still has no gap awareness and never will in this sprint (see `Q1.1_COVERAGE_SEMANTICS.md` "Gap-Aware Execution Boundary"). What changed: every gap the engine silently traded through is now captured in the requested job's `dataQuality` assessment, attached to the job record at creation and to the final result's `provenance.dataQuality` - visible in the API response and rendered in the UI (Setup, before submit; Results, above the fold) every time, not just when something looks wrong.
