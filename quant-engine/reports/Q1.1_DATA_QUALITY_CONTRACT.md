# Q1.1 — Data Quality Contract

## Types (`frontend/types/quant-lite-coverage.ts`)

- **`DataCoverage`** — one per (symbol, timeframe): session model, real min/max timestamp, row count, whole-range coverage %, gap count, largest gap, and the full list of `GapInterval`s. Generated data, never hand-edited (`data/quant-lite-gap-registry.ts`).
- **`GapInterval`** — `{ symbol, timeframe, start, end, durationDays, gapType, severity }`. One per real, located gap.
- **`CoverageAssessment`** — the result of judging one *specific* requested date range against the registry: requested vs. actual usable period, covered/missing duration, coverage %, largest gap and gap count *within that range*, `ContiguousCoverage`, the four-way `DateRangePolicy`, `worstSeverity`, a human message, and the registry/audit-rule versions that produced it (Q1.1.21/22).
- **`DataQualityGrade`** — `NONE | LOW | MEDIUM | HIGH | CRITICAL`.

## Server-authoritative (Q1.1.41)

`CoverageAssessment` is computed exactly once per request, server-side, in `coveragePolicy.ts::assessCoverage()` - a pure function over the real registry, taking only `(symbol, timeframe, start, end)`. Nothing in the request body can set a coverage status, gap registry value, quality grade, or performance classification directly; a client can only supply the inputs that get looked up, never the outputs. The full ~2.9MB generated registry (`data/quant-lite-gap-registry.ts`) is imported only by this module and by API routes - never by a `"use client"` component, so it is never sent to the browser; the client only ever receives the small `CoverageAssessment` result via `GET /api/quant-lite/coverage` or embedded in a job/result response.

## Where it lives

| Stage | Field |
|---|---|
| Live pre-submit check | `GET /api/quant-lite/coverage` response (not persisted) |
| Job creation | `BacktestJobRecord.dataQuality` (set once, at `POST /api/quant-lite/backtest`, never recomputed) |
| Job polling | `GetBacktestJobResponse.dataQuality` (visible even while `QUEUED`/`RUNNING`) |
| Completed result | `BacktestResult.provenance.dataQuality` (carried through unchanged from the job record) and `BacktestResult.resultDataQualityStatus` (`NORMAL` or `DATA_QUALITY_RESTRICTED`, Q1.1.10) |

## No false quality (Q1.1.42)

- A `RESTRICTED` result is never relabeled `SUPPORTED`, and partial coverage is never presented as full coverage - the UI (`CoverageAssessmentPanel`) always renders the real `coveragePct`/`largestGapDays`/`policy` values, with no rounding-up or friendlier substitute copy.
- The pre-existing `LEGACY-BACKTEST-EVIDENCE` library badge (Q0.8) is untouched by this contract - it was never claiming "Verified" in the first place, so nothing needed reconciling there.
- A completed job whose data quality later turns out to have been `RESTRICTED` still shows the `DATA QUALITY RESTRICTED` banner permanently on its Results page - the flag is stored on the result, not recomputed live (so a future gap-registry refresh cannot retroactively change how an old result is labeled without a new job).

## Backward compatibility

Job records created before Q1.1 (Q0.9/Q1.0) predate this field entirely - `dataQuality` is typed `CoverageAssessment | undefined` on `BacktestJobRecord`/`GetBacktestJobResponse`/`mapEngineOutputToResult`'s parameter, honestly reflecting that real stored data, rather than a type that promises a guarantee old records don't meet. Every job created from Q1.1 onward always has it set (enforced in `route.ts` - a request cannot reach `createJob()` without a real `CoverageAssessment` in hand).
