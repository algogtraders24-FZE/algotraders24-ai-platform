## Full Vercel → adapter → service round trip (a distinct, separate test from the two above)

A real request through the **actual, unmodified** `POST /api/quant-lite/backtest` route, with `QUANT_LITE_EXEC_SERVICE_URL` pointed at the locally-running service, produced:

```
Trades: 250, Win rate: 36.8%, Profit factor: 1.16, Return: +26.64%,
Final balance: $12,664.00
```

This used a deliberately distinct RSI threshold (not one of the 3 established golden strategies) specifically so it couldn't be a stale cached result — its purpose was to prove the **full software path** (`POST /api/quant-lite/backtest` → `executionAdapter.ts` → HTTP → service → `run_backtest_job.py` → `execution_mtf.py` → `market.db` → HTTP response → `mapEngineOutputToResult` → job store → `GET /api/quant-lite/backtest/[jobId]` → real browser render), not to re-prove baseline parity (already covered by the MACD/RSI/EMA cases above). Confirmed live in the browser: the Results page rendered every metric, the equity curve, and the trade ledger correctly — **real data from the (locally-proxied) VPS, not a fixture**.

## `requestHash`/`resultHash` semantics through the new path

`requestHash` is computed identically regardless of execution path (`requestHash.ts`'s `computeRequestHash()` runs before the adapter branches to local vs. remote — unchanged code, so no difference is possible by construction). `resultHash` is the service's own `provenance.resultHash`, computed by the unmodified `run_backtest_job.py` exactly as it always has been — the only "allowed difference" versus a purely local run is that this value now travels over one extra HTTP hop before reaching the job store, which does not alter the hash itself (confirmed: the hash was checked byte-for-byte identical in Q1.10's own direct-script testing for the same specs, and this sprint's HTTP-wrapped runs used the same underlying script unmodified).
