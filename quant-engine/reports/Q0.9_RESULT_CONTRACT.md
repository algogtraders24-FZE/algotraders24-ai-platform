# Q0.9 — Result Contract

## Division of labor

`run_backtest_job.py` writes a raw, engine-native JSON (snake_case, shaped directly by `engine.summarize()`'s own stats dict plus the trade ledger — see `Q0.9_EXISTING_EXECUTION_PATH.md`). `frontend/services/quant-lite/backend/resultMapper.ts::mapEngineOutputToResult()` is the **only** place that translates this into the frontend's frozen `BacktestResult` contract (`types/quant-lite.ts`, Q0.7/Q0.8) — replacing the one-off hand-mapping `quant-engine/scripts/q08_gen_frontend_data.py` did for a single static sample.

## Null semantics (preserved from Q0.8, unchanged)

A metric the engine genuinely doesn't compute stays `null` all the way to the UI, which renders "Not available" — never `0`. `sharpe` is not part of `BacktestMetrics` (the type never had it) and no fabricated value was added; `slPrice`/`tpPrice` on each trade stay `null` (the engine doesn't record the SL/TP level in force at exit time — irrelevant for Quant Lite since breakeven/trailing are always off, but the field genuinely isn't in the trade dict).

## Real capability gained vs. Q0.8

`winningTrades`, `losingTrades`, `averageTrade`, `largestWin`, `largestLoss` were hardcoded `null` in Q0.8's mock because `engine.summarize()` never computes them. Now that a real trade ledger is available per job, `resultMapper.ts::computeMetrics()` computes all five for real — a plain aggregate over real trade rows (wins/losses/max/min/average), not fabrication. Verified live: the MACD regression job showed `winningTrades: 91, losingTrades: 117, largestWin: 188.92, largestLoss: -126.08, averageTrade: 9.43` — internally consistent with `tradesTotal: 208` and `winRatePct: 43.75%` (91/208 ≈ 43.75%).

## accountBlown

Passed straight through from the engine's own `account_blown` boolean (`execution_mtf.py:223`, set only when `balance <= 0`) — never inferred from drawdown magnitude, trade count, or any other heuristic, per Q0.9.15's explicit instruction.

## Equity curve

`equityCurve` in the raw engine output is trade-by-trade balance observations (`initialCapital` at `time: "start"`, then one point per trade close) — **not** the engine's full per-minute equity series (which can be hundreds of thousands of points for a year of 1m data). The frontend's `EquityCurveChart` component already derives its plot from `trades[].balanceAfter` directly (a Q0.8 design decision, unchanged), so this is consistent, real, and not a fabricated downsample — every point is an actual balance after an actual trade closed.

## Trade ledger

Full ledger returned per job — `tradeNumber, direction (BUY/SELL), entryTime, entryPrice, exitTime, exitPrice, exitReason (SL/TP/PARTIAL), pnl, balanceAfter`. `balanceAfter` is computed in `run_backtest_job.py` as a running cumulative sum starting from `initialCapital`, in the same chronological order the engine itself appends trades — mathematically identical to the engine's own internal `balance` variable at each trade close.
