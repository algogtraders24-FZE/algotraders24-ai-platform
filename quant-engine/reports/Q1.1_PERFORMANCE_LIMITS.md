# Q1.1 — Performance Classification & Limits

## Classification (Q1.1.25) — defined AFTER measurement, from the real numbers in `Q1.1_PERFORMANCE_BENCHMARK.md`

| Class | Elapsed time | Meaning |
|---|---|---|
| `FAST` | <15s | 1-month windows at either timeframe |
| `NORMAL` | 15-45s | Up to ~1 year at either timeframe |
| `SLOW` | 45-100s | Full-history runs at 1m/5m |
| `LIMITED` | >100s | Not observed this sprint at any tested window |

No window tested this sprint reached `LIMITED`. The classification exists so a future window that does can be labeled without inventing a new scale mid-flight.

## Maximum safe window (Q1.1.26)

Per instruction, **no range is blocked without evidence of an actual problem** - nothing tested this sprint failed, timed out, or came close to the existing 180s job timeout (the slowest run used 81.6s, under half the budget). Recommended UI guidance, not a hard limit:

| Signal timeframe | Recommendation |
|---|---|
| 1m | Full history (~2.6 years) completes in ~80s and ~1.7GB peak memory - fine for the current single-job-at-a-time-per-slot deployment (Q0.9's `MAX_CONCURRENT_BACKTESTS=2`), worth a "large historical run" notice above ~1 year (Q1.1.27) |
| 5m | Full history completes in ~70s and ~1GB peak - same guidance, slightly more headroom than 1m |
| 15m/30m/1h/4h/1d | Not re-benchmarked this sprint (Q1.0's timeframe sweep already showed these complete in 3-35s at their tested windows, well inside `FAST`/`NORMAL`) |

## UI performance behavior (Q1.1.27)

`ExecutionAssumptionsPanel`/Backtest Setup do not currently render a "large historical run" notice - **this was not implemented in Q1.1**, scoped out given every measured case stayed well within `NORMAL`/`SLOW` and none approached the timeout. Adding an honest, measured-not-promised runtime estimate (e.g. "this may take up to ~90 seconds" for a 1m/full-history combination) is a clear, low-risk Q1.2 candidate now that real numbers exist to base it on - listed in `Q1.1_COMPLETE.md`'s Q1.2 recommendation rather than guessed at here.

## Performance safety (Q1.1.43)

All inherited unchanged from Q0.9/Q1.0, re-confirmed still true: the existing hard timeout (`SIGTERM` then `SIGKILL` after a grace period) still applies to every job regardless of gap-policy outcome; jobs remain cancellable only by that timeout (no explicit user-cancel endpoint exists, unchanged scope); no orphan process was observed across any of the 10 benchmark runs or the earlier gap-policy/API tests (`tasklist` checked clean after each); result state is written atomically as one JSON file per job (`jobStore.ts`, unchanged) so a crash mid-write cannot corrupt a previously-completed result.
