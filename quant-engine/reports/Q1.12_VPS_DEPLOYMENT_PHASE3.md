# Q1.12 Phase 3 — Persistent Process Management

## Status: PASS — real, deployed, verified live this sprint, after fixing two real deployment bugs

## Mechanism: Windows Task Scheduler, same pattern as `AT24-MT5-Bridge`

`AT24-QuantLite-ExecService` — `AtStartup` trigger, runs as `SYSTEM` (`LogonType ServiceAccount`, no login required ever), `RestartCount 999`/`RestartInterval 1 minute` (auto-restart on crash), `StartWhenAvailable`. Not a new mechanism — the same one `mt5-bridge/README.md` already documents and this VPS already runs successfully for `AT24-MT5-Bridge`/`AT24-MT5-Tunnel`.

## Two real bugs found and fixed during deployment, live

1. **`New-ScheduledTaskSettingsSet -Restart` is not a valid parameter** (ambiguous with `-RestartOnIdle`) — this repo's own draft script had it wrong. Caught immediately from the real PowerShell error, corrected to just `-RestartCount`/`-RestartInterval` (which alone are sufficient to configure restart-on-failure).
2. **A stale process survived `Stop-ScheduledTask`**: the original service process (PID 4888, first started when the task was registered) never actually terminated when `Stop-ScheduledTask` was called — twice — meaning two rounds of "fix the secret, restart, retest" silently kept hitting the *same* long-lived process with its *original* (wrong-length) secret still loaded in memory, since environment variables are read once at process start, never live-reloaded. Diagnosed by comparing the listening process's own `StartTime` against when the restart commands were issued — confirmed they never changed. Fixed with a direct `Stop-Process -Id 4888 -Force`, then a fresh `Start-ScheduledTask` produced a genuinely new PID (1580) with a current `StartTime`.

**Documented risk for the future**: `Stop-ScheduledTask` not reliably terminating a uvicorn/FastAPI process is a real operational characteristic of this specific setup, not a one-off fluke — worth remembering for any future restart (a config change, a version upgrade) rather than assuming `Stop-ScheduledTask` alone is sufficient.

## Also caught: a secret-generation/paste bug, unrelated to the scheduling mechanism itself

`secrets.token_urlsafe(32)` always produces exactly 43 characters. The first attempt to set `QUANT_LITE_EXEC_SECRET` resulted in a stored length of 45 (a paste including extra characters), then a second attempt accidentally pasted this agent's own template placeholder text literally (37 characters) instead of the generated value. **The 43-character value from that first flawed attempt was also treated as compromised** (it appeared in the visible terminal output pasted back into this conversation) and never reused — a fresh secret was generated for the value that ultimately went live. Final verification: length 43, confirmed correct, **never itself pasted into this conversation** (only the length, and success/failure of requests using it).
