# Q1.6 Part 1 — Existing Website & Quant Lite UI State (Audit)

Performed before any modification, per instruction. Everything below reflects the state of the codebase at the start of this sprint.

## Site structure

`frontend/app/` routes (top-level, non-exhaustive of dynamic segments): `(auth)/` (login/signup/forgot-reset), `api/**`, `auth/callback`, `company/{about,contact,disclaimer,vision}`, `dashboard/**` (12 authenticated sub-areas: admin, agents, assistant, automation, billing, knowledge, licenses, market-intelligence, memory, news, orders, publishing, purchases, signals, trading-copilot, workspace), `marketplace/**`, `platform/**` (assistant, knowledge-base, market-intelligence, publishing, research, workspace), `pricing`, `products/**`, `quant-lite/**`, `resources/**`, `solutions/**`.

`app/quant-lite/` already had a **complete, functional route tree** before this sprint:

## The one real gap found: navigation reachability

**Quant Lite had zero entry point anywhere in site navigation** - confirmed by grepping `Navbar.tsx`, `Footer.tsx`, the homepage (`app/page.tsx`), `PlatformOverview.tsx`, and `/pricing` for any `quant-lite`/`Quant Lite` reference: **zero matches everywhere**. The only way to reach it was to already know the `/quant-lite` URL. This is the single biggest, clearest Part 2 gap this sprint needed to close.

## Homepage

`app/page.tsx` is a deliberately curated 7-section page (Hero, TrustStrip, PlatformOverview, FeaturedMarketplace, PricingTeaser, FAQ, CTA, Footer) - explicitly documented in its own comments as compressed by Sprint D2.4.A3 specifically so a first-time visitor understands the platform in 2-3 scrolls, leaning on dedicated pages for depth rather than repeating it on the homepage. `PlatformOverview.tsx`'s 6-card grid is likewise explicitly documented as a **curated subset**, not the full breadth (AI News, Trading Copilot, Automation, and AI Agents are real, live features that are *not* shown there either). Given this established discipline, adding Quant Lite as a 7th homepage card or an 8th section would go against the page's own stated design intent and this sprint's "do not rewrite unrelated website sections" instruction - so the fix applied is at the navigation layer instead (see `Q1.6_COMPLETE.md` Part 3), not the homepage.

## Navigation

`Navbar.tsx`: 7 top-level items before this sprint (`Products`, `Marketplace`, `Platform` [dropdown], `Solutions` [dropdown], `Pricing`, `Resources` [dropdown], `Company` [dropdown]), plus `Login`/`Ask the AI Assistant`. Desktop: hover/focus dropdowns. Mobile (`<lg`, 1024px breakpoint): hamburger → accordion sheet. No `href="#"` placeholders anywhere (an established, enforced discipline per the file's own comments).

`Footer.tsx`: the deliberate "full Binance-style 8-category taxonomy" (Products, Platform, Solutions, Resources / Company, Developers, Legal, Account) in a fixed 4-column × 2-row grid. Every linked item resolves to a real page; every unbuilt one renders a disabled "Soon" badge, never an invented page.

## Authentication state

`app/(auth)/` has real login/signup/forgot-password/reset-password pages, and `app/auth/callback` handles an OAuth-style callback. **No custom `middleware.ts` exists anywhere in the frontend** (confirmed via `find`); the "Proxy (Middleware)" line in the build output is a Next.js-internal artifact, not a project-authored auth gate. **Zero auth integration exists in any `app/quant-lite/**` file** - confirmed via grep for `requireAuth`/`getServerSession`/`redirect(...login`/`useAuth`/Supabase-client-auth patterns across the whole `quant-lite` tree: no matches. Every Quant Lite page is fully public today. The Navbar shows a static `Login`/`Create Account` pair regardless of session state (not conditionally rendered) - a pre-existing site-wide pattern, not something this sprint needed to change.

## Design system

One shared primitive set (`components/ui/{Button,ButtonLink,Card,Badge,Input,Select,EmptyState,Table,Spinner}.tsx`) used consistently by every Quant Lite screen already - no parallel/duplicate styling system was found. Dark theme only (`bg-ink`/`text-text` tokens), Tailwind utility classes throughout, no CSS-in-JS. `components/ui/financial-typography.ts` centralizes the up/down/neutral color convention for numeric values (return, drawdown, PnL) - used identically in Quant Lite and the rest of the platform.

## Responsive behavior (pre-existing)

Every Quant Lite page already used the same responsive Tailwind patterns as the rest of the site (`grid-cols-2 sm:grid-cols-3 lg:grid-cols-6` etc., `lg:flex`/`lg:hidden` for the nav breakpoint) - nothing Quant-Lite-specific was found that diverged from the site's existing responsive conventions.

## CTA patterns

Established site-wide convention: `ButtonLink` (primary/secondary variant) for navigational CTAs, plain underlined `Link` for secondary in-page navigation. Quant Lite's builder/backtest/results/upgrade pages already followed this convention correctly before this sprint.

## Upgrade flow

Already real and honest (see `/quant-lite/upgrade` above) - correctly scoped as informational-only per the Q0.8 sprint's own explicit instruction, no payment logic, `at24-quant-engine/` never opened to build it.

## Conclusion

Quant Lite's actual functional UI (builder → setup → running → results → assumptions → codegen → download) was **already fully built and largely polished** going into this sprint - the real, concrete gap was reachability (no navigation entry point) plus several smaller content gaps against this sprint's explicit checklist (missing "Average Trade" metric despite being server-computed; landing page missing the explicit How-It-Works/Free-Features sections the brief calls out). See `Q1.6_COMPLETE.md` for exactly what was changed to close these.
