# Q0.5 — Engine Inventory

Read-only inspection of the three backtest engines. No engine was
modified. Where behavior could not be proven from source without
running code, it was verified by execution this sprint (cross-engine
test, synthetic tests) rather than inferred — every AMBIGUOUS item below
is one where even that wasn't sufficient.

---

## 1. `runner.py` (`spec_engine/runner.py`, 147 lines)

- **Entry point:** `run_spec_backtest(df, spec, risk)`.
- **Input format:** one `pd.DataFrame` at the spec's own timeframe
  (`ts, open, high, low, close`).
- **Data source / loading:** none — takes a pre-loaded DataFrame; the
  caller is responsible for sourcing it (typically
  `data_import.py::load_candles()` or a direct `market.db` query).
- **Timeframe handling:** single timeframe only — signal and execution
  both operate on the same bars.
- **Indicator calculation:** `indicators.py::compute_all()`, called once
  up front, vectorized over the whole df.
- **Signal timing:** evaluated once per row, `evaluate_entry(spec,
  rows[i], rows[i-1])` — one signal-timeframe bar per loop iteration.
- **Order creation / fill:** synchronous with signal detection — the
  same iteration that detects a signal opens the position, at
  `rows[i]["close"] ± spread/2`.
- **SL/TP:** ATR-mult or fixed price-distance, computed once at entry,
  checked every iteration against that iteration's own bar `high`/`low`.
- **Spread:** static `risk.spread_price`, caller-supplied constant.
- **Slippage:** none.
- **Commission:** none.
- **Position sizing:** `risk_money / (sl_dist × contract_size)`, floor
  0.01 lot.
- **Account handling:** `balance` updates on realized PnL only;
  `account_blown` guard (Q0.2 fix) halts new entries once `balance<=0`.
- **Multiple positions:** single position at a time
  (`if position is not None: continue`).
- **Same-bar behavior:** SL-wins tie-break when a single bar's range
  touches both SL and TP.
- **Intrabar behavior:** none modeled beyond the bar's own high/low —
  no sub-bar resolution at all.
- **MTF (multi-timeframe) behavior:** **not applicable** — this engine
  has no execution-timeframe concept, signal and fill are the same bar.
- **Session handling:** not implemented (confirmed absent — no
  `session_start`/`in_session` reference anywhere in the file).
- **Error handling:** `validate_spec()` errors raise `ValueError`
  upfront; `len(df)<50` returns an empty, well-formed result; no broad
  try/except around the main loop.
- **Determinism:** confirmed this sprint — byte-identical across 2 runs,
  both MACD and Bollinger, on real `XAUUSD_EXNESS` 2024 data.
- **Output format:** `(trades_df, equity_series, stats_dict)`.
- **Dependencies:** `quant_engine.engine.RiskConfig`/`summarize`,
  `.indicators`, `.interpreter`, `.schema`.

## 2. `execution_mtf.py` (`spec_engine/execution_mtf.py`, 212 lines)

- **Entry point:** `run_spec_backtest_mtf(df_signal, df_exec, spec, risk)`.
- **Input format:** two DataFrames — `df_signal` (spec's own timeframe,
  same shape as `runner.py`'s input) and `df_exec` (finer granularity,
  typically 1-minute, optionally with a `spread` column).
- **Data source / loading:** none — both DataFrames are caller-supplied.
- **Timeframe handling:** genuinely multi-timeframe — signals computed
  from `df_signal`, fills/SL/TP/position management resolved against
  `df_exec`.
- **Indicator calculation:** same `compute_all()` call, on `df_signal`
  only.
- **Signal timing — CONFIRMED BUG, see
  [`Q0.5_CROSS_ENGINE_MATRIX.md`](Q0.5_CROSS_ENGINE_MATRIX.md) for full
  evidence:** a signal bar is treated as "closed" the instant an
  execution-timeframe row's timestamp reaches `>=` that bar's own
  timestamp (`execution_mtf.py:114`, `while sig_ptr < len(sig_rows) and
  sig_ts[sig_ptr] <= ts_i`). Because `market.db`'s candle timestamps are
  left-labeled (bar **start**, not close — confirmed in
  `scripts/import_exness.py`'s `resample(..., label="left")`), this
  fires **up to one full signal-bar-period before that bar's close is
  actually known**, using indicator values that require the bar's close
  to be valid. Proven both on real data (MACD trade #3, this sprint's
  cross-engine test) and via a controlled synthetic scenario (entry at
  minute 0 of a jump bar, at the pre-jump price).
- **Order creation / fill:** at the first execution-timeframe row at or
  after the (mistimed) signal-close moment, using that row's real price
  and spread.
- **SL/TP:** same formula as `runner.py`, computed once at entry using
  `latest_atr` (the most recently "closed" — per the same mistimed
  logic — signal bar's ATR).
- **Spread:** real, per-minute average from `df_exec`'s `spread` column
  (`candle_spread` table in `market.db`), falls back to
  `risk.spread_price` if absent.
- **Slippage:** none.
- **Commission:** `commission_per_lot` hook added this program, always
  `0.0` in practice (`RiskConfig` has no such field).
- **Position sizing:** identical formula to `runner.py`.
- **Account handling:** same `account_blown` guard (Q0.2 fix).
- **Multiple positions:** single position at a time, same pattern.
- **Same-bar behavior:** SL-wins tie-break, resolved per execution-row
  (minute), counted via `same_minute_sl_tp_conflicts`.
- **Intrabar behavior:** resolved at 1-minute granularity for SL/TP —
  a real improvement over `runner.py` for *that* specific behavior,
  independent of the signal-timing bug above.
- **MTF behavior:** this is the engine's whole purpose — see the
  Signal timing entry above for its confirmed defect.
- **Session handling:** not implemented (confirmed absent, same as
  `runner.py`).
- **Error handling:** same three guards as `runner.py`
  (validation/insufficient-data/division-guards), no broader try/except.
- **Determinism:** confirmed this sprint — byte-identical across 2 runs,
  both specs.
- **Output format:** same 3-tuple as `runner.py`, plus
  `same_minute_sl_tp_conflicts` and `account_blown` in `stats`.
- **Dependencies:** same as `runner.py`.

## 3. `execution_tick.py` (`spec_engine/execution_tick.py`, ~210 lines)

- **Entry point:** `run_spec_backtest_tick(df_signal, spec, risk,
  zip_symbol, csv_symbol, years, downloads_dir=...)`.
- **Input format:** `df_signal` (same shape as the other two engines)
  **plus** `zip_symbol`/`csv_symbol`/`years` — execution data is **not**
  a DataFrame parameter at all.
- **Data source / loading:** execution ticks are streamed live from the
  Exness zip archives (`scripts/import_exness.py::iter_tick_chunks`) —
  **not** from `market.db`. This is a structural difference from the
  other two engines with a direct consequence for testability (§ below).
- **Timeframe handling:** signal timeframe (`df_signal`) + true,
  unaggregated tick-level execution.
- **Indicator calculation:** same `compute_all()` on `df_signal`.
- **Signal timing — SAME CONFIRMED BUG as `execution_mtf.py`:**
  identical `while sig_ptr < len(sig_rows) and sig_ts[sig_ptr] <= ts_i`
  pattern at `execution_tick.py:105`, same left-labeled-timestamp
  mismatch, same consequence. Confirmed by the near-exact match between
  `execution_mtf.py`'s and `execution_tick.py`'s trade #3 in this
  sprint's real-data comparison (same date, same direction, same reason,
  same PnL to within tick-level precision).
- **Order creation / fill:** at the exact real tick that triggers the
  (mistimed) signal check, using that tick's real Ask (buy) or Bid
  (sell).
- **SL/TP:** same formula, checked against real bid/ask on the correct
  side per direction (closing a long checks Bid, closing a short checks
  Ask) — the most realistic of the three for *this specific* behavior.
- **Spread:** the real bid/ask spread of the exact triggering tick — no
  averaging.
- **Slippage:** none.
- **Commission:** same dead hook as `execution_mtf.py`.
- **Position sizing:** identical formula.
- **Account handling:** same `account_blown` guard.
- **Multiple positions:** single position at a time, same pattern.
- **Same-bar (same-tick) behavior:** SL-wins tie-break, counted via
  `same_tick_sl_tp_conflicts` — observed 0 occurrences in every run this
  sprint and in Q0.3/Q0.4, consistent with tick-level ambiguity being
  genuinely rare.
- **Intrabar behavior:** none — true tick resolution removes the concept
  entirely except for the residual same-tick case above.
- **MTF behavior:** signal timeframe + tick-level execution; same
  confirmed defect as `execution_mtf.py`.
- **Session handling:** not implemented (confirmed absent).
- **Error handling:** same guards as the other two engines.
- **Determinism:** confirmed this sprint — byte-identical across 2 runs,
  both specs (each run replaying the full 34,194,748-tick 2024 XAUUSD
  stream).
- **Output format:** same 3-tuple, plus `same_tick_sl_tp_conflicts` and
  `total_ticks_replayed` in `stats`.
- **Dependencies:** same as the other two, plus
  `scripts.import_exness.iter_tick_chunks` and direct filesystem access
  to `C:\Users\om\Downloads\Exness_*.zip`.

**Testability, specifically:** because execution data is sourced from
real zip files with no injection point for synthetic ticks,
`execution_tick.py` **cannot run any of the Step 7 synthetic
micro-scenarios** without modifying the engine (out of scope this
sprint). `runner.py` and `execution_mtf.py` both accept arbitrary
DataFrames and were used for all synthetic testing in
[`Q0.5_CROSS_ENGINE_MATRIX.md`](Q0.5_CROSS_ENGINE_MATRIX.md). This is a
material, structural finding for the canonical-engine decision, not an
audit oversight.

## Known limitations (all three)

- No slippage model.
- No functioning commission model (hook present in 2 of 3, always inert).
- No session/trading-hours filter, despite `RiskConfig` implying one
  should exist.
- No broker minimum-stop-distance validation.
- No automated test suite prior to this program's own work
  (Q0.3/Q0.4/Q0.5's scripts are the first tests to exist at all).
