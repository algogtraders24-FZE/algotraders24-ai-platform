# Q0.7 — UI Implementation Plan

Design-only. Defines what a future dedicated UI sprint would build —
this sprint builds none of it, per explicit instruction.

---

## Page/component hierarchy

```
/quant-lite                          (Screen 1: Home)
  /quant-lite/strategies
    /quant-lite/strategies/new       (Screen 2: Strategy Builder)
    /quant-lite/strategies/[id]      (Screen 7: Strategy Detail)
  /quant-lite/backtest/[strategyId]  (Screen 3: Backtest Setup)
  /quant-lite/backtest/[backtestId]/running   (Screen 4)
  /quant-lite/backtest/[backtestId]/results   (Screen 5)
  /quant-lite/library                (Screen 6: Strategy Library)
  /quant-lite/upgrade                (Screen 8)

Shared components:
  <ExecutionAssumptionsPanel />      - one component, reused on Screens 3, 5, 7
                                        (single source of truth for disclosure copy,
                                         never re-worded per-screen)
  <StrategyRuleSummary spec={...} /> - renders a spec dict human-readably
                                        (Screens 2 preview, 5, 7)
  <EquityCurveChart series={...} /> - Screen 5
  <TradeListTable trades={...} />   - Screen 5
  <LegacyEvidenceBadge />           - the LEGACY-BACKTEST-EVIDENCE label,
                                        one component so its wording/styling
                                        can never drift across Screens 6/7
  <MetricTile value={...} unavailable={bool} />
                                     - renders "Not available" when unavailable,
                                        never silently falls back to "0"
```

Route naming above is illustrative, not a commitment to this exact
URL scheme — the actual placement under the existing `frontend/app/`
tree (e.g. as a new top-level section vs. nested under `/platform`) is
a decision for the implementation sprint, informed by but not decided
in this audit (Part 1 of the pipeline doc notes the existing structure
as context only).

## Required API calls (per the Part 13 design contract)

| Screen | Calls |
|---|---|
| Strategy Builder | `POST /quant-lite/strategies` (validate + save spec) |
| Backtest Setup | `GET /quant-lite/symbols` (data coverage per symbol, for date-range bounds) |
| Backtest Running → Results | `POST /quant-lite/backtest` (Part 13's contract), then `GET /quant-lite/backtest/{id}` to poll/fetch |
| Strategy Library | `GET /quant-lite/library?filters=...` |
| Strategy Detail | `GET /quant-lite/strategies/{id}` |

None of these routes exist. All require the persistence layer flagged
as undesigned in Part 15 of the pipeline doc.

## Required data structures

Directly derived from Part 6 (result contract) and Part 15 (provenance)
of `Q0.7_PRODUCT_PIPELINE.md` — not restated in full here to avoid two
documents drifting out of sync; implementation should treat that
document as the single source of truth for field names/types.

## Loading states

- Strategy save: synchronous, sub-second (spec validation is a pure
  function) — a disabled-button spinner is sufficient, no separate
  loading screen needed.
- Backtest run: **Screen 4 exists specifically for this.** Given
  `execution_mtf.py` measured at ~6-10 seconds for a full year of
  1-minute execution data (Q0.6), a single-symbol/single-year request
  is likely fast enough to feel synchronous with a simple spinner: a
  multi-year or especially a full-library-scale request would not be,
  and needs the staged messaging Screen 4 defines ("Loading price
  data" → "Running backtest" → "Calculating results") rather than one
  generic spinner for both cases. Where the threshold sits (and whether
  a job queue is needed at all) is not determined this sprint — flagged
  as an open engineering question, not assumed either way.

## Empty states

- No saved strategies yet: Screen 1/2 should route a first-time user
  directly into the builder, not show an empty list with no clear next
  step.
- Strategy Library with zero rows matching active filters: show the
  filter state clearly and an obvious "clear filters" action — never a
  bare "no results."

## Error states

Directly maps to Part 14's required list. Each row: technical reason →
user message → recovery action. **No raw Python traceback is ever
shown to a user** — every failure mode below has a specific,
translated message.

| State | Technical reason | User message | Recovery action |
|---|---|---|---|
| INVALID STRATEGY | `validate_spec()` returned errors | The itemized error list from `validate_spec()`, translated to plain language per error type (e.g. "unknown indicator type" → "This indicator isn't supported yet") | Return to Strategy Builder with the offending field highlighted |
| INVALID SYMBOL | Symbol not present in `market.db` | "This market isn't available yet" | Show the actual supported symbol list |
| INVALID TIMEFRAME | Not a timeframe the data supports | "This timeframe isn't available for this market" | Show supported timeframes for the selected symbol |
| INVALID DATE RANGE | Requested range outside actual data coverage | "Historical data for this market starts/ends on [date] — please adjust your range" | Auto-suggest the nearest valid range |
| INSUFFICIENT DATA | `len(sig) < 50` engine guard | "Not enough historical data in this range to run a reliable backtest" | Suggest widening the date range |
| INDICATOR DATA MISSING | NaN warmup rows exceed available data | Same message as INSUFFICIENT DATA — same underlying cause, no need for a separate user-facing category | Same |
| BACKTEST FAILED | Unhandled exception in the engine (per Q0.3's audit, no broad try/except exists beyond the specific guards above) | "Something went wrong running this backtest. Please try again" | Retry; if persistent, this should alert the team (not shown to the user as such) rather than looping silently |
| UNSUPPORTED FEATURE | User attempted something the Strategy Builder UI should have already prevented (e.g. via a malformed direct API call) | "This feature isn't supported in Quant Lite yet" | Return to Strategy Builder |
| DATA QUALITY WARNING | e.g. the rare real-data out-of-order-timestamp artifact documented in the Exness import work (Q0.2) | Not a hard failure — shown as a small, dismissible note alongside results, not a blocking error | None needed — informational only |

## Result states

Covered by Screen 5's design (`Q0.7_UI_INFORMATION_ARCHITECTURE.md`) —
notably, a *successful* backtest that lost money or hit
`account_blown=True` is still a "result state," not an "error state."
The UI must not conflate "the strategy lost money" with "the backtest
failed" — these are different, and only the second belongs in the error
table above.

## Mobile considerations

Trade list and equity curve are the two components most likely to need
real mobile-specific treatment (a wide table and a time-series chart
both compress badly on narrow viewports). Not designed in detail this
sprint — flagged as a real implementation concern, not a minor detail,
given this is explicitly meant to be an accessible, free product.

## Desktop considerations

None beyond standard responsive layout — no desktop-only feature is
implied by anything in this design.

## Part 17 — Resource limits (recommended, not implemented)

| Risk | Recommended limit | Reasoning |
|---|---|---|
| Extremely long date ranges | Cap at actual `market.db` coverage per symbol (already a hard ceiling — e.g. `XAUUSD_EXNESS` cannot exceed ~2.4 years regardless of user input) | Free correctness constraint, not just an abuse guard |
| Huge strategy searches (e.g. scripted parameter sweeps hitting the API) | Rate-limit backtest requests per user/session (specific number not prescribed here — a product/infra decision) | `execution_mtf.py` is fast per-run (~6-10s/year) but not free computationally at scale |
| Excessive concurrent backtests | Queue or reject beyond a small per-user concurrency limit | Same reasoning |
| Invalid strategy recursion (e.g. a malformed spec causing a retry loop) | The LLM parser already caps this internally (`MAX_REPAIR_ATTEMPTS = 3`) — the same discipline should apply to any future automated-retry UI flow, not just the LLM path | Prevents runaway API cost/loops |
| Excessive memory usage | Bound date range × symbol count per request (server-side, not just UI-suggested) | A full multi-year, multi-symbol backtest loads real minute-level DataFrames into memory — `execution_mtf.py` was not built or tested for unbounded input size |
| Oversized output | Cap trade-list page size in the API response (paginate rather than return an unbounded list) | A high-frequency strategy over a multi-year range could produce thousands of trade rows |
| Abusive repeated requests | Standard rate-limiting at the API gateway/auth layer | Not specific to Quant Lite's engine — a general product concern |

No infrastructure implementing any of the above was built this sprint,
per explicit instruction.
