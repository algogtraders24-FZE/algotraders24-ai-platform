# Q1.1 — Result Provenance

Every Q0.9-era provenance field is preserved unchanged (Q1.1's explicit instruction: "Do not remove Q0.9 provenance fields"): `symbol`, `timeframe`, `dateRange`, `initialCapital`, `engineVersion`, `generatedAt`, plus the request/result hashes already carried on the job record (`requestHash`) and the Python-side `resultHash` embedded by `run_backtest_job.py`.

## Added in Q1.1

`ResultProvenance.dataQuality: CoverageAssessment` — the complete assessment (see `Q1.1_DATA_QUALITY_CONTRACT.md`), computed once at job creation and never recomputed for that job. Contains, among other fields:

- `registryVersion` / `auditRuleVersion` — Q1.1.21/22: which exact gap-registry state and rule version produced this label. Two results for the identical request, run before and after a registry refresh, will show different `registryVersion` values even if the trade metrics are byte-identical (metrics depend only on `market.db` + the engine; data-quality labels depend on the registry).
- `requested` / `actual` — the period the user asked for vs. the real overlap with recorded data.
- `coveragePct`, `missingDurationDays`, `largestGapDays`, `gapCountInRange`, `contiguousCoverage`, `policy`, `worstSeverity`, `message`.

`BacktestResult.resultDataQualityStatus: "NORMAL" | "DATA_QUALITY_RESTRICTED"` — a coarse, UI-facing flag derived from `dataQuality.policy` at mapping time (`resultMapper.ts`), so the Results page can gate its RESTRICTED banner without re-deriving policy logic in a component.

## Reproducibility

Because `dataQuality` is attached once and never silently recomputed, a stored result remains a faithful record of what was known at the time it ran - even if a later gap-registry refresh would produce a different assessment for the same request today. This is deliberate: Q1.1.21 says "changing the gap registry must be detectable," not "old results must retroactively update." Detecting a stale label is possible by comparing a result's `registryVersion` against the current one (exposed via `GAP_REGISTRY_VERSION` in `data/quant-lite-gap-registry.ts`) - no tooling for automated re-labeling was built this sprint (not requested, and would conflict with "never mutate historical result data," the same principle Q0.9/Q1.0 applied to retry/idempotency).
