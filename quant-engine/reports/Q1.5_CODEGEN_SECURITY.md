# Q1.5 Parts 8/9/10/11 — Codegen Security, Compiler Verification, Regression & Boundary Testing

**No secret values appear anywhere in this document.**

## Part 8 — Generated code safety

Direct source review of `codegen_mql4.py`, `codegen_mql5.py`, `codegen_pine.py` (the only three places that emit MQL4/MQL5/Pine text), grepping for every dangerous-capability function each language exposes:

- **MQL4/MQL5**: `ShellExecute`, `WebRequest`, `FileOpen`/`FileWrite`/`FileDelete`/`FileFindFirst`, `#import` (DLL import), `iCustom` (loading an arbitrary external indicator), `SendFTP`, `SendMail`, `SendNotification` — **zero matches** in either generator. Nothing generated by this pipeline can execute a shell command, make a network request, touch the filesystem, load a DLL, or exfiltrate data.
- **Pine**: `request.security` (Pine's mechanism for pulling other-symbol/other-timeframe data, the same construct responsible for most real-world repainting/lookahead bugs) — **zero matches**, consistent with Q1.4's own "no lookahead anywhere" finding.
- Broader sanity grep across all of `spec_engine/` for `import os`, `import subprocess`, `eval(`, `exec(` (Python-level, not generated-code-level) turned up matches only in unrelated modules (`quant_lite_risk.py`, `execution_tick.py`, `runner.py`, `llm_parser.py`, `library_generator.py`) — none of which are invoked by the codegen path (`run_codegen_job.py` only imports `spec_engine.schema` and the three `codegen_*` modules).

Combined with Q1.4's still-standing findings (no BE/trailing/partial code anywhere, AND-only entry logic, closed-bar indexing) and this sprint's own name/id sanitization re-verification, generated code is confirmed to do nothing beyond compute indicator values and submit orders through each platform's own normal trading API.

## Part 9 — Real compiler verification

Checked for MetaEditor (`metaeditor64.exe`/`metaeditor.exe`) and any TradingView/Pine compiler on this machine: **none found**, same result as Q1.4. This is stated plainly, not silently assumed away: every artifact this pipeline produces is validated **statically only** — brace-balance checking, spec-conformance checking, and manual code review — never compiled by a real MetaEditor or TradingView. All reports and UI copy referring to generated code use **`STATIC-VALIDATION-ONLY`** language; nothing in this program claims "compiler-verified" or "guaranteed to compile."

## Part 10 — Security regression tests (Q1.4 findings + new Q1.5 findings)

`frontend/scripts/q15_security_tests.ts` (new, 67 assertions, run live against `/api/quant-lite/codegen`) is the permanent regression suite for this program's codegen attack surface:

- **Q1.4 permanent regressions** (2 tests): the original indicator-id code-injection case and the name string-literal-breakout case — both still correctly rejected/sanitized.
- **Indicator id fuzzing** (14 cases): null bytes, RTL-override unicode, `${jndi:...}`, `{{7*7}}`, `<%= %>`, path traversal, embedded newline, `\x00`, backtick, unicode "identifier-look-alike" letters, empty string, digit-leading, space, hyphen — all correctly rejected with `400`.
- **Strategy name fuzzing** (12 cases, including a 10,000-char string): the check here isn't "does a fixed dangerous substring survive" (that was this sprint's own first-draft bug — see below) but "does the **raw, unsanitized** name survive byte-for-byte into the generated code" — the only way a name-based attack could actually break out of its context. It never does; `_sanitize_name()`'s output charset is enforced correctly in all 12 cases plus the Q1.4 regression case.
- **Condition ref fuzzing** (8 cases, including the two genuine `NaN`/`Infinity` findings from Part 11 below): all correctly rejected.
- **Numeric extremes** (`1e308`, negative multipliers): handled without a crash, either accepted or rejected with a clean `400` — never an unhandled exception.
- **Language-selection injection** (7 cases: shell-metacharacter string, path traversal, wrong case, empty, `null`, a number, an array): all correctly rejected with `400` — confirms `targetLanguage` is checked against the fixed allow-list, never used to build a path or command.
- **Structural attacks**: `null`/array strategy, a 200-level-deep nested extra field, a `__proto__`/`constructor.prototype` pollution attempt, an empty `{}` strategy, a 5,000-element `entry_long` array — all handled safely (either a clean `400` or a bounded `200`, never a crash or hang).
- **Oversized/malformed request body**: a ~2MB single-field JSON body and deliberately-broken JSON — both rejected cleanly.
- **Post-battery health check**: the server is still healthy and still generates a valid, well-formed response for a normal request after all of the above — confirming none of this actually destabilized the process.

**A test-script correction, not a product bug**: the first draft of this suite flagged `req.comment="` as a "dangerous substring" — but that prefix is legitimate code present in *every* generated MQL5 file (it's how the sanitized name is embedded as the order comment), so it "matched" regardless of what the name actually was, producing false failures on completely benign names. Verified via direct curl inspection of the generated code (`req.comment="UnicodeStrategyNameTest";` — properly sanitized, no breakout) before correcting the test to the byte-for-byte-survival check described above.

## Part 11 — Real finding: undeclared-ref validation gap (found and fixed this sprint)

**Real defect, found via this sprint's own boundary testing, not previously known.** `"NaN"` and `"Infinity"` are syntactically valid identifiers under the existing `ID_PATTERN` (`^[A-Za-z_][A-Za-z0-9_]{0,63}$`) but were never checked against the set of **actually declared** indicator ids. Submitting a condition like `{"left": "NaN", "op": ">", "right": 0}` previously passed validation and generated:

```
bool longSignal = (NaN > 0);
```

— a reference to an undefined variable, which would fail to compile in MQL4/MQL5 and produce undefined behavior in Pine. This is **not an injection/security vulnerability** (`NaN`/`Infinity` are still safe identifiers, nothing escapes any quoting context) but a real **"generated code doesn't correspond to a valid program"** defect — exactly the class of bug Q1.4's own Part 4 principle ("BACKTEST BEHAVIOR ≠ GENERATED CODE CLAIM until parity is actually verified") exists to catch.

**Fix**: `_validate_ref(ref, known_ids)` in `quant-engine/spec_engine/schema.py` now takes the set of declared indicator ids and rejects any bare identifier or `id.field` reference whose base isn't in that set — `"totallyUndeclaredRef"`, `"NaN"`, `"Infinity"`, and any other typo are now all correctly rejected with `400 INVALID_STRATEGY`.

**Safety verification** (full regression, all still passing after the fix):
- `q09_regression_test.py` — 22/22 (MACD baseline unchanged: 208 trades, 43.75% win rate, PF 1.15, +19.61%, $11,961.23 final balance).
- `template_builder.py` self-test (runs at import, builds real specs) — OK.
- `q14_golden_strategies.py` — 42/42.
- `q14_indicator_matrix_test.py` — 73/73.
- `q15_security_tests.ts` — 67/67 including the two new `NaN`/`Infinity` cases.

No real strategy in this program's own template library or golden-strategy set ever used an undeclared ref (all real ids/refs were already valid), so this fix has zero behavioral impact on anything that previously worked correctly — confirmed by the unchanged regression numbers above.
