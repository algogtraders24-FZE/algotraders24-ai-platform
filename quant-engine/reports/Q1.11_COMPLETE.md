# Q1.11 COMPLETE — Quant Lite Production Execution Service

## Final classification: **CONDITIONALLY APPROVED**

Per this sprint's own rule: *"If VPS service works but Vercel/tunnel integration is incomplete → CONDITIONALLY APPROVED."* That is exactly this sprint's real state: the execution service and the Vercel adapter that talks to it both exist, both are built to the exact contract this three-sprint track designed, and both were proven correct through extensive live local testing — but the actual network hop (Cloudflare Tunnel route, real VPS deployment, real Vercel deployment) was not built or exercised this sprint. Not "PRODUCTION EXECUTION PATH VERIFIED" (that requires the complete real path), and correctly not "BLOCKED" either (nothing failed — MT5 coexistence wasn't even touched this sprint, since no real VPS execution happened).

## 1. Existing architecture audit

Q1.8's contract, Q1.9's topology, Q1.10's proof, and the current Node-side job contract were all re-read and cross-checked before writing any code — the new service's field names and job-lifecycle semantics were built to match the existing `BacktestJobStatus`/`BacktestJobErrorCode` types exactly, not invented separately. `Q1.11_EXISTING_ARCHITECTURE.md`.

## 2. VPS HTTP execution service — built and locally verified

`quant-engine/service/quant_lite_execution_service.py` — FastAPI, modeled directly on `mt5-bridge/bridge.py`'s own already-proven-in-production pattern. Thin transport wrapper only — spawns the exact same unmodified `run_backtest_job.py`, nothing about the engine reimplemented. Run and tested live, locally, end-to-end: real MACD/RSI/EMA backtests, 2-job concurrency with zero contamination, correct rejection of bad requests (auth, unknown fields, invalid strategies, path-traversal job IDs), `market.db` checksum confirmed unchanged before/after. `Q1.11_EXECUTION_SERVICE.md`.

## 3. Authentication

Constant-time bearer-token check (`hmac.compare_digest`), fail-closed if unconfigured, tested live: missing token → 401, wrong token → 401, correct token → proceeds. Never logged, never echoed in any response.

## 4. Network boundary

**Designed, not applied.** The live `cloudflared` config was still not read this sprint (no remote access) — per this sprint's own explicit instruction not to assume the existing tunnel can trivially carry Quant Lite traffic, no route was added blind. A concrete, ready-to-review proposed config addition exists. `Q1.11_NETWORK_TOPOLOGY.md`.

## 5. Vercel adapter

**Built, real code, in this repo.** `executionAdapter.ts`'s `startJob()` now branches on `QUANT_LITE_EXEC_SERVICE_URL`: unset (the default) preserves the exact existing local-spawn behavior byte-for-byte (confirmed: 238 live-API regression assertions unaffected), set → the new `runRemote()` forwards the validated request over HTTPS, polls for the result, and writes it through the identical `updateJob()`/`fail()` calls the local path already used — Vercel does not execute Python, does not touch `market.db`, and does not depend on `quant-engine` sibling files when this mode is active, per this sprint's own explicit rule.

## 6. Local vs. VPS parity

**3 for 3, exact matches** — MACD (208/43.75%/1.15/+19.61%/$11,961.23), RSI (227/35.68%/1.1/+14.55%/$11,455), EMA (121/31.4%/0.91/-7.5%/$9,250) — all reproduced through the real HTTP service, plus a distinct fourth request run through the **full** Vercel-adapter chain and confirmed correct in the real browser UI. `Q1.11_PARITY.md`.

## 7. Concurrency

2 simultaneous jobs through the real service, zero cross-contamination, correct isolated results per job — re-confirmed this sprint (building on Q1.10's own direct-script concurrency proof, now shown to hold through the HTTP layer too).

## 8. MT5 coexistence

**Not re-tested this sprint** — no real VPS execution happened (only the local proxy). Q1.10's own result (clean pass, single-job and 2-job) stands, unaffected by this sprint's code since nothing new has touched the VPS yet.
