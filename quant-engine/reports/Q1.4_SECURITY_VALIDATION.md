# Q1.4 Part 13/18 — Security Validation

## Two real vulnerabilities found and fixed

Security testing this sprint found — not assumed, not hypothetical — two genuine template-injection defects in the pre-existing generators, both now fixed.

### 1. Indicator `id` code injection (severe)

Indicator ids are embedded **unquoted, as raw MQL/Pine identifiers**, in every generated artifact (variable names, handle names, function calls). Before this sprint, `validate_spec()` never checked their format. A crafted request with `"id": "i1; Print(1); int x"` produced:

```
int h_i1; Print(1); int x;
   h_i1; Print(1); int x = iRSI(_Symbol, PERIOD_CURRENT, 14, PRICE_CLOSE);
   IndicatorRelease(h_i1; Print(1); int x);
   bool longSignal  = (i1; Print(1); int x < 30);
```

— arbitrary compilable MQL5 code injected into every line referencing that id. If a user compiled and ran the generated EA, the injected statement would execute.

**Fix**: `schema.py::ID_PATTERN` (`^[A-Za-z_][A-Za-z0-9_]{0,63}$`) — indicator ids, and condition `left`/`right` refs (including the `base`/`field` halves of `id.field` refs), are now validated and **rejected outright** if unsafe, before any generator ever runs. Rejection (not sanitization) is the correct fix for identifiers, since silently mangling an id would desync the spec from the generated code's actual variable names.

### 2. Strategy `name` string-literal breakout (moderate)

The free-text `name` field was embedded directly into a quoted MQL string literal (`req.comment="{name}"`) and into source comments, with no escaping. A name containing `"` produced:

```
req.comment="Evil";Print("INJECTED");//"; req.type_filling=ORDER_FILLING_IOC;
```

— breaking out of the string literal into executable MQL. A newline in the Pine variant could similarly break out of a `//` comment line.

**Fix**: `_sanitize_name()` added to all three generators (`codegen_mql4.py`/`codegen_mql5.py`/`codegen_pine.py`) — strips everything except letters, digits, spaces, and a small safe punctuation set before the name is embedded anywhere. Applied to both the header comment and every string-literal usage.

## Verified fixed (live, via the real API)

| Test | Before | After |
|---|---|---|
| `id: "i1; Print(1); int x"` | code generated, injection succeeded | `400 INVALID_STRATEGY`, generator never runs |
| `name: 'Evil"; Print("INJECTED"); //'` | `req.comment="Evil";Print("INJECTED");//"` (injection succeeded) | `req.comment="EvilPrint(INJECTED)"` (harmless, quoted) |

Both re-verified via `frontend/scripts/q14_codegen_tests.ts` (`security.*` cases) and confirmed not to have regressed the Q0.9 MACD baseline or `template_builder.py`'s own self-test (which builds real specs using ids like `trigger_rsi`/`filter_ema`/`atrRisk` — all already safe identifiers, unaffected).

## Other Part 13/18 checks (all pass, no new findings)

- **No shell execution**: `codegenAdapter.ts` uses `spawn(cmd, argsArray, {shell:false})` — identical pattern to the Q0.9 backtest adapter, already audited.
- **No arbitrary filesystem access**: config/output paths are server-generated (`crypto.randomUUID()`-based), never client-supplied. Verified: a request body containing filesystem-path-shaped strings in the `name` field is simply treated as text.
- **No external code injection / unexpected URLs**: generators only ever emit template-fixed strings + spec-derived values; no network calls exist anywhere in the codegen path.
- **No credentials in generated output or provenance**: `provenance` contains only hashes, a version string, the target language, and a timestamp — checked via automated regex (`provenance.no_secrets` test) for `api_key`/`token`/`password`/`secret` substrings.
- **Never executes generated code on the server**: confirmed by design — `run_codegen_job.py` only ever calls the Python `generate_*` functions (which return strings) and writes the result to a JSON file; nothing compiles, imports, or evaluates the generated MQL/Pine text.
- **Malformed spec handling**: non-object strategy, malformed JSON body, and missing required fields all rejected cleanly with structured 400 errors — never a partial or garbled generation attempt.
- **No secrets printed during this sprint's testing** — no `.env.local` or credential-dumping command was run (explicit care taken given the Q0.9 exposure incident).
