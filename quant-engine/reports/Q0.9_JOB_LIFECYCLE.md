# Q0.9 — Job Lifecycle

## States

`QUEUED -> RUNNING -> COMPLETED | FAILED` (`CANCELLED` is a defined state in the type but nothing currently produces it — no cancel endpoint was built this sprint, out of scope per Q0.9.48's deferral list not mentioning it explicitly but no requirement asked for it either; the UI renders it correctly if it ever appears).

## Storage

Per Q0.9.21's explicit instruction ("do NOT immediately create a large new database system... use the safest existing project persistence mechanism"), each job is one JSON file: `quant-engine/output/jobs/<jobId>.json`, written/read by `frontend/services/quant-lite/backend/jobStore.ts`. This reuses the exact pattern Q0.6 already used for its own backtest output (`quant-engine/output/q06/*.json`) rather than adding a new Prisma model + migration.

A `BacktestJobRecord` holds: `jobId, requestHash, status, request, dbSymbol, createdAt, startedAt?, completedAt?, durationMs?, result?, error?, engineExitCode?, stderrTail?`.

## Idempotency

`requestHash` (`services/quant-lite/backend/requestHash.ts`) is a SHA-256 over the *semantic* fields of the request (symbol, timeframe, date range, capital, risk%, and the strategy's indicators/conditions/risk — explicitly **not** the strategy's cosmetic `name`), with keys canonicalized (sorted) so field order never changes the hash. `POST /api/quant-lite/backtest` looks up `findActiveJobByRequestHash()` first — an identical `QUEUED`/`RUNNING`/`COMPLETED` request returns the existing job (`reused: true`) instead of starting duplicate work. A `FAILED` request hash is *not* treated as active, so retrying after a failure creates a fresh job — verified live (resubmitting the exact MACD test request returned the original `COMPLETED` job in 8ms with `reused: true`, no duplicate execution).

## Retry

The Results page's failure UI (`ResultsView.tsx`) offers "Try Again", which routes back to Backtest Setup — resubmitting creates a genuinely new execution attempt (new `jobId`) rather than mutating the failed job's record. Historical failed job records are never overwritten.

## Known limitations (explicit, not hidden)

- **Single-instance store.** The job-store directory scan (`findActiveJobByRequestHash`) and the in-memory concurrency counter both assume one Node process. Correct today; wrong for a future multi-instance deployment, which would need a real shared store — most likely Postgres via the schema this repo already has (`WorkflowRun`/`AgentTask` are the closest existing shape references, per the Q0.9.1 audit, though neither is symbol/spec/ledger-shaped and a new table would still be needed).
- **No authentication/ownership on jobs.** Anyone who knows a `jobId` can read its result via `GET`. Consistent with Quant Lite's existing no-login, free-tool design (Q0.7 scope) — not a regression, but worth noting before any future multi-user deployment.
- **No garbage collection.** Job JSON files accumulate indefinitely in `quant-engine/output/jobs/`. Fine at current usage volume; would need a retention policy before production scale.
