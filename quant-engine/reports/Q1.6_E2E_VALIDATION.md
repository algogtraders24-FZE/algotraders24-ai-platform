## Additional required states (Part 19)

- **RESTRICTED**: verified live as a natural byproduct of step 4/7 above (not synthetically forced) - the coverage panel and the `DATA QUALITY RESTRICTED` result banner both rendered with clearly distinct red styling, never visually equivalent to a SUPPORTED result.
- **DATA_UNAVAILABLE**: verified live by changing the Setup screen's date range to `2010-01-01`→`2010-12-31` (outside XAUUSD's real recorded range of 2024-01-01 to 2026-05-31). The coverage panel correctly updated to `Not Available` / 0% coverage / `CRITICAL` severity, and — confirmed directly via `element.disabled` — the **"Run Backtest" button is disabled** in this state, matching `BacktestSetupForm.tsx`'s `disabled={submitting || coverage?.policy === "DATA_UNAVAILABLE"}` guard. The client cannot submit a request the server already knows is unservable.
- **NEGATIVE_RESULT**: constructed a deliberately poor-expectancy strategy (contrarian RSI logic + an inverted 10/2 SL:TP ratio) and ran it live end-to-end through the real API and the real results page. Result: Return **-4.32%**, Profit Factor **0.91**, Average Trade **$-1.61**, Final Balance $9,568.00 - all rendered with the same negative/"down" styling as any other loss, nothing hidden, dimmed, or specially excused. Confirmed via screenshot as well as `get_page_text`.
- **FAILED**: attempted to trigger a genuine FAILED job through the real API with several inputs designed to fail (an unsupported symbol, an out-of-coverage date range on `POST /api/quant-lite/backtest` directly). In every case, the request was **rejected at `INVALID_REQUEST`/400 before a job was ever created** - the same server-side `validateStrategySpecServerSide` / coverage gate used by the UI runs again, authoritatively, at the API boundary, so most "bad request" paths never reach a job that could be polled to a FAILED state. This is a byproduct of the defense-in-depth already verified across Q0.9-Q1.5 (every layer re-validates, never trusts the layer above it), not a gap - but it means a live FAILED job (as opposed to an immediate 400) is reserved for genuine engine-side runtime failures (timeout, unexpected exception, unparseable result), which are exactly the cases `Q0.9`'s own regression suite (`q09_regression_test.py`: `data_unavailable.status_failed`, `invalid_strategy.status_failed`, `unsupported_symbol.status_failed` - all still passing this sprint) exercises directly against the real job runner and job store, bypassing the same pre-job validation a normal user's request would hit first. Combined with direct code review of `ResultsView.tsx`'s FAILED branch (`ERROR_COPY` mapping for every error code, `EmptyState` with a "Try Again" CTA, `error.details` rendered as a list when present) - correctness here is verified by real automated test + code review rather than a live browser click-through, and that limitation is stated plainly rather than silently claimed as a live UI pass.
- **LARGE_RUN**: re-confirmed server-side via the coverage API directly (`5m` timeframe, 517-day range) - `performanceClass: "SLOW"`, the exact same performance-notice copy as Q1.2/Q1.5, the 365-day threshold unchanged (Part 17's explicit instruction). Not re-clicked through the browser this sprint since the rendering logic (`CoverageAssessmentPanel.tsx`'s `performanceWarning` block) is unchanged from Q1.5's own live-verified state.
- **NO_TRADES**: not separately triggered live this sprint (would require a strategy whose conditions never fire across the whole test range - not naturally hit by the strategies above). Verified via direct code review instead: `TradeTable.tsx` renders `"Not available - no trades in this backtest."` and `EquityCurveChart.tsx` renders `"Not available - no closed trades to plot."` on an empty trade array - both pre-existing, unchanged this sprint.
- **EMPTY / LOADING**: verified via code review (`BacktestSetupForm.tsx`'s `draft === null` → `EmptyState` "No strategy selected"; `draft === undefined` → renders nothing until resolved) - unchanged this sprint, not re-clicked live.
