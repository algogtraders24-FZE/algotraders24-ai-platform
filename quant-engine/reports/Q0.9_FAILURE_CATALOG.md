# Q0.9 — Failure Catalog

`BacktestJobErrorCode` (`frontend/types/quant-lite-job.ts`) — the taxonomy Q0.9.24 requires, distinct from Q0.7's client-validation-oriented `QuantLiteErrorCode`:

| Code | When | Where it's produced |
|---|---|---|
| `INVALID_REQUEST` | Malformed JSON, missing/out-of-range fields, unsupported symbol/timeframe, malformed strategy spec | `validateBacktestRequest.ts` (before a job is even created) |
| `DATA_UNAVAILABLE` | Date range has no data for the symbol/timeframe, or (Python-side defense in depth) fewer than 50 signal bars survive indicator warmup | `dataCoverage.ts` (pre-flight, 422) and `run_backtest_job.py` (post-flight, independent re-check) |
| `BACKTEST_FAILED` | Reserved for a general engine-reported failure (not currently distinguished from `ENGINE_ERROR` by the runner — see Known Gaps below) | — |
| `BACKTEST_TIMEOUT` | Process exceeded `QUANT_LITE_BACKTEST_TIMEOUT_MS` (default 180s) | `executionAdapter.ts`, verified live at an artificially short 800ms timeout |
| `ENGINE_ERROR` | Uncaught Python exception, process failed to start, or exited without producing a result file | `run_backtest_job.py`'s catch-all, or `executionAdapter.ts` when no result file exists |
| `RESULT_INVALID` | Engine's result file exists but couldn't be parsed into `BacktestResult`, or reports an unrecognized `status` | `executionAdapter.ts` / `resultMapper.ts` |
| `UNKNOWN_ERROR` | A result file reports an `errorCode` not in this table (forward-compatibility guard) | `executionAdapter.ts` |

## UI behavior per state

`ResultsView.tsx` renders a distinct card for each: `QUEUED`/`RUNNING` show a spinner and real job id; `FAILED` shows the mapped human-readable message (`ERROR_COPY` lookup) plus any `details` array (e.g. every `validate_spec()` error string) plus a "Try Again" button; `CANCELLED` (defined, not currently producible) has its own copy; a `COMPLETED` job with no `result` (an internal inconsistency, not a normal path) gets its own honest "Result not available" card rather than crashing or showing a blank success state. No failure state is ever rendered as if it were a successful result — verified for `DATA_UNAVAILABLE`, `INVALID_REQUEST` (invalid strategy), and `BACKTEST_TIMEOUT` live.

## Known gaps (documented, not hidden)

- `BACKTEST_FAILED` is defined in the type but nothing currently emits it distinctly from `ENGINE_ERROR` — the Python runner's single catch-all always reports `ENGINE_ERROR`. A future refinement could distinguish "the engine ran and produced a definitively invalid result" from "the engine crashed," but nothing in this sprint's real testing produced a case needing that distinction.
- `RESULT_INVALID` is defended against (bad JSON, unrecognized status) but was not observed live — no test scenario in this sprint's verification actually produced a malformed result file, since `run_backtest_job.py` was written to always emit a well-formed one.
