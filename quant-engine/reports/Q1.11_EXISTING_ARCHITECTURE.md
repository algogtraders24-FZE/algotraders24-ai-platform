# Q1.11 Phase 1 — Existing Architecture Audit (Boundary Frozen Before Implementation)

## Q1.8 production architecture

Established: standard Vercel serverless deployment cannot run Quant Lite's Python backend (no Python runtime, no sibling-file inclusion, no 2GB DB support, timeouts far below what's needed). Target architecture: Vercel → HTTPS/bearer-token → execution service on a separate host → unmodified `execution_mtf.py` reading `market.db` read-only. This sprint builds exactly that target, now that Q1.10 proved the host (the existing VPS) is viable with real measured evidence.

## Q1.8 execution service contract

`POST /quant-lite/backtest`, `GET /quant-lite/backtest/:jobId`, accepting only the existing validated `BacktestRequest` shape, rejecting shell commands/filesystem paths/Python code/arbitrary queries, UUID job IDs, bounded concurrency, timeout, subprocess isolation, structured errors, server-side-only tracebacks, deterministic request/result hashing. **This is exactly what `quant-engine/service/quant_lite_execution_service.py` (built this sprint) implements** — not redesigned, built to this spec.

## Q1.8 production security

Bearer-token auth (server env var, never client code), no CORS, request-size cap, matching timeouts, server-side-only logging. **Implemented this sprint** via the same constant-time-comparison pattern `mt5-bridge/bridge.py` already uses in production (`hmac.compare_digest`, fail-closed if no secret configured).

## Q1.9 topology

VPS: 8GB RAM, 4-core Broadwell, ~150GB free disk, Python 3.11.0, MT5 terminals + `cloudflared` running. Corrected in Q1.9: the live tunnel mechanism is `cloudflared` (a named Cloudflare Tunnel), not Caddy as Q1.8 first assumed.

## Q1.10 VPS POC

**The load-bearing result this whole sprint builds on.** Real, measured, live evidence: `market.db` transferred and checksum-verified 3 times (always identical), 3 strategies (MACD/RSI/EMA) run with exact parity to local baselines including a negative-return case, single-job and 2-job MT5 coexistence both clean (no stop condition, MT5 CPU/RAM near-unchanged, free RAM held steady), zero orphan processes. Classification: **B — VPS CONDITIONALLY APPROVED**, with "build the actual HTTP service" as the named next step — precisely this sprint.

## Current Quant Lite API/job contract (re-read this sprint, unchanged)

`frontend/types/quant-lite-job.ts`: `BacktestJobStatus = QUEUED | RUNNING | COMPLETED | FAILED | CANCELLED`, `BacktestJobErrorCode` (includes `INVALID_STRATEGY`, the Q1.7 fix), `BacktestJobRecord`, `CreateBacktestJobResponse` (`jobId`, `status`, `requestHash`, `reused`), `GetBacktestJobResponse` (`jobId`, `status`, timestamps, `result`, `error`, `dataQuality`, `strategy`). **The new VPS service's own request/response shapes were built to match this contract's field names and semantics exactly** — `reused` boolean for idempotency, the same error-code taxonomy, the same job-lifecycle states — so the Vercel-side adapter (Phase 5) can translate between them with minimal impedance mismatch.

`frontend/services/quant-lite/backend/executionAdapter.ts`: currently `spawn()`s `run_backtest_job.py` locally, `MAX_CONCURRENT_BACKTESTS=2`, `BACKTEST_TIMEOUT_MS=180000`, `STDERR_TAIL_LIMIT=4000`, `SPREAD_PRICE=0.3`, `CONTRACT_SIZE=100` — **every one of these constants and values is preserved unchanged in the new VPS service** (same names, same defaults, same env-var override mechanism), so behavior is identical regardless of which side actually spawns the process.

## Existing `cloudflared` configuration

**Still not directly inspected — this agent has no remote access to read it.** `Q1.9_SECURITY.md`/`Q1.9_VPS_TOPOLOGY.md` already prepared the read-only inspection command (`Get-ChildItem "$env:USERPROFILE\.cloudflared"` + `Get-Content config.yml`). Per this sprint's own Phase 4 instruction ("do not assume the existing tunnel 'belongs to' or can trivially accept Quant Lite traffic"), the new route is **not** added blind — `Q1.11_NETWORK_TOPOLOGY.md` documents the exact config change needed, to be reviewed against the real file before applying.

## Boundary, frozen for this sprint

- The engine (`execution_mtf.py`, `quant_lite_risk_config()`, `schema.py`, all three codegen files) is **not touched or reimplemented** — the new service spawns the exact same `run_backtest_job.py`, unmodified.
- `market.db` stays VPS-side, read-only, never touched by this sprint's code.
- Vercel's own existing validation (`validateBacktestRequest.ts`, `dataCoverage.ts`, `coveragePolicy.ts`) is **preserved** — the new remote-execution path is a drop-in replacement for the local `spawn()` call inside `executionAdapter.ts`, not a rewrite of everything upstream of it.
- `at24-quant-engine/`, M-Series, G01, `mt5-bridge/`'s own implementation, `strategy_library.db`: not opened, not touched.
