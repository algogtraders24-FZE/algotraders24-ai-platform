# Q0.9 — Security Model

## Threat model addressed

The Q0.9 backend is the first place `frontend/` spawns a process and the first place it writes files whose names are influenced (indirectly) by a client request. Both are treated as a trust boundary.

## Controls

1. **No shell.** `child_process.spawn(cmd, argsArray, { shell: false })` — arguments are an array, never a concatenated string, so shell metacharacters in any value are inert.
2. **jobId is never client-supplied for writes.** `crypto.randomUUID()` generates every `jobId` server-side at job creation. The client only ever *reads* a jobId back (from the create response, or a URL) — it is never used to name a file for a `POST`.
3. **jobId is validated before every filesystem/route operation.** `jobStore.ts::isValidJobId()` — a strict UUID v4-shaped regex — gates every `recordPath()`/`configPath()`/`resultPath()` call and the `GET /api/quant-lite/backtest/[jobId]` route. A non-UUID string never reaches `path.join`.
4. **Server-side validation is authoritative.** `validateBacktestRequest.ts` re-implements `schema.py`'s exact rules in TypeScript for a fast 400, and `run_backtest_job.py` independently re-validates via the real `validate_spec()` before ever touching the engine — a client cannot bypass validation by skipping the TS layer, because the Python layer checks again.
5. **Config/result files use fixed, server-chosen paths.** `writeJobConfig`/`jobResultOutPath` build `<JOBS_DIR>/<uuid>.config.json` — no part of the path is built from request content.
6. **Hard timeout, guaranteed termination.** See `Q0.9_EXECUTION_ADAPTER.md`.

## Verified live (via the running dev server, real HTTP requests — see `Q0.9_REAL_EXECUTION_VALIDATION.md` for full transcripts)

| Test | Input | Result |
|---|---|---|
| Malformed JSON body | `{not valid json!!` | 400 `INVALID_REQUEST`, no crash |
| Path traversal (URL-encoded) | `..%2f..%2f..%2fetc%2fpasswd` as jobId | 400 `INVALID_REQUEST` — regex rejected before any fs call |
| Path traversal (literal) | `../../../../etc/passwd` in the URL path | 404 — Next's own router normalized it away |
| Shell-injection-looking jobId | `$(rm -rf /)` (URL-encoded) | 400 `INVALID_REQUEST`; repo filesystem confirmed untouched afterward |
| SQL-injection-looking jobId | `1' OR '1'='1` (URL-encoded) | 400 `INVALID_REQUEST` |
| Unknown but valid-format jobId | random UUID | 404 `NOT_FOUND` |
| Missing required fields | `{"foo":"bar"}` | 400 `INVALID_REQUEST` with itemized field errors |
| Unsupported symbol (no 1m data) | `XAUUSD` (legacy) | 400/422, rejected before any engine invocation |
| Malformed strategy spec | unknown indicator type, unknown op, missing atr_id | 400, rejected before any engine invocation; identical errors from the TS layer and the Python `validate_spec()` layer independently |

All nine automated equivalents of the above (jobId cases) are also covered in `frontend/scripts/q09_backend_tests.ts` (`jobid.*` tests) and re-run on demand via `npx tsx frontend/scripts/q09_backend_tests.ts`.

## Out of scope (unchanged from Quant Lite's existing design)

No authentication is added to these routes — consistent with Quant Lite's free, no-login product scope (Q0.7). Anyone who can reach the dev/prod server can create jobs and read job results by id. Noted as a limitation in `Q0.9_JOB_LIFECYCLE.md`, not a regression introduced by Q0.9.
