# Q0.6 — Look-Ahead Fix

## Confirmed bug (from Q0.5)

`execution_mtf.py` treated a signal-timeframe bar as "closed" — i.e.,
safe to read its close/indicator values and act on them — the instant an
execution-timeframe (1-minute) timestamp reached that bar's own **start**
timestamp, rather than waiting for the bar to actually finish forming.
Confirmed identical in `execution_tick.py` at the equivalent line
(untouched this sprint, see `Q0.6_COMPLETE.md` §execution_tick handling).

## Root cause

`market.db`'s candles are **left-labeled**
(`scripts/import_exness.py::resample(rule, label="left", closed="left")`)
— a candle timestamped `T` at timeframe `Δ` represents the interval
`[T, T+Δ)` and is not actually complete until `T+Δ`. The old code:

```python
while sig_ptr < len(sig_rows) and sig_ts[sig_ptr] <= ts_i:
```

compared the current execution-row timestamp directly against the
candidate signal bar's own **start** label (`sig_ts[sig_ptr]`), which
becomes true at `T`, a full bar-period before the bar genuinely closes at
`T+Δ`. This let a signal fire using that bar's already-known close value
(and any indicator computed from it) before that close time was real —
genuine look-ahead bias, not an approximation choice.

## Exact fix

**File:** `quant-engine/spec_engine/execution_mtf.py`, one condition
changed (plus an expanded explanatory comment, no other lines touched):

```python
# before
while sig_ptr < len(sig_rows) and sig_ts[sig_ptr] <= ts_i:

# after
while sig_ptr < len(sig_rows) - 1 and sig_ts[sig_ptr + 1] <= ts_i:
```

Bar `sig_ptr`'s true close time is derived directly from the data — the
**next** signal bar's own start timestamp, `sig_ts[sig_ptr + 1]` — rather
than hardcoding a timeframe duration the function has no independent way
to verify. This is deliberately data-driven, not a new timestamp
convention: it works for any signal timeframe (1h, 4h, 15m, ...) as long
as bars are sequential, which `compute_all()`'s vectorized output over a
regularly-resampled DataFrame always is.

**Direct, necessary consequence:** the current (most recent, still-open)
signal bar can never be marked "closed," because there is no
`sig_ptr + 1` to derive its real close time from until a genuinely new
bar appears in the data. This is correct, not a workaround — the bar's
true close time simply isn't knowable from the data until that happens.

## Why the fix is correct

- It changes only the timing condition that decides *when* a signal bar
  becomes eligible for evaluation. It does not touch `evaluate_entry()`,
  the indicator math, SL/TP formulas, position sizing, spread handling,
  or any risk-management logic — verified by diff (see
  `Q0.6_COMPLETE.md`, `git diff --stat`).
- It is derived directly from the actual data representation already in
  use (left-labeled candles, confirmed at the importer level), not an
  invented convention.
- No unrelated behavior changed: `runner.py` and `execution_tick.py`
  were not touched.

## Before/after semantics, concretely

| | Before (buggy) | After (fixed) |
|---|---|---|
| Bar `T` (spans `[T, T+Δ)`) considered closed at | `T` (its own start) | `T+Δ` (its real close, derived from the next bar's start) |
| Entry price basis | Whatever the execution-timeframe row nearest `T` shows — i.e., price action from **before** the signal bar even finished forming | The execution-timeframe row at/after `T+Δ` — price action from **after** the signal bar's close is real |
| Most recent signal bar | Actionable immediately | Never actionable until a new bar appears (correct — its close time isn't in the data yet) |
