## Chart Overlay — how candles and markers get onto the Native Chart

### The historical-window problem, and how it's solved

Native Chart's live candle feed (`useChartCandles`) only ever fetches the **latest N bars from now** (P3.1 finding, unchanged) - a backtest over a past date range (e.g. `2024-01-08`..`2024-01-13`) has no matching candles in that live feed. Rather than build a new historical-range chart-data endpoint (out of scope this sprint - "Prefer: Server: data + simulation. Browser: result + visualization"), the Algo Test API response already carries the exact bars the engine ran against (`AlgoTestRunView.candles`, sourced from `GoldenBacktestOutcome.bars` - P3.2A's `run-golden-backtest.ts`, extended this sprint to return the bars alongside the result). These are the SAME validated `OHLCVBar`s the simulation itself consumed, converted 1:1 to `ChartCandle` shape (`algo-test.service.ts::toChartCandles`) - not a second fetch, not a re-derived series.

`NativeChart.tsx`'s own candle source becomes:
```ts
const candles = useMemo(
  () => algoTestOverlay?.candles ?? result.series?.candles ?? [],
  [algoTestOverlay, result.series],
);
```
While an Algo Test result is active, the **entire chart** (candles, indicators, everything) shows that result's historical window instead of the live feed - the same mental model a real trading platform's own "strategy tester" chart mode uses (you're now looking at the backtest, not the live market). "Clear results" (`AlgoTestPanel.tsx`) resets `algoTestOverlay` to `null`, which reverts `candles` back to the live feed on the next render - no page reload needed.

**Disclosed limitation, per the brief's own "candles are only ever present on a fresh POST response" rule** (`types/algo-test.ts`): re-opening a *previously run* test via `GET /api/private/algo-test/runs/[id]` does **not** re-populate the chart overlay (that endpoint never returns `candles` - they're deliberately not persisted, per "do not store unnecessarily huge raw datasets"). Only a fresh run currently drives the chart overlay. A future release could re-fetch bars for a historical run's own date range on demand if this becomes a real need.

## Trade Markers (`lib/chart-engine/renderer.ts`)

New, purely additive `RenderParams` fields (default to `[]`/`null` - every existing `renderChart()` caller/test renders byte-for-byte unchanged, verified by the first test in `validate-algo-test-renderer.ts`):

```ts
algoTestTrades?: AlgoTestTradeMarker[];
selectedAlgoTestTradeId?: string | null;
```

```ts
export interface AlgoTestTradeMarker {
  tradeId: string;
  side: "BUY" | "SELL";
  entryTime: number; entryPrice: number;
  exitTime: number; exitPrice: number;
}
```

`drawAlgoTestTrades()` reuses the **exact same coordinate primitive** the existing Drawing Tools system already established (`drawing-renderer.ts`'s own `toPx()`: `fractionalIndexForTime` + `indexToX` + `priceToY`) - reimplemented locally as `algoTradePx()` rather than importing a private helper, but mathematically identical, not a second coordinate system. Per trade:
- **Entry**: a filled triangle, pointing up for BUY / down for SELL (direction is visually legible without reading a label).
- **Exit**: a filled square.
- A thin dashed line connects entry → exit, in the trade's own `colors.buyLine`/`colors.sellLine` (the same green/red already established for Paper Trading's own trade lines - P1/P2 - so a BUY looks the same whether it's a live paper trade or a backtest trade).
- The selected trade (`selectedAlgoTestTradeId`) renders at full opacity with a highlight ring (`ctx.arc`) around its entry marker and a thicker line; every other trade renders at reduced opacity (0.35) so the selected one reads clearly against the rest.

No clustering/aggregation for large trade counts was implemented - `docs/P3.1-DATA-COMPATIBILITY.md`'s own performance note already named this as a future need once wider date ranges are supported; this sprint's `MAX_RANGE_DAYS`-bounded requests keep trade counts small (~20-30 in this sprint's own real test runs), so every trade is drawn every frame without a measurable cost.

### Verified (`scripts/validate-algo-test-renderer.ts`, real canvas-fake harness)
`ctx.fill()` and `ctx.arc()` are used **only** by this new code path in the entire `renderChart()` pipeline (confirmed by source grep before relying on this as a test signal) - a clean, low-fragility way to assert "an entry marker was drawn" / "a selection ring was drawn" independent of however many candle/grid/axis draw calls happen in the same frame:
- Zero trades → zero `fill()`/`arc()` calls (no regression for any existing caller).
- N trades → exactly N `fill()` calls (one triangle each).
- A BUY trade's stroke color is `colors.buyLine`; a SELL trade's is `colors.sellLine` - never swapped, never both for one trade.
- The exit marker's `fillRect` lands at the exact pixel position independently computed via `fractionalIndexForTime`+`indexToX`+`priceToY` - the same math a trade-list click's own jump relies on, so a marker and a "jump to this trade" action can never visually disagree.
- Selecting one trade among several draws exactly one highlight ring, never zero, never N.

## Trade List (`AlgoTestPanel.tsx::AlgoTestResults`/`TradeRow`)

A compact table: `#`, Side (`Badge`, success/danger tone), Entry (price, with the real entry datetime as a hover title), Exit (same), P&L (colored via `text-signal-up`/`text-signal-down`, the same tokens Paper Trading's own P&L column already uses), R-multiple (`"—"` when genuinely `null` - **never coerced to `0`**, since a real `0R` breakeven trade is a different, legitimate value the engine can produce, and collapsing the two would misrepresent a "no stop-loss" trade as a real breakeven one). Rows are in ledger order (chronological, matching `SimulationResult.tradeLedger`'s own order - the engine's, never re-sorted).

## Trade ↔ Chart Synchronization (`NativeChart.tsx`)

```
User clicks Trade #N in the list
        ↓
AlgoTestPanel calls onSelectTrade(tradeId) [toggles off if already selected]
        ↓
NativeChart.tsx::handleSelectAlgoTestTrade
        ↓ setSelectedAlgoTestTradeId(tradeId)   -> drives the renderer's highlight (see above)
        ↓ jumpToAlgoTestTrade(trade)             -> moves the viewport
```

`jumpToAlgoTestTrade()` **reuses the existing viewport primitives** `handleFit()`/`fitToData()` already use (`candleStepMs`, `priceRangeForWindow`, `clampViewportToCandleBounds`) - composed around the trade's own `[entryTime, exitTime]` span, padded 8 candle-widths on each side for context, exactly the same "compose pure functions at the call site" pattern this file already establishes for every other viewport operation. **No new viewport system was built** (per the brief's explicit "do not rebuild the chart viewport system" instruction).

Clicking the same trade again deselects it (`AlgoTestPanel`'s own toggle logic) - `handleSelectAlgoTestTrade(null)` clears the highlight but does **not** move the viewport again (only a genuine trade selection triggers a jump).

A fresh test run (`handleAlgoTestOverlayChange`) resets `fittedKeyRef` so the *next* candles-effect pass genuinely re-fits the new historical window rather than "following" whatever viewport was showing the previous data - the same reset mechanism a real symbol/timeframe change already triggers, reused rather than duplicated.

## Equity Curve (`AlgoTestPanel.tsx::EquityCurveSparkline`)

A minimal, **self-contained inline SVG** - deliberately **not** Quant Lite's own `EquityCurveChart.tsx` (a different, unrelated system per `docs/P3.2A-QUANT-LITE-BOUNDARY.md`) and deliberately **not** the Native Chart canvas engine (disproportionate for one small line, matching Quant Lite's own `EquityCurveChart.tsx` header comment's exact reasoning for why IT doesn't reuse Native Chart either - the same judgment call, arrived at independently for the same reason). Plots `AlgoTestRunView.equityCurve` points as-is - `min`/`max` are computed only to scale the SVG viewport, never to alter a value. Line color reflects whether the curve ended above or below its start (`buyLine`/`sellLine` greens/reds, consistent with every other directional color in this feature).

## What the brief's "Do Not" list keeps this sprint clear of
No second backtest engine, no simulation logic in the browser (every number rendered traces back to `SimulationResult`/`GoldenBacktestOutcome` with only display-safe projections - `toChartCandles`, `toMetricsView`, `toTradeView`, `deriveEquityCurve` - none of which alter a value, only reshape/rename fields), no coupling to Quant Lite (its own boundary doc is unaffected; the equity sparkline explicitly avoids reusing Quant Lite's chart component), no Twelve Data credentials reaching the browser (verified in `P3.2B-ALGO-TEST-E2E.md`), and no claim that the execution assumptions are broker-realistic (disclosed verbatim on every result).

## Known limitations (disclosed, not silently absorbed)
1. Chart overlay only populates from a **fresh** run's response, not a re-opened historical one (see above).
2. No marker clustering for large trade counts - fine at this sprint's `MAX_RANGE_DAYS`-bounded scale, a named future need for wider ranges.
3. No pagination for the trade list/API response - same reasoning, same future need once ranges widen.
4. The equity curve is a simple min/max-scaled sparkline, not an interactive/zoomable chart - appropriate for this vertical slice's scope.
