`app/quant-lite/**` is a second, complete, already-shipped strategy-builder + backtest system running on a different (legacy Python) engine, not `at24-quant-engine`. This is a direct tension with "at24-quant-engine is canonical, do not build a second engine," except the second engine already exists, is live, and is being actively extended by a concurrent session as this audit runs. **Not resolved in this sprint** (explicitly out of scope) — recorded as the required strategic decision sitting above P3.2. This audit proceeds on the assumption that P3.2 builds a *new*, `at24-quant-engine`-backed feature inside Native Chart, and leaves Quant Lite untouched.

## F-1. Backtest Truth Audit (sprint §11)

Selected the engine's own golden-fixture end-to-end test (`test/simulation-e2e-golden.test.ts` + `test/fixtures/simulation-fixtures.ts`) — a simple, deterministic, hand-verified strategy — rather than writing a new one, per the sprint's "use the existing audited strategy/data infrastructure" instruction and "do not create a second calculation path" rule.

**Scenario**: signal fires with an entry rule producing a fill at 102, `stopLoss: {type: "fixed-distance", distance: 5}` measured from the 101 signal price → stop = 96; `takeProfit: {type: "risk-multiple", rMultiple: 2}`.

**Verified internally consistent, by hand, from the test's own asserted numbers:**

| Check | Computation | Asserted value | Consistent? |
|---|---|---|---|
| Trade count | — | 1 | ✅ (no entry before signal — separately asserted on the truncated 0-2 bar slice) |
| Entry price | actual fill (not signal price) | 102 | ✅ |
| Exit price | — | 111 | ✅ |
| Gross P&L | `(exit − entry) × quantity` = `(111 − 102) × 1` | 9 | ✅ matches `grossPnl: 9` |
| Fees | `ZeroFee` model | 0 | ✅ matches `fees: 0` |
| Net P&L | `grossPnl − fees` = `9 − 0` | 9 | ✅ matches `netPnl: 9` |
| R-multiple | `reward / risk` = `(111−102) / (102−96)` = `9 / 6` | **1.5** | ✅ matches `rMultiple: 1.5` — correctly computed from the *actual* entry/stop distance (6), not the nominal `rMultiple: 2` config target measured from the signal price, proving the engine doesn't fabricate a "clean" R value when the real fill slipped from the signal |
| Equity / balance | `initialBalance + netPnl` = `10,000 + 9` | 10,009 | ✅ matches `finalAccount.balance: 10009`, `finalAccount.equity: 10009` |
| Metrics | `computeCoreMetrics()` on 1 winning trade | `winRate: 100`, `netProfit: 9`, `averageR: 1.5` | ✅ all consistent with the single trade above |
| Determinism | `resultHash` | 64-char hex (sha256) | ✅ present and correctly shaped |
| Re-entry scenario | a strategy whose entry condition remains true after an exit legitimately re-enters | 2 orders created, 1 closed trade, 1 still-open position at `entryPrice: 105` | ✅ internally consistent (no phantom trade, no double-count) |

**Conclusion: Trade Ledger → Metrics is internally consistent for this scenario**, and — notably — the R-multiple math proves the engine measures realized risk/reward from *actual* fills, not nominal config targets, which is exactly the kind of honesty property this platform's standing discipline requires. No second calculation path was created to check this; the existing test's own hand-verified numbers were used as the ground truth.

**Caveat**: this validates the engine's *internal* arithmetic only. It does not validate against any *real* XAUUSD price history, because none exists in the repository (Data Compatibility doc, Gap-1) — that validation can only happen once a real historical dataset is wired in.

## F-2. Security Boundary (sprint §14)

### Authentication / authorization
- Every `/api/private/**` route (Paper Trading, Chart Workspace, etc.) resolves the user via `getUserOrNull()` and 401s before touching any service — the correct, universal pattern a new Algo-Test API must follow.
- **Quant Lite's routes are the counter-example, and a real gap today, independent of this sprint**: `POST /api/quant-lite/backtest` and `GET /api/quant-lite/backtest/[jobId]` call **no auth check at all**. Job records have no `userId` field. Anyone who obtains or guesses a `jobId` (a UUID — not guessable by brute force, but leakable via referrer/logs/screenshots) can read a full backtest result belonging to another session. **This is a pre-existing issue in code this sprint does not own or modify** (Strict Scope Rule: "do NOT modify unrelated Quant Lite functionality") — documented here as required, not fixed.

### Strategy / test ownership
No ownership model exists yet for a "backtest run" or "strategy" record (no Prisma model exists at all — Data Compatibility / Architecture docs). Recommendation (already reflected in the Contract doc): follow the `getUserOrNull()` + `sessionUser.profile.id`-scoped pattern exactly, never trust a client-supplied `userId`.

### Resource limits
Nothing in `at24-quant-engine` imposes a timeout, bar-count cap, or memory limit on a simulation run — it's a synchronous in-process function. A malicious or accidental request for an enormous date range × fine timeframe (e.g. M1 over 10 years) has no guardrail today. **This must be a new API-layer concern** (request validation: cap date range × timeframe granularity, impose a wall-clock timeout — see Contract doc's `TIMEOUT` error code), not an engine change.

### Arbitrary code execution risk — imported MQL/EA
This was the most important thing to verify carefully, and the answer is reassuring: **`at24-quant-engine`'s MQL importer never executes, evaluates, or code-generates from imported source.** The pipeline is strictly `tokenize → parse → analyze semantics → generate IR` — a pure parse/analysis chain producing a data structure (`StrategyIR`). `SourceGenerator` (the only place codegen was ever planned) is an unimplemented stub. There is no `eval`, no dynamic `Function()` construction, no shell-out, anywhere in this package. **Importing a malicious/malformed MQL/EA file can, at worst, produce a `BLOCKING` diagnostic or an unusual (but still statically-typed) `StrategyIR`/`StrategySpec` — it cannot execute attacker-controlled code.**
- The one real risk vector found is **not** code execution but **resource exhaustion**: an extremely large or pathologically malformed source file being fed to the lexer/parser with no documented size cap — worth a simple input-size limit at the API boundary (e.g. reject MQL source > some KB threshold) as cheap, standard hygiene, not a critical finding requiring urgent action.

### Arbitrary code execution risk — Quant Lite's Python path (adjacent system, flagged for completeness)
`services/quant-lite/backend/executionAdapter.ts` does spawn a real external process (`child_process.spawn(PYTHON_EXECUTABLE, [JOB_RUNNER_SCRIPT, "--config", configPath, "--out", outPath])`) — but it is **not a shell string** (no `shell: true` found, argv array form used), and the script path + flags are fixed, not attacker-influenced; only the *config file contents* (the strategy spec) are user-influenced, and that config is consumed by the Python engine as data, not as code to `eval`. This is a materially different (safer) shape than a shell-injection risk, and — since it's Quant Lite, not `at24-quant-engine` — is out of this sprint's remit regardless; noted for completeness since the sprint spec explicitly asked about "imported EA risks" broadly.

### Conclusion
**No critical vulnerability was discovered that would require an unscheduled fix under the sprint's own "only implement if critical" rule.** The two real, actionable items (Quant Lite's missing auth on its backtest routes; no resource-limit guardrail for a hypothetical future Algo-Test API) are both documented as required design inputs for P3.2 and/or a separate fix, not emergencies.

## F-3. Existing Test Coverage (sprint §15)

### `at24-quant-engine` (138 files, ~900+ tests) — full detail in the Architecture doc §2B; the tests directly protective of a future integration:
- `test/isolation.test.ts` — protects the package-boundary decision (Option B, Architecture doc §8) by continuing to fail if `at24-quant-engine` ever grows a runtime dependency or workspace membership that would make direct coupling look tempting.
- `test/simulation-e2e-golden.test.ts`, `test/q09-mql-e2e-golden.test.ts` — protect the exact request→trades→metrics path a new Algo-Test API would call; any breaking change to `SimulationResult`'s shape would fail these first.
- `test/determinism.test.ts` and siblings — protect the `resultHash`/reproducibility guarantee the Contract doc's `AlgoTestRunSummary.summary.resultHash` field depends on.
- `test/mql-failure-catalog.test.ts`, `test/q09-eligibility-gate.test.ts` — protect the exact diagnostic/blocking-reason shapes the Contract doc's error mapping (§4) depends on.

### Native Chart / frontend
- `scripts/validate-native-chart-*.ts` (11 files) — protect rendering, interaction, drawing tools, tiling, templates — all primitives a future trade-marker overlay would reuse (`toPx`, drawing-object renderer). None currently test anything backtest-related (expected — nothing to test yet).
- `scripts/validate-paper-trading*.ts` — protect the Paper Trading service/routes referenced throughout the Execution Parity doc; useful as a *pattern* reference for how a new `validate-algo-test.ts` should be structured, not directly reusable.
- No `validate-quant-lite-*` or `validate-backtest-*` exists under this naming convention; Quant Lite has its own separate, differently-named test scripts (`q09_backend_tests.ts` etc.) — confirms Quant Lite is tested, just not integrated with this codebase's dominant `validate-*` convention.

**Which tests can protect the new integration**: everything in the first bullet list above (isolation, golden e2e, determinism, eligibility/diagnostics) is already a real regression net for the exact surfaces a P3.2 implementation would call into — **no new engine-side tests are needed to "unlock" P3.2**; new tests are needed for the *new* code P3.2 would add (API routes, Prisma models, chart overlay, jump-to-time), none of which exist to test yet. Per the sprint's "do not duplicate existing tests unnecessarily" instruction, no redundant engine-side tests were written or proposed here.

## F-4. Miscellaneous findings (quick-reference list)

1. **`at24-quant-engine` has no package export surface** (`package.json` missing `main`/`exports`/`types`) — blocks *any* integration option, not just the recommended one. Cheapest, most load-bearing prerequisite fix for P3.2.
2. **No `equityCurve` exists in the real `SimulationResult`** — only in an old, unpopulated placeholder type. A UI equity curve must be derived from the trade list, not requested from the engine as a ready-made field.
3. **No `exitReason` on `SimulationTrade`** — exists only transiently in a simulation event payload. Needs a small, additive engine change to thread it onto the trade record (Contract doc §3).
4. **`stopLoss`/`takeProfit` are not attached to `SimulationTrade`** — they live on `Position`, a related-but-separate object. The API layer must correlate them at build time; the engine itself has no gap here (it's not lost information, just not co-located in the ledger's own record).
5. **Paper Trading has no seam for consuming an externally-computed trade ledger** — `openPosition`/`closePosition` always fetch a *live* snapshot internally. A future "replay this backtest as if it were paper-traded" feature (if ever wanted) would need new, read-only projection code, not reuse of the existing mutation methods.
6. **No historical-bars source is wired to `at24-quant-engine`** (Data Compatibility doc Gap-1) — the single largest blocker to a real, non-synthetic first backtest run.
7. **The only real MQL source in the repo (G01) is BLOCKED at reduction** — cannot be P3.2's initial validation strategy; use a hand-authored `StrategySpec` instead (same shape as the engine's own golden fixtures).
8. **Spread/slippage/fees/margin are all zero-cost/unenforced placeholders today** (Execution Parity doc) — every backtest result must visibly disclose this, mirroring Quant Lite's own `ExecutionAssumptions` disclosure pattern, to avoid presenting unrealistically clean results.
9. **Quant Lite's backtest routes have no authentication** — a real, pre-existing gap, explicitly out of this sprint's scope to fix, but the risk it illustrates (unauthenticated result access) is exactly why a new Algo-Test API must not copy that pattern.
10. **No "click list item → jump to chart point" pattern exists anywhere in the codebase today** — this is 100% new plumbing for P3.2, though it can be built entirely from existing primitives (`fractionalIndexForTime`, `toPx`, viewport helpers) without inventing new rendering concepts.
