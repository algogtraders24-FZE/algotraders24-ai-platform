# P3.1 — Native Chart ↔ Quant Engine Integration Contract

**Status:** Proposed contract derived from audit. Nothing below is implemented yet.
See `P3.1-QUANT-CHART-INTEGRATION-ARCHITECTURE.md` for how these boundaries fit together.

All fields below are chosen because they are **already required by an existing system on one side or the other** — no field is invented speculatively. Where a field is needed by `at24-quant-engine` but has no Native-Chart-side equivalent yet, that's noted.

---

## 1. Backtest Request

`at24-quant-engine`'s `SimulationConfig` (`src/runtime/simulation/simulation-engine.ts`) already defines everything the engine itself needs. The **new** Algo Test API request wraps it in the platform's standard shape and adds ownership/identity fields the engine doesn't (and shouldn't) know about:

```ts
// NEW — app/api/private/algo-test/runs (POST body)
export interface AlgoTestRunRequest {
  strategy:
    | { kind: "spec"; spec: StrategySpec }              // hand-authored / library strategy (at24-quant-engine StrategySpec)
    | { kind: "mql"; sourceText: string; fileName: string; instrument: Instrument; executionTimeframe: Timeframe }; // routed through importMQLSource()+compileStrategy() first
  symbol: string;              // e.g. "XAUUSD" — MUST match Instrument.symbol convention (plain, no broker suffix — see Data Compatibility doc)
  timeframe: Timeframe;        // "M1"|"M5"|"M15"|"M30"|"H1"|"H4"|"D1"|"W1"|"MN1" — engine's own enum, NOT Native Chart's SignalTimeframe (see Data Compatibility doc)
  startTime: string;           // ISO 8601 UTC
  endTime: string;             // ISO 8601 UTC
  initialBalance: number;      // engine field name is `initialBalance` (SimulationConfig) — NOT quant-lite's `initialCapital`
  riskConfig: RiskSpecification;      // pass through verbatim to StrategySpec.risk if kind === "spec"; required for MQL path's post-import risk override, if any
  executionConfig?: {
    spreadModel?: "zero" | "fixed";   // maps to engine's SpreadModel; engine only ships ZeroSpread today — see Execution Parity doc
    slippageModel?: "zero";
    feeModel?: "zero";
    latencyModel?: "zero";
  };
}
```

Notes:
- `strategy.kind: "mql"` is included because the importer pipeline exists and is real — but per the Architecture doc §7, **no real MQL source in this repo can reach a runnable result today** (G01 is blocked). The API should accept this shape (forward-compatible) but P3.2's own validation path should use `kind: "spec"` only.
- `initialBalance`/`riskConfig` names are picked to match the **engine's own field names** (`SimulationConfig.initialBalance`, `StrategySpec.risk: RiskSpecification`) rather than quant-lite's `initialCapital`/`riskPct` — deliberately, since this is a *new* contract for the canonical engine, not a copy of the legacy one. Do not silently rename between the two systems; if a future UI wants to feel consistent with Quant Lite's existing form, that's a presentation-layer choice, not a wire-contract one.
- **`startTime`/`endTime` require a historical-bars source that does not currently exist for `at24-quant-engine`** — see `P3.1-DATA-COMPATIBILITY.md` Gap-1. The API contract can be defined now; it cannot be *fulfilled* until that gap is closed.

## 2. Backtest Response

```ts
// NEW — response envelope, wrapped in the platform's standard ApiResponse.success({ run }, ...)
export interface AlgoTestRunSummary {
  testId: string;                 // new Prisma cuid, NOT the engine's internal resultHash (keep those separate — see below)
  status: "pending" | "running" | "completed" | "failed";  // mirrors quant-lite's own BacktestStatus union — proven-useful shape, safe to reuse verbatim
  summary?: {
    resultHash: string;           // engine's own deterministic fingerprint (SimulationResult.resultHash) — surfaced for provenance/debugging, not for UI display
    tradeCount: number;
    initialBalance: number;
    finalBalance: number;
  };
  metrics?: AlgoTestMetrics;      // present iff status === "completed"
  trades?: AlgoTestTrade[];       // present iff status === "completed" — see §Performance for why this might be a SEPARATE fetch for large N
  error?: { code: AlgoTestErrorCode; message: string };  // present iff status === "failed" — see §3 below
}
```

`AlgoTestMetrics` — directly reflects `computeCoreMetrics()`'s real output (`src/domain/metrics.ts`) plus what `runSimulation()` actually assembles (`simulation-engine.ts:607-619`). **Do not add fields the engine doesn't compute** (no Sharpe/Sortino/Calmar — those are `ReservedMetricName`s, declared but not implemented):

```ts
export interface AlgoTestMetrics {
  totalReturn: number;
  netProfit: number;
  grossProfit: number;
  grossLoss: number;
  profitFactor: number;   // Infinity if no losses and profit > 0; 0 if no trades — pass through as-is, do not coerce to null/0
  winRate: number;
  expectancy: number;
  maxDrawdown: number;
  averageTrade: number;
  tradeCount: number;
  averageR: number;       // engine-computed, mean of non-null rMultiple
  totalFees: number;
}
```

**No `equityCurve` field** — the real `SimulationResult` does not compute or expose one (only an old, unpopulated placeholder type has it). If the UI wants an equity curve, it must be **derived client-side (or in the new API layer) from the trade list** (`balanceAfter`-style running sum, exactly how Quant Lite's `EquityCurveChart.tsx` already does it from *its* `Trade[]`) — this is not duplicating simulation logic (§ per sprint rule "do not create a second calculation path"), it's a pure display-projection of already-final numbers, same as any chart derives a line from a data array. This should be flagged explicitly in the API doc/UI so nobody mistakes it for an engine-computed field.

## 3. Trade

Engine's real `SimulationTrade` (`src/domain/simulation/trade.ts`) vs. what the contract needs, field by field:

| Field | In engine's `SimulationTrade`? | Needed by Native Chart? | Contract field |
|---|---|---|---|
| trade id | ✅ `tradeId` | ✅ (React key, click target) | `tradeId: string` |
| symbol | ✅ `instrument.symbol` | ✅ | `symbol: string` |
| side | ✅ `side: "BUY"\|"SELL"` | ✅ | `side: "BUY" \| "SELL"` |
| quantity | ✅ `quantity` | ✅ | `quantity: number` |
| entry time | ✅ `entryTimestamp` (epoch ms) | ✅ (for `jumpToTime`) | `entryTime: string` (ISO — convert at the API boundary; Native Chart's `ChartCandle.time` is epoch ms, so the API should send **both** or just epoch ms — see decision below) |
| entry price | ✅ `entryPrice` | ✅ | `entryPrice: number` |
| exit time | ✅ `exitTimestamp` | ✅ | `exitTime: string \| number` |
| exit price | ✅ `exitPrice` | ✅ | `exitPrice: number` |
| stop loss | ⚠️ NOT on `SimulationTrade` — lives on `Position.stopLoss`/`initialStopLoss`, which is a *separate* object the ledger doesn't carry | ✅ (marker rendering) | `stopLoss?: number` — **requires the API layer to correlate each closed trade back to its originating position's `initialStopLoss` at build time; this is new plumbing, not present in the engine today** |
| take profit | ⚠️ same gap as stopLoss | ✅ | `takeProfit?: number` — same caveat |
| pnl | ✅ `netPnl` (and `grossPnl`, `fees`) | ✅ | `pnl: number` (= `netPnl`; expose `grossPnl`/`fees` too, they're free) |
| rMultiple | ✅ `rMultiple: number \| null` | ✅ | `rMultiple: number \| null` — **pass the `null` through as-is; never coerce to 0** (0 is a legitimate different value — a trade that closed exactly at breakeven — see Findings doc) |
| exit reason | ❌ **not on `SimulationTrade` at all** — only exists transiently in the `POSITION_CLOSED` simulation *event* payload (`reason`, `ambiguous`), which `runSimulation()` does not currently attach to the trade record | ✅ (quant-lite's own `Trade.exitReason: "SL"\|"TP"\|"PARTIAL"` proves this is a real, wanted field) | `exitReason?: "SL" \| "TP" \| "SIGNAL" \| "STOP_OUT" \| "END_OF_DATA"` — **requires a small, additive change inside `at24-quant-engine`: thread the exit-event's `reason` onto `SimulationTrade` when it's built** (`buildTrade()` / `trade-ledger.ts`). This is the one place where the engine itself is missing a field the contract needs — flagged here, not fixed in this audit. |

```ts
export interface AlgoTestTrade {
  tradeId: string;
  symbol: string;
  side: "BUY" | "SELL";
  quantity: number;
  entryTime: number;    // epoch ms — matches ChartCandle.time exactly, no client-side conversion needed
  entryPrice: number;
  exitTime: number;     // epoch ms
  exitPrice: number;
  stopLoss?: number;
  takeProfit?: number;
  pnl: number;
  grossPnl: number;
  fees: number;
  rMultiple: number | null;
  exitReason?: "SL" | "TP" | "SIGNAL" | "STOP_OUT" | "END_OF_DATA";  // absent until the engine-side addition above lands
}
```

Two real, non-invented gaps are called out inline above (`stopLoss`/`takeProfit` correlation, `exitReason` threading) — both are small, additive, engine/API-layer changes, not redesigns, and both should be listed as concrete P3.2 subtasks rather than assumed away.

## 4. Error / Failure Contract (sprint §13)

Every failure mode the sprint asks for, classified against what the engine already signals vs. what the new API layer must add:

| Failure | Engine signal today | New `AlgoTestErrorCode` | User-facing message source |
|---|---|---|---|
| Invalid strategy (fails IR structural validation) | `validateStrategyIRStructure()` → `ValidationResult.errors: string[]` | `INVALID_STRATEGY` | Join `errors[]`, never raw internals |
| Unsupported indicator | MQL importer: `iCustom` etc. flagged as a `Diagnostic` | `UNSUPPORTED_INDICATOR` | `Diagnostic.message` |
| Unsupported MQL construct | `Diagnostic{severity:"BLOCKING"}` (28 catalogued codes) | `UNSUPPORTED_MQL_CONSTRUCT` | `Diagnostic.message`, `Diagnostic.code` surfaced as a stable machine code, never the parser's internal exception text |
| Reduction-blocked strategy (e.g. G01) | `ReductionResult.status === "BLOCKED"`, `blockingReasons: string[]` | `STRATEGY_NOT_EXECUTION_ELIGIBLE` | Join `blockingReasons[]` |
| No historical data | N/A today (no data source wired — Gap-1) | `NO_HISTORICAL_DATA` | New API-layer check, modeled on quant-lite's own `checkDataCoverage()` → `DATA_UNAVAILABLE` pattern (proven UX, reuse the *pattern*, not the code) |
| Insufficient data (bars < warmup) | `compileToSimulation()` throws a plain `Error` | `INSUFFICIENT_DATA` | New API layer must catch the thrown `Error` and re-map — **never let a raw engine `Error.message`/stack reach the client** (see Security doc) |
| Backtest failure (engine invariant violation) | `runSimulation()` throws `Error` on invalid market series | `BACKTEST_FAILED` | Generic safe message + server-side log of the real error |
| Simulation exception (unexpected) | Any uncaught throw | `SIMULATION_EXCEPTION` | Generic safe message only |
| Timeout | N/A today — no timeout wrapper exists anywhere in the engine or a hypothetical API layer | `TIMEOUT` | New — API layer must impose one (engine has no async/IO, so a timeout only matters if a very large bar-count run is genuinely slow; see Performance §) |
| Malformed result | N/A — engine's own types are exhaustively validated internally | `MALFORMED_RESULT` | Defensive-only; should be unreachable if the above are handled correctly |

**Convention**: follows quant-lite's own precedent of a typed `{code, userMessage, recoveryAction}` shape (`QuantLiteError`) crossed with the platform's standard `ApiResponse.error({code, message, details?})` envelope (`P3.1-QUANT-CHART-INTEGRATION-ARCHITECTURE.md` §Findings on API conventions) — i.e. `AlgoTestErrorCode` populates `ApiError.code`, never a bespoke second envelope shape.

**Explicit rule**: no raw stack trace, no raw thrown `Error.message` from `at24-quant-engine` internals, and no raw MQL parser exception text ever reaches the client. Every one of the engine's thrown `Error`s (§ Architecture doc — the 4 documented throw sites) must be caught at the new API-service boundary and re-mapped to one of the codes above.
