# P3.4 — Parameter Versioning, Determinism & Reopen

**Status:** Implemented, tested, live-verified. See `P3.4-STRATEGY-PARAMETERS.md` for the audit and `P3.4-CONFIGURATION-CONTRACT.md` for the request/validation contract.

---

## 1. Parameters belong to a strategy version

`golden-strategy`'s parameter schema (`services/algo-test/strategy-registry.ts`'s `STRATEGY_REGISTRY[0].parameters`) is declared **under** `strategyVersion: "1.0.0"` — the same version P3.3 already established, read live from `buildGoldenStrategySpec().version`. Introducing `priceThreshold` in P3.4 did **not** bump this version, and that is a deliberate decision, not an oversight:

- The change is purely **additive and default-preserving** — `buildGoldenStrategySpec()` (no arguments) is byte-identical to its pre-P3.4 self, proven by `test/golden-strategy-parameters.test.ts` and re-proven at the service level in `scripts/validate-algo-test-service.ts` (the exact P3.3-era resultHash reproduces exactly).
- A `"1.0.0"` → `"1.1.0"` bump here would create a confusing mismatch: new default runs would be labeled a different version while claiming to reproduce `"1.0.0"`'s own canonical behavior.
- **The rule this decision does NOT relax**: an *incompatible* future change — one that alters what an existing parameter id means, removes a parameter, or changes a default such that OLD persisted runs' recorded values would be reinterpreted differently — would require a real version bump (`"1.0.0"` → `"2.0.0"` or similar), never a silent redefinition under the same version string. P3.4's own change doesn't trigger this because nothing about the *meaning* of any existing behavior changed — a brand new, previously-nonexistent knob was added, with a default that reproduces the old (only) behavior exactly.

## 2. Result identity / determinism

The effective test configuration folded into `resultHash` includes, transitively, every field section 10 names:

| Input | How it reaches `resultHash` |
|---|---|
| `strategyId` / `strategyVersion` | `AlgoTestRun.strategyId`/`strategyVersion` (persisted alongside, not inside the hash itself — the hash is the ENGINE's own `SimulationResult.resultHash`, over `finalAccount`/`finalPositions`/`tradeLedger`/`eventStatistics`/`executionStatistics`/`provenance`/`metrics`). |
| `parameters` | Flows into the entry rule's own `literal(priceThreshold)` inside the `StrategySpec` passed to `runSimulation()` — a genuinely different `priceThreshold` produces a genuinely different `provenance.strategyHash` (via `computeSemanticStrategyHash`), which flows into `resultHash`. A default-matching value produces the byte-identical spec, hence the byte-identical hash. |
| `symbol` / `timeframe` / date range | `datasetId`/`datasetVersion` (`SimulationConfig`), part of `provenance`. |
| `initialBalance` | `SimulationConfig.initialBalance`, part of `provenance`. |
| `riskConfig` | Fixed (unchanged, engine-internal) — not user-configurable this sprint (see `P3.4-STRATEGY-PARAMETERS.md` §2), so it contributes a constant, not a variable, to every hash. |
| `executionConfig` (spread/slippage/fee/latency) | Fixed `Zero*` models — same reasoning. |
| `engineVersion` | `provenance.runtimeVersion`, included directly. |
| `historicalDataset` | The real bars fetched from Twelve Data for the exact date range — identical range ⇒ identical bars (verified: two runs of the same request produce byte-identical `resultHash`). |

**Parameter ordering never creates a false difference**: `computeCanonicalHash()` (`at24-quant-engine/src/runtime/determinism.ts`) deep-sorts every object's keys before hashing (`sortKeysDeep`), so the hash is insensitive to JS object key insertion order anywhere in the hashed structure — including inside `StrategySpec`, `provenance`, and (were it ever populated) a `parameters` map. Confirmed by direct inspection of `canonicalStringify`/`sortKeysDeep`, not assumed.

**A deliberately NOT populated engine field**: `StrategySpec.parameters` (the engine's own declarative `StrategyParameterDefinition[]`) stays `[]` regardless of `priceThreshold`'s value — see `P3.4-STRATEGY-PARAMETERS.md` §5 for why. This means the parameter's effect on `resultHash` flows exclusively through its real, functional effect on the entry rule — never through a redundant, cosmetic declaration.

## 3. The Determinism investigation (documented per section 21's own instruction)

During this sprint's own test development, the "identical request twice → identical resultHash" test initially failed — not from a P3.4 regression, but from **Twelve Data's real free-tier rate limit** (8 API credits/minute; the extended test file's new parameter tests pushed one script run to 9 real calls within a rolling minute, tripping a `429`). This was root-caused by direct diagnostic logging (the failing run's own `errorCode`/`errorMessage`), confirmed reproducible, and fixed by removing one redundant real-network call (`scripts/validate-algo-test-service.ts`'s own inline comment explains the reasoning) — bringing the script back under the limit. This is an external, pre-existing infrastructure constraint of the free-tier plan, not a product defect; documented here rather than silently worked around.

Separately, a genuine resultHash *mismatch* was found and investigated (see `P3.4-STRATEGY-PARAMETERS.md` §9): the test's own recorded "P3.3 canonical hash" constant had been captured from a different request (the live browser E2E session's `endTime`, which differs from the automated test's own long-standing `VALID_REQUEST` fixture). Resolved by checking out the exact pre-P3.4 commit into an isolated worktree and running the identical request against it directly — proving P3.4 introduces zero change for this fixture, and correcting the test's own comparison constant. This is the section-22 "investigate the difference" process working as intended, not a shortcut.

## 4. Reopen — never a re-simulation

`algoTestService.getAlgoTestRun()` reconstructs a completed run's `parameters` field directly from the persisted `AlgoTestRun.parameters` column — no re-validation, no re-resolution against the (potentially since-changed) registry, no re-run of the engine. The same read-only `candles` reconstruction P3.3 already established (re-fetching bars for the run's own persisted date range via the historical provider) is unaffected by P3.4 — parameters are pure metadata alongside it, not something the reopened chart/marker rendering depends on.

Live-verified: run a Test-B-style non-default-parameter backtest → full browser refresh (F5) → re-select the same pane → the exact same persisted result (same trades, same metrics, same `parameters: {"priceThreshold": 2100}`) reappears without a new engine invocation. See the sprint's final report for the production URL/timestamp this was checked against.

## 5. Backward compatibility — summary

A pre-P3.4 `AlgoTestRun` row has `parameters = NULL`. `AlgoTestRunView.parameters` is `undefined` for such a row — never backfilled with `{priceThreshold: 100}` even though that value is, as a historical fact, what the hardcoded pre-P3.4 code always used. The UI (`ParameterSnapshot` in `AlgoTestPanel.tsx`) renders an explicit "not recorded" note in this case, distinguishing it from "this strategy genuinely has zero declared parameters" (which renders nothing at all). Both are honest; neither guesses.
