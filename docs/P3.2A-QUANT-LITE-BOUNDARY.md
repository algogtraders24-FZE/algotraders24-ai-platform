# P3.2A — Quant Lite / Quant Pro Boundary (Blocker 3)

**Status:** Final architectural sign-off for this phase.

---

## The decision

```text
AT24 Quant Lite
    ↓
Existing shipped legacy backtest system
    ↓
Separate product/path
```

```text
AT24 Quant Pro
    ↓
at24-quant-engine
    ↓
Canonical deterministic backtest engine
    ↓
Native Chart = visual front-end
```

**These two systems are not merged in this phase, and this sprint did not merge them.** Confirmed by `git diff --stat` against `origin/main` for this branch: zero files under `app/quant-lite/**`, `services/quant-lite/**`, `types/quant-lite*.ts`, `data/quant-lite-*.ts`, or `quant-engine/**` (the Python legacy engine) were touched. The concurrent `feat/quant-lite-q1.7-beta-release` branch and its own worktree were never checked out, reset, or written to by this sprint — all P3.2A work happened in an isolated worktree (`git worktree add -b feat/p3.2a-algo-test-foundation`) branched from `main`.

## Scope

- **Quant Lite** (`app/quant-lite/**`) remains on its existing architecture: its own strategy builder, its own execution engine (the legacy Python `execution_mtf.py`, spawned per job), its own file-based job store, its own results UI. Untouched, unmodified, not migrated, not deprecated.
- **Quant Pro** (`at24-quant-engine`) is the canonical deterministic engine for the new Algo Testing path. This sprint gave it a real, stable public package boundary (Blocker 1) and proved it can run a real deterministic backtest against real historical data end to end (Blocker 2 + the Golden Run).

## No cross-coupling, except one explicitly approved case

The brief permits crossing the boundary only "through an explicitly approved shared contract/provider boundary." Exactly one such crossing exists in this sprint's work, and it is data-only:

`services/algo-test/historical-data/market-db-provider.ts` reads `quant_engine/market.db` — the same real historical dataset Quant Lite's Python engine also reads — via its own independent, read-only `node:sqlite` connection and its own SQL query. It imports **nothing** from `services/quant-lite/**` (no job store, no execution adapter, no coverage-policy code, no request-hash logic) and nothing from `quant-engine/spec_engine/**` (no Python code, no subprocess spawning). `market.db` is treated purely as a stable, real data file — structurally the same relationship this provider would have to a CSV file or a broker API response. This is the "isolated provider/adapter" pattern the brief explicitly allows, and is documented in full in `P3.2A-HISTORICAL-DATA-CONTRACT.md` (including why this was chosen over extending a live-quote provider or coupling to Quant Lite's own TypeScript service code).

**What was explicitly NOT done, matching the brief's "Do NOT" list exactly:**
- Quant Lite was not replaced, migrated, or rewritten.
- Native Chart does not use Quant Lite's engine anywhere in this sprint's code.
- The new Pro Algo Test code (`services/algo-test/**`) does not import or depend on any `services/quant-lite/**` module.
- The concurrent `feat/quant-lite-q1.7-beta-release` branch was not modified, merged, reset, or checked out.

## Standing tension, unresolved by design

`P3.1-QUANT-CHART-INTEGRATION-ARCHITECTURE.md` §4 already documented that Quant Lite being a second, already-shipped backtest system is in real tension with "at24-quant-engine is canonical, don't build a second engine." That tension is **not resolved by this sprint** — it is explicitly deferred, per the architectural sign-off above ("two systems, explicitly scoped apart" — Option 1 from the P3.1 doc). This document exists to make that deferral a conscious, recorded decision rather than something a future sprint discovers by accident.
