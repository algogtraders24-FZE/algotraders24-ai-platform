## 2. Codebase Inventory (full detail in Explore findings; summarized here)

### A. Native Chart / AT24 platform (`frontend/`)
- **Native Chart**: `components/chart-engine/NativeChart.tsx` (canvas orchestrator) + `lib/chart-engine/renderer.ts` (stateless `renderChart()`) + `lib/chart-engine/coordinate-system.ts` (`priceToY`/`yToPrice`) + `lib/chart-engine/index-scale.ts` (gapless time↔index mapping) + `lib/chart-engine/drawing/*` (anchored `DrawingObject`s with a reusable `toPx(point, ...)` primitive — the correct model for future trade markers).
- **Chart data**: `useChartCandles()` → `GET /api/private/market-data/candles` → `MarketDataService.getTimeSeriesWithProvenance()` → provider adapters (Twelve Data / Alpha Vantage / Binance / Angel One / MT5). **Latest-N-bars only — no fixed date-range historical query exists** (see `P3.1-DATA-COMPATIBILITY.md` §Gap-1).
- **Paper Trading** (Phase P1+P2, already shipped): `services/paper-trading/paper-trading.service.ts`, `PaperPosition`/`PaperTradingAccount` Prisma models, `/api/private/paper-trading/**` routes. Tightly coupled to **live** bid/ask fetched at action time — has no seam for consuming an externally-computed trade ledger (see `P3.1-FINDINGS.md` §F-4).
- **Quant Lite** (already shipped, real, NOT a placeholder): `app/quant-lite/**`, `services/quant-lite/**`, `types/quant-lite.ts` — a full strategy-builder + backtest UI, backed by the **legacy Python engine** (`quant-engine/spec_engine/execution_mtf.py`) via `child_process.spawn`, file-based job store (`quant-engine/output/jobs/*.json`, **no Prisma, no auth**). This is the single most important fact for this audit — see §4.
- No existing "click result → chart jumps to candle" pattern anywhere in the codebase (confirmed absent, not just unused).

### B. `at24-quant-engine` (TypeScript, canonical per user directive)
- **Strategy IR**: `StrategyIR` (`src/domain/strategy-ir/strategy-ir.ts`) — full cross-platform IR, JSON-serializable. Reduced (lossy, one-way) to the narrower execution-ready `StrategySpec` (`src/domain/strategy-spec.ts`) via `reduceStrategyIRToSpec()`, gated by `checkReductionEligibility()`.
- **MQL4/MQL5 importer**: `importMQLSource()` (`src/runtime/mql-importer/mql-importer.ts`) — lexer→parser→dialect-detector→semantic-analyzer→IR-generator. Supports `iMA/iRSI/iATR/iMACD/iBands`, `OrderSend`/`CTrade.*`, no code generation, no execution of source. 28 catalogued rejection modes (`docs/Q0.8_FAILURE_CATALOG.md`).
- **No compiler/codegen** — `compileStrategy()` orchestrates IR-validation → reduction → hash; `compileToSimulation()` bridges a compiled spec straight into the simulator. `SourceGenerator` is a documented-but-unimplemented stub.
- **Simulation engine**: `runSimulation(bars: OHLCVBar[], config: SimulationConfig): SimulationResult` (`src/runtime/simulation/simulation-engine.ts`) — pure function, bars passed directly, **zero data-access abstraction of any kind**.
- **Orders/positions/risk/ledger/metrics**: fully modeled, deterministic IDs, netting-only positions, pluggable spread/slippage/fee/latency models, append-only `TradeLedger`, `computeCoreMetrics()`. **No `equityCurve` array exists in the real result type** (only in an old unpopulated placeholder). Full field-level detail in `P3.1-QUANT-CHART-CONTRACT.md`.
- **Package boundary**: `package.json` has **no `main`/`exports`/`types`/`bin`** — nothing points an external consumer at `dist/` or `src/index.ts`. Zero runtime dependencies (enforced by `test/isolation.test.ts`). **This package cannot be imported by the frontend today without new packaging work** — true regardless of which integration option is chosen (§16).
- **Tests**: 138 files, ~900+ tests, real determinism/lookahead/golden-fixture coverage. The one true MQL→IR→Spec→Simulation→Trades→Metrics E2E test (`q09-mql-e2e-golden.test.ts`) uses **synthetic** MQL source + synthetic bars. The one **real** MQL source test (the actual G01 gold EA, `mql-g01-import.test.ts` / `q09-g01-reduction.test.ts`) correctly imports but **stays BLOCKED at reduction** — G01 cannot reach a runnable backtest today (see `P3.1-READINESS-MATRIX.md`).
- **No real historical XAUUSD/M5 (or any) OHLCV dataset exists inside this package** — every simulation test uses hand-built fixture bars.

| Area | Expected canonical owner | Actual state | Conflict? |

| Strategy semantics | AT24 Quant Engine | ✅ Matches — `StrategyIR`/`StrategySpec` fully own this | None |

### ⚠️ THE EXACT CONFLICT — must be read before any implementation begins

**`app/quant-lite/**` is a second, complete, already-shipped backtest engine and UI, and it does not use `at24-quant-engine`.**

- It has its own strategy builder (`StrategyBuilderForm.tsx`), its own backtest submission flow (`/api/quant-lite/backtest`), its own execution engine (the **legacy Python** `quant-engine/spec_engine/execution_mtf.py`, invoked via `child_process.spawn`), its own job persistence (flat JSON files, not Prisma, **no auth check on either route**), its own results page (`ResultsView.tsx`), its own equity-curve chart (`EquityCurveChart.tsx` — a deliberately separate inline SVG component, explicitly *not* using Native Chart), and its own trade table (`TradeTable.tsx`).
- It is reachable from the real navbar (`components/layout/Navbar.tsx`), not a dead link or mock.
- It has its own `BacktestRequest`/`BacktestMetrics`/`Trade`/`BacktestResult` types (`types/quant-lite.ts`) — structurally similar in spirit to what `at24-quant-engine` would need for an API contract, but **field-incompatible** (see `P3.1-QUANT-CHART-CONTRACT.md` for the exact diff) and produced by a completely different runtime.
- A separate concurrent session (`feat/quant-lite-q1.7-beta-release`, the branch this audit is running from) is *actively extending* this legacy Python engine right now (Q0.6→Q1.7, "Beta Release Candidate").

**This is a direct violation of the stated architecture** ("`at24-quant-engine` is canonical... do not build a second engine") — except the second engine was built first and is live in production today, and a concurrent session is investing further in it as this audit runs.

**Per the Strict Scope Rule ("do NOT... modify unrelated Quant Lite functionality"), this audit does not attempt to resolve, merge, or deprecate Quant Lite.** It is documented here as a **required strategic decision that sits above P3.2**, not something P3.2 can silently paper over:

1. **Option 1 — Two systems, explicitly scoped apart.** `at24-quant-engine` powers a *new*, Native-Chart-embedded "Algo Test" feature (this sprint's actual target). Quant Lite continues to exist as a separate, older, standalone tool at `/quant-lite`, until a future sprint makes an explicit call on its fate. Users would see two different backtesting surfaces in the product. This is the only option compatible with the Strict Scope Rule *as written*, and is what §16/§17 of this document assume going forward.
2. **Option 2 — Deprecate/migrate Quant Lite onto `at24-quant-engine`.** Correct long-term architecture, but explicitly out of scope for this sprint and a non-trivial migration (different strategy schema, different execution semantics, an existing user-facing library of saved strategies).
3. **Option 3 — Merge forward:** treat Quant Lite's Python engine as the "canonical" one instead, and treat `at24-quant-engine` as the not-yet-shipped one. **Rejected** — contradicts the user's explicit, current directive, and `at24-quant-engine` is materially more rigorous (determinism-tested, typed diagnostics, no-lookahead-tested, real MQL importer) than what's known about the legacy engine.

**This audit recommends Option 1 for P3.2**, with the conflict recorded here so it is a conscious, visible decision rather than an accidental one.

## 5. Chart Visualization Capability (summary — full contract in `P3.1-QUANT-CHART-CONTRACT.md`)

Native Chart **can** already draw an arbitrary marker at an exact (timestamp, price) point — the Drawing Tools system's `toPx(point, candles, indexRange, viewport, plotWidth, row)` (`lib/chart-engine/drawing/drawing-renderer.ts`) is the exact primitive to reuse; `drawTradeLine()` (Paper Trading) is a live-price-only sibling, not directly reusable for a fixed-time trade marker but proof the rendering approach is sound and already shipped once.

Native Chart **cannot** today: accept an externally supplied "jump to this timestamp" instruction (no imperative ref, no such prop), render multiple simultaneous entry/exit/SL/TP markers for many trades at once (never built), or distinguish overlapping trades visually (never needed to before). All net-new work, but built on solid, proven primitives (`fractionalIndexForTime`, `indexToX`, `priceToY`, `fitToData`/viewport helpers).

## 6. Trade Selection / Inspection — Design

```
User clicks Trade #37 (in a new trade-list component, NOT the existing quant-lite TradeTable — that has zero
click handlers and lives in a different, unrelated feature)
        ↓
Client already holds the full AlgoTestRun result (fetched once; trades are typically small-N, see Data
Compatibility doc §Performance) — no extra API call needed to get trade #37's own fields
        ↓
new NativeChart imperative handle: chartRef.current.jumpToTime(trade.entryTime, trade.exitTime)
        ↓
Internally: fractionalIndexForTime() locates the candle index for entryTime/exitTime →
compute a Viewport bounding both (existing viewport.ts math, same style as fitToData) → setViewport()
        ↓
Renderer draws entry/exit/SL/TP markers via toPx() at the trade's own price fields — same render pass,
gated the same way trade-lines are (`symbol === activeSymbol`)
```

Requirements this surfaces that don't exist yet:
- `NativeChart` needs to become `forwardRef` with a `NativeChartHandle.jumpToTime(...)` method (mirrors the existing `PaperTradingPanelHandle` pattern exactly — same codebase idiom, zero new architecture invented).
- Candle data for the *backtest's own date range* must already be loaded in the chart (or fetched on demand) — if the user is viewing "live, latest 300 candles" and the backtest ran over 2023, the candles for trade #37's entry time will not be in `useChartCandles()`'s current window. This requires either (a) the historical-range candle fetch capability that's *also* needed for the engine's own bars (Gap-1, one fix serves both), or (b) accepting that Algo Test results can only be inspected for date ranges currently in the live chart's rolling window (a real, disclosable limitation for an MVP).

## 7. Strategy Import Flow — Audit Result

```
MQL4/MQL5 EA → importMQLSource() → StrategyIR → compileStrategy()/reduceStrategyIRToSpec() → StrategySpec → runSimulation()
```

This pipeline **is real and already connectable in principle** — nothing about it is frontend-shaped or frontend-blocked. The gap is entirely on the frontend side (no API wraps it, no UI calls it) and on the *content* side:

- **Supported syntax**: `iMA/iRSI/iATR/iMACD/iBands`, `OrderSend`/`CTrade.Buy/Sell`, basic control flow, `#include`/`#define` (recorded, not expanded).
- **Unsupported / explicitly rejected**: `iCustom`, negative/non-literal array shifts, `#import "x.dll"`, `WebRequest`, `TimeLocal()`, any cross-file function call (95 such calls found in the real G01 EA), `switch`/`while`/`do-while` (skip-recovered, not modeled).
- **The only real MQL source file in the repo, the G01 gold EA, imports cleanly (zero blocking diagnostics) but is correctly BLOCKED at the reduction/eligibility stage** — its entry logic is a cross-file, multi-bar state machine the current IR cannot represent. **G01 cannot be the initial P3.2 validation strategy.**
- Per the Strict Scope Rule, **importer scope is not to be expanded in this sprint** — this audit does not propose fixing G01's blocked status.

**Implication for P3.2's initial validation path (§ below)**: use a simple, hand-authored `StrategySpec` (the same shape the engine's own golden-fixture tests already use — e.g. an MA-cross or fixed-threshold entry with fixed SL/TP) rather than an imported MQL EA, to prove the Native-Chart↔Quant-Engine plumbing without being blocked by importer/reduction limitations that are out of scope to fix here.

## 8. Integration Strategy Decision (§16 of the sprint spec)

### Option A — Direct coupling
Native Chart (Next.js/React runtime) calls `at24-quant-engine`'s internal functions directly.
**Rejected.** `at24-quant-engine/test/isolation.test.ts` explicitly asserts this package has zero runtime dependencies and is not a workspace member — deliberately built to be usable by *anything*, but not deliberately wired to Next.js. Direct coupling would mean importing raw TypeScript source across a package boundary that was never built for it (no `main`/`exports`), and would blur "who validates a strategy is safe/eligible before running" — that logic should stay server-side, not duplicated into client bundles.

### Option B — API/service boundary *(recommended)*
Native Chart calls a new, stable `Algo Test` service (`services/algo-test/algo-test.service.ts` + `app/api/private/algo-test/**`, following the exact `withContext`+`getUserOrNull()`+`ApiResponse` convention every other private route uses). That service is the *only* code that imports `at24-quant-engine` (once it's given a proper package export — a genuinely tiny, additive change: a `main`/`exports`/`types` field plus keeping the existing `src/index.ts` barrel). Native Chart never knows `runSimulation`/`SimulationConfig`/`OHLCVBar` exist — it only knows the Algo Test API's request/response contract (`P3.1-QUANT-CHART-CONTRACT.md`).

This matches the user's own default recommendation and is the only option consistent with: (a) `at24-quant-engine`'s isolation test, (b) the platform's universal `/api/private/**` ownership/auth convention (§ Findings doc — quant-lite's unauthenticated routes are exactly the anti-pattern to avoid), (c) keeping strategy-eligibility/compilation logic server-side only.

### Option C — Shared library/package
Both systems import shared engine components as a formal internal package.
**Not recommended for P3.2.** This is really "Option A, formalized" — it still requires the same packaging fix as Option B, but additionally requires deciding on monorepo tooling (there is no existing pnpm/turborepo workspace linking `frontend/` and `at24-quant-engine/` — `isolation.test.ts` confirms the engine isn't a workspace member today). It's a reasonable *future* evolution once Option B's API boundary proves the contract is stable, not a starting point.

**Decision: Option B.**

## 9. Recommended Initial E2E Path (P3.2 target)

```
Native Chart
    ↓
Select a hand-authored deterministic StrategySpec (NOT an MQL import — G01 is blocked, see §7)
    ↓
Select XAUUSD / M5 / a fixed date range for which real historical bars can be sourced
    (requires closing Gap-1 — see Data Compatibility doc — or using Quant Lite's existing
     historical-data infrastructure as the bar source, which is real and already coverage-checked)
    ↓
Submit Algo Test → new POST /api/private/algo-test/runs
    ↓
Quant Engine: compileStrategy() → compileToSimulation()/runSimulation()
    ↓
Deterministic Backtest completes; SimulationResult persisted as a new Prisma AlgoTestRun record (userId-owned)
    ↓
Return Test Result → GET /api/private/algo-test/runs/[id]
    ↓
Native Chart renders trade list + calls new jumpToTime() handle
    ↓
Render trades (toPx()-based entry/exit/SL/TP markers)
    ↓
Select trade → jump to candle
```

Concrete build sequence (informational — not performed in this sprint):
1. Add `package.json` `main`/`exports`/`types` to `at24-quant-engine` pointing at its existing `dist/` build (additive, zero behavior change — the "tiny isolated proof" this sprint's scope allows if needed, though not executed here since no ambiguity required it).
2. Curate one new, minimal public function inside `at24-quant-engine` (e.g. `runDeterministicBacktest(request): AlgoTestEngineResult`) composing `compileStrategy()`+`compileToSimulation()`/`runSimulation()` — additive only, does not touch existing exports.
3. New Prisma models (`AlgoTestRun`, and either an embedded JSON trades array or a child `AlgoTestTrade` model — see Contract doc for the size/pagination tradeoff) under the existing schema conventions.
4. New `services/algo-test/algo-test.service.ts` + `app/api/private/algo-test/{runs, runs/[id]}/route.ts`, `getUserOrNull()`-gated.
5. Resolve the historical-bars source for the API layer (Gap-1) — either extend the market-data layer with a range query, or read from Quant Lite's existing real historical dataset (data only, not its execution engine — does not violate "don't build a second engine," and does not touch quant-lite's own UI/routes).
6. New Native Chart "Algo Test" panel (parallel to `PaperTradingPanel`, same activation gating) for strategy pick + submit + poll.
7. `NativeChart` becomes `forwardRef` with `jumpToTime()`; new trade-marker renderer using `toPx()`.
8. Trade-list UI with row selection (new component; do not reuse quant-lite's `TradeTable.tsx`, which has no click handling and belongs to the separate system per §4).
9. E2E validate on XAUUSD/M5 with the hand-authored strategy from step 1; live-verify per this platform's standing discipline.

See `P3.1-READINESS-MATRIX.md` for the final go/no-go call.
