# P3.3 — Result Contract Hardening

**Status:** Implemented, live-verified. See `P3.3-STRATEGY-REGISTRY.md` for where `strategyVersion` comes from and `P3.3-ALGO-TEST-PRODUCTIZATION.md` for the sprint's full scope.

---

## 1. What changed

Two things hardened: (a) every persisted `AlgoTestRun` now carries explicit version metadata for reproducibility, and (b) `SimulationTrade`/`AlgoTestTradeView` gained `exitReason`/`stopLoss`/`takeProfit` — a real, additive `at24-quant-engine` change, not a frontend-only reinterpretation of existing data.

## 2. Persisted version metadata

New nullable columns on `AlgoTestRun` (migration `20260902120000_add_algo_test_contract_versioning`):

| Column | Source | Populated when |
|---|---|---|
| `strategyVersion` | `strategy-registry.ts`'s `StrategyDefinition.strategyVersion` (itself `buildGoldenStrategySpec().version`) | Every run, including a failed one — the strategy identity is known before the engine ever runs. |
| `resultVersion` | `services/algo-test/result-contract.ts`'s `RESULT_CONTRACT_VERSION` (`"1.0"`) — this persisted row's own field-shape version | Only on a **completed** run — a failed run has no "result" to version. |
| `engineVersion` | `SimulationResult.provenance.runtimeVersion`, copied verbatim — never a duplicated literal | Only on a **completed** run. |

All three are nullable and **never backfilled** for rows created before this migration (P3.2B's own live-tested runs, `strategyId: "golden"` with no version recorded) — an old row stays honestly identifiable as pre-dating versioning, rather than being given a guessed value.

`resultHash` (unchanged from P3.2A/P3.2B) remains the engine's own `computeCanonicalHash()` fingerprint over the entire `SimulationResult` — the determinism proof (see §5) compares this directly, not a derived summary.

## 3. Trade Result Contract — engine-side additive change

`at24-quant-engine`'s `SimulationTrade` (`src/domain/simulation/trade.ts`) previously had no `stopLoss`/`takeProfit`/`exitReason` fields — flagged back in P3.1 (`P3.1-READINESS-MATRIX.md` row "Trade result contract: PARTIAL") as "two small additive gaps." P3.3 closed them:

```ts
export interface SimulationTrade {
  // ...unchanged fields (tradeId, side, entryPrice, exitPrice, netPnl, rMultiple, ...)
  readonly stopLoss?: number;
  readonly takeProfit?: number;
  readonly exitReason?: string;
}
```

**`stopLoss`/`takeProfit`** — zero new computation. `buildTrade()` (`src/runtime/simulation/trade-ledger.ts`) already receives the full closing `Position` object, which already carries `stopLoss`/`takeProfit` (set at entry, possibly moved by breakeven/trailing management). These are now copied straight onto the returned trade record, omitted (never `0` or fabricated) when the position never had one.

**`exitReason`** — threaded from the four places `simulation-engine.ts` actually closes a position, each genuinely known at its own call site, never invented:

| Close path | `exitReason` |
|---|---|
| Protective SL/TP resolution (`resolveProtectiveExit`) | The engine's own real reason string, e.g. `"stop-loss reached"`, `"take-profit reached"`, or the same-bar-ambiguous case's own description — passed through verbatim, `exit.reason`. |
| Risk-engine `FORCE_EXIT` | `"risk engine forced exit"` |
| Risk-engine `REDUCE_POSITION` (partial close) | `"risk engine partial close"` |
| Opposite-side order fill reducing/closing a position | `"opposite-side order fill reduced/closed the position"` |

There is deliberately **no fifth, catch-all case** — every real close path in the engine is one of these four (confirmed by direct code read of `simulation-engine.ts`; there is no end-of-data forced liquidation — an open position at the end of a backtest simply remains open, reported separately via `SimulationResult.finalPositions`, never synthesized into a trade). A future close path would need its own real reason threaded the same way, never a default string.

All 1095/1095 existing `at24-quant-engine` tests pass unchanged after this addition — confirmed via a full `npm test` run in the engine package before re-vendoring into `frontend/vendor/at24-quant-engine`.

`AlgoTestTradeView` (`types/algo-test.ts`) and `algo-test.service.ts`'s `toTradeView()` pass these three fields through the same way — present only when the engine's own trade record carried them.

## 4. Result Detail Page reopen (persisted, not re-simulated)

`GET /api/private/algo-test/runs/[id]` (`algoTestService.getAlgoTestRun()`) reconstructs a completed run's full view from the **persisted row alone** — `metrics`, `trades`, `equityCurve`, `assumptions`, `resultHash`, and the new `strategyVersion`/`resultVersion`/`engineVersion` fields are all read directly off the database row, byte-identical to what the original run produced. The engine is never re-invoked on this path.

The one exception is `candles`: deliberately never persisted (unchanged from P3.2B — see the field's own doc comment in `types/algo-test.ts`, "do not store unnecessarily huge raw datasets"). To let a reopened result still render chart trade markers, `getAlgoTestRun()` now re-fetches bars for the run's own persisted `symbol`/`timeframe`/date-range through the **same read-only historical provider** used at run time (`twelveDataHistoricalDataProvider`) — a data re-fetch, not a re-simulation. This is explicitly best-effort: if the provider call fails on reopen, `candles` is simply absent from the response and every other field (metrics/trades/equity/assumptions) remains fully intact — a transient provider hiccup on reopen must never turn an already-successful, fully-persisted result into an error.

The browser round-trips a completed run's `testId` through a `?algoTestId=` URL query parameter (`AlgoTestPanel.tsx`, `window.history.replaceState` after a successful run) so a page refresh re-fetches and re-renders the exact same persisted result via this same path — verified live (see `P3.3-ALGO-TEST-PRODUCTIZATION.md` §Live E2E).

## 5. Determinism (permanent regression)

`scripts/validate-algo-test-service.ts`'s "Determinism: RUN #1 === RUN #2" test (present since P3.2B, extended this sprint) runs the identical request twice through the real service against real Twelve Data data and asserts byte-identical `resultHash`, `metrics` (deep-equal), `strategyVersion`, `resultVersion`, `engineVersion`, and per-trade `tradeId`/`pnl` across both runs. This is a permanent, real (not mocked) regression test — not weakened to pass; both runs go through the complete real pipeline (provider → engine → persistence).
