## 20. Final Output

```
ARCHITECTURE DECISION:
REUSE AT24 QUANT ENGINE

P3.2 READINESS:
BLOCKED
```

### Exact blockers (must clear before P3.2 implementation begins, in dependency order)

1. **Package boundary.** `at24-quant-engine` needs `package.json` `main`/`exports`/`types` pointing at its existing `dist/` build (or an equivalent workspace-import mechanism). Purely additive, zero behavior change, low risk — the natural first PR of P3.2, not a design question.
2. **Historical-bars source decision.** Pick one of the two candidates in Data Compatibility doc §Gap-1 (extend a live provider with range-query support, or reuse Quant Lite's existing real dataset for *data only*) and confirm it can actually deliver XAUUSD/M5 for a real date range before any other P3.2 work depends on it. This is the one blocker that is a genuine open question, not just unbuilt code.
3. **Canonical-ownership decision (strategic, not code).** Explicit, recorded sign-off that P3.2 proceeds under "Option 1: two systems, explicitly scoped apart" (Architecture doc §4), so nobody later discovers Quant Lite mid-build and treats its existence as a P3.2 defect. This can be a one-line decision, but it must be made consciously before implementation, per the sprint's own instruction not to silently paper over the conflict.
4. **Execution-assumption disclosure requirement accepted as a P3.2 UI/contract requirement**, not an optional nice-to-have — every backtest result must state that spread/slippage/fees/margin are zero-cost/unenforced, exactly like Quant Lite's own `ExecutionAssumptions` pattern.

### Once the above three decisions/changes land, everything else in this matrix is genuinely **buildable, not blocked** — the engine's core logic, the chart's rendering primitives, the API/auth conventions, and the security posture are all already solid. This is not a "the codebase isn't ready" verdict; it is a "three specific, named things must be decided or added first, then P3.2 has a clean, low-risk path" verdict.

### If those three items are resolved, the exact P3.2 implementation sequence is (full detail in Architecture doc §9):

1. Add `at24-quant-engine` package exports (additive).
2. Add one new curated public function inside `at24-quant-engine` composing `compileStrategy()` + `runSimulation()`/`compileToSimulation()`, plus the small `exitReason`-threading addition (Contract doc §3).
3. New Prisma models (`AlgoTestRun` + trade storage), `userId`-owned, following the Paper Trading precedent exactly.
4. New `services/algo-test/algo-test.service.ts` + `app/api/private/algo-test/**` routes, `getUserOrNull()`-gated, using the standard `ApiResponse` envelope and the error-code mapping in Contract doc §4.
5. Wire the chosen historical-bars source (blocker #2) into that service layer.
6. New Native Chart "Algo Test" panel (parallel to `PaperTradingPanel`), a hand-authored deterministic starter strategy (not an MQL import — G01 stays out of scope), submit/poll UI.
7. `NativeChart` becomes `forwardRef` with `jumpToTime()`; new trade-marker renderer built on `toPx()`, with viewport-intersection clustering for large trade counts.
8. New trade-list component with row selection (do not reuse Quant Lite's `TradeTable.tsx` — different, unrelated system).
9. E2E validate on XAUUSD/M5 with the hand-authored strategy; live-verify per this platform's standing discipline before considering P3.2 shipped.
