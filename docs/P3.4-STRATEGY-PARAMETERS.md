# P3.4 — Strategy Parameters & Reproducible Configuration

**Status:** Implemented, tested, live-verified. Builds on the production-verified P3.3 architecture (`docs/P3.3-STRATEGY-REGISTRY.md`, `docs/P3.3-RESULT-CONTRACT.md`). Companion docs: `P3.4-CONFIGURATION-CONTRACT.md`, `P3.4-VERSIONING.md`.

---

## 1. The Golden Strategy parameter audit

Per this sprint's explicit instruction ("audit the existing Golden Strategy... only expose category #1 as Strategy Parameters... if the strategy has no configurable parameters that can safely be exposed without changing its semantics, STOP and report that fact rather than inventing parameters"), every numeric/boolean/string value in `at24-quant-engine/src/reference/golden-strategy.ts`'s `buildGoldenStrategySpec()` was classified:

| Value | Category | Exposed as a Strategy Parameter? |
|---|---|---|
| Entry condition threshold (`PRICE > 100`) | **#1 — genuine strategy parameter.** This is the entry signal's own defining input — the ONE thing that actually decides whether/when the strategy enters. | **Yes** — `priceThreshold`. |
| `risk.sizing.quantity` (fixed-quantity = 1) | #2 — execution/risk configuration (position sizing), not a signal parameter. | No — see §2. |
| `risk.stopLoss.distance` (fixed-distance = 5) | #2 — risk configuration. | No — see §2. |
| `risk.takeProfit.rMultiple` (risk-multiple = 2) | #2 — risk configuration. | No — see §2. |
| `execution.fillModel` / `costsExplicitlyZero` | #4 — engine/execution internals, already disclosed via `AlgoTestAssumptions` (P3.1/P3.2B). | No. |
| `spreadModel`/`slippageModel`/`feeModel`/`latencyModel` (all `Zero*`, set in `run-golden-backtest.ts`) | #4 — engine internals / execution assumptions. | No. |
| `datasetId`/`datasetVersion` | #3 — provider/data configuration (symbol/timeframe/date-range, already its own part of the canonical config, not a "strategy parameter"). | No. |
| `identity`, `version`, `metadata`, `instruments`, `timeframes` | Structural/identity fields, not parameters. | No. |

**Result: exactly ONE genuine, category-1 strategy parameter exists — `priceThreshold`.** No second parameter was invented to make the feature look richer than the strategy actually is. `risk.sizing`/`stopLoss`/`takeProfit` are real, currently-hardcoded configuration values, but they are risk/execution configuration (category #2, explicitly excluded from this sprint's "Strategy Parameters" per the spec's own taxonomy) — they remain fixed, unchanged, exactly as P3.2B/P3.3 already established ("Risk Configuration: Not exposed"). A future sprint could deliberately open up `riskConfig` as its own, separately-designed contract (already named as a placeholder field in the canonical config shape, see `P3.4-CONFIGURATION-CONTRACT.md`) — that is out of scope here.

## 2. Why risk/sizing values are NOT strategy parameters

The Golden Strategy's `risk` block answers "how much to risk and how to exit a position once entered" — a different question from "when does the strategy decide to enter." Exposing `stopLoss.distance`/`takeProfit.rMultiple`/`sizing.quantity` as user-tunable inputs would be building risk configuration (the P3.4 spec's own category #2, and its own separate, not-yet-designed `riskConfig` slot in the canonical contract) — not a strategy parameter. Conflating the two would blur a distinction the spec itself draws, and would silently expand this sprint's scope into risk-configuration design (which needs its own validation semantics — e.g., "is a 0-distance stop meaningful?" — that this sprint never asked for).

## 3. Parameter types actually implemented

`services/algo-test/strategy-registry.ts`'s `StrategyParameterType` supports exactly `"number" | "integer" | "boolean" | "select"` — the full type surface `validateParameterValues()` and `AlgoTestPanel.tsx`'s `ParameterField` can render, but **only `"number"` is exercised by the real registry** (the Golden Strategy's one parameter). No generic dynamic-form framework was built for hypothetical future needs; `boolean`/`select`/`integer` code paths exist because they cost nothing extra to implement generically alongside `number`, and are proven correct via `scripts/validate-algo-test-parameters.ts`'s own synthetic fixture (never registered in production) — not because a real parameter needs them today.

## 4. `priceThreshold` — the parameter itself

| Field | Value |
|---|---|
| `id` | `priceThreshold` |
| `label` | "Entry Price Threshold" |
| `type` | `number` |
| `defaultValue` | `100` (read from `at24-quant-engine`'s own exported `GOLDEN_STRATEGY_DEFAULT_PRICE_THRESHOLD` constant — never a duplicated literal) |
| `min` / `max` | `0` / `1,000,000` |
| `required` | `false` |

**Real, provable effect on execution**, not cosmetic: for XAUUSD (trading in the thousands), the default (100) makes the entry condition always true — matching the exact P3.3 canonical behavior. Raising it above the instrument's real price range (e.g. `2100` against a 2024-01-08→13 window whose bars never exceed ~2055) makes the strategy genuinely, correctly never enter — zero trades, not an error. Both directions are verified live: `test/golden-strategy-parameters.test.ts` (engine level) and `scripts/validate-algo-test-service.ts`'s "Test B" (full service level, real Twelve Data data).

## 5. The engine-side change — additive, default-preserving

`at24-quant-engine/src/reference/golden-strategy.ts`:

```ts
export const GOLDEN_STRATEGY_DEFAULT_PRICE_THRESHOLD = 100;
export interface GoldenStrategyParams { readonly priceThreshold?: number; }
export function buildGoldenStrategySpec(params: GoldenStrategyParams = {}): StrategySpec { /* ... */ }
```

`buildGoldenStrategySpec()` and `buildGoldenStrategySpec({})` both still produce the **exact pre-P3.4 spec** — same `parameters: []`, same `literal(100)` in the entry condition. No existing caller (the engine's own 1101 tests, `run-golden-backtest.ts`) needed to change.

**A deliberate design decision**: `spec.parameters` (the engine's own `StrategyParameterDefinition[]` field, part of `StrategySpec` since Q0) is left `[]` regardless of whether `priceThreshold` is overridden. An audit of the entire engine (`grep -r "spec.parameters"` across `src/`) found this field has **zero runtime consumers anywhere** — it is validated (duplicate-key/min-max checks in `validateStrategySpec()`) but never read by the signal generator, risk evaluator, or simulation engine. Populating it would only add a cosmetic, functionally-inert entry that changes `computeSemanticStrategyHash()`'s output for no behavioral reason (see `P3.4-VERSIONING.md` §Determinism for why this matters). The frontend Strategy Registry (`services/algo-test/strategy-registry.ts`) is this parameter's authoritative, user-facing schema — the engine's own `spec.parameters` stays exactly as unused as it always was.

## 6. Engine regression

`npm test` inside `at24-quant-engine/` after this change: **1101/1101 pass** (1095 pre-existing + 6 new, in `test/golden-strategy-parameters.test.ts`, covering: no-arg call unchanged, `{}` structurally identical to no-arg, an explicit default-matching value structurally identical, a non-default value changes only the entry condition literal, a threshold above every bar's price genuinely produces zero trades, and determinism for a non-default value).

## 7. Backward compatibility

Every `AlgoTestRun` row created before this migration (`prisma/migrations/20260903090000_add_algo_test_parameters`) has `parameters = NULL`. This is **never backfilled** with a guessed value (not even `{priceThreshold: 100}`, even though that was in fact the pre-P3.4 hardcoded behavior) — `algoTestService.getAlgoTestRun()` returns `parameters: undefined` for such a row, and `AlgoTestPanel.tsx`'s `ParameterSnapshot` renders an explicit "Not recorded — this result predates P3.4 parameter tracking" note rather than silently implying today's registered default was used. Verified live in `scripts/validate-algo-test-service.ts`'s backward-compatibility test (a real, directly-inserted legacy-shaped row, reopened via the real service).

## 8. Security

`validateParameterValues()` (`services/algo-test/strategy-registry.ts`) is the sole authority: it reads the parameter **schema** only from the server-resolved `StrategyDefinition` (never from the client request), and treats the client's `parameters` object purely as **submitted values** keyed by declared parameter id. A client submitting schema-shaped keys (`min`, `max`, `options`, extra unknown ids) alongside a real value has zero effect on validation rules — those keys are simply treated as unknown parameters and rejected, proven in `scripts/validate-algo-test-parameters.ts`'s security tests. No `eval`/`Function`/dynamic code path exists anywhere in the validation or engine-mapping code — every value is a plain JSON-typed primitive (`number | boolean | string`), and a string submitted where a number is required is rejected as a type error, never coerced or evaluated.

## 9. Determinism (permanent regression)

Section 22's own compatibility gate — the hardest requirement in this sprint — is proven directly, not assumed: `scripts/validate-algo-test-service.ts` checks out `origin/main` at the exact pre-P3.4 commit (`a8e0812`) into an isolated worktree and runs the identical canonical request (`VALID_REQUEST`: Golden Strategy defaults, XAUUSD/M5, `2024-01-08T00:00:00Z`→`2024-01-13T00:00:00Z`, $10,000) against it, confirming the exact resultHash `0522a91f136d6c94b757482aab7ef3f640f4c4192af8356b8362b449a9bf527f` and 26 trades — then asserts P3.4's own code produces the byte-identical hash and trade count for the same request. (An earlier draft of this test mistakenly compared against a resultHash captured from a *different* request — the program's live browser E2E session, which uses a different `endTime`, per `AlgoTestPanel.tsx`'s own end-of-day convention — that mismatch was investigated and resolved as a test-authoring error, not an engine regression; see the git history of this test file for the full investigation.)
