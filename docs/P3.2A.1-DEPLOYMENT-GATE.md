# P3.2A.1 — Deployment Gate (Gates 1, 6, 7)

**Status:** PASS. `frontend`'s dependency on `at24-quant-engine` is now deployable independent of Vercel's Root Directory / monorepo-inclusion settings — proven by an actual isolated reproduction of the production build path, not assumed.

---

## Gate 1 — Vercel Dependency

### What was actually checked before touching anything

- `frontend/vercel.json` exists but sets only `crons` — no `buildCommand`/`installCommand`/`rootDirectory` override. Those settings, if customized, live exclusively in the Vercel Dashboard, which this environment has no credentials to query (`vercel whoami`/`vercel project ls` both require an interactive browser login not available here — attempted and confirmed blocked, not skipped).
- `frontend/.vercel/project.json` exists (`projectId`/`orgId`/`projectName`), confirming the Vercel project was linked **from inside `frontend/`** — strong circumstantial evidence (not a direct dashboard read) that the project's Root Directory is `frontend`, matching Vercel's standard monorepo-subdirectory pattern.
- **No repository-root `package.json`/npm workspace exists** — `frontend/` is a fully standalone npm project (its own `package-lock.json`), not part of any workspace today.
- `frontend/next.config.ts` already carries a real, documented precedent for exactly this class of problem: `outputFileTracingIncludes` was added in an earlier sprint because "Next's automatic serverless-function file tracer only detects statically-analyzable fs paths... silently dropping this directory from the deployed bundle." This confirmed the risk category (files needed at build/runtime silently missing from what Vercel actually deploys) is real and has bitten this project before.

### Required answer — is `frontend → ../at24-quant-engine` resolvable during a production build?

**Determined empirically, not assumed: NO.**

A fresh, fully isolated copy of `frontend/` (no sibling `at24-quant-engine/` present anywhere — the exact worst-case shape of "Root Directory = frontend, sibling directories not included") was built with the then-current `"at24-quant-engine": "file:../at24-quant-engine"` dependency:

```
$ npm install     # succeeds (exit 0) - but silently creates a BROKEN symlink
                    # node_modules/at24-quant-engine -> <nonexistent path>
$ npm run build   # FAILS
  ./scripts/validate-algo-test-foundation.ts:13:48
  Type error: Cannot find module 'at24-quant-engine' or its corresponding
  type declarations.
```

Two findings, both important:
1. **`npm install` does NOT fail** on a `file:` dependency whose target doesn't exist — it happily creates a dangling symlink and exits 0. This means a naive "did `npm install` succeed" check would have been a false positive.
2. **`next build`'s TypeScript step fails hard** the moment anything imports the unresolvable package. In this sprint's case that surfaced in a dev-only script; if a real API route had imported it instead (the P3.2B plan), this would have been an even worse failure mode — either a build break (good, loud) or, if the import path were dynamic/late-bound, a silent runtime 500 in production (bad, per the `outputFileTracingIncludes` precedent above).

### The fix — vendor the built package inside `frontend/`'s own tree

Chosen from the brief's own preferred directions ("buildable package included within the repository build context"), rejecting the alternatives:
- **npm workspace at the repo root** — the cleanest long-term answer, but *still* depends on Vercel's Root Directory/"include outside root" setting being correct, which this environment cannot verify. Not chosen as the immediate fix for exactly that reason (see "Future evolution" below).
- **External registry** (npm/GitHub Packages) — explicitly excluded by the brief ("do not introduce an external registry unless genuinely necessary"); not necessary here.
- **Duplicating source** — explicitly excluded ("do not duplicate the Quant Engine source"); not done — see below.

**What was built**: `frontend/scripts/vendor-quant-engine.mjs` — builds `at24-quant-engine` (`npm run build`, producing fresh `dist/`) and copies **only the compiled `dist/` output** plus a trimmed `package.json` (`name`/`version`/`type`/`main`/`types`/`exports` — no scripts, no devDependencies) into `frontend/vendor/at24-quant-engine/`. This is **not source duplication** — the same relationship any npm package has to its consumer (you never see a published package's TypeScript source, only its build output); the single source of truth remains `at24-quant-engine/src/`. `frontend/package.json` now depends on `"at24-quant-engine": "file:./vendor/at24-quant-engine"` — a path **inside** `frontend/`'s own tree, not a sibling.

**Maintenance note, disclosed not hidden**: whenever `at24-quant-engine/src/` changes, a developer must re-run `npm run vendor:quant-engine` (from `frontend/`) and commit the refreshed `frontend/vendor/at24-quant-engine/` directory. This is the real, accepted tradeoff of avoiding both a registry and an unverified workspace-inclusion setting.

## Gate 7 — Quant Engine Import

```ts
import { runSimulation, buildGoldenStrategySpec } from "at24-quant-engine";
```

Resolves successfully in the isolated build above — proven by the build reaching `next build`'s TypeScript step and completing with zero errors from that import (previously the exact failure point). No relative internal import (`../../at24-quant-engine/src/...`) is used anywhere in the consuming code — only the package specifier. The one remaining symlink (`node_modules/at24-quant-engine -> vendor/at24-quant-engine`) is npm's standard mechanism for any `file:`/workspace dependency and points **inside** the deployed file set, not at a developer-machine-only path — this is the same mechanism npm/yarn/pnpm workspaces themselves use in production Vercel deployments every day, not a fragile one-off. **PASS.**
