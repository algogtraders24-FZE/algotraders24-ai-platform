# P3.4 — Canonical Configuration Contract

**Status:** Implemented. See `P3.4-STRATEGY-PARAMETERS.md` for the parameter audit and `P3.4-VERSIONING.md` for versioning/determinism detail.

---

## 1. The request contract

```ts
interface AlgoTestRunRequest {
  strategyId: string;
  strategyVersion?: string;               // P3.3 - optional pin
  parameters?: Record<string, unknown>;   // P3.4 - raw submitted values, id -> value
  symbol: string;
  timeframe: string;
  startTime: string;                      // ISO 8601
  endTime: string;                        // ISO 8601
  initialBalance?: number;
}
```

`riskConfig` (named in the P3.4 spec's own conceptual canonical shape) is **not** part of this contract. As established in `P3.4-STRATEGY-PARAMETERS.md` §2, the Golden Strategy's risk/sizing values are deliberately excluded from this sprint's scope (category #2, not a "strategy parameter"), and no new risk-configuration contract was designed or requested. `riskConfig` remains the engine's own fixed, internal default — unchanged since P3.2B ("Risk Configuration: Not exposed").

`parameters` is optional in two independent ways: the whole field may be omitted (every declared parameter uses its registered default), and any individual declared parameter within it may be omitted (that one parameter uses its own default while others are explicit). The server never requires a caller to enumerate every parameter.

## 2. Never trust the client's schema

Section 15/16 of the P3.4 spec: the client's `parameters` object is **values only**. The server (`algoTestService.runAlgoTest()` → `validateRequest()` → `validateParameterValues()`) always re-resolves the authoritative `StrategyDefinition` (and therefore its parameter schema — labels, types, min/max/step/options/defaults) from `services/algo-test/strategy-registry.ts`, keyed by the server-resolved `strategyId`/`strategyVersion` — never from anything the client sent. A client cannot widen a `min`/`max`, redefine a `type`, or inject a new parameter id by including schema-shaped keys in its request — those keys are simply unknown parameters and rejected (proven in `scripts/validate-algo-test-parameters.ts`'s Security section).

`GET /api/private/algo-test/strategies` is the one place schema metadata (label/description/type/default/min/max/step/options) is exposed to the browser, precisely so `AlgoTestPanel.tsx` can render real controls — but that response is itself server-generated from the same registry, never accepted back as input.

## 3. Server-side validation order

`algo-test.service.ts`'s `validateRequest()`, run in this exact order, before any historical-data fetch or simulation:

1. **Strategy** — registered and `status === "available"` → else `INVALID_STRATEGY`.
2. **Strategy version** (only if supplied) — exact match → else `INVALID_STRATEGY_VERSION`.
3. **Parameters** — every submitted key is a declared parameter id; every value matches its declared type; required parameters are present; numeric values respect `min`/`max`/`step`; `select` values are one of `options` → else `INVALID_PARAMETERS` (all violations joined into one message, `field: message; field: message`).
4. **Symbol** → else `INVALID_SYMBOL`.
5. **Timeframe** → else `INVALID_TIMEFRAME`.
6. **Date range** (parseable, `start < end`, not in the future, ≤ `MAX_RANGE_DAYS`) → else `INVALID_DATE_RANGE` / `RANGE_TOO_LARGE`.
7. **Initial balance** (finite, positive) → else `INVALID_INITIAL_BALANCE`.

This ordering mirrors the canonical config shape's own field order (strategy → version → parameters → symbol/timeframe → dates → balance). Every branch here is covered by a real test in `scripts/validate-algo-test-service.ts` (real DB + real Twelve Data) and `scripts/validate-algo-test-parameters.ts` (pure unit, the validator in isolation).

## 4. Engine mapping — one explicit, named function, not a generic pass-through

```ts
function toGoldenStrategyOverrides(parameters: AlgoTestParameterValues): { priceThreshold?: number } {
  const { priceThreshold } = parameters;
  return typeof priceThreshold === "number" ? { priceThreshold } : {};
}
```

This is the **one** place validated parameters cross into `at24-quant-engine`'s own public API (`buildGoldenStrategySpec()`). It is deliberately a small, named, per-strategy mapping — never `runGoldenBacktest({ ...parameters })` (spreading an arbitrary object into engine internals). A future second registered strategy gets its own equally explicit mapping function; there is no generic "spread the parameters object into whatever the engine wants" contract, matching the spec's own instruction ("map... through the existing engine's public API... no internal engine imports... do not hack around it").

Only ever called with an **already-validated** `AlgoTestParameterValues` (from `validateParameterValues()`'s own `normalized` output) — `priceThreshold` here is always a real, in-range number, never a raw client value.

## 5. Persistence

Every run — completed or failed — persists its fully-normalized parameter snapshot (`AlgoTestRun.parameters`, `JSONB`) at creation time, **before** the engine even runs, so the exact attempted configuration is on record even if the run itself later fails (a provider error, a real engine failure like a negative risk-distance case). See `P3.4-VERSIONING.md` for the immutability/backward-compatibility discussion.

## 6. UI

`AlgoTestPanel.tsx`'s config modal renders one `ParameterField` per registry-declared parameter (`number`/`integer` → numeric input with `min`/`max`/`step`; `boolean` → on/off select; `select` → option list) — never a raw JSON textbox. Values are client-side validated for immediate feedback (`validateParamFormValue()`, mirroring the server's own rules) but the server independently re-validates and remains the sole authority. A "Reset to defaults" control restores every parameter to its `defaultValue` as declared by the registry — the UI never hard-codes a second copy of the default.

The persisted result view (`ParameterSnapshot`) shows exactly the configuration that produced the result — reading `run.parameters` (the persisted snapshot), mapping each `id` to its registry `label` when available, falling back to the raw id if the registry entry can't be resolved (e.g. a since-changed registry).
