# P3.1 — Data Compatibility Audit

**Status:** Audit only. Documents required transformations; none implemented.
See `P3.1-QUANT-CHART-INTEGRATION-ARCHITECTURE.md` for how this fits the overall map.

---

## 1. Symbol naming

| System | Convention | Example |
|---|---|---|
| `at24-quant-engine` (`Instrument.symbol`) | free-form string, no enum/whitelist, tests consistently use plain names | `"XAUUSD"` |
| Native Chart / market-data layer (`getCanonicalInstrument()`) | canonical catalog entries | `"XAUUSD"`, `"EURUSD"` |
| Quant Lite (`SUPPORTED_SYMBOLS`, `types/quant-lite.ts`) | **broker-suffixed** variants, plus two plain ones | `"XAUUSD_EXNESS"`, `"XAUUSD_ZS_EXNESS"`, `"EURUSD_EXNESS"`, `"GBPUSD_EXNESS"`, `"USOIL_EXNESS"`, `"BTCUSD_EXNESS"`, plus plain `"XAUUSD"`, `"EURUSD"` |

**Transformation required**: none between `at24-quant-engine` and Native Chart's own catalog (both already use plain `"XAUUSD"`). **A transformation IS required if Quant Lite's historical dataset is reused as the bars source** (§4) — its capability registry is keyed by the suffixed names; the Algo Test API would need a fixed mapping table (`"XAUUSD"` → `"XAUUSD_EXNESS"`) at the point where it queries that dataset, never exposed to the engine or the UI.

## 2. Timeframe naming

| System | Convention |
|---|---|
| `at24-quant-engine` (`Timeframe`) | MT-style, uppercase: `"M1"\|"M5"\|"M15"\|"M30"\|"H1"\|"H4"\|"D1"\|"W1"\|"MN1"` |
| Native Chart (`SignalTimeframe`) | lowercase, shorthand: `"1m"\|"5m"\|"15m"\|"30m"\|"1h"\|"4h"\|"1d"\|"1w"` (no monthly) |
| Quant Lite (`SupportedTimeframe`) | same lowercase family as Native Chart, minus `"1w"`: `"1m"\|"5m"\|"15m"\|"30m"\|"1h"\|"4h"\|"1d"` |

**Transformation required, mandatory, both directions**: the Algo Test API is the correct — and only — place to do this, via a small fixed lookup table (`"M5" ↔ "5m"`, etc.). Neither existing convention should change; both are load-bearing elsewhere (the engine's tests/fixtures all use `"M5"`-style; Native Chart's whole rendering/candle-fetch stack uses `"5m"`-style). Note the asymmetry: the engine supports `"MN1"` (monthly) with no Native Chart equivalent, and Native Chart supports `"1w"` with no direct engine equivalent beyond `"W1"` (which does exist) — so the mapping is fully coverable except monthly, which should be excluded from the Algo Test UI's timeframe picker until/unless needed.

## 3. Timestamps / timezone

| System | Convention |
|---|---|
| `at24-quant-engine` (`OHLCVBar.timestamp`, all engine-internal times) | plain `number`, epoch **milliseconds**, UTC assumed throughout (`timezone.strategyTimezone` must be set explicitly on the IR — Q0.7.18, never inferred from host clock) |
| Native Chart (`ChartCandle.time`) | plain `number`, epoch **milliseconds**, UTC (confirmed by the frontend audit) |
| Quant Lite (`Trade.entryTime`/`exitTime`, `BacktestRequest.dateRange`) | ISO 8601 **strings** |

**Transformation required**: none between the engine and Native Chart — both already use epoch-ms UTC numbers, which is why the Contract doc's `AlgoTestTrade.entryTime`/`exitTime` are specified as `number` (epoch ms), not strings — this is a case where picking the contract to match the *engine and chart's* shared convention avoids a conversion Quant Lite's own ISO-string convention would have forced. If any UI component wants a human-readable date, format at render time only, never change the wire type.

## 4. OHLC precision / volume / missing candles

- **Precision**: `at24-quant-engine`'s `validateMarketSeries()` enforces `open`/`close` within `[low, high]` and `high >= low`, but imposes no fixed decimal precision — it accepts whatever `number` precision the caller supplies. Native Chart's live providers return float prices at whatever precision the upstream API gives (varies per provider/instrument — e.g. gold to 2-3 decimals, forex pairs to 5). **No transformation needed structurally**, but whichever historical-bars source is chosen (§ below) must supply *consistent* precision across a single backtest run — the engine does not itself normalize inconsistent precision within one series.
- **Volume**: `OHLCVBar.volume: number`, required, `>= 0` (engine enforces this). Native Chart's `ChartCandle.volume?: number` is **optional** — some providers don't return volume for FX/metals (a well-known, already-documented gap in this codebase for spot FX/gold). **Transformation required**: any bars fed to the engine must supply a real `volume`, even if `0` — never `undefined`. If the eventual bars source can't provide real volume (likely, for XAUUSD spot), the Algo Test layer should pass `0` explicitly and this should be disclosed in the UI/provenance, not silently faked as a plausible-looking number.
- **Missing candles / gaps**: `at24-quant-engine`'s `detectTimestampGaps()` is informational only — legitimate weekend/holiday gaps are allowed, not an error. Native Chart's candle-normalizer (`normalizeCandles()`) similarly rejects malformed bars but doesn't require gap-free series. **No transformation required**, but the Algo Test API's own coverage check (§Gap-1) should follow Quant Lite's proven precedent (`assessCoverage()` → `SUPPORTED` / `SUPPORTED_WITH_WARNING` / `RESTRICTED` / `DATA_UNAVAILABLE`) rather than inventing a new one, since gap-handling UX is a genuinely solved problem in this codebase already — just solved on the Quant Lite side, reusable as a *pattern*.

## 5. Special-attention path: XAUUSD / M5

This is the sprint's declared initial validation target, so its exact current state matters more than the general rules above:

- `at24-quant-engine` already treats `"XAUUSD"` + `"M5"` as a first-class validation identity — the real G01 EA import test uses exactly this combination (`test/mql-g01-import.test.ts`, `test/q09-g01-reduction.test.ts`), and correctly detects its true M5 execution + M15 higher-timeframe swing reference as genuine multi-timeframe usage. **However, this only proves the MQL-import/IR path works for this instrument/timeframe — it does not mean a runnable backtest exists for it (G01 stays BLOCKED at reduction, per the Architecture doc §7).**
- **No real historical XAUUSD M5 OHLCV dataset exists inside `at24-quant-engine/`** — confirmed by exhaustive search; every simulation-level test in that package uses synthetic/hand-built fixture bars, never real gold prices.
- Native Chart's live candle API (`GET /api/private/market-data/candles`) can supply *current, rolling* XAUUSD M5-equivalent (`"5m"`) candles — but **only the latest N bars from "now"**, not a fixed historical window. This is directly disqualifying for a Backtest Request's `startTime`/`endTime` unless the requested range happens to fall entirely within whatever rolling window is currently cached (impractical for a real backtest).
- Quant Lite's own capability registry (`data/quant-lite-capability.ts`) lists **`XAUUSD_EXNESS`** with a real, coverage-checked historical range (backed by the legacy Python engine's own dataset, likely the `market.db`/CSV store referenced in `quant-engine/` and `quant_engine/`) — this is the only **real, working, date-range-queryable historical XAUUSD dataset found anywhere in the repository.**

### Gap-1 (the single most consequential data-compatibility finding)

**`at24-quant-engine` has no historical-bars source of its own, and neither of the two existing candidate sources is a clean fit without new work:**

| Candidate source | Pros | Cons |
|---|---|---|
| Extend Native Chart's live-quote providers with a date-range query | Symbol/timeframe conventions already align with the engine (§1/§2 above show near-zero transformation); stays entirely inside the "canonical engine + existing market-data layer" ownership model the Architecture doc's §4 table expects | Real new work — none of the 5 provider adapters (Twelve Data/Alpha Vantage/Binance/Angel One/MT5) were found to support a range query today (only latest-N); likely rate-limited/costly for deep historical ranges depending on provider tier |
| Reuse Quant Lite's existing real historical dataset (data only) | Already real, already coverage-checked, already has XAUUSD at a broker-realistic identity; zero new data-acquisition work | Requires the symbol-suffix mapping (§1); requires crossing into Quant Lite's own infrastructure for *data* while deliberately not reusing its *execution engine* — needs a careful, explicit "we're borrowing the dataset, not the backtest logic" framing so this doesn't quietly become Option 2/3 from the Architecture doc's §4 decision by accident |

**This audit does not choose between them** (implementation is out of scope) but flags this as the #1 blocking item for P3.2's very first successful end-to-end run — see `P3.1-READINESS-MATRIX.md`.

## 6. Performance / Payload (sprint §12)

Estimated from the engine's actual types, not measured (no real large-N run exists to benchmark):

- **Trade payload size**: `AlgoTestTrade` (Contract doc) is ~12 scalar fields, all numbers/short strings/enums — roughly 250-400 bytes as JSON per trade, generously. 100 trades ≈ 30-40KB, 1,000 trades ≈ 300-400KB, 10,000 trades ≈ 3-4MB.
- **At 10,000 trades**, a single JSON response embedding the full trade list becomes large enough to matter for both API latency and initial page payload — this is the threshold where **trades should be fetched separately from the run summary** (`GET /api/private/algo-test/runs/[id]` returns `metrics` + `testId` + `status` only; `GET /api/private/algo-test/runs/[id]/trades?offset=&limit=` is a second, paginated call), matching quant-lite's own `TradeTable.tsx` precedent of rendering a `Trade[]` array directly (which already implies quant-lite has never needed to think about pagination because its own historical usage/testing never produced anything close to 10,000 trades either — this is a shared, not solved, problem).
- **Chart rendering implication**: drawing 10,000 individual entry/exit/SL/TP markers on one canvas view is a real rendering-performance risk regardless of API pagination — Native Chart's existing drawing-object renderer (`drawDrawingObjects`) was built for a handful of user-drawn objects, not thousands of programmatic ones. A future implementation should plan to **cluster/aggregate markers outside the current viewport** (only render markers for trades whose time range intersects the visible index range — cheap to compute via the same `indexRange` already used for candles) rather than iterate the full trade list every frame.
- **API latency**: the simulation itself is a synchronous, in-process, pure-function call (`runSimulation()` has no I/O) — its own runtime scales with bar count × strategy complexity, not trade count, and nothing in the audited code suggests this is slow for reasonable backtest windows (the engine's own benchmark script, `at24-quant-engine/scripts/benchmark-*.ts`, exists precisely to characterize this, but was not run as part of this audit — see Findings doc). The realistic latency risk is **fetching the historical bars** (Gap-1's unresolved source), not the simulation math.
- **No premature optimization performed or recommended** — this section identifies the 10,000-trade pagination threshold and the marker-clustering need as things to design for, not to build now.
