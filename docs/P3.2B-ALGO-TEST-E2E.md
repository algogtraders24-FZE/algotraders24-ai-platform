## User Flow (as built)

```
Open Native Chart (XAUUSD pane)
        ↓
Click "Algo Test" in the chart toolbar (ChartToolbar.tsx)
        ↓
AlgoTestPanel's config modal opens (Golden Strategy / XAUUSD / M5 fixed;
Start Date / End Date / Initial Balance editable)
        ↓
"Run Backtest" → POST /api/private/algo-test/runs (button shows "Running
Algo Test…", disabled - no duplicate submission possible)
        ↓
completed | failed (a synchronous request/response - see "Why synchronous"
below; no polling needed at this scale)
        ↓
Results render inline in the same panel: metrics, Execution Assumptions,
equity curve, trade list - AND the chart itself switches to the exact
historical candles the backtest used, with entry/exit markers overlaid
```

## Why the request is synchronous (no job queue/polling)

The engine has no I/O (`runSimulation()` is a pure, synchronous function over an in-memory bar array) and the one real I/O step - fetching historical bars from Twelve Data - is bounded by `MAX_RANGE_DAYS` (14 days, ≈1,300-1,400 M5 bars, one HTTP request). A single request/response round-trip completes in a few seconds in practice (confirmed by this sprint's own test runs). Building a job queue/polling UI for that latency would be over-engineering at this scale - the `AlgoTestRun.status` field (`"pending"` written at creation, `"completed"`/`"failed"` on completion) exists in the schema for forward-compatibility, but the current implementation never actually returns a `"pending"` state to the client; the button's own disabled/"Running Algo Test…" state is the entire loading UX.

## Data flow (API → provider → engine, never client → provider directly)

```
Browser (AlgoTestPanel.tsx)
  ↓ POST /api/private/algo-test/runs (JSON, session cookie only)
withContext + getUserOrNull() [app/api/private/algo-test/runs/route.ts]
  ↓ sessionUser.profile.id (never trusted from the request body)
algoTestService.runAlgoTest(userId, request) [algo-test.service.ts]
  ↓ validateRequest() - strategy/symbol/timeframe/date-range/balance
  ↓
runGoldenBacktest(request, twelveDataHistoricalDataProvider) [run-golden-backtest.ts, P3.2A]
  ↓
TwelveDataHistoricalDataProvider.getBars() [P3.2A.1] → TWELVEDATA_API_KEY (server env only, never sent to the browser)
  ↓ validateBars() [P3.2A]
runSimulation(bars, config) [at24-quant-engine, via the vendored package]
  ↓
SimulationResult → mapped to AlgoTestRunView, persisted (AlgoTestRun), returned
```

The Twelve Data API key never leaves the server - `TwelveDataHistoricalDataProvider` runs exclusively inside `algoTestService`, which is only ever called from a `withContext`-wrapped API route handler (server-only Next.js code). The browser never constructs a Twelve Data URL or sees the key.

## Date Range Validation (`algo-test.service.ts::validateRequest`)

| Check | Rule | Why |
|---|---|---|
| Strategy | must be `"golden"` | Only registered strategy this release (see "No Arbitrary Code Execution" below) |
| Symbol | must be `"XAUUSD"` | Only verified symbol/provider mapping this release |
| Timeframe | must be `"5m"` | Only verified timeframe this release |
| `startTime < endTime` | rejected otherwise | Basic sanity |
| `endTime <= now` | rejected otherwise | This is a historical backtest, not a live/forward test |
| Range span | `<= MAX_RANGE_DAYS` (14) | Twelve Data's practical single-request bar cap (~5,000/request, vendor-documented) is ≈17.4 days at M5 (288 bars/day); 14 days leaves real margin so a request never lands exactly on a truncation boundary - see `docs/P3.2A.1-HISTORICAL-DATA-DECISION.md`'s own `MAX_RANGE_DAYS` note, reused verbatim, not re-derived |
| `initialBalance` | finite, `> 0` | Basic sanity |

A pure validation failure (any of the above) is rejected **before any `AlgoTestRun` row is created** - `testId` comes back empty, HTTP 400. A request that passes validation but fails during the actual provider/engine call (e.g. `NO_HISTORICAL_DATA`) **is** persisted as a real `status: "failed"` row, HTTP 201/200 - it was a genuine attempt, not a malformed request.

## Backtest Request / No Arbitrary Code Execution

```ts
{ strategyId: "golden", symbol: "XAUUSD", timeframe: "5m", startTime, endTime, initialBalance }
```

`strategyId` is a **registered identifier looked up against a fixed allow-list** (`SUPPORTED_STRATEGY_IDS = ["golden"]`), never arbitrary code, never a strategy spec accepted from the client. The actual `StrategySpec` (`buildGoldenStrategySpec()`) lives entirely server-side inside `at24-quant-engine`'s own public export - the browser never sends, and the server never evaluates, any executable string from the client. MQL-imported strategies remain subject to the existing importer/security architecture (`at24-quant-engine`'s MQL pipeline, audited in `docs/P3.1-FINDINGS.md` F-2 - no code execution risk found there either) and are explicitly **not** wired into this release's UI.

## Backtest Execution

`algoTestService.runAlgoTest()` calls `runGoldenBacktest()` (P3.2A's already-proven composition), which calls `runSimulation()` - the **existing, unmodified** `at24-quant-engine` function, imported through its real public package boundary (`import { runSimulation, buildGoldenStrategySpec } from "at24-quant-engine"`, resolved via the vendored copy - P3.2A.1). No internal engine module is imported directly. No simulation logic was written or duplicated in this sprint.

## Result Model (consumed as-is, never recalculated)

`AlgoTestRunView.metrics` is `algo-test.service.ts::toMetricsView(result)` - a direct field-for-field mapping of the engine's own `SimulationResult.metrics`, never a recomputation. Displayed: Total Trades, Win Rate, Net P&L, Profit Factor, Max Drawdown, Final Equity (`initialBalance + netProfit` - simple arithmetic on two already-real engine numbers, not a second metric calculation). `trades` is `SimulationResult.tradeLedger` mapped field-for-field (`toTradeView()`). `equityCurve` is P3.2A's own `deriveEquityCurve()` - a running-sum projection of the ledger's own `netPnl` values, documented in `P3.2A-RESULT-CONTRACT.md` as a legitimate display derivation, not a second calculation path.

## Execution Assumptions Disclosure

Every result renders an "Execution Assumptions" block (`AlgoTestPanel.tsx::ExecutionAssumptions`), built from the **real** `executionMetadata` on the result's first trade (`algo-test.service.ts::buildAssumptions()`) - never a hardcoded claim independent of what the engine actually used:

```
Spread:   ZeroSpread (0 / placeholder)
Slippage: ZeroSlippage (0 / placeholder)
Fees:     ZeroFee (0 / placeholder)
Margin:   Leverage is a declared engine assumption, not enforced -
          position sizing is unconstrained by margin in this backtest.
```

With an explicit closing line: *"These are the engine's real, currently-in-effect assumptions - not a claim of broker-realistic execution."* Matches `docs/P3.1-EXECUTION-PARITY.md`'s disclosure requirement exactly.

## Loading State / Error Handling

The "Run Backtest" button becomes `disabled` and reads "Running Algo Test…" for the duration of the `fetch` call (`AlgoTestPanel.tsx::handleSubmit`) - `submitting` state prevents a duplicate submission by construction (the button can't be clicked while `disabled`). On any outcome:
- `status === "completed"` → results render, config modal closes.
- `status === "failed"` (validation, no data, provider error, backtest failure) → the modal stays open with `run.errorMessage` shown in red, so the user can adjust and retry without losing their in-progress date-range selection.
- A network-level failure (`fetch` itself throws) → caught, same error display, `submitting` always resets in a `finally` block - the UI can never get stuck.

## Golden E2E Test — what was actually verified, and how

**Fully verified, with real data, real persistence, and a real HTTP-shaped request/response contract** (`scripts/validate-algo-test-service.ts`, 11/11 passing against the real database and the live Twelve Data API):
- A valid request completes, produces real trades, and persists a real `AlgoTestRun` row.
- `getAlgoTestRun()` returns the persisted run for its real owner, without candles (never persisted).

**Verified at the render-logic level** (`scripts/validate-algo-test-renderer.ts`, 7/7 passing): entry/exit markers draw at the exact expected pixel position for a trade's own (time, price); BUY/SELL trades use the correct color; a selected trade renders a highlight ring, an unselected one doesn't; multiple trades render independently.

**Verified at the build level**: an isolated reproduction of the actual Vercel production build path (`npm install && npm run build` against a copy of `frontend/` with no sibling packages present, the same check `P3.2A.1-DEPLOYMENT-GATE.md` established) succeeds with zero errors, and both new routes (`/api/private/algo-test/runs`, `/api/private/algo-test/runs/[id]`) are present in the compiled route table. **A real, previously-latent bug was found and fixed during this check**: `services/algo-test/**`'s internal relative imports used a `.js`-suffixed NodeNext-style convention (copied from `at24-quant-engine`'s own internal style) that TypeScript's `tsc --noEmit` silently tolerated under this project's `moduleResolution: "bundler"` setting, but Next.js's real Turbopack bundler could not resolve - `tsc` passing was not sufficient proof; only the actual production build caught this.
