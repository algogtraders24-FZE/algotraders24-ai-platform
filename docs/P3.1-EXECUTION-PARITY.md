# P3.1 — Execution Semantics Parity Audit

**Status:** Audit only. Classifies differences; fixes none.
Compares `at24-quant-engine`'s simulation semantics against the existing (live) Paper Trading system (Phase P1/P2), since Paper Trading is the platform's only other real order/position execution model and the natural reference point for "does this feel like the same platform."

Classification per sprint §10: **EXPECTED** (a backtester and a live-price paper simulator are different tools and should differ here — not a defect), **SAFE** (differs, but cannot produce a misleading or incorrect result), **BUG** (an actual defect found during this audit), **UNRESOLVED** (a real open question that needs a decision before P3.2, not a code fix).

---

## Market order fill

| | `at24-quant-engine` | Paper Trading |
|---|---|---|
| Fill price | **Next bar's open**, spread/slippage-adjusted (`resolveMarketFill`) | **Immediate live ask/bid** at the moment of the API call |

**Classification: EXPECTED.** A backtester cannot fill "immediately" — there is no bar between the signal and the next bar's open; filling at the *signal* bar's own close would be lookahead (using information — that the signal fired — to trade at a price that was already fully formed knowing the signal). Paper Trading, running against a live feed, correctly has no such constraint. Different mechanisms, both correct for their own context.

## Limit order fill

| | `at24-quant-engine` | Paper Trading |
|---|---|---|
| Fill condition | Fills only if price **strictly trades through** the limit (`resolveLimitFill`); a favorable gap fills at the open, never at a better-than-limit synthetic price | Fills when `ask <= limitPrice` (buy) / `bid >= limitPrice` (sell), checked on each live snapshot poll (`fillPendingLimitOrders`) |

**Classification: SAFE.** Both encode the same real-world rule (fill only when price reaches the limit, never before), expressed differently because one operates on discrete historical bars and the other on discrete live polls — neither can produce a fill the real rule wouldn't allow. Worth noting for a future combined UI: the *engine's* fill price on a favorable gap (the bar's open, which may be better than the limit) differs from Paper Trading's fill price (always exactly the limit price, per its own documented "real MT5 behavior" convention) — this is a genuine behavioral difference a user could notice if shown both side by side, but each is independently correct for its own model.

## Stop order fill

| | `at24-quant-engine` | Paper Trading |
|---|---|---|
| Present? | ✅ `resolveStopFill` — unfavorable gap fills at the worse open price, never at the stop price itself | ❌ **not implemented** — Paper Trading only supports `"market"` and `"limit"` (`PaperOrderType`) |

**Classification: UNRESOLVED.** Not a bug (Paper Trading was never scoped to include stop orders), but a real asymmetry that matters if a future UI ever tries to present backtest results and live paper-trading using one shared order-type picker — a strategy that uses stop entries in a backtest has no live paper-trading equivalent to compare against today. Flag for a future phase, not for P3.2.

## Spread

| | `at24-quant-engine` | Paper Trading |
|---|---|---|
| Model | Pluggable `SpreadModel` interface; **only `ZeroSpread` is actually implemented** (`src/runtime/simulation/spread-model.ts`) | Real live bid/ask spread from the actual market-data snapshot at time of fill |

**Classification: UNRESOLVED, and the single most important parity gap for the sprint's stated XAUUSD validation path.** The engine's architecture correctly anticipates a real spread model (the interface exists, `SimulationConfig.spreadModel` is a required field), but **no non-zero implementation exists** — every backtest run today executes with a phantom zero-cost spread. This will make backtested XAUUSD results look meaningfully better than what Paper Trading (or a real account) would produce, since gold's spread is not economically negligible. This is not something to fix silently inside this audit (would be "expand engine scope," out of bounds) — it must be a disclosed, visible caveat on every backtest result ("Assumptions: ZeroSpread — real trading costs are not modeled"), exactly the same honesty pattern Quant Lite's own `ExecutionAssumptions` type already uses (`spread: string`, `slippage: string`, `commission: string`, all surfaced to the user, not hidden). **This is a genuine, real content-honesty risk if skipped**, not a hypothetical one — see Findings doc.

## Slippage / fees / latency

Same shape and same finding as spread: `SlippageModel`/`FeeModel`/`LatencyModel` interfaces exist, only `Zero*` implementations exist. **Classification: UNRESOLVED**, same disclosure requirement as spread — bundle into the same "Assumptions" surface in the result contract (already present as `AlgoTestMetrics`'s implicit provenance via `resultHash`/`executionMetadata` on each trade — see Contract doc).

## Stop-loss / take-profit

| | `at24-quant-engine` | Paper Trading |
|---|---|---|
| Mechanism | Checked every bar (`resolveProtectiveExit`); if both SL and TP are reachable within one bar's OHLC range, resolves conservatively to the **stop-loss** and flags `ambiguous: true` | No SL/TP concept exists at all in Paper Trading today — only manual close and automatic Stop Out (margin-based, not price-target-based) |

**Classification: EXPECTED** (Paper Trading was never scoped for per-position SL/TP — it's a leverage/margin simulator, not a strategy executor), but worth naming: the engine's conservative same-bar-ambiguity handling (`ambiguous: true`, always assume the worse outcome) is a real, deliberate honesty feature that has **no equivalent bar-level ambiguity in Paper Trading** since Paper Trading has no bars at all (it's tick/poll-driven) — nothing to reconcile, just noting the concepts don't overlap enough to compare directly.

## Margin

| | `at24-quant-engine` | Paper Trading |
|---|---|---|
| Model | `ExecutionAssumptions.marginAssumption.leverage` is a **static declared number, not evaluated** — the engine's own account model comment states margin/freeMargin are "tracked but always 0/equity ... since no MarginModel is wired in yet" | Real, live-computed `usedMargin`/`freeMargin`/`marginLevel`, with an actual Margin Call (100%) and Stop Out (50%) mechanism, verified live in production this session |

**Classification: UNRESOLVED, second most important gap after spread.** A backtest's reported "leverage" is currently cosmetic — it doesn't constrain position sizing or trigger any margin-call/stop-out behavior the way Paper Trading's very real, very tested mechanism does. This means a backtested strategy could show a sequence of trades that would have been **impossible in Paper Trading (or real life)** because margin would have force-closed a position first, and the backtest wouldn't know. **This must be disclosed prominently** ("Margin/leverage is not enforced in this backtest — position sizing is unconstrained") wherever backtest results are shown, exactly the same class of honesty requirement as the spread gap above, and is arguably more likely to mislead a user since Paper Trading's own Margin Call/Stop Out UI (already shipped, already visible elsewhere in the same Native Chart) sets a real expectation that margin is always enforced somewhere in this platform.

## Position sizing / netting vs. hedging

| | `at24-quant-engine` | Paper Trading |
|---|---|---|
| Model | **Netting only** (enforced at reduction/eligibility — hedging strategies are explicitly BLOCKED before they ever reach the simulator) | Also effectively netting per symbol (Paper Trading has no explicit hedging concept either — each `PaperPosition` row is independent, opening a second same-symbol position doesn't merge with an existing one, so this is actually closer to a *simple multi-position* model than strict netting) |

**Classification: SAFE**, with a caveat worth naming as **UNRESOLVED for future parity work**: the two systems aren't actually using the *same* definition of "netting" — the engine merges same-symbol fills into one position; Paper Trading allows multiple independent same-symbol positions to coexist. Neither is wrong for its own purpose, but a side-by-side comparison UI should not assume they'd produce the same position count for the same trade sequence.

## Pending order lifecycle

| | `at24-quant-engine` | Paper Trading |
|---|---|---|
| Model | `OrderStatus`: `NEW→SUBMITTED→ACCEPTED→TRIGGERED→PARTIALLY_FILLED→FILLED/CANCELLED/EXPIRED/REJECTED`; supports `OrderExpirationPolicy` (`GTC`/`DAY`/`BAR{maxBars}`/`TIMESTAMP`) | `PaperPositionStatus`: `pending→open→closed`/`cancelled`; no expiration policy — a pending limit order lives until manually cancelled or filled, forever |

**Classification: SAFE** — Paper Trading's simpler lifecycle is a strict subset of valid states the engine also models; nothing is contradictory, Paper Trading just doesn't need the extra states (no backtest-style bar-count expiration makes sense for a live, indefinite simulation).

## Position lifecycle / SL,TP mutation

The engine's `initialStopLoss` (frozen at entry, used only for R-multiple) vs. `stopLoss` (current, may be moved by breakeven/trailing rules) is a real, deliberate distinction with no Paper Trading equivalent (Paper Trading has no stop-loss concept at all, per above). **Classification: EXPECTED** — not a gap to close, just confirms the two systems' position concepts don't fully overlap and shouldn't be forced to.

## Summary table

| Area | Classification | Action needed before P3.2 ships anything to a real user |
|---|---|---|
| Market order fill timing | EXPECTED | None |
| Limit order fill rule | SAFE | None |
| Stop orders | UNRESOLVED | None for P3.2 (Paper Trading has no equivalent; not a blocker for a backtest-only feature) |
| Spread | **UNRESOLVED — must disclose** | Every backtest result must visibly state ZeroSpread is in effect |
| Slippage/fees/latency | **UNRESOLVED — must disclose** | Same disclosure surface as spread |
| SL/TP mechanics | EXPECTED | None |
| Margin/leverage enforcement | **UNRESOLVED — must disclose** | Every backtest result must visibly state leverage/margin is not enforced |
| Netting definition | SAFE (differs, not misleading) | None for P3.2; note for future side-by-side UI |
| Pending order lifecycle | SAFE | None |
| Position lifecycle (SL/TP mutation) | EXPECTED | None |

**No BUGs were found** in this audit — every real difference is either an intentional design choice appropriate to each system's purpose (EXPECTED/SAFE) or a known, engine-declared placeholder (zero-cost models, unenforced margin) that is safe *as long as it is disclosed*, not silently presented as if it were a fully realistic execution simulation.
