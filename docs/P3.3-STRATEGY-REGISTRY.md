# P3.3 — Strategy Registry & Capability Registry

**Status:** Implemented, live-verified. See `P3.3-ALGO-TEST-PRODUCTIZATION.md` for the sprint's full scope and `P3.3-RESULT-CONTRACT.md` for the persisted-result contract this registry feeds.

---

## 1. What changed

P3.2B hardcoded three constants in `services/algo-test/algo-test.service.ts` — `SUPPORTED_STRATEGY_IDS = ["golden"]`, `SUPPORTED_SYMBOLS = ["XAUUSD"]`, `SUPPORTED_TIMEFRAMES = ["5m"]` — and a parallel, independently-maintained set of UI constants in `components/chart-engine/AlgoTestPanel.tsx` (`FIXED_STRATEGY_LABEL`/`FIXED_SYMBOL`/`FIXED_TIMEFRAME_LABEL`). Two sources of truth for the same fact.

P3.3 replaces both with one explicit registry: `services/algo-test/strategy-registry.ts`.

```ts
export interface StrategyDefinition {
  strategyId: string;
  strategyVersion: string;      // read from buildGoldenStrategySpec().version - never a duplicated literal
  displayName: string;
  description: string;
  supportedSymbols: readonly string[];      // the Capability Registry
  supportedTimeframes: readonly string[];   // SignalTimeframe-shaped, e.g. "5m"
  status: "available";
}

export const STRATEGY_REGISTRY: readonly StrategyDefinition[] = [
  { strategyId: "golden", strategyVersion: goldenSpec.version, /* ... */ supportedSymbols: ["XAUUSD"], supportedTimeframes: ["5m"], status: "available" },
];
```

**Exactly one entry.** No artificial second strategy was added to "prove" the registry works — the sprint brief explicitly forbids this. Registering a second strategy later means adding one more array entry (plus a real `StrategySpec` for it to run against); it does not touch any validation, persistence, or UI code that reads the registry.

## 2. Capability Registry — not a second data source

`supportedSymbols`/`supportedTimeframes` live *on* the strategy's own registry entry, not in a separate table. `algo-test.service.ts`'s `validateRequest()` reads `strategy.supportedSymbols`/`strategy.supportedTimeframes` directly — there is exactly one place a symbol/timeframe combination is declared supported, so the UI, the API validation, and any future registry entry can never drift out of sync with each other.

## 3. Strategy Versioning

`strategyVersion` is **not** a new literal invented for this sprint — it is `buildGoldenStrategySpec().version` (`at24-quant-engine/src/reference/golden-strategy.ts`), read at module load. The engine already declared this version (`"1.0.0"` today) on every `SimulationTrade.strategyVersion` and on `SimulationResult.provenance.strategyVersion` since Q0.5 — P3.3 surfaces the existing value through the registry and the persisted `AlgoTestRun.strategyVersion` column, rather than duplicating it as a new string.

**Reproducibility guarantee:** every `AlgoTestRun` row now records the exact `strategyId` + `strategyVersion` it executed against (`algo-test.service.ts`'s `runAlgoTest()` always stamps `strategy.strategyVersion` from the server's own registry lookup — never the client-supplied value verbatim, even when one is supplied). If a future release bumps the Golden Strategy to `"1.1.0"` (a real semantic change to its entry/exit/risk rules), a historical run recorded at `"1.0.0"` stays identifiable as having run the older behavior — the registry is never allowed to silently reinterpret an old row's meaning.

**Version pinning (optional):** `AlgoTestRunRequest.strategyVersion` may be supplied by a caller to pin a version explicitly; if it does not exactly match the registry's current version for that `strategyId`, the request is rejected with `INVALID_STRATEGY_VERSION` before any historical-data fetch or simulation — never silently substituted. Omitting it (today's UI behavior) means the server resolves and records the current registered version itself.

## 4. Validation order (server-side, centralized)

`algo-test.service.ts`'s `validateRequest()` runs, in this fixed order, before any historical-data fetch or simulation:

1. **Strategy** — `getStrategyDefinition(strategyId)` exists and `status === "available"` → else `INVALID_STRATEGY`.
2. **Strategy version** (only if the caller supplied one) — exact match to the registry's current version → else `INVALID_STRATEGY_VERSION`.
3. **Symbol** — `strategy.supportedSymbols.includes(symbol)` → else `INVALID_SYMBOL`.
4. **Timeframe** — `strategy.supportedTimeframes.includes(timeframe)` → else `INVALID_TIMEFRAME`.
5. **Date range** — parseable, `startTime < endTime`, `endTime` not in the future, range ≤ `MAX_RANGE_DAYS` (14) → else `INVALID_DATE_RANGE` / `RANGE_TOO_LARGE`.
6. **Initial balance** — finite and positive → else `INVALID_INITIAL_BALANCE` (P3.3 also fixed a P3.2B leftover here: this case was previously mis-coded as `INVALID_DATE_RANGE`).

The UI (`AlgoTestPanel.tsx`) independently mirrors steps 3/4 (an inactive-symbol pane shows an honest "not supported" message instead of a form that would only fail server-side) — but the UI check is a convenience, never the enforcement boundary. Every case above is covered by a real, live test against the real service in `scripts/validate-algo-test-service.ts` (17/17 passing — see that sprint's own report).

## 5. Registry-backed UI

`GET /api/private/algo-test/strategies` (new route, same `withContext`/`getUserOrNull()`/`ApiResponse` gating as every other private route) returns `algoTestService.listStrategies()` — the registry's `status === "available"` entries. `AlgoTestPanel.tsx` fetches this once on mount and renders its Strategy/Symbol/Timeframe fields from the response (`lib/algo-test/store.ts`'s `fetchAlgoTestStrategies()`), falling back to static labels only during the brief pre-fetch window or if the fetch genuinely fails — the values actually **sent** to the server (`strategyId`, `symbol`, `timeframe`) always come from the fetched registry entry, never a hardcoded string, once it has loaded.
