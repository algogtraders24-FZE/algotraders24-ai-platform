## 4. PublishingJob lifecycle

`PublishingJobStatus` (UPPERCASE — Sprint §5):

```
PENDING ──▶ RUNNING ──▶ SUCCEEDED         (terminal)
   │           │  │
   │           │  └────▶ FAILED ──┐        (NOT terminal — awaiting retry)
   │           │          │  │    │
   │           ▼          │  ▼    │
   └────────▶ CANCELLED ◀─┴─(RUNNING / PENDING on retry)
              (terminal)
```

| Status | Meaning | Terminal? |
| --- | --- | --- |
| `PENDING` | Accepted, not executing (queued / awaiting its scheduled slot). | no |
| `RUNNING` | An execution attempt is in progress. | no |
| `SUCCEEDED` | A destination confirmed publication. Carries a `PublishResult`. | **yes** |
| `FAILED` | The last attempt failed. Carries a `PublishError`. Retry or manual intervention. | no |
| `CANCELLED` | Intentionally prevented from executing / abandoned. | **yes** |

**Transition table** (`PUBLISHING_JOB_STATUS_TRANSITIONS`, enforced by
`isValidJobTransition` / `validateJobTransition`):

| From | Allowed → |
| --- | --- |
| `PENDING` | `RUNNING`, `CANCELLED` |
| `RUNNING` | `SUCCEEDED`, `FAILED`, `CANCELLED` |
| `FAILED` | `RUNNING` (retry), `PENDING` (re-queue), `CANCELLED` (give up) |
| `SUCCEEDED` | — |
| `CANCELLED` | — |

A terminal job is never re-opened. **A new content version is a new job.**

### Relationship to `ArticleStatus` (advisory)

`ARTICLE_STATUS_ON_JOB_SUCCESS` is a documented, **advisory** map the
Publishing Service *may* apply — P2.1 does not apply it:

| `PublishingJobStatus` | suggested `ArticleStatus` |
| --- | --- |
| `SUCCEEDED` | `published` |
| `FAILED` | `failed` |
| `PENDING` / `RUNNING` / `CANCELLED` | *(leave untouched)* |

The two enums are independent axes (Sprint §3). The case difference
(`published` vs `SUCCEEDED`) is deliberate and keeps cross-references
unambiguous.

## 5. PublishingAttempt

A `PublishingJob` is the logical operation; a **`PublishingAttempt` is one
execution of it**. Append-only, immutable once terminal — a retry is a *new*
attempt row, never an edit (mirrors `AgentStep` / `AuditLog`).

```
Job #123
  Attempt #1 → FAILED     (error: RATE_LIMITED)
  Attempt #2 → FAILED     (error: TEMPORARY_FAILURE)
  Attempt #3 → SUCCEEDED  (externalReference: null, externalUrl: …)
```

`PublishingAttemptStatus`: `RUNNING → { SUCCEEDED | FAILED }` (both terminal).

Fields: `attemptNumber` (1-based, gapless), `status`, `startedAt`,
`completedAt`, `error?` (required when `FAILED`), `externalReference?`,
`externalUrl?`, `destinationResponseMeta?` (safe non-secret metadata only —
the adapter strips tokens/PII first), `createdAt`.

`validatePublishingAttempt` enforces: 1-based number, terminal ⇒ `completedAt`
set, `FAILED` ⇒ `error` present, `RUNNING` ⇒ no `completedAt`.

## 7. DestinationAdapter

```ts
interface DestinationAdapter {
  readonly destination: PublishingDestinationId;
  validate(input: NormalizedPublishInput): Promise<AdapterValidationResult>;
  publish(input: NormalizedPublishInput): Promise<PublishResult>; // rejects with PublishError
}
```

**An adapter MUST NOT** import/reference: React or any component/hook · a
Next.js `Request`/`Response`/route context/`headers()`/`cookies()` · Prisma /
`@/lib/prisma` / any repository · Vercel cron / scheduling · the Automation
layer · the Agent Framework runtime (`services/agent-framework/**`).

**An adapter DOES NOT**: perform authorization · decide retries · read/write
job or attempt rows · compute or re-verify `contentHash`.

**An adapter RECEIVES** exactly a `NormalizedPublishInput` and
**returns/throws** exactly `PublishResult` / `PublishError`.

`validate()` returns `{ valid, errors: PublishError[] }` for *expected*
rejections (never throws for those); it may still reject its promise for an
infrastructure failure.

`publish()` must be **safe to call again** with the same input after a lost
invocation — a destination that already holds this `contentHash` returns its
existing item or rejects `DUPLICATE`; it never creates a second copy.

`isDestinationAdapter(x)` structurally verifies the shape (used by tests and
the future adapter registry).

## 8. Normalized publish input

`NormalizedPublishInput` — the *only* object an adapter sees. A **projection**
of an existing `Article` (+ its `SeoMetadata`), assembled on demand by the
Publishing Service. **No `Article` data is copied into a new table** by this
contract (Sprint §9, §19).

| field | source | in `contentHash`? |
| --- | --- | --- |
| `articleId` | `Article.id` | ❌ — SOURCE identity, stable across edits |
| `destination` | caller | ❌ — separate identity axis |
| `title` | `Article.title` | ✅ |
| `slug` | `Article.seo.slug` | ✅ |
| `body` | `Article.sections[]` serialized (serializer defined in P2.2) | ✅ |
| `excerpt` | `Article.summary` | ✅ |
| `canonicalUrl` | `Article.seo.canonicalUrl` | ✅ |
| `disclaimer` | `Article.disclaimer` | ✅ |
| `seo.metaDescription` | `Article.seo.metaDescription` | ✅ |
| `seo.keywords` | `Article.seo.keywords` (order preserved) | ✅ |
| `contentHash` | derived (§9) | — (it is the output) |

`body` is the task's "content" field — renamed so "content" stays a concept,
not one field. The `Article.sections[] → body` serializer is **P2.2**, not
P2.1.

Split types: `PublishableContent` (the 8 hashable fields) ⊂
`NormalizedPublishInput` (adds `articleId`, `destination`, `contentHash`).

`validateNormalizedPublishInput()` is a shape + required-field gate. It does
**not** verify the hash value — that needs the digest and lives in
`content-hash.ts#contentHashMatches`.

## 9. Content hashing

**Purpose:** tie a publication to a deterministic content *version*, suitable
for idempotency (Sprint §10).

**Algorithm — LOCKED as `PUB-v1`:**

```
basis = join( U+001F , [
  "title="               + title,
  "slug="                + slug,
  "body="                + body,
  "excerpt="             + excerpt,
  "canonicalUrl="        + canonicalUrl,
  "disclaimer="          + disclaimer,
  "seo.metaDescription=" + seo.metaDescription,
  "seo.keywords="        + seo.keywords.join(","),
] )

contentHash = sha256_hex( utf8( basis ) )      // 64 lowercase hex chars
```

- **Participating fields:** exactly `CONTENT_HASH_FIELDS` (the 8 above), in
  that order. `articleId` and `destination` do **not** participate.
- `canonicalContentBasis()` (pure, in the contract layer) builds the string;
  `computeContentHash()` (`services/publishing/content-hash.ts`) applies the
  digest — the only runtime line in P2.1.
- **Deterministic:** same content → same hash on any machine, forever.
- **Sensitive:** any change to a participating value (including a trailing
  space, or reordering `seo.keywords`) changes the hash. Field labels are in
  the basis so a value moving between fields also changes it.
- **No normalization:** whitespace is *not* trimmed — a whitespace-only edit
  is a real content change.
- **No secret** participates → the hash is safe to log and to expose as an
  idempotency key.
- **Algorithm choice** (`sha256`/hex, `|`-style labelled join) matches every
  other content-identity hash in the repo (`services/news/normalize.service`,
  `services/calendar/normalize.service`, `services/licensing/adapters`,
  `services/quant-lite/backend/requestHash`). No new hashing framework.

Changing the participating fields, their order, the separator, or the digest
is a **`PUB-v2`** bump (every historical hash would change).

## 10. Idempotency

**Logical publication identity** (Sprint §11):

```
PublicationIdentity = { articleId, destination, contentHash }
publicationIdentityKey(id) === `${articleId}:${destination}:${contentHash}`
```

- `:` cannot appear in a cuid, a destination id, or a hex hash → the key is
  unambiguous and reversible (`parsePublicationIdentityKey`).
- This is the value a **future `@@unique` index / upsert key** enforces
  (**P2.2** — no migration in P2.1) and the natural `PublishingJob.idempotencyKey`.

**Idempotency rules** (stated here for completeness; enforced in P2.3):

1. A `PublishingJob` for an identity that already has a `SUCCEEDED` job is a
   **no-op returning the existing publication** — not a second job.
2. A `DUPLICATE` `PublishError` from an adapter is **reconciled to the
   existing publication**, never counted as a retryable failure
   (`PublishRetryClass = "IDEMPOTENT_DUPLICATE"`).
3. Re-publishing after a content edit is a **different identity** (new
   `contentHash`) and a legitimately new job.

## 12. PublishError

```ts
type PublishErrorCode =
  | "VALIDATION_ERROR" | "AUTHENTICATION_ERROR" | "AUTHORIZATION_ERROR"
  | "RATE_LIMITED"     | "TEMPORARY_FAILURE"    | "PERMANENT_FAILURE"
  | "DUPLICATE"        | "UNKNOWN";

interface PublishError {
  code: PublishErrorCode;
  message: string;                     // human-readable, NEVER contains a secret (Sprint §13)
  destination?: PublishingDestinationId | null;
  retryClass: PublishRetryClass;       // derived from code, stored for a self-describing audit row
  cause?: string | null;               // safe upstream detail ("HTTP 503"), never a raw payload
}
```

`makePublishError(code, message, opts?)` is the **only** constructor — it
keeps `retryClass` consistent with `code`, and `validatePublishError()`
rejects an inconsistent pair.

## 13. Retry semantics

`PUBLISH_ERROR_RETRY_CLASS` (Sprint §14) — P2.1 **documents** this; it does
**not** implement automatic retries.

| Code | `PublishRetryClass` | Meaning |
| --- | --- | --- |
| `RATE_LIMITED` | `RETRYABLE` | a later attempt may succeed unchanged |
| `TEMPORARY_FAILURE` | `RETRYABLE` | ″ |
| `VALIDATION_ERROR` | `NON_RETRYABLE` | needs a content fix |
| `AUTHENTICATION_ERROR` | `NON_RETRYABLE` | needs a credential fix |
| `AUTHORIZATION_ERROR` | `NON_RETRYABLE` | needs a permission fix |
| `PERMANENT_FAILURE` | `NON_RETRYABLE` | destination rejected it for good |
| `UNKNOWN` | `NON_RETRYABLE` | conservative — an unclassifiable error is not auto-retried |
| `DUPLICATE` | `IDEMPOTENT_DUPLICATE` | **not a failure** — reconcile to the existing publication (§10) |

`RETRYABLE_PUBLISH_ERROR_CODES` is derived from this table (single source of
truth). Helpers: `retryClassFor`, `isRetryablePublishErrorCode`,
`isDuplicatePublishError`.

## 14. Authorization boundary

**Authorization stays ABOVE the adapter** (Sprint §15, §16).

- `PublishingJob.userId` carries the Article owner. The Publishing Service
  sets it **from the server session, never from a request body** (the lock
  the agent-framework routes already enforce), and checks
  `article.userId === session.userId` **before** it builds a
  `NormalizedPublishInput`.
- `NormalizedPublishInput` deliberately carries **no** session, role, token,
  permission list, or `isOwner` flag. A contract test
  (`NormalizedPublishInput carries NO auth material`) pins its exact key set
  so any future edit that leaks auth material into the adapter boundary fails
  loudly.
- Adapters therefore **cannot** self-authorize or widen access — they have
  nothing to authorize with.
- `validatePublishingJob()` treats a missing `userId` as invalid.

Cross-user protection: a `PublishingJob` cannot publish another user's
Article because the service resolves the Article by `(id, userId)` (the
existing `articleService.findOwned` pattern from P1) before a job is created.
