## 2. P2.3-B — Close the Article drift window

**Before:** `PublishingJob = SUCCEEDED` but `Article` still editable → the
published content could silently change under a reader.

**After:** a successful publish, the job, and `Article.status = published` all
commit **in one transaction** (`PublishingRepository.commitSuccess` →
`prisma.$transaction`). A published Article is already read-only via the
existing `articleService.update()` conflict guard.

```
PENDING ─▶ RUNNING ─▶ SUCCEEDED ─(same tx)─▶ Article.status = published ─▶ Article read-only
                   └▶ FAILED   ──────────────▶ Article UNCHANGED
```

- Driven by the P2.1 contract's advisory `ARTICLE_STATUS_ON_JOB_SUCCESS`
  (`SUCCEEDED → "published"`), gated per-destination by
  `shouldPublishArticleOnSuccess()` (today: `true` for the only destination,
  INTERNAL_BLOG; a future non-website destination is excluded there).
- **Idempotent:** an already-`published` Article is left untouched
  (`articleStatusChanged: false` in the audit metadata).
- **Failure never publishes** the Article — asserted by tests.
- The history entry `{ action: "published", actor, metadata: { via: "publishing-job", jobId } }` is appended in the same transaction.

> **Pre-existing legacy path unchanged:** the D2.3 route
> `POST /api/private/publishing/articles/:id/publish` still flips
> `Article.status` directly (no job). P2.3 does not touch it; a later cleanup
> should redirect it through `PublishingService` or remove it.

## 3. P2.3-C — Audit trail

Three actions added to `AuditLogService.AuditAction` (the existing append-only
`AuditLog` model — **no new table**, mirrors the `marketplace.*` precedent):

| action | fired by | `targetId` | metadata |
| --- | --- | --- | --- |
| `article.drafted` | `articleService.createDraft` | article id | `{ category, sourceType }` |
| `article.published` | `PublishingService` on job `SUCCEEDED` | article id | `{ jobId, destination, contentHash, externalUrl, articleStatusChanged }` |
| `article.publish_failed` | `PublishingService` on job `FAILED` | article id | `{ jobId, destination, errorCode, retryClass, attemptNumber }` |

All writes are **best-effort** — a failed audit write never fails the
operation (house pattern; audit is written *outside* the state transaction,
like `marketplace/factory/auditTrail.ts`). The audit sink is injected into
`PublishingService` (real `auditLogService` in production, a capturing fake in
tests).

## 4. P2.3-D — Retry policy

| rule | value |
| --- | --- |
| Max attempts per job | **`MAX_PUBLISH_ATTEMPTS = 3`** (hard cap in `runAttempt` and the dispatcher) |
| Auto-retryable errors | `RATE_LIMITED`, `TEMPORARY_FAILURE` only |
| Never auto-retried | `VALIDATION_ERROR`, `AUTHENTICATION_ERROR`, `AUTHORIZATION_ERROR`, `PERMANENT_FAILURE`, `UNKNOWN` |
| `DUPLICATE` | reconciled to a SUCCEEDED job (idempotent), never retried |
| Spacing | **slot-spaced** — a `FAILED` job is only picked up by the next dispatcher run; there is no in-process retry loop |
| After 3 attempts | job stays `FAILED`; `runAttempt` refuses further attempts. A new publication requires editing the Article (→ new `contentHash` → new job identity). |

`isEligibleForAutoRetry(job)` = `status === FAILED && attemptCount < 3 &&
lastError.retryClass === "RETRYABLE"` — the single predicate the dispatcher
uses.

## 5. P2.3-E — Dispatcher

`POST` **and** `GET` `/api/private/publishing/dispatch`

```
Cron (Bearer <CRON_SECRET>)  ──┐
                               ├─▶  isValidCronSecret(req)  OR  requireAdmin()
Authenticated admin  ──────────┘         │
                                         ▼
                          PublishingService.dispatch({ limit })
                                         │  repo.findDispatchableJobs(limit, 3)
                                         │    → PENDING  +  FAILED&retryable&<3 attempts
                                         │    → scheduledFor in the future is skipped
                                         ▼
                          for each:  runAttempt({ userId: job.userId, jobId })
                                         ▼
                          { scanned, ran, results: [{ jobId, outcome }] }
```

- Auth is the exact `admin/intelligence/ingest-news` shape — **cron secret OR
  admin, never a plain user**.
- `export const maxDuration = 60`. Batch capped: default **25**, max **100**,
  `?limit=` override. One `runAttempt` per job per invocation.
- **No `vercel.json` cron entry in this sprint** — the endpoint exists and is
  admin-triggerable; P2.4 wires the daily Hobby-slot schedule.
- Privileged / not user-scoped: each job carries its owner `userId`, which
  `runAttempt` uses for the Article read, so per-job ownership still holds.

## 6. P2.3-F — Private API

Thin `withContext` handlers — `auth → validate → PublishingService → ApiResponse`.
No business logic in the routes.

| route | method | does |
| --- | --- | --- |
| `/api/private/publishing/articles/[id]/publish-jobs` | `POST` | `createJob({ userId, articleId, destination })` — `destination` defaults to `INTERNAL_BLOG`; returns the job (201). Idempotent (returns the existing job for the same content). |
| `/api/private/publishing/articles/[id]/publish-jobs` | `GET` | the caller's jobs for this Article, newest first |
| `/api/private/publishing/articles/[id]/publish-jobs/[jobId]` | `GET` | `{ job, attempts }` — 404 if the job isn't the caller's or isn't for this article |

`userId` is always `sessionUser.profile.id` — never a request body value.
