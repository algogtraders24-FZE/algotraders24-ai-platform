## 2. Data model

Two new tables, one additive back-relation on `articles` (**no new column
there**), zero change to any other model. Schema diff: **+120 lines, 0
deletions**.

### `PublishingJob` (`@@map("publishing_jobs")`)

The logical "publish Article X to destination D at content version H"
operation. Owns lifecycle, idempotency and the authorization boundary.

| column | type | notes |
| --- | --- | --- |
| `id` | `String @id @default(cuid())` | |
| `articleId` | `String` | FK → `articles.id`, `onDelete: Cascade` |
| `userId` | `String` | Article owner. Denormalised (like `articles.userId`); **no User FK** (matches every model). Always from the server session. |
| `destination` | `String` | `PublishingDestinationId` (`"INTERNAL_BLOG"`). **String, not a Prisma enum** — a new destination is then one union member in `types/publishing` + **zero migration** (the free-string `agent.type` rationale, AN1.2 D1). |
| `status` | `enum PublishingJobStatus` | `PENDING RUNNING SUCCEEDED FAILED CANCELLED` — the P2.1 vocab, DB-enforced (matches the sibling `articles.status` being an enum) |
| `contentHash` | `String` | 64-hex sha256 of `canonicalContentBasis()` — the content **version** (P2.1 §9). Not the Article's content. |
| `idempotencyKey` | `String` | `"{articleId}:{destination}:{contentHash}"` — denormalised `publicationIdentityKey`, for logs/single-handle lookups |
| `scheduledFor` | `DateTime?` | set only by P2.4 (a preset slot) |
| `requestedAt` / `startedAt?` / `completedAt?` | `DateTime` / `?` | |
| `attemptCount` | `Int @default(0)` | incremented atomically as each attempt starts |
| `lastError` | `Json?` | `PublishError` — present while `FAILED`, cleared on `SUCCEEDED` |
| `result` | `Json?` | `PublishResult` — present once `SUCCEEDED` |
| `createdAt` / `updatedAt` / `deletedAt?` | | standard |

Indexes: **`@@unique([articleId, destination, contentHash])`** (the P2.1
idempotency identity), `@@index([userId])`, `@@index([status])`,
`@@index([status, scheduledFor])` (P2.3/P2.4 dispatcher scan),
`@@index([idempotencyKey])`, `@@index([articleId])`, `@@index([deletedAt])`.

### `PublishingAttempt` (`@@map("publishing_attempts")`)

One execution of a job. **Append-only** — a retry is a new row, never an edit
(mirrors `AgentStep` / `AuditLog`). **No `updatedAt`, no `deletedAt`.**

| column | type | notes |
| --- | --- | --- |
| `id` | `String @id @default(cuid())` | |
| `jobId` | `String` | FK → `publishing_jobs.id`, `onDelete: Cascade` |
| `attemptNumber` | `Int` | 1-based, gapless. `@@unique([jobId, attemptNumber])` |
| `status` | `enum PublishingAttemptStatus` | `RUNNING SUCCEEDED FAILED` |
| `startedAt` / `completedAt?` | `DateTime` / `?` | |
| `error` | `Json?` | `PublishError` — required when `FAILED` |
| `externalReference?` / `externalUrl?` | `String?` | destination-issued; `null` for `INTERNAL_BLOG`, never fabricated |
| `destinationResponseMeta` | `Json?` | safe, non-secret metadata only (adapter strips tokens/PII) |
| `createdAt` | `DateTime @default(now())` | |

Indexes: `@@index([jobId])`, `@@index([status])`.

### `Article` change

Only `publishingJobs PublishingJob[]` (a virtual back-relation — **no column,
no data migration**).

## 4. Architecture (as built)

```
route / server action / (P2.3 dispatch) / (future Automation, Agent)
        │  { userId (from session), articleId, destination }
        ▼
┌──────────────────────────  PublishingService  ──────────────────────────┐
│  createJob():                                                            │
│     articleService.getById(userId, articleId)   ← OWNERSHIP GATE (404)   │
│     projectArticleToPublishInput(article, destination)  → contentHash    │
│     repo.findJobByIdentity({articleId,destination,contentHash})          │
│        └ hit  → return it (idempotent, any status)                       │
│        └ miss → repo.createJob(... status PENDING)                       │
│                                                                         │
│  runAttempt():                                                           │
│     getJob(userId, jobId)                        ← OWNERSHIP GATE (404)   │
│     assert status ∈ {PENDING, FAILED}            ← runnable?             │
│     re-project Article; computeContentHash === job.contentHash ?         │
│        └ no  → PERMANENT_FAILURE (stale job)     ← INTEGRITY GATE        │
│     job → RUNNING; repo.incrementAttemptCount(); repo.appendAttempt()    │
│     adapter.validate(input)   → !valid ⇒ attempt FAILED, job FAILED      │
│     adapter.publish(input)                                               │
│        └ PublishResult   ⇒ attempt SUCCEEDED, job SUCCEEDED (+result)    │
│        └ PublishError DUPLICATE ⇒ reconcile to SUCCEEDED (idempotent)    │
│        └ PublishError other      ⇒ attempt FAILED, job FAILED (+lastError)│
│        └ non-PublishError throw  ⇒ wrapped as UNKNOWN, same failure path │
└─────────────────────────────────────────────────────────────────────────┘
        │  NormalizedPublishInput            ▲  PublishResult / PublishError
        ▼                                    │
┌────────────────  InternalBlogAdapter (DestinationAdapter)  ──────────────┐
│  validate(): title / slug / body ≥ 80 chars / excerpt / disclaimer /     │
│              seo.metaDescription / canonicalUrl == blog-origin+slug /     │
│              no raw <script> (stored-XSS guard, P1 Security #3)           │
│  publish():  re-validate, then return { success, externalUrl = canonical │
│              URL, externalReference: null, publishedAt }                  │
│  NO React / HTTP / Prisma / cron / Automation / Agent.  NO authz.         │
│  NO job/attempt writes.  Does NOT recompute contentHash.                 │
└─────────────────────────────────────────────────────────────────────────┘

PublishingRepository  ── the ONLY module that touches publishing_jobs /
                         publishing_attempts.  Append-only for attempts.
```

**The adapter never owns job/attempt lifecycle** (Sprint P2.2 requirement).
The service does. The adapter is handed a `NormalizedPublishInput` and returns
a `PublishResult` / throws a `PublishError` — nothing else.

## 5. Article → PublishableContent serializer

`serializeArticleBody(sections)` — **deterministic**, section-ordered:

```
## {heading}\n\n{body}          (per section, joined by "\n\n")
```

No whitespace normalization (a trailing-space edit is a real content change
and must change the hash — P2.1 §9). This body string feeds
`canonicalContentBasis()`, so the format is **LOCKED** — changing it is a
`PUB-v2` concern.

`projectArticleToPublishInput(article, { destination })` maps:
`title←title`, `slug←seo.slug`, `body←serializeArticleBody(sections)`,
`excerpt←summary`, `canonicalUrl←seo.canonicalUrl`, `disclaimer←disclaimer`,
`seo←{metaDescription, keywords}`, then `contentHash←computeContentHash(...)`.
**Article content is not copied into any table** — the input is assembled on
demand (Sprint P2.2 §1).

Tests pin: equivalent content → identical hash; any publishable-field edit →
different hash; `articleId` / `destination` do not affect the hash.

## 6. `INTERNAL_BLOG` — what "publish" means in P2.2

There is **no reader yet** (the `/blog` route is P2.5). So `publish()` does not
post anywhere. It is the **gate**: it enforces the blog's content rules and
returns the on-site canonical URL as the confirmed result.

**The publication record for `INTERNAL_BLOG` is the `SUCCEEDED`
`PublishingJob`** (its `result.externalUrl` = the canonical URL,
`result.publishedAt`) plus its attempt history. No third "published content"
table — the spec's "no duplication of Article content" rule and the Article's
own read-only-once-published guarantee (existing
`articleService.update()` conflict guard) make a snapshot table unnecessary.
The P2.5 reader will query
`publishing_jobs WHERE destination='INTERNAL_BLOG' AND status='SUCCEEDED'`
joined to `articles`.

**Interim drift window (closed by P2.3):** until P2.3 wires the advisory
`ARTICLE_STATUS_ON_JOB_SUCCESS` map (job `SUCCEEDED` → `Article.status =
published`, which makes the Article read-only), a user could edit an Article
that has a `SUCCEEDED` job. The **integrity gate** in `runAttempt` already
refuses to *re-run* a stale job; the reader-side "published version ≠ current
Article" check lands with the reader in P2.5.

## 7. Boundaries held

| Rule (P2.1 §15–§18, P2.2) | How |
| --- | --- |
| Adapter is provider-neutral, no framework imports | `internal-blog.adapter.ts` imports only `@/types/publishing`. Verified. |
| Adapter performs no authorization | It receives a `NormalizedPublishInput`, which carries **no** `userId` / session / role / token (contract test pins the key set). |
| Adapter owns no job/attempt lifecycle | Only `PublishingService` calls the repository. |
| Authorization above the adapter | Every service entry point calls `articleService.getById(userId, …)` / `getJob(userId, …)` **first**. Cross-user reads and runs are rejected (tests). |
| No `types/agent-framework` / `services/agent-framework` dependency | None added. |
| Automation not wired | No trigger, no action, no import. |
| `ArticleStatus` untouched | No schema or code change to it. |
| No secret in errors/logs | `PublishError.message` is human text; `destinationResponseMeta` is documented "safe metadata only"; `InternalBlogAdapter` handles no secrets. |

## 11. P2.3 recommendation (do NOT start automatically)

**Next: P2.3 — Retry + dispatch.**

1. `apply + verify` the P2.2 migration (authorized step) — `migrate deploy` +
   `migrate status`, then a smoke test that `createJob`/`runAttempt` work
   against the real DB.
2. Wire the advisory `ARTICLE_STATUS_ON_JOB_SUCCESS` map: a `SUCCEEDED`
   `INTERNAL_BLOG` job moves the Article to `published` (in the service, in a
   transaction with the job patch). This closes the interim drift window (§6).
3. `article.*` audit actions in `AuditLogService` — one row per
   drafted/published/publish_failed.
4. Retry policy: a capped auto-retry (e.g. 3) for `RETRYABLE` `PublishError`s
   only, slot-spaced; `NON_RETRYABLE` and `IDEMPOTENT_DUPLICATE` are terminal.
5. A cron-authed `POST /api/private/publishing/dispatch`
   (`isValidCronSecret || requireAdmin`, `maxDuration = 60`, capped batch)
   that scans `status IN (PENDING, FAILED) AND retryable` and calls
   `runAttempt`.
6. The private API routes (`POST /articles/:id/publish-jobs`, `GET` job + its
   attempts) — thin `withContext` handlers over `PublishingService`.

P2.4 = scheduling (Hobby daily slot). P2.5 = `/blog` reader + public SEO
surface. P2.6 = end-to-end verification.
