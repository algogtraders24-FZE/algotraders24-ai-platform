## 1. The one constraint that shapes everything

The project is on the **Vercel Hobby plan → at most one cron run per path per
day**. A sub-daily `vercel.json` entry silently blocks *every* deployment
(documented trap; prior ~1-day outage). So **the publishing dispatcher runs
once a day**, and the scheduling model is built around that — not the other
way round.

---

## 2. Vercel cron — exactly one, daily

`frontend/vercel.json` `crons[]` now has **three** daily entries, the new one being:

```json
{ "path": "/api/private/publishing/dispatch", "schedule": "0 7 * * *" }
```

- **`0 7 * * *`** = 07:00 UTC, once a day. Slots in after the existing
  `02:00` (evaluate-outcomes) and `06:00` (ingest-news) crons, so any
  news-influenced content is fresh.
- **Exactly one** cron entry targets the dispatcher (asserted by a test).
- Every cron in the file pins minute + hour and leaves DOM/MONTH/DOW = `*`
  (asserted: no `*` / `*/n` in minute or hour anywhere).
- Vercel Cron invokes it as a **GET** with `Authorization: Bearer
  <CRON_SECRET>`; the P2.3 route already handles that
  (`isValidCronSecret(req) || requireAdmin(...)`, `maxDuration = 60`).

## 3. Scheduling contract  (`types/publishing/schedule-contract.ts`)

Pure module, exported from `@/types/publishing`. Additive — **contract stays
`PUB-v1`** (no breaking change).

### Preset slots — NOT a free clock

```ts
type PublishingSlot = "00:00" | "12:00";          // HH:MM, UTC
const PUBLISHING_SLOTS = ["00:00", "12:00"] as const;
```

A scheduled job targets one of these fixed UTC times of day — never an
arbitrary user-picked instant. The set is small and fixed; adding a slot is
one member here plus a product decision, with no schema change and no
contract-version bump.

> With a single daily Hobby cron the *effective* resolution is "the next daily
> dispatch". Two slots (start-of-day / midday UTC) is enough to express
> "publish in the earliest batch" vs "hold for the next one". The model is
> already correct for when more cron runs are added on a paid plan.

### `PublishSchedule`

```ts
type PublishSchedule =
  | { kind: "immediate" }               // publish in the very next dispatcher run
  | { kind: "slot"; slot: PublishingSlot };  // publish at/after the next UTC occurrence of `slot`
```

Guards: `isPublishingSlot`, `isPublishSchedule`, `validatePublishSchedule`
(returns `ContractValidationResult` with a human-readable message).

### `nextSlotOccurrence(slot, from)` — deterministic

The next UTC instant matching `slot`, **strictly after** `from`:

- today's slot instant is used **only if it is strictly in the future**
  relative to `from`;
- otherwise (it is now, or already past) → **tomorrow's** slot instant.

"Strictly after" makes the boundary unambiguous — scheduling for the 12:00
slot at exactly `12:00:00.000Z` targets *tomorrow*, never a same-instant race.
Same `from` → same result, on any machine, forever. Handles month/year
rollover (tested).

### `resolveScheduledFor(schedule, now)`

`immediate → null` · `slot → nextSlotOccurrence(slot, now).toISOString()`.
`now` is injected (the service reads `new Date()` once, here).

## 4. Timezone — LOCKED: backend is UTC-only

- Slots are UTC times of day. `PublishingJob.scheduledFor` is a UTC instant.
- **No timezone conversion anywhere in the backend.**
- A future UI will let a user pick a local time and convert it to the nearest
  approved UTC slot **before** calling the API — that conversion is a UI
  concern, explicitly **out of P2.4 scope**. P2.4 deliberately introduces zero
  timezone complexity.

## 5. Create-job scheduling  (`PublishingService.createJob`)

`CreateJobParams` gains an optional `schedule?: PublishSchedule`.

| request | `scheduledFor` on the new job | dispatcher behaviour |
| --- | --- | --- |
| omitted, or `{ kind: "immediate" }` | `null` | picked up by the **next** dispatch run |
| `{ kind: "slot", slot }` | `nextSlotOccurrence(slot, now)` (a future UTC instant) | **skipped** until that instant passes, then picked up by the next dispatch run |

- **Past-slot handling is deterministic** — `nextSlotOccurrence` rolls a
  now-or-past slot to tomorrow; there is no ambiguous "publish immediately
  because the slot already passed" path.
- **Idempotency unchanged:** if a job already exists for the publication
  identity, `createJob` returns it **without changing its schedule**.
  Rescheduling an existing job is a separate capability, out of P2.4 scope.
- The dispatcher's due-filter was already built in P2.3
  (`findDispatchableJobs`: `scheduledFor IS NULL OR scheduledFor <= now`) —
  P2.4 only starts *setting* `scheduledFor`.

## 6. Private API

`POST /api/private/publishing/articles/[id]/publish-jobs` accepts an optional
`schedule` in the body:

```jsonc
{ "destination": "INTERNAL_BLOG" }                              // immediate (default)
{ "schedule": { "kind": "immediate" } }                        // immediate (explicit)
{ "schedule": { "kind": "slot", "slot": "12:00" } }            // next 12:00 UTC
```

An unknown/invalid `schedule` shape → `422` with the validator's message
(`validatePublishSchedule`). `userId` is still always the server session.
