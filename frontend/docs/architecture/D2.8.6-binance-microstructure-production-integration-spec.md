# D2.8.6 — Binance Microstructure Production Data-Fabric Integration & Runtime Verification

**Status:** Implemented and tested against REAL, live Binance data. **Baseline:** D2.8.5 (`5dc71d1`).
**Scope:** Move D2.8.5's Binance microstructure foundation one controlled step closer to production by (1) proving the full pipeline works end-to-end against real BTCUSDT/ETHUSDT data through the actual production code, and (2) exposing a minimal, established-pattern production-consumable boundary. **No trading signal, strategy, or Intelligence-layer wiring exists anywhere in this sprint.**

---

## 1. Executive summary

Every D2.8.5 component was reused verbatim — no calculation, validation, or type was reimplemented. This sprint's own contribution is narrow and additive: one new shared-instance file (`services/microstructure/shared-instance.ts`, mirroring the existing `services/market-data/shared-instance.ts` pattern exactly) and one real-network validation script (`scripts/validate-microstructure-runtime.ts`) that calls the real production `BinanceProvider` + `MicrostructureSnapshotService` against Binance's live public API — not a fake transport, not a reimplementation. **19/19 tests pass, including two genuine live network calls that returned real BTCUSDT and ETHUSDT microstructure evidence.**

## 2. Phase 0 — repository audit and integration decision

Traced fresh (not assumed from D2.8.5's own memory): `BinanceProvider.getMicrostructureSnapshot()`, `MicrostructureSnapshotService.getSnapshot()`/`buildMicrostructureSnapshot()`, every `lib/microstructure/*` function, and the capability registry. **Nothing needed duplication.** `MicrostructureSnapshotService` was already, exactly, D2.8.5's own "controlled production-consumable data boundary" — this sprint's job was to (a) prove it works against real data (D2.8.5 only ever exercised it with a fake transport) and (b) give it the same shared-instance treatment every other production data source in this codebase already has.

**Integration decision:** `services/microstructure/shared-instance.ts` was added, exporting `binanceMicrostructureProvider` (a `BinanceProvider` instance) and `microstructureSnapshots` (a `MicrostructureSnapshotService` instance) — mirroring `services/market-data/shared-instance.ts`'s exact shape (D2.3 Phase 9). **No new API route was added.** The sprint's own success criteria (§ SUCCESS CRITERIA, 14 items) are all satisfiable without one — they are about proof-of-correctness (real data reaches the pipeline, calculations are D2.8.5-only, capability registry accuracy, failure handling, regression) — and adding a new HTTP-facing, user-triggerable endpoint that returns real live financial microstructure data would be new user-facing surface area beyond this sprint's own framing ("one controlled step," "prove... travels through safely"). The shared-instance file is the boundary; a route consuming it (if ever wanted) is a natural, small addition for a future, explicitly-scoped sprint.

No duplicate data-fabric architecture was created. No calculation or validation logic was duplicated. Provider priority ordering (`MarketDataService`'s default array) was not touched — reconfirmed by rerunning every prior sprint's own provider-order assertion (§10).

## 3. Real Binance runtime path (Phase 1) — exact endpoints used

Identical to D2.8.3/D2.8.5, confirmed reachable this session (`GET https://api.binance.com/api/v3/ping` → `200`):

## 8. Raw evidence mapping (Phase 2, reconfirmed against real data)

All rules are D2.8.5's own, exercised here against genuine Binance responses rather than fakes for the first time: bid/ask taken from `depth.bids[0]`/`depth.asks[0]`, validated for finiteness/positivity/non-crossed; order-book levels validated per-side (any single malformed level invalidates that whole side); trades mapped through `isBuyerMaker` (documented meaning: `false` → buy-side aggressor, `true` → sell-side aggressor); sequence ID taken from `lastUpdateId`, validated as a non-negative integer string. Every real BTCUSDT/ETHUSDT trade observed this sprint carried real `isBuyerMaker` evidence — none needed to fall back to "unavailable."

## 9. Validation behavior (Phase 2/7, reconfirmed live + degradation-tested)

Live-confirmed: real bid ≤ real ask, real spread ≥ 0, real depth > 0 on both sides, real depth imbalance within `[-1, 1]`. Degradation-tested against a controlled fake transport (deterministic, since real failure conditions can't be reliably reproduced against a live third-party API): a negative order-book quantity is rejected as `"invalid"` (never repaired); a request failure raises a real, typed `MarketDataProviderError` (`kind: "http_error"`), never a silently empty snapshot; a malformed (non-array) trades response degrades to an `"invalid"` trades field, never a crash; a stale trade timestamp is honestly classified `"stale"`.

## 10. Deterministic calculation behavior (Phase 3/4, reconfirmed live)

Every derived field in §4/§5 was produced exclusively by the exact D2.8.5 functions listed in §5's closing sentence — none was reimplemented, extended, or bypassed this sprint. `volumeDelta`'s mathematical identity (`buyVolume - sellVolume`) was verified to hold exactly (within floating-point tolerance) against real trade data for both instruments. Where real evidence didn't exist (this sprint's fake-transport degradation tests, e.g. trades without `isBuyerMaker`), `buyVolume`/`sellVolume`/`volumeDelta` were confirmed `"unavailable"`, never `0`.

## 12. Failure / degradation behavior (Phase 7)

All 12 conditions from the brief were exercised (via the deterministic fake-transport tests, since a live third-party API cannot be reliably forced into a specific failure mode): request failure → typed error, never silent; malformed response → invalid field, never a crash; missing bid/missing ask → unavailable; crossed market → invalid, never swapped; stale timestamp → `"stale"`; invalid order-book level → invalid, whole side rejected; missing aggressor field → unavailable, never guessed; empty trade set → unavailable; partial/malformed order-book response → invalid or unavailable per the specific defect. **No fabricated value, no silent unavailable→zero conversion, and no OHLC-derived fake microstructure was found or introduced anywhere.** Existing OHLC functionality (`BinanceProvider.getSnapshot()`/`getMarketContext()`) was directly re-verified this sprint (test 19) to be byte-identical in shape — no microstructure field leaked into it.

## 14. WebSocket vs REST distinction (explicit, per the sprint's own instruction)

- **Production transport (this sprint, and D2.8.5 before it): REST only.** `BinanceProvider.getMicrostructureSnapshot()` calls `/depth` and `/trades` via plain HTTP GET. No WebSocket client exists in any production file.
- **WebSocket capability: proven, but research-only, from D2.8.3.** D2.8.3's disposable probe scripts (never committed, deleted after use) confirmed Binance's public WebSocket streams work and carry richer real-time semantics (incremental diff-depth with `U`/`u` sequencing). That capability is real and documented, but this sprint does **not** claim it as the production transport, and no WebSocket infrastructure was added, redesigned, or even referenced in any file this sprint touched.
- **Future streaming integration** would be a distinctly-scoped future sprint's decision, not silently introduced here.

## 20. Known limitations

- No API route consumes `services/microstructure/shared-instance.ts` yet — deliberate, per §2's reasoning. A future sprint would need to add one (with its own auth/rate-limit/symbol-validation review) before any real user-facing consumption exists.
- `HISTORICAL_TICKS`/`historicalTrades` remain untested — out of this sprint's scope, unchanged from D2.8.5.
- The two REST calls (`/depth`, `/trades`) inside one `getMicrostructureSnapshot()` invocation are not perfectly atomic (a few milliseconds can separate them) — disclosed in D2.8.5 already, unchanged here; stricter atomicity would require the WebSocket diff-depth stream, explicitly out of scope.
- This sprint's real-network evidence (§4/§5) is a point-in-time capture, not a continuously-running production feed — no caching, scheduling, or persistence of microstructure snapshots exists anywhere.
