# D2.7.11 - Native Chart MT5 Feature-Parity Roadmap

## Why this exists

The user's explicit, long-term ask (this session): make the Native Chart not just LOOK like their live MT5 terminal (D2.7.x's own "mt5" canvas theme - hollow candles, black background, teal current-price line - already shipped), but actually carry the FEATURES they use in real MT5 day to day. Their own words: "sirf mai usme use honewale feature bhi implement karna chahta hu" (I also want the features it uses implemented) and "sare banao, time lelo, lekin hame ye chahiye long term goal ke liye" (build all of them, take your time, this is for a long-term goal).

This is deliberately scoped as a multi-phase program, not a single sprint - the full MT5 feature set (44 analytical objects, 38 built-in indicators, multi-chart workspaces, saved templates) is large. Each phase below ships independently, fully tested, with zero regression to what already exists - the same discipline every D2.7.x phase has followed.

**Not in scope for this roadmap:** no order execution, no BUY/SELL, no "Algo Trading" toggle, no broker connectivity beyond the existing read-only MT5 market-data bridge - this chart shows and annotates price, it never places a trade. (2026-08-21: the user's stated long-term plan is to build a paper-trading terminal on top of this chart later, so this is a scoping boundary for the current roadmap, not a permanent platform invariant - order execution is simply its own, not-yet-opened epic, distinct from chart feature-parity work.)

## Research basis

MetaTrader 5's real feature set (metatrader5.com/mql5.com, verified this session):
- **46 analytical objects** across 8 categories: Lines, Channels, Gann Tools, Fibonacci Tools, Elliott Tools, Shapes, Arrows, Graphical Objects.
- **38 built-in technical indicators** across 4 categories: Trend, Oscillators, Volumes, Bill Williams' tools.
- Multi-chart workspaces (multiple symbol/timeframe charts open as tabs/tiles within one terminal window).
- Per-chart saved templates (a named bundle of indicators/objects/colors, reusable across symbols) and object persistence across terminal restarts.

## Phase status

### Phase 1 - Drawing Tools foundation: SHIPPED (this session)

Trend Line, Horizontal Line, Rectangle. Object model, hit-testing (endpoint + body handles), drag-to-move/resize, 2-click placement with a live preview, Delete/Escape, sessionStorage persistence per symbol+timeframe (tab-scoped - see Phase 1b below for why this isn't durable cross-session storage yet).

Files: `lib/chart-engine/drawing/{types,geometry,store,drawing-renderer}.ts`, `components/chart-engine/DrawingToolbar.tsx`, `NativeChart.tsx` wiring. Tests: `scripts/validate-native-chart-drawing-tools.ts` (27 assertions), zero regression across the existing 698+ native-chart assertions.

### Phase 1b - Fibonacci Retracement + durable persistence: SHIPPED

- **Fibonacci Retracement** (`OBJ_FIBO`): SHIPPED (commit `7175977`). Reuses the exact same 2-click placement/drag/select pipeline Phase 1 already built (a trend-line-shaped anchor pair, plus MT5's real ratio levels: 0, 0.236, 0.382, 0.5, 0.618, 0.786, 1 drawn as horizontal sub-lines between the two anchors) - additive to the existing `DrawingObject` union, not a rework.
- **Durable persistence**: SHIPPED. The open design decision (new Prisma model vs. extending WorkspacePreference) was resolved in favor of a dedicated table - `ChartDrawingSet` (one row per `userId`+`symbol`+`timeframe`, the exact compound key the old sessionStorage entries already used, storing the whole object array as JSONB). WorkspacePreference is a flat one-row-per-user model with no per-symbol dimension at all, so it couldn't hold a per-(symbol,timeframe) array without becoming a second table in practice anyway. New: `services/chart/chart-drawing.service.ts` (validation, whole-array-replace upsert), `GET`/`PUT /api/private/chart-drawings`, `lib/chart-engine/drawing/validation.ts` (the one `isValidDrawingObject` shared by client and server). `lib/chart-engine/drawing/store.ts`'s `readDrawingObjects`/`writeDrawingObjects` kept their names/roles but became async fetch calls; writes for the same symbol+timeframe key are serialized through a per-key promise queue in store.ts so async network resolution can never land out of order (a rapid add-then-delete could otherwise resurrect the deleted object). `NativeChart.tsx`'s load/save effects gained a `drawingsLoadedKeyRef` guard (mirrors the file's existing `fittedKeyRef` pattern) so the "clear local state while the new symbol's real data loads" step can never itself be mistaken for a real edit and overwrite a symbol's saved drawings with `[]` before they've loaded. Tests: `scripts/validate-chart-drawing-persistence.ts` (11 assertions, real Postgres, synthetic tagged user, self-cleaning) + the persistence section of `scripts/validate-native-chart-drawing-tools.ts` (fetch-mocked, including a dedicated out-of-order-write race test).

### Phase 2 - Expanded indicator library: SHIPPED (this session)

Today's `DEFAULT_INDICATOR_CONFIGS` (EMA-20/50, SMA-20, Bollinger-20/2, RSI-14, MACD-12/26/9, Volume) covered 6 of MT5's 38 at the start of this phase. All 7 planned additions are now shipped, each with its own real MT5-verified default (mql5.com/metatrader5.com, never a textbook/invented value) and its own dedicated test coverage in `scripts/validate-native-chart-indicators-phase2.ts` (49 assertions):

1. **ATR-14** - own sub-panel, dynamic 0..max scale.
2. **Stochastic Oscillator 5/3/3** ("Slow Stochastic", MT5's real default - not the textbook fast-stochastic every other platform ships) - own sub-panel, %K/%D lines, real 80/20 reference lines.
3. **ADX-14** - own sub-panel, ADX/+DI/-DI three-line display, deliberately no reference line (MT5's own ADX indicator has none by default).
4. **CCI-14** (MT5's real default - not Lambert's original 20) - own sub-panel, real +-100 reference lines.
5. **Williams %R-14** - own sub-panel, real -20/-80 reference lines (the mirror of Stochastic's 80/20, on its own -100..0 range).
6. **Parabolic SAR 0.02/0.2** - price overlay, discrete dots (never a connected line - a stop-and-reverse LEVEL, not a continuous value).
7. **Ichimoku Kinko Hyo 9/26/52** (Tenkan/Kijun/Senkou) - price overlay, five lines (Tenkan-sen, Kijun-sen, Senkou Span A, Senkou Span B, Chikou Span). The architecturally distinct one of the batch: Senkou Span A/B plot `kijunPeriod` (26) candles AHEAD of the candle they're computed from, and Chikou Span plots 26 candles BEHIND - genuine time-shifted output, not just a new formula. This works with zero renderer changes because the chart's existing gapless index-scale extrapolation (`fractionalIndexForTime` in `index-scale.ts`) already positions a time beyond the real candle range correctly in both directions - a shifted `IndicatorPoint.time` (a real value, honestly computed, at a synthetic/extrapolated time) renders exactly like a real candle's time would. The cloud fill between Senkou Span A/B (a cosmetic convenience some platforms shade) was deliberately left as two plain lines rather than a filled polygon - filling would need `ctx.closePath()`/`ctx.fill()`, two canvas primitives this codebase's test-fake `CanvasRenderingContext2D` mocks don't implement, the same "don't introduce an untested canvas primitive" discipline `strokeRect`/`ctx.arc` were avoided for elsewhere in this phase.

Bill Williams' tools (Alligator, Awesome Oscillator, Fractals) remain the one deferred, lower-priority item from the original Phase 2 scope - niche relative to the 7 shipped above; not currently planned as a near-term next step.

Each indicator followed the existing `lib/chart-engine/indicators/compute.ts` pattern exactly (a pure function keyed by `IndicatorConfig.id`, added to `panel-registry.ts`'s `DEFAULT_INDICATOR_CONFIGS` and `INDICATOR_PANEL_ID`) - no new architecture needed for 6 of the 7; Ichimoku's time-shifted lines were the one genuine architectural question this phase raised, and resolved without any renderer/index-scale change (see above).

### Phase 3 - Multi-symbol tiled chart layout: SHIPPED

MT5's ability to have several symbol/timeframe charts open and genuinely SIMULTANEOUSLY VISIBLE (real tiling - a grid of independently-driven charts, not tabs where only one is ever mounted at a time). This was, as flagged, the largest architectural change in the whole roadmap - a dedicated read-only investigation (an Explore agent mapping every consumer of `WorkspaceContext.symbol`) ran before any code, confirming the actual blast radius: `symbol` is read directly by 9 components, but only the chart itself needed to become multi-instance. Every other panel (header, AI Intelligence, Assistant, Research, ribbon, favorites, the global search) deliberately keeps following ONE shared "active" symbol - duplicating those N times per pane would fight how this product actually works (deep-dive intelligence tools tied to one instrument, not a simple MT5-style Market Watch list), and there is no real MT5 analog for "AI Intelligence panel locked to symbol X while chart pane B shows symbol Y" to imitate anyway.

**Scope, deliberately narrowed and documented (not silently invented):**
- **Native-engine only.** This whole roadmap has only ever touched the Native chart - TradingView (`AdvancedChart.tsx`) is completely untouched, stays a single non-tiled instance always following `WorkspaceContext.symbol` exactly as before this phase. The provider toggle stays global; a layout selector only appears when Native is active.
- **Real grid presets (1 / 2 / 2×2), not a full drag/resize window manager.** MT5's own common tiling arrangements; freeform window management would be a separate, much larger undertaking with little added value over fixed presets.
- **`panes` always has exactly `layout` entries** (front-truncated on shrink, grown from the primary pane's own symbol on grow) - simpler and more honest than silently keeping a hidden 4-pane buffer in memory "just in case."
- **Session-scoped persistence, not a new durable DB table** - mirrors exactly how Phase 1's drawn-object persistence started sessionStorage-only before Phase 1b later earned it a real table once proven. Keeps this already-large phase contained; durable tab/layout persistence is a natural, separately-flagged future increment, not bundled in here.

**Design**: exactly one pane is "primary", bidirectionally synced with `WorkspaceContext.symbol` - switching which pane is primary (or editing the primary pane's own symbol) updates the page's shared active symbol, so the rest of the workspace follows whichever chart the user designated as driving it (the exact pre-Phase-3 single-chart behavior, now a deliberate choice among several open panes instead of the only option). Every other pane owns a fully independent symbol/timeframe/indicator set with no such sync. Changing the symbol via the global search/ribbon/favorites updates the currently-primary pane in place - it never silently spawns a new pane.

**Files**: `NativeChart.tsx`'s `symbol`/`name` became controlled props (previously read from `WorkspaceContext` directly) - the one genuinely deep change, since a page can now have several `NativeChart` instances mounted at once, each showing a different instrument, which a single shared context value could never represent. Its `hypothesisType` relay (D2.8.13, fed by `WorkspaceResearch` for whichever symbol is primary) gained a guard - `symbol === activeSymbol` - so a pane showing a DIFFERENT instrument never receives another instrument's hypothesis. New `ChartPane.tsx` (one grid cell: a compact per-pane header - independent instrument search + "set primary" control, shown only when more than one pane is visible - above one `NativeChart`). `GlobalSymbolSelector.tsx`'s real search/debounce/keyboard-nav/discovery implementation was extracted into a new generic `InstrumentSearchBox.tsx` (`value`/`onChange` props, zero `WorkspaceContext` coupling) so each pane's own search reuses the exact same real behavior instead of a second, drifting copy - `GlobalSymbolSelector` is now a thin wrapper around it. `ChartPanel.tsx` was rewritten to own `panes`/`layout`/`primaryPaneId` (previously a single flat `timeframe`/`activeIndicatorKeys` pair) and `chart-session-state.ts`'s persisted shape was restructured to match (storage key bumped to `.v2`, old shape retired).

**Drawing objects, templates, and useChartCandles/useLiveQuote needed zero changes** - they already keyed off a `symbol` parameter (never `WorkspaceContext` directly), so N simultaneously-mounted panes each showing a different instrument was already safe at the data layer.

Tests: `scripts/validate-native-chart-tiling.ts` (19 assertions - layout growth/shrink, primary-pane sync in both directions, the hypothesisType guard, the InstrumentSearchBox extraction, session persistence) + updated assertions across `validate-native-chart-workspace.ts`, `validate-native-chart-verification.ts`, `validate-native-chart-professionalization.ts`, and `validate-universal-instrument-discovery.ts` wherever they encoded the pre-Phase-3 "NativeChart reads symbol from context" / "one flat session-state shape" assumptions as literal source-text checks - each one was a real, load-bearing assertion that needed a genuine update, not a deletion.

### Phase 4 - Object/template management: SHIPPED

Save a named bundle of active indicators + drawn objects as a reusable "template" (MT5's own Template feature), list/apply/delete templates. New `ChartTemplate` table (one row per `userId`+`name`, deliberately NOT scoped by symbol/timeframe - a template is a per-user library applicable to any chart, matching real MT5 template behavior including its own real limitation: a drawn object's saved price/time coordinates are reapplied as-is to whatever symbol/timeframe the template lands on, which can look nonsensical on a very different instrument - MT5 itself has this same limitation, so this isn't a shortfall to engineer around). Saving under an existing name is a deliberate upsert (overwrite), not a rejected duplicate.

New: `services/chart/chart-template.service.ts` (validation against the one canonical `DEFAULT_INDICATOR_CONFIGS` registry + `isValidDrawingObject`, per-user 50-template limit), `GET`/`POST /api/private/chart-templates` + `DELETE /api/private/chart-templates/:id`, `lib/chart-engine/templates/store.ts` (async fetch wrappers, same never-throws contract as `drawing/store.ts`). UI: a second "Templates" dropdown in `ChartToolbar.tsx` (own dismissal state, independent of the Indicators dropdown) with a `Modal`-based (`components/ui/Modal.tsx`, not a native `prompt()`) "Save as Template…" flow in `NativeChart.tsx`. Applying a template replaces BOTH halves at once: the active indicator set (bubbles up to `ChartPanel.tsx`, which owns that state, via a new `onApplyIndicatorKeys` prop distinct from the existing per-key `onToggleIndicator`) and the current chart's drawn objects (`commitDrawingObjects`, which piggybacks on Phase 1b's existing persistence-write effect - no new plumbing needed there). Tests: `scripts/validate-chart-template-persistence.ts` (11 assertions, real Postgres, self-cleaning) + `scripts/validate-native-chart-templates.ts` (14 assertions: fetch-mocked client store + source-text wiring checks for all three touched components).

### Phase 5 - Chart Properties & Presentation: IN PROGRESS

Opened after the user shared 4 real MT5 desktop screenshots (the chart right-click context menu, and the Properties dialog's Common/Show/Colors tabs) and asked what else from those is genuinely implementable. Scoped down from the full menu to pure presentation/UX items with no order-execution surface: chart type (Bar/Candlesticks/Line), a Properties panel (grid, period separators, OHLC-readout toggle, object-descriptions toggle, color-scheme presets), Save-as-Picture (PNG export), and an Object List panel (manage drawn objects). Explicitly excluded: Depth of Market, One Click Trading, Trade Levels/History, Expert List (order-execution-adjacent, out of scope per the working agreement below) and tick-vs-real-volume toggle / Chart Shift / Docked (low value regardless of scope - real volume is meaningless for forex/CFD, Chart Shift/Docked are desktop-window concepts with no browser analog).

**Strategic context**: the user's stated long-term intent is to use this chart as the foundation for a future paper-trading terminal, competing with other platforms - so this phase is held to a genuine MT5-parity bar rather than a "good enough" one. Paper trading itself (virtual portfolio, simulated order matching, BUY/SELL UI) is a distinct, not-yet-scoped future epic - this roadmap still touches zero order-execution surface.

**Phase 5a - Chart type toggle (Candles/Bars/Line): SHIPPED, live-verified** (commit `39563c3`). `renderChart()` gained an optional `chartType` param (default `"candlestick"`, so every existing caller renders byte-for-byte unchanged); new `drawBars` (plain OHLC bar - high-low line + open/close ticks, no filled body) and `drawLine` (single polyline through each candle's close, styled in the current-price marker's accent color) share the exact same index-scale x positioning as the existing `drawCandles`. `chartType` is local `NativeChart` state (like `isLive`/`activeTool`), deliberately NOT lifted to `ChartPanel` - it's a rendering-style preference, not per-instrument data. Live-verified on production in a 2x2 tiled layout: one pane set to Bars, a different pane to Line, simultaneously and independently.

**Phase 5b - Properties panel: Grid + Period separators: SHIPPED, live-verified** (commit `ca4065a`). `renderChart()` gained `showGrid` (default true, preserves the pre-existing always-on grid) and `showPeriodSeparators` (default false, matches real MT5's own default per the user's Properties dialog screenshot). New `computePeriodSeparators` (`time-axis.ts`) finds UTC day boundaries, scoped to intraday timeframes only - a D1+ bar already IS a day, so a same-scale boundary line there would be redundant. New "Properties" toolbar button opens a `Chart Properties` Modal (reusing the existing `Modal` component, same one Save-as-Template already uses) with Grid/Period separators checkboxes. Deferred from this slice: OHLC-readout toggle (our OHLC display is a different, hover/crosshair-driven feature from MT5's always-visible latest-bar readout) and object-descriptions toggle (nothing to toggle until the Object List panel gives drawn objects real labels). Live-verified on production: Grid off genuinely removes gridlines (confirmed via zoomed screenshot), Period separators on renders a distinct dashed vertical line exactly at the day boundary, independent of the (disabled) grid.

`scripts/validate-native-chart-phase5.ts` grew from 12 to 23 assertions across 5a+5b, mirroring Phase 2's one-file-per-phase indicator test pattern.

**Remaining Phase 5 sub-slices (not yet started):** color-scheme presets (Colors tab), Save-as-Picture, Object List panel.

## Working agreement for this roadmap

- Each phase ships as its own tested, reviewed unit - never several phases half-done at once.
- Every new drawing object/indicator reuses the EXISTING coordinate-system/viewport/panel-layout primitives (`priceToY`/`timeToX`/`Viewport`/`PanelRow`) - never a second geometry system.
- No phase touches order execution, ever.
- Research claims (MT5's real default behavior for a given tool) are grounded against mql5.com/metatrader5.com before being implemented as fact, matching this session's own research-first discipline - a cosmetic choice (e.g. a drawing tool's default color) is never presented as "this is MT5's real default," only a genuine platform behavior claim is.
