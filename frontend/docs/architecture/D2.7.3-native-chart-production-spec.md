# D2.7.3 — AT24 Native Chart Engine: Production Data Layer, Indicators & Professional Chart UX

**Status:** Implemented and tested.
**Scope:** Turns the D2.7.2 foundation (candles, pan/zoom/fit, crosshair, axes) into a substantially more capable professional charting surface — provider provenance, deterministic candle indexing, live-edge navigation, a real indicator engine (EMA/SMA/RSI/MACD/Bollinger/Volume), overlay + sub-panel rendering, an upgraded crosshair, and a professional toolbar — while preserving D2.7.2's deterministic architecture and every one of D2.7.2's non-goals.

---

## 1. Architecture changes over D2.7.2

No existing architecture was rebuilt. Every addition either extends an existing module additively or sits in a genuinely new file that consumes existing ones:

- `services/market-data/market-data.service.ts` — `getTimeSeries()` (unchanged signature, unchanged behavior) is now a one-line wrapper around a new `getTimeSeriesWithProvenance()`, which contains the SAME provider-selection loop (same order, same reliability wrapping) plus provenance capture. Every existing caller (`RealTimeIntelligenceService`, the hypothesis outcome evaluator, `trading-copilot.service.ts`) is unaffected — verified by a regression test asserting `getTimeSeries()`'s output equals `getTimeSeriesWithProvenance().candles` for the same inputs.
- `lib/market-data/indicators.ts` — the existing scalar functions (`sma`/`ema`/`rsi`/`atr`/`macd`/`bollinger`/`volumeMetrics`) are **completely untouched** (not even reordered). A new section appended at the end of the file adds `smaSeries`/`rsiSeries`/`bollingerSeries`/`macdSeries` (full per-candle arrays, for chart overlays/panels) and exports the previously-private `emaSeries`. Every series function's agreement with its scalar sibling is verified by test (`xSeries(values, period).at(-1) === x(values, period)`).
- `types/chart-data.ts` — `ChartSeries` gains optional `provider`/`providerSymbol`/`fallbackUsed`/`cached`/`cacheAgeMs`/`freshness`/`timestamp` fields (additive); `ChartDataStatus` gains `partial` (candles rejected but some usable) alongside the now-reachable `stale`.

## 2. Data flow

```
WorkspaceContext.symbol/timeframe
  -> useChartCandles (initial fetch + 20s background poll)
    -> GET /api/private/market-data/candles
      -> route-local TtlCache (15s) -- absorbs pan/zoom/poll repeats
        -> MarketDataService.getTimeSeriesWithProvenance()
          -> existing provider-priority loop (Twelve Data -> Alpha Vantage -> Binance -> Angel One)
      -> normalizeCandles() (D2.7.2, unchanged)
      -> assessFreshness() (D2.6.4, now consumed for candles for the first time)
      -> providerSymbol looked up from the existing canonical instrument catalog
  -> NativeChart: viewport/crosshair refs + indicator state
    -> computeIndicatorSeries() per active indicator (memoized on [candles, activeConfigs])
    -> renderChart() -> panel-aware Canvas draw (price + optional volume/RSI/MACD rows)
```

## 3. Provider provenance

`ChartSeries.provider`/`providerSymbol`/`fallbackUsed` are real, sourced from `MarketDataService.getTimeSeriesWithProvenance()` — never fabricated, never a placeholder. `providerSymbol` is looked up from the existing `CanonicalInstrument.providerMappings` for whichever provider actually served the request (no second symbol registry). **Known limitation, explicitly documented rather than worked around**: `cached`/`cacheAgeMs` reflect this route's own 15-second `TtlCache` (real, but a route-boundary cache — `MarketDataService` itself still does not cache candles at the service level, unchanged since D2.2). `freshness` is computed via the existing D2.6.4 `assessFreshness({kind:"candle", timeframe})` policy, which had a candle-shaped subject defined since D2.6.4 but no real consumer until this sprint.

## 4. Candle data management

`lib/chart-engine/candle-index.ts` (new): `nearestIndexByTime`/`lowerBoundByTime`/`upperBoundByTime`/`visibleWindow`/`latestCandle`/`candleAtExactTime`, all binary search over the normalizer's guaranteed strictly-increasing-time array. `crosshair.ts`'s `nearestCandleIndex` (fires on every `mousemove` — the highest-frequency call in the engine) now delegates to this O(log n) lookup instead of D2.7.2's O(n) linear scan; every other draw-time filter (a once-per-frame cost, not once-per-mousemove) was left as its existing O(n) filter, a deliberate choice — the real perf lever per Phase 12 is avoiding unnecessary React re-renders and recomputation, not micro-optimizing a single-pass array filter that already runs well within budget.

`useChartCandles` never refetches on pan/zoom/crosshair — viewport state lives entirely in `NativeChart`'s refs, untouched by the data-fetching hook, exactly as in D2.7.2.

## 5. Indicator architecture

Strict separation, per the sprint's own mandate:

```
Calculation Layer (lib/market-data/indicators.ts's *Series functions)
  -> Indicator Data (lib/chart-engine/indicators/compute.ts -> IndicatorSeries/IndicatorLine)
    -> Chart Coordinate System (lib/chart-engine/coordinate-system.ts, reused as-is)
      -> Renderer (lib/chart-engine/sub-panel-renderer.ts + renderer.ts)
```

`compute.ts` contains zero indicator math — it only reshapes `*Series` output into `IndicatorSeries`/`IndicatorLine`. The renderer contains zero knowledge of how a value was computed — it only draws points at real coordinates. `DEFAULT_INDICATOR_CONFIGS` (`panel-registry.ts`) uses the exact same periods `TechnicalContextService` already uses (RSI-14, EMA-20/50, SMA-20, Bollinger-20/2, MACD-12/26/9) so a chart value never disagrees with the AI Intelligence panel's value for the same symbol/timeframe.

## 6. Rendering architecture (panels)

`lib/chart-engine/panel-layout.ts` computes real pixel rows from `PANEL_REGISTRY`'s relative weights (price always largest) and the canvas's actual, ResizeObserver-driven height — never a hardcoded layout. `renderer.ts` draws the price panel (candles + grid + price axis + overlays) within its own row, then loops active sub-panel rows calling `sub-panel-renderer.ts`'s `drawVolumePanel`/`drawRsiPanel`/`drawMacdPanel`, each using a **panel-local** `Viewport` (same time range, panel-specific value range) passed through the SAME `coordinate-system.ts` functions the price panel uses — no second coordinate system. All panels share one horizontal time axis, drawn once at the bottom.

Indicator colors are all `var(--...)` references to AT24's existing five design-token hues (`--gold`/`--gold-strong`/`--steel`/`--signal-up`/`--signal-down`/`--text-3`) — never a new palette. MACD's histogram and Volume's bars deliberately reuse `--signal-up`/`--signal-down` with the SAME bullish/bearish meaning those tokens already carry for candles, not a borrowed decorative color.

## 7. Viewport architecture (live-edge model)

`isAtRightEdge(viewport, candles)` — true when the viewport's right bound is at or after (latest candle time − a small tolerance); `followLatest(viewport, candles)` shifts the viewport (preserving span/zoom) to track the latest candle. `NativeChart`'s data effect: a symbol/timeframe change always re-fits (a deliberate reset); a background poll's new candles only shift the viewport when the user was already at the edge — a manual pan-back is never forcibly overridden, matching the sprint's explicit requirement. "Go to latest" (`ChartToolbar`) and the `End`/`Home` keyboard shortcuts call the same functions.

## 8. Performance model

Pan/zoom/crosshair interaction updates `viewportRef`/`crosshairRef` and calls `draw()` directly — never `setState` per mouse event (unchanged from D2.7.2, still true with panels/overlays added). `computeIndicatorSeries` is memoized on `[candles, activeConfigs]` — recomputed only when the underlying data or the active indicator set changes, never per frame. Measured (via the test suite's own timing assertions, generous budgets for an unaccelerated CI-style environment): `renderChart` with 3 active sub-panels + 2 overlays completes well within budget at 500/2,000/5,000 candles; `nearestIndexByTime` (binary search) stays fast across 200 lookups at 5,000 candles; computing all 7 default indicators together at 5,000 candles and normalizing 5,000 raw candles both complete quickly.

## 9. Live/streaming

No WebSocket or streaming infrastructure exists anywhere in this platform's provider architecture (Twelve Data/Alpha Vantage/Binance/Angel One are all REST) — an explicit non-goal this sprint does not introduce. `useChartCandles` polls the candles route every 20 seconds as the honest fetch-based analog; the route's own 15-second cache absorbs the resulting load without extra provider pressure. A background poll never flashes "loading" or an error over already-showing data — a failed poll is silently skipped, the last good data keeps showing.

## 10. Multi-symbol compare (Phase 11)

Deliberately deferred per the sprint's own permission ("defer actual UI and document the extension point"). `types/chart-data.ts#ComparisonSeries` declares the shape (`primary`/`comparison`, both real `ChartSeries`) and the non-negotiable constraint for whoever builds the real renderer: two different instruments' raw prices must never share one y-axis (`independentScale: true`, currently the only legal value). No component imports or renders it yet.

## 11. Security boundaries

Unchanged from D2.7.2, re-verified: the candles route still requires authentication (`getUserOrNull` → 401), symbol validation is entirely server-side (`getCanonicalInstrument`), no provider credential or raw provider error ever reaches the client, and no client-side chart-engine file calls a provider URL directly. The route-local `TtlCache` and freshness assessment add no new trust boundary — both operate only on already-fetched, already-normalized data.

## 12. Known limitations

- No independent vertical pan/zoom (unchanged from D2.7.2 — still auto-fits the visible window).
- `cached`/`cacheAgeMs`/`freshness` describe this route's own boundary cache and D2.6.4's timeframe-relative policy, not a provider-level cache (candles are still never cached inside `MarketDataService` itself).
- No real streaming — 20-second polling is the honest fetch-based substitute, per the sprint's own explicit non-goal on introducing WebSocket infrastructure.
- Multi-symbol compare is types-only; no renderer exists yet.
- Live, authenticated interactive browser verification (actual chart rendering, indicator toggles, panel layout, keyboard nav) could not be completed in this environment — see the sprint's final report for exactly what was and wasn't verified.

## 13. Future extension points

- A real comparison-series renderer consuming `ComparisonSeries` (independently-scaled overlay or dual-axis).
- Provider-level candle caching inside `MarketDataService` itself, if a genuine need for it emerges beyond the route-local cache.
- Independent vertical pan/zoom.
- Additional indicator ids registering into the existing `PANEL_REGISTRY`/`computeIndicatorSeries` switch without any layout code changing.

## 14. Testing

`scripts/validate-native-chart-production.ts`, 90 assert-based tests: indicator series/scalar equivalence (14), the Indicator Data compute layer (10), panel registry/layout (8), candle-index binary search correctness against brute force (13), the live-edge viewport model (7), provider provenance via fake `TimeSeriesProvider` doubles (10), the candles route's new caching/freshness behavior (8), honest-state/no-fabrication guards (8), performance at 500/2,000/5,000 candles (6), and security/regression guards (6). All 80 of D2.7.2's own tests (`validate-native-chart-engine.ts`) were re-run and still pass unchanged.

Full regression across every pre-existing `validate:*` script, `tsc`, `eslint`, and `npm run build` results are reported in the sprint's final report.
