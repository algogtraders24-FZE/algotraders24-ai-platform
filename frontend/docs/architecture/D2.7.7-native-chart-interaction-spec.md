# D2.7.7 — AT24 Native Chart Engine: Professional Interaction & Navigation

**Status:** Implemented and tested.
**Scope:** An interaction-quality sprint, not a visual-redesign sprint. Moves the already-verified, already-professionalized D2.7.2–D2.7.6 chart engine's pan/zoom/crosshair/keyboard/touch interaction from "functional" to "deterministic, smooth, professional" — entirely by extending the existing viewport/coordinate-system/renderer architecture, never by duplicating it.

---

## 1. Interaction architecture (overview)

`NativeChart.tsx` remains the sole React/Canvas orchestrator: it owns interaction refs (`viewportRef`, `crosshairRef`, `dragRef`, and — new this sprint — `activePointersRef`/`pinchRef`/`isLiveRef`/`drawRafRef`) and wires DOM events to the existing pure core (`lib/chart-engine/viewport.ts`, `coordinate-system.ts`, `crosshair.ts`, `renderer.ts`), unchanged in structure since D2.7.2. The one real architectural change this sprint makes is **migrating the DOM event model from legacy Mouse Events to the standard, unified Pointer Events API** (`onPointerDown/Move/Up/Cancel/Leave`) — not a new interaction model, but the correct, modern replacement for the one the Phase 1 audit found was silently broken.

## 2. Architecture audit findings (Phase 1)

Re-read `NativeChart.tsx`, `ChartPanel.tsx`, `ChartToolbar.tsx`, `ChartHeader.tsx`, `ChartTimeframeSelector.tsx`, `renderer.ts`, `viewport.ts`, `crosshair.ts`, `candle-index.ts`, `coordinate-system.ts`, `panel-layout.ts`, `sub-panel-renderer.ts`, `useChartCandles.ts`, `ChartProviderToggle.tsx`, and every D2.7.1–D2.7.6 spec/test. Found seven genuine, verifiable interaction defects/gaps (§3) and confirmed the rest of the interaction surface (follow-latest state machine, binary-search crosshair, indicator memoization, multi-panel coordinate scoping, wheel-zoom velocity safety) was already correct — none of it was touched merely for style.

## 3. Genuine defects found and fixed

1. **A real "stuck dragging" bug.** Mouse Events have no capture mechanism: if a real drag ends with the button released *outside* the canvas (an extremely common fast-drag scenario), the canvas's own `mouseup` never fires at all, permanently leaving `dragRef` set — every subsequent hover would then misinterpret itself as a continuing drag from stale data. **Fixed** by migrating to Pointer Events with `canvas.setPointerCapture(e.pointerId)` on pointerdown: the browser now guarantees `pointermove`/`pointerup` reach the canvas regardless of where the cursor physically is.
2. **Zero touch/pinch support existed at all** — no touch handlers of any kind were present, meaning pan and zoom simply didn't work via touch on a real mobile device. **Fixed**: Pointer Events unify mouse/touch/pen through one model, so migrating to them gave single-finger pan "for free"; two-finger pinch-zoom was added by tracking pointers in `activePointersRef` (keyed by `pointerId`) and reusing the *exact same* `zoomViewport` wheel-zoom already uses, anchored at the real midpoint between the two live touch points.
3. **Keyboard focus state was invisible.** The canvas's `outline-none` class silently opted it out of the site's existing global `:focus-visible` gold-ring rule (`app/globals.css`, established since Sprint H1.6) that every other focusable element already gets. **Fixed** by simply removing the class — zero new CSS.
4. **Escape didn't cancel an in-progress interaction.** It only ever exited fullscreen (a separate, window-level D2.7.5 listener, left untouched). **Fixed**: the canvas's own `handleKeyDown` now also clears an active drag/pinch and the crosshair on Escape, without `stopPropagation` — so a single press correctly handles both scopes.
5. **Panning had no bounds** — a user could drag arbitrarily far past the real data into a permanently empty viewport. **Fixed** with a new, additive `clampViewportToCandleBounds()` (§5).
6. **`setIsLive` (a React state setter) was called unconditionally on every single pointer-move tick** of a drag/zoom gesture. React's own re-render bailout already prevented most of the resulting re-renders, but the setter call itself still ran every tick. **Fixed** by comparing against a new `isLiveRef` and only calling `setIsLive` when the value actually changes.
7. **The canvas redraw itself was never frame-coalesced** — `draw()` ran synchronously on every raw pointer event, which on a high-polling-rate input device could exceed the display's actual refresh rate, wasting CPU on redraws nothing ever displays. **Fixed** with a new `scheduleDraw()` (rAF-coalesced), used for the high-frequency pan/hover/pinch paths.

Everything else audited was already correct and is unchanged: the D2.7.4 `fittedKeyRef` initial-viewport-race fix, `isAtRightEdge`/`followLatest`, binary-search crosshair snapping (`candle-index.ts`), indicator memoization, wheel-zoom's inherent velocity safety (the applied factor depends only on `deltaY`'s sign, never its magnitude), and the renderer's D2.7.6 multi-panel coordinate scoping.

## 4. Pointer model

Unified Pointer Events (`onPointerDown/Move/Up/Cancel/Leave`) replace the previous Mouse-Events-only model. `setPointerCapture`/`releasePointerCapture` (wrapped in a `try`/`catch` — releasing an already-released pointer is a valid browser state, never fatal) guarantee correct delivery regardless of cursor position. `pointerleave` deliberately does **not** cancel an active drag — with real capture in effect, `pointermove` keeps being delivered even once the cursor visually exits the canvas, so a fast drag correctly continues rather than abruptly stopping at the edge (a genuine UX improvement that falls directly out of using capture correctly, not scope creep). A window-level `blur` listener is an always-on safety net that resets all interaction state for the one case pointer capture itself cannot guarantee an up/cancel event for (alt-tab, a native OS dialog stealing focus).

## 5. Pan model

`panViewport` (pure, unchanged since D2.7.2) computes the raw shifted viewport; the interaction layer then passes the result through the new `clampViewportToCandleBounds(viewport, candles)` (`lib/chart-engine/viewport.ts`, additive) before applying it. The clamp rule: the real data's oldest/latest candle can never be pushed further than the viewport's *own current span* past the near edge — i.e. pan-back stops once the oldest candle reaches the right edge of the view, pan-forward stops once the latest candle reaches the left edge. Span (zoom level) is always preserved when clamping. Deliberately **not** applied inside `panViewport`/`zoomViewport` themselves — both stay pure and unclamped, exactly matching D2.7.2's own locked-in test contract (`vp.minTime === candles[0].time` for `fitToData`) — clamping is composed at the call site, the same pattern `applyViewport` already used for `priceRangeForWindow`.

## 6. Zoom model

Wheel, keyboard (`+`/`-`), and the new pinch gesture all funnel through the *same* `zoomViewport` — never a second zoom model. Pinch computes a real Euclidean distance (`Math.hypot`) between the two live touch points; the ratio of the starting distance to the current distance becomes the zoom factor, anchored at the real midpoint between the fingers. All three paths route their result through `clampViewportToCandleBounds` before applying.

## 7. Follow-latest state machine

Unchanged from D2.7.3/D2.7.4: a symbol/timeframe change always re-fits (`fitToData`); a background poll's new candles shift the viewport only when `isAtRightEdge` was already true before the poll landed; a manual pan away disables follow; Go-Live/`End` restores it via `followLatest` (span-preserving). The D2.7.4 `fittedKeyRef` fix (never treating the empty-loading placeholder as a real "previous viewport" to follow from) is completely untouched and re-verified this sprint.

## 8. Crosshair behavior

Unchanged: binary-search nearest-candle snapping (`candle-index.ts`), never interpolated, cleared when the pointer exits the plot's horizontal bounds or the symbol/timeframe changes. New this sprint: Escape also clears it, and pointer movement is confirmed to never trigger `computeIndicatorSeries` (already-computed values are read via `valueAtIndex`).

## 9. Tooltip behavior

Unchanged and re-verified: Open/High/Low/Close via `formatPrice`, timestamp via `formatTimestamp`, Volume only when the hovered candle genuinely has one, indicator values read from the already-memoized series. No change/range figure was added to the tooltip — only fields deterministically derivable from the hovered candle itself are ever shown, per the sprint's own "do not invent missing values" instruction.

## 10. Keyboard behavior

Arrow-key pan and `+`/`-` zoom (unchanged in spirit, now clamped), `Home`/`End` for Fit/Go-Live (unchanged), and the new Escape-cancels-transient-state handling (§3.4). Focus is now visibly indicated (§3.3). No key handler swallows `Tab` — focus can always leave the canvas, no keyboard trap.

## 11. Touch behavior

Single-finger pan and two-finger pinch-zoom both work via the same unified Pointer Event handlers as mouse (§4, §6). `touch-action: none` on the canvas tells the browser never to interpret a touch there as a native scroll/pinch/navigation gesture, so the custom handling is the only thing responding to it. Desktop mouse behavior is provably unaffected: pinch requires `activePointersRef.size === 2`, which a single mouse pointer can never reach.

## 12. Performance model

`scheduleDraw()` (new) coalesces the actual canvas redraw to at most once per animation frame during a pan/hover/pinch pointer stream — a separate rAF handle (`drawRafRef`) from the pre-existing hover-readout throttle (`rafRef`), both cancelled on unmount. `applyViewport` now skips the `setIsLive` state-setter call entirely (not just relying on React's re-render bailout) when the live/not-live value hasn't changed. Indicator series remain memoized on `[candles, activeConfigs]`, recomputed only when data or the active indicator set changes — never during an interaction frame. `ResizeObserver` cleanup is unaffected.

## 13. Security

Unaffected — no interaction-layer change touches the candles route, provider credentials, session storage's field set, or any caching code. Re-verified via regression tests.

## 15. A note on the three updated pre-existing tests

Three prior sprints' test files (D2.7.4/D2.7.5/D2.7.6) asserted the literal function names `handleMouseMove`/`handleMouseUp` existed in `NativeChart.tsx`, to verify "no direct `setState` from the pointer-move handler except via the rAF throttle." The Pointer Events migration (§3.1–3.2, a genuine, justified architecture change) legitimately renamed these to `handlePointerMove`/`handlePointerUp`. Each of the three assertions was updated to reference the new names, with an inline comment explaining why — the underlying invariant those tests protect is unchanged and still verified; only the source-string reference was updated, matching the exact precedent already established in D2.7.5/D2.7.6 for this codebase's own prior legitimate-refactor-requires-test-update cases.

## 16. Known limitations

- Ending a pinch gesture (dropping from 2 pointers to 1) fully resets interaction state rather than seamlessly continuing as a single-finger pan with the remaining finger — a deliberate simplicity choice (`do not over-engineer`), not an oversight. The user simply starts a new gesture.
- Double-tap-to-fit for touch was not implemented — `onDoubleClick` remains mouse/pen-oriented. Not explicitly required by this sprint's brief; flagged as a real, tractable future addition rather than faked.
- No independent vertical pan/zoom (unchanged design decision since D2.7.2).
- Live, authenticated interactive browser verification (of the actual drag/pinch/keyboard feel) was not performed — see the sprint's final report for exactly what was and wasn't verified.

## 17. Extension points

- `clampViewportToCandleBounds` is a pure, standalone function — a future sprint could expose it as a user-configurable "elastic pan" behavior (e.g. a rubber-band bounce at the edge) without touching its callers' contracts.
- `activePointersRef`/`pinchRef`'s pointer-tracking pattern generalizes cleanly to a future multi-touch drawing-tool feature, if one is ever added, without a second pointer-tracking system.
- `scheduleDraw()`'s rAF-coalescing pattern is the natural place to add a "reduced motion" accessibility preference check in the future, if requested.
