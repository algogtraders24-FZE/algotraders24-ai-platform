# D2.6.2 — Real-Time Intelligence Query & Context Orchestration

**Status:** Implemented and tested. This is the authoritative contract for how a trader question becomes verified, relevant, authorized intelligence context.
**Scope:** Deterministic orchestration only — turns a raw question into a normalized `IntelligenceQuery`, then an explicit `IntelligenceContextRequest`, then a relevance-filtered `IntelligenceQueryContext`. No LLM, no ML classification, no network call beyond the real, authorization-checked database lookup for prior-analysis questions.

---

## 1. Query normalization

`IntelligenceQueryService.parse()` (`services/intelligence/query/intelligence-query.service.ts`) is pure, synchronous, and versioned (`INTELLIGENCE_QUERY_PARSER_VERSION = "1.0.0"`). Classification is a fixed, ordered list of keyword/phrase rules (`QUERY_TYPE_RULES`) checked against the lowercased question - never an LLM, never a trained intent classifier. Every rule that matches contributes its scopes to a deduplicated union; the **first** matching rule (checked in priority order: invalidation → hypothesis → evidence → regime → historical → risk → score → comparison → current-state) sets `queryType`. This exactly reproduces the sprint's own worked example: *"Why is Gold weak and what could invalidate this view?"* matches both the `invalidation` and `evidence` rules and reports the union `[hypotheses, invalidation, evidence, conflicts, market-state, regime]`, with `queryType: "hypothesis"` (the more specific/actionable phrasing wins the type). When **zero** rules match, `queryType` is honestly `"general-intelligence"`, `classificationConfidence` is `"low"`, `ambiguous` is `true`, and `requestedScopes` falls back to `["decision-context"]` (the caller gets the full picture rather than a guessed narrow one). Deliberately not over-engineered: no stemming, no synonym expansion beyond the small explicit tables below, no fuzzy matching.

## 2. Symbol resolution

`resolveSymbol()` follows the sprint's exact priority order: (1) a symbol mentioned explicitly in the question text, (2) a caller-supplied `requestContextSymbol` (e.g. a UI's active symbol selector), (3) `conversationContext.activeSymbol`, (4) unresolved. Explicit-text extraction tokenizes the question and checks each token against a small, hand-authored `SYMBOL_ALIASES` table (`gold`→`XAUUSD`, `bitcoin`/`btc`→`BTCUSD`, etc.) plus the real market registry's own canonical symbols (`lib/market-data/market-registry.ts#isKnownMarket`) - never a fuzzy/semantic match, and every alias resolves to a symbol that genuinely exists in the registry. If **more than one** distinct known symbol is mentioned (e.g. *"is gold or bitcoin moving more?"*), the resolver returns `symbol: undefined` with the real candidates listed in `ambiguousCandidates` - it never guesses which one the trader means. A symbol that cannot be resolved from any source is `undefined`, recorded in `IntelligenceQuery.missingContext`, and never defaulted or invented.

## 3. Timeframe resolution

`resolveTimeframe()` follows the identical priority order and the identical "never invent" discipline. Explicit-text extraction matches the real `SignalTimeframe` literals (`1m`/`5m`/`15m`/`30m`/`1h`/`4h`/`1d`/`1w`) directly, plus a small alias table (`m15`→`15m`, `hourly`→`1h`, `daily`→`1d`, `weekly`→`1w`). A missing timeframe is never defaulted to a platform-wide default (e.g. `1h`) merely because one exists elsewhere in the codebase - it stays `undefined` and is recorded in `missingContext`.

## 4. Scope selection

`buildContextRequest()` (`services/intelligence/query/intelligence-query-context.service.ts`) is a pure function mapping `IntelligenceQuery.requestedScopes` to explicit `include*` booleans on `IntelligenceContextRequest` - the sprint's own "no hidden implicit data gathering" rule made literal. A `"decision-context"` scope sets every `include*` flag (a caller asking for everything gets everything, explicitly, not by omission); every other scope sets only its own corresponding flag(s) (e.g. `"evidence"` also implies `includeConflicts`, since evidence and its conflicts are inseparable in this platform's contracts). Every selection function downstream gates on these flags rather than defaulting to "include everything."

## 5. Evidence selection

`selectedEvidence` is the real `EvidenceBundle.items` for the resolved symbol (already same-symbol-scoped by construction - `EvidenceBundle` is per-symbol, 15D.4), deterministically ordered by the existing, **unmodified** `EvidenceRankingService.rank()` (type-priority, then chronological, then source name - no new ranking algorithm, per the sprint's explicit instruction). This is deliberately **not** `DecisionContext.supportingEvidence`/`opposingEvidence` (D2.6.1's own narrower, hypothesis-derived-technical-string concept) - see §16 for why the two must not be conflated. Of the sprint's seven possible ranking factors (same symbol, same timeframe, direct hypothesis relationship, conflict relationship, source priority, recency, existing ranking), same-symbol is structural, source-priority/recency/existing-ranking are `EvidenceRankingService`'s own job, and direct-hypothesis-relationship/conflict-relationship are **not** separately implemented - see §17 for why.

## 6. Hypothesis selection

`selectedHypotheses` is drawn from the real, complete `Hypothesis[]` on the supplied `IntelligenceEnvelope` (not `DecisionContext.primaryHypotheses`, which is D2.6.1's deliberately narrower `DecisionHypothesisContext` restatement missing fields like `symbol`/`regimeContext`/`status`) - a presenter that receives `selectedHypotheses` sees the complete D2.5.3 object. Filtered to only those whose real, stored `predictionWindow` has not yet closed: `dueAt = decisionContext.generatedAt + candles * timeframeMs`, compared against the caller-supplied `generatedAt` ("now"). D2.6.2 **never generates a new hypothesis** - it only selects among what D2.5.3 already produced. A regime with zero generated hypotheses, or a regime whose one hypothesis has expired, is reported honestly in `missingContext`, never silently hidden.

## 7. Historical selection

`historicalContext` is `DecisionContext.historicalContext` (D2.6.1, itself a direct passthrough of D2.5.4's `HistoricalValidation`) - never a new statistical computation. `status` stays `"unavailable"`/`"insufficient-sample"` exactly per D2.6.1's own honest three-state model; `validatedRate` is never fabricated below D2.5.4's `MIN_HISTORICAL_VALIDATION_SAMPLE`. When the requested scope includes `historical-validation` but the status isn't `"available"`, the exact status is recorded in `missingContext` (e.g. `"historical-validation: insufficient-sample"`) - never silently dropped, never replaced with generic market statistics.

## 8. Previous-analysis retrieval

`AnalysisHistoryService` (`services/intelligence/query/analysis-history.service.ts`) adds new retrieval capability - by `analysisRunId` (with real outcomes attached), and by `userId` + optional `symbol`/`timeframe`/time-range filter - **without modifying D2.5.1's frozen `IntelligenceAnalysisRunService`/`IntelligenceAnalysisOutcomeService`**, which remain byte-identical. The orchestrator triggers this lookup **only** when the caller explicitly supplies `conversationContext.previousAnalysisRunId` (Example C) - never by pattern-matching words like "earlier"/"previously" in the question text, which would be exactly the kind of semantic guessing §4 of the sprint brief prohibits. The caller (a future chat orchestrator that already tracks conversation history) is responsible for knowing which prior run a follow-up question refers to; D2.6.2's job is only to retrieve and authorize it.

## 9. Authorization

Every lookup in `AnalysisHistoryService` is scoped by a caller-supplied, session-derived `userId` in the database WHERE clause itself - never a post-hoc filter, never a client-supplied value trusted at face value. `getOwnedAnalysisRun()` delegates directly to D2.5.1's own `IntelligenceAnalysisRunService.getAnalysisRun(id, userId)`, which already does `findFirst({where: {id, userId, deletedAt: null}})`. This mirrors the established platform-wide pattern (`services/ai/conversation-ownership.service.ts`): a run that exists but belongs to a different user is **indistinguishable from one that does not exist at all** - both resolve to `undefined`/`[]`, recorded honestly in `missingContext` as `"previous-analysis: the referenced analysis run was not found, or does not belong to this user"`, never a distinct "forbidden" that would leak the run's existence. Verified directly: a second, unrelated user requesting the same `analysisRunId` receives `previousAnalysis: undefined`.

## 10. Context completeness

`ContextCompleteness = "complete" | "partial" | "insufficient"` - **not** another Intelligence Score (the sprint is explicit: no new numeric score). Rules, evaluated in `IntelligenceQueryContextService.classifyCompleteness()`:

- **`"insufficient"`** — the query's symbol could not be resolved, or no `DecisionContext` could be built at all (no envelope was available for the resolved symbol/timeframe).
- **`"complete"`** — the symbol **and** timeframe both resolved, and every requested scope is satisfied (see below).
- **`"partial"`** — everything else: real data exists, but the timeframe is unresolved and/or at least one requested scope is genuinely unavailable.

A scope is "satisfied" per `isScopeSatisfied()`: `"risk"` requires `riskContext.dataAvailable === true`; `"historical-validation"` requires `historicalContext.status === "available"`; every other scope (market-state, regime, hypotheses, evidence, conflicts, intelligence-score, invalidation, monitoring, missing-information, decision-context) is satisfied whenever a real `DecisionContext` exists, because D2.6.1 already guarantees an honest, non-fabricated (possibly empty) answer for all of those - an empty `primaryHypotheses[]` is a complete, correct answer for an `insufficient-data` regime, not missing information.

## 11. Ambiguity

`IntelligenceQuery.ambiguous` is `true` in exactly two cases, both real and mechanical, never a subjective judgment: (1) zero keyword rules matched the question (fell back to `general-intelligence`), or (2) more than one known symbol was mentioned with no way to pick between them. Example D (*"What about Gold?"*) demonstrates both halves of the honest-uncertainty contract working together: the symbol resolves cleanly (only one candidate, "gold"→`XAUUSD`), but zero intent rules match, so the query is still `ambiguous: true`, `general-intelligence`, with `timeframe` in `missingContext` - never silently reinterpreted as "tell me whether Gold is bullish."

## 12. Freshness

`IntelligenceQueryContext.dataAsOf` is `DecisionContext.generatedAt` verbatim - the real timestamp the underlying `MarketState`/envelope was actually assembled at, `undefined` (never fabricated) when no envelope was available. `generatedAt` on the context itself is the caller-supplied "now" for this orchestration call, always distinct from `dataAsOf` when time has passed between analysis and query - verified directly (`dataAsOf` equals the envelope's real timestamp even when the query context's own `generatedAt` is a full day later). This is exactly the material a future presenter needs to say *"this analysis is based on data available at [dataAsOf]."* No scheduler, no background worker, no polling was added or implied.

## 13. Conversation continuity

`ConversationIntelligenceContext` (`types/intelligence-context-request.ts`) is caller-supplied **context, never market truth** - `activeSymbol`/`activeTimeframe` participate in symbol/timeframe resolution priority (§2-3) purely as a fallback source, and `previousAnalysisRunId`/`previousHypothesisId` gate the prior-analysis lookup (§8). The deterministic Intelligence Engine (D2.5.x/D2.6.1) remains the only source of what's actually happening in the market; this type only tells the orchestrator what the trader was just discussing.

## 14. AI Presenter boundary

`AIIntelligencePresenter` (D2.5.5, `types/intelligence-envelope.ts`) is unchanged. The intended chain is now:

```
Trader Question -> IntelligenceQuery -> Query Orchestrator -> IntelligenceQueryContext -> AIIntelligencePresenter -> Gemini / Claude / OpenAI / Future Model
```

The presenter receives only the verified, relevance-filtered `IntelligenceQueryContext` - never the raw envelope, never a live database connection. Extended presenter safety contract (documentation-only this sprint, no code change to the interface): a conforming presenter must use only the supplied context; never add a market fact, new evidence, or a new hypothesis; never alter regime, risk, historical validation, or Intelligence Score; explicitly acknowledge anything in `missingContext`; preserve every item in `selectedConflicts` as unresolved; and distinguish historical facts (`previousAnalysis`) from current observations (`decisionContext`) and a hypothesis (a falsifiable claim) from a fact. No model gets authority to modify the intelligence state - the deterministic AT24 Intelligence Engine remains the sole source of truth.

## 15. Security

Beyond the authorization boundary in §9: no client-supplied `userId` is ever trusted (every route wiring this service must derive `userId` from the authenticated session, matching `lib/auth/protectedRoute.ts`'s established convention); no new public API route was added this sprint (out of scope); `IntelligenceQueryContext`'s own shape has no `action`/`recommendation`/`signal`/`positionSize` field, structurally preventing a future consumer from mistaking it for a trade instruction - enforced by a dedicated regression test scanning both the key set and the full serialized output against real regex patterns (not a naive substring search, for the same false-positive reason documented in the D2.6.1 spec).

## 16. Known limitations

- Evidence selection does not implement "direct hypothesis relationship" or "conflict relationship" as separate ranking factors (sprint §10's factors 3-4) - `EvidenceBundle` items have no structural back-reference to which hypothesis they informed (a `Hypothesis`'s own `supportingEvidence`/`opposingEvidence` are D2.5.3's own curated re-citations from `MarketState`, not literally drawn from the caller-supplied `EvidenceBundle`), so implementing this honestly would require inventing a new cross-reference this sprint deliberately avoids fabricating. `selectedEvidence` is the full same-symbol bundle, ranked by type/recency/source only.
- `"comparison"` queries (e.g. *"compare gold and silver"*) are correctly **classified** but not given dedicated multi-symbol context assembly this sprint - `resolveSymbol()`'s own "never guess between multiple mentioned symbols" rule means a comparison question's symbol resolves to `undefined` by the same honest mechanism as true ambiguity, and the resulting context is `"insufficient"`. A future sprint building real side-by-side comparison would need a deliberate multi-symbol extension to `IntelligenceQuery`, not built ahead of that real need.
- `DecisionContext.supportingEvidence`/`opposingEvidence` (D2.6.1) and this sprint's `selectedEvidence` (D2.6.2) are intentionally two different evidence views over two different real sources (hypothesis-attributed technical citations vs. the raw `EvidenceBundle`) - a future presenter combining both must not conflate them as the same list.
- `INTELLIGENCE_QUERY_PARSER_VERSION`/`INTELLIGENCE_QUERY_ORCHESTRATION_VERSION` are both `"1.0.0"` - the classification rule table is intentionally small and literal per the sprint's own "do not over-engineer the parser" instruction, not an attempt at comprehensive natural-language coverage.

## Example flows (verified against the real services)

**A — "Why is XAUUSD weak?"** → `queryType: "evidence"`, scopes `[evidence, conflicts, market-state, regime]`. Selects the real `EvidenceBundle` (ranked), the current `MarketState`/`Regime`, no hypothesis scope requested. `completeness: "partial"` (timeframe not mentioned).

**B — "What would invalidate the current bullish hypothesis?"** → `queryType: "hypothesis"`, scopes `[hypotheses, invalidation]`. Selects the real, still-active `trend-continuation-bullish` hypothesis with its stored `invalidationCondition` - never a new interpretation of what would invalidate it.

**C — "Was your earlier breakout hypothesis correct?"** → triggers `AnalysisHistoryService.getAnalysisWithOutcomes()` via `conversationContext.previousAnalysisRunId` (never keyword-guessed). Returns the real prior `IntelligenceAnalysisRun` (with its immutable `hypothesisSnapshot`) and its real `IntelligenceAnalysisOutcome[]` - no rewriting of history, verified with an object-identity-preserving test.

**D — "What about Gold?"** → symbol resolves to `XAUUSD` (one clean candidate), but zero intent rules match: `ambiguous: true`, `queryType: "general-intelligence"`, `timeframe` missing, scopes `[decision-context]` (the full picture, since no narrower intent could be honestly determined). No fabricated "Gold is bullish" answer.
