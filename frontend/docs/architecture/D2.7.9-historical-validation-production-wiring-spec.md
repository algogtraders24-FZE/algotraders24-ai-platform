# D2.7.9 — Historical Validation Production Wiring

**Status:** Implemented and tested. **Baseline:** D2.7.8 (investigation-only, commit `1790f9a`).
**Scope:** Wire the existing D2.5.4/D2.6.5 hypothesis-outcome evaluator into a real, bounded, authenticated production trigger. Fix the idempotency gaps that made repeated/concurrent invocation unsafe. Do **not** redesign the evaluator, change historical-validation math, lower `MIN_HISTORICAL_VALIDATION_SAMPLE`, or touch chart-engine/Intelligence Score/DecisionContext/provider architecture.

---

## 1. Why this sprint exists

D2.7.8 found that the warning *"historical sample below minimum for validation"* is guaranteed to appear for every user/symbol/timeframe/regime/hypothesis combination in production, because the one function capable of producing real `validated`/`invalidated` `IntelligenceAnalysisOutcome` rows — `HypothesisOutcomeEvaluatorService.evaluatePendingAnalysisRun()`, wrapped by `evaluatePendingAnalysisRunsForUser()` — had **zero production callers**. It was deliberately built (D2.5.4, D2.6.5) as a callable seam for "a future cron/route," which was never added.

D2.7.9's job is narrow: add that trigger. Nothing about the evaluator's semantics, the 30-sample threshold, or the scoring formula changes. The warning will only go away as real evidence genuinely accumulates.

## 3. Two real bugs found and fixed during the audit (Phase 1)

Both were found by reading the existing evaluator against its own documented contract (`docs/architecture/D2.5.4-hypothesis-outcome-validation-spec.md`) before writing any trigger code, per this sprint's explicit instruction.

**Bug 1 — no-hypothesisSnapshot runs were never marked evaluated.** `evaluateAnalysisRun()`'s no-snapshot branch created its one honest `"inconclusive"` outcome but returned before calling `markEvaluated()`. Because the run's `evaluationStatus` stayed `"pending"` forever, every repeated trigger invocation would re-pick it up and create *another* `"inconclusive"` row — unbounded growth, once per trigger tick, for the lifetime of the deployment. Fixed: the branch now calls `markEvaluated()`, and a repeat invocation that finds an existing outcome reuses it instead of creating a second one.

**Bug 2 — partial resolution duplicated finalized verdicts.** In a multi-hypothesis run, if hypothesis A resolved (`validated`) but hypothesis B's window hadn't closed yet, the run correctly stayed `"pending"` — but the *next* trigger invocation re-evaluated **every** hypothesis in the run again, including A, appending a second `validated`/`invalidated` row for the same real event. This would have silently inflated `sampleSize` with duplicates. Fixed: before evaluating, the evaluator now looks up existing outcomes for the run and skips (reuses) any hypothesis that already has a finalized (`validated`/`invalidated`) verdict. `pending`/`inconclusive` results remain retryable on purpose (see §6).

**Secondary finding — "pending" outcome rows were persisted despite the spec saying they shouldn't be.** The D2.5.4 spec (§1) states a still-open prediction window "produces no outcome row yet." The code persisted one anyway on every call. This meant a 20-hour prediction window hit by a trigger every 15 minutes would accumulate ~80 duplicate `"pending"` rows before ever resolving. Fixed to match the documented contract: a still-pending hypothesis is skipped entirely (no row), and the run is only marked evaluated once no hypothesis remains pending.

None of these three fixes touch evaluation *semantics* (what counts as validated/invalidated/inconclusive, the prediction-window formula, or the historical-candle lookup) — only *how many times and how durably* a result gets persisted.

## 4. Idempotency

| Case | Guarantee | Mechanism |
|---|---|---|
| Same run, same hypothesis, evaluated twice sequentially | Exactly one finalized outcome row | Application-level check: existing `validated`/`invalidated` outcomes are looked up before evaluating; a match is reused, never re-persisted. |
| Same run, no hypothesisSnapshot, evaluated twice | Exactly one outcome row, run flips to `evaluated` after the first call | Same lookup-and-reuse pattern applied to the no-snapshot branch; `markEvaluated()` is now always called. |
| Still-pending hypothesis, evaluated repeatedly before its window closes | Zero rows persisted per attempt | No row is created at all for a `"pending"` result (§3, secondary finding); the run simply stays `"pending"`. |
| Two evaluator invocations racing on the exact same (run, hypothesis) | Exactly one finalized row survives | DB-level backstop — see §5. |
| `inconclusive` result (provider outage, insufficient historical data) | Retries are allowed and expected; duplicate `inconclusive` rows are harmless | Deliberately excluded from the idempotency guard — see §5's migration comment. `inconclusive` never counts toward `sampleSize`. |

## 5. Concurrency

Two layers, matching the sprint's "use the existing DB model and transaction mechanisms — do not introduce Redis/Kafka" instruction:

1. **Application-level read-then-skip** (§4) closes the common case (sequential repeated trigger calls, e.g. a cron firing every N minutes).
2. **DB-level partial unique index** (`prisma/migrations/20260813090000_add_outcome_idempotency_guard/migration.sql`) is the backstop for a genuine race — two evaluator invocations overlapping in time (a scheduler and a manual admin trigger firing together, or a retry racing the original):

   ```sql
   CREATE UNIQUE INDEX "intelligence_analysis_outcomes_finalized_unique"
   ON "intelligence_analysis_outcomes" ("analysisRunId", "hypothesisId")
   WHERE "hypothesisId" IS NOT NULL
     AND "status" IN ('validated', 'invalidated');
   ```

   Scoped to only the two verdicts that matter for `sampleSize`. `pending`/`inconclusive` are excluded so retries are never blocked. When the second concurrent insert hits this constraint, `HypothesisOutcomeEvaluatorService` catches the unique-constraint violation (Prisma error code `P2002`), re-reads the winning row, and returns it — the losing invocation reports success with the winner's verdict, not an error.

   This migration was applied to the real database (`prisma migrate deploy`, following this repo's established hand-written-migration convention — `prisma migrate dev` is never used here, see the pgvector shadow-DB gotcha in earlier sprint notes) and verified live: a direct duplicate insert for the same `(analysisRunId, hypothesisId, status='validated')` was confirmed rejected, and two genuinely concurrent `evaluateAnalysisRun()` calls (`Promise.all`) against the same resolved hypothesis were confirmed to converge on exactly one finalized row.

## 6. Trigger architecture

The repository has no existing scheduler, no `vercel.json`, no background-worker infrastructure of any kind (confirmed during D2.7.8's audit and re-confirmed here). Per the sprint's own comparison of Option A (scheduled job) vs. B (protected route) vs. C (hybrid), **C was chosen**: a single protected API route, `POST /api/private/admin/intelligence/evaluate-outcomes`, reachable two ways:

1. **`Authorization: Bearer <INTELLIGENCE_EVALUATION_CRON_SECRET>`** — for an external scheduler (Vercel Cron, an external cron pinger, a scheduled CI job — deployment-agnostic, since this repo commits to no specific hosting platform). Always runs the full bounded batch; never accepts a client-supplied `userId` (see §7).
2. **An authenticated admin session** (`requireAdmin`, the exact gate every other `/api/private/admin/*` route already uses) — runs the same batch, or, for support/debugging, a single user's evaluation via `?userId=`.

Both paths call the same two functions in `services/intelligence/orchestration/scheduled-outcome-evaluation.service.ts`, which in turn call the *unmodified* `evaluatePendingAnalysisRunsForUser()` (D2.6.5) — there is exactly one evaluation implementation, never two.

`runScheduledOutcomeEvaluation({ maxUsers, perUserLimit })`:
- Enumerates up to `maxUsers` distinct userIds with at least one pending run (`listUserIdsWithPendingEvaluationRuns`, new in D2.7.9, oldest-pending-first, using the existing `@@index([evaluationStatus])` — no new index needed for this query).
- Calls `evaluatePendingAnalysisRunsForUser(userId, perUserLimit)` once per user, **inside a try/catch** — one user's failure (provider outage, malformed data, DB hiccup) is recorded in `summary.errors` and does not stop or corrupt any other user's evaluation.
- Returns `{ usersScanned, usersProcessed, usersFailed, outcomesCreated, errors }` — honest counts, no fabricated success.

## 7. Security

- The cron-secret path never reads a client-supplied `userId` — a leaked/shared secret could otherwise become an impersonation vector. It always runs the bounded, server-decided batch.
- The admin path reuses `requireAdmin` verbatim — no new auth mechanism.
- The secret is compared with `crypto.timingSafeEqual` (never `===`), matching the standard constant-time-comparison pattern.
- `INTELLIGENCE_EVALUATION_CRON_SECRET` is optional (mirrors `lib/payments/env.ts`'s pattern for Stripe/NOWPayments): absent means the cron-secret path is disabled and the route falls back to admin-only — never "accept anyone."
- Batch size is hard-capped (`MAX_USERS_CAP = 200`, `PER_USER_LIMIT_CAP = 100`) regardless of what a caller requests via query params — prevents unrestricted bulk execution even from an authenticated caller.
- No secret is hardcoded or committed; `.env.example` documents the variable as a placeholder only.

## 8. Scope boundary: the D2.5.1 evaluator remains unwired

`evaluatePendingAnalysisRun()` only processes runs whose `hypothesisSnapshot` is non-null. A run with no snapshot (pre-D2.5.4, or a run with no real hypothesis) is — by the *existing, unmodified* D2.5.4 code's own design — left to a separate, older evaluator (`services/intelligence/memory/outcome-evaluator.service.ts`, D2.5.1), which itself has no production trigger and, per its own header comment, can only ever produce `pending`/`inconclusive` (never `validated`/`invalidated`, since it predates the Hypothesis Engine). D2.7.9 does not wire that evaluator up: it is structurally incapable of ever affecting `sampleSize` (which only counts `validated`+`invalidated`), so doing so would add trigger surface without moving the metric this sprint targets. This is a deliberate scope boundary, not an oversight — noted here for a future sprint that might want it for other reasons (e.g. general observability).

## 9. Known limitation: Twelve Data's bounded window

Unchanged from D2.7.8's finding: `TimeSeriesProvider.getTimeSeries()` returns only the latest N candles as of *now* — no date-range query capability. A hypothesis whose evaluation boundary has receded too far into the past for the fetched window to reach will honestly resolve to `inconclusive` (`source: "insufficient-historical-data"`), never fabricated. This sprint does not change the provider. In this development environment specifically, `TWELVEDATA_API_KEY` is unset, so every forex symbol (EURUSD, GBPUSD, USDJPY, etc.) currently resolves through this same honest `inconclusive` path in live testing; only crypto symbols (routed through Binance, which needs no key) can reach a real `validated`/`invalidated` verdict here. A production deployment with a real Twelve Data key will not have this limitation for forex/commodities.

## 11. Operational note

This route is a production seam, not a fully automated pipeline yet: nothing in this deployment calls it automatically. An operator (or a platform-level scheduler, once one is configured against this route) still needs to invoke it periodically. This is intentional — D2.7.9's brief was to make the evaluator *callable* safely and correctly, not to add scheduling infrastructure. Historical validation will not become "fully reliable" the moment this ships; it becomes *able* to accumulate real evidence, which will take real time and real triggering.
