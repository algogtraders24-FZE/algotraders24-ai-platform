# D2.8.7 — Microstructure Intelligence Context Integration

**Status:** Implemented and tested. **Baseline:** D2.8.6 (`424ff0f`).
**Scope:** Make the already-implemented D2.8.5/D2.8.6 `MicrostructureSnapshot` available to `RealTimeIntelligenceService`/`VerifiedRealTimeIntelligenceContext`, opt-in, provider/instrument-attributed, fabrication-safe. **No new microstructure engine, no second `IntelligenceContext`, no scoring change, no route, no WebSocket, no trading logic.**

---

## 1. Existing architecture (Phase 1 audit findings)

Traced fresh, not assumed:

- `RealTimeIntelligenceService.build()` (`services/intelligence/orchestration/real-time-intelligence.service.ts`) is the single orchestrator turning a trader's question into a `VerifiedRealTimeIntelligenceContext`: query parsing (D2.6.2) → market data via `sharedMarketData` (D2.6.3/D2.6.4) → `MarketStateService`/`RegimeService`/`HypothesisService` (D2.5.2/D2.5.3) → the frozen 15D pipeline (evidence/risk/confidence) → `HistoricalValidationService` (D2.5.4) → `IntelligenceEnvelopeService` (D2.5.5) → `IntelligenceQueryContextService` (D2.6.1/D2.6.2) → `IntelligenceAnalysisRunService` persistence (D2.5.1). Fully deterministic — no Gemini/Claude/OpenAI call anywhere in this file.
- `VerifiedRealTimeIntelligenceContext` (`types/real-time-intelligence.ts`) is the single verified output object every downstream presenter/route reads from.
- `IntelligenceChatContextService.resolve()` (`services/intelligence/chat/intelligence-chat-context.service.ts`) is a thin pass-through: it calls `RealTimeIntelligenceService.build()` and returns the result unchanged (plus best-effort conversation-context persistence). It required **zero changes** — any new field on `VerifiedRealTimeIntelligenceContext` flows through automatically.
- `AIIntelligencePresenter.present(envelope: IntelligenceEnvelope, userQuestion: string)` (`types/intelligence-envelope.ts`) is documented in that file's own header as a **permanent architectural rule**, and is used identically across ~80 call sites (`intelligence-presentation.service.ts`, `ai-response-integrity.service.ts`, `ai-presenter-orchestrator.service.ts`, every relevant `validate-*.ts`). It takes only an `IntelligenceEnvelope` — never the richer `VerifiedRealTimeIntelligenceContext` — and this sprint does not change that.
- `DecisionContextService.build(envelope: IntelligenceEnvelope)` (`services/intelligence/decision/decision-context.service.ts`) likewise takes only `IntelligenceEnvelope`, not the richer context where `microstructure` now lives.
- D2.8.5's `MicrostructureSnapshotService.getSnapshot(provider, request)` and D2.8.6's `services/microstructure/shared-instance.ts` (`binanceMicrostructureProvider`, `microstructureSnapshots`) already form a complete, provider-neutral, production-consumable boundary — this sprint reuses both verbatim.
- `getCanonicalInstrument(symbol).providerMappings` (`lib/market-data/instrument-catalog.ts`) already records, per real catalog entry, which providers cover which capabilities — BTCUSD/ETHUSD's entries include a real `{ provider: "binance", providerSymbol: "BTCUSDT"/"ETHUSDT", supportedCapabilities: ["quote", "candles"], verified: true }` mapping. `runCrossProviderValidation()` already uses this exact mechanism to prove a second provider's coverage for a different purpose — this sprint reuses the identical check for microstructure instrument safety rather than maintaining a second symbol allowlist.

## 2. Integration point

`RealTimeIntelligenceService.build()`, immediately after the existing optional `crossProviderValidation` block and before analysis-run persistence — the narrowest point that already has the resolved `symbol` and is already the single place `VerifiedRealTimeIntelligenceContext` gets assembled. No second orchestrator, no second `IntelligenceContext`, no second market-data provider chain, no change to provider priority order (`TwelveDataProvider → AlphaVantageProvider → BinanceProvider → AngelOneProvider`, reconfirmed unchanged by test 17 of the new validation script).

## 3. Context contract

`VerifiedRealTimeIntelligenceContext` (`types/real-time-intelligence.ts`) gained exactly one new optional field:

```ts
microstructure?: MicrostructureSnapshot;
```

`MicrostructureSnapshot` (and every type/state it composes — `RawMicrostructureEvidence`, `DerivedMicrostructure`, `MicrostructureField<T>`, `CapabilityState`, `MicrostructureFreshnessStatus`) is D2.8.5's own type, imported and reused verbatim — nothing was duplicated. `RealTimeIntelligenceRequest` gained one new optional flag:

```ts
includeMicrostructure?: boolean;
```

mirroring the existing `crossProviderValidation?: boolean` field's own reasoning: microstructure is additive evidence, never fetched by default, so a request that doesn't ask for it pays no extra latency/cost. `RealTimeIntelligenceDeps` gained two injectable, test-only overrides (`microstructureProvider`, `microstructureService`) that default to D2.8.6's real shared instances.

## 4. Provider attribution

Every `MicrostructureSnapshot.provider` field is the real originating venue string (`"binance"`), copied straight through from D2.8.5/D2.8.6's own `RawMicrostructureResult.provider` — never renamed, never generalized. `formatMicrostructureEvidence()` (new, `lib/microstructure/microstructure-presentation.ts`) prints `Provider: binance` and `Instrument: BTCUSD` as the first two lines of any rendered evidence block, and its final line is an explicit scope statement: `Evidence scope: binance BTCUSD order book only - not global market liquidity.` — preserving D2.8.2's own rule that a single venue's order book is never presented as a market-wide fact.

## 5. Instrument safety

`fetchMicrostructure(symbol)` (new private method on `RealTimeIntelligenceService`) only ever calls the microstructure provider when `getCanonicalInstrument(symbol)?.providerMappings` contains an entry for `this.microstructureProvider.name` with `"quote"` in `supportedCapabilities` — the exact same real, existing mechanism `runCrossProviderValidation()` already uses, never a second hardcoded symbol list. Today this is true only for BTCUSD/ETHUSD (Binance). Verified via test 14/14b: XAUUSD and EURUSD never even trigger a call to the microstructure provider (`callCount` stays `0`), let alone receive fabricated or substituted evidence.

## 6. Freshness semantics

Snapshot-level freshness (`fresh`/`stale`/`unknown`/`invalid`) is D2.8.5's own `assessMicrostructureFreshness()`, reused unmodified via `MicrostructureSnapshotService.getSnapshot()`. This sprint adds no second freshness computation. Verified via test 12: a snapshot whose evidence timestamp is ~27 minutes old (past crypto's 30-second threshold) is honestly reported `stale`, never silently presented as fresh.

## 7. Unavailable / invalid semantics

Every `CapabilityState` value (`available`/`unavailable`/`not_supported_by_provider`/`stale`/`invalid`) produced by D2.8.5's calculation layer flows through unchanged into `VerifiedRealTimeIntelligenceContext.microstructure`. Nothing in the D2.8.7 integration layer converts an unavailable/invalid field into a number. Verified via tests 10/11/13/18: missing aggressor evidence leaves `volumeDelta` `unavailable` (never `0`); an entirely empty raw evidence payload leaves every derived field non-`available` with no `value`; a crossed-market bid/ask is preserved as `invalid`, not repaired; a JSON scan of an all-unavailable snapshot's `derived` object contains no literal `"value":0`.

## 8. DecisionContext interaction

**`DecisionContextService` was NOT modified.** `DecisionContextService.build()` takes only an `IntelligenceEnvelope`, and `IntelligenceEnvelope`/its scoring are explicitly protected files this sprint must not touch. Its existing, honest `missingInformation` entries — `"Liquidity zone data is not implemented..."`, `"Execution risk (spread/slippage/latency) is not integrated..."`, `"Liquidity risk (order book depth) has no data source..."` — remain exactly as D2.6.1 defined them, completely unaffected by whether `includeMicrostructure` was set on the same request. This is a deliberate, conservative answer to Phase 8's "determine whether the current context can safely attach real microstructure evidence": it can, structurally, once a future sprint chooses to widen `DecisionContextService`'s input beyond `IntelligenceEnvelope` — but doing that widening was out of this sprint's scope (no DecisionContext scoring/semantics change, per Phase 15's protected-systems list). Verified via test 19 (reusing the real, unmodified `DecisionContextService`) and by rerunning the full, unmodified `validate:decision-context` suite (16/16 pass).

## 9. AI presenter interaction

`formatMicrostructureEvidence(snapshot: MicrostructureSnapshot): string[]` (new, pure, `lib/microstructure/microstructure-presentation.ts`) proves the safety property Phase 9 requires: it always states provider/instrument/freshness, and for every field prints either the real value (`Bid: 63189.99`) or the honest state word (`Volume delta: unavailable`) — never a guessed number, never `"neutral"`, never a fabricated `0`. Verified via test 20.

**This formatter is NOT wired into the live `AIIntelligencePresenter.present(envelope, userQuestion)` call this sprint** — see §13 "Known limitations."

## 10. Multi-provider future compatibility

Nothing in `VerifiedRealTimeIntelligenceContext.microstructure`, `RealTimeIntelligenceRequest.includeMicrostructure`, or `fetchMicrostructure()` hardcodes "Binance" into a generic field name — the field is typed as `MicrostructureSnapshot`, whose own `provider: string` field is what carries venue identity (D2.8.5's own design). A future Angel One/dxFeed/Databento/Dukascopy microstructure adapter would plug into the exact same `MicrostructureProvider` interface and `microstructureProvider`/`microstructureService` injection points without any change to this sprint's contract shape. No empty adapters or speculative interfaces were added for those providers — only the existing, already-proven extensibility point was preserved.

## 11. Degradation / failure behavior

`fetchMicrostructure()` is called only when `request.includeMicrostructure` is true, and:

- returns `undefined` immediately (never calling the provider) when the instrument isn't Binance-mapped (§5);
- wraps the actual fetch in `try/catch`, returning `undefined` on any error (network failure, timeout, malformed response, provider throw) — never propagating the error, never failing the rest of `build()`.

Verified via test 15: a provider that always throws `MarketDataProviderError` still yields `status: "resolved"` with a real `envelope`, and `microstructure: undefined`. The full 12-scenario failure matrix the brief calls for (available/unavailable/timeout/malformed/invalid bid-ask/crossed market/stale/unsupported instrument/missing aggressor/missing order book/partial data/provider error) is covered jointly by this sprint's own test 15 plus D2.8.5's `validate:microstructure-foundation` (24/24) and D2.8.6's `validate:microstructure-runtime` (19/19), both rerun clean as part of this sprint's regression (§14 of the brief) — none of that behavior was changed, so it was verified, not re-implemented.

## 12. Fabrication safeguards

Repo-wide grep for `liquidityZones|volumeDelta|executionRisk` found only the same pre-existing, honest "not implemented" declarations already audited in D2.5.2/D2.5.5 (`intelligence-score.service.ts`, `market-state.service.ts`, their type files) — unmodified by this sprint, not a new finding. A targeted grep for `volumeDelta\s*[:=]\s*0|spread\s*[:=]\s*0|bid\s*[:=]\s*0` across the repo returned zero matches — no unavailable→zero fallback exists anywhere. `formatMicrostructureEvidence()` was specifically designed and tested (test 20) to never substitute a neutral/zero value for an unavailable field. No liquidity zones, no fake order-book data, no estimated spread, and no AI-prompt instruction telling a model to fill in missing microstructure data were introduced.

## 13. Explicit non-goals (this sprint)

- **No API route added.** D2.8.6 deliberately shipped no route; this sprint's own success criteria (context field present, attributed, safe) are fully satisfiable through the orchestrator/service layer alone. **No API route added.**
- **No WebSocket** — the fetch path is `MicrostructureSnapshotService.getSnapshot()` → `BinanceProvider.getMicrostructureSnapshot()`, REST-only, identical to D2.8.6.
- **No trading logic** — no BUY/SELL recommendation, entry signal, automated trading, SL/TP, alert, or position sizing exists anywhere in the new code; microstructure is additive evidence only.
- **No Intelligence Score change** — `IntelligenceScoreService`'s formula/weights/thresholds were not touched; test 16 proves two otherwise-identical requests (with and without `includeMicrostructure`) produce a byte-identical `intelligenceScore`.
- **No DecisionContext scoring change** — see §8.
- **No live-presenter wiring** — see §9 and "Known limitations" below.

### Known limitations

`formatMicrostructureEvidence()` exists and is tested, but is not yet called from `GeminiIntelligencePresenter`/`AIPresenterOrchestratorService`/any live LLM prompt. Doing so would mean either (a) extending the protected `AIIntelligencePresenter.present(envelope, userQuestion)` signature to accept a second, optional evidence source, or (b) building a new wrapping layer around it — both real design decisions with their own testing/architecture-review needs, deliberately left to a future, separately-scoped sprint rather than folded into this one's "make evidence reach the context" mandate.
