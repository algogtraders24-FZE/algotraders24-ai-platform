## 4. A real bug found and fixed by this sprint's own real-data run

The first real run against BTCUSD/ETHUSD produced **81/81 observations classified `insufficient_evidence`** — every single one, with basis "freshness is stale." Investigating rather than accepting this at face value found two real, related bugs:

1. **Truncation**: Binance's aggTrades endpoint caps a response at 1000 rows. BTCUSDT/ETHUSDT are liquid enough that a 15-minute lookback window almost always exceeds that cap, silently returning only the *earliest* slice of the window — dropping every trade closest to the hypothesis's own creation time. Fixed by (a) shortening `AGG_TRADES_LOOKBACK_MS` to 2 minutes (empirically verified via a live call to stay safely under the cap: ~149 BTCUSDT / ~116 ETHUSDT trades), and (b) adding an honest `aggtrades-window-truncated` rejection reason so a future truncated window is never silently used.
2. **Timestamp source**: The snapshot's own `timestamp` was set to the *last returned trade's* timestamp rather than the query's own end boundary (`createdAt`). Combined with truncation, this made freshness depend on how recently a trade happened to print rather than on the deliberate "as of createdAt" boundary the query itself defines. Fixed by using `createdAt` as the snapshot's timestamp directly — architecturally correct regardless of truncation, since the snapshot is deliberately "as of" that instant by construction.

A third, smaller issue was also found and fixed in the leakage audit itself: the original `stale-snapshot-reuse` check flagged *any* reuse of `(symbol, snapshot timestamp)` across observations — but multiple hypotheses generated from the **same** analysis run legitimately and correctly share one microstructure snapshot (they came from the same market read). Fixed to only flag reuse across **different** `analysisRunId`s.

After both fixes, the real run produced a healthy, plausible distribution (see §6) — this is reported as a real methodological correction, not glossed over.

## 5. Outcome definition

`OUTCOME_NEUTRAL_BAND_PCT = 0.15` (%) — reused as a fixed, documented constant, decided before any group statistic was computed, never tuned against this sprint's own results. For a BUY (bullish) hypothesis: `directionalOutcome = "positive"` when forward return > +0.15%, `"negative"` when < −0.15%, else `"inconclusive"`. Reversed for SELL (bearish) hypotheses. `MIN_GROUP_SAMPLE = 30` is reused verbatim from `HistoricalValidationService.MIN_HISTORICAL_VALIDATION_SAMPLE` (D2.5.4) — no second, competing threshold invented.

## 6. Real runtime results (this report's own evidence)

- **Observations considered**: 85 real AT24 analysis runs (BTCUSD: 73, ETHUSD: 12), 2026-08-11 to 2026-08-17.
- **Observations usable**: 63.
- **Observations rejected**: 22 (`no-hypotheses-in-snapshot`: 4, `aggtrades-window-truncated`: 18 — the truncation guard now correctly excludes rather than silently biases these).
- **Duplicates removed**: 0. **Leakage findings**: 0.
- **Group counts**: CONFIRMS 31, CONTRADICTS 15, NEUTRAL 16, INSUFFICIENT_EVIDENCE 1.
- **Chronological split**: SPLIT succeeded (42 train / 18 test, split at 2026-08-12T15:15:41Z — never randomly shuffled).
- **Comparisons**: all 8 (CONFIRMS-vs-CONTRADICTS and CONFIRMS-vs-NEUTRAL, across all 4 windows) returned `INSUFFICIENT_SAMPLE` — CONTRADICTS (13-15) and NEUTRAL (16) never cleared the 30-sample minimum, even though CONFIRMS (29-31) came close.
- **Final classification**: **INSUFFICIENT_SAMPLE**.

## 7. Has microstructure demonstrated predictive value?

**No conclusion can be honestly drawn yet.** 63 usable observations, split across 4 relationship states and evaluated at 4 forward windows, does not clear the 30-per-group minimum this research itself requires before comparing means. This is not evidence of "no edge" (`EDGE_NOT_SUPPORTED`) — it is evidence of *not enough data to know either way* (`INSUFFICIENT_SAMPLE`). The CONFIRMS group is closest to being usable (29-31 across windows); CONTRADICTS and NEUTRAL are further away. Continued production activation (already shipped in D2.8.11-D2.8.13) will accumulate more real observations over time; this research should be re-run periodically as that history grows, using the exact same fixed, pre-registered outcome definition and sample thresholds documented here — never re-tuned in hindsight.

## 10. Known limitations

- Historical depth-imbalance is permanently unavailable via this method (a genuine external Binance API limitation, not an AT24 gap) — this research's directional signal is volume-delta-only, a narrower basis than D2.8.11's live two-signal formula uses when depth is also available.
- The 2-minute aggTrades lookback window is shorter than the live production path's own (unbounded, "last N trades returned") window — a deliberate, documented trade-off to stay under Binance's 1000-row response cap for these two liquid pairs; it is not tuned against any outcome result.
- `IntelligenceAnalysisOutcome` (D2.5.4) records use a different resolution window per-hypothesis than this sprint's fixed +1/+3/+5/+10 candle windows — the two are not directly comparable without translation, and this sprint did not attempt to reconcile them.
- Sample size is small because production microstructure evidence only began being computed in this same session (D2.8.11, hours before this sprint) — accumulation will improve with time, not with a larger one-off backfill (no larger backfill is possible: Binance's aggTrades retention and the 1000-row cap jointly bound how much can ever be reconstructed for a fixed historical window size).
