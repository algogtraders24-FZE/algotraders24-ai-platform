# D2.6.1 — Trader Intelligence Decision Context

**Status:** Implemented and tested. This is the authoritative contract for the future real-time AI conversation / Intelligence Workspace integration.
**Scope:** A deterministic, trader-facing restatement of an existing `IntelligenceEnvelope` (D2.5.5) into structured decision context. No LLM, no Gemini/Claude/OpenAI integration, no new indicator/risk/regime computation, no trading signal, no broker execution, no notifications, no UI.

---

## 1. Purpose

Every D2.5.x sprint produced one real, deterministic layer of intelligence, culminating in the D2.5.5 `IntelligenceEnvelope` - a verified bundle of `MarketState`, `Regime`, `Hypothesis[]`, `EvidenceBundle`, `RiskProfile`, `HistoricalValidation`, and `IntelligenceScore`. Nothing until now restated that bundle in the shape a trader actually needs to make a decision: what's happening, why, what could prove it wrong, and how much to trust it. `DecisionContextService` (`services/intelligence/decision/decision-context.service.ts`) is that restatement layer - a pure transform, not a new source of facts.

## 2. Product meaning

**Permanent principle**: *"AT24 does not tell the trader what to believe. It shows what the available evidence supports, what contradicts it, what could invalidate it, and how complete the intelligence is."* This is a decision-intelligence system, not a signal generator. `IntelligenceDecisionContext` never contains a BUY/SELL instruction, a target price, a stop loss, a win-rate claim, or a probability of profit/direction - see §16 for the enforced, permanent list and how it's verified.

## 3. DecisionContext schema

`types/intelligence-decision-context.ts#IntelligenceDecisionContext`:

```
symbol, timeframe, state (DecisionState)
currentState        - DecisionCurrentState
regimeContext       - DecisionRegimeContext
primaryHypotheses[] - DecisionHypothesisContext[]
supportingEvidence[], opposingEvidence[], unresolvedConflicts[]
riskContext         - DecisionRiskContext
historicalContext   - DecisionHistoricalContext
intelligenceScore   - IntelligenceScore (D2.5.5, reused verbatim)
invalidationConditions[]
monitoringItems[]
missingInformation[]
summaryBasis[]
generatedAt, pipelineVersion, intelligenceEngineVersion
```

Every sub-object carries its own `basis: string[]` - see §17 (provenance is a hard, tested requirement, not a convention).

## 4. Source mapping

`DecisionContextService.build(envelope: IntelligenceEnvelope)` is the single entry point - it takes **one input**, the already-verified envelope, and derives everything else. No field is computed from raw candles, a fresh provider call, or an LLM.

| DecisionContext field | Source | Recomputed? |
|---|---|---|
| `currentState` | `envelope.marketState` | No - direct passthrough of `snapshot`/`technical`/`structure`/`dataQuality` |
| `regimeContext` | `envelope.regime` | No - `Regime.confidence`/`.basis` reused verbatim |
| `primaryHypotheses` | `envelope.hypotheses` | No - `Hypothesis.statement.claim` is D2.5.3's own deterministic template text, never rewritten |
| `supportingEvidence`/`opposingEvidence` | deduplicated union of every hypothesis's own `supportingEvidence`/`opposingEvidence` | Dedup only (by `type+symbol+claim`), no re-classification |
| `unresolvedConflicts` | `envelope.evidence?.conflicts` filtered to `resolution === "unresolved"` | Filter only |
| `riskContext` | `envelope.risk` | No - `RiskProfile.categories` reused verbatim |
| `historicalContext` | `envelope.historicalValidation` | No - `HistoricalValidation` fields reused verbatim |
| `intelligenceScore` | `envelope.intelligenceScore` | **No - object identity preserved, never recalculated** (verified directly: `dc.intelligenceScore === envelope.intelligenceScore`) |
| `invalidationConditions` | flattened `Hypothesis.statement.invalidationCondition` per hypothesis | Flatten only |
| `monitoringItems`, `missingInformation`, `state` | derived from the above | Deterministic rules only - see §5, §12, §13 |

## 5. State classification

`DecisionState = "well-supported" | "partially-supported" | "conflicted" | "insufficient-intelligence"` - describes the **quality of the decision context itself**, never market direction. Explicit, versioned, documented rules (`decision-context.service.ts`'s `classifyState()`), evaluated in this exact order:

1. **`insufficient-intelligence`** — `regime.regimeType === "insufficient-data"` **or** `intelligenceScore.overallScore === undefined`. Critical data/regime/evidence is unavailable; the market cannot currently be characterized reliably.
2. **`conflicted`** — the envelope's own already-computed `intelligenceScore.components.evidenceAgreement` is available and scores below `CONFLICTED_EVIDENCE_AGREEMENT_THRESHOLD = 50`. Reuses D2.5.5's Evidence Agreement component (real conflicting-evidence-fraction signal) rather than inventing a second, parallel conflict-counting formula.
3. **`well-supported`** — `overallScore >= WELL_SUPPORTED_SCORE_THRESHOLD = 70` (and not already caught by rule 2).
4. **`partially-supported`** — everything else: real intelligence exists but is incomplete.

Both thresholds are explicit, documented "V1 heuristic" constants - not statistically tuned, same honesty-labeling discipline as D2.5.5's own score ceilings/weights. `summaryBasis` always states which rule fired and why.

## 6. Hypothesis handling

Each `Hypothesis` becomes a `DecisionHypothesisContext` - `type`, `claim` (D2.5.3's own template string, reused verbatim), `predictionWindow`, `invalidationCondition`, `requiredEvidence`, `supportingEvidence`, `opposingEvidence` - a structural restatement, never a signal. `primaryHypotheses` is legitimately `[]` for 3 of 10 regime types (D2.5.3) - never fabricated to avoid an empty array, verified directly (`hypotheses: []` produces `primaryHypotheses: []`, `invalidationConditions: []`, no fabricated scenario).

## 7. Evidence handling

Top-level `supportingEvidence`/`opposingEvidence` are the deduplicated union across every hypothesis's own evidence arrays - the only supporting/opposing classification this envelope carries (D2.5.3's own hypothesis-generation logic), never re-derived independently. Deduplication is by `type+symbol+claim`, matching the same key used throughout D2.5.5's own evidence-quality/agreement formulas.

## 8. Conflict handling

`unresolvedConflicts` is `envelope.evidence?.conflicts` filtered to `resolution === "unresolved"` - real, already-detected `EvidenceConflict`s from the 15D Evidence engine, **never auto-resolved here**. Verified directly: a fixture with 2 unresolved conflicts produces exactly 2 `unresolvedConflicts` entries and drives `state` to `"conflicted"` via the Evidence Agreement threshold (§5) - the system prefers "evidence is mixed" over an artificially decisive answer, exactly as required.

## 9. Risk handling

`riskContext` is a direct passthrough of `RiskProfile.categories`, split into `categoriesWithEvidence`/`categoriesUnavailable` by `RiskCategoryScore.basis.length > 0` - the same honest signal D2.5.5's `riskAwareness` component already uses, not a new formula. `liquidity`/`execution` are structurally always in `categoriesUnavailable` (`RiskEngineService`'s own permanent design - no data source exists in this platform for either) and are never presented as a failure, only as an honest count. When no `RiskProfile` was supplied at all, `dataAvailable: false` and `categories: []` - never a fabricated risk level, never "this trade is safe."

## 10. Historical validation

`historicalContext.status` is one of three real states, never collapsed:

- `"unavailable"` — `envelope.historicalValidation` is `undefined` (no segment exists at all for this symbol/timeframe/regime/hypothesis combination).
- `"insufficient-sample"` — a segment exists but `validatedRate` is `undefined` (D2.5.4's own `MIN_HISTORICAL_VALIDATION_SAMPLE` gate wasn't met). `validatedRate` stays `undefined`, never manufactured.
- `"available"` — `validatedRate` is defined; all D2.5.4 fields (`sampleSize`/`validatedCount`/`invalidatedCount`/`inconclusiveCount`/`validatedRate`/`minSampleSize`) are reused verbatim.

## 11. Invalidation conditions

`invalidationConditions[]` flattens every hypothesis's own `statement.invalidationCondition` into one trader-facing list, each item carrying `hypothesisId`, `hypothesisType`, `description`, `field`, `comparator`, `referenceValue`, and a `basis` note tying it back to the originating hypothesis. This answers "what would make this current view wrong?" directly from D2.5.3's own structured, machine-checkable condition - never a new interpretation.

## 12. Monitoring items

Derived **only** from real, currently-true conditions on the envelope - never an arbitrary or hypothetical alert, and never a scheduled/notified alert (no notification infrastructure exists or is implied). Categories: `trend` (only when `structure.trend.direction` is actually known - **not** merely when the `trend` object exists, since `MarketStateService` always returns a real `trend` object even when direction is unavailable, with its own honest "unavailable" basis - see the caught bug below), `recent-range`, `volatility`, `evidence-conflict`, `hypothesis-invalidation` (one per real hypothesis), `historical-sample` (only when historical context isn't yet `"available"`), `data-quality` (only when the band isn't `"high"`). Every item carries a non-empty `basis`.

**Bug caught by the empirical test checklist, not by design review**: the first implementation checked `if (marketState.structure?.trend)` truthiness to decide whether to emit a `"trend"` monitoring item - but `computeTrend()` in `market-state.service.ts` always returns a real object (`{basis: [...]}`) even when EMA20/EMA50 couldn't be computed, so this check was always true and fabricated a `"Monitor trend condition (currently 'undetermined')"` item even with zero real trend information. Fixed by checking `trend?.direction !== undefined` instead (the real signal for whether a trend condition genuinely exists to monitor). The same fix was applied to `missingInformation`'s equivalent check. This is exactly the kind of bug this project's empirical-verification methodology (a locked, checklist-driven test suite run against real services before considering a sprint done) exists to catch.

## 13. Missing information

Three distinct, never-collapsed kinds (`MissingInformationKind`):

- **`"unsupported"`** — this platform has no data source for this at all, permanently (liquidity zones, volume delta, execution risk, liquidity risk - the same permanent gaps D2.5.2/D2.5.5 already documented). Always present, every run - these are structural facts about the platform, not per-analysis gaps.
- **`"unavailable"`** — the input simply wasn't supplied to this particular analysis (no `EvidenceBundle`/`RiskProfile`/`HistoricalValidation` passed to `IntelligenceEnvelopeService.build()`).
- **`"insufficient-data"`** — the input was attempted but real data was too thin (e.g. too few candles for `recentRange`/RSI/ATR, or a historical sample below the minimum).

## 14. Intelligence Score integration

`intelligenceScore` is `envelope.intelligenceScore` by direct reference - never recalculated, never reinterpreted as trade probability. Verified with an object-identity assertion (`dc.intelligenceScore === envelope.intelligenceScore`), not just a value-equality check, to prove no copy-and-mutate path exists anywhere in this file.

## 15. AI Presenter boundary

`AIIntelligencePresenter` (D2.5.5, `types/intelligence-envelope.ts`) is completely unchanged by this sprint. The intended future chain is:

```
Verified Intelligence Envelope -> DecisionContext -> AI Presenter Interface -> Gemini / Claude / OpenAI
```

The LLM will eventually **explain** a `DecisionContext` in natural language for a specific trader question (§17's question-mapping table is the product contract for that future presenter); it must never **create** one. No concrete presenter wiring was added in this sprint, per its own stop condition.

## 16. Prohibited outputs

Permanently forbidden, anywhere in this file's output: `BUY NOW`/`SELL NOW`-style imperative instructions, a stated win rate (e.g. `"90% WIN RATE"`), a `TARGET = X` or `STOP LOSS = Y` field, or any probability-of-profit/directional-probability claim. Enforced two ways:

1. **Type-level**: `IntelligenceDecisionContext` has no `action`/`recommendation`/`signal`/`positionSize` field anywhere in its shape - structurally impossible to populate one.
2. **Regression test**: `scripts/validate-decision-context.ts` scans the full serialized output against a set of real regex patterns (`buy now`, `sell now`, `\d+%\s*win rate`, `target\s*=`, `stop loss\s*=`, `\d+%\s*chance`, `\d+%\s*probability`, `probability of profit\s*[:=]\s*\d`) - patterns chosen to catch an actual assertive claim while correctly *not* flagging this engine's own honest disclaimer text (D2.5.5's `IntelligenceScore.limitations` legitimately contains the phrase "...is never a probability of profit..." as a negation; a naive bare-substring search would have false-positived against the very sentence that enforces the rule).

## 17. Known limitations

- `evidenceAgreement`-based conflict detection for `state` classification only fires when an `EvidenceBundle` was supplied to the envelope; an envelope with no evidence at all cannot be classified `"conflicted"` even if a trader's intuition might expect it - this is intentional (no evidence means no known disagreement, not "assume conflict"), but worth remembering when interpreting a `"partially-supported"` result with no evidence context.
- `monitoringItems`/`missingInformation` are deterministic snapshots of the current envelope, not a live, re-evaluated watch list - re-running `build()` on a fresh envelope is required to get updated items; no polling/scheduling exists or is implied.
- The trader-question-to-field mapping (§18 below) is a documented product contract for a future presenter, not itself tested by natural-language output - this sprint produces no natural language at all (§18 of the brief: "do not create a chat response").

## 18. Future extension points

- A concrete `AIIntelligencePresenter` implementation (Gemini first, matching the existing restate-only precedent) that turns a `DecisionContext` into the trader's actual natural-language answer, strictly bound to the question-mapping table below.
- Multi-hypothesis historical validation (currently `IntelligenceEnvelope.historicalValidation` is single-valued, tied to D2.5.3's at-most-one-hypothesis-per-regime behavior - see the D2.5.5 spec's own limitations).
- Real-time re-computation triggers (a scheduler invoking `evaluatePendingAnalysisRun()` then rebuilding a fresh `DecisionContext`) - explicitly out of scope this sprint.

## Trader question mapping (product contract)

| Trader question | Answered by |
|---|---|
| "What's happening?" | `currentState` + `regimeContext` |
| "Why?" | `supportingEvidence` / `opposingEvidence` |
| "What could happen?" | `primaryHypotheses` |
| "What would prove this wrong?" | `invalidationConditions` |
| "What risks exist?" | `riskContext` |
| "Has this worked historically?" | `historicalContext` |
| "How much should I trust the analysis?" | `intelligenceScore` |
| "What information is missing?" | `missingInformation` |
| "What should I watch?" | `monitoringItems` |
