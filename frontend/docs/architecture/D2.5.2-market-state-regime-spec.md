# D2.5.2 — Market State & Regime Engine

**Status:** Implemented and tested. This is the authoritative reference for D2.5.3+.
**Scope:** `MarketState` assembly and deterministic `Regime` classification only. No Hypothesis Engine, no Memory changes, no ML, no Gemini involvement, no Wave/FFT/Hurst/Fractal/Chaos.

---

## 1. MarketState definition

`MarketState` (`types/intelligence-market-state.ts`) is a pure **observation** layer for one symbol/timeframe at one point in time. It contains only what was actually computed from real data — no recommendation, no instruction, no LLM content, no hypothesis, no conclusion presented as fact. Every optional field is optional because the real value genuinely wasn't available, never because a value was estimated and hidden behind "optional."

It is assembled by `MarketStateService.assemble()` (`services/intelligence/market-state/market-state.service.ts`), a **pure, synchronous, I/O-free function**: it takes an already-fetched `MarketSnapshot` and an already-fetched, oldest-first `Candle[]` and returns a `MarketState`. It never calls a provider, never calls Gemini, and never reads the network or the clock for anything except the `generatedAt` timestamp (which does not affect any classification decision).

## 2. Regime definition

`Regime` (`types/intelligence-regime.ts`) is a deterministic classification of a `MarketState`, produced by `RegimeService.classify()` (`services/intelligence/regime/regime.service.ts`). No trained model, no LLM, no probabilistic scoring. For identical `MarketState` input, `classify()` always returns an identical `regimeType`, `confidence`, and `basis`. Every classification carries a `basis: string[]` — plain, precise, human-readable statements citing the actual numbers involved, never a vague claim like "market looks bullish."

## 3. Data sources

| Field | Source | Reused from |
|---|---|---|
| `snapshot` | Real `MarketSnapshot` (already fetched by the caller) | `types/market-snapshot.ts` — unchanged |
| `technical.rsi14/ema20/ema50/atr14/macd/bollinger/volume` | Real OHLCV `Candle[]` | `lib/market-data/indicators.ts` — the exact same functions `services/ai/technical-context.service.ts` already uses, called directly, not reimplemented |
| `structure.trend` | Derived from `technical.ema20`/`ema50` + `snapshot.price` | New in D2.5.2, built only from the above |
| `structure.recentRange`/`breakoutSignal` | Derived from `Candle[]` highs/lows over a lookback window | New in D2.5.2 |
| `structure.volatilityBand`/`atrPercent` | `technical.atr14` as a percent of price | **Reused verbatim** from `services/ai/technical-context.service.ts`'s existing `RiskContext.volatility` logic (same 0.5%/1.5% thresholds) — not reinvented |
| `dataQuality` | Count of the 7 tracked indicators that computed | Reuses `types/technical-context.ts#DataConfidence` directly as the field's type |

No new provider, no new external dependency, no new API call was added. Everything above already existed in the codebase before this sprint except the `structure` derivations themselves, which are pure arithmetic over data that was already flowing through the platform.

## 4. Deterministic rules

### 4.1 Trend (`computeTrend`)
```
ema20AboveEma50 = EMA20 > EMA50
priceAboveEma20 = price > EMA20
direction =
  "up"       if ema20AboveEma50 AND priceAboveEma20
  "down"     if NOT ema20AboveEma50 AND NOT priceAboveEma20
  "sideways" otherwise (a genuine mixed signal)
  undefined  if either EMA is uncomputable
```
This is the exact worked example the sprint brief itself specifies ("EMA20 > EMA50, price above EMA20").

### 4.2 Recent range / breakout / breakdown (`computeRecentRange`, `computeBreakoutSignal`)
```
recentRange.high = max(high) over the 20 candles STRICTLY BEFORE the latest candle
recentRange.low  = min(low)  over the same window
breakoutSignal =
  "breakout"  if latestClose > recentRange.high
  "breakdown" if latestClose < recentRange.low
  undefined   otherwise, or if fewer than 21 candles exist
```
The latest candle is deliberately excluded from the range it's being compared against — otherwise a candle could never break its own high/low.

### 4.3 Volatility (`computeVolatility`)
```
atrPercent = (ATR14 / price) * 100
volatilityBand =
  "low"    if atrPercent < 0.5
  "medium" if atrPercent < 1.5
  "high"   otherwise
```
Copied verbatim from `services/ai/technical-context.service.ts`'s already-shipped `RiskContext.volatility` — the same market state is never described as two different volatility levels by two different parts of the platform.

### 4.4 Data quality (`computeDataQuality`)
7 tracked indicators (rsi14, ema20, ema50, atr14, macd, bollinger, volume). `computed` = how many are not `undefined`.
```
band =
  "insufficient" if computed === 0
  "low"          if computed <  3.5  (i.e. < total/2)
  "medium"       if computed <  7    (i.e. < total)
  "high"         if computed === 7
```

## 6. Regime precedence — and why it deviates from the brief's suggested order

Checked in this exact order; the **first match wins**:

1. **`insufficient-data`** — gate. Fires when none of `trend.direction`, `recentRange`, `volatilityBand` could be computed. Deliberately **not** tied to `dataQuality.band` directly: that count includes `volume`/`macd`/`bollinger`, which don't feed any regime rule — a market state where only `volume` was computable is still regime-`insufficient-data`, even though its `dataQuality.band` reads `"low"`, not `"insufficient"`. (Caught by an early test run against a 3-candle fixture and fixed before this was locked in — see the "Real bugs found" note at the end of this file.)
2. **`breakout`** / 3. **`breakdown`** — the most specific, highest-conviction discrete events. Checked before trend: a fresh break of a 20-bar range is more informative than "still trending."
4. **`high-volatility`** — a risk condition worth surfacing even over a live trend (whipsaw risk), so it's checked before trend rather than after.
5. **`trending-bullish`** / 6. **`trending-bearish`**
7. **`low-volatility`** — checked *after* trend, not before: a genuine trend is more useful information than "it's just quiet." (Asymmetric with high-volatility's placement — deliberate: high volatility is a warning that should override a trend claim; low volatility is a fallback descriptor that shouldn't override a real trend.)
8. **`ranging`** — the default fallback once data exists but nothing more specific matched.

`low-liquidity` is in the `RegimeType` enum for forward compatibility but **never fires** — no real liquidity/order-book data source exists anywhere in this platform's providers (confirmed by the D2.5.0 audit and `RiskEngineService`'s own long-standing design note). A dedicated regression test (`validate:regime-engine`) asserts it across every fixture.

`transition` is **not a rung in this chain** — it's an overlay applied *after* the raw classification above, only when a real `previousRegime` was supplied and materially differs from the fresh result. Treating it as a wrapper rather than a competing precedence level avoids an ambiguous question ("does a bullish-trend-turning-into-a-breakout count as a trend regime or a transition regime?") that a flat ordering can't answer cleanly.

This intentionally differs from the sprint brief's own suggested list (which put `low-liquidity` second and did not distinguish `transition` as an overlay) — per the brief's own instruction to document and justify a better hierarchy rather than use it verbatim.

## 7. Insufficient-data behavior

- Never forced: if the three regime-relevant signals are all uncomputable, the result is honestly `insufficient-data`, not a guessed `ranging`.
- Always carries `confidence: 0`, regardless of what `dataQuality.band` happens to read (fixed during development — see §9).
- `transition` never overlays `insufficient-data` — a non-classification is never relabeled as "a change from the previous regime."

## 8. What is intentionally NOT implemented

- **`structure.bos`/`.choch`** — a real, deterministic BOS/CHOCH detector needs a swing-point (fractal high/low) algorithm with its own carefully-justified parameters (lookback width, minimum bar spacing). Judged too large to do justice to inside this sprint without rushing it. Declared in the type, always `undefined`.
- **`structure.liquidityZones`** — no genuine order-book/liquidity data source exists in any provider this platform uses. Declared, always `undefined`.
- **`structure.volumeDelta`** — real buy/sell volume delta needs tick-level or order-flow data; `MarketSnapshot`/`Candle` only ever carry one undifferentiated `volume` figure, when present at all. Declared, always `undefined`.
- **`quant` (Wave/FFT, Hurst, Fractal, Chaos)** — explicitly out of scope this sprint; not even declared as a field yet (see §9 for why omitting entirely, rather than declaring-and-never-populating, was the better choice here).
- **`context` (macro/news/cross-asset)** — the D2.5.0 audit flagged `news.service.ts`/`economic-calendar.service.ts`/`sentiment.service.ts` as not yet re-verified as real vs. mock-backed. Adding them to an observation-layer contract before that verification would risk silently laundering unverified data as if it were as solid as the real indicator/evidence pipeline. Not declared this sprint.
- **Regime persistence / real `previousRegime` lookup** — `RegimeService.classify()` accepts a caller-supplied `previousRegime`; it does not fetch one itself. D2.5.1's `IntelligenceAnalysisRun` persistence exists but was deliberately not extended or wired up here, per the explicit instruction not to expand D2.5.1 scope.
- **Wiring into `/market-intelligence/analyze` or any other production route.** Both services are tested as standalone, explicit deterministic capabilities only.

## 9. Future extension points

- `structure.bos`/`.choch`/`.liquidityZones`/`.volumeDelta` are already typed (always `undefined`) so populating them later is additive, not a breaking change.
- `quant` and `context` were deliberately left **off** the `MarketState` interface entirely (not declared-and-undefined) because their eventual shape isn't yet decided by any approved spec — declaring a guessed shape now would risk locking in the wrong contract. A future sprint should add them as new optional fields once each is genuinely ready.
- `RegimeService.classify()`'s `previousRegime` parameter is the seam for a future D2.5.x sprint to wire in real historical regime lookups via D2.5.1's persistence, without changing `RegimeService`'s own logic.
- `INTELLIGENCE_ENGINE_VERSION` is exported from `market-state.service.ts` specifically so it can be imported by `regime.service.ts` and any future V2 engine without redefining it.

## 10. Versioning

`INTELLIGENCE_ENGINE_VERSION = "2.0.0"` — a new, distinct component version for Intelligence Engine V2, exported from `services/intelligence/market-state/market-state.service.ts`. `MARKET_INTELLIGENCE_PIPELINE_VERSION = "15D.12.0"` is **unchanged** and untouched — the 15D pipeline remains a separate, still-current dependency/component, not superseded. `MarketState.pipelineVersion` and `Regime.pipelineVersion` both carry `INTELLIGENCE_ENGINE_VERSION`, never the 15D tag, so the two version spaces can never be confused in a persisted or logged record.

## Real bugs found and fixed during this sprint's own development

In the interest of the same honesty this contract enforces on the code: two real logic errors were caught and fixed while empirically verifying test fixtures against the actual services (not just hand-calculated), before anything was locked in as a passing test:

1. The `insufficient-data` gate originally required `dataQuality.band === "insufficient"` **and** all three structural signals undefined. A 3-candle fixture where only `volume` was computable had `dataQuality.band === "low"` (not `"insufficient"`), so the gate never fired, and the engine fell through the entire precedence chain to a fabricated `"ranging"` classification on essentially no data. Fixed by decoupling the gate from `dataQuality.band` entirely — it now checks only whether the three regime-relevant signals themselves are all `undefined`.
2. `confidence` was originally always derived from `dataQuality.band`, which meant an `insufficient-data` result could report a nonzero confidence (e.g. `40`) whenever an unrelated indicator like volume happened to compute. Fixed by forcing `confidence: 0` whenever `regimeType === "insufficient-data"`, unconditionally.

Both are covered by dedicated regression tests in `scripts/validate-regime-engine.ts` and `scripts/validate-market-state.ts` so they cannot silently regress.
