# D2.6.10 — Trader Intelligence Workspace & Verified Answer Experience

**Status:** Implemented and tested.
**Scope:** The first trader-facing surface for the D2.5.x/D2.6.x deterministic pipeline. This sprint makes existing, already-verified intelligence *visible and useful* — it computes nothing new about the market.

**Non-negotiable principle** (repeat before touching any file here): the product must never fabricate market information. Every trader-facing answer traces back to Real Market Data → Provider Reliability/Smart Fallback → MarketState → Regime → Hypothesis → Evidence → Historical Validation → Intelligence Score → Decision Context → AI Presenter → Deterministic Integrity Validation → Audit Trace → Trader Answer. LLMs are presenters only.

---

## 1. Response contract

`VerifiedAnswerResponse` (`types/verified-answer-response.ts`) is the one stable, trader-facing shape every UI component consumes. It is built by a pure function, `buildVerifiedAnswerResponse()` (`services/intelligence/chat/verified-answer-response.service.ts`), which regroups an already-computed `IntelligenceEnvelope` + `IntelligenceDecisionContext` + `DataQualityAssessment` + the D2.6.8 presenter result — it computes nothing, it only renames and reshapes real fields already produced by D2.5.x/D2.6.1–D2.6.9. `IntelligencePresentationService.present()` (D2.6.9) now also returns `verifiedAnswer?: VerifiedAnswerResponse`, present only when `context.status === "resolved"`.

The contract deliberately has no field shaped like a BUY/SELL instruction, a target price, a stop loss, a win-rate claim, or a probability of a trading outcome — the same permanent prohibition D2.6.1's `IntelligenceDecisionContext` established, extended to this new surface. Verified directly: a serialized `VerifiedAnswerResponse` never contains a `"probability"` key anywhere (`scripts/validate-verified-intelligence-workspace.ts`, test 30).

## 2. UI architecture

Six new components in `components/intelligence-workspace/`, matching the existing black/gold design system (`components/market-intelligence/AnalysisResult.tsx`'s established tone/spacing conventions — `rounded-card`/`rounded-panel`/`rounded-control`, `Badge`, `InfoTooltip`, `Disclaimer` — reused, never a second design language):

- **`VerifiedMarketContext`** — the header strip: symbol, timeframe, market, regime, data status, provider (only when genuinely known), Intelligence Score.
- **`VerifiedAIAnswerCard`** — the primary card. Renders the presented answer text, then only the sections real intelligence backs (Why/What Could Happen/Risks/What Is Missing) — an `insufficient-intelligence` decision state renders exactly that, with the real missing-information list, never generic filler. Composes the panels below plus a "Why this answer?" toggle and a "View analysis trace" toggle.
- **`EvidencePanel`** — real supporting/opposing evidence and unresolved conflicts (D2.6.1's `DecisionContext`, unmodified) — no new ranking system; `EvidenceRankingService` (15D.4) already ordered these server-side. A conflict is shown honestly, never folded into a fake consensus.
- **`HypothesisPanel`** — real `DecisionHypothesisContext[]`, phrased as a falsifiable current view ("Current hypothesis", "Invalidated if") — never "will happen". Renders nothing when there are zero hypotheses (not every regime generates one).
- **`IntelligenceScorePanel`** — the real, unmodified D2.5.5 `IntelligenceScore`, with an explicit "NOT a probability of profit" disclosure and an expandable per-component breakdown. A component with `dataAvailable: false` renders "Unavailable", never a fabricated 0.
- **`MarketDataProvenance`** — real provider/freshness/cache/fallback state only.
- **`AuditTraceView`** — the read-only "View analysis trace" client (§8 below).

`components/intelligence-workspace/format.ts` centralizes label/tone formatting only (no computation) — reusing `AnalysisResult.tsx`'s own GOOD/MID/BAD tone convention rather than inventing a second color system.

## 3. Chat integration

`MessageBubble.tsx`'s `DisplayMessage` gained a fourth, similarly-conditional field: `intelligence?: VerifiedAnswerResponse`, rendered as `<VerifiedAIAnswerCard>` exactly like the pre-existing `marketAnalysis` field renders `<AnalysisResult>` — same conditional pattern, same message-bubble placement, same disclaimer-exclusion rule (a card supplies its own `<Disclaimer />`).

The chat route (`app/api/private/knowledge/chat/route.ts`) already resolves `verifiedAnswer` via `IntelligencePresentationService` (D2.6.9) — this sprint changed only how the route SERIALIZES it: `intelligence: {resolved: true, ...verifiedAnswer}` on the wire (streaming "done" event and the non-streaming response), replacing the previous narrower ad-hoc summary object. `services/ai/assistant.service.ts`'s `sendMessageStreaming()` now parses this field and returns it as `StreamChatResult.intelligence`, a direct passthrough — no client-side recomputation anywhere.

## 4. Provenance behavior

`VerifiedMarketContext`/`MarketDataProvenance` render `result.provider`/`result.dataStatus`/`result.fallbackUsed` — all three read directly from `DataQualityAssessment` (D2.6.5), never guessed. No provider name is ever shown when provenance is genuinely unavailable (`provider` stays `undefined`, the UI shows "Unavailable" rather than a default). "Fresh" is never displayed unless the real D2.6.4 freshness policy actually classified the data as fresh.

**A real bug was found and fixed while building this contract**: `VerifiedAnswerResponse.fallbackUsed` was initially wired from `presented.fallbackUsed` (D2.6.8's AI-*presenter* fallback signal — was the deterministic text presenter used?) rather than `dataQuality.fallbackUsed` (D2.6.3/D2.6.4's *market-data provider* fallback signal — did an earlier-priority quote/candle provider fail?). These are two genuinely different signals, and the UI components (`VerifiedMarketContext`'s "Fallback used" badge, `MarketDataProvenance`'s "Fallback: Used/Not used") were built expecting the market-data one, matching §7/§12 of the sprint brief. Caught by a fixture-driven test asserting `fallbackUsed` toggles with a real market-data fallback, not a presenter fallback. Fixed at the root: `BuildVerifiedAnswerResponseInput` no longer accepts `fallbackUsed` as a separate parameter at all — `buildVerifiedAnswerResponse()` derives it internally from `dataQuality.fallbackUsed`, so a future caller cannot repeat this mistake by passing the wrong signal into a same-named field. The AI-presenter fallback signal remains fully disclosed, just through the correct channel: `presentedBy === "deterministic-fallback"`.

## 5. Audit behavior

"Why this answer?" (§8 of the brief) is built entirely from the `VerifiedAnswerResponse` already delivered with the message — zero additional network requests, satisfying the sprint's performance constraint (§15: "Do not introduce additional market-data requests from the frontend"). "View analysis trace" (§9) is a deliberately separate, explicit action: `AuditTraceView` fetches the existing `GET /api/private/intelligence/audit/[traceId]` (D2.6.9) only when the trader clicks it, never eagerly, never duplicated per message. It offers no modify/delete affordance anywhere — matching the audit trace's own permanent immutability (D2.6.9 §13).

## 6. Safety behavior

Every AI-provider disclosure line reads "Presented by X — explains verified intelligence, does not generate it" (§13), never implying a specific model calculated the underlying analysis. Hypothesis copy uses "Current hypothesis"/"Could continue if"/"Invalidated if" — never "will happen" (§5). The Intelligence Score panel's own header text states explicitly: "NOT a probability of profit or trade success" (§6).

## 7. Insufficient-data behavior

When `decisionState === "insufficient-intelligence"`, `VerifiedAIAnswerCard` renders a dedicated "Insufficient intelligence" block with the real `missingInformation` list — it never attempts to render the Why/Hypothesis/Risk sections with empty or fabricated content. When market data is entirely unavailable (§12: "all providers fail"), `IntelligencePresentationService` never reaches the presenter at all — `context.status` is `"insufficient-data"`, `verifiedAnswer` stays `undefined`, and the chat route's existing deterministic message ("I attempted to retrieve verified, real-time market data... could not confirm it right now") renders as a plain bubble, never a fabricated AI market answer. Verified directly (`scripts/validate-verified-intelligence-workspace.ts`, tests 8–9).

## 8. Provider fallback behavior

If a market-data provider fails but a fallback provider succeeds, the trader still receives a real, complete answer — `MarketDataProvenance` discloses "Fallback: Used" honestly (§12). D2.6.9's own documented scope limitation still applies and is repeated here: the exact pre-fallback provider *attempt order* (which specific earlier providers failed, in what order) is not structurally available without modifying `MarketDataService`'s hot, heavily-tested return path — this UI never fabricates that ordered chain, it only ever discloses the real winning provider plus the real boolean fallback flag.

If an AI presenter's response is rejected on integrity grounds (D2.6.5/D2.6.8, unmodified), the trader never sees it — the pipeline falls through to the next presenter, and ultimately to `DeterministicSafeFallbackPresenter` if every presenter fails or is rejected, whose text is always itself integrity-valid. Verified end to end (tests 26–29).

## 9. Authorization

Every audit-trace read (`AuditTraceView` → `GET /api/private/intelligence/audit/[traceId]`) is scoped by `(traceId, authenticated userId)` — D2.6.9's own `AuditTraceService.getTrace()`, unmodified. A forged traceId and cross-user access both resolve to a 404, indistinguishable from each other (no existence leak). Verified directly, including a real forged-id case and a real cross-user case (tests 21, 33).

## 10. Frontend/server boundary

The frontend never imports `MarketStateService`, `RegimeService`, `HypothesisService`, `OutcomeEvaluatorService`, `IntelligenceScoreService`, `MarketDataService`, or any provider implementation — confirmed by the fact that every `components/intelligence-workspace/*` file imports only `types/*` (pure data shapes) and `components/ui/*` (presentation primitives). The chat route continues to depend only on the chat-facing intelligence layer (`IntelligencePresentationService`), unchanged from D2.6.9 — all 11 zero-coupling regression scripts re-pass. The frontend performs zero additional market-data requests; it consumes the server-generated `VerifiedAnswerResponse` verbatim, never recomputing MarketState/Regime/Hypothesis/Intelligence Score client-side.

## 11. Testing strategy

This project has no React/component test framework — UI correctness for every prior D2.3/D2.4 UI sprint was verified via `tsc`/`eslint`/`npm run build` plus a manual browser check, and this sprint follows the identical convention. `scripts/validate-verified-intelligence-workspace.ts` (42 assert-based tests, exceeding the ≥40 requirement) covers the deterministic SERVER contract every UI component consumes: response structure, all five freshness states, provider provenance, fallback disclosure (including the bug above, now regression-tested), provider-unavailable/all-unavailable, insufficient intelligence, conflicted/supporting/opposing evidence, the hypothesis rendering contract, invalidation conditions, historical validation, the Intelligence Score and its component discriminated union, audit-trace linkage and authorization (owner/forged-id/cross-user), real end-to-end conversation continuity and explicit symbol-switching (no stale-context leakage), ambiguous-symbol clarification, missing-timeframe defaulting, AI-presenter fallback chains, integrity rejection, deterministic-fallback text equality, the no-probability-language structural check, JSON round-trip safety, and several empty/missing-data edge cases. Full regression across every pre-existing `validate:*` script, `tsc`, `eslint`, and `npm run build` all pass with zero regressions.

## 12. Non-goals (explicitly not built)

No ML, no new trading signals, no BUY/SELL probability, no profit prediction, no automated trading, no broker execution, no order placement, no scheduler, no Redis/Kafka, no vector-DB redesign, no new market-data provider, no new intelligence/scoring formula, no provider voting/ensemble, no autonomous AI reasoning, no automatic trade recommendations. No redesign of the existing website design system — every new component reuses established tokens/primitives.
