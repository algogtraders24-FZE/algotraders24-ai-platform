# D2.8.15 — Intelligence Data Sufficiency, Evidence-State Reconciliation & Production Intelligence Remediation

**Objective**: fix the systemic risk that missing/unavailable evidence in ONE category (microstructure, historical validation) could cascade into a fabricated-looking "Insufficient intelligence" collapse of the OVERALL presentation, even when core OHLC-derived technical intelligence is genuinely available. This sprint made the Intelligence Engine's evidence-state composition provably correct, not merely cosmetically better.

## 1. Root-cause audit (Phase 1)

The triggering screenshot showed EURUSD at "Insufficient Data" / 31/100 / "Trend/RSI14/ATR14 could not be computed" alongside static "not implemented" disclaimers. Investigation (code-reading + live runtime testing) found:

- **`RegimeService.classifyRaw()`'s insufficient-data gate is already correct**: it fires only when `trend.direction`, `structure.recentRange`, AND `structure.volatilityBand` are ALL simultaneously undefined — explicitly documented as independent of `MarketState.dataQuality.band`, so MACD/Bollinger/volume absence never triggers it.
- **`IntelligenceScoreService` already applies a ceiling, not a zero**: `CEILING_INSUFFICIENT_REGIME`/`CEILING_NO_MARKET_STATE` cap the score rather than collapsing it.
- **`DecisionContextService.classifyState()` already allows `well-supported` alongside a non-empty `missingInformation`**: proven live (EURUSD scored 80/well-supported with 5 real missingInformation items simultaneously present).
- **One real, provable bug**: `buildMissingInformation()` unconditionally emitted "Buy/sell volume delta data is not implemented" and "Liquidity risk (order book depth) has no data source" for **every** symbol, including BTCUSD/ETHUSD — stale since D2.8.5/D2.8.11-13 genuinely implemented real Binance volume-delta/order-flow evidence for those two symbols.
- **One real, provable gap**: zero candle-array validation (chronological order, duplicates, malformed OHLC, future timestamps) existed anywhere before indicators were computed.
- The exact screenshot symptom (regime = insufficient-data + 31/100) requires trend/recentRange/volatilityBand to be *simultaneously* uncomputable — a genuinely severe, transient data-scarcity state that did not reproduce during this sprint's live testing. Per this sprint's own stop condition, this is reported honestly as a likely transient provider-side event rather than a fabricated "fix."

**Conclusion**: the regime/score/decisionState composition layer was already non-cascading and correctly designed. The two provable, in-scope issues (stale disclaimers; absent candle validation) were fixed; nothing else in that layer was touched.

## 2. Candle sufficiency model (Phase 2)

`lib/market-data/indicator-requirements.ts` — a pure, additive, reporting-only model. Every number is read directly off `lib/market-data/indicators.ts`'s own real guard clauses, never invented:

| Indicator | Minimum candles | Formula |
|---|---|---|
| EMA20 | 20 | `values.length >= period` |
| EMA50 | 50 | `values.length >= period` |
| RSI14 | 15 | `period + 1` |
| ATR14 | 15 | `period + 1` |
| MACD(12,26,9) | 34 | `slow + signal − 1` |
| Bollinger(20) | 20 | `values.length >= period` |
| Recent range (20-bar lookback) | 21 | `candles.length > lookbackBars` |

`buildCandleSufficiencyReport(requested, received)` never lowers a real requirement — it only reports whether a candle count clears each real, unmodified threshold. Never called from `MarketStateService` itself (which continues to let the real indicator functions decide); used only by the validation script and per-instrument reporting.

## 3. Candle validation (Phase 3)

`lib/market-data/candle-validation.ts` — `validateCandles(candles, nowMs)` rejects, never repairs: duplicate timestamp, out-of-order timestamp, missing/unparseable timestamp, future timestamp (>5s tolerance, matching D2.8.5's own convention), invalid OHLC (non-finite/non-positive/`high<low`/open-close outside range), negative/non-finite volume. Detection is relative to the last *accepted* candle, so one bad row never cascades into rejecting everything after it.

Wired into `MarketStateService.assemble()`: every downstream computation (`computeTechnical`, `computeTrend`, `computeRecentRange`) now uses only `validation.validCandles`, never the raw input. The result is recorded on the new `MarketState.candleValidation` field (`totalReceived`/`totalValid`/`issues`) — always present, never hidden. `assemble()` gained an optional `nowMs` parameter (defaults to `Date.now()`) for deterministic testing.

**Real production finding**: live-running this against Twelve Data's EURUSD/XAUUSD 1h candles found 5 candles per response with timestamps 6–10 hours in the future relative to UTC "now" — a genuine provider timestamp/timezone-labeling ambiguity (not a candle-validation bug), now honestly rejected rather than silently trusted. Indicators remained fully computable from the 95 remaining valid candles.

## 4. missingInformation capability gating (Phase 7)

`DecisionContextService.buildMissingInformation()` — the real, provable bug fix. The "Buy/sell volume delta" and "Liquidity risk (order book depth)" disclaimers are now conditional on the instrument's real, structural microstructure-provider capability:

```ts
const instrument = getCanonicalInstrument(envelope.symbol);
const microstructureCapable = (instrument?.providerMappings ?? []).some(
  (m) => m.provider === binanceMicrostructureProvider.name && m.supportedCapabilities.includes("quote"),
);
```

This reuses the *exact* structural, synchronous check `RealTimeIntelligenceService.fetchMicrostructure()` already uses to decide whether to attempt a live fetch — never a second capability model, and deliberately **not** keyed off `microstructureEvidence`'s presence (which reflects one caller's transient opt-in/fetch-success, not the instrument's permanent capability).

"Liquidity zone data" and "Execution risk" remain unconditional — confirmed genuinely permanent: no liquidity-zone or execution-risk data source exists anywhere in this platform for any instrument (per `types/intelligence-market-state.ts`'s own standing design notes).

**Verified live**: BTCUSD/ETHUSD (Binance-capable) no longer show the stale disclaimers; EURUSD/XAUUSD/XAGUSD/NIFTY50/BANKNIFTY (not Binance-capable) correctly still do.

**Key findings, honestly reported:**

- **XAGUSD genuinely fails at the provider layer** — reproduced twice: `twelve-data` returns `http_error`/`rate_limit`, `alpha-vantage` returns `invalid_response`. Confirmed non-fabricated, provider-side, matching the standing project memory note. Not a D2.8.15 regression — `MarketDataService`'s own honest `insufficient-data` status surfaces correctly.
- **NIFTY50/BANKNIFTY genuinely receive only 18 candles, not 100** — traced to `AngelOneProvider.getTimeSeries()`: the code correctly requests `outputSize: 100`, and `candleWindow()` correctly computes a ~4-day calendar span for 100 hourly bars — but NSE only trades ~6.25 hours/day, so a real trading-hours-only window cannot contain 100 real hourly candles. **This is a genuine market-structure/provider limitation, not an AT24 request-window bug** — the request logic is already correct.
- **This is the exact scenario D2.8.15 exists to fix**: with only 18 real candles, EMA20/EMA50/MACD/Bollinger/recentRange are honestly unavailable (below their real minimums), yet RSI14/ATR14/volume/regime/hypothesis remain available, and `decisionState` correctly reads **"partially-supported"** — never collapsing to "insufficient-intelligence" merely because some indicators lack history. Core intelligence survives partial data exactly as required.
