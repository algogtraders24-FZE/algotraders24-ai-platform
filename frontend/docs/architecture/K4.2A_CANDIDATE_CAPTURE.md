## 2. Candidate capture contract (LOCKED for K4.2-A)

### 2.1 `CandidateService.propose(input): Promise<ProposeCandidateResult>`

Pure orchestration over three ports (constructor-injected, same DI pattern as `KnowledgeService`):
- `CandidateStorePort` — the only thing that writes `KnowledgeCandidate`.
- `EmbeddingPort` — reused from `services/knowledge-loop/knowledge/ports.ts` (no new embedding provider).
- `VectorSearchPort` — reused from the same file (no new vector-search code).

`propose()` **never** imports `KnowledgeService`, never calls `markActive`/`create`/`createVersionOf`, and never writes `Knowledge` or `KnowledgeChunk`. This is the K4.2-A governance boundary — asserted structurally (§5).

### 2.2 Input validation (structural, not a governance decision — throws on violation)

- `canonicalQuestion`, `proposedAnswer`, `createdByUserId`, `sourceType`, `knowledgeType`, `reasonForCandidate`, `confidence` (0–1) are required.
- `sourceType === "web_researched"` requires `evidence.webSources` non-empty (`KNOWLEDGE_CONTRACT.md` §8, "invalid and rejected at creation") — modeled as a `blocked-invalid` **outcome**, not a thrown error, since it is a contract rule a caller could legitimately hit, not a programmer bug.

### 2.3 Privacy scan (K0.5 §7.2 — LOCKED behavior, IMPLEMENTED here for the first time)

Runs on `canonicalQuestion + "\n" + proposedAnswer` combined. **Block-on-hit, beta = reject** (no redaction, no partial creation):

| K0.5 §7.2 check | Implementation | Coverage |
|---|---|---|
| email address | reused `classify.ts` `SENSITIVE` email pattern | full |
| API key / token / secret (`sk-`, `Bearer `, PEM) | reused `classify.ts` `SENSITIVE` pattern | full |
| card number (Luhn-length) | reused `classify.ts` `SENSITIVE` 13–19-digit pattern | full |
| SSN | reused `classify.ts` `SENSITIVE` `\d{3}-\d{2}-\d{4}` pattern | full |
| account-specific references ("your order #", etc.) | reused `classify.ts` `ACCOUNT_SPECIFIC` pattern **+ new** `CANDIDATE_ACCOUNT_REFERENCE` — `ACCOUNT_SPECIFIC` is keyed on first-person "my X" (correct for a live user asking about their own account); a proposed candidate's *text* leaking an account detail reads second-person or as a bare reference ("your order #12345" — §7.2's own literal example), which needed its own narrow pattern | full |
| a `userId`/`conversationId`/`licenseKey`/`invoiceId` **value** | **new** — a cuid()-shaped token regex (`\bc[a-z0-9]{20,}\b`, matching Prisma's default id format used by every id in this schema) | covers any raw internal id leaking into candidate text, which is the concrete risk this row describes; there is no fixed wire format for `licenseKey`/`invoiceId` specifically to pattern-match beyond "looks like one of our ids" |
| phone number | **new** — a conservative pattern for a run of 10+ digits with common separators | full |
| IBAN | **new** — 2 letters + 2 digits + 15–30 alphanumerics | full |
| forbidden trading language | reused `scanForForbiddenLanguage` (`lib/ai/compliance.ts`) | **non-blocking** per K0.5 (`warn`, not `block`) — returned as `forbiddenLanguageWarnings` on the result, re-scanned again at approval time (K4.2-B), never persisted onto the candidate row |
| **full name** | **disclosed gap, not implemented** | no reliable low-false-positive regex exists for "this is a person's full name" in free text; K0.5 lists it but building a name-detection heuristic here would either miss real names or block ordinary product text ("Sarah" is also a common product/feature nickname in this codebase's fixtures). Left as an explicit limitation — see §7 |
| **postal address** | **disclosed gap, not implemented** | same reasoning — a reliable street-address regex without a geocoding dependency has a high false-positive/negative rate; explicitly out of scope for this beta heuristic scanner, consistent with `classify.ts`'s own documented "errs conservatively" philosophy |

**K4.2A-D1: LOCKED.** Block-on-hit for the 8 implemented checks; full-name and postal-address detection explicitly deferred (disclosed limitation, not silently dropped) — flagged as OQ-K4.2A-1 below for a future sprint if the owner wants stronger coverage (e.g., an admin-side secondary review is still the backstop, per K0.5 §2.1 step 3's second scan at approval time).

### 2.4 Dedup against active knowledge (K4.1 §13 / K0.2 §4.2 — LOCKED, IMPLEMENTED here for the first time)

- Embed `canonicalQuestion` (same target the retrieval pipeline embeds — consistency with how similarity is judged everywhere else in this codebase).
- `VectorSearchPort.searchSimilar({embedding, topK: 5, scopes: [proposedScope], visibilities: ["public","customer","admin","internal"], includeUserScope: false, callerUserId: ""})` — **all visibilities**, deliberately: dedup asks "does this fact already exist," not "can this caller see it," so it must not miss a duplicate merely because it's `visibility: internal`.
- Take the maximum `similarity` across returned hits, grouped by `knowledgeId` (a doc can return multiple chunk hits; the doc's dedup score is its best chunk).
- `similarity >= DUP_HARD (0.94)` → candidate is still **created** (never silently dropped — needed for "Duplicate Suppression Rate" analytics, K0.5 §8 retention, and so an admin can see it happened), but with `status: "duplicate"`, `duplicateOfId` set, never reaching `candidate`/reviewable state. Outcome: `duplicate-of-active`.
- `DUP_SOFT (0.85) <= similarity < DUP_HARD` → normal `status: "candidate"`, `duplicateOfId` + `similarityScore` recorded for the reviewer (K0.5 §2.2). Outcome: `created`.
- `similarity < DUP_SOFT` → normal `status: "candidate"`, no duplicate fields. Outcome: `created`.

**K4.2A-D2: LOCKED.**

### 2.5 Idempotency (NEW — K4.1 did not address this; locked here)

K4.1's dedup design (§13) answers "is this the same *fact* as something already published" — it does not answer "is this the same *proposal* being submitted again" (e.g., a caller retries after a timeout, or the same orchestrator turn fires `propose()` twice). Without a guard, that creates unbounded duplicate `candidate` rows for one real event, which would pollute the review queue and the retention-forever `KnowledgeCandidate` table (K0.5 §8).

**Design (no schema change — K4.1 §19 holds: zero new tables/columns):**
- When `originatingMessageId` is present: look up an existing, non-deleted `KnowledgeCandidate` with the same `originatingMessageId` **and** `sourceType`. If found, `propose()` makes **no write at all** (no embedding call, no dedup search, no insert) and returns `outcome: "idempotent-replay"` with the existing candidate. This is the common case (an orchestrator/tool call always carries a message id) and is O(1) via the existing `@@index([originatingConversationId])`-adjacent lookup pattern (filtered further by `originatingMessageId`/`sourceType` in the query — not separately indexed; acceptable at beta scale, noted as a future index candidate if `KnowledgeCandidate` volume grows, not a correctness concern).
- When `originatingMessageId` is absent (e.g., `admin-flagged`, `imported-doc` — no message to point at): fall back to an exact-match natural key — `createdByUserId + sourceType + canonicalQuestion + proposedAnswer` (byte-exact, not fuzzy — fuzzy near-duplicates are §2.4's job, not idempotency's). If an existing candidate matches exactly, same short-circuit.
- Idempotency is checked **before** the privacy scan and **before** dedup — a replayed request does no new work and triggers no new privacy/dedup evaluation (it already passed or failed the first time; replaying does not re-litigate that decision). If the original request was blocked by privacy scan, no row exists to match, so a retry correctly re-runs the full check (this is intentional — a blocked proposal leaves no candidate row, so there is nothing to be "idempotent" against; re-submission is treated as a fresh proposal every time until one succeeds in creating a row).

## 8. Acceptance — PASSED

**RED-first proof:** `services/knowledge-loop/classifier/classify.ts`, `types/knowledge-loop/index.ts`, and the entire `services/knowledge-loop/governance/` directory were `git stash push -u`'d, leaving only the contract doc and the new test file. Running `validate-k4.2a-candidate-capture.ts` against that pre-implementation tree failed immediately with `Cannot find module '../services/knowledge-loop/governance/candidate-service'` — the strongest possible RED, since this is entirely new capability. `git stash pop` restored the implementation; the same run then passed.

**Implementation, then 3 genuine test-design fixes found and fixed (not production-code bugs):**
1. **B6** (`ACCOUNT_SPECIFIC` reuse gap) — `classify.ts`'s `ACCOUNT_SPECIFIC` is keyed on first-person "my X" (correct for a live user asking about their own account); a candidate's proposed *text* leaking an account detail reads second-person ("your order #12345" — K0.5 §7.2's own literal example). Added a narrow, purpose-built `CANDIDATE_ACCOUNT_REFERENCE` pattern in `privacy-scan.ts` rather than stretching the classifier's pattern to cover both directions.
2. **E1/E2** (self-referential doc comments) — `candidate-service.ts`'s own header comment names `markActive`/`createVersionOf`/`KnowledgeService` in prose explaining the boundary it enforces — which tripped the structural test asserting those tokens are absent. Fixed by stripping comments before the structural regex match (the test now checks real code, not documentation).
3. **CRLF `$`-anchor bug** in the test's own `stripComments` helper — `line.replace(/\/\/.*$/, "")` silently no-ops on a line ending `\r\n` because `.` excludes `\r` and `$` (no `/m`) anchors past it. Fixed by matching `/\/\/[^\r\n]*/g` directly on the whole source instead of splitting/mapping per line.

**One genuine regression found in a PRE-EXISTING K1-era test, fixed by scope, not by weakening:** `validate-knowledge-loop-schema.ts`'s INV-1 test asserted "no `services/knowledge-loop/**` file EVER references `KnowledgeCandidate`" — true before K4 existed, but K4.2-A's entire purpose (always deferred to K4 by `K1_DECISION`/ADR-K3-M8) is to be the first sanctioned writer of that table. Narrowed the test to exclude `services/knowledge-loop/governance/**` by directory, keeping the real invariant — retrieval/answer-generation code never touches `KnowledgeCandidate` — fully enforced for every other file, unchanged. Re-verified 19/19 after the fix.
