# D2.6.3 — Global Instrument Discovery & Intelligent Multi-Provider Data Fabric

**Status:** Implemented and tested. Infrastructure-first: no AI presenter, no signals, no execution.
**Scope:** A provider-agnostic, deterministic, fault-tolerant market-data layer that lets a trader search for instruments globally (TradingView-style) and obtain verified market data - feeding the existing, unmodified 15D → D2.5 → D2.6 intelligence pipeline.

---

## 1. Architecture

```
Trader
  ↓
Instrument Search           NEW - InstrumentSearchService
  ↓
Canonical Instrument        NEW - CanonicalInstrument (instrument-catalog.ts)
  ↓
Provider Capability Resolution   NEW - ProviderMapping.supportedCapabilities, checked by each adapter
  ↓
Multi-Provider Market Data Router     REUSED - MarketDataService (extended, not rebuilt)
  ↓
Data Quality / Freshness Gate    REUSED - TtlCache/staleFallback + snapshot.cached/cacheAgeMs
  ↓
Verified MarketSnapshot          EXTENDED - +providerSymbol, +fallbackUsed (both optional)
  ↓
EXISTING 15D pipeline → D2.5 Intelligence Engine → D2.6 Decision Context → (future) AI Presenter
```

The single most important finding of this sprint's mandatory pre-implementation audit: **the "Multi-Provider Market Data Router" the mission describes already existed.** `MarketDataService` (`services/market-data/market-data.service.ts`, Sprint D2.2/D2.3.S3) already implements deterministic provider-priority fallback, per-call timeout/retry/backoff (`withReliability`), health monitoring, stale-cache grace-window fallback, and structured aggregate failure - never fabricating a result. This sprint **extends** it (two new providers appended to its default array, two new provenance fields) rather than building a second, parallel router - directly satisfying the mission's explicit "do not create a second intelligence pipeline" and "reuse existing infrastructure wherever possible."

## 2. Canonical instrument model

`CanonicalInstrument` (`types/canonical-instrument.ts`) is the provider-neutral identity of a tradable market. `id` is always the exact existing platform `MarketSymbol` (e.g. `"BTCUSD"`) - the same string every downstream engine (MarketState/Regime/Hypothesis/DecisionContext) already keys on, so this richer model never requires touching any of that code. `symbol` (e.g. `"BTC/USD"`) and `displayName` are presentation-only, never lookup keys. `aliases` is a small, hand-authored, deterministic list (`["bitcoin", "btc"]`) - never auto-generated or fuzzy-derived. `providerMappings[]` is the real list of `{provider, providerSymbol, providerInstrumentId?, supportedCapabilities, verified}` entries - a canonical instrument may have zero, one, or several.

Relationship to `lib/market-data/market-registry.ts` (existing, unmodified): that file remains the lightweight catalog the existing pipeline/UI already depend on. `lib/market-data/instrument-catalog.ts` (new) is the richer, searchable superset - every instrument that exists in both uses the identical `id`, so the two never diverge.

## 3. Provider abstraction

Two source-of-truth strategies, deliberately different, both documented in the catalog's own header:

- **Twelve Data / Alpha Vantage** (existing, frozen, already-tested adapters): never rewritten to read from the catalog. Their `SYMBOL_MAP`s stay exactly as they are; the catalog's entries for these providers are a truthful, manually-kept-in-sync **mirror**, for search/display only.
- **Binance / Angel One** (new adapters, no prior frozen table): read their symbol resolution **directly from the catalog** via `mappingsForProvider(name)` - a single source of truth, never a second copy. Adding a new Binance/Angel-One-covered instrument means adding one `providerMapping` to the catalog, never editing the adapter file.

Both new adapters implement the existing, unmodified `MarketDataProvider`/`SnapshotProvider`/`TimeSeriesProvider` interfaces (`types/market-data-provider.ts`) - drop-ins for `MarketDataService`'s provider array, zero changes above the provider layer.

## 4. Provider capability resolution

Every `ProviderMapping` declares `supportedCapabilities: ("quote" | "candles")[]`. Both new adapters check this **before** issuing a request (`resolveSymbol(symbol, requiredCapability)` in both `binance.provider.ts` and `angel-one.provider.ts`): a symbol mapped for a provider but not declaring the requested capability is rejected the same honest way as a symbol not mapped at all - `unsupported_symbol`, never a silent attempt. The router never blindly calls every provider - `MarketDataService` already skips a provider entirely when it doesn't implement `SnapshotProvider`/`TimeSeriesProvider` at all (`isSnapshotProvider`/`isTimeSeriesProvider` type guards, unmodified).

## 5. Provider priority

`MarketDataService`'s default provider array, in order: **Twelve Data → Alpha Vantage → Binance → Angel One**. This ordering is a deliberate, backward-compatible choice, not a new priority engine: every symbol Twelve Data/Alpha Vantage already served keeps its **exact existing selection behavior** - only the new instruments these two adapters uniquely cover (Binance: a 3rd real fallback for BTCUSD/ETHUSD/SOLUSD/XRPUSD; Angel One: first-ever coverage of NIFTY50/RELIANCE) are affected by the array's extra length. Priority remains a single, centralized, documented constructor default (`MarketDataServiceOptions.providers`) - never hidden per-call assumptions scattered through the codebase.

## 6. Fallback rules

Unchanged, reused verbatim from `MarketDataService`: providers are attempted in array order; a typed `MarketDataProviderError` (`unconfigured`, `unsupported_symbol`, `auth`, `rate_limit`, `http_error`, `timeout`, `invalid_response`) moves the loop to the next provider; `http_error`/`timeout`/`rate_limit` get bounded, jittered retry **within** a provider first (`lib/market-data/reliability.ts`, unmodified) before falling back; `auth`/`unsupported_symbol`/`invalid_response`/`unconfigured` fail fast to the next provider immediately (no retry storm). If every provider fails, a single aggregate `MarketDataProviderError` is thrown, citing every attempt - never a fabricated snapshot. Verified directly: 4-provider fallback chains (A→B, A→B→C, all-fail) and capability-based skipping.

## 7. Freshness rules

Reused verbatim: `TtlCache.getStale(key, maxAgeMs)` distinguishes a fresh hit (served within `cacheTtlMs`) from a resilience-grade stale-fallback (served only after every provider failed, within `staleFallbackMs`) - both are marked `cached: true`/`cacheAgeMs` on the returned `MarketSnapshot`, **never silently presented as live**. This sprint adds no new freshness concept; it only proves (via a dedicated router test) that this existing mechanism still functions correctly with the extended, 4-provider array.

## 8. Provenance

`MarketSnapshot` (`types/market-snapshot.ts`) gains two new **optional** fields, additive only, no existing field's meaning changed:

- `providerSymbol?: string` - the winning provider's own symbol/pair spelling (e.g. `"BTCUSDT"` for canonical `"BTCUSD"`), when it differs from the canonical `symbol`.
- `fallbackUsed?: boolean` - `true` only when the router's priority loop had to move past a real failure (never merely "not configured") on an earlier-priority provider to obtain this snapshot.

`snapshot.timestamp` (existing field, unchanged) already carries the provider's own real reading time, distinct from `retrievedAt` - this **is** the "source timestamp"; no duplicate field was added. Verified directly: `providerSymbol` correctness, `fallbackUsed` correctness in both the "no fallback" and "fallback occurred" cases, and that `timestamp` stays distinct from `retrievedAt`.

## 9. Failure states

Every failure this sprint's two new adapters can produce maps onto the **existing** `MarketDataErrorKind` union (`lib/market-data/errors.ts`, unmodified) - no new error kind was needed:

| Sprint's failure condition | Classification |
|---|---|
| Timeout | `timeout` (applied by the reliability layer around every provider call) |
| Network error | `http_error` |
| HTTP error | `http_error` (401/403 → `auth`, 429/418 → `rate_limit`) |
| Rate limit | `rate_limit` |
| Auth failure | `auth` (Binance: HTTP 401/403; Angel One: HTTP 401/403 or a real `errorcode` starting `AB1`/`AB2`) |
| Unsupported symbol | `unsupported_symbol` (checked before any network call, and via Binance's real documented `-1121` code) |
| Malformed response | `invalid_response` |
| Missing required fields | `invalid_response` (e.g. a missing `lastPrice`/`ltp` never becomes `0`) |
| Invalid timestamp | Falls back to `retrievedAt` honestly - not a separate error, since a missing/invalid source timestamp doesn't invalidate the price itself |
| Stale data | Not an error - the existing `cached`/`cacheAgeMs` freshness mechanism (§7) |
| Provider-specific error response | Classified by the provider's own real, documented error shape (never string-matched) |

## 10. No-fabrication policy

The sprint's absolute rule, verified directly with dedicated tests: when every compatible provider fails, `MarketDataService` throws a structured `MarketDataProviderError` citing every real attempt - it never invents a price, never creates a synthetic candle, never asks an LLM for a price, never infers missing data, and never silently substitutes an unrelated symbol for the one requested. Existing stale-cache behavior (§7, already part of the approved D2.3.S3 architecture) is the one sanctioned exception to "no data ever," and it remains explicitly, honestly marked stale via `cached`/`cacheAgeMs` - never silently promoted to fresh.

## 11. Security boundaries

- **Binance**: its public market-data REST endpoints (`/ticker/24hr`, `/klines`) require no API key or signature at all - this adapter never reads `BINANCE_API_KEY`. The project's `.env.local` `BINANCE_API_KEY`/`SEC_KEY` line is additionally malformed (a second value concatenated into the same line rather than its own variable) - moot for this sprint since no credential is used, but flagged for the user rather than silently "fixed."
- **Angel One**: reads the project's exact existing credential variable names (`API_KEY`, `CLIENT_CODE`, `PIN`, `TOTP_SECRET`) - never renamed, never invented, per explicit instruction. These generic (non-`ANGEL_`-prefixed) names are a real collision risk worth a future cleanup, not silently renamed here. No credential, TOTP code, JWT, or refresh token is ever logged, ever included in a thrown error message, or ever echoed anywhere - the same "the key lives in the request, never in a log" discipline every existing provider file already follows, extended to every derived credential a session produces.
- **Live authentication was deliberately never attempted** against the real Angel One API this sprint, even though real credentials exist in `.env.local` - see §14 for the full reasoning. `.env.local` itself was never modified.
- **The new API route** (`GET /api/instruments/search`) requires authentication (`getUserOrNull`, matching every other private route) and returns only public symbol/token/capability metadata - never a provider secret, never an internal credential.
- **No secret is ever placed in an AI prompt** - this sprint adds no AI call of any kind.

## 12. Integration with the existing 15D pipeline

Unmodified, by construction: `MarketDataService.getSnapshot()`/`getTimeSeries()` still return the exact same `MarketSnapshot`/`Candle[]` contracts every existing consumer (the 15D Evidence Collector, `services/ai/technical-context.service.ts`, D2.5.2's `MarketStateService`, the workspace UI) already expects - the two new provenance fields are optional and additive, so no existing consumer's type or runtime behavior changes. Nothing in D2.5/D2.6 (Regime, Hypothesis, Memory/Outcome, Historical Validation, Intelligence Score, DecisionContext, IntelligenceQueryContext) was touched this sprint.

## 13. Instrument search & frontend selector

`InstrumentSearchService` (`services/market-data/instrument-search.service.ts`) is pure, synchronous, and deterministic - a fixed 7-level ranking precedence (exact canonical → exact provider symbol → exact display name → exact alias → prefix symbol → prefix name → substring), checked in that exact order per candidate instrument; every matching instrument is returned, ranked, never silently narrowed to one. No LLM, no fuzzy/semantic matching anywhere. `GlobalSymbolSelector.tsx` was upgraded (not redesigned - the sprint's own instruction) from a fixed 10-option `<select>` to a debounced search box over the new `GET /api/instruments/search` route, showing asset class, provider(s), and provider symbol per result, using the exact same `WorkspaceContext.setSymbol()` contract every other part of the app already relies on.

## 14. Live verification status (read before trusting any provider claim in this sprint)

- **Binance**: fully live-verified. `/ticker/24hr`, `/klines`, and the real `-1121` unsupported-symbol error were all confirmed against the real, live `https://api.binance.com` before the adapter was written, and the finished adapter was re-verified end-to-end live (real snapshot, real evidence, real 5-candle series, correct error classification) after the catalog-driven refactor.
- **Angel One**: the **symbol/token identity mapping** for NIFTY 50 (token `99926000`) and RELIANCE (token `2885`, symbol `RELIANCE-EQ`) is live-verified - fetched from Angel One's own public, unauthenticated instrument scrip master (`https://margincalculator.angelbroking.com/OpenAPI_File/files/OpenAPIScripMaster.json`) on 2026-08-10. The **authenticated login + quote flow** was built to SmartAPI's own documented, stable contract and tested only against fake HTTP responses matching that contract (including the real RFC 6238 TOTP algorithm, verified against all 5 of RFC 6238 Appendix B's own published test vectors) - a live call using the real credentials present in `.env.local` was deliberately never attempted. Logging into a real brokerage account's API session from an automated coding session - even read-only - is a real, external, hard-to-reverse action (subject to the broker's own session/rate-limit semantics) that this project's safety discipline treats as needing the user's own explicit action, never a coding agent's default. `isConfigured()` still honestly reports whether real credentials exist; nothing fabricates a successful login.
- **Twelve Data / Alpha Vantage**: unchanged, already live-verified in prior sprints (D2.2/D2.3.S3/L2.1) - not re-verified here since nothing about them changed.

## 15. Known limitations

- Angel One's historical-candle date-window computation (`candleWindow()` in `angel-one.provider.ts`) is a best-effort, documented estimate - unverified against a real response (see §14). A future sprint with live access should confirm it actually yields the requested candle count.
- Instrument search covers a small, hand-authored catalog (12 instruments) - not the full breadth of any provider's real universe (e.g. Angel One's public scrip master alone lists 152,044 instruments). Deliberately scoped this way, matching the sprint's own "do not over-engineer" instruction and `market-registry.ts`'s established "list only what's real and intentional" discipline - not a technical ceiling.
- `Router priority` is still a single hardcoded default array (extended, not restructured into a configurable "strategy" object) - the sprint allowed this ("prefer a centralized configuration/strategy... do not hardcode hidden priority assumptions throughout the code"), and the array *is* that single, centralized, documented configuration; a more dynamic per-instrument/per-asset-class priority system was judged out of scope for this sprint.
- The `.env.local` credential-naming issues (Angel One's generic `API_KEY`/`CLIENT_CODE`/`PIN` names; the malformed `BINANCE_API_KEY`/`SEC_KEY` line) are flagged, not fixed - see §11.

## 16. Future extension path

- A concrete authenticated Angel One live-verification pass, once the user explicitly authorizes a real login session.
- Expanding the instrument catalog with more real, verified instruments per asset class as genuine coverage is confirmed (mirroring how Twelve Data's own `SYMBOL_MAP` grew symbol-by-symbol, each with a live-verification comment, across D2.2/D2.3.S3).
- A `GET /api/instruments/:id` detail route, if a future UI needs a single instrument's full provider-mapping detail beyond what search already returns.
- Wiring `MarketDataService.getSnapshot()`'s new `providerSymbol`/`fallbackUsed` provenance into the D2.6.2 `IntelligenceQueryContext`'s `dataAsOf` narrative, so a future AI presenter can say not just "as of when" but "from which real provider, with or without fallback" - not built this sprint (out of scope: AI Presenter integration).
