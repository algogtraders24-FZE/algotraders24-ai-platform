# D2.5.3 — Deterministic Hypothesis Engine

**Status:** Implemented and tested. This is the authoritative contract for later validation work (D2.5.4+).
**Scope:** Hypothesis generation only, from real `MarketState` + `Regime` (+ an optional real `EvidenceBundle`). No historical validation, no outcome evaluation, no Intelligence Score, no ML, no Gemini involvement.

---

## 1. Hypothesis philosophy

A `Hypothesis` is a **falsifiable research claim**, not a verdict and not an instruction. It states what the current deterministic evidence is consistent with, over an explicit, bounded window, with an explicit condition under which it would be proven wrong. It is built entirely from real, already-computed `MarketState`/`Regime` fields — `HypothesisService` performs no I/O, calls no AI, and generates no new indicator math of its own (see §16 of the sprint brief: reuse, don't duplicate, D2.5.2).

## 2. Signal vs hypothesis boundary

| | Signal (never produced) | Hypothesis (this sprint) |
|---|---|---|
| Example | "Buy XAUUSD." | "Current evidence is consistent with bullish trend continuation over the defined prediction window, invalidated if the specified structure condition fails." |
| Contains | Execution instruction, target, position size | A claim, a window, an invalidation condition |
| Certainty framing | Implies the system decided for you | States what it's consistent with and how it could be wrong |

Enforced structurally, not just by convention: `types/intelligence-hypothesis.ts#Hypothesis` has no `action`/`recommendation`/`positionSize`/`broker` field anywhere in its shape, and `scripts/validate-hypothesis-engine.ts` has a dedicated regression test that JSON-serializes every generated hypothesis and asserts it contains no `BUY`/`SELL`/`execute`/`position size` text anywhere, plus an explicit check that those four fields are `undefined` on the object itself.

## 3. Supported hypothesis types

**Generated in D2.5.3 (7):** `trend-continuation-bullish`, `trend-continuation-bearish`, `breakout-confirmation-bullish`, `breakout-confirmation-bearish`, `range-continuation`, `volatility-expansion`, `volatility-contraction`.

**Declared but never generated in D2.5.3 (2):** `reversal-candidate-bullish`, `reversal-candidate-bearish` — see §13.

Exactly one hypothesis type maps to each `Regime.regimeType` (a closed, 1:1 table — see §4). `HypothesisService.generate()` never returns more than one hypothesis per call, and returns zero for `insufficient-data`, `transition`, and `low-liquidity`.

## 4. Generation rules

| Regime | Hypothesis | Additional gate |
|---|---|---|
| `trending-bullish` | `trend-continuation-bullish` | `structure.trend.direction === "up"` (defensive re-check; Regime's own rule already guarantees this) |
| `trending-bearish` | `trend-continuation-bearish` | `structure.trend.direction === "down"` |
| `breakout` | `breakout-confirmation-bullish` | `structure.recentRange` must be real (defensive) |
| `breakdown` | `breakout-confirmation-bearish` | `structure.recentRange` must be real (defensive) |
| `ranging` | `range-continuation` | `structure.recentRange` must be real — **never fabricated if absent** |
| `high-volatility` | `volatility-expansion` | `structure.volatilityBand`/`atrPercent` must be real (defensive) |
| `low-volatility` | `volatility-contraction` | `structure.volatilityBand`/`atrPercent` must be real (defensive) |
| `insufficient-data`, `transition`, `low-liquidity` | none | — |

Each rule is a small, named function in `services/intelligence/hypothesis/hypothesis.service.ts` (`generateTrendContinuation`, `generateBreakoutConfirmation`, `generateRangeContinuation`, `generateVolatility`) — no shared "scoring" logic, no rule reused across types beyond the common `buildHypothesis()` assembler.

This sprint deliberately does **not** independently re-derive multiple simultaneous hypotheses from raw `structure` fields (e.g. "also generate a trend hypothesis during a breakout, since the trend also happens to be up"). `RegimeService`'s own precedence already picked the single most informative classification for the current `MarketState` — re-deriving a second, competing hypothesis on top of it would duplicate that precedence logic and risk disagreeing with it.

## 5. Evidence requirements

`requiredEvidence: EvidenceType[]` declares, per type, which of the existing `types/evidence.ts#EvidenceType` values the rule depends on: `["technical"]` for trend/volatility hypotheses (EMA/ATR-derived), `["price", "technical"]` for breakout/breakdown/range hypotheses (their `recentRange`/breakout boundary is directly price-derived). No new `EvidenceType` value was added — the existing 8-value enum from Sprint 15D.4 already covers everything this sprint needs.

**`confidence` is deliberately not a new, separate field on `Hypothesis`.** `regimeContext.confidence` — `Regime`'s own, already-deterministic "how much underlying data was available" score (D2.5.2) — is reused as the hypothesis's strength/completeness signal. This is a deliberate design choice, not an oversight: adding a second, parallel confidence number here would risk it drifting out of sync with the regime confidence it would necessarily be derived from anyway (the evidence backing a hypothesis *is* the regime's own basis), and the sprint brief itself asks that this number represent "strength/completeness of the deterministic evidence," which `regimeContext.confidence` already is, verbatim. **It is never a probability of profit, a win rate, or an "85% chance price will rise" style claim** — there is no statistical model anywhere in this sprint that could honestly produce one.

## 6. Prediction windows

Candle-based, never vague language (`predictionWindow: { candles: number, timeframe: SignalTimeframe }`):

| Hypothesis family | Candles | Rationale |
|---|---|---|
| Trend / range continuation | 20 | Matches `MarketStateService`'s own `BREAKOUT_LOOKBACK_BARS` — the same "recent swing window" length the hypothesis is already reasoning about |
| Breakout / breakdown confirmation | 5 | A short confirmation window — a breakout that immediately fails within a handful of bars is conventionally a failed breakout, not a slow continuation |
| Volatility expansion / contraction | 10 | Shorter than a trend window — volatility regimes conventionally mean-revert faster than directional trends |

These are documented, versioned constants in `hypothesis.service.ts`, explicitly **not** claimed to be statistically optimized — that is named future research, not a V2 deliverable.

## 7. Invalidation conditions

Every directional hypothesis's `statement.invalidationCondition` is a **structured**, machine-checkable object — not just a sentence:

```ts
interface InvalidationCondition {
  description: string;                 // human-readable
  field: string;                       // dot-path into a future MarketState, e.g. "structure.trend.direction"
  comparator: "equals" | "not-equals" | "crosses-below" | "crosses-above";
  referenceValue: string | number;      // the REAL value recorded at hypothesis-creation time
}
```

| Hypothesis | field | comparator | referenceValue |
|---|---|---|---|
| `trend-continuation-bullish` | `structure.trend.direction` | `not-equals` | `"up"` |
| `trend-continuation-bearish` | `structure.trend.direction` | `not-equals` | `"down"` |
| `breakout-confirmation-bullish` | `snapshot.price` | `crosses-below` | the real `recentRange.high` at creation time |
| `breakout-confirmation-bearish` | `snapshot.price` | `crosses-above` | the real `recentRange.low` at creation time |
| `range-continuation` | `structure.breakoutSignal` | `not-equals` | `"undefined"` (a real breakout/breakdown occurring) |
| `volatility-expansion` | `structure.volatilityBand` | `not-equals` | `"high"` |
| `volatility-contraction` | `structure.volatilityBand` | `not-equals` | `"low"` |

A future evaluator can re-check `field` against a later `MarketState`, apply `comparator` against the stored `referenceValue`, and determine validated/invalidated without re-deriving anything or parsing English — this is the sprint's own stated "most important property," and it's satisfied structurally, not just by a well-written description string.

## 8. Supporting/opposing evidence

`supportingEvidence: EvidenceItem[]` is built directly from the real `MarketState` fields that satisfied the rule (e.g. the trend's own `basis` strings, the recent-range boundary, the ATR percent) — reusing `types/evidence.ts#EvidenceItem` exactly, attributed to `services/intelligence/market-state/market-state.service.ts` as the source. Never empty for a generated hypothesis.

`opposingEvidence: EvidenceItem[]` is sourced **only** from a real, caller-supplied `EvidenceBundle`'s own already-detected `EvidenceConflict`s for the same symbol (`opposingFromConflicts()`) — never independently interpreted from free text, never invented to "make the UI look balanced." If no `EvidenceBundle` is passed, or it has no conflicts for this symbol, `opposingEvidence` is genuinely `[]`. This is a deliberately conservative, structurally-grounded integration with the existing Evidence/Conflict architecture rather than a new interpretation layer — see §11.

## 9. Insufficient-data behavior

`HypothesisService.generate()` returns `[]` whenever `regime.regimeType === "insufficient-data"` — no branch of the generation switch handles it, so it falls through the `default: return []`. Additionally, every individual rule has its own defensive re-check of the `MarketState` fields it needs (e.g. `range-continuation` re-checks `structure.recentRange` even though `Regime`'s own `ranging` rule should already guarantee it) — if a required field is genuinely missing for any reason, the rule returns `undefined` and no hypothesis is produced, rather than fabricating one. Covered by dedicated tests, including a defensive test that hand-constructs a `MarketState`/`Regime` mismatch to prove the guard fires even in that edge case.

## 10. Conflict handling

Consistent with the existing Evidence/Conflict philosophy (`EvidenceConflict.resolution` defaults to `"unresolved"` and is never auto-picked — Sprint 15D.4): a hypothesis **can** still be generated even when real opposing evidence exists for it — the deterministic generation rule is checked independently of conflicts. The conflict is preserved in `opposingEvidence`, never silently resolved into an "overall bullish" verdict, and never used to suppress hypothesis generation. This sprint does not implement any logic that would drop or downgrade a hypothesis because opposing evidence exists — that judgment is left to whoever consumes the hypothesis later, exactly as the raw evidence-ranking engine leaves `EvidenceConflict.resolution: "unresolved"` for a human/future engine to weigh, not itself.

## 11. Determinism

`HypothesisService.generate()` is pure and synchronous: no network call, no database read, no `Math.random()`, no `Date.now()`-dependent branching (the only clock read is `generatedAt`, which never affects which hypothesis is produced). Even `id` — normally a good candidate for a random/DB-generated value — is derived deterministically from `${symbol}-${timeframe}-${type}-${regime.generatedAt}`, specifically so that identical input produces a byte-identical output, field for field, not just the same classification. Verified by a dedicated determinism test (`scripts/validate-hypothesis-engine.ts`) that calls `generate()` twice on the same input and deep-equals the results, including `id`.

## 12. Future historical validation

Out of scope for this sprint, on purpose. `Hypothesis.status` starts `"active"` and stays there — this engine never marks a hypothesis `"invalidated"`/`"expired"` itself, and never computes a validated rate, win rate, historical probability, expected return, or success percentage. That is explicitly D2.5.1's `IntelligenceAnalysisRun`/`IntelligenceAnalysisOutcome` persistence's eventual job (already built, not extended or modified here) once real outcomes accumulate. The seam for that future work is exactly `statement.invalidationCondition`: a later evaluator reads it, rechecks `field` against a real future `MarketState`, and produces a real `AnalysisOutcome` — no redesign of either this contract or D2.5.1's needed.

## 13. Explicitly unsupported hypothesis types

**`reversal-candidate-bullish`/`reversal-candidate-bearish` are declared in `HypothesisType` but never generated in D2.5.3.**

The sprint brief is explicit that RSI thresholds alone (`RSI > 70` / `< 30`) are not an acceptable standalone reversal rule, and that reversal hypotheses should be left unimplemented rather than built on weak evidence. The only structurally-available reversal-adjacent signal in the current architecture is `Regime`'s own `"transition"` classification (D2.5.2) — but `Regime` exposes the fact that a transition occurred only inside a human-readable `basis` string (e.g. *"the fresh classification is 'trending-bearish'"*), not as a separate, strongly-typed field naming the new regime. Building a falsifiable, strongly-typed reversal hypothesis on top of that would require either fragile string-parsing (contrary to "use strong enums/unions rather than arbitrary strings wherever appropriate") or extending D2.5.2's `Regime` contract — and this sprint's instructions treat D2.5.1 and D2.5.2 as frozen, not to be modified or regressed.

Per the sprint's own framing — *"it is better to have fewer valid hypotheses than many unreliable ones"* — reversal hypotheses are left unimplemented rather than built on an inadequate foundation. A future sprint that first extends `Regime` to expose its raw pre-overlay classification as a real field would have a clean, honest path to implementing them.

## Verified against the real services, not just designed on paper

Every fixture used in `scripts/validate-hypothesis-engine.ts` reuses the exact candle sequences already empirically verified in `scripts/validate-regime-engine.ts` (D2.5.2) to produce specific, known regimes — not re-derived or assumed. No new logic bugs were found while wiring `HypothesisService` on top of them; all 21 tests passed on the first full run, which is itself evidence that the D2.5.2 contracts (`MarketState`, `Regime`) were solid enough to build on without needing another round of empirical correction this time.
