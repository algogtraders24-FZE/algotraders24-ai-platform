## 1. What the owner's checklist requires evidence for

Verbatim from the K4.2-A PASS message, the full pipeline:
```
Assistant answer → eligibility → CandidateService.propose() → PENDING_REVIEW →
admin approval → Knowledge → KnowledgeChunk/embedding → retrieval
```
must be **exactly one controlled path**, with evidence for: replay/idempotency, concurrent approval, candidate→Knowledge atomicity/failure behavior, authorization, provenance transfer, duplicate promotion, rejection, retrieval isolation.

K4.2-B covers everything from "admin approval" onward (approve/reject/deprecate/archive/reinstate/publishNewVersion, plus the ingestion step that makes an approved row actually retrievable). The "Assistant answer → eligibility → propose()" half is orchestrator wiring — still explicitly out of scope (OQ-K4.2A-2) — so today's evidence starts from an already-created candidate (built directly with `CandidateService`, exactly as K4.2-A's own tests do) rather than a live end-to-end Assistant turn.

## 2. A deliberate, disclosed deviation from K4.1 §20's literal wording

K4.1 §20 describes `governance-service.ts` as wrapping "`KnowledgeService`'s existing `markActive`/`createVersionOf`/`deprecate`/etc. **as the transactional primitive** it wraps." Taken literally, that means: call `KnowledgeService.create()` (draft) then `KnowledgeService.markActive()` (activate) as two separate calls, then a *third*, separate `AuditLog` write. Re-reading this design against the owner's explicit new requirement — **prove atomicity/failure-behavior with evidence** — surfaces a real gap: between `create()` and `markActive()` there is a window where a process crash leaves an orphaned `draft` row with no candidate update and no audit row. `KNOWLEDGE_GOVERNANCE_CONTRACT.md` §2.1 itself hedges with "single DB transaction **where possible**" and explicitly carves ingestion out as the one step allowed to run after commit — it does not sanction a two-call, non-transactional create+activate.

**K4.2B-D1: LOCKED — `governance-service.ts` re-implements the transition semantics directly, fused into ONE Prisma transaction per operation, rather than composing two separate `KnowledgeService` calls.** Specifically:
- `approve()`: one transaction creates the `Knowledge` row **already active** (not draft→active), updates the candidate to `approved` + `finalKnowledgeId`, writes the `AuditLog` row, and bumps `KnowledgeVersionCounter` — all four, or none.
- `reject()`: one transaction updates the candidate + writes `AuditLog`.
- `deprecate()` / `archive()` / `reinstate()`: one transaction does the `Knowledge` state transition + writes `AuditLog` (K1's `PrismaKnowledgeStore.transition()` already fuses the state change with the counter bump, but not with an audit write — since governance-service.ts needs the audit write to be atomic too, it re-implements the same field-setting logic rather than calling into `PrismaKnowledgeStore`, to keep everything in one transaction it controls end-to-end).
- `publishNewVersion()`: one transaction creates the new version + deprecates the old + writes `AuditLog` (mirrors `PrismaKnowledgeStore.createVersionOf()`'s existing logic, re-implemented for the same reason).

This does **not** touch `services/knowledge-loop/knowledge/prisma-backend.ts` (the K1-era file) at all — the governance store is entirely new code in `governance/`, independently transactional. The field-setting rules (`approvedAt`/`approvedBy` on activation, `deprecatedAt`/`deprecatedBy` on deprecation, etc.) are copied to match `PrismaKnowledgeStore` exactly, verified by a structural test that diffs the two field-setting rulesets.

Ingestion (chunking + embedding) is **not** part of the transaction (K0.5 §2.1 step 10, "ingestion runs after commit because it calls an external embedding API") — `approve()`/`publishNewVersion()` call the existing, unmodified `realIngestionPort()` (K1) after the transaction commits, exactly matching `publishKnowledge()`'s established pattern. A partial embedding failure sets `embeddingStatus: "failed"` (existing K1 behavior) and is surfaced on the result as `reindexNeeded: true` — it never rolls back the already-committed approval.

## 3. Authorization (LOCKED, defense-in-depth)

K0.5 §2.1: "`adminId` comes from the verified admin session (`requireAdmin().user.id`), never from a request body." K4.2-B has no HTTP route yet (that's K4.2-C), so there is no `requireAdmin` call in this sprint's own code path. To avoid shipping a service that silently *trusts* whatever `adminId` string it's given, `governance-service.ts` independently re-verifies the given id against the real `User.role` column before any write — the same defense-in-depth principle AN1.9's `MemoryGateway` uses ("approver is always a real admin id, never an agent"). A non-admin (or nonexistent) `adminId` fails every governance method with `outcome: "unauthorized"` before any table is touched.

**K4.2B-D2: LOCKED.**

## 4. Concurrency safety (LOCKED, new — K4.1 did not specify a mechanism)

Two admins opening and approving the same candidate near-simultaneously must not both succeed (which would create two `Knowledge` rows from one candidate, or corrupt the audit trail). K0.5 §2.1 step 1 says "assert status ∈ {candidate, under_review}; else 409" but doesn't specify how to make that check race-safe. **K4.2B-D3: LOCKED** — the status guard is enforced as a *conditional update* inside the transaction (`updateMany` filtered on `id` AND `status IN (candidate, under_review)`, checking the affected-row count is exactly 1) rather than a plain read-then-write, which closes the read/write race a naive check-then-act would leave open. The same mechanism is the **idempotency** guard: re-approving an already-`approved` (or already-`rejected`/`duplicate`) candidate fails the conditional update (0 rows affected) and returns `outcome: "wrong-status"` — it can never double-create a `Knowledge` row from one candidate.

## 5. Duplicate promotion (LOCKED — falls out of §4, not a separate mechanism)

A candidate with `status: "duplicate"` (K4.2-A's dedup outcome) is not in `{candidate, under_review}`, so `approve()`'s own status guard (§4) refuses it — `outcome: "wrong-status"`. No separate "is this a duplicate" check is needed; the state machine already forbids it.

## 6. Provenance transfer (LOCKED, K0.5 §2.1 step 4, applied as-is)

`Knowledge.provenance` = `candidate.evidence` merged with `{ reviewerNotes?, editedByReviewer? }`. `editedByReviewer` is computed, not admin-supplied: `true` iff `opts.editedAnswer` (or any other overridden field) differs from the candidate's proposed value. The candidate's original `evidence` is never mutated — `Knowledge.provenance` is a **new** object built from it, per `KnowledgeProvenance`'s own "immutable once written" rule (K0.2 §3).

## 7b. Ingestion failure isolation (LOCKED, caught during implementation, not a design decision that existed before writing the code)

A naive implementation `await`s `IngestionPort.ingest()` unguarded after the approval transaction commits. If `ingest()` *throws* (not just reports some embeddings failed — an actual exception, e.g. the embedding API being unreachable), that exception would propagate out of `approve()`/`publishNewVersion()` even though the `Knowledge` row, the candidate update, and the `AuditLog` row are **already committed and durable** by that point — misreporting a real, successful approval as a failure to the caller. **K4.2B-D4: LOCKED** — both `approve()` and `publishNewVersion()` wrap their post-commit `ingest()` call in a `try/catch`; a thrown exception is treated identically to a fully-failed embed (`reindexNeeded: true`), never re-thrown. Caught while implementing, not anticipated in the original design — the owner's explicit "atomicity/failure behavior" requirement is exactly what surfaced it on review.

## 8. Retrieval isolation (re-proven, not re-designed)

- The candidate row itself is **never** retrievable at any status, including `approved` (K1/K2's `VectorRepository` query has no `KnowledgeCandidate` join — unchanged, re-verified by the existing INV-1 tests).
- Before `approve()` commits, no `Knowledge` row exists for the candidate — nothing to retrieve.
- After `approve()` commits, the new `Knowledge` row is created with `lifecycleStatus: "active"`, `supersededById: null`, `deletedAt: null` — satisfying the K1/K2 eligibility predicate directly (asserted structurally against the real eligibility SQL in `VectorRepository.ts`, matching K4.2-A's own INV-1-extension style, since this worktree has no live DB smoke authorized in this sprint).

## 10. Acceptance — PASSED

**RED-first proof:** `package.json`, `types/knowledge-loop/index.ts`, and the entire modified/new `services/knowledge-loop/governance/` surface were `git stash push -u`'d back to the K4.2-A baseline, leaving only the contract doc and the new test file. **2 genuine bugs caught and fixed during implementation (before shipping, not discovered later):**
1. **B6** — a naive implementation let a *total* `IngestionPort.ingest()` exception (network down, not just a partial embed failure) propagate out of `approve()`/`publishNewVersion()`, even though the `Knowledge` row, candidate update, and `AuditLog` write were already committed by that point — an already-successful approval would have misreported itself as a failure. Fixed (K4.2B-D4, §7b): both methods wrap the post-commit ingest call in `try/catch`, treating a throw identically to a fully-failed embed (`reindexNeeded: true`), never re-thrown.
2. **F3** — the in-memory `GovernanceStorePort` fake didn't enforce the same "source row must be active" precondition the real `PrismaGovernanceStore.publishNewVersion()` does (via its conditional `updateMany`), so the fake silently allowed publishing a new version from an already-deprecated row — a fake/real behavioral mismatch that would have given false confidence in the offline suite. Fixed by adding the same precondition check to the fake.

**1 necessary, disclosed test update to K4.2-A (not a K4.2-A defect)** — see §7: K4.2-A's own `E6` assertion ("`governance-service.ts` must not exist yet") was a snapshot-in-time scope boundary for K4.2-A's own closure, not a permanent invariant; it necessarily went stale the moment K4.2-B correctly landed the file it names. Updated to assert what is still actually true (no admin route/UI exists yet — that remains K4.2-C). Re-verified 43/43 on K4.2-A after the fix.
