# D2.7.2 — AT24 Native Chart Engine Foundation

**Status:** Implemented and tested (foundation only).
**Scope:** A deterministic, provider-agnostic, isolated rendering engine capable of rendering real OHLC candlestick data with a coordinate system, viewport, basic pan/zoom/crosshair, and price/time axes. Coexists with the existing TradingView integration via an explicit `ChartProvider: native | tradingview` boundary. No indicators, no drawing tools, no ML/AI chart interpretation, no trading execution.

---

## 1. Current chart-data flow (Phase 1 audit findings)

Before this sprint, TradingView (`components/workspace/tradingview/AdvancedChart.tsx`, D2.6.11) was the platform's only chart. It fetches its own OHLC data externally via TradingView's embed script — **no route ever exposed AT24's own `MarketDataService.getTimeSeries()` candles to the browser.** That is the one genuine gap this sprint fills.

Three existing pieces the Phase 1 audit found and reused rather than duplicated:

- **Timeframe registry**: `SignalTimeframe` (`types/signal.ts`) is the platform's one canonical timeframe union. `PROVIDER_INTERVAL` (already exported from `services/intelligence/hypothesis/hypothesis-outcome-evaluator.service.ts`, already used in production by `RealTimeIntelligenceService`) is the existing `SignalTimeframe → provider-interval-string` mapping. The new candles route imports both directly.
- **Instrument catalog**: `getCanonicalInstrument()` (`lib/market-data/instrument-catalog.ts`, D2.6.3/D2.6.12) validates the requested symbol — the same catalog `chart-instrument-resolver.ts` and every other market-data route already use.
- **MarketDataService**: `marketData.getTimeSeries()` (the shared singleton, `services/market-data/shared-instance.ts`) is called exactly as `RealTimeIntelligenceService`/`hypothesis-outcome-evaluator.service.ts` already call it — no new provider, no new caching layer, no new fallback logic.

`Candle` (`types/market-candle.ts`) has no per-instrument decimal-precision field, so the price axis derives display precision from the tick step itself (the same principle `lib/financial-format.ts` already applies), never a hardcoded per-instrument lookup.

## 2. Chart data contract (`types/chart-data.ts`)

`ChartCandle` is a thin, chart-local view over the existing `Candle` — every OHLCV value copied through unchanged; only `datetime` is converted to an epoch-millisecond `time` field the coordinate system can do arithmetic on. `ChartSeries` carries `candles`, `rejectedCount` (how many raw candles failed integrity validation — reported honestly, never hidden), and `retrievedAt`. `ChartDataStatus` is `loading | ready | empty | stale | error | unsupported` — `unsupported` means chart-instrument-resolver/the candles route has already determined no real data can ever be fetched; `error` means a fetch attempt genuinely failed.

## 3. The new candles route (`app/api/private/market-data/candles/route.ts`)

`GET /api/private/market-data/candles?symbol=&timeframe=&outputSize=`. Auth via the same `getUserOrNull()` pattern every other market-data route uses. Validates `symbol` against `getCanonicalInstrument()` and `timeframe` against `isSignalTimeframe()` (both existing/newly-additive-but-shared checks, never route-local ad hoc validation). Calls `marketData.getTimeSeries({ symbol, interval: PROVIDER_INTERVAL[timeframe], outputSize })`, normalizes the result (§5), and returns the same `toMarketDataErrorDTO`/`statusCodeForReason` failure shape every other market-data route already returns on a `MarketDataProviderError`.

**Known limitation**: `MarketDataService.getTimeSeries()` does not expose which provider ultimately served the request or a provider-reported timestamp (unlike `getSnapshot()`, which returns a full `MarketSnapshot` with `provider`/`retrievedAt`). `ChartSeries.retrievedAt` is therefore this route's own success timestamp, not a provider-attributed one — an honest, real timestamp, just not provider provenance. A future sprint could extend `MarketDataService.getTimeSeries()`'s return type to include this if a real need emerges; not done here to avoid touching that frozen, widely-depended-on method's signature for this foundation sprint.

## 4. Timeframe support

`SIGNAL_TIMEFRAMES`/`isSignalTimeframe()` were added to `types/signal.ts` (additive — the union itself is unchanged) as the one runtime companion to `SignalTimeframe`, reusable by any future caller that needs to validate a request-supplied timeframe string. `ChartTimeframeSelector.tsx` renders all 8 real timeframes (1m/5m/15m/30m/1H/4H/1D/1W) — exceeding Phase 10's minimum (M1–D1) requirement using the same union, never a second list.

## 5. Candle data-integrity validation (`lib/chart-engine/candle-normalizer.ts`)

Never repairs a bad candle — a candle failing any check is dropped and counted in `rejectedCount`. Rules: OHLC must all be finite real numbers; `high >= low`; `open`/`close` must fall within `[low, high]`; `datetime` must parse to a finite timestamp; each **accepted** candle's time must be strictly greater than the previous accepted candle's time (one rule that rejects both duplicate timestamps and out-of-order candles without a sort/dedupe pass that could silently reorder bad data into looking clean); an invalid volume drops only that field, never the whole candle.

## 6. Pure engine core (`lib/chart-engine/`)

Deliberately not one monolithic React component — each concern is its own pure, framework-agnostic module, independently unit-testable via `tsx` (no DOM/Canvas required for any of these):

- `coordinate-system.ts` — `priceToY`/`yToPrice`/`timeToX`/`xToTime`, computed fresh from the viewport's absolute bounds every call (no accumulated delta, no floating-point drift across repeated pan/zoom).
- `viewport.ts` — `fitToData`, `panViewport`, `zoomViewport` (clamped to a 5–2000 visible-candle floor/ceiling), `priceRangeForWindow` (auto vertical fit to whatever's horizontally visible, recomputed after every pan/zoom).
- `price-axis.ts` — the standard 1/2/2.5/5/10-per-decade "nice number" tick algorithm; decimal precision derived from the tick step itself, so the same logic serves forex/crypto/equity/index instruments without a per-asset-class lookup table.
- `time-axis.ts` — ticks always placed AT a real candle's own timestamp (never synthesized between candles); intraday timeframes render clock-time ticks, day+ timeframes render date ticks.
- `candle-classifier.ts` — bullish/bearish/doji from real OHLC only (doji threshold: body ≤5% of the candle's own high-low range, a standard published convention, not an arbitrary pixel value).
- `crosshair.ts` — nearest-real-candle lookup; never interpolates a synthetic OHLC value.
- `canvas-typography.ts` / `canvas-colors.ts` — bridge D2.7.1's CSS-variable typography/color tokens (`--font-mono`, `--signal-up`, `--signal-down`, `--gold`, etc.) into Canvas 2D, which cannot apply CSS classes/variables directly. Client-only with real-token-value fallbacks for SSR/test environments.
- `renderer.ts` — the Canvas 2D draw layer: grid, candlesticks, price axis, time axis, crosshair. A function of its inputs only — no hidden state.

## 7. Coordinate system & viewport model

CSS-pixel space throughout (devicePixelRatio scaling applied once by `NativeChart.tsx` via `ctx.setTransform`, never re-derived per draw call). Horizontal pan/zoom is the primary interaction; vertical price range auto-fits whatever candles are currently horizontally visible rather than being independently pannable — a deliberate v1 scope decision (see §12), not an oversight.

## 8. Crosshair & typography

The crosshair snaps to the nearest real candle (never an interpolated point). The OHLC/timestamp readout is rendered as a DOM strip (not canvas text) using `FIN_PRIMARY`/`FIN_SECONDARY`/`FIN_LABEL` (`components/ui/financial-typography.ts`) and `formatPrice`/`formatTimestamp` (`lib/financial-format.ts`) — the same typography every other numeric value on the platform uses, per `types/chart-typography-contract.ts`'s own D2.7.1 declaration. `formatTimestamp()` was added to `lib/financial-format.ts` this sprint specifically to fulfill that contract's pre-declared but previously unimplemented `"timestamp"` formatter role.

## 9. Price & time axes

See §6. Both are fully deterministic — identical viewport/candle input always produces identical ticks (verified by test).

## 10. Real data wiring

`WorkspaceContext.symbol` → `NativeChart` → `useChartCandles(symbol, timeframe)` → `GET /api/private/market-data/candles` → `MarketDataService.getTimeSeries()` → provider routing/fallback (unchanged) → `normalizeCandles()` → `ChartSeries`. Provider credentials never leave the server; the browser only ever calls AT24's own route.

## 11. Instrument resolution

`NativeChart` calls `resolveChartInstrument()` (D2.6.11/D2.6.12, unchanged) purely to check `resolution.supported` before attempting a fetch, so an instrument chart-instrument-resolver already knows has no chart representation renders an honest message immediately. This does **not** replace or duplicate that resolver — the native chart's actual data availability (via `MarketDataService`) is a separate, sometimes narrower set than TradingView's own coverage (e.g. AAPL has a TradingView chart but zero `MarketDataService` provider mapping) — both are honestly surfaced, never conflated.

## 12. Workspace integration (`ChartProvider: native | tradingview`)

`ChartPanel.tsx` composes `ChartProviderToggle` with either `NativeChart` or the existing `AdvancedChart` (TradingView) — wired into the Workspace's existing "Chart" `WorkspaceSection` **in place of** a bare `<AdvancedChart/>`, but `AdvancedChart.tsx` itself is completely untouched. **Sprint D2.9.6**: after the D2.9.1–D2.9.5 hardening pass (light theme, cross-pane crosshair sync, mobile verification, trade clustering, equity overlay) and live verification on production, the default flipped to **Native** — no longer labeled "(Beta)". TradingView remains fully intact and reachable via the toggle, now the explicit fallback; a session with an already-saved `tradingview` preference (`ChartWorkspaceLayout`) keeps seeing it unchanged. Neither is a silent fallback for the other, in either direction.

## 13. Performance

Canvas-based rendering — never one DOM node per candle, so it scales the same at 50 or 5,000 candles. Pan/zoom/crosshair interaction updates `viewportRef`/`crosshairRef` (React refs) and calls `draw()` directly; it does **not** go through `setState` on every `mousemove`, so a drag or zoom gesture never triggers a React re-render per frame. The one piece of interaction state that IS reflected in React (the DOM OHLC readout, for typography reasons — see §8) is throttled to at most one `setState` per animation frame via `requestAnimationFrame`.

## 14. Responsive behavior

`ResizeObserver` on the chart's container drives both the CSS size and the canvas's real pixel buffer (`width * devicePixelRatio`) — no hardcoded chart dimensions anywhere in the engine; only the surrounding gutter constants (`PRICE_AXIS_WIDTH`, `TIME_AXIS_HEIGHT`) are fixed UI layout values, not data dimensions.

## 15. States

`loading` / `ready` / `empty` (zero candles after validation) / `error` (fetch failed) / `unsupported` (resolver or route already knows no data exists) all render distinct, honest copy — no spinner disguised as data, no silent substitution of a different symbol. Provider credentials and raw provider error text are never surfaced to the client (the route's error DTO strips them, matching every other market-data route).

## 16. Data-integrity guarantees

See §5. `rejectedCount` is surfaced in the UI (a small caption under the chart) rather than silently absorbed — the same "honest, never hidden" discipline the rest of the intelligence pipeline already follows.

## 17. Known limitations (explicit, non-goals for this sprint)

- **No independent vertical pan/zoom** — price range always auto-fits the horizontally visible window. A real, deliberate v1 scope cut, not an oversight; a future sprint could add it without changing the coordinate-system/viewport contract.
- **No indicators, no drawing tools, no ML/AI chart interpretation, no trading execution** — explicitly out of scope per the sprint brief.
- **No candle-level caching in the new route** — `MarketDataService.getTimeSeries()` itself is not cached at the service level (see that method's own long-standing comment); every native-chart data request is a live fetch. `ChartDataStatus.stale` is declared for a future caching layer but not currently reachable.
- **Provider attribution for candle data is not available** — see §3's known limitation.
- **Live, authenticated interactive browser verification** could not be completed in this environment — see the sprint's final report for exactly what was and wasn't verified.

## 18. Testing

`scripts/validate-native-chart-engine.ts`, 80 assert-based tests (no test framework, matching this project's established convention): candle-integrity validation (12), coordinate-system inversion/degenerate-input safety (8), viewport pan/zoom/fit/clamping (12), price-axis tick generation and precision (8), time-axis tick generation reusing `SignalTimeframe` (8), candle classification (4), crosshair nearest-candle lookup (4), canvas typography/color token bridging (4), end-to-end renderer smoke tests against a recording fake `CanvasRenderingContext2D` (4), `SignalTimeframe` reuse guards (4), structural/regression guards (8), and no-fabrication/honesty guards (4).

Full regression across every pre-existing `validate:*` script (including this sprint's own), `tsc`, `eslint`, and `npm run build` results are reported in the sprint's final report.
