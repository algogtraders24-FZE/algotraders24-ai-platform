# D2.7.10 — Historical Validation Automatic Scheduler

**Status:** Implemented and tested. **Baseline:** D2.7.9 (commit `bc79bb5`).
**Scope:** Add a production scheduler (Vercel Cron) that periodically invokes the *existing* D2.7.9 evaluation route. No new evaluator, no changes to evaluation semantics, no threshold changes.

---

## 1. Why this sprint exists

D2.7.9 made the D2.5.4/D2.6.5 evaluator infrastructure safely callable via `POST /api/private/admin/intelligence/evaluate-outcomes`, but nothing in the deployment called it automatically — an operator still had to trigger it by hand. D2.7.10 closes that gap with the smallest addition that makes the route self-triggering: a Vercel Cron entry pointed at the same route, once a day.

## 2. Scheduler architecture

```
Vercel Cron (vercel.json, "0 2 * * *")
        |
        v  HTTP GET, production deployment only, user-agent "vercel-cron/1.0"
GET /api/private/admin/intelligence/evaluate-outcomes
        |
        v  Authorization: Bearer <CRON_SECRET or INTELLIGENCE_EVALUATION_CRON_SECRET>
isValidCronSecret() [lib/intelligence/cron-auth.ts]
        |
        v  (same handler as the D2.7.9 admin/manual POST path)
runScheduledOutcomeEvaluation({ maxUsers: 50, perUserLimit: 20 }, "cron")
        |
        v  (unchanged from D2.7.9)
evaluatePendingAnalysisRunsForUser() -> HypothesisOutcomeEvaluatorService
        |
        v
validated / invalidated / inconclusive -> IntelligenceAnalysisOutcome
        |
        v
HistoricalValidationService.buildHistoricalValidation() - unchanged, sampleSize >= 30 gate untouched
```

Everything below `runScheduledOutcomeEvaluation` is byte-identical to D2.7.9. This sprint only adds: a `vercel.json` cron entry, a `GET` export on the existing route (Cron requires GET; D2.7.9 only had `POST`), an alternate secret-variable name Vercel can auto-inject, and observability logging.

## 3. Cron configuration

`vercel.json` (new file — none existed before this sprint):

```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "crons": [
    {
      "path": "/api/private/admin/intelligence/evaluate-outcomes",
      "schedule": "0 2 * * *"
    }
  ]
}
```

**Schedule: `0 2 * * *`** — once daily, nominally 02:00 UTC. Confirmed against Vercel's own documentation (fetched during this sprint, not assumed from training data):

- Hobby plan: cron jobs are restricted to **once per day**; any expression that would run more often fails at deploy time. `0 2 * * *` is a fixed single minute+hour with wildcard day/month/weekday — genuinely once-daily, compatible.
- Hobby precision: Vercel does not guarantee the exact minute — an hourly-scoped expression like this "could trigger anywhere between 02:00:00 and 02:59:59." This is expected and does not need special handling; historical-outcome evaluation has no minute-level requirement (per the sprint brief's own reasoning).
- This sprint does **not** upgrade the Vercel plan and does not assume Pro/Enterprise scheduling precision.

## 4. Authentication

Two independent, additive paths into the same code, in the exact order the route checks them:

1. **Cron secret** (`Authorization: Bearer <secret>`, verified in constant time via `crypto.timingSafeEqual` in `lib/intelligence/cron-auth.ts`, extracted from the D2.7.9 route this sprint so it's directly unit-testable). The secret is read by `loadIntelligenceEvaluationCronSecret()` (`lib/intelligence/evaluation-env.ts`):
   - `INTELLIGENCE_EVALUATION_CRON_SECRET` (the original D2.7.9 name) is checked **first**.
   - `CRON_SECRET` is checked as a **fallback**, recognizing Vercel's own documented convention: *"adding an environment variable called `CRON_SECRET` to your Vercel project... the value... will be automatically sent as an `Authorization` header when Vercel invokes your cron job"* (verified against Vercel's live documentation this sprint). This name is not configurable on Vercel's side — it must be exactly `CRON_SECRET` for the automatic injection to happen.
   - This is one secret *concept* recognized under two variable *names*, not a second independent secret. An operator can set either (or both, with the same value) — setting only `CRON_SECRET` gets Vercel's zero-extra-configuration auto-injection; setting `INTELLIGENCE_EVALUATION_CRON_SECRET` keeps working exactly as it did in D2.7.9 for any other caller (a manual curl, a non-Vercel scheduler).
   - Never falls back to "accept anyone" — both must be genuinely absent (or the header genuinely wrong) for the check to fail, matching D2.7.9's original behavior.
2. **Admin session** (`requireAdmin`, unchanged from D2.7.9) — for manual/support triggering, batch or single-user (`?userId=`).

The cron-authenticated branch **never** reads `maxUsers`, `perUserLimit`, or `userId` from the request — it always uses the fixed production defaults (`maxUsers: 50, perUserLimit: 20`), matching the sprint's "deterministic, repeatable" requirement. Vercel's own cron invocation never appends query parameters to the configured `path` in the first place, so this is a hardening against a hypothetical leaked-secret misuse, not a response to an observed gap.

## 5. GET vs POST

Vercel Cron always invokes via HTTP **GET** against the path in `vercel.json` (confirmed against Vercel's documentation: *"Vercel makes an HTTP GET request to your project's production deployment URL"*). D2.7.9's route only exported `POST`, which would never have been reachable by Cron. This sprint adds a `GET` export sharing the exact same handler function as `POST` — the D2.7.9 admin/manual trigger (documented as `POST`) is fully preserved; nothing was removed or renamed.

## 6. Existing evaluator reuse

No new evaluator, no duplicated evaluation logic. The call chain from the route down through `ScheduledOutcomeEvaluationService` → `PendingOutcomeEvaluationService` → `HypothesisOutcomeEvaluatorService` is exactly D2.7.9's, unmodified by this sprint. The only new code in the orchestration layer is observability logging and a read-only `listPendingEvaluationRuns` call purely for a log/metric count (see §9) — no new write path, no new business logic.

## 7. Idempotency and concurrency

Both are entirely D2.7.9's mechanisms, untouched:

- **Application-level**: a hypothesis with an existing finalized (`validated`/`invalidated`) outcome is reused, never re-evaluated.
- **DB-level backstop**: the partial unique index `intelligence_analysis_outcomes_finalized_unique` on `(analysisRunId, hypothesisId) WHERE status IN ('validated','invalidated')` — this sprint does not touch the schema or the migration in any way.

This is exactly what makes daily-Cron-with-Vercel's-best-effort-delivery safe: Vercel's own documentation warns that *"cron delivery can also occasionally invoke the same scheduled run more than once"* and recommends idempotent, reconciliation-based operations. D2.7.9's design already satisfies this — repeated invocation, whether from a delivery duplicate, a manual admin trigger overlapping with the scheduled run, or an operator retry, converges on the same outcome set without creating duplicates. No new locking mechanism (Redis or otherwise) was introduced; the existing DB constraint and idempotent read-before-write checks are sufficient, matching the sprint's explicit "prefer the smallest solution" instruction.

## 8. Failure handling

Unchanged in spirit from D2.7.9, examined again for the scheduler context:

- A per-user failure (provider outage, malformed data) is caught inside `runScheduledOutcomeEvaluation`'s loop, recorded in `summary.errors`, and never converted into a fabricated `validated`/`invalidated` verdict — the loop continues to the next user.
- A catastrophic failure (e.g. the database itself is unreachable, so `listUserIdsWithPendingEvaluationRuns` throws before the loop even starts) propagates out of the route handler and is caught by `withContext`'s existing `ErrorHandler`, which returns a proper error HTTP response — it is never silently swallowed into a `200 OK`.
- Missing cron secret configuration is a *quiet* rejection (falls through to `requireAdmin`, which then returns 401 for an unauthenticated cron caller) — not a crash, not a fabricated success.

## 9. Observability

Using the existing `services/backend/Logger.ts` convention (no new logging framework), scoped via `logger.child("intelligence-scheduler")`. Every invocation logs:

- **Start**: `triggerSource` ("cron" | "admin-batch" | "admin-manual"), `usersScanned`, `maxUsers`, `perUserLimit`.
- **Per-user failure**: `triggerSource`, `userId`, error `message` only (no stack trace, no query text, no secrets).
- **Completion**: `triggerSource`, `usersScanned`, `usersProcessed`, `usersFailed`, `runsConsidered` (total pending `IntelligenceAnalysisRun` rows found across scanned users, via a read-only `listPendingEvaluationRuns` call added purely for this metric), `outcomesCreated`, `validatedCount`, `invalidatedCount`, `inconclusiveCount`, `durationMs`.

Never logged: the `Authorization` header, the configured secret value, or any user data beyond `userId`. The `x-vercel-cron-schedule` header Vercel sends is not currently read (there is only one cron entry for this route, so there is nothing to disambiguate) — noted for a future sprint if a second schedule is ever added to the same path.

## 10. Deployment configuration

Environment variables (names only — see `.env.example`, never a real value committed):

- `INTELLIGENCE_EVALUATION_CRON_SECRET` — optional, original D2.7.9 name.
- `CRON_SECRET` — optional, Vercel's native auto-injected name (D2.7.10 fallback).

Neither is prefixed `NEXT_PUBLIC_*` — both remain server-only. Per Vercel's own guidance, these should be set on the **Production** environment (this feature has no meaningful Preview/Development use — see §11). A redeploy is required after setting either in the Vercel dashboard, per Vercel's standard environment-variable behavior.

## 11. Preview / local development safety

No code-level guard was added, because none is needed — this is guaranteed by Vercel's own cron architecture, not by anything in this repository: *"Vercel makes an HTTP GET request to your project's **production deployment URL**"* (Vercel's own wording). Cron jobs are configured once per project and only ever target the Production deployment; they are never triggered against Preview deployments. Vercel's documentation also states explicitly that there is *"currently no support for `vercel dev`, `next dev`, or other framework-native local development servers"* for cron jobs — running `npm run dev` locally does not and cannot trigger a scheduled evaluation. The route remains reachable via manual `GET`/`POST` in any environment (as it always was, for admin/debug purposes), but nothing schedules it outside of the real Vercel Production cron registration.

## 12. Known limitations

- **Daily scheduling is a Hobby-plan constraint, not a product decision about freshness.** Historical-outcome evaluation does not need minute-level execution (the evaluation horizon is inherently historical/future-window based), but daily is also the *ceiling* Hobby allows, not a chosen optimum. A future sprint on a paid plan could schedule more frequently without any evaluator changes — this sprint deliberately does not request or assume that upgrade.
- **Twelve Data's bounded historical window is unchanged** (D2.7.8/D2.7.9 finding): the provider returns only the latest N candles as of now, with no date-range query capability. An older pending hypothesis whose evaluation boundary has receded out of that window will still honestly resolve to `inconclusive`, exactly as before. The scheduler does not change how often this happens — it only causes the existing, correct logic to run automatically instead of never.
- **The historical sample still requires genuine outcomes.** As of this sprint, the real database contains 22 invalidated + 2 validated (24 meaningful outcomes) from D2.7.9's testing — still below `MIN_HISTORICAL_VALIDATION_SAMPLE = 30`. This sprint does not add, alter, or manufacture any outcome to reach that threshold; the sample grows only as the daily scheduler processes genuinely eligible, genuinely-closed-window hypotheses over time.
- **"Configured" is not "observed running."** See the Final Report's Runtime Observation section for the explicit distinction between what this sprint verified (configuration correctness, local authentication logic, build/deploy-readiness) versus what requires an actual production deployment with real Vercel cron registration to observe (a real scheduled invocation showing up in Vercel's cron logs).
