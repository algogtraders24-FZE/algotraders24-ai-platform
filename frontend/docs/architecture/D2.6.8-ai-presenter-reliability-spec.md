# D2.6.8 — Verified AI Presenter, Multi-Model Fallback & Response Integrity

**Status:** Implemented and tested.
**Scope:** A provider-agnostic orchestration layer on top of D2.6.5's existing presenter/integrity/fallback architecture — Gemini → Claude → OpenAI → deterministic fallback, in priority order, gated on real credential availability. No redesign of working architecture; no new intelligence computation of any kind.

**Non-negotiable principle** (repeat before touching any file here): the deterministic intelligence engine (D2.5.x/D2.6.1–D2.6.7) is the sole source of market facts. Every language-model backend added by this sprint — Gemini, Claude, OpenAI — is a **presentation layer only**. None of them computes a price, an indicator, a regime, a hypothesis, a risk level, a historical statistic, or a probability of profit. None of them ever votes on market direction with the others.

---

## 1. Existing architecture (audit summary)

D2.6.5 already built everything this sprint needed to extend, never rebuild:

- `AIIntelligencePresenter` (`types/intelligence-envelope.ts`) — a narrow, provider-agnostic interface (`name`, `present(envelope, question)`) whose return type structurally cannot carry a new market fact.
- `GeminiIntelligencePresenter` — already provider-generic. Its constructor takes `{provider?: AIProvider}`, defaulting to `new GeminiProvider()`, and its `.name` getter reflects the *injected* provider's own name, not a hardcoded literal. This one class is a drop-in presenter for **any** `AIProvider`, confirmed by reading it directly before writing any new code.
- `AIResponseIntegrityService` (`validateResponseIntegrity`, `presentSafely`) — a pure, deterministic (never a second LLM) validator checking a presenter's output against the real `IntelligenceDecisionContext`: unsupported numeric claims, unsupported symbols, guaranteed-profit/directional language, unsupported indicators, unsupported historical claims, and contradiction of a real unresolved conflict or an insufficient-intelligence state.
- `DeterministicSafeFallbackPresenter` — never calls an LLM; formats the real `IntelligenceDecisionContext` into prose directly.

The one real gap: `presentSafely()` is hardcoded to exactly **one** presenter and **one** fallback — it has no concept of a priority chain across multiple providers. This sprint does not modify `presentSafely()` (it stays exported, unchanged, for any existing single-presenter caller) — it adds a new orchestrator that reuses the same underlying `validateResponseIntegrity()` pure function in its own N-provider loop.

`lib/ai/provider.interface.ts`'s `AIProvider` has no `isConfigured()` method, and `GeminiProvider`'s constructor (via `loadGeminiEnv()`) **throws** immediately when `GEMINI_API_KEY` is missing — it does not return a graceful null/false. This is why availability is checked via real env-var presence *before* a provider is ever constructed, not via a try/catch around a throwing constructor as the primary signal.

## 2. New provider adapters

`ClaudeProvider` (`lib/ai/providers/claude.provider.ts`) and `OpenAIProvider` (`lib/ai/providers/openai.provider.ts`) implement the existing, unmodified `AIProvider` interface as raw, documented REST calls via an injectable `fetch` — no `@anthropic-ai/sdk` or `openai` npm dependency, matching the same "no SDK, injectable transport" precedent already established by `AngelOneProvider`/`BinanceProvider`. Neither has a real credential configured in this project; both are tested exclusively against injected fake HTTP transports (`scripts/validate-ai-presenter-orchestration.ts`, "ClaudeProvider"/"OpenAIProvider" sections — 17 tests total covering success, HTTP 401/403/429, network failure, malformed JSON, and empty-content rejection).

Anthropic's Messages API has a dedicated top-level `system` field rather than a `"system"` role inside `messages` — `ClaudeProvider.splitSystem()` folds every system-role `AIMessage` into that field, never silently dropping it. OpenAI accepts `role` directly inside `messages`, so no such split is needed.

`lib/ai/env.ts` gained `loadAnthropicEnv()`/`loadOpenAIEnv()`, following the exact same "fail fast, fail loud" throw-based style as the pre-existing `loadGeminiEnv()` — these are a defensive last resort only; the orchestrator's own availability check (§4 below) is what normally prevents them from ever being called with a missing key.

No new `ClaudeIntelligencePresenter`/`OpenAIIntelligencePresenter` classes were created. `GeminiIntelligencePresenter` is reused generically, injected with a `ClaudeProvider`/`OpenAIProvider` instance instead of the default `GeminiProvider` — verified directly (`scripts/validate-ai-presenter-orchestration.ts`, "consistency 2"): the presenter's `.name` reflects whichever real provider it was given, proving it is genuinely provider-generic rather than Gemini-specific in practice, not just in its type signature.

## 3. The AI Presenter Orchestrator

`AIPresenterOrchestratorService` (`services/intelligence/chat/ai-presenter-orchestrator.service.ts`) is the single new seam a chat caller uses instead of calling a presenter directly. It:

1. Builds the real `IntelligenceDecisionContext` once per call (`DecisionContextService.build(envelope)` — unmodified).
2. Iterates a priority-ordered list of `PresenterSlot`s (`{name, isAvailable(), createPresenter()}`).
3. For each slot: skips it (recording `failureCategory: "unavailable"`, never constructing a presenter) if `isAvailable()` is false; otherwise constructs the presenter, calls `.present(envelope, userQuestion)`, and on a genuine (non-empty) response, validates it via the same `validateResponseIntegrity()` D2.6.5 already uses.
4. A valid response is returned immediately — no further providers are tried, and it is never re-validated by a second model.
5. Any failure at any stage (unavailable, construction throw, provider exception, empty response, integrity rejection) advances to the next slot without ever crashing the pipeline.
6. If every configured slot is exhausted, `DeterministicSafeFallbackPresenter` is invoked as the final, always-valid answer — the response the trader receives is **never** an unvalidated LLM answer.

It never computes market intelligence itself — every fact in every output traces back to the `IntelligenceEnvelope` it was handed.

## 4. Provider selection & priority

`DEFAULT_PRESENTER_SLOTS` = `[gemini, claude, openai]`, in that exact, fixed order — matches the sprint's required default priority. Each slot's `isAvailable()` checks only real env-var presence (`GEMINI_API_KEY` / `ANTHROPIC_API_KEY` / `OPENAI_API_KEY`, non-empty after `.trim()`) — a whitespace-only value is treated as absent, never as a valid credential (verified: "availability 8"). This project currently has only `GEMINI_API_KEY` configured; Claude and OpenAI are honestly `"unavailable"` in production today, and the pipeline still functions correctly end to end because of this design, not despite it (verified: "availability 4" — the sole configured slot being unavailable still resolves to the deterministic fallback, never an error).

## 5. Provider fallback behavior

Every rule the sprint required is verified directly:

- An unavailable provider is skipped, never attempted, never constructed (`countingSlot` fixtures assert the presenter factory is called zero times).
- A missing credential is indistinguishable from "unavailable" — both route through the same `isAvailable()` gate.
- Timeout / rate-limit / malformed-response are classified as **provider failures**, not integrity failures — `classifyFailure()` maps a real `AIProviderError.kind` (`auth`/`rate_limit`/`timeout`/`invalid_output`/`network`/`invalid_input`/`invalid_dimensions`/`unknown`) to a `PresenterFailureCategory`, with every kind covered by a dedicated test ("observability 5").
- A provider exception — thrown synchronously during construction or asynchronously during `.complete()` — never crashes the pipeline; it is caught, classified, and the loop proceeds to the next slot on the very same call (verified: "fallback 5" proves no retry of the same slot; "fallback 6" proves a synchronous constructor throw is handled identically to an async rejection).
- All providers failing (or all unavailable) never fabricates an answer — `DeterministicSafeFallbackPresenter` is used, and its output is proven to always itself pass integrity validation (verified: "integrity gate 11").

## 6. Response integrity

No new validation logic was added. The orchestrator calls the exact same `validateResponseIntegrity()` D2.6.5's `presentSafely()` already uses, over the exact same real `IntelligenceDecisionContext`. Verified end-to-end through the orchestrator (not just at the unit level, which D2.6.5's own suite already covers): a genuinely valid response is accepted directly; a fabricated price-like number, a fabricated foreign indicator (e.g. "Stochastic"), an RSI claim with no real `rsi14` computed, a fabricated historical-performance claim, guaranteed-profit language, and the Intelligence Score being restated as a win probability ("85% probability of winning") are all rejected and advance the orchestrator to the next provider (or the deterministic fallback). Over-certainty while a real unresolved evidence conflict exists, and confident language with no hedging while the decision state is `insufficient-intelligence`, are both rejected identically through the orchestrator's own loop.

An empty presenter response is classified as `"malformed-response"` and never even reaches the integrity checker — `integrityPassed` stays `undefined` for that attempt, honestly reflecting that no check was actually performed (verified: "integrity gate 10").

## 7. Deterministic safe fallback

Unchanged from D2.6.5 (`DeterministicSafeFallbackPresenter`) — this sprint did not need to modify it. It is generated entirely from the real `IntelligenceDecisionContext`: current state, regime, supporting/opposing evidence, primary hypotheses, invalidation conditions, risk context, historical validation, Intelligence Score, missing information, and monitoring items are all present in its output (verified section-by-section: "context 2" through "context 7"), and it never invents anything it wasn't given — the "## Risk" and "## Historical Validation" sections state their own real unavailability honestly rather than omitting the section.

## 8. Chat integration

`app/api/private/knowledge/chat/route.ts` (Sprint 15C, frozen) now calls `AIPresenterOrchestratorService.present(envelope, query)` in place of the previous single `presentSafely({presenter: geminiIntelligencePresenter, fallback: deterministicFallbackPresenter, ...})` call. The route still imports **only** the chat-facing layer (`IntelligenceChatContextService`, `AIPresenterOrchestratorService`) — never a 15D/D2.5 internal engine directly — preserving the exact "zero coupling" boundary asserted by 11 separate regression scripts via literal `source.includes()` checks on the route file's full text. All 11 scripts, plus `validate-orchestration` (Sprint 15C's own chat orchestration suite), were re-run after this change and pass with zero regressions.

## 9. Conversation continuity

Fully preserved, unmodified. The orchestrator receives an already-resolved `IntelligenceEnvelope` — conversation-context resolution (D2.6.7's `ConversationContextService`/`IntelligenceChatContextService`) happens entirely upstream, before the orchestrator is ever called. The orchestrator never infers a symbol or timeframe from conversational language; it has no access to conversation history at all, only the envelope it was handed. Verified directly that the orchestrator carries no state across calls: two consecutive `present()` calls on the same orchestrator instance for two different symbols never leak one call's decision context into the other ("context 8"). `scripts/validate-conversation-continuity.ts` (D2.6.7's own 53-test suite) was re-run unmodified and passes with zero regressions.

## 10. Security boundary

- `PresenterAttempt`/`PresenterOrchestrationResult` carry only a closed, documented vocabulary of fields (`provider`, `attempted`, `success`, `latencyMs`, `failureCategory`, `integrityPassed`, `timestamp`, `text`, `presentedBy`, `envelopeGeneratedAt`, `attempts`, `fallbackUsed`) — verified that no credential-shaped field (`key`/`secret`/`token`/`credential`, case-insensitive) ever appears ("security 1", "security 5").
- A provider error's raw message is **never** propagated into the result — only its closed-vocabulary `failureCategory` is. Verified with a fake error message containing a synthetic secret string: the full serialized orchestration result never contains it ("security 2").
- `ClaudeProvider`/`OpenAIProvider` never include the raw API key in their own thrown error messages on an HTTP failure ("security 3", "security 4") — the key is used only in the request header, never echoed back.
- No `.env`/`.env.local` file was modified by this sprint. No credential value is printed by any test, log statement, or committed file.

## 11. Strict AI presentation contract

The sprint asked for a specific system-instruction wording documenting the presenter/integrity boundary. Rather than introduce a second, differently-worded instruction alongside D2.6.5's existing one — which would fragment the single source of truth for what a presenter is told never to do — this sprint deliberately **reuses `GEMINI_PRESENTER_SYSTEM_INSTRUCTION`** (`services/intelligence/chat/gemini-intelligence-presenter.service.ts`, unmodified) for every provider slot, since `GeminiIntelligencePresenter` is now genuinely provider-generic (§2). Its real, verbatim text — sent identically regardless of which underlying `AIProvider` is injected:

> You are a presenter of verified market intelligence.
>
> You must not introduce facts that are absent from the supplied intelligence context.
>
> You must not invent prices, indicators, market conditions, historical outcomes, probabilities, risks, or predictions.
>
> If information is missing or unresolved, say so.
>
> Do not convert a hypothesis into a guaranteed prediction.
>
> Do not present IntelligenceScore as probability of profit.
>
> Do not claim that an analysis guarantees a trading outcome.

Every clause in this instruction is independently, deterministically re-checked by `AIResponseIntegrityService` (§6) — the instruction is the first line of defense; the validator is the second, and the second is what actually gates whether a response reaches the trader.

## 12. Context boundary

The orchestrator (and every presenter it constructs) receives only the already-verified `IntelligenceEnvelope` and the trader's raw question string — never a raw database row, never a provider API key, never write access to the envelope or the underlying engines. `AIPresentationResult`'s shape (`{text, presentedBy, envelopeGeneratedAt}`, D2.5.5, unmodified) structurally cannot carry a new market fact, evidence item, hypothesis, regime, risk level, or historical-validation number back into the system — a presenter can only ever return prose plus provenance metadata about the envelope it was given.

## 13. Observability

Every attempt — successful, failed, or skipped — produces a `PresenterAttempt`: `{provider, attempted, success, latencyMs?, failureCategory?, integrityPassed?, timestamp}`. `latencyMs` is only ever present for a slot that was genuinely attempted — an unavailable slot's attempt has no `latencyMs`, never a fabricated `0` or invented duration (verified: "observability 3"). This is explicitly **presenter reliability metadata only** — `PresenterFailureCategory`/`PresenterAttempt` (`types/ai-presenter-orchestration.ts`) are never read by, or fed into, any Intelligence Score component; the two systems have no shared code path.

## 14. Why LLMs are presenters, not intelligence engines

Repeated from D2.5.5/D2.6.5 because this sprint adds three new LLM backends and the boundary must hold for all of them equally: `AIIntelligencePresenter.present()` returns `AIPresentationResult`, a type with no field capable of expressing a new fact. Every number, claim, regime, hypothesis, and risk level a presenter's prose contains must already exist in the `IntelligenceDecisionContext` it was given, or `AIResponseIntegrityService` rejects it. Adding Claude and OpenAI as alternative wordings of the same real facts does not weaken this boundary — it is enforced identically, per-provider, by the same one validator, not by each provider being separately trusted.

## 15. Why provider ensemble voting is intentionally NOT used

Gemini, Claude, and OpenAI are never asked to independently analyze the market and have their answers compared, averaged, or voted on — that would make the LLMs a second, competing source of market judgment, which is exactly the architecture this whole Intelligence Engine V2 program exists to prevent. Instead: the deterministic `IntelligenceDecisionContext` supplied to every provider is byte-for-byte identical (verified: "consistency 1" — every slot receives the literal same envelope object reference); providers are tried **strictly one at a time, in priority order**, and the loop stops at the first one whose output is genuinely valid. A later provider in the chain is only ever consulted because an earlier one was *unavailable or failed* — never because its answer was compared against another provider's and found wanting. There is no code path anywhere in this sprint that calls two LLM providers for the same request and compares their outputs.

## 16. Failure states

- No provider configured at all (all three env vars absent) → every slot recorded `"unavailable"`, deterministic fallback used, response still fully informative and never blank.
- A configured provider's credential rejected by the real API (HTTP 401/403) → `failureCategory: "authentication"`, next slot tried.
- A configured provider rate-limited (HTTP 429) → `failureCategory: "rate-limit"`, next slot tried.
- A configured provider timing out → `failureCategory: "timeout"`, next slot tried.
- A configured provider returning empty or unparseable content → `failureCategory: "malformed-response"`, next slot tried.
- A configured provider's response containing an unsupported claim → `failureCategory: "integrity-rejection"`, next slot tried — never silently rewritten, never returned to the trader as-is.
- Every slot exhausted → `DeterministicSafeFallbackPresenter`, `fallbackUsed: true`, itself always integrity-valid.

## 17. Testing

`scripts/validate-ai-presenter-orchestration.ts` (`npm run validate:ai-presenter-orchestration`) — 65 assert-based checks plus one conditionally-run live check (66/66 passing in this environment, where `GEMINI_API_KEY` is configured), exceeding the ≥50 requirement:

- **Availability** (8): available/unavailable gating for each named slot, `DEFAULT_PRESENTER_SLOTS`' fixed priority order, real env-var toggling, whitespace-only value rejection.
- **Fallback chains** (6): Gemini→Claude, Gemini→OpenAI (Claude unavailable), Gemini+Claude fail→OpenAI, all fail→deterministic fallback with the exact real formatted text, no same-slot retry, synchronous construction-throw handling.
- **Integrity gating** (11): valid-response acceptance; fabricated price/indicator/RSI/historical-performance/risk/win-probability claims all rejected through the live orchestrator loop (not just the underlying validator in isolation); over-certainty against a real unresolved conflict; confident language against a real insufficient-intelligence state; empty-response handling; the deterministic fallback's own guaranteed validity.
- **Context preservation** (8): symbol, regime, hypotheses, invalidation conditions, historical-validation status, risk context, and missing-information items all reach the final text; no state leakage across two consecutive calls for different symbols.
- **Security** (5): no credential-shaped field in any result object; no raw provider-error message leakage; `ClaudeProvider`/`OpenAIProvider` never echo the real key in a thrown error; no raw prompt/request text in the result.
- **Determinism & observability** (8): identical inputs at a fixed clock produce byte-identical results, including for a rejected/fallback outcome; every attempt shape is well-formed; latency is only ever recorded for genuinely attempted work; every real `AIErrorKind` maps to a documented category; a non-`AIProviderError` exception never crashes the loop.
- **ClaudeProvider** (8) / **OpenAIProvider** (9): constructor throws on a genuinely missing key; correct request shaping (Claude's `system` field split vs. OpenAI's inline `role`); correct response parsing and usage mapping; HTTP 401/403/429 → `auth`/`rate_limit`; network failure → `network`; malformed JSON → `invalid_output`; empty content → `invalid_output`; optional fields omitted (never defaulted) when not supplied.
- **Multi-provider consistency** (2): every slot receives the literal same envelope object; `GeminiIntelligencePresenter` genuinely reflects an injected non-Gemini provider's real name.
- **Live smoke test** (1, conditional): when `GEMINI_API_KEY` is present, a real Gemini call is made through the default orchestrator slot and its outcome (pass or an honest fallback) is asserted; when absent, the test self-skips with an explicit, honest log line — never substituting a fabricated "passed."

Regression: all 11 chat-route zero-coupling scripts, `validate:orchestration` (Sprint 15C), `validate:realtime-intelligence` (D2.6.5, 47/47), and `validate:conversation-continuity` (D2.6.7, 53/53) were re-run after the chat-route change and pass with zero failures.
