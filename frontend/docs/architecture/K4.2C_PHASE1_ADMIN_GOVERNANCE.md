## 2. Analytics — design (K4.2C-D1, LOCKED)

**Reuse finding, not built:** `KNOWLEDGE_CANDIDATE_CREATED`/`_REVIEWED`/`KNOWLEDGE_APPROVED`/`_REJECTED`/`_DEPRECATED` are already named in `KNOWLEDGE_ANALYTICS_CONTRACT.md` §2.2, with the exact instrumentation points listed in §4: `CandidateService.propose()` and `Governance.*`. Phase 1 implements exactly these 5, exactly at those call sites — nothing invented.

**Injection, not import (K4.2-A/B stay untouched):** both `CandidateServiceDeps` and `GovernanceServiceDeps` gain one new field, `analytics?: AnalyticsPort`, **optional** with an internal no-op default when omitted. This means:
- K4.2-A's and K4.2-B's own test files (`validate-k4.2a-candidate-capture.ts`, `validate-k4.2b-governance-approval.ts`) compile and pass **completely unmodified** — they never pass an `analytics` dep, so it defaults to the no-op, so their assertions (which don't check for analytics calls) are unaffected.
- `candidate-service.ts` and `governance-service.ts` themselves **do** gain a few new lines each (the optional field + the `.record(...).catch(() => {})` calls at the existing outcome branches) — this is a real, disclosed touch to K4.2-A/B's *files*, but not to their *locked decisions, contracts, or existing test-observable behavior*. Every existing K4.2-A/B assertion is re-run and must still pass byte-for-byte (§6).

```ts
export interface AnalyticsPort {
  record(userId: string | null, type: string, metadata?: Record<string, unknown>): Promise<void>;
}
```

Emission points (best-effort, never on the write path's critical section — called AFTER the store write has already succeeded, exactly like every other best-effort event in this codebase):

| Event | Service method | Outcome branch |
|---|---|---|
| `KNOWLEDGE_CANDIDATE_CREATED` | `CandidateService.propose()` | `"created"` or `"duplicate-of-active"` (a row was actually written) — never on `idempotent-replay`/`blocked-privacy`/`blocked-invalid` (no new row) |
| `KNOWLEDGE_CANDIDATE_REVIEWED` + `KNOWLEDGE_APPROVED` | `GovernanceService.approve()` | `"approved"` |
| `KNOWLEDGE_CANDIDATE_REVIEWED` + `KNOWLEDGE_REJECTED` | `GovernanceService.reject()` | `"rejected"` |
| `KNOWLEDGE_DEPRECATED` | `GovernanceService.deprecate()` | `"deprecated"` |
| `KNOWLEDGE_APPROVED` | `GovernanceService.publishNewVersion()` | `"new-version-published"` (K0.2 §4.2: `active → active(v+1)` is a `KNOWLEDGE_APPROVED`-class transition) |

`archive()`/`reinstate()` are not in K0.6's event vocabulary and none is invented for them.

## 3. Admin read queries (K4.2C-D2, LOCKED — new file, zero A/B touch)

Neither `CandidateStorePort` nor `GovernanceStorePort` (K4.2-A/B) expose a **list** capability — they were built exactly to their own sprints' needs (create + point-lookups only). Rather than extend those locked ports (which would touch K4.2-A/B's files for a concern that's purely Phase-1's own), Phase 1 adds one new, self-contained, **read-only** file: `services/knowledge-loop/governance/admin-queries.ts`. It queries `prisma.knowledgeCandidate` / `prisma.knowledge` directly for listing and detail reads — no mutation capability, nothing K4.2-A/B's stores don't already independently guarantee is safe to read. This keeps K4.2-A/B at zero diff for this phase's read needs.

## 4. Admin routes (K4.2C-D3, LOCKED)

All `requireAdmin`-gated (identical gate as every existing admin route), delegating to the **existing, unmodified** `createCandidateService()`/`createGovernanceService()` factories (K4.2-A/B) for every write, and the new `admin-queries.ts` for reads:

| Route | Method | Delegates to |
|---|---|---|
| `/api/private/admin/knowledge-loop/candidates` | GET | `admin-queries.listCandidates` |
| `/api/private/admin/knowledge-loop/candidates/[id]` | GET | `admin-queries.getCandidateDetail` |
| `/api/private/admin/knowledge-loop/candidates/[id]/approve` | POST | `GovernanceService.approve()` |
| `/api/private/admin/knowledge-loop/candidates/[id]/reject` | POST | `GovernanceService.reject()` |
| `/api/private/admin/knowledge-loop/knowledge` | GET | `admin-queries.listKnowledge` |
| `/api/private/admin/knowledge-loop/knowledge/[id]/deprecate` | POST | `GovernanceService.deprecate()` |

`archive`/`reinstate`/`publishNewVersion` routes are **not** built in Phase 1 (not in the owner's explicit C1 item list) — `GovernanceService` already supports them (K4.2-B), so adding routes for them later is a small, isolated addition, not a redesign.
