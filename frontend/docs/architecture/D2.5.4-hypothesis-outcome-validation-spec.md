# D2.5.4 — Hypothesis Outcome & Historical Validation Engine

**Status:** Implemented and tested. This is the authoritative contract for later scheduler/UI work.
**Scope:** Evaluating already-generated `Hypothesis` objects (D2.5.3) against real subsequent market data, and aggregating the resulting outcomes into honest historical statistics. No ML, no LLM reasoning, no new indicator math, no cron/queue/worker infrastructure, no Intelligence Score, no trading signals. `MarketState` (D2.5.2), `Regime` (D2.5.2), `Hypothesis` (D2.5.3), and D2.5.1's own `IntelligenceAnalysisRun`/`IntelligenceAnalysisOutcome` persistence and `outcome-evaluator.service.ts` are unmodified — this sprint only adds to them.

---

## 1. Outcome lifecycle

Every hypothesis evaluation resolves to exactly one of four `IntelligenceAnalysisOutcomeStatus` values (unchanged enum from D2.5.1, `types/intelligence-analysis-outcome.ts`):

```
pending -> validated | invalidated | inconclusive
```

`pending` is not itself persisted by `HypothesisOutcomeEvaluatorService` — it is a **transient computation result** returned by `evaluateHypothesis()` when the prediction window has not yet closed (see §2). `evaluateAnalysisRun()` only calls `IntelligenceAnalysisOutcomeService.createOutcome()` (persists a row) once a real, conclusive verdict exists: `validated`, `invalidated`, or `inconclusive`. A hypothesis whose window hasn't closed simply produces no outcome row yet — it is re-evaluated on a later call, exactly as often as the future caller (see §14) chooses to invoke it. This avoids persisting a `pending` row that would immediately be stale.

`validated`/`invalidated` were declared in D2.5.1's schema but structurally unreachable until this sprint (D2.5.1's own `outcome-evaluator.service.ts` only ever produced `pending`/`inconclusive`, since no `Hypothesis` existed yet). `HypothesisOutcomeEvaluatorService` (`services/intelligence/hypothesis/hypothesis-outcome-evaluator.service.ts`) is the first code in this codebase that reaches them — via a **separate, new service**, not a modification of D2.5.1's evaluator, which remains byte-identical and still handles runs with no hypothesis.

## 2. Evaluation timing

```
evaluationDue = createdAt + (predictionWindow.candles * timeframeDurationMs(predictionWindow.timeframe))
```

Implemented in `evaluationDueAt()`. `createdAt` is always the REAL, persisted `IntelligenceAnalysisRun.createdAt` (the actual DB insert time), never a value re-derived from today's clock. `candlesToMs()` multiplies the hypothesis's own `statement.predictionWindow.candles` by a documented, exact `TIMEFRAME_MS` lookup (`1m`→60,000ms … `1w`→604,800,000ms) — never a silent reinterpretation of "N candles" as "N minutes." A hypothesis whose `predictionWindow` is `{ candles: 20, timeframe: "1h" }` is due in exactly 20 hours; `{ candles: 5, timeframe: "1h" }` (breakout confirmation) in exactly 5 hours.

`clock.now() < evaluationDueAt` → `pending`, with `evaluationBasis.source: "window-not-closed"` recording the exact due timestamp. This is the only branch that never touches a `TimeSeriesProvider` — no point fetching data for a window that hasn't closed.

## 3. Historical data requirements

The codebase has **no capability** to request historical OHLC candles ending at an arbitrary past timestamp — `TimeSeriesRequest` (`types/market-candle.ts`) only accepts `{symbol, interval?, outputSize?}`, and every real `TimeSeriesProvider` implementation fetches the latest N candles as of *now*. Rather than add a new provider capability (out of scope — the sprint's own instructions treat the market-data layer as frozen unless a real gap forces a change, and this gap has an honest fallback), the evaluator:

1. Requests `EVALUATION_LOOKBACK_BUFFER_CANDLES (60) + predictionWindow.candles + 10` candles from `TimeSeriesProvider.getTimeSeries()` — the existing, unmodified "latest N from now" call.
2. Locates the real candle at/after `createdAt` (`creationIdx`) and the real candle at/after `evaluationDueAt` (`evalIdx`) by timestamp matching (`>=`) within the returned, oldest-first series.
3. If either index is not found (`-1`) — the fetched window doesn't reach back far enough — returns `inconclusive` with `evaluationBasis.source: "insufficient-historical-data"`, citing the fetched series' actual date range versus the required one. **Never fabricates, interpolates, or substitutes today's price for a missing historical point.**
4. If the provider throws, or returns zero candles, returns `inconclusive` with `source: "provider-unavailable"`.

`EVALUATION_LOOKBACK_BUFFER_CANDLES = 60` exists so that, when a point-in-time invalidation check needs to reconstruct a real historical `MarketState` (§5), enough real preceding candles exist for `MarketStateService`'s own EMA50 to compute — matching `MarketStateService.EMA_SLOW_PERIOD` with margin.

## 4. Evaluation formulas

```
actualPriceMovePct = ((evaluationPrice - creationPrice) / creationPrice) * 100
```

- `creationPrice` — read directly from the persisted `HypothesisSnapshot.marketState.snapshot.price` (§8). **Never** re-derived from the freshly-fetched candle series, even though that series happens to contain a candle at the creation timestamp.
- `evaluationPrice` — the real `close` of the candle at `evalIdx` (the evaluation-boundary candle) in the freshly-fetched series.
- Signed: positive for a price increase, negative for a decrease. `null` whenever `pending`/`inconclusive` (prices genuinely unavailable or the window hasn't closed) — never `0` as a stand-in for "unknown."

Computed once per hypothesis, in the same branch that produces `validated`/`invalidated` — `pending` and `inconclusive` results always carry `actualPriceMovePct: null`.

## 5. Invalidation semantics

`InvalidationCondition.comparator` (D2.5.3) selects one of two structurally distinct check strategies — both read the hypothesis's own **stored** `referenceValue`, never a boundary recalculated from today's data (§12):

**Point-in-time (`equals` / `not-equals`)** — used by `trend-continuation-*`, `range-continuation`, `volatility-expansion`/`contraction`. A real historical `MarketState` is reconstructed exactly AT the evaluation-boundary candle, by feeding `EVALUATION_LOOKBACK_BUFFER_CANDLES` real preceding candles into the **unmodified** `MarketStateService.assemble()` — reuse, not a new indicator engine. `readField()` (a dot-path reader, e.g. `"structure.trend.direction"`) pulls the actual field value off that reconstructed state, and `pointInTimeBreach()` compares it against the stored `referenceValue` string-wise.

**Intra-window scan (`crosses-below` / `crosses-above`)** — used by `breakout-confirmation-*`. Every real candle's `low` (or `high`) across the **entire window** `[creationIdx, evalIdx]` is checked against the stored numeric boundary (e.g. the real `recentRange.high` captured at creation time — §3 of the D2.5.3 spec). A breach counts even if price later recovers above/below the boundary by the final evaluation candle — an endpoint-only check would silently miss a real, already-happened invalidation. Verified by a dedicated regression case: price dips below the boundary on candle 2 of a 5-candle window, recovers by candle 5, and the evaluator still correctly reports `invalidated`.

`invalidationObserved: boolean` is recorded verbatim in `evaluationBasis` regardless of which strategy produced it.

## 6. Validation semantics

`status = invalidationObserved ? "invalidated" : "validated"`. There is no independent, separate "did the price move in the predicted direction" check — validation is defined **exclusively** by the hypothesis's own falsifiable claim (its stored `invalidationCondition`), never by a generic "price went up = bullish hypothesis validated" heuristic. A `trend-continuation-bullish` hypothesis is `validated` because `structure.trend.direction` was still `"up"` at the evaluation boundary — not merely because price happened to be numerically higher.

## 7. Inconclusive semantics

`inconclusive` is a **legitimate, first-class terminal state** — never silently converted to `validated`/`invalidated` to inflate a sample, and never treated as a "soft failure." It is reached only through explicit, named causes, each recorded in `evaluationBasis.source`:

| `source` | Cause |
|---|---|
| `insufficient-historical-data` | The fetched candle series doesn't cover `[createdAt, evaluationDueAt]` |
| `provider-unavailable` | The `TimeSeriesProvider` threw, or returned zero candles |
| `no-hypothesis-snapshot` | The `IntelligenceAnalysisRun` predates D2.5.4 or was captured with no real hypothesis — nothing for this evaluator to evaluate |

`evaluateAnalysisRun()` on a run with no `hypothesisSnapshot` persists exactly one `inconclusive` outcome with `hypothesisId: null` rather than throwing or silently skipping the run — an honest, explicit record that evaluation was attempted and genuinely couldn't produce a verdict.

## 8. Creation-time snapshot principle

`IntelligenceAnalysisRun.hypothesisSnapshot` (new, nullable `Json` column — additive to D2.5.1's schema) stores the complete, real `HypothesisSnapshot` (`types/intelligence-hypothesis-snapshot.ts`): the actual `MarketState`, `Regime`, and `Hypothesis[]` that existed at generation time, plus a `capturedAt` timestamp. This is "what the system actually knew at that moment" made concrete and persisted verbatim — not a pointer that could later resolve to different data, and not a value the evaluator ever recomputes from today's live `MarketState`/`Regime`.

Every place the evaluator needs a creation-time value — `creationPrice` (§4), the invalidation boundary (§5), the prediction window (§2) — reads it from this stored snapshot or the hypothesis's own `statement`, never from a fresh call to `MarketStateService`/`RegimeService`/`HypothesisService`. The only *new* computation this sprint's evaluator ever performs against fresh data is reconstructing a `MarketState` **at the historical evaluation boundary** (§5) — a real past point, not today.

## 9. Historical validation aggregation

`HistoricalValidationService.buildHistoricalValidation()` (`services/intelligence/memory/historical-validation.service.ts`) is a dedicated, read-only aggregation service — it never itself decides `validated`/`invalidated`/`inconclusive` (that is exclusively `HypothesisOutcomeEvaluatorService`'s job); it only counts already-persisted `IntelligenceAnalysisOutcome` rows, scoped to one `{symbol, timeframe, regimeType, hypothesisType}` segment (`types/intelligence-historical-validation.ts#HistoricalValidationKey`) and one `userId`.

`hypothesisType`/`regimeType` are new, additive, indexed columns on `IntelligenceAnalysisOutcome` (denormalized copies of the evaluated `Hypothesis.type`/`Hypothesis.regimeContext.regimeType`), added purely so this query can filter without a fragile join into `hypothesisSnapshot`'s JSON.

## 10. Minimum sample size

```ts
export const MIN_HISTORICAL_VALIDATION_SAMPLE = 30;
```

A conventional "small sample" statistics threshold — an explicit, documented architecture decision, **not** empirically tuned against this platform's own outcome data (there isn't nearly enough of it yet to tune against; doing so would be circular). `sampleSize = validatedCount + invalidatedCount` — **`inconclusiveCount` is deliberately excluded** from both the sample size and the rate's denominator (see §11 for why), and is reported alongside it for transparency.

`validatedRate` is `undefined` whenever `sampleSize < MIN_HISTORICAL_VALIDATION_SAMPLE`. **Never `0`.** `0%` would assert "real evidence exists that this always fails" — a claim exactly as strong and exactly as false as reporting a high rate off five lucky samples. `undefined` means "not enough real evidence exists yet," and the two must never be confused. Verified directly: a segment with 5/5 validated (a real 100% rate, were it reported) still returns `validatedRate: undefined` below threshold.

## 11. Statistical interpretation

`validatedRate` means **only**: *"the percentage of completed, objectively evaluated historical hypotheses in this exact segment that satisfied their own defined validation condition."* It is never presented, internally or in any future UI, as:

- a probability of future profit or future price movement,
- a win rate, expected return, or trading edge,
- a guarantee, forecast, or confidence score for what will happen next.

`inconclusiveCount` is excluded from `sampleSize`/`validatedRate`'s denominator because an inconclusive result carries **zero evidence** about whether the hypothesis's claim was right — folding it into the denominator (as an implicit "didn't validate") would understate the true rate; folding it into the numerator would overstate it. Either direction is a form of statistical dishonesty this sprint's brief explicitly rules out. Reporting it as a separate, visible count instead is the honest alternative.

## 12. No-future-leakage rule

The sprint's own non-negotiable principle, restated as the concrete rules this codebase enforces:

1. `creationPrice`, the invalidation boundary/`referenceValue`, and the prediction window are **always** read from data stored at creation time (§8) — never recalculated from a `MarketState`/`Regime` computed today.
2. The only fresh computation the evaluator performs (§5's point-in-time reconstruction) targets the real **historical** evaluation-boundary candle — never "now."
3. `HistoricalValidationService` only reads already-finalized `IntelligenceAnalysisOutcome` rows — it has no code path that peeks at a run's current, live market data.

Verified by a dedicated regression case that deliberately corrupts the "creation" candle inside the freshly-fetched series (setting its close to an absurd `999`) and confirms the evaluator's reported `creationPrice`/`actualPriceMovePct` are unaffected — proof the evaluator never re-derives `creationPrice` from the fetched series, only from the stored snapshot.

## 13. Immutability

`HypothesisOutcomeEvaluatorService` never calls `IntelligenceAnalysisOutcomeService.updateOutcomeStatus()` on an already-finalized outcome. Every evaluation attempt that reaches a conclusive verdict appends a **new** row via `createOutcome()` — historical evidence is never mutated in place, and re-running an evaluation never silently overwrites a prior finding. `updateOutcomeStatus()` (D2.5.1) still exists on the service for narrow, explicit correction use cases, but this evaluator does not call it. A future genuine-correction mechanism (e.g. a provider returned bad data and needs a documented fix) would need its own explicit, traceable superseding-record design — not built in this sprint.

Verified directly: after `evaluateAnalysisRun()` persists an outcome, the run's own `hypothesisSnapshot` is re-fetched and confirmed unchanged (same hypothesis count, same symbol) — the original analysis context is never touched by evaluation.

## 14. Future scheduler integration

No cron, queue, worker, Redis, or BullMQ is added in this sprint, per the sprint's explicit instruction. `HypothesisOutcomeEvaluatorService` exposes three plain, callable, `async` methods for a future scheduler/route to invoke:

- `evaluateHypothesis(input)` — evaluates one hypothesis against real historical data. Pure computation; persists nothing.
- `evaluateAnalysisRun(analysisRunId, userId, deps)` — evaluates every hypothesis in one run's stored snapshot, persists one outcome row per hypothesis, flips the run to `evaluationStatus: "evaluated"` once every produced outcome is conclusive (no outcome left `pending`).
- `evaluatePendingAnalysisRun(userId, deps, limit)` — evaluates every one of a user's still-pending runs that has a real D2.5.4 `hypothesisSnapshot` (runs with none are left to D2.5.1's own evaluator, unmodified).

A future scheduler only needs to call `evaluatePendingAnalysisRun()` on an interval, injecting a real `TimeSeriesProvider` — no redesign of this contract required.

## Verified against the real services, not just designed on paper

`scripts/validate-hypothesis-outcome.ts` (20 tests) exercises `HypothesisOutcomeEvaluatorService` and `HistoricalValidationService` end-to-end through the real, unmodified `MarketStateService` → `RegimeService` → `HypothesisService` chain (no mocked indicator math), using fixture candle sequences copied verbatim from `scripts/validate-hypothesis-engine.ts` (already verified there) plus two new breakout fixtures whose exact numeric boundary (`recentRange.high ≈ 1.10104`) was empirically probed against the real services before being locked into the test file — the same discipline established in D2.5.2/D2.5.3. One genuine test-authoring bug was caught and fixed during this process: the persistence end-to-end test initially anchored its injected candle series to a synthetic fixture timestamp rather than the real, DB-assigned `IntelligenceAnalysisRun.createdAt` that `evaluateAnalysisRun()` actually searches against — not a service defect, but exactly the kind of subtle timing mismatch this sprint's no-future-leakage discipline is designed to catch early.
