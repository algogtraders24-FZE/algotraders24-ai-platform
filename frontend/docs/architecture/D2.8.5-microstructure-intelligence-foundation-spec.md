# D2.8.5 — Microstructure Intelligence Foundation

**Status:** Implemented and tested. **Baseline:** D2.8.4 (`8fa235f`).
**Scope:** A provider-neutral microstructure evidence contract, a deterministic calculation layer, freshness/validation reusing D2.6.4 conventions, and a real (REST-only) Binance adapter extension confirming the whole pipeline against real payload shapes. **Foundation only** — nothing here is wired into IntelligenceScore, MarketState, Regime, Hypothesis, or DecisionContext, and no trading signal/execution capability exists anywhere in this sprint.

---

## 1. Architecture decision (Phase 1)

Read fresh before writing anything: `types/market-snapshot.ts`, `types/market-data-provider.ts` (the `SnapshotProvider`/`TimeSeriesProvider` additive-interface pattern), `services/market-data/market-data.service.ts`, `services/market-data/freshness-policy.service.ts`, `services/market-data/market-snapshot-integrity.service.ts`, `types/provider-reliability.ts`, `lib/market-data/providers/binance.provider.ts`, `lib/market-data/providers/angel-one.provider.ts`.

**Conclusion: no existing abstraction needed to be redesigned.** `MarketSnapshot` is the OHLC/quote model every consumer already depends on; it was left untouched. The exact pattern that already exists for adding a capability without disturbing anything else — `SnapshotProvider`/`TimeSeriesProvider` as **additive, duck-typed interfaces** detected at runtime via `isSnapshotProvider()`/`isTimeSeriesProvider()` — is the pattern this sprint reuses verbatim for microstructure: a new `MicrostructureProvider` interface (`types/microstructure-provider.ts`) and a matching `isMicrostructureProvider()` guard, with zero changes to `types/market-data-provider.ts` itself.

The smallest safe extension point was therefore: (1) a new, standalone type contract (`types/microstructure.ts`), (2) a new, standalone deterministic calculation/validation layer (`lib/microstructure/*`), (3) one new method (`getMicrostructureSnapshot()`) added to the existing `BinanceProvider` class, reusing its existing `fetchImpl`/`resolveSymbol()`/`MarketDataProviderError` machinery, and (4) a small, separate orchestrator (`services/microstructure/microstructure-snapshot.service.ts`) that is never wired into `MarketDataService`'s own provider-priority/fallback loop.

**Why no priority/fallback chain for microstructure:** `MarketDataService.getSnapshot()`'s whole point is that any configured provider can serve an OHLC/quote for the same instrument — that is legitimate, since a quote is a quote. Microstructure evidence is different: D2.8.2/D2.8.3/D2.8.4 all independently established that order-book/tick data is **inherently venue-specific** (a Binance order book is not interchangeable with an Angel One or Dukascopy one for the same nominal instrument). Building a priority/fallback chain here would have meant silently substituting one venue's microstructure for another's — exactly the fabrication risk those three prior sprints spent their whole scope warning against. `MicrostructureSnapshotService.getSnapshot()` therefore takes an explicit, single provider argument, never a list, and never falls back.

## 2. Microstructure contract (Phase 2)

`types/microstructure.ts` — new, standalone, zero dependency on `MarketSnapshot`:

- **`CapabilityState`** — the five-state vocabulary the sprint requires: `"available" | "unavailable" | "not_supported_by_provider" | "stale" | "invalid"`.
- **`MicrostructureField<T>`** — `{ state: CapabilityState; value?: T; reason?: string }`. `value` is present only for `"available"`/`"stale"`; every other state carries a `reason`, never a silent gap.
- **Raw evidence** (`RawMicrostructureEvidence`): `bid`, `ask`, `bidLevels`, `askLevels` (`MicrostructureOrderBookLevel[]` — `{price, quantity}`), `trades` (`MicrostructureTrade[]` — `{price, quantity, timestamp, aggressorSide}`), `sequenceId`. Every one of these is a `MicrostructureField`, never a bare optional.
- **Derived data** (`DerivedMicrostructure`): `midPrice`, `spread`, `bidDepth`, `askDepth`, `depthImbalance`, `buyVolume`, `sellVolume`, `volumeDelta`, `liquidityConcentration` — each also a `MicrostructureField`.
- **`MicrostructureSnapshot`** — the complete, ready-to-consume shape: symbol/provider/assetClass/timestamp/retrievedAt/freshnessStatus + `evidence` + `derived` + `generatedAt`/`version`.

## 3. Capability-state semantics

`hasValue(field)` (`lib/microstructure/microstructure-field.ts`) is the one gate every calculation function uses before reading `.value` — true only for `"available"`/`"stale"`. `propagateState()` carries the most informative upstream state into a dependent field: a depth figure derived from a `"not_supported_by_provider"` order book itself reads `"not_supported_by_provider"`, not a generic `"unavailable"`; one derived from an `"invalid"` book reads `"invalid"`. `volumeDelta = unavailable` is never confused with `volumeDelta = 0` anywhere in this codebase — reconfirmed explicitly by test 20 (§9).

## 4. Deterministic formulas (Phase 3)

All in `lib/microstructure/microstructure-calculation.ts`, pure, no I/O, no LLM call anywhere in this module:

```
midPrice          = (bid + ask) / 2                                    [both bid, ask available]
spread             = ask - bid                                          [both available, ask >= bid]
bidDepth/askDepth = sum(level.quantity for level in levels)            [levels available]
depthImbalance     = (bidDepth - askDepth) / (bidDepth + askDepth)      [denominator > 0]
buyVolume          = sum(trade.quantity where trade.aggressorSide == "buy")
sellVolume         = sum(trade.quantity where trade.aggressorSide == "sell")
volumeDelta         = buyVolume - sellVolume                            [both available]
liquidityConcentration = (top-3-levels quantity, both sides) / (total quantity, both sides)  [total > 0]
```

`buyVolume`/`sellVolume` never generalize Binance's `isBuyerMaker` semantics to any other provider — the mapping happens exactly once, inside `BinanceProvider.getMicrostructureSnapshot()` (§5), and `computeAggressorVolumes()` itself only ever reads each trade's own already-mapped `aggressorSide` field, honestly `"unavailable"` for a provider that never supplies one.

## 5. Binance adapter behavior (Phase 4)

Extended, not duplicated: `lib/market-data/providers/binance.provider.ts` gained one new public method (`getMicrostructureSnapshot()`) and two new private helpers (`fetchDepth()`, `fetchRecentTrades()`), reusing the class's existing `request<T>()`, `resolveSymbol()`, `TtlCache`/`Clock` conventions, and `MarketDataProviderError` classification — no second Binance client exists anywhere.

- **`GET /api/v3/depth?symbol=X&limit=10`** — REST order-book snapshot (10 levels each side), the same endpoint D2.8.3 live-verified. Best bid/ask is taken directly from `bids[0]`/`asks[0]` (no separate `bookTicker` call needed).
- **`GET /api/v3/trades?symbol=X&limit=50`** — REST recent-trade tape, including Binance's real `isBuyerMaker` flag. Mapped exactly per Binance's own documented meaning: `isBuyerMaker === false` → the buy side was the taker/aggressor → `"buy"`; `isBuyerMaker === true` → `"sell"`.
- **REST only** — no WebSocket client was added anywhere in production code; D2.8.3's WebSocket captures were disposable research, never infrastructure, and adding one now was an explicit non-goal.
- **Not cached** — unlike `getSnapshot()`/`getTimeSeries()`, this method has no TTL cache, since this sprint adds no repeated/scheduled caller that would benefit from one; a future consumer can add caching at its own layer without touching this method.
- **The adapter never decides a trading action** — it returns `RawMicrostructureResult` only; every derivation happens downstream in `lib/microstructure/microstructure-calculation.ts`.

## 6. Freshness/validation rules (Phase 5)

`lib/microstructure/microstructure-validation.ts` reuses `assessFreshness()` (`services/market-data/freshness-policy.service.ts`, D2.6.4) **verbatim** for the fresh/stale/unknown classification — no competing freshness system was created. One gap in `assessFreshness()` itself is compensated for here rather than by modifying that file: it clamps a negative age to 0 (a future timestamp would read as "perfectly fresh"), so `assessMicrostructureFreshness()` adds exactly one extra check — a timestamp more than 5 seconds in the future is classified `"invalid"` before `assessFreshness()` is ever consulted.

Structural validation (never "fixed by guessing", always rejected outright):

- **Missing bid/ask** → both `"unavailable"`.
- **Invalid bid/ask** (non-finite, non-positive) → both `"invalid"`.
- **Crossed market** (`ask < bid`) → both `"invalid"`, never swapped/clamped into a valid-looking pair.
- **Negative/non-finite quantities** anywhere in an order-book level → the **whole side** (`bidLevels`/`askLevels`) is `"invalid"`, not silently dropped-and-continued (a partial book with an unknown gap could distort depth/imbalance more dangerously than an honest failure).
- **Malformed sequence/update identifier** (non-numeric) → `"invalid"`.
- **A single malformed trade row** is dropped from the trades array (never fabricated), but the array itself is `"invalid"` only if *every* row fails to parse.

## 13. Known limitations

- Angel One and Dukascopy remain exactly as unverified/research-only as D2.8.3/D2.8.4 left them — this sprint's registry documents that honestly rather than closing the gap (closing it was explicitly out of scope: "Do NOT... Angel One integration... Dukascopy integration").
- `liquidityConcentration`'s top-3-levels formula is one reasonable, documented, deterministic choice among several possible windowings — a future sprint could parameterize or reconsider it once a real consumer exists; it is not claimed as the only correct definition.
- No caching layer exists for `getMicrostructureSnapshot()` — a future production consumer calling it frequently would need to add its own, at whichever layer actually needs it (not decided here, per this sprint's foundation-only scope).
- The Binance adapter's REST snapshot (`/depth` + `/trades`, called together via `Promise.all`) is not perfectly atomic — the two calls can observe the book microseconds apart. This is disclosed here rather than hidden; a future sprint wanting stricter atomicity would need Binance's diff-depth WebSocket stream (D2.8.3's own research), which remains explicitly out of production scope.
