# D2.6.6 — Indian Market Data Fabric & Angel One Live Validation

**Status:** Implemented and tested. Makes Indian instruments (NIFTY 50, NIFTY Bank, RELIANCE, TCS, INFY, HDFCBANK) a first-class, capability-routed part of the existing D2.6.3/D2.6.4 data fabric.
**Scope:** Extends existing contracts only — no new provider adapter, no rebuild of any prior sprint's architecture.

---

Every box above is either untouched or additively extended. No file from D2.5.1 through D2.6.5 had its own logic rewritten — MarketState/Regime/Hypothesis/IntelligenceScore/DecisionContext/AIPresenter remain fully provider-neutral, exactly as sprint §17 requires.

## 2. Angel One integration

`AngelOneProvider` (`lib/market-data/providers/angel-one.provider.ts`) was **not rebuilt** — the D2.6.3 audit (this sprint's own §1 requirement) found it already implements both `SnapshotProvider` (`getLtpData`) and `TimeSeriesProvider` (`getCandleData`), contrary to an initial assumption that candles needed building. This sprint's only change to this file's *behavior* is zero — the file is unmodified. What changed is coverage: `AngelOneProvider.getTimeSeries()`/`getCandleData` had **zero test coverage** before this sprint (confirmed by reading every existing `validate:*` script); `scripts/validate-indian-market-data.ts` now covers candle parsing, interval-enum correctness, cache behavior, malformed-row filtering, and every relevant error path (auth, rate_limit, http_error, unsupported_symbol) against fake transport.

## 3. Authentication boundary

D2.6.3-D2.6.5 deliberately never attempted a live authenticated Angel One call — a real login against a live brokerage account is an external, hard-to-reverse action, reserved for the user's own explicit go-ahead rather than a coding agent's default. This sprint's main test suite continues to exercise the adapter only against fake/injected HTTP responses by default — a separate, clearly gated `liveAngelOneSmokeTest()` function exists at the bottom of `scripts/validate-indian-market-data.ts`, disabled unless `RUN_LIVE_ANGEL_ONE_SMOKE_TEST=1` is explicitly set.

**This sprint, the user explicitly authorized running it**, and it was run once, live, on 2026-08-11 against the real account (data-access only — no order/execution call exists anywhere in this file or this sprint's additions):

```
=== LIVE ANGEL ONE SMOKE TEST ===
  authenticated + NIFTY 50 quote: PASS (price 24435.45)
  BANKNIFTY quote: PASS (price 57261.25)
  NSE equity (RELIANCE) quote: PASS (price 1318.8)
  historical candles (NIFTY50, 1d): PASS (count 3)
  timestamp freshness: PASS (status "fresh")
```

All five checks genuinely passed against the live API using the project's own real credentials — the adapter's documented-contract implementation (login, TOTP, quote parsing, candle parsing, freshness) is now confirmed correct end to end, not just structurally plausible. One honest observation, not a failure: the daily-candle request returned 3 candles for a 5-candle request — `candleWindow()`'s date-range sizing (flagged as unverified in the file's own header before this sprint) appears to under-deliver somewhat against a real response, plausibly consistent with weekend/non-trading-day sparsity in a short calendar window, but not conclusively diagnosed this sprint. This remains a documented limitation (§14), not silently claimed as fully solved.

## 4. Instrument mapping

Six real `CanonicalInstrument` entries now exist in `lib/market-data/instrument-catalog.ts`, each with a real Angel One token confirmed against the same public, unauthenticated scrip master (`https://margincalculator.angelbroking.com/OpenAPI_File/files/OpenAPIScripMaster.json`) already used for NIFTY50/RELIANCE in D2.6.3:

| id | providerSymbol | token | type |
|---|---|---|---|
| NIFTY50 | `Nifty 50` | `99926000` | index (AMXIDX) |
| BANKNIFTY | `Nifty Bank` | `99926009` | index (AMXIDX) |
| RELIANCE | `RELIANCE-EQ` | `2885` | equity |
| TCS | `TCS-EQ` | `11536` | equity |
| INFY | `INFY-EQ` | `1594` | equity |
| HDFCBANK | `HDFCBANK-EQ` | `1333` | equity |

No token was invented — each was looked up directly in a freshly-downloaded copy of the real scrip master (152,555 real instruments), and the two index entries were specifically matched against the `instrumenttype: "AMXIDX"` cash-index variant (not the plain futures-style `BANKNIFTY`/`26009` entry the same file also contains, which is a different real instrument) — the same convention NIFTY50's own already-verified `99926000` entry uses.

**Confirmed real gap fixed**: `IntelligenceQueryService.resolveSymbol()` (D2.6.2) checks `isKnownMarket()` against `lib/market-data/market-registry.ts` — a separate, older, lighter table than the D2.6.3 catalog. Before this sprint, that registry had zero Indian entries, so a chat question mentioning "NIFTY" could never resolve a symbol at all, even though the instrument was fully fetchable via `MarketDataService`. Fixed by adding the same six symbols to `market-registry.ts` (`enabled: true`, since Angel One genuinely serves them) — exactly the "data change here plus a provider mapping" extension point that file's own header already described, never a redesign. `SYMBOL_ALIASES` (`services/intelligence/query/intelligence-query.service.ts`) gained `nifty`/`nifty50`/`banknifty`/`infosys` — TCS/INFY/HDFCBANK/RELIANCE/BANKNIFTY already resolve without an alias because their raw uppercased token exactly equals their registry symbol id.

**Known limitation**: the existing `resolveSymbol()` tokenizer matches single words only. "bank nifty" (two words) cannot be distinguished from "nifty" alone — "banknifty" (no space) is the reliable free-text form. This is a pre-existing, documented property of the D2.6.2 tokenizer design, not something this sprint redesigns.

## 5. Provider capabilities

New: `lib/market-data/provider-capabilities.ts` — a general, provider-level `ProviderCapabilityProfile` (`supportedExchanges?`, `supportedCountries?`, `supportedAssetClasses`, `supportedMarketCategories`, plus realtime/historical/search flags) for each of the four configured providers, making rules like "Angel One only ever serves NSE/BSE, India, index/equity instruments" an explicit, documented, testable fact rather than an emergent property of which catalog entries happen to omit which provider.

`providerSupportsInstrument(providerName, instrument)` is pure and deterministic: a provider with **no registered profile** is never more restricted than before this sprint (falls through to `true`, leaving the catalog's own `providerMappings` as the sole gate — D2.6.4's exact existing behavior, unaffected). A registered profile can only ever further **exclude** an instrument, never grant one the catalog doesn't already map.

## 6. Routing / fallback

Wired additively into `orderProviders()` (`services/market-data/provider-reliability.service.ts`) — the existing capability-exclusion step (`available = ...`) now ANDs the catalog-mapping check with `providerSupportsInstrument()`. Sprint §7's required order was already correct in D2.6.4's existing implementation and is unchanged: canonical instrument resolution → capability filtering (exclude) → health/cooldown filtering (deprioritize, never exclude) → reliability ranking → request → integrity/freshness validation → fallback. Verified directly: NIFTY50/BANKNIFTY/TCS/INFY/HDFCBANK ordering never includes Binance/Twelve Data/Alpha Vantage; BTCUSD ordering never includes Angel One. A hypothetical future second Indian provider needs only a catalog entry — proven by a test that adds an unmapped `"future-indian-provider"` and confirms it's correctly excluded (not because of hardcoded logic, but because no mapping exists), demonstrating the real extension seam without fabricating one.

## 7. Data integrity

No new integrity system was built. `validateSnapshotIntegrity()`, `assessFreshness()`, `compareSnapshots()`/`summarizeConflicts()` (all D2.6.4, unmodified) are applied directly to Indian fixtures in this sprint's test suite: symbol-identity, timestamp, price-validity, and freshness checks all behave identically for INR-denominated instruments as for any other asset class — `assessFreshness`'s existing `indices`/`stocks` category thresholds (5 minutes) already applied correctly to NIFTY50/RELIANCE with zero changes needed. A genuine two-provider price disagreement on NIFTY50 is preserved as `unresolved-conflict`, never silently resolved.

## 8. Freshness

Reused verbatim from D2.6.4's `QUOTE_FRESHNESS_THRESHOLD_MS` — `indices`/`stocks` both use the existing 5-minute threshold, which already applied to NIFTY50/RELIANCE before this sprint and now applies identically to the four new entries. No India-specific freshness policy was introduced (NSE market-hours-aware freshness is explicitly out of scope — `marketStatus` remains honestly `"unknown"` on every Angel One snapshot, per that provider's own existing, unmodified comment).

## 9. Chat integration

No change to D2.6.5's chat route, orchestrator, presenter, or integrity validator. The only reason Indian chat questions didn't work before this sprint was the resolveSymbol gap fixed in §4 — once a real `MarketSymbol` resolves, `RealTimeIntelligenceService`/`IntelligenceChatContextService` handle it exactly like any other instrument, verified directly with "What's happening in NIFTY?" and "Analyze BANKNIFTY right now." test cases producing real, correctly-scoped `IntelligenceEnvelope`s.

## 10. Failure states

Unchanged from D2.6.4/D2.6.5's existing honest failure taxonomy: Angel One unavailable for a resolved Indian symbol → `insufficient-data`, never a fabricated answer (verified). A genuinely unmapped Indian-sounding symbol (e.g. "SENSEX", not in the catalog) → `clarification-required`, never guessed. Every Angel One error path (auth/rate_limit/http_error/invalid_response/unsupported_symbol) was already typed by D2.6.3 and required no changes.

## 11. Future provider extensibility

Adding a second Indian data source (a future Global Datafeeds integration, explicitly out of scope this sprint) requires: (1) a new provider adapter implementing the existing `MarketDataProvider`/`SnapshotProvider`/`TimeSeriesProvider` interfaces, (2) a `ProviderCapabilityProfile` entry in `provider-capabilities.ts`, (3) `providerMappings` entries on the relevant `CanonicalInstrument`s. Zero changes to `MarketState`/`Regime`/`Hypothesis`/`IntelligenceScore`/`DecisionContext`/the AI presenter layer — exactly sprint §17's requirement, proven by this sprint's own test (`Fallback: future-provider seam`) which adds a hypothetical unmapped provider and confirms the router correctly excludes it without any code change.

## 12. Security

No secret value was ever printed, logged, or included in this document — every reference to `.env.local` state in this sprint's audit and this document reports only variable presence/absence, never values. `ANGEL_SMARTAPI` (empty, dead/unused by any loader) and the malformed `BINANCE_API_KEY`/`SEC_KEY` line (harmless today — `BinanceProvider` reads no env var) were both identified and **left untouched**, per the sprint's explicit instruction not to silently rewrite secrets. No credential reaches the frontend, no `NEXT_PUBLIC_` variable carries a private value, every Angel One call remains server-side (`AngelOneProvider` is only ever constructed inside `services/market-data/shared-instance.ts` and this sprint's server-side test script).

## 13. Testing

`scripts/validate-indian-market-data.ts` (`npm run validate:indian-market-data`) — 58 assert-based checks (exceeds the ≥40 requirement), covering: instrument resolution (catalog lookup, search, query-text resolution, ambiguity), provider capability (profile assertions, exclusion ordering for every new instrument), Angel One (auth, quote, **new candle coverage**, token mapping, malformed response, API error, rate limit, timeout, staleness), fallback (success, failure, future-provider seam, all-unavailable, no-irrelevant-fallback), integrity (timestamp, staleness, malformed price, symbol mismatch, provenance, conflict preservation), intelligence (real Indian snapshot through MarketState/Regime/Hypothesis/Envelope/DecisionContext), and chat (NIFTY/BANKNIFTY questions, unavailable-data, insufficient-data, AI integrity validation). A separate, clearly labeled, opt-in-only live Angel One smoke test exists but is not run by default.

## 14. Limitations

- Live Angel One authentication **was** verified this sprint (§3) — quote retrieval for NIFTY 50, BANKNIFTY, and RELIANCE, plus historical candles and freshness, all genuinely passed against the real API. TCS/INFY/HDFCBANK quotes were not individually live-tested (only their scrip-master token lookup was, same as every other entry) — the same adapter code path handles them, but that specific claim is not separately confirmed.
- The `AngelOneProvider.candleWindow()` date-range sizing produced fewer candles than requested against the real API this sprint (3 of 5 requested) — plausibly explained by non-trading-day sparsity, but not conclusively diagnosed; still an open item for a future sprint with more live budget.
- The tokenizer's single-word alias matching means "bank nifty" (two words) does not resolve as reliably as "banknifty" (one word) — see §4.
- No NSE-market-hours-aware freshness policy exists; `marketStatus` stays honestly `"unknown"`.
- Global Datafeeds and any other second Indian provider remain unintegrated, per this sprint's explicit stop condition.
