# D2.6.4 — Provider Reliability, Smart Fallback & Cross-Provider Data Integrity

**Status:** Implemented and tested. Infrastructure-first: no AI presenter, no ML, no signals, no execution.
**Scope:** Evolves the existing multi-provider market-data layer (D2.2/D2.3.S3/D2.6.3) from "Provider A failed → try Provider B" into "which currently-available provider is the most trustworthy source for this instrument" — deterministic, auditable, provider-neutral. The Intelligence Engine (15D → D2.5 → D2.6) is untouched.

---

## 1. Existing architecture (audit summary)

Before writing any new code, `MarketDataService` (`services/market-data/market-data.service.ts`) and its supporting modules were re-audited:

- **Provider execution order**: a fixed constructor-time array (`MarketDataServiceOptions.providers`, default `[TwelveData, AlphaVantage, Binance, AngelOne]`), attempted strictly in order.
- **Health tracking**: `ProviderHealthMonitor` (`lib/market-data/health-monitor.ts`) already records a rolling window (last 20 outcomes) per provider — `consecutiveFailures`, `successCount`, `failureCount`, `lastLatencyMs`, `lastErrorKind`, `lastCheckedAt` — and classifies a separate 4-state `ProviderHealthState` (`healthy`/`degraded`/`rate_limited`/`offline`) used today by the health/status routes.
- **Cache**: `TtlCache<T>` (`lib/market-data/cache.ts`), with `getStale(key, maxAgeMs)` distinguishing a fresh hit from a stale-but-usable grace-window entry.
- **Retry/timeout**: `withReliability()` (`lib/market-data/reliability.ts`) — bounded exponential backoff, retried only for `http_error`/`timeout`/`rate_limit`.
- **Error taxonomy**: `MarketDataErrorKind` (`unconfigured`/`unsupported_symbol`/`auth`/`rate_limit`/`http_error`/`timeout`/`invalid_response`/`unknown`), `MarketDataProviderError`.
- **Provenance**: `MarketSnapshot.providerSymbol`/`fallbackUsed` (D2.6.3), `cached`/`cacheAgeMs` (D2.3.S3).
- **Capability model**: `CanonicalInstrument.providerMappings[].supportedCapabilities` (D2.6.3, `lib/market-data/instrument-catalog.ts`).

**Conclusion of the audit**: everything §1–§4 of the sprint asked to inspect already exists and is well-tested. D2.6.4 therefore adds a **new interpretation/ranking layer over this existing data** — it introduces zero new health-tracking, caching, retry, or timeout infrastructure. `ProviderHealthMonitor` is read-only from this sprint's code; it is never modified, subclassed, or duplicated.

## 2. Provider reliability model

`ProviderReliability` (`types/provider-reliability.ts`), computed by `computeReliability()` (`services/market-data/provider-reliability.service.ts`) — a pure function over a single `ProviderHealthSnapshot` (the existing monitor's own output) plus the current time. Fields: `provider`, `symbol`, `capability`, `available`, `state`, `healthy`, `consecutiveFailures`, `lastSuccessAt?`, `lastFailureAt?`, `lastLatencyMs?`, `recentSuccessRate?`, `recentFailureRate?`, `inCooldown`, `reliabilityScore?`, `basis: string[]`, `generatedAt`, `version`.

**Non-negotiable meaning** (stated in both the type file's header and the service's header): a reliability score measures **one thing** — how reliably a provider actually delivers real data right now. It is never a market-confidence score, never a probability a trade succeeds, and never influenced by price direction, historical profitability, or any trading outcome. This is a deliberately different concept from D2.5.5's `IntelligenceScore` and 15D.7's `ConfidenceProfile`, which must never be conflated with it.

`lastSuccessAt`/`lastFailureAt` are derived honestly from the fact that `ProviderHealthSnapshot.lastCheckedAt` updates on every push (success or failure): when the most recent push was a success (`consecutiveFailures === 0` and at least one success exists) it *is* the last success time; when the most recent push was a failure it *is* the last failure time. No new timestamp field was invented anywhere.

## 3. Health-state implementation

Five states, all pure classification (`classifyState()`) — never a second, independently-mutated state machine, and deliberately distinct from the existing 4-state `ProviderHealthState` (both types now coexist, computed from the same underlying snapshot by different functions, never conflated):

| State | Meaning |
|---|---|
| `unknown` | Zero real observations exist yet — never presented as "healthy". |
| `healthy` | No failures anywhere in the recent observation window. |
| `degraded` | At least one recent failure, below the circuit-breaker trip threshold — still eligible for real requests. |
| `unavailable` | Tripped the circuit breaker and still within its cooldown window. |
| `recovering` | Most recent attempt succeeded, but a real failure still exists in the recent window — trust is rebuilding, not yet fully restored. |

A cooldown that has **elapsed but not yet been re-attempted** deliberately collapses into `degraded`, not a falsely-fresh `healthy` — the provider hasn't actually been re-proven, so honesty wins over optimism. `healthy` on the `ProviderReliability` object is `true` for `healthy` or `recovering` only — the two states a caller should treat as safe to prefer.

## 4. Reliability scoring formula

Documented "V1 heuristic", explicitly **not** LLM/ML/historical-profitability/price-direction/trading-outcome-based, and explicitly untuned pending real production traffic:

```
score = clamp(0, 100, successRate × 70 + latencyPoints)

successRate  = successCount / (successCount + failureCount)   [over the existing rolling window]
latencyPoints = 30 if lastLatencyMs ≤ 500ms
              = 20 if lastLatencyMs ≤ 2000ms
              = 10 if lastLatencyMs ≤ 5000ms
              =  0 otherwise
              = 15 (neutral) if lastLatencyMs is unmeasured
```

Below `MIN_RELIABILITY_OBSERVATIONS = 3` total recorded outcomes, `reliabilityScore` is **`undefined`**, never `0` or `100` — the same "never silently convert unknown to zero" discipline used throughout this codebase (D2.5.4's `MIN_HISTORICAL_VALIDATION_SAMPLE`, D2.5.5's `IntelligenceScoreComponent`). Every component is explained in a human-readable `basis: string[]`, never a bare number.

## 5. Smart fallback behavior

`orderProviders()` replaces a request's fixed provider list with a reliability-aware ordering, opt-in via `MarketDataServiceOptions.smartFallback` (default `false` — see §"Backward compatibility" below):

```
configured providers
  → capability filter   (via the D2.6.3 catalog — only applied when the symbol IS cataloged;
                          never breaks an un-cataloged symbol's existing reactive
                          unsupported_symbol handling; never returns zero candidates
                          even if the filter would otherwise over-eagerly exclude everyone)
  → split into "not in cooldown" / "in cooldown" groups
  → each group sorted by reliabilityScore (unknown treated as a neutral 50 for ranking
     purposes only — never written into the provider's own reported score) descending,
     ties broken by original array index (the existing documented priority order)
  → "not in cooldown" group first, "in cooldown" group appended last
```

Preference can therefore vary by instrument (via the catalog's per-symbol `providerMappings`), by capability (`quote` vs `candles` are ranked independently), and by real recorded health — never a single global reordering applied blindly to every request. With zero health data (a freshly started server), the function is a byte-for-byte no-op: every provider is "neutral", so ties fall back to the original priority order exactly as before this sprint.

## 6. Circuit-breaker / cooldown behavior

Derived **entirely** from existing `ProviderHealthSnapshot` fields plus two documented time constants — no new mutable state anywhere:

- `CIRCUIT_BREAKER_FAILURE_THRESHOLD = 3` consecutive failures trips the breaker.
- `CIRCUIT_BREAKER_COOLDOWN_MS = 30_000` — how long a tripped provider is deprioritized before it's eligible for a real recovery-probe attempt again (`isInCooldown()`, computed from `lastCheckedAt`).

A provider in cooldown is **deprioritized, never excluded** — it is moved to the end of the ordered list rather than dropped, so if every other provider also fails, a cooling-down provider (e.g. Angel One, the only real provider for NIFTY50/RELIANCE) is still tried as a last resort. This guarantees smart fallback is never *more* likely to return `insufficient-data` than the plain fixed-order router it replaces. Recovery is real, not timer-only: the next actual request attempt against the provider is what proves recovery (via the existing `recordedAttempt()` → `ProviderHealthMonitor.recordSuccess()` path) — the cooldown constant only controls *when* the router is willing to try again, never fabricates a "recovered" state on its own.

## 7. Cross-provider validation

`compareSnapshots()` (`services/market-data/cross-provider-validation.service.ts`) is a standalone, explicitly-callable comparison of two already-fetched `MarketSnapshot`s for the same instrument — it never fetches data itself and is **not** wired into `MarketDataService`'s single-snapshot-per-request hot path, so no existing caller's cost/latency changes.

- Compares `price`/`open`/`high`/`low`/`close` (via `fieldValue()`) and `timestamp` independently.
- A field present on only one snapshot is **never compared** — no fabricated 0-vs-real-value conflict.
- **Volume is deliberately never compared**: this codebase has no confirmed evidence that different providers' volume figures share a comparable unit/convention (e.g. Binance's base-asset 24h volume vs. a forex/equity provider's own tick-volume definition) — comparing them risks a false "conflict" that is actually just a unit mismatch.
- `PRICE_RELATIVE_TOLERANCE = 0.01` (1%) — looser than `EvidenceRankingService`'s own `RELATIVE_TOLERANCE` (0.5%) because this compares two independent **vendors**, not two evidence claims from the same 15D pipeline run, so a larger natural gap (bid/ask spread, quote timing) is expected and real.

Classification order: freshness is checked **first** — if either snapshot is stale (per §8), status is `stale-provider` (the observed difference may simply reflect staleness, not real disagreement) rather than a value judgment. Otherwise, divergence ≤ tolerance is `acceptable-difference`; divergence > tolerance while both are fresh is `unresolved-conflict`. **A conflict is never auto-resolved** — both real values (`valueA`, `valueB`) are always preserved for a downstream consumer to judge, matching the existing precedent of 15D's `EvidenceRankingService.detectConflicts()`.

## 8. Freshness policy

`assessFreshness()` (`services/market-data/freshness-policy.service.ts`) is deliberately **not** one global threshold — the sprint's own example (a 1-minute candle and a daily candle do not share freshness semantics) is directly encoded:

- **Quotes**, per `MarketCategory`: crypto 30s, forex/commodities 60s, indices/stocks 5min — crypto trades 24/7 with faster-refreshing providers; equities/indices are expected to refresh less aggressively.
- **Candles**, relative to the timeframe's own bar duration (`TIMEFRAME_MS[timeframe] × CANDLE_FRESHNESS_BAR_MULTIPLIER(=1)`) — a candle is fresh as long as its own bar period hasn't fully elapsed since it closed.

A missing or unparseable timestamp is honestly `unknown`, never guessed as `fresh`. This is a new analysis layer over real, already-existing timestamp fields (`MarketSnapshot.timestamp`, `Candle.datetime`) — it does not replace or duplicate `TtlCache`'s own TTL/stale-fallback mechanism, which remains the only thing that decides what `MarketDataService` actually serves.

## 9. Provenance behavior

No new provenance fields were added to `MarketSnapshot` itself this sprint — the existing D2.6.3 fields (`providerSymbol`, `fallbackUsed`) plus D2.3.S3's (`cached`, `cacheAgeMs`) remain sufficient to answer "which provider, which providerSymbol, was a fallback used, was this served from cache". The new `ProviderReliability`, `CrossProviderConflict`, and `MarketSnapshotIntegrityResult` objects are each independently timestamped (`generatedAt`/`detectedAt`/`checkedAt`) and carry their own `basis`/`issues` explanation arrays — every one of them is a diagnostic overlay a caller can request, never a mutation of the underlying snapshot. No credentials, API keys, or TOTP secrets appear in any of these structures.

## 10. Failure behavior

If every candidate provider fails, `MarketDataService` throws its existing aggregate `MarketDataProviderError` (citing every attempt) exactly as before — `smartFallback` changes *which order* providers are tried, never *whether* a failure is reported honestly. There is no new "insufficient-data" object; the existing thrown-error contract already satisfies the sprint's requirement that a total failure never produces an estimated or fabricated snapshot. `MarketSnapshotIntegrityService` provides a second, independent gate a caller can apply to a snapshot that *did* come back, to catch structural corruption (bad symbol, missing provider, non-finite price, inconsistent OHLC) before it reaches the Intelligence Engine — it reports issues, it never manufactures a replacement value.

## 11. Backward compatibility

`MarketDataServiceOptions.smartFallback` defaults to `false`. `orderedProviders()` — the single seam every one of `MarketDataService`'s three fetch methods (`getMarketContext`, `getSnapshot`, `getTimeSeries`) now reads its candidate list through — returns `this.providers` completely unchanged (same order, same array reference) when the flag is off. Every pre-existing caller/test that constructs a `MarketDataService` directly is therefore provably unaffected; confirmed by re-running the full pre-existing `validate:market-data-resilience` (20/20) and `validate:multi-provider-router` (42/42) suites with zero changes required. The real production singleton (`services/market-data/shared-instance.ts`) explicitly sets `smartFallback: true` to activate the new behavior.

## 12. Security considerations

No API keys, TOTP secrets, or provider credentials are read, logged, or exposed by any file in this sprint — every new service operates purely on `ProviderHealthSnapshot`/`MarketSnapshot` data that was already flowing through the existing, audited logging paths. No `.env` files were modified. Angel One's authenticated live login was **not** attempted or exercised this sprint (only its already-existing fake-transport adapter tests and the D2.6.3 live public scrip-master verification are reused). Binance's public REST endpoints require no credentials.

## 13. Test strategy

`scripts/validate-provider-reliability.ts` (`npm run validate:provider-reliability`) — 49 assert-based checks, no test framework, following the established `scripts/validate-*.ts` pattern:

- Reliability scoring & state classification (9 checks): zero/insufficient observations, healthy/degraded/recovering, latency-neutral fallback, determinism, basis explanations, unavailable-capability reporting.
- Circuit breaker (4 checks): below-threshold, tripped, cooldown-elapsed-collapses-to-degraded, real recovery.
- Freshness policy (6 checks): per-asset-class thresholds, per-timeframe candle semantics, missing/unparseable timestamp, determinism.
- Cross-provider validation (7 checks): agreement, unresolved conflict (both values preserved), stale-provider classification, missing-field skip, volume never compared, independent timestamp comparison, determinism.
- MarketSnapshot integrity (8 checks): valid snapshot, symbol substitution, missing provider, bad timestamp, invalid price, inconsistent OHLC, freshness-is-separate-from-validity, snapshot never mutated.
- Smart fallback ordering (7 checks): no-op with zero health data, real-reliability promotion, cooldown deprioritization (never excluded), capability filtering, never-zero-candidates, un-cataloged-symbol pass-through, determinism.
- `MarketDataService` integration (5 checks): `smartFallback:false` is a true no-op, `smartFallback:true` reorders based on **this exact instance's own real recorded outcomes** (proving no second health tracker exists), total failure still throws a structured error, existing stale-cache fallback still works, a real `BinanceProvider` instance still works unmodified.
- No-fabrication guarantees (3 checks): score never defaults to 0, conflicts never silently resolve to one value, integrity issues never contain a fabricated replacement.
- One **non-fatal** live Binance public-REST smoke test (additional only, per the sprint's explicit instruction) — verified BTCUSD returned a real live price in this run. Angel One authenticated live testing was **not** performed, per §12.

All fake provider/health-snapshot fixtures were probe-verified against the real service logic in the scratchpad before being locked into the permanent test file; two fixture-only mistakes were caught this way (using a cataloged symbol whose real `providerMappings` legitimately filtered out one test provider by capability) and corrected — no implementation bugs were found.

## 14. Future provider extensibility

Unchanged from D2.6.3's model, and explicitly preserved by this sprint: adding a new provider requires only (1) a Provider Adapter implementing the existing `MarketDataProvider`/`SnapshotProvider`/`TimeSeriesProvider` interfaces, (2) a Capability Mapping (`supportedCapabilities` in its `CanonicalInstrument.providerMappings` entries), and (3) Canonical Instrument Mapping entries in `lib/market-data/instrument-catalog.ts`. Reliability scoring, health-state classification, smart fallback, circuit-breaking, and cross-provider validation all operate generically over `provider.name` and the existing `ProviderHealthMonitor` — none of them require any change for a new provider to participate. The Regime/Hypothesis/Intelligence-Score/Decision-Context engines remain completely provider-agnostic and were not touched by this sprint.
