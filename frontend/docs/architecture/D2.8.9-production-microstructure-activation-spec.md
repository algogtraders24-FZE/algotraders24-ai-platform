# D2.8.9 — Production Microstructure Activation & Controlled Rollout

**Status:** Implemented and tested. **Baseline:** D2.8.8 (`bd0ed81`).
**Scope:** Safely activate D2.8.7/D2.8.8's presentation-safe microstructure pipeline in the real production intelligence flow, controlled, capability-gated, and non-fatal to normal intelligence.

---

## 1. Production entry point

Repository-wide search for every real caller of `IntelligencePresentationService`, `IntelligenceChatContextService`, and `RealTimeIntelligenceService` found **two, not one**, production callers:

1. **`app/api/private/knowledge/chat/route.ts`** → `IntelligencePresentationService.present()` → `AIPresenterOrchestratorService.present()` → a real LLM presenter. This is the only production path that reaches an AI presenter and therefore the only path D2.8.8's presentation bridge actually benefits.
2. **`app/api/private/intelligence/research/route.ts`** → `ResearchSnapshotService.build()` → `IntelligenceChatContextService.resolve()` directly. This path (powering the Workspace "Research" panel) **never calls an AI presenter** — it is explicitly a deterministic, non-conversational data view (D2.6.11's own design), and its output type (`VerifiedAnswerResponse`) has no microstructure field.

**Activation decision:** only the chat route (#1) was activated. Setting `includeMicrostructure: true` on the Research path (#2) would fetch real Binance data into `context.microstructure` with **no consumer anywhere** — pure wasted network calls, violating Phase 5's "do not add unnecessary provider calls." This is a deliberate, documented choice, not an oversight (verified by test 1b).

## 2. Activation decision

One line changed in `app/api/private/knowledge/chat/route.ts`: the existing call to `intelligencePresentationService.present({...})` now includes `includeMicrostructure: true`. This is a **default-on, capability-gated** request — never a universal fallback. The actual Binance network call only ever happens when `RealTimeIntelligenceService.fetchMicrostructure()` (D2.8.7, unmodified in its gating logic) confirms the resolved instrument is genuinely Binance-mapped; for every other instrument the flag is a complete no-op with zero network cost (verified by test 5-10's `callCount === 0` assertions).

## 3. Capability gating

Unchanged from D2.8.7: `getCanonicalInstrument(symbol)?.providerMappings.some(m => m.provider === "binance" && m.supportedCapabilities.includes("quote"))`. No second instrument registry was created — this sprint reuses the exact existing check.

## 4. Supported instruments

**BTCUSD, ETHUSD** — real, verified Binance provider mappings in the canonical catalog (tests 3/4).

## 5. Unsupported instruments

**XAUUSD, XAGUSD, EURUSD, GBPUSD, NIFTY, BANKNIFTY** — confirmed to have no Binance provider mapping in the real catalog; the microstructure provider is never even called for any of them (tests 5–11, `callCount === 0` in every case).

## 6. Failure isolation

A genuine architectural gap was found and fixed during Phase 1 audit: `MicrostructureSnapshotService.getSnapshot()` (D2.8.5) deliberately bypasses `MarketDataService`'s own retry/timeout wrapper (`withReliability`, `lib/market-data/reliability.ts`, D2.2/D2.6.4) by design — it is a single-provider, no-fallback seam. This meant the microstructure fetch call had **no timeout protection at all**: a hung Binance response could stall the entire chat request indefinitely, even though microstructure is meant to be a non-critical enhancement.

**Fix:** `RealTimeIntelligenceService.fetchMicrostructure()` now wraps the fetch with the existing `withReliability(fn, provider, { retries: 0 })` primitive — the same one `MarketDataService` already wraps every OHLC/quote provider call with, reused unmodified, with its default 8-second timeout budget and zero retries (a retry would only add latency to a best-effort fetch). This is the one change made to D2.8.7's own `fetchMicrostructure()` method, justified as "strictly necessary" per the protected-files exception — no calculation, validation, provider-parsing, or gating logic was touched.

Verified scenarios (tests 14–19, 24): Binance available, hung/never-resolving (real ~8s timeout fires, test 14), HTTP failure, malformed/invalid response, stale response, unsupported instrument, and normal OHLC intelligence surviving every one of these failures with a fully populated envelope/regime/hypotheses.

## 7. Performance observations

Measured (not estimated) via the new test script:

- **Real live Binance microstructure fetch:** BTCUSD ≈ 330–400ms, ETHUSD ≈ 150–160ms (single combined depth+trades request, this session's actual runs).
- **Provider call count:** exactly one call for a supported instrument's request, zero for an unsupported one (tests 2, 28).
- **Added latency with a controlled fake delay:** activating microstructure added latency equal to the one real provider call's delay (±small overhead), never a multiple of it — confirming no duplicate/retried calls under normal conditions.
- **No new caching system, no Redis, no Kafka, no WebSocket** were added. The existing per-request, uncached microstructure fetch (D2.8.5's own deliberate choice — "meant to be read close to real-time") was reused as-is.

## 8. Presentation flow

Unchanged from D2.8.8, now genuinely reachable end-to-end from the real chat route: `context.microstructure` → `AIPresenterOrchestratorService.present(envelope, userQuestion, microstructure)` → `buildPresenterQuestionWithMicrostructure()` → the candidate presenter receives `Direct Evidence`/`Derived Evidence` sections plus symbol/provider/freshness/venue-scope metadata (test 24).

## 9. Evidence attribution

Unchanged: `provider: "binance"`, real instrument symbol, explicit freshness state, and the closing "not global market liquidity" scope line — all confirmed reachable through the now-activated path (tests 12, 13).

## 12. Tests

Deterministic fixtures for all failure-isolation/attribution/no-mutation tests; **2 real live network calls** (tests 29/30) through the actual production `binanceMicrostructureProvider`/`microstructureSnapshots` shared instances, both captured successfully this session (real BTCUSD/ETHUSD bid/ask/spread/freshness logged above). Test 14 genuinely waits ~8 seconds to prove the real timeout fires (not simulated/mocked away).

## 13. Known limitations

- The Research panel path (`ResearchSnapshotService`) does not receive microstructure — see §1. Its `VerifiedAnswerResponse` output type has no microstructure field; adding one is a distinct, separately-scoped UI/API decision.
- The chat route's `includeMicrostructure: true` is a hardcoded default, not a per-request client-controllable flag — a future sprint could expose it as an opt-out if a product reason emerges, but no such reason exists today.
- `DeterministicSafeFallbackPresenter` still never includes microstructure evidence (D2.8.8's own documented limitation, unchanged) — if every real LLM provider fails, the trader-facing fallback answer never mentions microstructure even when it was fetched successfully.
- The `/dashboard/market-intelligence` prompt-design finding (§11) remains open, tracked since D2.8.2, unrelated to this pipeline.

## 14. Future WebSocket boundary

No WebSocket was added. The activated path is still exactly D2.8.6's REST-only `MicrostructureSnapshotService.getSnapshot()` → `BinanceProvider.getMicrostructureSnapshot()`, now additionally timeout-bounded (§6). A future push-based microstructure source would need its own explicitly-scoped sprint; nothing in this activation assumes or blocks that.
