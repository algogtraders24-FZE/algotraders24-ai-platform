# D2.7.1 — AT24 Financial Typography & Rendering Foundation

**Status:** Implemented and tested.
**Scope:** A rendering-quality and financial-typography foundation sprint. No visual redesign, no brand change, no chart engine. Establishes the typography contract every future AT24 surface — including the eventual native chart engine — will reuse.

---

## 1. Typography architecture

AT24 already had a sound three-font stack (Geist Sans for body, Geist Mono for numeric/code contexts, Urbanist for headings/brand) with no synthesis risk (every weight actually used is actually loaded). The real gap was never the font stack — it was the absence of a **shared contract** for how a financial number gets formatted and styled. Every component (`MarketRibbon`, `WorkspaceHeader`, `IntelligencePanel`, `AuditTraceView`, `IntelligenceScorePanel`) had independently hand-rolled its own `toLocaleString`/template-literal call with a slightly different precision rule, and independently chosen its own `font-mono text-{size} text-{color}` chain. This sprint centralizes both without introducing a second design system:

- `lib/financial-format.ts` — the one deterministic numeric-formatting layer.
- `components/ui/financial-typography.ts` — the one set of composed class-string constants (`FIN_PRIMARY`/`FIN_SECONDARY`/`FIN_TERTIARY`/`FIN_LABEL`), built entirely from tokens that already existed in `app/globals.css` (`--text`/`--text-2`/`--text-3`/`--signal-up`/`--signal-down`) and the font already loaded in `app/layout.tsx` (Geist Mono). No new color, no new font.
- `components/ui/FinancialValue.tsx` — the one reusable label+price[+change] display, built on top of the pre-existing `StatField` primitive (D2.3-P8), never a competing shape.

## 2. Font strategy

**No new font was installed.** The audit (Phase 1) confirmed:

- Geist Sans (variable, full weight range) is the default body font via Tailwind's `--font-sans` theme variable, applied by Tailwind v4's own preflight — no explicit `font-sans` class needed anywhere.
- Geist Mono (variable) already backs every `font-mono` numeric context across ~34 files — a true monospace font, whose glyphs already have identical advance widths by construction.
- Urbanist (static weights 500/600/700/800, non-variable) backs headings/brand only, via `--font-display`; every weight actually referenced in the codebase (h1-h6's implicit browser-default 700, and the explicit 500-800 utility classes seen in use) is one of the four loaded static weights — **no font-weight synthesis risk was found**.

Because Geist Mono is already a true monospace font, `font-variant-numeric: tabular-nums` has **zero visual effect** on it today (tabular figure widths are already guaranteed by monospacing). It was added anyway, scoped to a new `.fin-num` utility class (§3), for two real reasons: it is the literal instruction Phase 2 of this sprint asks for, and it is the correct preparation for the future native chart engine (§8), whose axis/tooltip/crosshair numbers will very likely render in non-monospace contexts (canvas/SVG text, or a proportional UI font) where tabular-nums genuinely changes layout stability.

## 3. Numeric rendering strategy

`.fin-num` (`app/globals.css`):

```css
.fin-num {
  font-variant-numeric: tabular-nums;
  font-feature-settings: "tnum" 1;
}
```

Applied via the `FIN_PRIMARY`/`FIN_SECONDARY`/`FIN_TERTIARY` constants, never hand-typed per component. Kept as an explicit, separate class rather than overriding Tailwind's own built-in `tabular-nums` utility, so intent stays traceable to this sprint's own contract.

**`-webkit-font-smoothing: antialiased` was investigated and NOT adopted.** Phase 6 explicitly warns against adopting it on the strength of assumption alone, since it can make text read thinner rather than clearer. No verifiable crispness gain could be demonstrated for this project's already-modern variable/static web-font stack, and this session's environment has no pixel-level before/after comparison capability to prove otherwise. Per the sprint's own instruction ("test whether it actually improves the visual result before adopting it"), it was not added anywhere — documented here as an investigated-but-rejected option, not silently skipped.

## 4. Financial formatting contract (`lib/financial-format.ts`)

Every function is pure, deterministic, and preserves the source value's real precision — it only caps/pads *display* digits, never invents a significant digit the market data didn't provide, and never mutates the underlying numeric value.

| Function | Example | Rule |
|---|---|---|
| `formatPrice(value, {maxDecimals?})` | `1537.9` → `"1,537.90"` | Pads to a 2-decimal minimum (the universal currency-display convention — 1537.9 and 1537.90 are the same real number, this is not fabricated precision), caps at `maxDecimals` (default 2, pass a higher value for FX-style pairs) without ever adding a digit beyond what the source has. |
| `formatPercent(value, {decimals?, signed?})` | `1.24` → `"+1.24%"`, `-0.37` → `"-0.37%"` | Signed by default (the trading convention every existing component already followed by hand); `signed:false` for an unsigned 0–100 value like AI confidence. |
| `formatQuantity(value)` | `1500000` → `"1,500,000"` | Whole-unit, thousands-grouped, no fabricated decimals. |
| `formatDecimalQuantity(value, maxDecimals?)` | `1500000.5` → `"1,500,000.5"` | Same, preserving real decimal precision. |
| `formatCompactVolume(value)` | `1500000` → `"1.5M"` | Compact notation for volume/scale figures **only** — never applied to a price, which always shows full precision. |
| `formatScore(value, max=100)` | `72` → `"72/100"`, `undefined` → `"Unavailable"` | The Intelligence Score contract (D2.5.5's formula, unmodified) — always `X/100`, **never** a percentage, **never** a probability of profit or trade success. |
| `formatRatio(n, d)` | `3, 5` → `"3/5"` | Same X/Y shape as `formatScore`, for any other real ratio. |
| `formatDuration(ms)` | `842` → `"842ms"`, `2400` → `"2.4s"`, `185000` → `"3m 5s"` | Real elapsed time only. |

## 5. Contrast hierarchy

Formalized (not new tokens — the same `--text`/`--text-2`/`--text-3` already used everywhere):

- **PRIMARY** (`FIN_PRIMARY`) — the number a trader looks at first: price, main symbol value. `text-text` (pure white).
- **SECONDARY** (`FIN_SECONDARY`) — the next-most-important number: percentage change, OHLC, key metrics. `text-text-2` (slate accent).
- **TERTIARY** (`FIN_TERTIARY`) — provenance/metadata: provider, timestamp, freshness, latency. `text-text-3`.
- **MUTED** (`FIN_MUTED`) — explanatory prose, deliberately not numeric/tabular.
- **LABEL** (`FIN_LABEL`) — the small uppercase caption above a value, identical to `StatField`'s own pre-existing label rule (verified structurally so the two can never drift apart).

Never solved by making everything brighter or bolder — the direction color (`financialDirectionClass`) reuses the exact same `--signal-up`/`--signal-down` tokens every badge/ribbon cell already used.

## 6. Components updated (Phase 5 priority list)

`MarketRibbon`, `WorkspaceHeader`, `IntelligencePanel` (AI Confidence), `VerifiedMarketContext`, `IntelligenceScorePanel`, `MarketDataProvenance` (label consistency), `EvidencePanel` (metadata tone), `HypothesisPanel` (candle count), `AuditTraceView` (latency + score) all now render their numeric values through the shared `lib/financial-format.ts` functions and `FIN_*` tokens instead of independent ad hoc formatting. `GlobalSymbolSelector` and the chart/TradingView integration were deliberately left untouched — they render no raw financial numbers of their own (symbol/name text and TradingView's own internal rendering, respectively), matching this sprint's "don't unnecessarily touch unrelated surfaces" instruction and the explicit prohibition on modifying the TradingView integration.

## 7. Responsive behavior

`FinancialValue`'s value row uses `flex-wrap` so a price + change badge never clips or overlaps on narrow viewports; `MarketRibbon` keeps its existing `overflow-x-auto` + `min-w-[132px]` cell pattern (unchanged, verified still present) so financial values stay visually stable at mobile widths instead of wrapping mid-number.

## 8. Accessibility

No information is conveyed by color alone — every direction change is still paired with the literal `+`/`-` sign text (`formatPercent`), and every status still carries its own text label (`Badge` components, unchanged). Contrast tokens are unchanged (no color value was modified by this sprint) — `--text-3` was previously verified to stay ≥4.5:1 on `--ink` (D1.0). `.fin-num` affects only numeral rendering, never removes or obscures text at any zoom level.

## 9. Future native chart contract (`types/chart-typography-contract.ts`)

Foundation only — no chart rendering exists yet. Declares the typography role a future native AT24 chart engine will need (axis label, price scale, time scale, OHLC value, crosshair value, tooltip value, indicator label, volume label, drawing-tool label), each mapped to one of the **same** `FIN_*` class constants and one of the **same** `lib/financial-format.ts` formatters already used across the Workspace today — so a future chart's numbers look identical to every other number on the platform, never a second typography system invented later under time pressure.

## 10. Testing

`scripts/validate-financial-typography.ts`, 52 assert-based tests (no test framework, matching this project's established convention): numeric/percent/quantity/volume/score/ratio/duration formatting (including decimal-preservation and no-fabrication guarantees), direction/state helpers, the `FinancialValue` component's loading/unavailable/stale state contract and its no-hardcoded-value guarantee, tabular-numeral configuration and design-token availability (including a structural cross-check that `FIN_LABEL` can never drift from `StatField`'s own label rule), per-component rendering contracts (each updated component genuinely calls the shared formatter, never a hand-rolled duplicate), responsive structural checks, the Intelligence Score X/100-never-a-probability contract, and regression guards proving this sprint never touched provider routing, market-data logic, the chart resolver, or Workspace symbol-state.

Full regression across every pre-existing `validate:*` script, `tsc`, `eslint`, and `npm run build` results are reported in the sprint's final report.

## 11. Known limitations

- `-webkit-font-smoothing: antialiased` was investigated but not adopted — no verifiable crispness gain could be demonstrated in this environment; a future sprint with real pixel-comparison tooling could revisit this specifically for `.fin-num` contexts if a genuine case emerges.
- The financial typography contract (`FIN_*`, `formatPrice`/`formatPercent`/etc.) was applied to the Phase 5 priority component list; components outside the Workspace/intelligence-workspace surfaces (billing, licenses, products, admin) were deliberately left untouched — they were out of this sprint's scope and use `lib/currency.ts`'s own, unrelated USD-price formatting for product/subscription prices, which this sprint does not touch or replace.
- `types/chart-typography-contract.ts` is a declaration only — it has no consumer yet, since the native chart engine itself is explicitly out of scope for this sprint.
- Live, authenticated interactive browser verification (Phase 11's visual checklist) could not be completed in this environment — see the sprint's final report for exactly what was and wasn't verified.
