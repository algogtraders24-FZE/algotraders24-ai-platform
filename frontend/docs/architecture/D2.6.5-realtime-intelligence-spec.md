# D2.6.5 — Real-Time Intelligence Context + Trader Chat Integration

**Status:** Implemented and tested. Connects the deterministic D2.5/D2.6 intelligence pipeline to the real trader-facing chat route for the first time.
**Scope:** A real-time orchestrator that turns a trader's chat question into a verified intelligence context, a production-safe Gemini presenter that can only paraphrase that context, a deterministic response-integrity validator, and a deterministic safe-fallback presenter — wired into the existing chat route behind a strictly gated, deterministic condition.

**Non-negotiable architectural rule** (repeat before touching any file in this sprint): the intelligence engine is the product; Gemini is a replaceable presentation layer. `DATA → DETERMINISTIC ENGINES → VERIFIED ENVELOPE → AI PRESENTATION`, never `USER → LLM → MARKET ANSWER`. No file in this sprint lets an LLM originate a price, indicator, regime, hypothesis, confidence, risk, or historical-outcome fact.

---

## 1. Architecture

```
Trader chat message
  ↓
IntelligenceChatContextService.resolve()     NEW - thin chat-facing entry point
  ↓
RealTimeIntelligenceService.build()          NEW - the orchestrator
  ↓
IntelligenceQueryService.parse()             REUSED (D2.6.2) - symbol/timeframe/query-type resolution
  ↓ (only if a real symbol resolved - never guessed)
MarketDataService.getSnapshot()/.getTimeSeries()   REUSED (D2.6.3/D2.6.4, smart fallback already active)
  ↓
validateSnapshotIntegrity() + assessFreshness()    REUSED (D2.6.4) - structural/freshness gate
  ↓
MarketStateService → RegimeService → HypothesisService   REUSED (D2.5.2/D2.5.3)
  ↓ (in parallel, same real market data)
MarketIntelligencePipelineService (frozen 15D)     REUSED - evidence/reasoning/risk/confidence
  ↓
HistoricalValidationService                        REUSED (D2.5.4, only when exactly 1 hypothesis)
  ↓
IntelligenceEnvelopeService.build()                 REUSED (D2.5.5)
  ↓
IntelligenceQueryContextService.build()             REUSED (D2.6.1/D2.6.2) - builds DecisionContext + selects evidence
  ↓
IntelligenceAnalysisRunService.createAnalysisRun()  REUSED (D2.5.1) - persists the real hypothesis snapshot
  ↓
VerifiedRealTimeIntelligenceContext                 NEW - the one object every presenter is allowed to read facts from
  ↓
presentSafely(): AIIntelligencePresenter (Gemini) → AIResponseIntegrityService → DeterministicSafeFallbackPresenter
  ↓
Chat route: persist assistant turn, return response
```

Every box above except the six marked NEW already existed and is reused verbatim — `RealTimeIntelligenceService` (`services/intelligence/orchestration/real-time-intelligence.service.ts`) is a pure sequencing/glue layer, not a second implementation of any engine. It never computes a market fact itself.

## 2. Fresh data policy

`DataQualityAssessment` (`types/real-time-intelligence.ts`) reports one of five honest states — `fresh` / `stale` / `cached` / `unknown` / `unavailable` — computed from D2.6.4's own `assessFreshness()` plus the real `MarketSnapshot.cached` flag. `cached` is distinguished from `fresh`: a within-TTL cache hit is real and current but is still labeled `cached` so a caller can tell "served from cache" from "freshly fetched this request," matching the sprint's explicit "never silently treat stale/cached data as live" instruction. Provenance (`provider`, `providerSymbol`, `fallbackUsed`, `timestamp`) is carried through unchanged from the existing `MarketSnapshot` fields — no new provenance mechanism was built.

Before any snapshot reaches the intelligence engines, `validateSnapshotIntegrity()` (D2.6.4) re-checks it structurally; a failure here is treated identically to a total fetch failure — `dataQuality.state` becomes `unavailable` and the orchestrator returns `status: "insufficient-data"` without ever calling `MarketStateService`. Nothing is ever estimated, interpolated, or LLM-filled.

## 3. Multi-provider fallback

The orchestrator calls `MarketDataService.getSnapshot()`/`.getTimeSeries()` on the shared production singleton (`services/market-data/shared-instance.ts`, `smartFallback: true` since D2.6.4) and never touches provider selection itself. Adding a new provider requires zero changes to this sprint's files — exactly the same guarantee D2.6.3/D2.6.4 already established for `MarketState`/`Regime`/`Hypothesis`/`DecisionContext`, now extended to the chat/presenter layer.

## 4. Cross-provider data integrity

`RealTimeIntelligenceRequest.crossProviderValidation` is an explicit, default-`false` opt-in (sprint §4 says "optionally compare") — enabling it on every chat turn would double provider cost/latency for a capability the sprint itself calls optional. When enabled, the orchestrator looks up a second real provider for the same instrument via the D2.6.3 catalog (`getCanonicalInstrument`), fetches a second real snapshot directly from that provider's own adapter (bypassing the router, which would just return the same winning snapshot again), and compares via D2.6.4's `compareSnapshots()`. The new `summarizeConflicts()` (additive export on `cross-provider-validation.service.ts`) reduces the per-field conflict list to one aggregate `{status, providers, basis, generatedAt}` matching the sprint's requested shape — precedence: any `unresolved-conflict` field wins, then `stale-provider`, otherwise `consistent`. A disagreement is never auto-resolved; both real values are preserved in the underlying per-field conflicts.

## 5. Real-time analysis run persistence

Every `resolved` result calls `IntelligenceAnalysisRunService.createAnalysisRun()` (D2.5.1, unmodified) with the real `hypothesisSnapshot: {marketState, regime, hypotheses, capturedAt}` — the exact object D2.5.4's evaluator expects, never just the final presenter text. Persistence is best-effort: a DB failure never breaks the response the trader already has (the run simply isn't recorded that turn — `analysisRunId` stays `undefined`, observable in the response's `intelligence` metadata).

## 6. Pending outcome evaluation boundary

`evaluatePendingAnalysisRunsForUser()` (`services/intelligence/orchestration/pending-outcome-evaluation.service.ts`) is a thin wrapper around D2.5.4's already-existing `HypothesisOutcomeEvaluatorService.evaluatePendingAnalysisRun()`, wired with the shared `marketData` singleton as its `timeSeriesProvider`. No scheduler, cron, worker, or queue was built this sprint — this function is the seam a future sprint calls from one.

## 7. Trader chat context adapter

`IntelligenceChatContextService` (`services/intelligence/chat/intelligence-chat-context.service.ts`) is a deliberately thin wrapper: it adapts a raw chat turn (`message` + optional `conversationContext`) into `RealTimeIntelligenceService.build()`'s request shape and returns its result unchanged. It exists so every current and future chat surface has one stable, documented entry point rather than each caller wiring the orchestrator's many dependencies itself.

**Ambiguity handling (sprint §8)**: `IntelligenceQueryService.parse()`'s existing symbol/timeframe resolution (D2.6.2) is reused unmodified. If no symbol resolves at all, `RealTimeIntelligenceService` returns `clarification-required` with `reason: "unresolved-symbol"` and never calls any market-data or intelligence engine. If multiple real symbols are mentioned (`resolveSymbol()`'s own `ambiguousCandidates`), the reason is `"ambiguous-symbol"` and the real candidate list is returned — never an arbitrary pick. A missing timeframe does **not** block analysis: `DEFAULT_INTELLIGENCE_TIMEFRAME = "1h"` (a documented, versioned constant) is used only for the working computation, while `IntelligenceQuery.timeframe` itself stays honestly `undefined` — `IntelligenceQueryContextService`'s own existing `classifyCompleteness()` rule already downgrades `completeness` to `"partial"` in this case, so the trader-facing context still signals "you didn't specify a timeframe" without inventing a new field.

## 8. AI Presenter boundary

`AIIntelligencePresenter` (D2.5.5's own interface, `types/intelligence-envelope.ts`) receives only `IntelligenceEnvelope` + the raw question and returns `{text, presentedBy, envelopeGeneratedAt}` — structurally incapable of carrying a new fact back into the system, exactly as the sprint requires. Neither `GeminiIntelligencePresenter` nor `DeterministicSafeFallbackPresenter` has database write authority, market-data tools, web access, or broker execution tools; both are constructed with only an `AIProvider`/`DecisionContextService` dependency.

## 9. Gemini implementation

`GeminiIntelligencePresenter` (`services/intelligence/chat/gemini-intelligence-presenter.service.ts`) is built around the existing, provider-agnostic `AIProvider` interface (`lib/ai/provider.interface.ts`, already designed for gemini/openai/claude/deepseek) rather than a hardcoded Gemini transport — `presenter.name` reflects the real injected provider's own name. Its system instruction is the sprint's exact §10 text (`GEMINI_PRESENTER_SYSTEM_INSTRUCTION`); the user message carries a deterministic "verified facts" block built by `formatDecisionContextAsText()` plus the trader's raw question. No deterministic engine's logic is touched — the presenter only reads an already-built `IntelligenceEnvelope`.

## 10. AI response validation

`AIResponseIntegrityService` (`services/intelligence/chat/ai-response-integrity.service.ts`) is **not** a second LLM — every check is a documented, deterministic regex/set-membership rule over real data, explicitly labeled a "V1 heuristic":

| Check | Rule |
|---|---|
| Unsupported numeric claim | Every percent/price-like number in the response must match (within tolerance) a real number from the DecisionContext's own structured fields **or** its own basis/evidence/claim text — the same discipline that lets the deterministic fallback always pass its own check, since it only ever echoes that text. |
| Unsupported symbol | A response mentioning a different real cataloged instrument than the one actually analyzed. |
| Unsupported directional / guaranteed-profit language | Reuses D2.6.1's own regression `PROHIBITED_PATTERNS` (buy/sell now, win-rate%, target=, stop-loss=, probability language) plus explicit guarantee/sure-thing/can't-lose phrasing. |
| Unsupported indicator | A named indicator this platform's `MarketState.technical` engine has never computed (Stochastic, ADX, Ichimoku, Fibonacci, …), or RSI mentioned when `rsi14` wasn't actually computable. |
| Unsupported historical claim | Historical-performance language while `historicalContext.status !== "available"`. |
| Unsupported confidence/probability claim | IntelligenceScore or historical rate presented as a win probability. |
| Contradicts unresolved conflict | High-certainty language while a real `unresolvedConflicts` entry exists. |
| Contradicts insufficient-data | `state === "insufficient-intelligence"` with no hedging language at all. |

`presentSafely()` is the single seam a caller uses instead of calling a presenter directly: if the presenter throws, times out, or returns empty text, or its output fails integrity validation, the deterministic fallback is used instead and the reason (`presenter-error` | `integrity-violation`) is recorded — the trader-facing product never breaks from an LLM provider having a bad moment, and never silently ships an unsupported claim.

## 11. Deterministic safe fallback presenter

`DeterministicSafeFallbackPresenter` never calls an LLM. It builds `DecisionContextService.build(envelope)` (unmodified D2.6.1) and formats it via `formatDecisionContextAsText()` (`services/intelligence/chat/decision-context-formatter.ts`) into the exact section structure the sprint's own worked example gives: Current State, Regime, Supporting/Opposing Evidence, Hypotheses, Invalidation Conditions, Risk, Historical Validation, Intelligence Score, Missing Information. This formatter is the single source both presenters draw from — the Gemini presenter feeds it to the LLM as ground truth; the fallback presenter returns it verbatim.

## 12. AI provider abstraction

`GeminiIntelligencePresenter`/`DeterministicSafeFallbackPresenter` both implement the same `AIIntelligencePresenter` interface and both consume the same `IntelligenceEnvelope`. A future `ClaudeIntelligencePresenter`/`OpenAIIntelligencePresenter` is a drop-in sibling class needing only a different `AIProvider` implementation — never a change to `RealTimeIntelligenceService`, the deterministic engines, or `AIResponseIntegrityService`.

## 13. Chat route integration

`app/api/private/knowledge/chat/route.ts` (Sprint 15C, previously frozen) now imports exactly four new modules: `IntelligenceChatContextService`, `GeminiIntelligencePresenter`, `DeterministicSafeFallbackPresenter`, `presentSafely` — never a 15D/D2.5 internal engine directly. The gate is deterministic, not guessed: after the existing user-turn persistence, `chatIntelligenceService.resolve()` is called once; its `status` decides the branch:

- `"resolved"` → `presentSafely()` produces the answer; the existing raw-Gemini/RAG path is skipped entirely for this turn.
- `"insufficient-data"` or `"clarification-required"` with `reason: "ambiguous-symbol"` → a deterministic, honest message is returned directly (never let Gemini free-associate a market answer with zero real grounding).
- `"clarification-required"` with `reason: "unresolved-symbol"` (i.e., no real instrument resolved at all — the ordinary case for a non-market question) → falls straight through to the existing, completely unchanged RAG/Gemini flow.

This means every existing regression script asserting the chat route's "zero coupling to [evidence/confidence/reasoning/risk/market-intelligence-pipeline/…]" (11 scripts spanning D2.5.x/D2.6.2/D2.6.3) still passes unmodified: the route's own source never references those internal engine module paths — it only ever imports the four D2.6.5 chat-facing modules, which are themselves responsible for wiring the internals. This is not incidental; it is the intended, permanent architectural boundary — the route may never reach around the orchestrator into a low-level engine directly, in the same way `IntelligenceQueryContextService` already wires `EvidenceRankingService`/`DecisionContextService` internally rather than exposing them to its own callers.

Streaming and non-streaming response shapes are both preserved: the intelligence path emits the same NDJSON event vocabulary (`stage`/`token`/`done`) as one full-text token (since the post-hoc integrity check needs the complete text before it can validate it — incompatible with true token-by-token streaming), and the non-streaming path returns the same `{content, ragApplied, sourcesCount, sources, conversationId}` shape with one new, additive `intelligence` field.

**Known, documented scope limitation**: `conversationContext` (symbol/timeframe/previous-analysis continuity) is not yet populated from any persisted per-conversation state in this route — no such mechanism exists in the codebase yet, and building one was out of this sprint's scope (no major redesign, no new persistent conversation-state infra). A follow-up question like "what about the 4h chart?" therefore resolves independently rather than inheriting the prior turn's symbol. `RealTimeIntelligenceService` and `IntelligenceQueryContextService` both already accept `conversationContext` and will honor it the moment a caller supplies it.

## 14. Security

`userId` is always session-derived (`getUserOrNull()`), never accepted from the request body, throughout every new file. No provider credentials, API keys, or TOTP secrets are read, logged, or exposed by any file in this sprint. The presenter receives only the verified envelope and the trader's raw question — never database write authority, market-data tools, web access, or broker execution tools. `AnalysisHistoryService`'s existing ownership scoping (D2.6.2) is reused unmodified for the previous-analysis lookup — a different user's analysis run resolves to `null`, never a distinct "forbidden" (same posture as `conversation-ownership.service.ts`), verified directly in this sprint's test suite (§17).

## 15. Failure behavior

Every failure mode collapses to an honest, structured result — never a fabricated fact:
- All market-data providers fail, or a structurally invalid snapshot is returned → `status: "insufficient-data"`, no envelope, no intelligence engines called.
- No real symbol resolves → `status: "clarification-required"`, no market-data call at all.
- The 15D evidence/risk/confidence leg is unavailable → `MarketState`/`Regime`/`Hypothesis` still stand on the real snapshot/candles already obtained; `IntelligenceScore` is still honestly computed with the affected components marked `dataAvailable: false`, never defaulted to 0.
- Gemini is unavailable, times out, or returns empty/unsupported text → the deterministic fallback is used; the trader always receives a real, verified answer.

## 16. Observability

`RealTimeIntelligenceObservability` (`types/real-time-intelligence.ts`) carries `requestId`, `userId`, `symbol`, `timeframe`, `providerUsed`, `fallbackUsed`, `dataFreshness`, `pipelineVersion`, `intelligenceEngineVersion`, `presenter`, `responseIntegrityStatus`, `generatedAt` on every `VerifiedRealTimeIntelligenceContext` — never API keys, TOTP secrets, passwords, or raw authorization headers. The chat route surfaces a subset of this (`symbol`, `timeframe`, `presentedBy`, `responseIntegrityStatus`, `dataFreshness`) in its response payload's new `intelligence` field.

## 17. Test strategy

`scripts/validate-realtime-intelligence.ts` (`npm run validate:realtime-intelligence`) — 47 assert-based checks, no test framework, following the established pattern. Only the market-data seam (`FakeMarketData`) and the AI-provider seam (`FakeAIProvider`) are faked; `MarketStateService`, `RegimeService`, `HypothesisService`, the frozen 15D pipeline, `IntelligenceEnvelopeService`, `IntelligenceQueryContextService`, and `DecisionContextService` all run for real against the fake market data, so the suite proves genuine end-to-end wiring rather than isolated units. Covers every sprint §17 scenario (A–T): fresh/stale/unavailable/structurally-invalid data, unresolved/ambiguous symbol, missing timeframe, valid hypothesis generation, historical-validation pass-through (including an honest insufficient-sample state), an honestly-computed IntelligenceScore under partial input, cross-provider agreement/disagreement, Gemini unavailable/empty/unsupported-claim/contradicts-conflict fallback behavior, the safe fallback's own self-consistency, real-DB analysis-run + hypothesis-snapshot persistence, user-authorization isolation, and the pending-outcome-evaluation boundary. Two real implementation gaps were found and fixed via this suite (not fixture-only mistakes this time): the numeric-claim checker's allow-list didn't include EMA values embedded only in basis text (not a dedicated structured field) and didn't strip ISO-8601 timestamps before number extraction — both fixed in `ai-response-integrity.service.ts`, verified by rerunning the suite to a clean 47/47.

## 18. Future provider extensibility

Unchanged from D2.6.3/D2.6.4's model: a new market-data provider needs no change to this sprint's files. A new AI provider needs one new `AIProvider` implementation and one new presenter class implementing `AIIntelligencePresenter` — never a change to `RealTimeIntelligenceService`, the deterministic engines, or the chat route's own gating logic.
