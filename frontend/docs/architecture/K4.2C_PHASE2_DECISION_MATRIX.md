## 1. The 8 primary decisions

### D1 — Candidate trigger: which AI answers become a `KnowledgeCandidate`?

| Option | Description | Tradeoff |
|---|---|---|
| **A** | Only `web-answer-worth-keeping` — a `generated` outcome where `winner.res.webSearchUsed === true` and the answer passed the forbidden-language scan. | Most conservative. Real new information (web search found something AT24 Knowledge didn't have) becomes a candidate; nothing else does. Misses the "we get asked this and can't answer at all" gap entirely. |
| **B** | A, **plus** `unanswered-high-value` — a `KNOWLEDGE_MISS` answered from general model reasoning, but **gated on repeat count** (same `queryHash` recurring ≥ N times with no existing candidate/knowledge covering it yet — mirrors the contract's own "Unresolved Questions" metric definition, §3.4). | Captures genuine knowledge gaps, not just web-augmented answers. The repeat-count gate is the difference between this being useful signal vs. flooding the Phase 1 review queue on every one-off miss (discovery's own flagged risk). Needs `N` and a lookup mechanism (query the existing `KnowledgeRetrievalLog` for prior misses on the same `queryHash` — no new table). |
| **C** | Neither automatic trigger. Phase 2 only ships the analytics events (D7); `propose()` wiring itself is deferred to a later phase, opened only by an explicit user-facing "flag this answer" feature (`assistant-correction`, already user-initiated per K0.5). | Splits "wiring the pipe" from "deciding what flows through it" into two even smaller phases. Safest, but means Phase 2 doesn't actually close OQ-K4.2A-2 — a 3rd phase would be needed just for automatic candidate creation. |

**Recommendation: B.** A alone leaves the "assistant can't answer, and we never find out it's a gap" problem completely unaddressed — which is a real part of what K4.2 is for. C defers the actual point of this phase. B's repeat-count gate is a small, bounded, easily-testable addition, not open-ended new scope.

**Depends on / feeds:** D2 (confidence), D3 (timing).

### D2 — Confidence: what number does `propose()` get, and how is it computed?

`ProposeCandidateInput.confidence` (0–1) is required; nothing today computes
it for an orchestrator-originated proposal.

| Option | Description | Tradeoff |
|---|---|---|
| **A** | Derive from retrieval facts (`bestSimilarity`) for both trigger types. | For `unanswered-high-value`, `bestSimilarity` genuinely reflects "how close was the near-miss" — meaningful. For `web-answer-worth-keeping`, `bestSimilarity` reflects how *little* the KB had — it says nothing about the *quality* of the web answer itself. Reusing it there is a stretch, arguably misleading to a reviewer sorting by confidence. |
| **B** | A flat, named constant per trigger type in `KNOWLEDGE_LOOP_CONFIG` (same file `DUP_HARD`/`DUP_SOFT` already live in) — e.g. `web-answer-worth-keeping` always proposes at one fixed value; `unanswered-high-value` scales lightly with repeat count. | Deterministic, auditable, trivially testable. Explicitly a heuristic placeholder, not a computed quality score — must be labeled as such in the contract so a reviewer doesn't mistake it for a real confidence model (matches this program's no-fabrication-default discipline: a fabricated-looking number needs an honest label, not a silent invention). |
| **C** | No real scoring — every candidate proposes at one single fixed minimum (e.g. `0.5`). `propose()`'s own privacy scan + dedup are the real quality gates; `confidence` becomes purely a reviewer-facing sort hint, not a decision input. | Simplest possible implementation, zero new heuristic to defend. Downside: candidates from a strong web answer and a marginal one look identical in the review queue's sort order — but the admin reviewer reads the actual proposed answer before approving either way (K4.2-B), so this may not matter in practice. |

**Recommendation: C.** The real quality gate in this system is the human reviewer (K4.2-B's approve/reject), not a pre-review confidence score — inventing a heuristic formula (B) adds a defend-later decision for marginal benefit, and A's reuse of `bestSimilarity` for the web-answer case is not actually the right signal. If the owner disagrees, B is the fallback, not A.

**Depends on:** D1 (only matters for whichever trigger(s) D1 picks).

### D3 — Timing: does `propose()` run on the answer's critical path, or async?

| Option | Description | Tradeoff |
|---|---|---|
| **A — Eager/awaited** | `answer()` calls and awaits `propose()` before returning. | `candidateCreatedId` populates correctly, matching the field's original intent exactly. Adds real latency (embed + vector search + DB write, all sequential inside `propose()`) to every triggering answer — a genuine product-facing cost on the user's response time. |
| **B — Fire-and-forget, no backfill** | `propose()` is called detached (`void`), after the response is already finalized. `candidateCreatedId` stays `null` forever, as it is today. | Zero latency impact — the answer path is completely unaffected. `KnowledgeCandidate.originatingMessageId` (already exists, K4.2-A) still lets anyone trace a candidate back to its originating turn, so nothing is actually lost — just not joined through the provenance row itself. |
| **C — Fire-and-forget with backfill** | Same as B, but a new `ProvenanceStorePort.update(id, { candidateCreatedId })` method is added and called once `propose()` resolves. | Zero latency impact AND the field gets populated as originally intended. Costs the most new surface area of the three: a new K3-C provenance-store capability (`ports.ts` + `provenance-store.ts`), plus eventual-consistency between the provenance row and the candidate row (a brief window where they disagree). |

**Recommendation: B.** It is the only option with zero latency cost and zero new K3-C capability surface — directly minimizes the diff footprint on files the owner has been explicitly protective of throughout this program. The traceability C would add (via a new port method) is achievable today for free via `originatingMessageId`; C's marginal benefit (one field populated inline vs. reachable one hop away) doesn't obviously justify the new surface area.

**Resolves:** D4 (directly — see below).

### D4 — Provenance: how does `candidateCreatedId` actually get attached (if at all)?

This decision is **not independent of D3** — it's the same decision viewed
from the provenance side. Restated for clarity since the owner listed it
separately:

- If D3 = **A**: `candidateCreatedId` is set inline, in the same
  `buildProvenance()` call, from `propose()`'s real return value.
- If D3 = **B**: `candidateCreatedId` stays `null` permanently (as today).
  The contract should explicitly document that this field is intentionally
  never populated in Phase 2, and that candidate↔turn traceability instead
  goes through `KnowledgeCandidate.originatingMessageId` — a reviewer or
  future K5+ sprint reads the *candidate* row to find its origin, not the
  *provenance* row to find its candidate.
- If D3 = **C**: `candidateCreatedId` is set via the new async backfill
  method, arriving slightly after the provenance row's initial write.

**Recommendation:** follows D3 = B — accept permanent `null`, document the
`originatingMessageId` reverse-lookup as the sanctioned traceability path.

### D5 — Conflict: build `KNOWLEDGE_CONFLICT` detection now, or defer?

| Option | Description | Tradeoff |
|---|---|---|
| **A — Build it now** | Implement real kk/kw (knowledge-vs-knowledge, knowledge-vs-web) contradiction detection as part of Phase 2, populate `ProvenanceFacts.retrieval.conflict` for real, emit `KNOWLEDGE_CONFLICT`. | Discovery found **zero existing detection logic anywhere** — this is net-new orchestrator logic (comparing candidate facts, deciding `chosen`/`basis`), materially larger than every other piece of Phase 2 combined. Would need its own RED-first test suite and arguably its own K-number, by the same "one phase, one bounded scope" discipline this program has used throughout (K4.2-C itself was split into two phases for exactly this kind of size reason). |
| **B — Defer** | `KNOWLEDGE_CONFLICT` is not implemented in Phase 2 at all. `conflict` stays always-null, exactly as it is today. The event-type literal is not added to `AnalyticsEventType` until a later, dedicated sprint builds the real detection logic. | Zero new orchestrator logic. Keeps Phase 2 scoped to "wire up signals the code already computes" — matches this document's own framing that Phase 2 should be low-risk, additive wiring, not new capability-building. |

**Recommendation: B — matches the owner's own instinct** as stated in this
turn: *"Agar K4.2 ka primary objective verified answer → candidate → admin
approval → permanent Knowledge hai, toh conflict detection ko separate
scope mein rakhna cleaner ho sakta hai."* Conflict detection is a real,
independently-scoped feature, not a wiring task — building it inside
"Phase 2" would silently balloon the phase the owner has twice now kept
deliberately narrow.

### D6 — Cache: retrieval-only, or defer both `CACHE_HIT`/`CACHE_MISS` halves?

| Option | Description | Tradeoff |
|---|---|---|
| **A — Retrieval only** | Emit `CACHE_HIT`/`CACHE_MISS` with `cache: "retrieval"` from the existing, real `RetrievalResult.fromCache` boolean. `cache: "answer"` is never emitted — documented as blocked on K5 (`KnowledgeAnswerCache` doesn't exist). | Ships a real, honest, already-computed signal. Contract's §2.1 event definition technically allows both `cache` values; Phase 2 only ever produces one of them — worth stating explicitly in the contract so a dashboard-metric reader doesn't assume `answer` numbers exist. |
| **B — Defer both** | Neither half ships this phase; `CACHE_*` waits entirely for K5. | Avoids a half-implemented event pair, but withholds a real, free, already-available signal (retrieval-cache hit rate) for no real reason — nothing about "answer" cache not existing makes "retrieval" cache data less true. |

**Recommendation: A — already the owner's own stated preference** in this
turn ("Sirf retrieval `CACHE_HIT/MISS`, answer-cache defer"). Recorded here
as the locked answer, not re-opened.

### D8 — INV-1: how is the new `orchestrator → governance` edge structurally locked?

Discovery confirmed the existing INV-1 tests don't cover this edge in
either direction — they assert `agent-framework ↔ knowledge-loop` stays cut,
and that `governance` never touches `Knowledge`/`KnowledgeChunk`. Neither
rule currently says anything about `orchestrator/**` calling
`governance/**`.

| Option | Description | Tradeoff |
|---|---|---|
| **A** | A new structural test (in the Phase 2 validator) asserting exactly which file(s) in `orchestrator/**` may import `governance/**` (only `knowledge-answer-orchestrator.ts`/`ports.ts`/`index.ts`, per whatever D3 wiring shape is chosen) and nothing else — same "assert the boundary, don't just hope it holds" discipline every prior K4.2 sub-sprint used for its own new edge. | One more test to write and maintain; near-zero cost, matches established program discipline exactly. |
| **B** | No new automated test — rely on code review / the file-diff discipline already used at merge time (`git diff` against the baseline, as done in K4.2-C Phase 1 and the post-merge verification). | Cheaper to write, but this specific edge (`orchestrator → governance`) is new and has no structural guard rail if a future change accidentally widens it (e.g., orchestrator starts calling `GovernanceService.approve()` directly, which would be a real violation of "AI may propose, never approve," K4.1 §17). |

**Recommendation: A.** This program has locked every new cross-boundary
edge with an explicit structural test at the moment it was introduced
(K4.2-A locked `governance → Knowledge` non-access; K4.2-B locked the
atomicity/race guards; K4.2-C Phase 1 locked the K3/K1/K2 zero-diff
boundary). Skipping it here would be the first inconsistency in that
pattern, for the one edge this phase actually adds.
