### 1.1 The Assistant answer path, end to end

`app/api/private/knowledge/chat/route.ts` → (after the market-intel gate) →
`createKnowledgeAnswerOrchestrator()` (`services/knowledge-loop/orchestrator/index.ts`,
module-level cached promise) → `KnowledgeAnswerOrchestrator.answer()`
(`knowledge-answer-orchestrator.ts`) → internally:


### 1.2 What K4.2-C Phase 1 actually instrumented (confirmed in code)

`services/analytics/AnalyticsEventService.ts`'s `AnalyticsEventType` union
today contains exactly 5 knowledge-loop values, all comment-labeled
"K4.2-C Phase 1 — Knowledge Governance candidate lifecycle":
`KNOWLEDGE_CANDIDATE_CREATED`, `KNOWLEDGE_CANDIDATE_REVIEWED`,
`KNOWLEDGE_APPROVED`, `KNOWLEDGE_REJECTED`, `KNOWLEDGE_DEPRECATED` — i.e.

and call `.record()` for their own event only. This is the **entire**
existing analytics footprint of the knowledge loop.

### 1.3 `CandidateService.propose()` — the wiring target

Signature: `propose(input: ProposeCandidateInput): Promise<ProposeCandidateResult>`.
`ProposeCandidateInput` requires `createdByUserId`, `canonicalQuestion`,
`proposedAnswer`, `knowledgeType`, `sourceType`, `reasonForCandidate:
CandidateReason`, `confidence` (0-1), optional `evidence.{knowledgeSources,
webSources}`, optional `originatingConversationId`/`originatingMessageId`
(idempotency key). `CandidateReason` (`types/knowledge-loop/index.ts:398-402`)
is a closed union: `"unanswered-high-value" | "web-answer-worth-keeping" |
"assistant-correction" | ...` (4th value present in file, needs full read at
implementation time — not reproduced here since this doc adds no code).

`sourceType === "web_researched"` structurally requires
`evidence.webSources.length >= 1` (enforced inside `propose()` itself) — so a
caller proposing from a web-grounded answer MUST pass `winner.res.webSources`
through.

Governance boundary already proven structurally (K4.2A-D4/D5, INV-1): calling
`propose()` from the orchestrator does **not** violate any existing invariant
— `propose()` only ever writes `KnowledgeCandidate`, never `Knowledge`, and
`KnowledgeCandidate` remains structurally unreachable by retrieval. **The
existing INV-1 tests do not need to change for this reason** — they assert
`agent-framework → knowledge-loop` stays cut, and separately that governance
never touches `Knowledge`/`KnowledgeChunk`; neither is what changes here.
What *does* change is a new edge: `orchestrator → governance`, which today's
test suite has never asserted about in either direction (see §5, Q1).

### 1.4 `KnowledgeAnswerCache` (K5) does not exist

Grepped the full tree: no `KnowledgeAnswerCache` model usage, no
`answer-cache`/`AnswerCache` service file anywhere. Only the retrieval cache
(K2, `KnowledgeRetrievalCache` / `retrieval-cache.ts`) exists, exposed via
`RetrievalResult.fromCache`. **This means `CACHE_HIT`/`CACHE_MISS` with
`cache: "answer"` has no source of truth to fire from — that half of the
event is not implementable until K5.** `cache: "retrieval"` is implementable
today from the existing `fromCache` boolean.

### 1.5 `KNOWLEDGE_CONFLICT` has no detection logic anywhere

`RetrievalResult.conflict` and `ProvenanceFacts.retrieval.conflict` exist as
typed fields (`types/knowledge-loop/index.ts`, `build-provenance.ts`) and are
threaded through (`toRetrievalFacts()` in the orchestrator passes
`r.conflict ?? null`), but **nothing in the codebase ever sets `conflict` to
a non-null value** — grepped every file under `services/knowledge-loop/` for
`conflict` (19 files matched; all are type declarations or `?? null`
passthrough, zero assignment of a real conflict object). The kk/kw
(knowledge-vs-knowledge / knowledge-vs-web) contradiction-detection logic the
contract's `KNOWLEDGE_CONFLICT` event describes (§2.1: `kind`, `aId`,
`bId`/`webDomain`, `chosen`, `basis`) **has never been built.** Emitting this
event for real would mean building that detection logic now — a materially
larger, riskier piece of new orchestrator logic than "add an analytics call
after an existing decision," and arguably its own K-numbered sub-sprint. See
§5, Q2 — **this needs an explicit owner scope decision, not a silent
build-it-anyway or silent skip-it** (per the project's standing
no-fabrication-by-default rule: don't silently comply with an
under-specified ask, and don't silently drop it either — flag it).

## 3. The candidate-proposal trigger rule (needs owner lock before implementation)

The contract's `CandidateReason` gives two triggers that plausibly fire from
inside the orchestrator (the 3rd, `assistant-correction`, is user-initiated —
a "flag this answer" UI action, likely its own small feature outside
`knowledge-answer-orchestrator.ts` entirely, e.g. a new route calling
`propose()` directly; not analyzed further here since it doesn't touch K3-C
code):

- **`web-answer-worth-keeping`** — an answer that used web search
  (`sourceClassIfGenerated ∈ {CLAUDE_WEB_SEARCH, MIXED}`) and produced a
  clean, non-forbidden, non-deterministic-fallback answer. `sourceType:
  "web_researched"`, `evidence.webSources` = `winner.res.webSources`
  (satisfies `propose()`'s own structural check, §1.3).
- **`unanswered-high-value`** — a `KNOWLEDGE_MISS` (retrieval insufficient)
  that still got answered from general model reasoning
  (`sourceClass === CLAUDE_REASONING`), i.e. the gap the contract's §3.4
  "Unresolved Questions" metric is meant to surface. Needs a repeat-question
  or confidence threshold to avoid proposing on every single miss — the
  contract doesn't lock this threshold anywhere; **this is a real open
  design decision, not just a wiring detail** (see §5 Q5).

Both triggers need a `confidence` (0-1) value `propose()` requires — nothing
in `AnswerResult`/`AnswerGenResult` currently computes one. Likely candidate:
derive from `retrieval.bestSimilarity` for knowledge-adjacent cases, or a
flat heuristic constant for pure-web/reasoning answers — **this is a new
small pure function, not present today, and needs its own owner sign-off on
the heuristic**, not just where to put it.

**Recommendation:** given `unanswered-high-value`'s repeat-question
threshold is undefined and `web-answer-worth-keeping`'s confidence heuristic
is undefined, Phase 2's *contract* (the deliverable this discovery feeds)
should lock both explicitly — this discovery doc surfaces that they're
missing, it doesn't invent values for them.

## 4a. `propose()` latency + `candidateCreatedId` backfill (found in a parallel discovery pass, folded in here)

Two things worth flagging before locking the candidate-wiring design, on top
of §3's trigger-rule gap:

**`propose()` is not free.** Reading `candidate-service.ts`: it does an
idempotency lookup, a privacy/forbidden-language scan, **an embedding call**,
**a vector-similarity search** (dedup against active knowledge), and a DB
write — all awaited, sequentially. That is meaningfully more expensive than
every other analytics call in this phase (all fire-and-forget
`.record(...).catch(() => {})`, per contract §2.3's "never on the critical
path" rule). Calling `propose()` inline and awaited inside `answer()` before
the response returns would add all of that latency to every triggering
answer — a real product-facing cost, not just an implementation detail.

**`candidateCreatedId` has no backfill path today.** `ProvenanceStorePort`
(`orchestrator/ports.ts`) exposes only `write()` — no `update()`. If
candidate proposal instead runs fire-and-forget *after* the response is
already returned (avoiding the latency above), there is currently no
mechanism to go back and set `candidateCreatedId` on the provenance row that
was already written with `null`. Three real options exist, none free:

- **(a) Eager/awaited** — accept the latency; `candidateCreatedId` gets
  populated correctly in the same write, matching the field's original
  intent exactly.
- **(b) Fire-and-forget, no backfill** — `candidateCreatedId` stays `null`
  forever (as it is today); a candidate is still traceable back to its
  originating turn via `KnowledgeCandidate.originatingMessageId` (already
  exists, K4.2-A). Zero latency impact, but the field never gets populated
  by anything, ever — worth asking whether it should be retired/repurposed
  instead of left permanently null.
- **(c) Fire-and-forget with backfill** — add `ProvenanceStorePort.update(id,
  { candidateCreatedId })` (a new, small K3-C file change to `ports.ts` +
  `provenance-store.ts`), called once `propose()` resolves. Zero latency
  impact AND the field gets populated as intended, at the cost of a new
  provenance-store capability and eventual consistency between the two rows.

This needs the same explicit owner lock as the trigger-rule and confidence
questions in §3/§5 — see §5 Q8 below.

## 5. Open questions requiring an explicit owner decision before implementation

1. **INV-1 scope.** The existing INV-1 tests assert `agent-framework →
   knowledge-loop` is cut and `governance` never touches `Knowledge`/
   `KnowledgeChunk`. Neither assertion covers the NEW edge this phase adds:
   `orchestrator → governance` (the answer path calling `propose()`). Should
   a new, explicit structural test lock this edge (e.g. "orchestrator may
   call `CandidateService.propose()` and nothing else in governance") the
   same way K4.2-A locked its own boundary? (Recommended: yes — this is
   exactly the kind of coupling the owner has been careful to gate at every
   prior step.)
2. **`KNOWLEDGE_CONFLICT` scope (§1.5).** No detection logic exists. Options:
   (a) build real kk/kw conflict detection this phase (materially larger
   scope than the rest of Phase 2 combined), (b) explicitly defer
   `KNOWLEDGE_CONFLICT` emission to a later phase/K-number and say so in the
   contract, (c) something narrower the owner has in mind. This discovery
   does not recommend a default — it's flagged, not resolved.
3. **`AnalyticsPort` duplication.** `governance/ports.ts` already defines an
   `AnalyticsPort` shape (used by `CandidateService`/`GovernanceService`).
   Should the orchestrator/K1/K2 side import that same type (from
   `governance/ports.ts` or a new shared location), or define its own
   structurally-identical port to keep the K3-C/K1-K2 ↔ K4.2 boundary
   textually separate? Precedent (`RetrievalPort` narrowing `KnowledgeService`)
   suggests "narrow, don't reuse the wide type," but reusing a trivial
   1-method interface may be fine — owner call.
4. **`ProposeCandidateInput` sufficiency.** Needs a final confirm-by-reading
   of the full `CandidateReason` union and `ProposeCandidateInput` optional
   fields (this discovery read enough to locate the trigger points, not a
   full line-by-line of `types/knowledge-loop/index.ts`) before the contract
   can assert "no new field needed" with full confidence.
5. **`unanswered-high-value` firing threshold (§3).** Every miss, or only
   repeat misses (same `queryHash` recurring N times, mirroring the
   contract's own "Unresolved Questions" metric definition in §3.4)? Firing
   on every miss risks flooding the candidate queue K4.2-C Phase 1 just
   built review UI for.
6. **`web-answer-worth-keeping` confidence heuristic (§3).** What value/
   formula, and does it need `KNOWLEDGE_LOOP_CONFIG` additions (same file
   K4.1 already used for `DUP_HARD`/`DUP_SOFT`)?
7. **CACHE_HIT/MISS answer-cache half (§1.4).** Confirm the owner is fine
   with Phase 2 emitting only `cache: "retrieval"` events and leaving
   `cache: "answer"` as a documented future-K5 gap, rather than either
   fabricating an answer-cache signal or silently omitting the field from
   the contract.
8. **Candidate-proposal timing (§4a).** Eager/awaited (adds real latency to
   the critical path, but `candidateCreatedId` populates correctly) vs.
   fire-and-forget with no backfill (zero latency cost, `candidateCreatedId`
   stays permanently `null`) vs. fire-and-forget with a new
   `ProvenanceStorePort.update()` backfill method (zero latency cost, field
   gets populated, but adds a new K3-C provenance-store capability). No
   default is recommended here — this is the owner's call, and it shapes
   how big the `ports.ts`/`provenance-store.ts` diff in §2.1 actually is.
