# D2.6.9 — Verified Intelligence Audit, Explainability & Answer Traceability

**Status:** Implemented and tested.
**Scope:** An immutable audit/provenance layer over the existing D2.5.x/D2.6.x deterministic pipeline and D2.6.8's presenter orchestration. This sprint computes nothing new about the market — it records, deterministically and permanently, what the system already knew and did.

**Non-negotiable principle** (repeat before touching any file here): a trader must never receive an answer that cannot be traced back to the verified intelligence available at the time of analysis. This layer is what makes that claim checkable after the fact. It is an **audit/traceability layer, not a second reasoning engine** — every field it writes is either a direct, immutable copy of an already-computed value, or a real, deterministic classification derived from one.

---

## 1. Audit architecture

`IntelligenceAuditTrace` (`types/intelligence-audit-trace.ts`) is created exactly once per **presented answer** — a resolved real-time intelligence turn whose envelope was actually handed to the D2.6.8 `AIPresenterOrchestratorService`. A clarification-required or insufficient-data turn has no presented answer and therefore no audit trace: there is nothing to trace. This scope was a deliberate design choice, not an oversight — the sprint's own repeated framing is "a trader must never receive an **answer** that cannot be traced," not "every internal state must be logged."

The pipeline is a strict composition, implemented in the new `IntelligencePresentationService` (`services/intelligence/chat/intelligence-presentation.service.ts`):

```
User Question
  -> IntelligenceChatContextService   (D2.6.5/D2.6.7, unmodified)
      -> RealTimeIntelligenceService   (D2.6.5, unmodified)
          -> IntelligenceQueryContext  (D2.6.2, unmodified)
  -> AIPresenterOrchestratorService    (D2.6.8, additively extended)
  -> AIResponseIntegrityService        (D2.6.5, unmodified - re-invoked, never replaced)
  -> AuditTraceService.createTrace()   (D2.6.9, new)
  -> Response
```

This is the sprint's own required flow, verified end to end (`scripts/validate-intelligence-audit.ts`, section L). `AuditTraceService` and `ExplanationService` are pure classification/persistence boundaries — neither imports `lib/ai`, a market-data provider, or any 15D/D2.5 engine's computation logic. `IntelligencePresentationService` is the **only** new coupling point the chat route touches, preserving the "route only imports the chat-facing layer" invariant D2.6.5 established and every subsequent sprint (D2.6.7, D2.6.8) preserved in turn — confirmed by re-running all 11 zero-coupling regression scripts after the route change.

## 2. Provenance model

`AuditMarketDataProvenance` reuses D2.6.3/D2.6.4/D2.6.5 fields verbatim — `provider`, `providerSymbol`, `fallbackUsed`, `cached`, `cacheAgeMs`, `freshnessStatus`, the real source timestamp, and (when at least `MIN_RELIABILITY_OBSERVATIONS` real outcomes exist) the winning provider's own `ProviderReliability` state, looked up from the existing, unmodified shared `MarketDataService` singleton's `healthReport()`. No second provider-health system was built.

**Honest scope boundary, stated explicitly rather than papered over**: `MarketDataService.getSnapshot()`/`getMarketContext()` accumulate a per-request list of provider failures internally, but only to build a single aggregate error on total failure — that list is discarded on a successful call, never returned to the caller. There is therefore no real, structural way today to reconstruct an exact ordered "Twelve Data → failed, Alpha Vantage → failed, Binance → unavailable, Angel One → success" attempt sequence without modifying `MarketDataService`'s hot, heavily-tested return path — an invasive change the sprint's own "do not build another provider-health system" instruction argues against. Rather than fabricate a plausible-looking ordered list this program has no real data for, the audit trace honestly records the one signal that **is** real and already tracked — `fallbackUsed: boolean` — and states this exact scope limitation in the trace's own `basis` array whenever a fallback occurred. This is the same "never fabricate, always disclose the honest limitation" discipline that runs through every prior sprint in this program (see, e.g., D2.6.1's `DecisionMissingInformationItem` or D2.5.5's `IntelligenceScoreComponentUnavailable`).

## 3. Immutable snapshot model

Every audit trace embeds a full, immutable copy of the real `IntelligenceEnvelope` and `IntelligenceDecisionContext` at analysis time. Together, this single pair already contains everything the sprint's §4 required — `MarketState`, `Regime`, `Hypotheses`, `EvidenceBundle`, `RiskProfile`, `HistoricalValidation`, and `IntelligenceScore` (via the envelope), plus the trader-facing `DecisionContext` view. `IntelligenceQueryContext` itself is deliberately **not** duplicated in full — it is a relevance-filtered subset of these same two objects (D2.6.2's own framing); only its distinguishing fields (`completeness`, `relevanceBasis`, `missingContext`) are captured directly on the trace, per the sprint's own "do not duplicate large payloads unnecessarily" instruction.

Nothing here is recomputed on read. `AuditTraceService.getTrace()` returns the exact bytes written at creation time — describing what the system knew **then**, never what the market looks like now. Verified directly (`scripts/validate-intelligence-audit.ts`, section E): a second trace built from a genuinely different market state, regime, and Intelligence Score never alters an earlier trace's own stored snapshot, re-read from the database after the second trace was created.

## 4. Provider (presenter) trace

`AuditPresenterTrace` is built directly from D2.6.8's own `PresenterOrchestrationResult` — `selectedProvider` (the real `presentedBy`), one `AuditPresenterAttemptTrace` per real attempt (provider, attempted, success, latencyMs, failureCategory, timestamp), and `fallbackUsed`. One small, additive extension was made to D2.6.8's own `PresenterAttempt` type: an optional `integrityViolationKinds?: ResponseIntegrityViolationKind[]`, populated only when an attempt is rejected on integrity grounds. This exists because a rejected candidate's text is never surfaced or persisted anywhere else in the pipeline — without recording the violation kinds at rejection time, "if fallback was used, why?" would be structurally unanswerable after the fact. The recorded value is a closed, safe vocabulary (`unsupported-numeric-claim`, `guaranteed-profit-language`, etc.) — never raw response text, never a sensitive error detail. Verified that this extension is fully backward-compatible: every pre-existing D2.6.8 test (66/66) still passes unmodified.

The trace's own `integrity: ResponseIntegrityResult` field is filled by re-invoking `validateResponseIntegrity()` — the exact same, unmodified D2.6.5 function — against the exact final response text. This was a deliberate design choice over threading a new field through `PresenterOrchestrationResult`: the check is pure and cheap, and re-running it costs nothing while keeping D2.6.8's own result type untouched for the accepted-response case.

## 5. Claim traceability

`traceResponseClaims()` (`services/intelligence/audit/response-claim-tracer.service.ts`) is the sprint's required "deterministic response traceability checker" — explicitly **not** another LLM judging the first one's output, and explicitly not unrestricted natural-language semantic reasoning. It reuses, via additive exports, the exact extraction/matching functions `AIResponseIntegrityService` (D2.6.5) already validates against — numeric-claim extraction, real-value tolerance checks, the real canonical-instrument list, the closed foreign-indicator/guaranteed-profit/high-certainty pattern sets. Nothing is duplicated or reimplemented.

Four categories, matching the sprint's own required distinction:
- **supported** — the claim matches a real value/state in the verified context (within the same documented tolerances D2.6.5 already uses).
- **unsupported** — the claim has no real counterpart anywhere in the context (a foreign indicator, a historical claim with no real segment, a number nowhere close to anything real). "The model said something that was not present."
- **conflicting** — the claim directly misstates something the system *does* know: a numeric value close enough to a real one to be clearly referencing it but wrong (a documented, honestly-labeled "V1 heuristic" 20% band, wider than the pass tolerance), a different real instrument named instead of the one being discussed, over-certainty against a real unresolved conflict or insufficient-intelligence state, or the Intelligence Score restated as a probability of profit. "The model said something that directly conflicts with verified context."
- **unverifiable** — a narrow, explicitly documented set of hedging/qualitative markers ("might", "seems", "possibly") this checker does not attempt to resolve either way, flagged honestly rather than silently forced into supported or unsupported.

## 6. Authorization

Every read is scoped by `(traceId, userId)` in the same query — `AuditTraceService.getTrace()` returns `null` for a stranger's request, a forged/nonexistent traceId, an empty userId, or a genuinely missing trace, all indistinguishable from each other (no existence leak). Creation never trusts a client-supplied ownership claim. `conversationId`/`analysisRunId` are loose references (matching `PersistedConversationContext.lastAnalysisRunId`'s established convention) rather than hard foreign keys — a forged or nonexistent reference never blocks trace creation, since the trace's own authenticity depends only on `(traceId, userId)`, not on the referenced record actually existing. Verified directly, including through the new `GET /api/private/intelligence/audit/[traceId]` route's own ownership boundary (which delegates to the identical `AuditTraceService.getTrace()` check).

## 7. Historical immutability

`AuditTraceService` has no update or delete method — verified structurally, not just by convention (`scripts/validate-intelligence-audit.ts`, "E5"). A later re-analysis of the same symbol always creates a brand-new trace via `createTrace()`; it never rewrites an earlier one. This is critical for research integrity: an audit trace is a permanent record of what the system knew and did at one specific moment, and a future viewer must be able to trust that it has not been quietly revised.

## 8. Why audit data is not intelligence

Nothing in `IntelligenceAuditTrace`/`ResponseClaimTrace`/`AuditPresenterTrace` feeds back into any deterministic engine, the Intelligence Score, or any future analysis. It is read-only observability about how an already-computed answer was produced and presented. This mirrors D2.6.8's own explicit boundary for `PresenterFailureCategory` ("never an Intelligence Score component") — extended here to the entire audit surface.

## 9. Why the LLM cannot modify the audit

The presenter never receives the audit trace, never writes to `AuditTraceService`, and has no code path that could alter `envelope`/`decisionContext`/`marketData` after the fact — those are captured from the same real, already-verified objects the presenter itself was given, by a caller (`IntelligencePresentationService`) the presenter has no access to. `AIPresentationResult`'s narrow shape (D2.5.5, unmodified) already prevents a presenter from returning anything the audit layer could mistake for a new fact.

## 10. Why historical snapshots are immutable

Because the entire premise of this sprint is that a trader — or a future auditor, or the system itself evaluating a past hypothesis's outcome (D2.5.4) — must be able to trust that "what the system said it knew on this date" cannot have been quietly revised after the fact. An immutable, create-only model is the only way to make that guarantee structural rather than a documentation promise.

## 11. Chat integration

`app/api/private/knowledge/chat/route.ts` now calls `IntelligencePresentationService.present()` in place of the previous separate `IntelligenceChatContextService.resolve()` + `AIPresenterOrchestratorService.present()` calls — still importing only the chat-facing layer, never a 15D/D2.5 internal or a market-data provider directly. All 11 zero-coupling regression scripts, `validate:orchestration`, `validate:realtime-intelligence` (D2.6.5, 47/47), `validate:conversation-continuity` (D2.6.7, 53/53), and `validate:ai-presenter-orchestration` (D2.6.8, 66/66) were re-run after this change and pass with zero regressions.

## 12. Testing note (worth recording for future validate scripts)

While building `scripts/validate-intelligence-audit.ts`, the two-statement dotenv pattern established in D2.6.6/D2.6.8 (`import dotenv from "dotenv"; dotenv.config(); dotenv.config({path:".env.local", override:true});`) produced a genuine `ECONNREFUSED` failure the moment a script combining that pattern with a real, eager-at-module-load Prisma client (`lib/prisma.ts` constructs its client at module top level) was written for the first time. Root cause: ES module import declarations are all evaluated, in source order, **before** any of the importing module's own top-level statements run — so `dotenv.config()` as a plain statement sandwiched between `import` lines runs too late to affect how an eagerly-evaluated import like `lib/prisma.ts` reads `process.env.DATABASE_URL`. Neither prior script using this pattern (`validate-indian-market-data.ts`, `validate-ai-presenter-orchestration.ts`) happened to import anything that touches `lib/prisma.ts` eagerly, so the bug was latent until now. Fixed by using the side-effect import form (`import "dotenv/config";`) for the base `.env` load — itself an import declaration, guaranteed to evaluate before `lib/prisma` — with the `.env.local` overlay applied as a normal statement afterward (safe, since nothing needing it is read at module-evaluation time). **Any future validate script that both needs `.env.local` and imports anything that touches `lib/prisma.ts`** should use this exact ordering, not the plain two-statement form.
