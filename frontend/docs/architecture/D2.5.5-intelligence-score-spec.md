# D2.5.5 — Deterministic Intelligence Score & Intelligence Envelope

**Status:** Implemented and tested. This is the authoritative contract for the future AI Presenter layer.
**Scope:** A deterministic quality score over the existing D2.5.1-D2.5.4 outputs, plus the canonical `IntelligenceEnvelope` bundle and the `AIIntelligencePresenter` interface. No ML, no LLM scoring, no Gemini/Claude/OpenAI integration, no trading signals, no automatic scheduler, no UI.

---

## 1. Purpose

Every prior D2.5.x sprint produced one real, deterministic piece of intelligence: `MarketState` (observation), `Regime` (classification), `Hypothesis` (falsifiable claim), `IntelligenceAnalysisRun`/`Outcome` (persistence + real-data evaluation), `HistoricalValidation` (honest aggregate statistics). Nothing until now measured **how good the available intelligence actually is** in one transparent, explainable number. `IntelligenceScoreService` (`services/intelligence/score/intelligence-score.service.ts`) is that measurement layer, and `IntelligenceEnvelopeService` (`services/intelligence/envelope/intelligence-envelope.service.ts`) is the canonical bundle that carries it, alongside everything it was computed from, to a future presentation layer.

## 2. What Intelligence Score means

"Intelligence quality score: 78/100" means: *the evidence, market observation, regime classification, hypothesis, risk context, and historical track record available to the system for this analysis are, on the documented deterministic formula below, 78% as complete/consistent/well-supported as they could be.* Every number is traceable to real, already-computed fields (`types/intelligence-score.ts#IntelligenceScoreComponent.basis`) - never an LLM's impression, never a trained model's output.

## 3. What it does NOT mean

It is **never**: a probability of profit, a probability of price direction, a trade-success probability, a BUY/SELL confidence, an expected return, or a prediction-accuracy claim. "85/100" must never be read or presented as "85% chance of winning" - those are two different claims, and only the first one is true of this system. This score is also explicitly **not** the same concept as the existing Sprint 15D.7 `ConfidenceProfile` ("model confidence") - see §14.

## 4. Components

Eight components, each a discriminated union (`IntelligenceScoreComponent`, `types/intelligence-score.ts`):

```ts
{ dataAvailable: true;  score: number;    basis: string[] }
| { dataAvailable: false; score: undefined; basis: string[] }
```

This is a deliberate deviation from the sprint brief's literal `{score: number, basis, dataAvailable: boolean}` snippet, in favor of its explicit spirit ("do NOT silently convert unavailable data into 0"): the type system itself makes it impossible to write `dataAvailable: false, score: 0` by accident. `basis` always explains *why* - a real low score ("known weak"), no data supplied ("unknown"), or genuinely nothing to measure ("not applicable") all collapse to `dataAvailable: false`, distinguished only by the `basis` text (the sprint's own contract doesn't ask for a third enum state).

| Component | Reuses |
|---|---|
| `dataQuality` | `MarketState.dataQuality` (D2.5.2, itself `types/technical-context.ts#DataConfidence`) + `MarketState.snapshot` |
| `evidenceQuality` | `EvidenceBundle.items` (15D.4) |
| `evidenceAgreement` | `EvidenceBundle.conflicts` (15D.4, already-detected, never re-derived) |
| `marketStateQuality` | `MarketState.structure`/`dataQuality` (D2.5.2) |
| `regimeConfidence` | `Regime.confidence` (D2.5.2) - reused verbatim, never recomputed |
| `hypothesisStrength` | `Hypothesis[]` (D2.5.3) |
| `riskAwareness` | `RiskProfile.categories` (15D.6) |
| `historicalValidation` | `HistoricalValidation` (D2.5.4) - reused verbatim, never recomputed |

## 5. Component formulas

**Data Quality** — `round(100 * dataQuality.computed / dataQuality.total)`. `basis` cites the exact indicator ratio, the band, and whether the snapshot was live or cache-served (informational only, never penalized - no documented staleness threshold exists anywhere in this codebase to justify one).

**Evidence Quality** — average of two real, deterministic fractions over `evidence.items`: the fraction with non-empty `source` (attribution), and the fraction that are unique by `type+symbol+claim` (non-duplication). Zero items → a real `0` (not unavailable - the codebase's own `confidence-engine.service.ts` precedent for "no evidence" is exactly this: a real, low, known score).

**Evidence Agreement** — `1 - min(1, conflictingItemCount / totalItems)`, where `conflictingItemCount` is the count of distinct items appearing in at least one of `evidence.conflicts` (real, already-detected by the 15D Evidence engine - never re-resolved or re-derived here). Zero items → `dataAvailable: false` ("not applicable - nothing to compare"), distinct from the zero-conflict case (`dataAvailable: true, score: 100`).

**MarketState Quality** — average of four checks: the same technical-indicator ratio as Data Quality (sprint §8 explicitly lists it as an input here too - the two components are allowed to overlap, per the brief's own component descriptions), plus three binary structural-completeness checks (`structure.trend`, `structure.recentRange`, `structure.volatilityBand`/`atrPercent` present). The four permanently-unimplemented `MarketStateStructure` fields (`liquidityZones`, `volumeDelta`, `bos`, `choch` - see `types/intelligence-market-state.ts`'s own header) are **never referenced anywhere in this formula** - not "penalized as 0", structurally absent from the calculation entirely.

**Regime Confidence** — `regime.confidence` verbatim. No new computation.

**Hypothesis Strength** — `undefined` if hypothesis generation was never attempted; a real `0` with an explanatory basis if it was attempted and genuinely produced none (3 of 10 regime types never generate a hypothesis - see `hypothesis.service.ts`); otherwise `60 + min(1, supportingEvidence.length / 3) * 40` per hypothesis, averaged. The baseline 60 reflects that every D2.5.3-generated hypothesis is already structurally guaranteed to have real `supportingEvidence`, a real `invalidationCondition`, and a real `predictionWindow` (`Hypothesis`'s own contract) - the bonus rewards how much supporting evidence backs it, saturating at 3 items (same "documented, untuned round-number target" style as `confidence-engine.service.ts`'s `EVIDENCE_QUANTITY_TARGET`).

**Risk Awareness** — `round(100 * categoriesWithRealBasis / 8)`, where "real basis" means `RiskCategoryScore.basis.length > 0` (an actual attributed `EvidenceItem`, not just a rationale sentence). `liquidity`/`execution` are permanently `basis: []` by `RiskEngineService`'s own documented design (no evidence source exists in this platform for either) - this is never presented as a Risk Awareness *failure*, only as an honest count, with the excluded categories named explicitly in `basis`.

**Historical Validation** — `round(historicalValidation.validatedRate * 100)` verbatim, only when `validatedRate` is defined (i.e., the D2.5.4 sample met `MIN_HISTORICAL_VALIDATION_SAMPLE`). No independent recomputation.

## 6. Weights

```
Data Quality              15
Evidence Quality          15
Evidence Agreement        10
MarketState Quality       15
Regime Confidence         15
Hypothesis Strength       10
Risk Awareness            10
Historical Validation     10
                          ---
                          100
```

**Audit performed before implementation, per the sprint's explicit instruction**: the four highest-weighted components (Data Quality, Evidence Quality, MarketState Quality, Regime Confidence) are exactly the components that are *always attemptable* the moment a `MarketState` exists - they don't depend on a hypothesis having been generated, on a sufficient historical sample existing, or on a `RiskProfile` having been supplied. The four lower-weighted components are more derived or more often absent in practice (Historical Validation specifically is gated behind a 30-sample minimum that most segments won't meet for a long time). This ordering is defensible against what's actually reliably available, but it is **explicitly labeled a "V2 heuristic deterministic weighting"** (`IntelligenceScoreService`'s own header comment) - not statistically optimized, because there isn't remotely enough real outcome data yet to optimize against without being circular (the same honesty constraint D2.5.4 already documented for `MIN_HISTORICAL_VALIDATION_SAMPLE`).

## 7. Missing-data semantics

Never converted either direction: an unavailable component is never `0` (which would claim "we know this is bad") and never silently `100` (which would claim "we know this is perfect"). Every component that is genuinely `dataAvailable: false` is **excluded from the weighted average entirely**, and the remaining eligible components' weights are renormalized to sum to 100 among themselves (`eligibleWeightSum = sum(WEIGHTS[k] for k in eligible)`; each eligible component's effective weight becomes `WEIGHTS[k] / eligibleWeightSum`). The excluded components are named explicitly in the top-level `basis` array - a caller can always see exactly which 8-of-8 (or fewer) components produced the number.

## 8. Critical-data ceilings

Renormalization alone isn't enough: a handful of genuinely excellent components could otherwise renormalize into a misleadingly high score while the system is fundamentally uninformed. Two explicit, documented ceiling constants (never empirically tuned) cap the final `overallScore`:

- **`CEILING_INSUFFICIENT_REGIME = 40`** — applied whenever `regime` is unavailable *or* `regime.regimeType === "insufficient-data"`. Verified directly: an analysis whose `MarketState` is too thin to classify (3 candles) never reports above 40, regardless of how complete its evidence/risk context looks.
- **`CEILING_NO_MARKET_STATE = 25`** — applied whenever no `MarketState` was supplied at all - the most fundamental input missing. The lower of the two applies when both trigger.

A **data-completeness penalty** (`COMPLETENESS_PENALTY_PER_MISSING_COMPONENT = 2` points per excluded component) is subtracted before clamping - satisfying the sprint's explicit "never hide missing components behind a blindly-averaged high score" instruction with a small, honestly-labeled, additional deduction on top of renormalization.

`overallScore` is `undefined` only in the total-blackout case: every one of the 8 components was unavailable. This is a deliberate deviation from the sprint's literal `overallScore: number` snippet, for the same reason as §4 - fabricating a number with zero real inputs would be worse than an honest "cannot be computed."

## 9. Historical-validation semantics

Governed entirely by D2.5.4's own `MIN_HISTORICAL_VALIDATION_SAMPLE` and `validatedRate` semantics - never recomputed or re-interpreted here. Below the minimum sample, the component is `dataAvailable: false` with a `basis` line naming the exact sample size vs. the minimum (matching the sprint's own literal example text). Because unavailable components are fully excluded from the weighted average (§7), a small, lucky-looking historical sample can never inflate the overall score - it simply isn't counted until it earns real statistical weight.

## 10. Versioning

`IntelligenceScore.methodology.version` (`INTELLIGENCE_SCORE_METHODOLOGY_VERSION = "1.0.0"`) is independent of `intelligenceEngineVersion` - it bumps only when the scoring formula, weights, or component logic itself changes, never when an upstream engine (`MarketState`/`Regime`/`Hypothesis`) changes. `pipelineVersion` (`MARKET_INTELLIGENCE_PIPELINE_VERSION`, currently `"15D.12.0"`) and `intelligenceEngineVersion` (`INTELLIGENCE_ENGINE_VERSION`, currently `"2.0.0"`) are both static constants imported unchanged from their respective owning services - this sprint does not bump either.

## 11. Intelligence Envelope

`IntelligenceEnvelope` (`types/intelligence-envelope.ts`) is the single canonical, verified bundle: `marketState`, `regime`, `hypotheses`, optional `evidence`/`conflicts`/`risk`/`confidence`/`historicalValidation`, the freshly computed `intelligenceScore`, plus version/timestamp metadata. `IntelligenceEnvelopeService.build()` is a pure assembler - it never fetches data, never calls an LLM, and never fabricates a missing optional field; it computes `intelligenceScore` by delegating to `IntelligenceScoreService` with the exact same inputs it was given, and derives `conflicts` as a direct mirror of `evidence?.conflicts` (never a separate detection pass).

`confidence?: ConfidenceProfile` (the existing 15D.7 "model confidence" concept) is included for the presenter's awareness but is **never consumed by `IntelligenceScoreService`'s own formula** - see §14 for why the two must stay architecturally separate rather than have the new score quietly depend on the old one.

`historicalValidation` is included only when `hypotheses.length === 1` (matching D2.5.3's current at-most-one-hypothesis-per-regime behavior) - `IntelligenceEnvelopeService` enforces this structurally rather than trusting the caller, dropping it silently (never guessing which hypothesis it belongs to) when zero or multiple hypotheses are present.

## 12. AI Presenter boundary

`AIIntelligencePresenter` (`types/intelligence-envelope.ts`) is a single-method interface: `present(envelope, userQuestion): Promise<AIPresentationResult>`. `AIPresentationResult` is deliberately narrow - `{text, presentedBy, envelopeGeneratedAt}` only. There is no field for a new evidence item, hypothesis, regime, risk level, or historical-validation number. This is an architectural guarantee, not a convention: a presenter implementation *cannot* return a new market fact through this interface's type, because the type has nowhere to put one. The presenter receives verified intelligence and presents it; it can never become the source of it.

No concrete implementation is wired up in this sprint - not Gemini, not Claude, not OpenAI. The existing Gemini restate-only behavior and `AI_COMMUNICATION_POLICY` (`lib/ai/response-policy.ts`) are completely unchanged and unweakened.

## 13. Future multi-model architecture

The interface is designed so a future sprint can add `GeminiPresenter`, `ClaudePresenter`, `OpenAIPresenter`, or any other `implements AIIntelligencePresenter` class without a breaking change to `IntelligenceEnvelope` or the interface itself - each concrete presenter would simply translate a real `IntelligenceEnvelope` into natural language using its own model, constrained to the same narrow `AIPresentationResult` return shape. Not built in this sprint, per the explicit stop condition.

## 14. Security/data-honesty rules

- **No LLM/network dependency in the score engine itself**: `IntelligenceScoreService`/`IntelligenceEnvelopeService` are pure, synchronous, and import nothing from `lib/ai`, `@google/genai`, or any HTTP client - verified by a dedicated structural regression test that scans both files' import statements and raw source for `fetch(`/`XMLHttpRequest`.
- **Intelligence Score vs. model confidence are permanently distinct concepts** (sprint §4): `ConfidenceProfile` (15D.7) is exposed on the envelope purely for a presenter's context, never folded into `IntelligenceScore`'s own formula. A UI that ever surfaces both must label them separately (e.g. "Intelligence Quality" vs. "Model Confidence"), never as interchangeable numbers.
- **No prediction language anywhere in this engine's output**: no field, constant, or basis string in this sprint's code says "bullish probability," "win probability," "expected profit," or similar - grep-verifiable, and enforced by convention alongside every other D2.5.x sprint's compliance work (D2.3.S4).
- **Determinism**: identical input → byte-identical `IntelligenceScore`/`IntelligenceEnvelope` (`generatedAt` is always caller-supplied, never `Date.now()` internally) - verified directly.

## 15. Known limitations

- `evidenceQuality`'s "currency"/freshness dimension (sprint §6: "evidence is current enough") was deliberately **not** implemented as a wall-clock-based check - doing so would require comparing against `Date.now()` inside the score engine, breaking the determinism guarantee this sprint also requires. A future sprint could add a real freshness check based on a caller-supplied `asOfTime` parameter without breaking this contract.
- `hypothesisStrength` averages all hypotheses in the array, but D2.5.3 currently generates at most one per regime - the multi-hypothesis averaging path is real code but not yet exercised by any real caller.
- `historicalValidation` on the envelope is single-valued and tied to the one-hypothesis-per-regime assumption (§11) - a future sprint generating multiple simultaneous hypotheses would need a multi-segment shape here, not built ahead of that real need.
- `riskAwareness`'s "categories with real basis" proxy is a structural signal (whether `RiskCategoryScore.basis` is non-empty), not a semantic one - it does not and cannot distinguish "this category was thoroughly assessed" from "this category happened to have one attributable evidence item." Documented as a known simplification, not silently assumed precise.
