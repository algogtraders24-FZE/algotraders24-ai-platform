## 6. Candidate-trigger semantics (D1 = B, LOCKED)

**K4.2C-P2-D1: LOCKED.** Exactly two automatic triggers, both evaluated
inside `KnowledgeAnswerOrchestrator.answer()`, after a `generated` outcome
(never for `finishDeterministic()`'s three deterministic terminals —
account-specific, chain-exhausted, dynamic-unverifiable — none of those
produce a real fact worth proposing):

| Trigger | Fires when | `sourceType` | `reasonForCandidate` |
|---|---|---|---|
| `web-answer-worth-keeping` | The winning outcome is `generated`, `winner.res.webSearchUsed === true`, and the answer passed the forbidden-language scan (i.e. it reached `attempts.push({..., ok: true})` — already guaranteed by the time `outcome` is built). | `"web_researched"` (Prisma enum `KnowledgeSourceType`, confirmed exists) | `"web-answer-worth-keeping"` (confirmed `CandidateReason` literal) |
| `unanswered-high-value` | `retrieval.sufficiency === "INSUFFICIENT"` (a true `KNOWLEDGE_MISS`, per §2.1's own definition — not `"LOW"`/`"STALE"`, which are `KNOWLEDGE_LOW_RELEVANCE` territory, a different signal not wired to candidate creation this phase) **and** the repeat-count gate (§7) passes. | `"unanswered_question"` (confirmed `KnowledgeSourceType` literal — the enum already anticipated exactly this case) | `"unanswered-high-value"` (confirmed `CandidateReason` literal) |

**Mutual exclusivity:** a turn can fire at most one trigger — `web-answer-
worth-keeping` requires `webSearchUsed === true`, which by `decide-path.ts`'s
existing gate logic never co-occurs with `retrieval.sufficiency ===
"INSUFFICIENT"` driving the *proposal* decision (the web-search gate may
still have been *offered* on a miss, but if it was used and produced a
clean answer, that answer — not the miss — is the fact worth capturing).

**Not automatic, explicitly out of scope for this phase:** `assistant-
correction` (K0.5: user-initiated "flag this answer," a separate future UI
feature, not an orchestrator-turn trigger), `admin-flagged`,
`support-resolution`, `imported-doc` — none of these originate from
`answer()`.

**Idempotency-key precondition (found while drafting, not in discovery or
the matrix):** `AnswerTurn.messageId` is `string | undefined` — the current
caller (`chat/route.ts`) always passes a real, just-persisted message id in
practice, but the type permits `undefined`. **Locked rule:** if
`turn.messageId` is `undefined` for a triggering turn, **skip proposal for
that turn entirely** (fail-safe, not fail-open) — this avoids relying on
`propose()`'s exact-content fallback idempotency key for a case the
orchestrator can trivially avoid instead.

## 7. Repeat-count gate semantics (part of D1 = B)

**K4.2C-P2-D2: LOCKED (mechanism), NEW capability required (§18).**

The gate exists to prevent flooding the K4.2-C Phase 1 review queue on every
one-off `KNOWLEDGE_MISS` (discovery's own flagged risk). Mechanism:

- Before proposing an `unanswered-high-value` candidate, the orchestrator
  checks: has this **same `queryHash`** (K1's existing `queryHash()`
  function, already computed inside `KnowledgeService.retrieve()`) produced
  a `KNOWLEDGE_MISS`-equivalent `KnowledgeRetrievalLog` row **at least `N`
  times** in the trailing lookback window, **and** does no
  `KnowledgeCandidate` already exist for it (via
  `CandidateStorePort.findByExactContent`/`findByOriginatingMessage` —
  already exists, K4.2-A)?
- `N` and the lookback window are **new named constants** in
  `KNOWLEDGE_LOOP_CONFIG` (same file `DUP_HARD`/`DUP_SOFT` already live in
  — precedent for adding a small, explicit, documented threshold rather
  than a magic literal). Exact values are an implementation-time detail,
  not a contract-blocking decision — but the *existence* of the constants,
  and that they live in `KNOWLEDGE_LOOP_CONFIG`, is locked here.
- **This requires a NEW read query** that does not exist on any port today
  — see §18. Neither `KnowledgeStorePort` (K1) nor any other existing
  interface exposes a way to count prior `KnowledgeRetrievalLog` rows by
  `queryHash`. `propose()`'s own idempotency check (`findByExactContent`/
  `findByOriginatingMessage`) only prevents an exact duplicate proposal —
  it does not answer "how many times has this query missed."

## 8. Confidence / minimum-threshold semantics (D2 = C, LOCKED)

**K4.2C-P2-D3: LOCKED.** No heuristic confidence-scoring subsystem.
`ProposeCandidateInput.confidence` is set to **one fixed, named constant**
(e.g. `KNOWLEDGE_LOOP_CONFIG.CANDIDATE_CONFIDENCE_DEFAULT`, exact value an
implementation-time detail, not contract-blocking) for **every** proposal
this phase creates, regardless of trigger. `propose()`'s own privacy scan
and dedup logic (K4.2-A, unmodified) remain the real automated quality
gates; the human reviewer (K4.2-B's approve/reject) remains the real
judgment gate. **Explicitly prohibited by this decision:** deriving
confidence from `retrieval.bestSimilarity`, provider identity, or any other
per-turn signal — that would be exactly the "heuristic confidence-scoring
subsystem" the owner's critical boundary rules name as unauthorized.

## 9. Fire-and-forget lifecycle (D3 = B, LOCKED)

**K4.2C-P2-D4: LOCKED.** `answer()` calls `propose()` **after** the
`AnswerResult` it returns is already fully built (i.e., after
`buildProvenance()`/`provenance.write()`/`emitAnswerTelemetry()` have run),
as a detached, non-blocking call: `void this.candidates.propose(input).catch(() => {})`
(same discipline as every existing best-effort write in this codebase —
analytics `.record().catch()`, `provenance.write().catch(() => null)`).

**Explicitly locked, not open for reinterpretation:**
- `propose()` is **never** `await`-ed on the response path. A slow or
  failing `propose()` call (embedding timeout, DB contention, anything)
  **never** delays or fails the user's answer.
- **No historical backfill mechanism is introduced.** `ProvenanceStorePort`
  gains **no** `update()` method. `provenance-store.ts` is **not** modified
  by this phase.
- The candidate is proposed using the **already-settled, already-returned**
  answer text and facts — it reads from local variables already in scope
  at the end of `answer()` (`winner.res.text`, `retrieval`, `turn`), not
  from a re-fetch of anything.

## 10. Provenance model (D4, follows D3 = B, LOCKED)

**K4.2C-P2-D5: LOCKED.** `build-provenance.ts`'s
`candidateCreatedId: null, // K4 — never in K3` line **does not change** —
it remains hardcoded `null` for every `KnowledgeAnswerProvenance` row this
phase writes, exactly as it is today. This is a **deliberate, permanent**
choice, not a temporary gap:

- Traceability from a candidate back to its originating turn goes through
  `KnowledgeCandidate.originatingMessageId` / `originatingConversationId`
  (already exist, K4.2-A, populated by this phase's `propose()` calls) —
  **not** through `KnowledgeAnswerProvenance.candidateCreatedId`.
- A future sprint wanting the reverse join (provenance row → its resulting
  candidate) can compute it via a lookup query
  (`WHERE originatingMessageId = provenance.messageId`) without needing any
  new column or port method — the data to do that join already exists once
  this phase ships.
- `orchestrator/ports.ts`'s `ProvenanceStorePort` interface is **not**
  modified by this phase (its single `write()` method is untouched).

## 15. `AnalyticsPort` decision (D9, RESOLVED)

**K4.2C-P2-D10: RESOLVED — reuse, do not duplicate.** Read
`governance/ports.ts`'s `AnalyticsPort`:

```ts
export interface AnalyticsPort {
  record(userId: string | null, type: string, metadata?: Record<string, unknown>): Promise<void>;
}
```

This is already a minimal, one-method, structurally-generic interface — it
carries no dependency on `CandidateService`, `GovernanceService`, or any
governance-specific type. The `RetrievalPort`-narrowing precedent
(`orchestrator/ports.ts` narrows the full `KnowledgeService` class down to
one method, `retrieve()`) exists to avoid a *wide, feature-specific class*
becoming a dependency — it does not apply here, because there is nothing
left to narrow: `AnalyticsPort` is already as narrow as `RetrievalPort`
itself. TypeScript's structural typing also means a textually-duplicated
interface with the identical signature is interchangeable with the
original anyway — "textual separation" would buy no actual decoupling, only
an extra one-method interface to keep in sync forever. **Decision:**
`orchestrator/ports.ts` and `knowledge/ports.ts` both import and re-export
`AnalyticsPort` from `governance/ports.ts` (or, if a cleaner shared home is
preferred at implementation time, promote it to `types/knowledge-loop/index.ts`
— an implementation-time style choice, not a contract-blocking one). Either
way: **one** `AnalyticsPort` definition, not three.

existing semantic fit for an arbitrary, unclassified chat-originated
question, and consistent with D2's "keep it simple, let the human reviewer
be the real gate" spirit (the reviewer can re-classify on approval, K4.2-B's
existing edit-before-approve flow already supports this). No new enum
value, no classification logic. If the owner wants a real
`Classification.intent → KnowledgeType` mapping instead, that is a
follow-up decision, not assumed here.
