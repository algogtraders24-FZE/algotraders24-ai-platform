# D2.8.8 — Microstructure Intelligence Presentation & Evidence Attribution

**Status:** Implemented and tested. **Baseline:** D2.8.7 (`ca020d9`).
**Scope:** Safely expose D2.8.7's `VerifiedRealTimeIntelligenceContext.microstructure` to the existing AI presentation layer — additively, without touching the locked `AIIntelligencePresenter` interface, without modifying scoring/regime/hypothesis logic, without adding a route, WebSocket, or trading logic.

---

## 1. Current presenter architecture (Phase 1 audit findings)

- `AIIntelligencePresenter.present(envelope: IntelligenceEnvelope, userQuestion: string): Promise<AIPresentationResult>` (`types/intelligence-envelope.ts`) is documented as a **permanent architectural rule** and is implemented identically by `GeminiIntelligencePresenter` (also used, via dependency injection, for Claude/OpenAI) and `DeterministicSafeFallbackPresenter`. This interface's signature was **not touched**.
- `AIPresenterOrchestratorService` (`services/intelligence/chat/ai-presenter-orchestrator.service.ts`, D2.6.8) is a *composition class*, not the locked interface — it tries each configured presenter in priority order (Gemini → Claude → OpenAI → deterministic fallback), validates every candidate via `AIResponseIntegrityService.validateResponseIntegrity()`, and never returns an unvalidated LLM answer.
- `IntelligencePresentationService.present()` (`services/intelligence/chat/intelligence-presentation.service.ts`, D2.6.9) is the real chat-facing composition root: it calls `IntelligenceChatContextService.resolve()` (which produces the full `VerifiedRealTimeIntelligenceContext`, including D2.8.7's `microstructure` field) and then `AIPresenterOrchestratorService.present(envelope, input.message)`. This is the exact seam where real microstructure evidence (already resolved, already attributed) meets the presentation layer.
- `AIResponseIntegrityService.validateResponseIntegrity(text, envelope, decisionContext)` (`services/intelligence/chat/ai-response-integrity.service.ts`, D2.6.5) is a pure, deterministic rule-checker that rejects a presenter's output if it contains a numeric claim unsupported by the real `IntelligenceDecisionContext`.

## 2. Integration point selected

**`AIPresenterOrchestratorService.present()`** gained an optional third parameter, `microstructure?: MicrostructureSnapshot`, defaulting to `undefined`. This is the safest point because:

1. It is **not** the locked `AIIntelligencePresenter` interface — it is this codebase's own D2.6.8 composition class, free to grow additively.
2. It already sits between the real, resolved context and every candidate presenter, so it can enrich what each presenter receives without any individual presenter (Gemini/Claude/OpenAI/fallback) knowing this sprint exists.
3. The optional parameter is backward compatible: every existing call site (all of D2.6.5–D2.8.7's own test suites, `IntelligencePresentationService`) compiles and behaves byte-identically when it is omitted.

`IntelligencePresentationService.present()` was extended by exactly one line — passing `context.microstructure` (D2.8.7's own field, `undefined` unless the caller opted in) as the new third argument. `IntelligenceChatContextService.resolve()` gained one pass-through optional field, `includeMicrostructure?: boolean`, mirroring `crossProviderValidation`'s existing pattern exactly, so the D2.8.7 opt-in flag can actually reach a real chat caller. **No route was changed to set this flag by default** — see §12 "Known limitations."

## 3. Microstructure evidence flow

```
Real Binance evidence
  -> RawMicrostructureResult (D2.8.5)
  -> MicrostructureSnapshot (D2.8.5, via D2.8.6's shared instance)
  -> VerifiedRealTimeIntelligenceContext.microstructure (D2.8.7)
  -> IntelligencePresentationService.present() reads context.microstructure
  -> AIPresenterOrchestratorService.present(envelope, userQuestion, microstructure)
       -> buildPresenterQuestionWithMicrostructure(userQuestion, microstructure)
            (lib/microstructure/microstructure-presentation.ts, new this sprint)
       -> each candidate presenter receives the ENRICHED question string
          (AIIntelligencePresenter.present(envelope, enrichedQuestion) - signature unchanged)
       -> validateResponseIntegrity(text, envelope, decisionContext, microstructure)
          (extended this sprint to recognize real microstructure numbers as supported)
```

Every step reuses an existing D2.8.5/D2.8.6/D2.8.7 type or function verbatim. No microstructure calculation, validation, or fetch logic was reimplemented.

## 4. Raw vs. derived evidence

`formatMicrostructureEvidence()` (`lib/microstructure/microstructure-presentation.ts`, originally D2.8.7, corrected this sprint per Phase 2/4) now explicitly groups fields under two headings:

- **`Direct Evidence (reported directly by <provider>):`** — bid, ask only (the two fields Binance itself reports).
- **`Derived Evidence (computed from the direct evidence above - never independently reported by the provider):`** — spread, mid-price, bid/ask depth, depth imbalance, liquidity concentration, buy/sell volume, volume delta.

This was the one "concrete defect" found in the Phase 2 audit of the existing D2.8.7 formatter: its fields were correctly sourced, attributed, and honest, but did not explicitly separate raw from computed values. The correction is a relabeling only — no field, no calculation, no state-handling logic changed.

## 5. Provider attribution

Unchanged from D2.8.7: `MicrostructureSnapshot.provider` (e.g. `"binance"`) is printed verbatim as `Provider: binance` in every evidence block, and the block's closing line states `Evidence scope: binance BTCUSD order book only - not global market liquidity.` The new `buildMicrostructureLLMEvidenceBlock()` wraps this with an explicit rule (see §9) reiterating the same constraint for the LLM specifically.

## 6. Venue-specific limitation

`buildMicrostructureLLMEvidenceBlock()` (new, Phase 7) states explicitly: *"Never describe it as global crypto liquidity, institutional liquidity, CME liquidity, combined spot+futures liquidity, global FX liquidity, or XAUUSD/any other instrument's liquidity."* This sentence is generated from the real `snapshot.provider`/`snapshot.symbol`, not a hardcoded example, so it stays accurate for any future Binance-covered instrument.

## 7. Unsupported instrument behavior

Reuses D2.8.7's `RealTimeIntelligenceService.fetchMicrostructure()` unchanged — instrument safety is decided once, upstream of presentation, via the real canonical-instrument→provider-mapping check. This sprint adds no second check. Verified directly against the real instrument catalog for all six required symbols: **BTCUSDT/ETHUSDT** (Binance-mapped) *may* receive microstructure; **XAUUSD, XAGUSD, EURUSD, GBPUSD, NIFTY, BANKNIFTY** are confirmed to have no Binance provider mapping, so `context.microstructure` stays `undefined` for them and `buildPresenterQuestionWithMicrostructure()` returns the trader's question completely unchanged — no evidence block, no symbol substitution, no fallback from one instrument to another.

## 8. Stale / unavailable / invalid semantics

Unchanged from D2.8.5/D2.8.7: every field is a `MicrostructureField<T>` carrying its own `CapabilityState`. `formatMicrostructureEvidence()` prints the honest state word for every non-`available`/`stale` field. This sprint's `collectMicrostructureRealNumbers()` (used by the integrity-checker extension, §9) only ever collects a number from a field whose state is `"available"` or `"stale"` — `"unavailable"`, `"invalid"`, and `"not_supported_by_provider"` fields never contribute a value anywhere, confirmed by dedicated tests (12, 13, 14, 23 in the new suite).

## 9. LLM safety boundary

`buildMicrostructureLLMEvidenceBlock(snapshot)` wraps the evidence lines with an explicit rules section stating, verbatim:

- the evidence is venue-specific and must never be generalized (with the specific prohibited generalizations spelled out);
- it is evidence, not a prediction, signal, or recommendation;
- any non-`available`/`stale` field must be reported using its exact state word, never inferred;
- volume delta (when available) is derived from the provider's real aggressor-side flag, not estimated;
- the *absence* of this block does not imply neutral market conditions.

This text is **not** sent as a system instruction — the locked `GEMINI_PRESENTER_SYSTEM_INSTRUCTION` in `GeminiIntelligencePresenter` is completely untouched. It travels inside the enriched user-turn content instead (§3), so it applies identically to whichever candidate presenter (Gemini, Claude, OpenAI) the orchestrator tries.

A second, necessary safety-coherence fix: `AIResponseIntegrityService.validateResponseIntegrity()` gained an optional fourth parameter, `microstructure?: MicrostructureSnapshot`. Without it, a presenter response that *honestly* cited a real microstructure number (e.g. "the Binance bid is 63189.99") would have been misclassified as an unsupported/fabricated numeric claim by the existing `checkUnsupportedNumericClaims()` check — which only knew about numbers embedded in `IntelligenceDecisionContext` — and incorrectly routed to the deterministic fallback (which never mentions microstructure). `collectMicrostructureRealNumbers()` supplies the real, state-gated numbers so genuine evidence is recognized as supported, while a response inventing an unrelated number (tested with a fabricated price far outside tolerance) is still correctly rejected.

Repository-wide search for `liquidity zones`, `volume delta`, `order book`, `depth`, `spread`, `aggressor`, `microstructure` (case-insensitive) found:

- `data/products.ts` (`"Smart Money Indicator"` marketplace listing, `features: ["Order-block detection", "Liquidity zones", ...]`) — a third-party product's own advertised capabilities in the product catalog, unrelated to AT24's own AI Intelligence output. Reviewed, out of scope.
- **`services/ai/prompts/prompt-library.service.ts`'s `"gold-analysis"` template** (`"Analyze XAUUSD (Gold). Cover trend, key levels, liquidity zones, and directional bias."`), consumed by the live, separate `/dashboard/market-intelligence` pipeline (`services/ai/market-analysis-orchestration.service.ts`) — **this is the exact same finding D2.8.2 already documented** (its §13, item 4): a prompt-design fabrication *risk* in an older pipeline that predates D2.6.1+'s evidence-gated `DecisionContextService`. No new fabrication was found or introduced. No synthetic liquidity zones, no unsourced order-book claims, no unavailable→zero conversions, and no AI-prompt instruction telling a model to invent missing microstructure data exist anywhere in the code this sprint touched.

## 12. Known limitations

- **`DeterministicSafeFallbackPresenter` never includes microstructure evidence**, by its own pre-existing, documented design (`present(envelope)` intentionally omits `userQuestion` entirely — "never tailors its output to the phrasing of the question"). If every LLM provider is unavailable/fails, the trader-facing answer falls back to a response that never mentions microstructure, even when it was available. This is a deliberate consequence of not touching that presenter's carefully-reasoned design, not an oversight.
- **`presentSafely()`** (`services/intelligence/chat/ai-response-integrity.service.ts`, D2.6.5's lower-level single-presenter primitive) was **not** extended with a microstructure parameter — it has zero production callers today (confirmed via repository-wide search; only `AIPresenterOrchestratorService`, used by the real chat route, is production-wired). Extending it was unnecessary for this sprint's scope.
- **No route was changed to set `includeMicrostructure: true` by default.** `app/api/private/knowledge/chat/route.ts` still calls `IntelligencePresentationService.present()` without it, so `context.microstructure` remains `undefined` for every real end-user request today — exactly D2.8.7's own "opt-in only" posture, now simply reachable end-to-end for a caller that does set it (e.g. a future route parameter, or a direct service caller). Turning this on for real traffic is a distinct, separately-scoped product decision.
- **The `/dashboard/market-intelligence` prompt-design finding** (§10) remains unresolved, exactly as D2.8.2 first reported it — unrelated to and untouched by this sprint's pipeline.

## 13. Future WebSocket integration boundary

No WebSocket exists anywhere in this sprint's code — the fetch path is still `MicrostructureSnapshotService.getSnapshot()` → `BinanceProvider.getMicrostructureSnapshot()` → Binance's public REST endpoints, identical to D2.8.6. D2.8.3's disposable WebSocket research remains documented but unused. A future sprint that wants push-based (rather than pull/REST) microstructure updates would need its own explicitly-scoped design — nothing in this sprint's presentation bridge assumes or blocks that; `buildPresenterQuestionWithMicrostructure()` operates on a `MicrostructureSnapshot` value regardless of how it was obtained.
