# D2.8.11 — Microstructure-Aware Decision Intelligence & Evidence Fusion

**Status:** Implemented and tested. **Baseline:** D2.8.10 (`b3e98e1`).
**Scope:** A deterministic evidence-fusion layer comparing real microstructure evidence against the existing hypothesis's direction, exposed additively on `IntelligenceDecisionContext`. Never a trading signal. Never a modification to Intelligence Score weights/formula.

---

## 3. Evidence interpretation rules

`assessMicrostructureEvidence(snapshot, hypothesis, generatedAt)` (pure, synchronous, no I/O, no new clock read) combines up to two independent, already-normalized, relative signals — **never an arbitrary absolute threshold**:

1. **Order-book depth imbalance** — D2.8.5's own `derived.depthImbalance`, already a ratio in `[-1, 1]`. Used only when `state === "available"`.
2. **Aggressor-normalized volume delta** — `derived.volumeDelta / (buyVolume + sellVolume)`, bounded to `[-1, 1]`. Used only when `volumeDelta`, `buyVolume`, AND `sellVolume` are all `"available"` — inheriting D2.8.5's own aggressor-evidence gate exactly (no genuine aggressor data ⇒ these fields are already `"unavailable"` ⇒ signal excluded, never a second check).

`netPressure` is the mean of whichever signals are available. Two documented, versioned V1 constants (`NEUTRAL_PRESSURE_BAND = 0.15`, `STRONG_PRESSURE_THRESHOLD = 0.5`, both relative ratios) classify magnitude into `evidenceStrength` (`weak`/`moderate`/`strong`) and `balance` (`bullish`/`bearish`/`neutral`).

## 4. Hypothesis relationship rules

`hypothesisDirection` is derived purely from the hypothesis type's own naming suffix (`-bullish`/`-bearish`; everything else is `"neutral"` — non-directional). Then:

- `balance === hypothesisDirection` → **`confirms`**
- `balance` is the opposite directional value → **`contradicts`**
- `balance === "neutral"` (real signal existed, magnitude too small) → **`neutral`**
- No snapshot / no usable signal / no hypothesis / non-directional hypothesis → **`insufficient_evidence`** (never forced into a direction).

## 5. Confidence / score impact

**None, by design.** `IntelligenceScoreService`'s formula/weights were not touched — confirmed by a structural test asserting that file contains no reference to "microstructure" at all. `microstructureEvidence` is purely an additive, narrative field on `DecisionContext`, never a numeric input anywhere in the score pipeline. A dedicated test proves two otherwise-identical requests (with and without microstructure) produce a byte-identical `envelope.intelligenceScore`. This directly follows Phase 5's own instruction: *"expose the evidence relationship to DecisionContext first and defer score-weight modification."*

## 6. Data-quality gate behavior

`assessMicrostructureEvidence()` returns `insufficient_evidence` (never a fabricated numeric neutral) whenever:

- no snapshot was supplied at all;
- `snapshot.freshnessStatus !== "fresh"` (covers stale, unknown, **and** invalid/future-timestamp — D2.8.5's own `assessMicrostructureFreshness` already classifies an impossible-future timestamp as `"invalid"`);
- `evidence.bid.state === "invalid" || evidence.ask.state === "invalid"` (a crossed/malformed top-of-book — a deliberately conservative, whole-snapshot-level gate, even though depth/volume signals might independently still compute);
- neither the depth-imbalance nor the volume-delta signal was `"available"` at all.

`bullishPressure`/`bearishPressure` are `undefined` (never `0`) in every one of these cases.

## 7. Instrument safety

Unchanged from D2.7–D2.9: BTCUSD/ETHUSD are Binance-capable; XAUUSD/XAGUSD/EURUSD/GBPUSD/NIFTY/BANKNIFTY are not. For an unsupported instrument, `RealTimeIntelligenceService.fetchMicrostructure()` (D2.8.7, unmodified) never calls Binance at all, so `context.microstructure` is `undefined`, so `DecisionContextService.build(envelope, undefined)` never even attempts an assessment — `microstructureEvidence` is simply absent from the result. Confirmed for all six unsupported instruments with zero-provider-call assertions.

## 8. Evidence attribution

Every non-trivial `MicrostructureEvidenceAssessment` carries `provider`, `instrument`, `freshness`, and `timestamp` copied verbatim from the real snapshot — never a generic or "global" label. Confirmed the live-runtime test never claims global liquidity; the assessment is always scoped to the exact venue (`"binance"`) and instrument that produced it.

## 15. Known limitations

- `microstructureEvidence` is populated only when the caller explicitly passes a real `MicrostructureSnapshot` to `build()`; a request that opted into microstructure but received nothing (unsupported instrument, provider failure) looks identical, at the `DecisionContext` level, to a request that never asked at all — both simply omit the field. This mirrors D2.8.8's own established precedent for the same ambiguity (`AIPresenterOrchestratorService.present()`'s optional 3rd parameter) and is a deliberate simplicity choice, not an oversight — the *reason* (never attempted vs. attempted-and-unavailable) remains fully visible one layer up, on `VerifiedRealTimeIntelligenceContext` itself.
- `DecisionContext`'s existing, permanent "liquidity zone / volume delta / execution risk not implemented" disclaimers (D2.6.1) are **unconditional** and remain exactly as-is even when a real `microstructureEvidence` object is also present on the same `DecisionContext` for a Binance-capable instrument — a documented tension, not a bug: those disclaimers describe the engine's *default* capability, independent of any one request's real evidence, and two existing regression suites (`validate:decision-context`, `validate:market-data-integrity`) explicitly pin this behavior.
- The evidence-fusion assessment is not yet surfaced in the D2.8.8 AI-presentation text block or the D2.8.10 chart visualization panel — this sprint's scope was the `DecisionContext` layer only, per the brief's own "expose to DecisionContext first" instruction. Presenting it to the trader-facing chat/UI is a natural, separately-scoped future step.
