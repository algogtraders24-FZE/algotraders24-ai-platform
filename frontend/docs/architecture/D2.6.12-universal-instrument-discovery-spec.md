# D2.6.12 — Universal Instrument Discovery & Dynamic Provider Catalog

**Status:** Implemented and tested.
**Scope:** A scalable instrument-discovery layer over the existing D2.6.3 canonical instrument architecture. No new architecture, no new AI, no new trading capability. TradingView, `MarketDataService`, provider reliability, and the entire D2.5.x/D2.6.x intelligence pipeline remain untouched.

---

## 1. Problem

D2.6.3's `INSTRUMENT_CATALOG` was a fixed, 16-entry, hand-authored array. The Workspace treated it as if it were the complete tradable universe: searching "MSFT", "NVDA", "SBIN", or "BNB" returned nothing, even though Binance, Angel One, Twelve Data, and Alpha Vantage can all genuinely discover instruments far beyond that set. This sprint makes the 16 existing instruments **default/popular suggestions**, not a whitelist, while preserving the canonical-instrument architecture as the single source of truth for everything downstream.

## 2. Canonical identity design

`CanonicalInstrument` (`types/canonical-instrument.ts`) gained one additive, optional field: `discovery?: {source, discoveredAt}` — present only on a runtime-discovered instrument, `undefined` on all 16 hand-curated entries. No other field changed shape.

`lib/market-data/instrument-catalog.ts` gained an in-memory `DISCOVERED` registry (`registerDiscoveredInstrument()`, `clearDiscoveredInstruments()` for tests) — **not a second registry**: `getCanonicalInstrument()`, `listCanonicalInstruments()`, and `mappingsForProvider()` all now read the static array merged with this registry, so every existing consumer (`WorkspaceContext`, `InstrumentSearchService`, `BinanceProvider`, `AngelOneProvider`, chat symbol resolution) sees a discovered instrument the moment it's registered, with zero new lookup path anywhere else. Registration is a no-op for any id already present in the static catalog — a discovery can never overwrite a hand-curated entry.

**Identity rule (never merge by name similarity):** a discovered candidate is only ever treated as "the same instrument" as an existing catalog entry when its exact `providerSymbol`/`providerInstrumentId` already appears in that provider's own real mapping. Otherwise it gets a provider-scoped synthetic id — `disc:<provider>:<providerSymbolOrToken>` — that can never collide with a different provider's discovery of a similarly-named instrument. Verified directly: Angel One's `AXISBANK-EQ` and Twelve Data's unrelated `AXP` never merge just because both queries mention "Axis" (`scripts/validate-universal-instrument-discovery.ts`, test 41).

## 3. Discovery sources (real, existing provider APIs — nothing invented)

- **Binance** (`services/market-data/discovery/binance-instrument-discovery.service.ts`) — the real, public, credential-free `GET /api/v3/exchangeInfo`, the same fact `binance.provider.ts`'s own header already documents. Filtered to `status: "TRADING"` and a small allow-list of real settlement quote assets (USDT/USD/USDC/BUSD/FDUSD). Full capability claim: `["quote", "candles"]` — genuinely deliverable today via the existing, unmodified `BinanceProvider`.
- **Angel One** (`angel-one-instrument-discovery.service.ts`) — the real, public, unauthenticated instrument scrip master already cited in `instrument-catalog.ts`'s and `angel-one.provider.ts`'s headers (`OpenAPIScripMaster.json`, live-verified 2026-08-10/11). Filtered to `exch_seg: "NSE"` and the two real `instrumenttype` values (`""` cash equity, `"AMXIDX"` index) this project's own 6 hand-curated Indian entries already use. Full capability claim: `["quote", "candles"]`.
- **Twelve Data** (`twelve-data-instrument-discovery.service.ts`) — the real, documented `GET /symbol_search`, reusing the exact configured `TWELVEDATA_API_KEY` (`loadTwelveDataEnv()`). **Discovery-only** — `twelve-data.provider.ts`'s own header documents its `SYMBOL_MAP` as frozen; this sprint's own instruction is to preserve that, never rewrite it. Capability claim: always `[]`.
- **Alpha Vantage** (`alpha-vantage-instrument-discovery.service.ts`) — the real, documented `GET ?function=SYMBOL_SEARCH`, reusing `ALPHA_VANTAGE_API_KEY`. Also discovery-only, for the same reason plus the fact that Alpha Vantage's frozen adapter has never served equities in this codebase at all (only FX/metals via `CURRENCY_EXCHANGE_RATE`). Capability claim: always `[]`.

A discovery-only candidate is not a lesser result — it still carries its real, provider-reported `exchange` field, which is enough for the chart resolver to derive an honest chart symbol even with zero market-data capability (the exact `AAPL` pattern D2.6.11 established, now extended to any discovered US equity — e.g. NVDA: chart available, intelligence honestly unavailable).

## 4. Provider mapping — capabilities stay separate, on purpose

Every registered instrument carries exactly one `ProviderMapping` per discovery, with `supportedCapabilities` reflecting **only what that provider's real adapter can deliver today** — never inferred from "the provider knows this symbol exists." An empty `supportedCapabilities` array is not the same as "no mapping" — dropping the mapping entirely would also destroy the real `providerSymbol`/`exchange` the chart resolver needs, silently coupling chart support to market-data support (the exact conflation this sprint's brief explicitly prohibits). A real bug of exactly this shape was caught by the test suite (see §11) and fixed at the root.

## 5. Caching strategy (no Redis/Kafka, reuses the existing `TtlCache`)

Every discovery service uses `lib/market-data/cache.ts`'s existing `TtlCache<T>` — the same primitive every provider adapter in this codebase already uses for live quotes/candles:

| Source | Cache shape | TTL | Stale-fallback grace |
|---|---|---|---|
| Binance | one entry, the full `exchangeInfo` symbol list | 6h | 24h |
| Angel One | one entry, the full scrip master (~150k rows) | 12h | 48h |
| Twelve Data | per-query | 10min | 1h |
| Alpha Vantage | per-query | 10min | 1h |

A live fetch failure never destroys the existing catalog — it falls back to the last successful cache read (honestly marked `stale: true`) if one exists within the grace window, or contributes zero candidates otherwise; `InstrumentSearchService`'s own catalog search always still runs independently. **A real bug was found and fixed here**: the first implementation read the cache via `TtlCache.get()`, which *deletes* an expired entry as a side effect — by the time the catch branch tried `getStale()` as a fallback, the entry was already gone. Fixed by reading via `getStale(key, cacheTtlMs)` for the "still fresh?" check too (a non-destructive read), the exact idiom `MarketDataService.getSnapshot()` already established for its own live-then-stale-fallback resilience (`services/market-data/market-data.service.ts`) — reused, not reinvented. Caught by test 17 before it ever reached production.

Provider discovery only runs when the existing catalog search doesn't already answer a query well (an exact match, or a full page of results) — the common case (searching a default/popular instrument) never pays for a live round trip. Each provider is queried in parallel and individually time-boxed (3s default); a slow or hung provider is treated as failed, never blocks the other three or the response.

## 6. Search ranking & deduplication

`UniversalInstrumentDiscoveryService` (`services/market-data/discovery/universal-instrument-discovery.service.ts`) owns **zero ranking logic of its own** — it calls `InstrumentSearchService.search()` (D2.6.3, unmodified) before discovery to check sufficiency, registers any genuinely new candidates into the shared catalog, then calls the exact same `InstrumentSearchService.search()` again so ranking is uniform regardless of whether a result came from the static catalog or a live provider. Deduplication happens at registration time (§2), not at ranking time — by the time ranking runs, the catalog already has no duplicates to rank.

## 7. Chart resolution — still the one layer

`lib/market-data/chart-instrument-resolver.ts` remains the single chart-resolution module. It gained one additive derivation path, applied **only** when `instrument.discovery` is present (a hand-curated entry always resolves via the original static `TRADINGVIEW_SYMBOL` table first, unchanged):

- Binance-discovered → `BINANCE:<providerSymbol>` (TradingView's own documented exchange prefix).
- Angel One-discovered NSE equity → `NSE:<ticker>` (strips the real, confirmed `-EQ` suffix Angel One's own symbol format uses).
- Any exchange a discovery source itself reported that maps to a confirmed real TradingView prefix (`NASDAQ`, `NYSE` today) → `<PREFIX>:<providerSymbol>`.
- Anything else → `supported: false` with an honest reason.

**Never**: an unknown/discovered instrument falling back to `FX:EURUSD` or to the previously-selected chart — the exact D2.6.11 bug this sprint explicitly must not reintroduce. Verified directly (tests 29–33, 56).

## 8. Provider capability & provenance in the search response

Every result now additionally carries `capabilities: {quote, candles, intelligence, chart}` and `chart: {supported, chartSymbol?, reason?}` — `intelligence` mirrors `quote` (the minimum a real snapshot the deterministic pipeline needs), never independently true. `discoverySource` is present only on a genuinely discovered instrument. A hand-curated, multi-provider instrument's real provider list (e.g. BTCUSD: both `twelve-data` and `binance`) is never conflated with "who discovered it" — discovery provenance and market-data provenance are deliberately separate fields (test 38).

## 9. Fallback behavior (D2.6.4, unmodified)

`MarketDataService`'s provider-priority, reliability-ranked smart fallback is untouched. This sprint's only interaction with it is additive: a discovered Binance/Angel One instrument becomes resolvable by `BinanceProvider`/`AngelOneProvider` because their `SYMBOL_MAP` is now computed fresh per call (`getSymbolMap()`) from `mappingsForProvider()` instead of being frozen at module load — functionally identical output for every pre-existing symbol (confirmed by the unmodified D2.6.3/D2.6.4/D2.6.6 test suites still passing byte-for-byte), just computed at the time it's needed instead of once at import time, so a newly-registered instrument is fetchable without a server restart.

## 10. Security

- `GET /api/private/instruments/search` requires authentication before the discovery orchestrator is ever invoked (verified structurally, test 43).
- No provider credential ever reaches the browser — Twelve Data/Alpha Vantage discovery reuse the exact same server-side `loadTwelveDataEnv()`/`loadAlphaVantageEnv()` every existing adapter already uses; Binance/Angel One discovery need no credential at all (public endpoints).
- The response never carries a raw provider error message, only a sanitized failure reason.
- `CanonicalInstrument`/`ProviderMapping` field names are structurally checked to contain no secret-shaped field.

## 11. Testing

`scripts/validate-universal-instrument-discovery.ts`, 61 assert-based tests (no test framework, matching this project's established `validate:*` convention) — every discovery service exercised against an injected fake fetch and a fake `Clock`, never a live network call by default. Covers: catalog-first ranking and early-exit, exchange/category/provider fields, deduplication and ambiguity protection, all four discovery services individually, resilience (success/failure/stale/refresh/timeout/malformed), the orchestrator's registration + capability matrix + chart resolution + provenance, default suggestions, every pre-existing catalog instrument (regression), all-provider failure, cache isolation, and the route's auth/response contract.

**Two real bugs were found and fixed by this test suite, not by inspection:**
1. `TtlCache.get()`'s side-effect eviction silently defeating the stale-cache-fallback path (§5).
2. Registering a discovery-only candidate (Twelve Data/Alpha Vantage) with an empty `providerMappings` array instead of a mapping with an empty `supportedCapabilities` array — this accidentally coupled chart support to market-data support (a discovered US equity with zero market-data capability also lost its real `providerSymbol`/`exchange`, so the chart resolver had nothing to derive from and reported `supported: false` even though a real TradingView chart exists for it). Fixed at the root: the mapping is always attached; only `supportedCapabilities` reflects true/false capability.

Full regression: every pre-existing `validate:*` script re-run individually — see the sprint's final report for the pass/fail count (the only known pre-existing exception across this entire program remains `validate:ai-response-compliance`, which requires a live `GEMINI_API_KEY`, unrelated to this or any recent sprint). `tsc`, `eslint`, and `npm run build` results are also in the final report.

## 12. Future provider extension

A future provider needs only: (1) a `MarketDataProvider`/`SnapshotProvider`/`TimeSeriesProvider` adapter (unchanged D2.2 contract), (2) a discovery service implementing `DiscoverableProvider` (`{name, search(query)}`), added to `UniversalInstrumentDiscoveryService`'s constructor. Nothing else in the fabric changes — `WorkspaceContext`, `GlobalSymbolSelector`, `WorkspaceAssistant`, `WorkspaceResearch`, `IntelligenceQueryService`, `DecisionContextService`, `IntelligenceScoreService`, the AI presenter orchestrator, and the audit trace architecture all consume the same `CanonicalInstrument`/search-result shape regardless of how many providers exist behind it.

## 13. Non-goals (explicitly not built)

No ML, no LLM/embeddings/vector search for symbol resolution (search remains 100% deterministic, reusing D2.6.3's own ranking rules). No new trading signals, automated trading, broker execution, or order placement. No change to Intelligence Score/Regime/Hypothesis/`DecisionContext` formulas. No Redis/Kafka. No second symbol registry, no second chart-resolution layer, no second AI pipeline. No replacement of TradingView, `MarketDataService`, or provider reliability. No weakened response integrity; no provider credential ever exposed.

## 14. Known limitations

- Angel One discovery performs a linear scan over the full ~150k-row scrip master per cache-cold query — acceptable at this platform's real query volume, but a genuine scaling limit if instrument search traffic grows significantly; an indexed store would be the natural next step (deliberately out of scope this sprint — no Redis/Kafka).
- Twelve Data/Alpha Vantage-discovered instruments are permanently discovery-only (zero market-data capability) unless a future sprint deliberately extends those two adapters' frozen symbol tables — an explicit, disclosed constraint, not an oversight.
- The chart-exchange-prefix map (`KNOWN_TRADINGVIEW_EXCHANGE_PREFIX`) currently covers NSE/NASDAQ/NYSE — a discovered instrument on any other real exchange honestly reports `chart.supported: false` until that exchange's TradingView prefix is confirmed and added.
- `disc:` synthetic ids are process-lifetime only (in-memory registry, deliberately no DB persistence per this sprint's "no database explosion" constraint) — a server restart clears runtime-discovered instruments; they are simply rediscovered on the next matching search.
