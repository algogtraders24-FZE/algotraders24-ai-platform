# D2.5.0 — Intelligence Engine V2: Architecture & USP Specification

**Status:** Draft for Principal AI Architect review. Specification only — no production code was modified to produce this document.
**Author:** Claude (repository audit + architecture proposal), per user instruction.
**Scope:** Repository audit, gap analysis, and proposed contracts for MarketState, Regime, Hypothesis, Evidence, Conflict, Memory/Outcome, and IntelligenceScore. Implementation is explicitly deferred to D2.5.1+, pending approval.

---

## 0. Framing: this is not a new direction, it's a scheduled one

`docs/releases/D2.3_ARCHITECTURE.md` already states, verbatim, at the D2.3 freeze:

> **"Explicitly NOT in D2.3 scope (deferred to D2.4): Market structure analysis (BOS/CHOCH), liquidity analysis, order blocks, fair value gaps, multi-timeframe intelligence, multi-agent reasoning, memory/learning systems. D2.3's AI layer is deterministic evidence-restatement; D2.4 is where genuine advanced financial intelligence begins."**

Two things follow from this:

1. Everything proposed for Intelligence Engine V2 — market structure, regime detection, memory/learning — was already anticipated and named as deferred work, not an improvised pivot. This spec fulfills a standing commitment.
2. The deterministic, evidence-restatement pipeline shipped in D2.3 (Sprint 15D) is a **deliberate, locked design choice**, not a placeholder to be discarded. V2 must be additive to it, not a replacement.

`docs/architecture/AI_RESPONSE_GUIDELINES.md` independently names *"any later Research or Intelligence Engine v2 surface"* as a module that must import the existing `AI_COMMUNICATION_POLICY` rather than invent its own tone/structure/confidence-banding rules. This spec treats that as binding.

## 1. Audit findings: what already exists

### 1.1 The real, production deterministic pipeline (Sprint 15D)

One real pipeline is live behind `POST /api/private/market-intelligence/analyze`:

```
MarketDataProvider (Twelve Data → Alpha Vantage → stale-cache → structured failure)
        │
        ▼
EvidenceCollectorService        (services/ai/evidence/evidence-collector.service.ts)
        │  raw provider result → typed EvidenceItem[], emits only fields actually returned
        ▼
EvidenceFusionService           (services/ai/evidence-fusion.service.ts)
        │  exact-text dedup + corroboration scoring across source groups → FusedEvidence[]
        ▼
EvidenceRankingService          (services/ai/evidence/evidence-ranking.service.ts)
        │  fixed TYPE_PRIORITY ordering, numeric (0.5% tolerance) / textual conflict
        │  detection — never auto-resolves, always "unresolved"
        ▼
ReasoningEngineService          (services/ai/reasoning/reasoning-engine.service.ts)
        │  supporting/opposing/unresolved classification, Assumption[] for coverage
        │  gaps, Uncertainty score, ConfidenceDriver[]/RiskDriver[] — pure counting,
        │  zero AI
        ▼
RiskEngineService                (services/ai/risk/risk-engine.service.ts)
        │  8 fixed RiskCategory scores. liquidity + execution are ALWAYS "medium" —
        │  no evidence source exists for either, by explicit design
        ▼
ConfidenceEngineService          (services/ai/confidence/confidence-engine.service.ts)
        │  7 fixed ConfidenceCategory scores, penalized by risk profile
        ▼
ExplainableAnalysisService       (services/ai/explainable/explainable-analysis.service.ts)
        │  string interpolation only, NO AI call. marketThesis never asserts a
        │  directional call — nothing upstream computes one
        ▼
MarketAnalysisOrchestrationService (services/ai/market-analysis-orchestration.service.ts)
        │  builds a bounded, restate-only prompt from ExplainableAnalysis fields only
        ▼
Gemini (via lib/ai/ai.service.ts#AIService.complete())
        │  restates in plain language — instructed never to add a fact, price,
        │  headline, or conclusion not already present
        ▼
MarketAnalysisResult { symbol, intent, summary, explainable, risk, confidence }
```

Pipeline version tag: `MARKET_INTELLIGENCE_PIPELINE_VERSION = "15D.12.0"`. This is a mature, well-documented, internally-consistent system — every service's header comment functions as a de facto ADR (design rationale is written into the code, not just this doc).

A second, parallel, real pipeline exists for the Trading Copilot / Intelligence Panel surface — snapshot+candle based rather than evidence-based:

```
MarketDataService.getSnapshot() + .getTimeSeries()
        ▼
TechnicalContextService  → real RSI/EMA/MACD/ATR/Bollinger (lib/market-data/indicators.ts)
        ▼
MarketContextBuilderService.explainStructured()  → Gemini, restate-only
        ▼
IntelligencePanelService  → pure projection (trend/momentum/bias labels from EMA20/50 + MACD histogram)
```

**These two pipelines currently do not share a regime/state concept, a hypothesis concept, or a memory concept.** V2's job is to give both a common foundation without breaking either.

### 1.2 What must NOT be built on: legacy mock code

- `services/ai/market-analysis.service.ts` — reads a static mock array, literally commented `(mock only)`.
- `services/ai/trading/*.service.ts` (8 files) — look like real technical analysis but are seeded from `price % 100` (e.g. `rsi: 40 + (seed % 40)`). Not wired into any current route. **Fake data. Do not extend, do not reference as precedent.**
- `types/market-analysis.ts` — the type these mocks use, easily confused by name with the real `types/market-analysis-orchestration.ts`. V2 must not reuse this name.
- `services/ai/providers/gemini-provider.ts` (legacy `AIProvider` interface, calls `/api/ai`) — superseded by `lib/ai`'s `createAIService()`. Not the integration point for V2.

### 1.3 The confirmed, load-bearing gap: no memory, no outcome tracking

This is the most important finding in the audit, and it is confirmed, not inferred:

- **There is no `AnalysisRun` Prisma model.** `services/ai/analysis-run.service.ts`'s own header states: *"No Prisma model or migration exists yet (explicitly deferred per the Sprint 15D locked decisions)... `InMemoryAnalysisRunStore` are a reference implementation only."* Every analysis result lives in an in-process `Map` and is lost on restart.
- **`types/memory.ts`** (Sprint 12F, "AI Memory & Context Engine") is a fully-specified, 132-line type scaffold — `MemoryRecord`, `MemorySession`, `ContextBundle`, `MemoryRetrievalEvent`, `RetentionPolicy`, `MemoryMetrics`, `MemoryInsight` — **with zero consumers anywhere in the codebase.** No service, no Prisma model, no route imports it. It's designed but never built.
- Conclusion: **nothing in the platform today persists a past analysis and later compares it to what actually happened.** There is no "was this hypothesis right" feedback loop of any kind. This is the single biggest actual gap between the current platform and the diagram in the sprint brief.

Important distinction for the spec below: `types/memory.ts` is shaped for **conversational/agent memory** (`memoryType` includes `"conversation" | "agent" | "knowledge" | "userPreference"`, generic retrieval-scoring design). It is **not** structurally suited, as-is, to market-outcome tracking (regime-linked, hypothesis-linked, time-windowed, statistically-aggregatable). Recommendation: build a new, purpose-specific Memory/Outcome model (§2.6) rather than retrofitting `types/memory.ts`. The two can be cross-referenced later (e.g. adding `"market-outcome"` to `MemoryType`) but that is not required for D2.5.1.

### 1.4 What exists that V2 can and should reuse directly

| Concept | Existing artifact | V2 disposition |
|---|---|---|
| Provider-neutral quote | `types/market-snapshot.ts#MarketSnapshot` | **Reuse unchanged** as the price layer inside MarketState |
| Real indicators | `lib/market-data/indicators.ts` (RSI, EMA, MACD, ATR, Bollinger, volume) | **Reuse unchanged** inside MarketState's technical layer |

| Data-honesty convention | `undefined` when data insufficient, never estimated (indicators.ts, risk-engine.ts, evidence-collector.ts) | **This convention is the platform's actual moat. Every new engine must follow it exactly.** |
| AI restate-only boundary | `market-analysis-orchestration.service.ts#buildPrompt()`, `AI_COMMUNICATION_POLICY` | **Reuse unchanged in kind**, extended in scope (§3) |
| Provider health/failover | `lib/market-data/health-monitor.ts`, `reliability.ts` | **Reuse unchanged** |

## 2. The seven contracts

Design rules applied uniformly across all seven (carried over from the existing 15D pipeline's own conventions, not invented for this doc):

- A field is either **present with a real, sourced value**, or **absent (`undefined`)** — never a guessed/interpolated placeholder.
- Every derived/classified field carries its **basis** (which upstream items produced it), matching the existing `RiskCategoryScore.basis` / `ConfidenceProfile.basis` pattern — full traceability, no "black box" score anywhere.
- Every contract carries `generatedAt` and a `pipelineVersion`-style tag, matching `MARKET_INTELLIGENCE_PIPELINE_VERSION`.
- Nothing in these seven contracts is LLM output. All seven are deterministic engine output. The LLM only ever sees the finished `IntelligenceScore` (§2.7) and restates it — no contract here is "written" by Gemini, ever.

### 2.1 MarketState Contract — the "Observe + Measure" step

Purpose: one honest, timestamped snapshot of everything objectively measurable about a symbol right now. Pure observation — no interpretation, no classification, no verdict.

```ts
interface MarketState {
  symbol: MarketSymbol;
  timeframe: Timeframe;                 // e.g. "M15" | "H1" | "H4" | "D1"
  snapshot: MarketSnapshot;             // REUSE types/market-snapshot.ts, unchanged

  technical?: {                         // REUSE lib/market-data/indicators.ts outputs
    rsi?: number;
    ema?: { period: number; value: number }[];
    macd?: { macd: number; signal: number; histogram: number };
    atr?: number;
    bollinger?: { upper: number; middle: number; lower: number };
    volume?: VolumeMetrics;
  };

  structure?: {                         // NET NEW — each field independently optional
    trend?: { direction: "up" | "down" | "sideways"; strength: number; basis: string[] };
    liquidityZones?: LiquidityZone[];   // NET NEW type — order-book/volume-profile derived
    volumeDelta?: { buyVolume: number; sellVolume: number; netDelta: number };
    marketStructureEvents?: ("BOS" | "CHOCH")[]; // NET NEW — break of structure / change of character
  };

  quant?: {                             // NET NEW — all optional, all "undefined if not computable"
    waveMetrics?: { dominantCyclePeriod?: number; phase?: number };
    hurstExponent?: number;             // >0.5 trending, <0.5 mean-reverting, ~0.5 random walk
    fractalDimension?: number;
    chaosMeasures?: { lyapunovExponent?: number };
  };

  context?: {                           // PARTIAL REUSE — news.service.ts/economic-calendar.service.ts
    macro?: MacroEvent[];               // exist today but are mock-backed; must be re-verified as
    news?: NewsItem[];                  // real before V2 treats them as evidence sources (see §4)
    crossAsset?: CrossAssetSignal[];    // NET NEW
  };

  dataQuality: {                        // REUSE the DataConfidence concept from technical-context.service.ts
    completeness: number;               // 0..1, fraction of expected fields actually populated
    freshnessMs: number;
    provider: string;
  };

  generatedAt: string;
  pipelineVersion: string;
}
```

**Build note:** `structure` and `quant` are entirely net-new computation surfaces. No dependency in `package.json` today supports Hurst/fractal/wave math (confirmed — no `simple-statistics`, no `ml-*` packages). This is a real, scoped build decision for D2.5.1, not a research question — pure-TS implementations are standard and small (Hurst via rescaled range, fractal dimension via box-counting), no new heavy dependency is required.

### 2.2 Regime Contract — the "Detect Regime" step

Purpose: classify the current market condition from `MarketState`, deterministically. **This concept does not exist anywhere in the codebase today** — confirmed by audit (the closest things, `TrendDirection`/`VolatilityLevel`/`MarketStatusLabel`, are single-signal derived labels, not a genuine regime classification with transition tracking).

```ts
type RegimeType =
  | "trending-bullish" | "trending-bearish"
  | "ranging" | "breakout" | "breakdown"
  | "high-volatility" | "low-volatility"
  | "low-liquidity" | "transition"
  | "insufficient-data";              // explicit, honest — never force a classification

interface Regime {
  symbol: MarketSymbol;
  timeframe: Timeframe;
  regimeType: RegimeType;
  confidence: number;                 // 0..100, deterministic — NOT an LLM opinion
  basis: { field: string; value: unknown; weight: number }[]; // which MarketState fields drove this
  previousRegime?: RegimeType;
  transitionDetectedAt?: string;      // when the regime last changed, for Memory (§2.6)
  generatedAt: string;
}
```

Design constraint: `regimeType` classification must be a **fixed, documented rule set** (e.g. ADX/trend-strength thresholds + volatility bands + liquidity flags), the same style as `risk-engine.service.ts`'s fixed category scoring — not a trained model in V2. `insufficient-data` must be a real, reachable outcome, not a fallback that never fires (matching the pipeline's existing `"provider-unavailable"` honesty pattern).

### 2.3 Hypothesis Contract — the "Generate Hypotheses" step

Purpose: given a `Regime` + `MarketState`, generate candidate, falsifiable claims about what might happen — explicitly **not** verdicts. This is net-new.

```ts
type HypothesisType =
  | "trend-continuation" | "trend-reversal"
  | "breakout-confirmation" | "breakout-failure"
  | "range-bound" | "volatility-expansion" | "volatility-contraction";

interface Hypothesis {
  id: string;
  symbol: MarketSymbol;
  regimeContext: Pick<Regime, "regimeType" | "confidence" | "generatedAt">;
  type: HypothesisType;
  statement: {                        // STRUCTURED, not a free-text LLM-generated sentence
    claim: string;                    // template-filled from `type` + regime, deterministic
    predictionWindow: string;         // e.g. "next 4h" — must be explicit and falsifiable
    invalidationCondition: string;    // what would prove this wrong — required, not optional
  };
  requiredEvidence: EvidenceType[];   // declares what would support/refute it
  generatedBy: string;                // engine/rule name — NEVER "llm"
  generatedAt: string;
}
```

**Critical open decision for architect review:** the current pipeline's `ExplainableAnalysisService` explicitly designs `marketThesis` to **never** assert a directional call, because nothing upstream computes one. Hypotheses are directional by definition. This is not a contradiction — Hypotheses are candidate/falsifiable, framed with an explicit invalidation condition, and are never presented to the user as a verdict (Evidence/Conflict/Validation still have to weigh in before anything reaches `IntelligenceScore`). But this is a real philosophy boundary that the architect should explicitly rule on before D2.5.1: **how directional is Algotraders24 AI allowed to sound, even about a "hypothesis"?** This governs prompt-policy changes in `AI_COMMUNICATION_POLICY` and should be decided, not defaulted.

### 2.4 Evidence Contract — REUSE, extend only

Purpose: unchanged from today — a claim, its source, and its freshness. The existing `types/evidence.ts#EvidenceItem`/`EvidenceBundle` is well-designed and already handles this correctly.

```ts
// EXISTING, unchanged:
type EvidenceType = "price" | "technical" | "news" | "macro" | "sentiment"
  | "historical-pattern" | "cross-asset" | "provider-meta";
// PROPOSED ADDITION ONLY:
type EvidenceTypeV2Extension = "structure" | "quant" | "regime" | "hypothesis-support";
```

`EvidenceCollectorService` and `EvidenceFusionService` need new emitters for the new `MarketState.structure`/`.quant` fields (following the exact existing pattern: emit an item only for fields actually returned/computed). **No redesign required** — this is additive work against a stable contract.

### 2.5 Conflict Contract — REUSE at evidence level, extend at hypothesis level

Purpose: the existing `EvidenceConflict` (numeric 0.5%-tolerance / textual conflict detection in `evidence-ranking.service.ts`) stays exactly as-is for evidence-vs-evidence conflicts. **Net-new**: a Conflict Engine layer that operates on **Hypotheses**, since two evidence-backed hypotheses can contradict each other even when no individual evidence items conflict (e.g. a Structure-based continuation hypothesis vs. a Quant-based reversal hypothesis, each internally well-evidenced).

```ts
// EXISTING, unchanged: EvidenceConflict (types/evidence.ts)

// NET NEW:
interface HypothesisConflict {
  id: string;
  symbol: MarketSymbol;
  hypothesisA: Pick<Hypothesis, "id" | "type" | "statement">;
  hypothesisB: Pick<Hypothesis, "id" | "type" | "statement">;
  conflictReason: string;
  resolution: "preferred-a" | "preferred-b" | "unresolved"; // SAME pattern as EvidenceConflict —
                                                              // default is always "unresolved"
  resolutionBasis?: string[];         // required if resolution !== "unresolved"
  generatedAt: string;
}
```

The `"unresolved"`-by-default posture is deliberate and must be preserved — the existing evidence-ranking service **never auto-resolves** a conflict without an explicit, evidenced reason. This is core to the platform's credibility and must not be relaxed for hypothesis conflicts either.

### 2.6 Memory/Outcome Contract — the confirmed real gap, net new

Purpose: close the loop the audit found completely absent. Persist what was predicted, and later record what actually happened, so the platform can eventually report a real, honest historical validation rate — never an invented one.

```ts
interface AnalysisRun {                // NEW Prisma model required — none exists today
  id: string;
  symbol: MarketSymbol;
  regimeAtTime: Regime;
  marketStateSnapshot: MarketState;    // or a stored reference/id if payload size requires it
  hypotheses: Hypothesis[];
  intelligenceScoreId: string;         // FK to the IntelligenceScore this run produced
  createdAt: string;
}

interface AnalysisOutcome {
  id: string;
  analysisRunId: string;               // FK
  hypothesisId: string;                // which specific hypothesis this evaluates
  evaluatedAt: string;
  status: "validated" | "invalidated" | "inconclusive" | "pending";
  actualPriceMoveePct?: number;
  actualRegimeAfter?: RegimeType;
  evaluationBasis: string;             // how the verdict was computed — deterministic rule, not opinion
}

interface HistoricalValidation {       // aggregate, computed on read, not stored as a black-box number
  regimeType: RegimeType;
  hypothesisType: HypothesisType;
  sampleSize: number;
  validatedCount: number;
  validatedRate?: number;              // undefined (not 0, not fabricated) when sampleSize < MIN_SAMPLE
}
```

Build note: this requires a genuinely new Prisma model + migration (there is no `AnalysisRun` table today — `services/ai/analysis-run.service.ts` is explicitly an in-memory reference implementation only, per its own header). This is the single largest net-new implementation item in the whole spec, and the one with real backend/scheduling implications (something has to run later and evaluate outcomes — a cron job or on-next-analysis check). Flagging this clearly for D2.5.1 scoping and sequencing.

### 2.7 IntelligenceScore Contract — the final synthesis, before AI Analyst

Purpose: this is `MarketIntelligenceResult` (the existing envelope), extended — not replaced. Today's envelope already aggregates `evidence + reasoning + risk + confidence`. V2 adds `regime`, `hypotheses` (with per-hypothesis evidence and conflict resolution), and `historicalValidation`.

```ts
interface IntelligenceScore {
  symbol: MarketSymbol;
  marketState: MarketState;
  regime: Regime;

  // EXISTING, unchanged — the whole 15D pipeline output nests in here as-is:
  evidence: EvidenceBundle;
  reasoning: ReasoningResult;
  risk: RiskProfile;                   // unchanged 8-category shape
  confidence: ConfidenceProfile;       // possibly + 1-2 new categories: "regime-stability",
                                        // "historical-validation" — architect call

  // NEW:
  hypotheses: {
    hypothesis: Hypothesis;
    supportingEvidence: EvidenceItem[];
    opposingEvidence: EvidenceItem[];
    conflicts: HypothesisConflict[];
    historicalValidation?: HistoricalValidation;  // undefined until enough AnalysisOutcome rows exist
  }[];

  overallIntelligenceScore: number;    // 0..100, deterministic composite formula — documented,
                                        // reviewable, NOT a trained model output in V2

  metadata: {
    pipelineVersion: string;           // e.g. "V2.0.0", distinct from "15D.12.0" nested inside
    executionTimeMs: number;
    generatedAt: string;
  };
}
```

**AI Analyst boundary (unchanged in kind):** exactly the same restate-only pattern as `market-analysis-orchestration.service.ts#buildPrompt()` today, extended to cover the new `regime`/`hypotheses`/`historicalValidation` sections with the same category of explicit instruction already proven in production:

> *"You are given a fully-computed, deterministic market intelligence analysis below. Your only task is to express it in clear, natural language... Do not add facts... Do not change the stated risk level, confidence level, or any evidence claim."*

This is the platform's one non-negotiable architectural rule, and this spec does not touch it — it only gives the translator more (still fully deterministic) material to translate.

## 3. Proposed pipeline, mapped to reuse vs. net-new

```
MARKET DATA  ────────────────────────  REUSE (lib/market-data/*, unchanged)
     │
     ▼
MARKET STATE ENGINE  ────────────────  PARTIAL REUSE (snapshot + technical = existing;
     │                                  structure + quant + context = NET NEW)
     ▼
REGIME ENGINE  ───────────────────────  NET NEW (nothing like this exists today)
     │
 ┌───┼─────────────┬─────────────┐
 ▼   ▼              ▼             ▼
STRUCTURE          QUANT       CONTEXT   ──  all NET NEW compute, but slot into
(part of MarketState.structure)          existing EvidenceItem shape once computed
     │
     ▼
HYPOTHESIS ENGINE  ───────────────────  NET NEW
     ▼
EVIDENCE ENGINE  ─────────────────────  REUSE (evidence-collector/fusion/ranking),
     │                                  extended with new EvidenceType values only
     ▼
CONFLICT ENGINE  ─────────────────────  REUSE at evidence level (unchanged),
     │                                  NET NEW at hypothesis level
     ▼
MEMORY ENGINE  ────────────────────────  NET NEW (confirmed zero prior art — biggest gap)
     ▼
VALIDATION  ───────────────────────────  REUSE (ReasoningEngineService's uncertainty/
     │                                  driver logic is already exactly this step)
     ▼
INTELLIGENCE SCORE  ───────────────────  EXTENSION of existing MarketIntelligenceResult
     ▼
AI ANALYST  ────────────────────────────  REUSE, unchanged boundary (Gemini restate-only,
                                          AI_COMMUNICATION_POLICY, same prompt discipline)
```

Roughly: **4 of 10 pipeline stages are pure reuse, 2 are partial/extension, 4 are genuinely net-new** (MarketState's structure/quant/context sub-layers, Regime, Hypothesis, Memory). This is a meaningfully large build, concentrated almost entirely in Regime/Hypothesis/Memory — not a rewrite of what already works.

### Compatibility / rollout posture

- The existing `MarketAnalysisResult` / `/market-intelligence/analyze` route continues to work unmodified through the V2 build. `IntelligenceScore` nests the existing `MarketIntelligenceResult` shape inside it rather than replacing its fields, so nothing downstream (Trading Copilot, Intelligence Panel, any current consumer) needs to change on day one.
- Recommend V2 services live under a new `services/intelligence/` namespace (parallel to `services/ai/`, which stays as the 15D/legacy home) so reuse vs. net-new is visible in the file tree itself, not just in this doc.
- A new pipeline version tag (e.g. `"V2.0.0"`) should be introduced distinct from `MARKET_INTELLIGENCE_PIPELINE_VERSION = "15D.12.0"` — the 15D tag should **not** be bumped, since 15D's own scope and guarantees are unchanged; it's now a component inside a larger pipeline, not superseded.

## 4. What should NOT be built (commodity functionality)

Per the explicit instruction, and consistent with the platform's own stated positioning (`sections/FAQ.tsx`: *"We don't sell buy-or-sell signals"*):

- **Single-indicator crossover "signals"** (e.g. "RSI < 30 → buy") — free in every retail EA and TradingView public script. Zero differentiation, and directly contradicts the platform's own no-signal-selling positioning.
- **Shallow news-headline sentiment scoring** with no evidence attribution — many chatbot wrappers already fake this convincingly. If Context/news evidence is added, it must carry the same `source`/`asOf`/traceability fields as everything else, or it shouldn't ship at all.
- **Chart-pattern "AI recognizes head-and-shoulders"** style detection — low real signal value, historically overclaimed across the retail-trading-tool industry, and hard to make honestly falsifiable. Not a good fit for an evidence-based platform.
- **A generic "ask me anything" chatbot with no grounding** — already explicitly rejected; the existing Assistant is retrieval-grounded by design (`app/api/private/knowledge/chat/route.ts`), and that constraint should extend to any V2 conversational surface.
- **Basic price alerts / notifications** — commodity, not intelligence.
- **Broker/order execution integration** — explicitly out of scope by the existing Risk Engine's own design (`risk-engine.service.ts`: *"This platform does not integrate broker/execution data by design"*). Liquidity/execution risk stay honestly "medium/unmeasured" in V2 too, unless this specific constraint is separately revisited.
- **A trained ML model as the source of Regime/Hypothesis classification in V2.** The diagram names "ML models" as a possible *future* engine implementing these same contracts — that's the right home for it. V2 itself should stay rule-based/deterministic, matching every existing engine's actual implementation style, so Regime and Hypothesis outputs remain as auditable and explainable as Risk/Confidence are today. Introducing a black-box model at this stage would be the one change that actually breaks the platform's core differentiator.

## 5. Open questions for architect sign-off before D2.5.1

1. **Hypothesis directionality boundary** (§2.3) — how directional can a falsifiable Hypothesis be, given `ExplainableAnalysisService` currently never asserts one? Needs an explicit ruling, likely an `AI_COMMUNICATION_POLICY` addendum.
2. **Context/news evidence honesty audit** — `news.service.ts`/`economic-calendar.service.ts`/`sentiment.service.ts` were flagged by the audit as currently mock-backed (not deep-verified in this pass). Before `MarketState.context` treats them as real evidence sources, they need the same real-vs-mock verification the 15D pipeline already went through.
3. **Memory Engine scheduling** — outcome evaluation (`AnalysisOutcome`) needs *something* to run after the prediction window closes (cron job vs. lazy evaluation on next analysis for the same symbol). This is a real infrastructure decision, not just a schema decision.
4. **Confidence category additions** (§2.7) — should `ConfidenceProfile` gain `"regime-stability"` / `"historical-validation"` categories, or should those stay reported separately inside `IntelligenceScore.hypotheses[].historicalValidation`? Affects whether `types/confidence-intelligence.ts` needs a breaking-ish change or IntelligenceScore is purely additive.
5. **`services/intelligence/` vs. extending `services/ai/`** — naming/namespace call for D2.5.1's actual file layout.
6. **Minimum sample size for `HistoricalValidation.validatedRate`** — needs an explicit number (this doc left it as `MIN_SAMPLE`, a placeholder) so the "undefined rather than fabricated" rule has a concrete threshold from day one.

## 6. Summary for the architect

- Reuse is real and substantial: `MarketSnapshot`, `lib/market-data/indicators.ts`, `EvidenceItem`/`EvidenceBundle`, `RiskProfile`, `ConfidenceProfile`, the AI restate-only boundary, and the provider/health/failover infrastructure all carry into V2 unchanged.
- The genuine net-new work is concentrated in exactly three places the audit confirms don't exist today: **Regime classification, Hypothesis generation, and the Memory/Outcome loop** — plus the Structure/Quant/Context sub-layers of MarketState that feed them.
- The platform's actual moat — never fabricate, always show basis, default to "unresolved"/"insufficient-data" rather than force an answer — is a convention already proven across five existing engines. Every contract in this spec was written to extend that convention, not introduce a new one.
- No production code changes were made to produce this document.
